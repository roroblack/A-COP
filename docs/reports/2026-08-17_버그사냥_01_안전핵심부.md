# S-BUGHUNT-01-CORE-SAFETY — 안전 핵심부 버그 사냥

범위: `app/core/transition.py`, `app/core/verification.py`, `app/application/proposal_guard.py`, `app/infrastructure/messaging/worker.py`, `app/infrastructure/messaging/outbox.py`, `app/presentation/api/cases.py`.

코드 수정은 하지 않았다. 아래 재현 명령은 이 보고서 작성 중 실행한 결과를 기준으로 한다.

### app/infrastructure/messaging/worker.py:30-37 — 처리 중 워커가 죽으면 outbox 메시지가 영구 정지한다
- 시나리오: 워커가 `pending` 행을 `FOR UPDATE SKIP LOCKED`로 잡고 `processing`으로 커밋한 직후, `publisher()` 호출 전 또는 호출 중 프로세스가 종료된다. 재시작한 워커는 `status='pending'`만 조회하므로 이 행을 다시 잡지 않는다. `locked_at`은 기록되지만 만료 복구 조건이 없다. 해당 메시지는 `processing`에 영구 잔류하여 at-least-once 배달이 깨진다.
- 왜 기존 테스트가 못 잡는가: 기존 테스트는 정상 배달·publisher 예외·tenant scope만 검증하고, claim 이후 프로세스 종료/재시작과 stale `processing` 행 복구를 검증하지 않는다.
- 재현 시도: 재현 안 해봄, 코드 읽기로만 판단. 확인 명령: `rg -n "status='pending'|status='processing'|locked_at" app/infrastructure/messaging/worker.py`
- 위험도: 높음(승인·후속 실행 이벤트가 배달되지 않아 업무가 멈추거나, 운영자가 수동 재처리해야 함)

### app/infrastructure/messaging/outbox.py:20-26 — case_id 조회에 tenant 조건이 없어 다른 tenant의 case와 outbox tenant를 섞는다
- 시나리오: tenant A가 `payload={"tenant_id": "A", "case_id": <tenant B의 case>}`로 publish를 호출한다. 20행의 조회는 `case_id`만으로 B의 tenant를 찾고, 22행의 `payload.get("tenant_id")`가 우선되어 A tenant의 outbox 행에 B case_id가 들어간다. 반대로 tenant_id를 생략하면 호출자가 지정한 tenant 검증 없이 case_id 소유 tenant를 사용한다. 즉 payload의 tenant와 case 소유 tenant가 불일치해도 거부하지 않는다.
- 왜 기존 테스트가 못 잡는가: 기존 tenant 테스트는 정상적으로 같은 tenant의 `tenant_id`와 `case_id`를 함께 넣고, foreign pending 메시지를 worker가 건너뛰는지만 확인한다. 서로 다른 tenant의 case_id와 payload tenant를 의도적으로 섞는 입력은 없다.
- 재현 시도: 재현 안 해봄, 코드 읽기로만 판단. 확인 명령: `rg -n -C 2 "SELECT tenant_id FROM customer_cases|payload.get\(\"tenant_id\"\)" app/infrastructure/messaging/outbox.py`
- 위험도: 높음(tenant 격리 위반 및 다른 tenant case를 가리키는 메시지 생성)

### app/core/transition.py:81-86 — outbox dedupe 키가 전역이라 tenant 간 동일 키가 서로의 배달을 억제한다
- 시나리오: tenant A와 tenant B가 같은 `topic`과 `dedupe_key`를 사용해 각각 상태 전이를 수행한다. outbox의 유일성 계약은 `UNIQUE(topic, dedupe_key)`이고, 이 INSERT도 `ON CONFLICT (topic, dedupe_key) DO NOTHING`을 사용한다. A의 행이 먼저 있으면 B의 상태 전이는 성공해도 B의 outbox INSERT는 무시되고 `TransitionResult.published`는 빈 목록이 된다. B의 후속 consumer 배달이 누락된다.
- 왜 기존 테스트가 못 잡는가: 기존 outbox tenant 테스트는 tenant별로 서로 다른 dedupe key를 사용하고, worker의 조회 tenant scope를 검증한다. 동일 topic·동일 dedupe key를 두 tenant가 동시에/순차적으로 사용하는 경계는 테스트하지 않는다.
- 재현 시도: 재현 안 해봄, 코드 읽기로만 판단. 확인 명령: `rg -n -C 3 "UNIQUE\(topic, dedupe_key\)|ON CONFLICT \(topic, dedupe_key\)" app/core/transition.py app/infrastructure/db/migrations/001_schema.sql`
- 위험도: 높음(한 tenant의 승인·상태 후속 이벤트가 조용히 배달되지 않음)

### app/core/verification.py:185-203 — NaN/Infinity 금액이 불일치로 차단되지 않고 예외를 낸다
- 시나리오: 제안의 `amount`가 문자열 `"NaN"` 또는 `"Infinity"`이고 해당 payment가 존재한다. `_to_decimal()`은 이를 Decimal로 변환해 성공으로 취급한다. 이후 `scaled > limit` 비교에서 NaN은 `decimal.InvalidOperation`을 내고, Infinity는 `int(scaled)`에서 `OverflowError`를 낸다. 따라서 `list[Mismatch]`로 거부해야 할 입력이 예외로 빠져 승인 API의 500 경로가 된다.
- 왜 기존 테스트가 못 잡는가: 기존 단위 테스트는 0·음수·정상 숫자·한도 초과만 테스트하며 Decimal 특수값을 넣지 않는다.
- 재현 시도: 재현함. 명령: `@' ... verify_proposal(arguments={'payment_id': payment, 'amount': value}, ...) ... '@ | python -` (값 `NaN`, `Infinity`, `-Infinity` 각각 실행). 결과: `NaN EXCEPTION InvalidOperation`, `Infinity EXCEPTION OverflowError cannot convert Infinity to integer`, `-Infinity EXCEPTION OverflowError cannot convert Infinity to integer`.
- 위험도: 보통(승인 요청이 500으로 실패하고 명시적 검증 거부·감사 불일치 기록이 남지 않음)

### app/application/proposal_guard.py:72-86, app/presentation/api/cases.py:153-187 — 승인 직전 재검증과 실제 승인이 하나의 원자적 경계가 아니다
- 시나리오: 승인 요청이 들어오면 `recheck_before_execution()`은 72-78행의 조회 트랜잭션과 84행의 facts 조회를 마친다. 그 뒤 cases.py가 별도의 175행 트랜잭션에서 action approval과 `APPROVED` 전이를 수행한다. 재검증 직후 다른 트랜잭션이 payment 금액/상태를 바꾸거나 entitlement를 회수하면, 재검증 당시에는 통과한 제안이 바뀐 사실 기준으로도 승인된다. 최종 transition의 version 검사는 case version만 보호하며 payment/subscription/entitlement 행의 변경과는 연결되지 않는다.
- 왜 기존 테스트가 못 잡는가: 기존 재검증 테스트는 승인 전에 payment를 변경하는 단일 순차 경로만 검증한다. 재검증 완료와 approval transaction 사이에 다른 트랜잭션이 커밋되는 동시성 경계를 주입하지 않는다.
- 재현 시도: 재현 안 해봄, 코드 읽기로만 판단. 확인 명령: `rg -n -C 3 "with conn.transaction|recheck_before_execution|create_approval|event_type=EventType.APPROVED" app/application/proposal_guard.py app/presentation/api/cases.py`
- 위험도: 높음(검증을 통과한 금액·식별자와 실제 승인 시점의 원장이 달라질 수 있음)

## 검증

보고서만 추가했으며 애플리케이션 코드는 수정하지 않았다. 완료 기준 명령:

```powershell
python -m pytest -q
```

실측 결과: `3 failed, 331 passed, 1 deselected` (23.42초). 실패 3건은 모두 `tests/integration/rag/test_rag_integration.py`에서 OpenAI embeddings API 연결이 `[WinError 10013]`으로 거부된 건이며, 이번 스캔 대상 파일의 변경으로 발생한 실패는 아니다. 따라서 사용자 요청의 `334 passed` 기준은 이 실행 환경에서 외부 네트워크 제한 때문에 충족하지 못했다.
