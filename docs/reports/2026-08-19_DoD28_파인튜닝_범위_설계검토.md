# DoD-28 파인튜닝 범위 설계 검토

- 검토일: 2026-08-19 (Asia/Seoul)
- 범위: 설계 검토만. 코드 수정, 학습 실행, 학습 데이터 export, 파인튜닝 API 호출은 하지 않았다.
- 판정: **지금은 파인튜닝 착수하지 않음.** 데이터·평가 기준선·judge agreement가 먼저 보강되어야 한다.

## 요약 결론

현재 Proposed에서 확인되는 문제는 “모델이 정책을 몰라서”라기보다 다음 행동 매핑과 평가 기준선의 문제다. 보존된 결과에서는 정책 근거는 강하지만 `next_action`이 `respond`로 고정되어 기대 행동을 놓치는 사례가 반복된다(`eval/reports/raw_proposed.jsonl`, 예: `g-billing-01`, `g-billing-02`). 반면 RAG/context를 제거하면 근거가 사라지고 `degraded_context`로 기권한다(`eval/reports/abl_no_context_broker.jsonl`, `g-billing-01`~). 따라서 우선순위는 파인튜닝보다 행동 라벨·프롬프트·RAG·평가 하네스 정합성 확정이다.

현재 후보 중 착수할 수 있는 것은 장래의 **분류기 파일럿**뿐이다. 단, 현재 golden 60건은 8개 issue code와 intent/sentiment/severity를 모두 안정적으로 대표한다고 입증되지 않았고, holdout 20건은 평가용으로 보존해야 하므로 학습에 쓰지 않는다. 톤 REV와 GEN은 지금 착수하지 않는다.

## 1. 현재 파이프라인의 실측 실패와 원인 분류

### 1.1 먼저 확인해야 할 평가 상태

평가 리포트의 서로 다른 산출물이 같은 기준선으로 정리되어 있지 않다.

| 산출물 | 관측값 | 해석상의 문제 |
|---|---:|---|
| `eval/reports/2026-08-12_평가결과_리포트.md:9-13,27-37` | mock, golden 60 × 3 × 3 = 540 observations; Proposed task success 180/180, grounding 1.00 | 실제 외부 LLM 호출 0회이며 holdout 20건은 미실행(`:9-14`, `:55-57`) |
| `eval/reports/raw_proposed.jsonl` 실측 | 180행, success 0/180; score 분포는 7~15 | 원시 Proposed 결과는 요약 리포트의 1.00과 불일치 |
| `eval/reports/rescored_proposed.jsonl` 실측 | 180행, success 40/180 | rescoring 기준은 달라졌지만, 무엇이 최신 기준선인지 문서화되어 있지 않음 |
| `CLAUDE.md:134-136` | 요약 상태표에 Proposed 40/180, grounding 3.98, judge 검증 미완 | 요약 수치 자체도 mock/실호출·rescore 버전 구분이 필요 |

OpenAI도 eval을 먼저 만들고 base와 fine-tuned model을 representative test data로 비교하라고 명시한다([Model optimization](https://developers.openai.com/api/docs/guides/model-optimization), [Supervised fine-tuning](https://developers.openai.com/api/docs/guides/supervised-fine-tuning)).

### 1.3 “프롬프트로 해결”과 “FT 후보”의 경계

현재 증거로 FT의 필요성이 남는 문제는 다음 세 가지뿐이다.

1. **일관된 형식/톤**: 입력·정책 context가 동일하게 주어졌는데도 답변 구조나 브랜드 톤을 안정적으로 맞춰야 하고, prompt 개선으로도 반복 실패가 확인될 때.
2. **반복되는 분류 출력**: intent/sentiment/issue_code/severity처럼 단일 정답에 가까운 구조화 출력에서, 충분한 실제 라벨이 쌓인 뒤 latency·호출비용을 낮추고 싶은 경우.
3. **짧은 지시로 동작**: 긴 system prompt를 매번 넣지 않아도 고정된 출력 규약을 지켜야 한다는 운영 목표가 측정된 경우.

현재는 1~3의 개선 필요량이 분리 측정되지 않았다. 특히 GEN의 5종 방어 지표는 실제 LLM output이 아니라 fixture에 대해 측정되었다(`DoD-28...md:101-118`). 그러므로 “파인튜닝이 아니면 안 된다”는 결론은 현재 근거로 낼 수 없다.

## 2. 후보 3종 비교

비용의 숫자를 임의로 산정하지 않았다. 공식 문서는 SFT가 classification·특정 format·instruction-following에 적합하다고 설명하지만, 현재 OpenAI 문서는 파인튜닝 플랫폼이 신규 사용자에게 종료 수순이라고 명시한다([Supervised fine-tuning](https://developers.openai.com/api/docs/guides/supervised-fine-tuning)). 따라서 아래 API 비용은 **모델·계정 접근권·토큰량 확정 후 공식 pricing에서 확인할 항목**이며, 데이터 준비 인력은 이 저장소에서 측정된 값이 없어 `미측정`으로 둔다. 기존 평가 리포트의 `$0.648`은 mock 실행의 사전 추정치일 뿐 FT 비용이 아니다(`eval/reports/2026-08-12_평가결과_리포트.md:17-21`).

| 후보 | 학습 데이터 소스와 최소 범위 | 평가 방법 | API/운영 비용 및 위험 | 설계 판정 |
|---|---|---|---|---|
| 분류기 (intent/sentiment/issue_code/severity) | 실제 masked feedback와 사람이 확정한 4개 라벨. 현재 `feedback.py:31-39`의 label 공간은 intent 3, sentiment 3, severity 4, issue code 8. golden 60은 학습·검증·test를 동시에 충족하지 못함. holdout 20은 보존 | 기존 분류 정확도·macro-F1·invalid output·`classification_failed` 비율 재사용. 학습에 쓰지 않은 신규 test와 holdout을 별도 비교; latency/cost는 실제 API 호출에서 측정 | 세 후보 중 가장 작은 출력으로 추정되나 현재 API 접근·학습 토큰·데이터 준비 인력은 미측정. 분류 오류는 `classification_failed`→`escalated` 경로로 운영 영향이 큼(`feedback.py:83-103`, `CLAUDE.md:67-68`) | **조건부 MVP 후보**. 새 라벨이 충분히 쌓이고 split이 고정될 때만 |

### GEN을 파인튜닝하면 반드시 다시 재야 하는 것

DoD-28의 5종은 현재 fixture에서만 산출되었고, 실제 LLM proposal 측정은 미완료다(`docs/evidence/DoD-28_파인튜닝_방어지표.md:101-118`). 따라서 GEN을 바꾸면 다음을 같은 분모 규칙으로 base/FT 양쪽에 다시 기록해야 한다.

- grounding match, grounding excess
- proper abstention, over-abstention
- schema compliance
- 추가 회귀: PII leak, harmful-instruction refusal, billing overclaim, policy violation

`eval/defense_metrics.py:77-153`은 이 5종을 계산하며 분모 0을 `null`로 보존하고, parse 실패를 abstention으로 세지 않는다(`:113-115`). 이 정의를 바꾸지 않고 model/version/prompt snapshot을 함께 고정해야 한다.

## 3. 데이터 부족과 착수 가능성

### 3.1 프로젝트 내 실측 제약

- `docs/plans/2026-08-12_1507_A-COP_실행계획서_v1.md:199-208`은 golden 60, holdout 20, holdout으로 prompt를 고치지 않음, 2인 라벨+adjudication을 평가 계약으로 둔다.
- `eval/reports/2026-08-12_평가결과_리포트.md:11-14,55-57`은 golden 60만 실행했고 holdout 20은 미실행이며, 결과가 mock이라 실제 품질·지연·과금을 측정하지 않았다고 명시한다.
- DoD-28 증거는 방어 fixture 15건만 실제로 계산했고, Proposed vs Proposed+FT 및 golden/holdout 5종 비교는 미착수다(`docs/evidence/DoD-28_파인튜닝_방어지표.md:58-72,101-114`).
- `CLAUDE.md:101-104`는 표본이 작으면 방향성 불확실성을 말하고 paired bootstrap/McNemar를 함께 쓰도록 요구한다.

### 3.2 OpenAI 공식 기준과 이 프로젝트의 의미

OpenAI 공식 SFT 문서의 현재 명시는 “최소 10개”, “50~100개에서 개선을 관찰”, “50개의 잘 만든 demonstration부터 시작”, “대표적인 실제 입력”, “train/test 분리”다([Supervised fine-tuning](https://developers.openai.com/api/docs/guides/supervised-fine-tuning)). 이는 “분류기는 일반적으로 수백~수천 건이 공식 최소”라는 문장을 뒷받침하지 않는다. 이 검토에서는 그 숫자를 사실로 쓰지 않는다.

다만 60건이 10건과 50건을 넘는다는 사실만으로 충분하지 않다. 이 프로젝트는 4개 분류 라벨과 8개 issue code를 다루며, 각 조합·경계 사례·언어 변형·오류 사례의 분포와 라벨 합의가 보고되어 있지 않다. 60건을 train/test/검증으로 나누면 각 strata의 분모가 더 작아지고, holdout 20을 제외하면 실제 학습 후보는 더 줄어든다. 따라서 **공식 형식 최소는 넘을 수 있으나, 이 프로젝트의 일반화 근거로는 부족**하다.

OpenAI도 데이터 품질·균형·다양성·라벨 agreement를 확인하고, 학습 set과 test set을 분리하라고 한다([Fine-tuning best practices](https://developers.openai.com/api/docs/guides/fine-tuning-best-practices)). 현재는 judge agreement 자체가 미측정 상태다(`docs/release_checklist.md:83-102`).

### 3.3 결론

**전체 파인튜닝은 불가능/부적절, 분류기만 조건부 가능**이다.

- 지금 가능한 일: 학습 데이터 schema, label policy, split 계획, leakage 검사, 평가 명세를 설계하는 것.
- 지금 불가능한 일: golden 60으로 성능 개선을 확정하거나 GEN을 학습해 방어 지표가 좋아졌다고 주장하는 것.
- 착수 전 반드시 필요한 추가 데이터: 신규 masked feedback의 사람 확정 라벨, 각 label/edge case의 분포, 2인 독립 라벨과 adjudication, frozen test set.

## 4. 반대 의견과 위험

### “50건이면 공식 권고를 충족하므로 지금 분류기를 해볼 수 있다”

반대 의견은 타당한 일부가 있다. OpenAI는 50개의 잘 만든 demonstration으로 시작해 평가하라고 한다. 그러나 이 저장소의 60건이 잘 만든 독립 demonstration인지, label 균형과 합의가 있는지는 측정되지 않았다. 60건을 golden 그대로 쓰는 순간 기존 benchmark와 학습셋이 겹칠 수 있고, holdout 20을 쓰면 holdout 계약을 깨뜨린다. 그러므로 “50 이상”은 착수 승인 조건이 아니라 데이터 품질 점검을 시작할 수 있는 하한이다.

### 오염(leakage)

golden/holdout의 prompt, 정답 next_action, 답변을 training examples로 재사용하면 FT 전후 비교가 의미 없어진다. 특히 현재 Proposed 실패가 `respond` 대 `investigate_and_propose_refund` 같은 action mapping 문제이므로, 그 정답을 학습하고 같은 행을 평가하면 성능이 부풀려진다. split은 case ID뿐 아니라 template·정책 문서·paraphrase family 기준으로도 분리해야 한다.

### 모델 버전·재현성

`CLAUDE.md:68-73`은 prompt `(prompt_key, version)` unique + SHA-256 immutable, `llm_calls.prompt_id` 추적, eval run_id/seed/model/prompt snapshot을 요구한다. FT도 최소한 다음 불변 manifest가 필요하다.

`base_model_snapshot`, `fine_tuned_model_id`, `training_file_sha256`, `validation_file_sha256`, `label_schema_version`, `prompt_snapshot`, `dataset_split_manifest`, `hyperparameters`, `created_at`, `eval_run_id`.

모델 ID만 저장하면 prompt version처럼 재현되지 않는다. OpenAI 공식 문서가 현재 fine-tuning platform의 신규 사용자 접근 종료 수순을 안내하므로, 장기 운영 모델을 이 API에 종속할 availability risk도 별도로 승인해야 한다([Fine-tuning best practices](https://developers.openai.com/api/docs/guides/fine-tuning-best-practices)).

### 아직 RC가 아닌 상태에서의 우선순위

`docs/release_checklist.md:12-18`은 M3 미도달·RC 아님을 명시하고, `:83-102`는 judge agreement 미측정을 blocker로 둔다. 실제로 요약 리포트는 mock이며 holdout도 실행하지 않았다. 이 상태에서 FT에 자원을 쓰면 모델 최적화보다 먼저 해결해야 할 평가 신뢰성 문제가 남는다. OpenAI의 공식 순서도 eval baseline → prompt → 필요 시 fine-tune → representative test 비교다([Model optimization](https://developers.openai.com/api/docs/guides/model-optimization)).

## 5. 권고 및 도입 트리거

### 권고

**2026-08-19 기준 도입: 보류.** 지금 산출할 MVP는 “분류기 파인튜닝 실행”이 아니라 “분류기 파일럿을 실행할 수 있는 데이터·평가 계약”이다. 톤 REV와 GEN은 이 계약 이후에도 별도 트리거 없이는 시작하지 않는다.

### 분류기 MVP 트리거

다음 조건을 모두 충족할 때만 분류기 후보를 shadow mode로 검토한다.

1. holdout 20건은 계속 frozen으로 보존하고, 별도 신규 test를 만든다.
2. 신규 masked feedback을 사람이 2인 독립 라벨링하고 adjudication을 남긴다.
3. label별 건수·분포·경계 사례·라벨 agreement를 보고한다. 현재처럼 `null`/미측정이면 통과로 세지 않는다.
4. golden·holdout·training 간 exact/near-duplicate와 template family leakage가 0임을 검사한다.
5. base와 classifier-FT를 같은 prompt/schema에서 비교한다. 기존 `classify()` 출력 검증과 `classification_failed`/escalation 경로를 유지한다.
6. 정확도만 보지 않고 macro-F1, label별 recall, invalid schema, p95 latency, cost/case를 함께 보고한다. 개선이 있어도 safety/PII 관련 회귀가 있으면 채택하지 않는다.
7. 최소 1회 shadow run 후 사람이 결과를 검토하고, 모델 manifest를 prompt version과 동급으로 immutable하게 저장한다.

### 톤 REV 트리거

- deterministic `decide_tone` 대 LLM REV 대 사람 2인 agreement를 별도 test에서 측정할 것.
- 불일치율·false warning·false pass의 분모가 있고, 규칙보다 FT가 개선해야 할 운영 손실이 수치로 확인될 것.
- PII·과금·정책 위반 판정은 학습 모델로 대체하지 않고 현재 결정론 방어를 유지할 것.

### GEN 트리거

- RC 도달: holdout 실행, judge agreement, 실제 LLM baseline, 비용·지연 측정이 완료될 것(`docs/release_checklist.md:83-110`).
- 독립적인 대표 train/test와 사람 승인 응답 corpus가 확보될 것.
- base 대비 개선 목표를 사전에 정할 것: next_action/correctness 개선뿐 아니라 DoD-28 5종과 PII·유해 지시 거부·과금 오류·정책 준수 회귀를 모두 만족해야 한다.
- `Proposed+FT`를 기존 동일 golden/holdout 하네스에서 비교하고, 변경된 GEN이면 5종 지표를 두 세트 모두 재측정할 것.

이 트리거가 충족되기 전에는 “파인튜닝 미착수”가 실패가 아니라, 오염 없는 비교와 안전한 도입을 보장하는 정당한 판정이다.
