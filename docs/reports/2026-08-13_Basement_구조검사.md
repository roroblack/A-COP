# Basement 구조 검사

## 판정 요약

| 축 | 판정 | 근거 |

## 2-1. Team 교체 가능성

### 관측

- 계약상 새 모듈은 `manifest: TeamManifest`와 `async execute(task) -> TeamResult`를 제공하면 된다 (`app/core/contracts.py:298-325`). Registry는 모듈 import 없이 리스트로 주입받고, contract version·active·중복 ID만 검사한다 (`app/core/registry.py:29-48`).
- 실제 Team 구현은 manifest 안에 Team ID, capability, case type, tool allowlist, knowledge scope를 함께 선언한다 (`app/modules/customer_ops/billing.py:15-16`, `app/modules/customer_ops/technical.py:9-10`). 따라서 새 Team의 최소 구현 파일 수는 1개다.
- 그러나 실행 경로에는 Registry를 만드는 운영 composition root가 보이지 않는다. Controller는 Registry를 외부에서 받지만, 없으면 `LocalTeamExecutor(registry)`만 만든다 (`app/application/controller.py:27-37`). API 앱은 Team Registry가 아니라 feedback 모듈을 직접 import한다 (`app/presentation/api/app.py:5-12`).
- Prompt는 별도 파일로 분리되어 있고 prompt 등록은 `prompts` 하위 파일을 순회한다 (`app/tools/read_tools.py:119-134`). Tool은 `allowed_tools`와 이름 매핑을 검사한다 (`app/tools/read_tools.py:99-116`).

### 판정: 새 Team 추가 시 고칠 파일 수

- **현재 코드 기준 최소 1개 파일**: Team 구현과 manifest를 한 파일에 넣을 수 있다 (`app/modules/customer_ops/billing.py:15-53`). Registry의 `register()`는 TeamModule만 받는다 (`app/core/registry.py:38-48`).
- **운영에서 실제로 선택되게 하려면 최소 2개 파일**: 새 Team 모듈 1개 + 외부 composition root/부트스트랩 1개가 필요하다. 현재 저장소에는 후자가 없어, “파일 1개 추가만으로 운영 등록”은 성립하지 않는다 (`app/application/controller.py:27-37`, `app/presentation/api/app.py:5-12`).
- **도메인 전용 Team을 정상 동작시키려면 보통 3개 이상**: 구현/manifest, prompt 파일, 정책·knowledge scope 데이터가 각각 필요할 수 있다. Prompt 등록 경로와 manifest scope가 분리되어 있다는 근거는 `app/tools/read_tools.py:119-134`, `app/modules/customer_ops/billing.py:15-16`이다.

### Core의 Team 이름 결합 여부

- `git grep -n "Billing\\|Technical" app/core/` 결과는 **0건**이다. Core의 Registry는 `team_id` 문자열을 저장/조회하지만 특정 클래스 이름을 import하지 않는다 (`app/core/registry.py:29-60`).
- 다만 Core가 아니라 Application Controller에 도메인 결합이 있다. `technical/entitlement/access`이면 `entitlement.diagnose`, 아니면 `billing.investigate`로 고정한다 (`app/application/controller.py:39-42`).

### Team 제거 시 Core가 깨지는가

- **Registry 자체는 깨지지 않도록 설계**되어 있다. 팀이 없으면 `get()`/`resolve()`가 `RegistryError`를 낸다 (`app/core/registry.py:50-60`).
- **Case 실행은 깨진다.** Controller는 routing에서 capability를 반드시 resolve하고, 실패 시 `ROUTING_FAILED`로 전환한다 (`app/application/controller.py:90-100`). 따라서 Team 제거는 Core import 오류가 아니라 해당 Case의 정상 실행 불가로 나타난다.

## 2-2. 도메인 교체 가능성

- `customer_ops`를 HR/물류로 바꾸려면 Controller의 capability 분기부터 바꿔야 한다 (`app/application/controller.py:39-42`). 기존 Team manifest도 `billing`, `technical`, `subscription`, `entitlement`, `incident`에 묶여 있다 (`app/modules/customer_ops/billing.py:15-16`, `app/modules/customer_ops/technical.py:9-10`).
- Case 상태 12종은 `new`, `classifying`, `routing`, `running`, 세 종류의 waiting, `resuming`, `resolved`, `escalated`, `failed`, `cancelled`로 구성된다 (`app/core/contracts.py:53-65`). 이 어휘는 고객 자체보다는 일반적인 접수·분류·라우팅·실행·대기·재개·종료 lifecycle에 가깝다.
- 그러나 이벤트 payload와 현재 데이터 모델에는 고객운영 어휘가 남아 있다. `EventType.CREATED`는 `channel/message`, `CLASSIFIED`는 `intent/issue_code/sentiment`, `ROUTED`는 `owner_team_id/capability`를 요구한다 (`app/domain/events.py:90-110`). 저장 테이블도 `customer_cases`와 `customers`를 전제로 한다 (`app/infrastructure/db/migrations/001_schema.sql:13-14`). 그러므로 상태명만으로는 도메인 교체가 가능해도 전체 Case contract는 일반화되지 않았다.
- Guardrail의 실행 수치 자체는 대체로 도메인 중립적이지만, 보안 scope와 평가 크기는 도메인 종속이다. 예를 들어 `subscription:read`, `technical:read`, billing/technical 평가 분할이 설정되어 있다 (`config/guardrails.yaml:37-49`, `config/guardrails.yaml:90-110`). Vector 차원·embedding model도 특정 provider/스키마와 결합되어 있다 (`config/guardrails.yaml:64-77`).

## 2-3. 저장소·LLM·전송 교체 가능성

- Port/Adapter 의도는 있다. `MessageBrokerPort`는 `publish/ack`만 정의한다 (`app/core/contracts.py:333-341`). `TeamExecutorPort`는 `execute`만 정의한다 (`app/core/remote_team/executor.py:8-9`). `GraphStorePort`는 `neighbors/path/subgraph`를 정의한다 (`app/core/graph_retrieval/port.py:4-7`).
- 하지만 Core의 저장소 경계는 지켜지지 않는다. `app/core/transition.py`가 `psycopg.Connection`, `psycopg.types.json.Json`을 직접 import한다 (`app/core/transition.py:26-27`) 및 SQL로 `customer_cases`를 직접 UPDATE한다 (`app/core/transition.py:54-69`).
- 더 직접적인 경계 위반으로 Core가 `app.presentation.security.mask_json`을 import한다 (`app/core/transition.py:29-32`). Core→modules import는 **0건**, Core→infrastructure import는 **0건**, Core→presentation import는 **1건**이다.
- Message broker 구현은 Infrastructure에 있지만 Core Controller가 주입받아 사용하지 않는다. 구현체는 `OutboxBrokerAdapter`로 존재하고 (`app/infrastructure/messaging/outbox.py:12-34`), Controller는 repository/connection을 직접 사용한다 (`app/application/controller.py:17-20`, `app/application/controller.py:72-80`).
- Graph adapter도 connection을 직접 주입받지만 `GraphStorePort`를 명시적으로 구현/상속하거나 Controller에 연결하지 않는다 (`app/infrastructure/graphstore/sql_adapter.py:6-17`, `app/application/controller.py:27-64`).
- LLM Provider 교체 지점은 최소 2곳 이상이다. Team LLM adapter는 OpenAI client와 `chat.completions.create`를 직접 호출한다 (`app/infrastructure/llm/openai.py:17-35`). RAG embedding도 별도로 OpenAI client를 직접 호출한다 (`app/infrastructure/rag/retriever.py:14-24`). Inline feedback classifier도 provider 호출을 자체 구현한다 (`app/modules/customer_ops/feedback.py:50-82`). 공통 `LLMPort`가 검색되지 않으므로 Provider 교체는 **최소 3개 구현 경로**를 확인·수정해야 한다.

## 2-4. 경계 검사

1. `app/core/**` → `app/modules/**`: **0건**. Registry도 `app.modules`를 import하지 않는다 (`app/core/registry.py:29-32`).
2. `app/core/**` → `app/presentation/**`: **1건** — `app/core/transition.py:32`.
3. `app/core/**` → `app/infrastructure/**`: **0건**. 다만 Core가 `psycopg`를 직접 import하므로 외부 구체 DB 라이브러리 결합은 **2개 import line**이다 (`app/core/transition.py:26-27`).
4. Team이 `transition_case()`를 직접 부르는 곳: 검색상 **0건**. Team 파일은 `TeamResult`를 반환할 뿐이다 (`app/modules/customer_ops/billing.py:27-50`, `app/modules/customer_ops/technical.py:15-34`).
5. `customer_cases` UPDATE 위치: **1곳** — `app/core/transition.py:61-69`. 단, CREATE는 repository가 직접 INSERT한다 (`app/infrastructure/db/repository.py:12-15`). 따라서 UPDATE 단일화는 관측되지만, 저장소 전체가 Case Port로 추상화된 것은 아니다.

## 2-5. A2A로 Team 원격 분리 가능성

- Controller는 실행 호출 자체를 `self.team_executor.execute(task)`로 한다 (`app/application/controller.py:121-135`). 생성자에는 `TeamExecutorPort` 주입 인자가 있다 (`app/application/controller.py:27-37`).
- Local 실행기는 Registry의 module을 호출하고 (`app/core/remote_team/executor.py:12-19`), A2A 실행기는 주입된 transport로 submit/poll한 뒤 같은 `TeamResult`를 만든다 (`app/core/remote_team/a2a_executor.py:10-26`, `app/core/remote_team/a2a_executor.py:46-73`).
- Local/A2A 교체 시 Controller 호출부는 그대로 둘 수 있다. 다만 기본값은 Local로 하드코딩되어 있으므로 A2A를 실제 운영에 쓰려면 Controller 생성부의 `team_executor` 주입을 별도로 고쳐야 한다 (`app/application/controller.py:31-37`). 현재 `app/**`에서 A2A executor를 Controller에 주입하는 운영 wiring은 확인되지 않았다.
- 계약은 양쪽에서 동일하다. Local은 Team의 반환을 그대로 전달하고 (`app/core/remote_team/executor.py:18-19`), A2A는 원격 artifact를 `TeamResult`로 검증한다 (`app/core/remote_team/a2a_executor.py:59-67`). 실패/입력대기 mapping도 동일한 `TeamResult` 계약을 사용한다 (`app/core/remote_team/a2a_executor.py:51-73`).

## 2-6. 확장 시 걸림돌

- **가장 먼저 부러질 곳**: Controller의 `_capability()`가 두 capability만 알고 있다 (`app/application/controller.py:39-42`). HR/물류 Team을 추가해도 이 분기를 바꾸지 않으면 기존 두 Team 중 하나로 잘못 라우팅된다.
- **Team 5~10개 확장 시**: capability 분기와 Team별 도메인 vocabulary가 Controller에 누적될 가능성이 가장 크다 (`app/application/controller.py:39-42`). Registry 자체는 capability 단일 매칭만 제공하므로 분류/정책/우선순위/충돌 해결 모델이 없다 (`app/core/registry.py:56-60`).
- **운영 등록 확장 시**: production composition root가 보이지 않아 Team 목록을 한 곳에서 선언·교체하는 경로가 없다 (`app/application/controller.py:27-37`, `app/presentation/api/app.py:16-23`). 현재 구조의 “갈아 끼움”은 테스트나 외부 호출자가 Registry를 조립할 때만 명확하다.
- **아직 하드코딩된 Port 부재 지점**: Case transition이 `psycopg`/SQL에 직접 결합되어 있다 (`app/core/transition.py:26-32`, `app/core/transition.py:54-69`). LLM은 공통 Port가 없고 OpenAI 호출이 Team adapter, RAG retriever, feedback classifier에 분산되어 있다 (`app/infrastructure/llm/openai.py:22-35`, `app/infrastructure/rag/retriever.py:6-24`, `app/modules/customer_ops/feedback.py:50-82`). Graph Port는 선언만 있고 호출 경로가 없다 (`app/core/graph_retrieval/port.py:4-7`, `app/application/controller.py:27-64`).

## ★가장 먼저 부러질 곳

1. **도메인 교체**: `app/application/controller.py:39-42`의 Billing/Technical capability 분기.
2. **운영 Team 추가**: Registry를 실제로 조립하는 production wiring 부재 (`app/application/controller.py:27-37`, `app/presentation/api/app.py:16-23`).
3. **저장소 교체**: Core transition의 직접 `psycopg`·SQL 의존 (`app/core/transition.py:26-32`, `app/core/transition.py:54-69`).
4. **Graph 활용 확대**: Port와 adapter는 있으나 Runtime에서 전달·호출되지 않음 (`app/core/graph_retrieval/port.py:4-7`, `app/infrastructure/graphstore/sql_adapter.py:6-17`, `app/application/controller.py:27-64`).

## 결론

이 저장소는 **Team 계약과 Local/A2A 실행 계약의 뼈대는 있으나, “무엇이든 올릴 수 있는 Basement” 주장은 부분적으로만 성립**한다. TeamModule/TeamResult/TeamExecutorPort 수준의 교체성은 확인되지만, 실제 운영 등록 경로, 도메인 라우팅, Case 저장소 경계, Graph 연결, 공통 LLM Port가 약점이다 (`app/core/contracts.py:218-325`, `app/core/remote_team/executor.py:8-19`, `app/application/controller.py:39-42`).

## 확인하지 못한 것

- 실제 배포 환경에서 외부 A2A transport가 어떤 프로토콜/endpoint를 사용하는지는 확인할 수 없다. 현재 코드에는 transport가 주입될 뿐 구체 전송 구현이 없다 (`app/core/remote_team/a2a_executor.py:13-21`).
- 실제 production bootstrap이 저장소 바깥에서 Registry와 executor를 조립하는지는 이 저장소 코드만으로 확인할 수 없다. 저장소 내부 Controller는 의존성을 인자로 받지만 기본 Local executor를 선택한다 (`app/application/controller.py:27-37`).
- GraphStore가 다른 서비스에서 별도 호출되는지 여부는 확인하지 못했다. 저장소 내부에서 확인되는 것은 Port 선언과 SQL adapter 구현뿐이다 (`app/core/graph_retrieval/port.py:4-7`, `app/infrastructure/graphstore/sql_adapter.py:6-17`).
