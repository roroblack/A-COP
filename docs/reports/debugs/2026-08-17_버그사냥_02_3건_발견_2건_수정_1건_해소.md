## 고친 것 2건

### 1. `app/core/remote_team/a2a_executor.py:17-26` — deadline 검사가 원격 호출 hang 을 못 뚫는다
- **재현 확인**: `submit()` 이 즉시 응답해도, deadline(2초) 보다 훨씬 오래
  `sleep`하는 `poll()` 을 만들면 executor 가 deadline 을 훨씬 넘기고서야
  (외부에서 강제로 끊지 않으면 무기한) 끝난다. 직접 async 테스트로 재현:
  hang 하는 poll + 2초 deadline 을 `asyncio.wait_for(..., timeout=3.5)` 로
  감싸 확인. 고치기 전에는 이 wait_for 자체가 타임아웃됐다.
- **왜 위험한가**: DoD-27("A2A 실패·타임아웃·취소·인증")이 claim 하는 타임아웃
  보장이 **원격이 정말 안 끊기고 계속 대기만 할 때는 성립하지 않았다.** 게다가
  deadline 을 넘겨 포기할 때도 원격에 취소를 보내지 않아 — `A2AHttpTransport.cancel()`
  이 이미 구현돼 있는데도 — 원격 작업이 계속 실행될 수 있었다.
- **고침**: `_submit`/`_poll` 개별 호출을 남은 deadline 으로 직접 `asyncio.wait_for`
  로 감싸고, 포기할 때 `transport.cancel()` 을 best-effort 로 호출한다(취소 자체가
  실패해도 우리 쪽 실패 처리는 그대로 진행 — 결과를 `warnings` 에 남긴다).
  ★첫 구현에서 "코루틴이 await 되지 않았다" `RuntimeWarning` 이 실제로 났다
  (deadline 이 이미 지나 그냥 버릴 때 코루틴을 미리 만들어 뒀던 탓) — 0-인자
  콜러블로 바꿔 실제로 await 할 때만 코루틴을 만들도록 고쳤다.
- **테스트**: `tests/unit/ports/test_team_ports.py::test_hanging_poll_past_deadline_fails_promptly_and_cancels_remote`,
  `::test_hanging_submit_past_deadline_fails_without_leaking_a_warning`

### 2. `app/core/remote_team/executor.py:18-19` — LocalTeamExecutor 가 task 의 allowed_tools 를 manifest 와 대조하지 않는다
- **재현 확인**: `app/modules/customer_ops/billing.py`·`technical.py` 는
  `self.tools.call(..., task.allowed_tools, seen)` 로 **task 가 주장하는 목록을
  그대로** 신뢰해서 toolbox 에 넘긴다. `LocalTeamExecutor.execute()` 는
  `registry.get(task.team_id)` 로 manifest 를 얻고도 그 목록과 task 의 목록을
  대조하지 않는다.
- **왜 지금은 안 뚫리는가(그런데도 고친 이유)**: 유일한 프로덕션 호출부
  (`app/application/controller.py:88`)는 `allowed_tools=entry.manifest.allowed_tools`
  로 **항상 manifest 에서** 채운다 — 그래서 오늘은 뚫리지 않는다. 그런데
  CLAUDE.md §2 는 "Team 은 TeamManifest.allowed_tools 밖의 tool 을 호출할 수
  없다. Registry 가 거부한다" 라고 **이미 단정적으로 적혀 있었다** — 실제로는
  Registry 가 거부하는 게 아니라 유일한 호출자가 우연히 항상 옳게 채워서
  안전했을 뿐이다. 이 문장을 사실로 만들려고 고쳤다.
- **고침**: `LocalTeamExecutor.execute()` 가 `task.allowed_tools ⊆ manifest.allowed_tools`
  를 확인하고, 벗어나면 `ToolScopeViolation` 을 던진다.
- **테스트**: `tests/unit/ports/test_team_ports.py::test_local_executor_rejects_a_task_claiming_tools_outside_the_manifest`

## 버그 아님으로 확인한 것 1건

### `app/core/registry.py:54-79` — capability→Team resolve 에 tenant 경계가 없다 (Codex 는 "의심됨"으로 정직하게 표시함)
- **추적 결과**: `TeamRegistry` 는 프로세스당 **하나만** 있고, `config/project.yaml`
  선언 하나로 조립되며, 이 basement 아키텍처는 "한 인스턴스 = 한 설정 = 모든
  tenant 가 같은 Team 정의를 공유"다. tenant 격리는 **DB 행 스코프**(`tenant_id`
  컬럼)에서 이뤄지지, "tenant 별로 다른 Team manifest 세트가 같은 registry 에
  등록"되는 모델이 아니다 — 그런 모델 자체가 이 코드베이스에 없다.
- **왜 버그가 아닌가**: Codex 리포트 스스로도 "현재 기본 구성은 전역 Team
  manifest 만 사용하므로 실제 tenant 별 등록 방식은 확인 필요"라고 정직하게
  적었다 — 확인한 결과 그런 등록 방식 자체가 설계에 없다. `docs/vision/TODO_VISION.md`
  의 "아직 문서화하지 않은 후보" 목록에 이미 "멀티테넌시 실운영(현재는 컬럼만
  있고 값 1개 고정) / tenant 수·계약·운영자 모델이 정리되지 않았다"로 등록돼
  있는 것과 정확히 같은 항목이다 — 새 버그가 아니라 기존에 알려진, 트리거
  없는(=아직 계획 아닌) 확장 여지다.
- **조치 없음.** 코드 변경도, vision 문서 갱신도 하지 않았다 — 이미 정확히
  이 내용으로 등록돼 있다.
