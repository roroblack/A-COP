## 고친 것 2건

### 1. `app/presentation/api/cases.py:_mcp_open()` — MCP open_support_case 가 매번 새 Case 를 만들었다
- **재현 확인**: `request.request_id` 를 계산만 하고 안 썼다. `POST /v1/cases`
  (REST, 67-92행)는 조회-후-생성으로 idempotency 를 지키는데(DoD-11 이 이걸
  증명한다), `_mcp_open()` 은 그 검사 없이 `repository.create_case()` 를
  무조건 호출했다. 직접 테스트로 재현: 같은 `customer_id`+`message` 로 두 번
  호출하면 서로 다른 `case_id` 두 개가 나왔다.
- **왜 위험한가**: DoD-11 이 "동일 요청 10회 → action_requests 1행"을 증명한다고
  claim 하는데, 그 증거는 REST 경로만 봤다 — MCP 경로는 같은 보장이 없었다.
  MCP 클라이언트(개인 AI)가 네트워크 재시도를 하면 같은 문의가 Case 여러 개로
  중복 생성됐다.
- **고침**: REST `POST /v1/cases` 와 같은 패턴(조회 → 있으면 반환, 없으면
  생성 + `action_requests` 기록)을 그대로 적용했다.
- **테스트**: `tests/integration/api/test_api_runtime.py::test_mcp_open_support_case_is_idempotent`.
  기존 `test_mcp_open_support_case_changes_only_case_state` 도 갱신 —
  `action_requests` 가 이제 정확히 1행 늘어나는 게 맞는 동작이라 그 단언을
  고쳤다(payments/subscriptions 는 그대로 0건 유지 — DoD-13 은 안 바뀜).

### 2. `app/core/idempotency.py` — 필드 구분자 없는 결합으로 다른 요청이 같은 key 가 될 수 있었다
- **재현 확인**: `("ab","c","d","e")` 와 `("a","bc","d","e")` 는 결합하면 둘 다
  `"abcde"` 라 SHA-256 도 같다. `action_type` 은 보통 고정 리터럴이라 실전에서
  자주 부딪히진 않지만, `business_subject`(예: `f"{customer_id}:{message}"`)
  는 자유 텍스트를 포함해 이론적으로 충돌 가능하다.
- **고침**: 필드 각각을 먼저 SHA-256 으로 고정 길이로 줄인 뒤 이어 붙이고
  다시 해시한다 — 어떤 필드에 어떤 문자가 와도 경계가 흔들리지 않는다.
  ★알고리즘이 바뀌므로 같은 논리 요청이라도 이전 배포에서 계산된 key 와
  값 자체는 달라진다 — 이 함수는 요청 생명주기 안의 중복 방지용 순수 함수라
  장기 감사 식별자가 아니므로 문제 없다고 판단했다.
- **테스트**: `tests/unit/core/test_idempotency.py`(신규 파일) —
  `test_field_boundary_shift_does_not_collide` 가 정확히 이 시나리오를 검사.

## 보류 — 사용자 결정 필요 (고치지 않음)

### 3. `app/presentation/api/cases.py:116-126` — `POST /v1/cases/{case_id}/messages` 가 실제 resume token 을 전혀 검증하지 않는다
- **재현 확인(코드 사실)**: `MessageRequest` 스키마(34-38행)에는 token 필드가
  아예 없다 — `request_id`·`message`·`expected_version` 뿐이다. 핸들러는
  `hashlib.sha256(request.message.encode())`(고객이 보낸 **자유 텍스트**)를
  그대로 `resume_token_hash` 라고 이름 붙여 저장하고 바로 `VALID_INPUT` 전이를
  실행한다. **실제 토큰과 대조하는 코드가 없다.**
- **왜 심각한가**: `docs/handoff/03_REST_MCP_인터페이스.md` §1-4 는 이 엔드포인트를
  "resume token 은 hash 만 저장. 24h TTL, 일회성, 동일 event_id 재처리
  idempotent" 라고 **이미 문서화**해 뒀다 — 그런데 실제 코드는 이 계약을
  지키는 척만 한다(필드 이름만 `resume_token_hash` 다).
- **더 조사한 것 — 진짜 토큰 검증 로직은 어디 있나**: `CaseService.validate_resume()`
  (`app/application/case_service.py:68`, 실제 hash 대조·`resume_token_used`·
  24h TTL 을 전부 확인하는 진짜 로직)은 **오직 `Controller.resume()`
  (`controller.py:265`)에서만 호출된다.** 그런데 `Controller.resume()` 을
  부르는 REST 라우트가 **하나도 없다** — `grep` 으로 확인. 즉 이 저장소엔
  **완전히 분리된, 서로 연결 안 된 두 개의 "resume" 구현**이 있다:
  1. `Controller.resume(token=...)` + `validate_resume()` — 진짜 토큰/TTL/
     일회성 로직이 다 있고 테스트도 있지만(`test_controller_integration.py:324-338`),
     **REST 밖에서 도달 불가능**하다.
  2. `POST /v1/cases/{case_id}/messages` — REST 로 실제 도달 가능하지만,
     토큰을 아예 안 받고 안 대조한다.
- **왜 지금 고치지 않는가**: 이걸 고치려면 **REST 계약을 바꿔야 한다**
  (`MessageRequest` 에 토큰 필드를 추가하고, 이 핸들러를 `Controller.resume()`
  경유로 다시 연결해야 한다). 이건 인증/인가 경계를 다시 그리는 결정이고,
  기존 호출자(있다면)와의 하위호환도 걸린다 — CLAUDE.md §0 이 요구하는
  "되돌릴 수 없는 것에 가까운 결정"에 해당해 사용자 검토 없이 진행하지 않는다.
  버그사냥 01 의 finding #5(재검증-승인 트랜잭션 경계)와 같은 성격의 보류다.
- **위험도**: 높음. `case:write` scope 를 가진 호출자라면 실제 resume token
  을 몰라도(=고객에게 전송된 이메일/링크를 안 봤어도) 대기 중인 Case 를
  임의 텍스트로 재개시킬 수 있다.

## 버그 아님으로 확인한 것 1건

### `app/application/case_service.py:68-75` — event_id 일치 시 조기 반환이 만료/재사용 검사를 건너뛴다 (Codex 는 "보통 위험도"로 표시)
- **추적 결과**: `last_resume_event_id` 는 `controller.py:276` 에서 **오직**
  `RESUMED` 전이가 성공한 뒤에만 기록된다 — 즉 이 값이 세팅돼 있다는 것
  자체가 "그 `event_id` 로 이미 한 번 정상적으로(토큰 검증까지 통과해서)
  resume 가 성공했다"는 뜻이다. 그러니 같은 `event_id` 재요청에서 만료/
  재사용 검사를 다시 안 하는 건 **버그가 아니라 의도된 idempotent-retry
  동작**이다 — 이미 성공한 요청의 응답이 유실돼 재시도할 때, "토큰이 이미
  쓰였다"고 틀리게 거부하지 않기 위함이다(DoD-11 이 요구하는 "동일 요청
  → 1회 side effect, 재시도는 같은 응답"과 정확히 같은 패턴).
- **조치 없음.**

## 사용자에게 — 다음에 확인해 줄 것

**#3(resume token 미검증)이 이번 4라운드 중 가장 중요한 보류 항목이다.**
`POST /v1/cases/{case_id}/messages` 를 실제 토큰 검증 경로로 다시 연결할지,
아니면 이 엔드포인트는 원래 `case:write` scope 자체를 신뢰 경계로 삼고
(고객 개인이 아니라 이미 인증된 백엔드가 대신 호출하는 채널이라) 별도
토큰이 필요 없다는 설계였는지 확인이 필요하다. 후자라면
`docs/handoff/03_REST_MCP_인터페이스.md` §1-4 의 문구("resume token 은
hash 만 저장")가 오해를 부르니 정정해야 한다.
