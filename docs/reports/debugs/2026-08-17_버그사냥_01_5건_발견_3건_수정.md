# 버그사냥 01 — 안전 핵심부 5건 발견, 3건 수정

Codex 에 리포트만(수정 금지) 발주(`docs/handoff/_prompts/S-BUGHUNT-01-CORE-SAFETY.md`,
`docs/reports/2026-08-17_버그사냥_01_안전핵심부.md`)한 뒤, Claude 가 5건 전부
직접 재현·재검증했다(RULE.md §3.6-3). 3건은 재현 가능하고 안전하게 고칠 수
있어 고쳤다. 2건은 재현은 되지만 (a) 현재 살아있는 경로가 아니거나 (b) 승인/
결제 경계를 넓히는 설계 결정이 필요해 **고치지 않고 이 리포트로만 남긴다**
(RULE.md §4.1 — 고쳤는지와 무관하게 쓴다).

## 고친 것 3건

### 1. `app/core/verification.py:106` — NaN/Infinity 금액이 검증을 예외로 죽인다
- **재현 확인**: `Decimal("NaN")`/`Decimal("Infinity")` 는 생성은 성공하지만
  `>` 비교는 `InvalidOperation`, `int()` 변환은 `OverflowError` 를 던진다.
  독립 재현:
  ```python
  from decimal import Decimal
  Decimal('NaN') > Decimal('5')      # InvalidOperation
  int(Decimal('Infinity'))            # OverflowError
  ```
- **왜 위험한가**: `verify_proposal()` 은 v7 §9-E 할루시네이션 방어의 핵심이다.
  검증 함수 자체가 죽으면 "확인 불가 → 거부" 대신 500 이 나가 방어선이 사라진다.
- **재현 경로**: `_reject_unverified()` → `verify_proposal()`(DoD-24 살아있는 경로).
  LLM 이 금액 필드에 비유한 문자열을 만들어내면(또는 상류 파싱 버그로 새면)
  바로 이 경로를 탄다.
- **고침**: `_to_decimal()` 이 `is_finite()` 아닌 값을 `None` 으로 취급해
  기존 "숫자가 아니다" 거부 경로로 합류시켰다.
- **테스트**: `tests/unit/core/test_proposal_verification.py::test_non_finite_amount_is_rejected_not_a_crash`

### 2. `app/infrastructure/messaging/outbox.py:16` — payload 의 tenant_id 가 case 소유 tenant 와 달라도 거부 안 함
- **재현 확인**: `payload={"tenant_id": "B", "case_id": <A의 case>}` 로 `publish()`
  를 부르면, 20행 조회는 A 를 찾지만 22행이 `payload.get("tenant_id")`(B)를
  우선시켜 **B 의 outbox 행에 A 의 case_id 가 들어간다.**
- **왜 위험한가**: tenant 격리는 CLAUDE.md §0 최상위 원칙이다. 지금은 이 메서드를
  부르는 곳이 코드에 없어(아래 "발견 3" 참조) 당장 뚫리는 경로는 아니지만,
  Port 로 이미 조립돼 있어(`config/project.yaml` 의 `message_broker: outbox`)
  누군가 이 메서드를 쓰기 시작하는 순간 조용히 뚫린다.
- **고침**: `payload.get("tenant_id")` 가 case 의 실제 소유 tenant 와 다르면
  `ValueError` 를 던지도록 명시적 대조를 추가했다.
- **테스트**: `tests/integration/controller/test_outbox_tenant_isolation.py::test_publish_rejects_payload_tenant_that_does_not_own_the_case`

### 3. `app/infrastructure/messaging/worker.py:37` — claim 후 워커가 죽으면 행이 영구히 processing 에 멈춘다
- **재현 확인**: `UPDATE outbox SET status='processing' ...` 커밋 후 `publisher()`
  호출 전/도중에 프로세스가 죽으면, 재시작한 워커는 `status='pending'` 만
  조회하므로 그 행을 다시 집지 않는다. 테스트로 이 상태를 직접 만들어(오래된
  `locked_at` 을 가진 `processing` 행을 심어) 확인했다.
- **왜 위험한가**: at-least-once 배달이 깨진다. 승인·후속 실행 이벤트가 배달
  안 됐는데 아무도 모른다.
- **고침**: `config/guardrails.yaml` 에 `reliability.outbox_stale_processing_seconds`
  (300초) 를 추가하고, `OutboxWorker._reclaim_stale_processing()` 이 매
  `process_once()` 호출마다 임계값을 넘긴 `processing` 행을 **provider
  timeout 과 같은 근거로 `unknown`** 으로 되돌린다. 자동 재실행하지 않는다 —
  이미 만들어 둔 `/ops/outbox` 운영 화면(오늘 세션 앞부분에서 완성)에서
  사람이 결론짓는다.
- **테스트**: `tests/integration/controller/test_provider_timeout_unknown.py::test_crashed_worker_leaves_processing_row_reclaimed_to_unknown`,
  `::test_fresh_processing_row_is_not_reclaimed`(임계값 안은 안 건드리는지)

## 고치지 않고 남긴 것 2건

### 4. `app/core/transition.py:81-86` — outbox dedupe 키가 tenant 를 포함하지 않는다
- **재현 확인(코드 사실)**: `UNIQUE(topic, dedupe_key)` 는 `tenant_id` 를 포함하지
  않는다(`001_schema.sql:19`). 두 tenant 가 같은 `(topic, dedupe_key)` 를 쓰면
  `ON CONFLICT DO NOTHING` 이 조용히 뒤의 것을 버린다.
- **왜 지금은 고치지 않는가**: `transition_case(..., outbox=[...])` 로 실제
  outbox 행을 만드는 유일한 프로덕션 호출부(`app/application/controller.py:170`)
  를 추적한 결과, `_event_for_result()` 의 **네 분기 전부 `outbox=[]` 를
  반환한다** — 즉 이 삽입 경로는 **지금 프로덕션에서 도달 불가능**하다(테스트만
  `OutboxMessage` 를 직접 만들어 이 경로를 돈다). 실제 살아있는 outbox 기록
  경로는 `app/infrastructure/messaging/outbox.py`(위 2번, 고침) 와
  `app/application/feedback_job.py` 의 직접 SQL 뿐이다.
- **왜 그래도 적어두는가**: `outbox=[...]` 지원 자체는 계약(`docs/handoff/01`)에
  있고 테스트도 있다 — Controller 가 실제로 이걸 채우기 시작하는 순간(예: Team
  결과에 따라 외부 알림을 발행하는 기능이 생기면) 이 gap 이 살아난다. UNIQUE
  제약에 `tenant_id` 를 추가하는 건 DoD-12 evidence 가 근거로 든 제약을
  바꾸는 것이라 **사용자 검토 없이 지금 바꾸지 않는다.**
- ★부가 관찰: `_event_for_result()` 가 outbox 를 전혀 채우지 않는 게 의도된
  "아직 안 만든 기능"인지, 리팩터 중 빠진 배선인지도 확인이 필요하다 —
  버그라기보다 설계 확인 항목이다.

### 5. `app/application/proposal_guard.py:72-86` + `app/presentation/api/cases.py:153-187` — 재검증과 승인이 하나의 원자적 경계가 아니다
- **재현 확인(코드 사실)**: `recheck_before_execution()`(157행)의 조회와 실제
  승인 트랜잭션(175행)은 **서로 다른 트랜잭션**이다. 재검증 통과 직후, 승인
  커밋 전에 다른 트랜잭션이 같은 payment/entitlement 를 바꾸면, 재검증
  시점에는 맞았던 사실 기준으로 승인이 확정된다. 최종 `transition_case()` 의
  `expected_version` 은 **case 행**만 보호하고 참조된 payment/subscription
  행의 변경과는 연결되지 않는다.
- **왜 지금은 고치지 않는가**: 이건 한 줄짜리 버그가 아니라 **트랜잭션 경계를
  다시 그리는 설계 결정**이다(두 방법 검토함: (a) 재검증과 승인을 하나의
  트랜잭션으로 합친다 — 그러면 GUARDRAIL_ESCALATED 조기 종료 경로의 락 보유
  시간이 늘어난다, (b) 승인 트랜잭션 안에서 재검증을 한 번 더 돈다 — 왕복
  비용이 는다). 어느 쪽이든 결제·승인처럼 되돌릴 수 없는 코드 경로를 사용자
  검토 없이 바꾸지 않는다(CLAUDE.md §0.2).
- **위험도**: 높음(검증을 통과한 금액·식별자와 실제 승인 시점의 원장이 달라질
  수 있음) — 그러나 **동시에 같은 case 의 같은 액션을 승인하려는 요청**과
  **그 사이 참조 레코드가 바뀌는 것**이 함께 일어나야 하므로 발생 빈도는
  낮다고 추정된다(실측 아님 — 추정이라고 표시한다).
