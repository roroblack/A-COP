# 결함 — 검사하는 척하는 검사들 (2026-08-17)

하루에 같은 유형이 네 번 나왔다. **형태는 검사인데 아무것도 막지 못하는 것들**이다.
이 저장소가 반복해서 당한 유형이라 한 문서로 묶어 남긴다.

> 검사하지 않는 규칙은 지켜지지 않는다.
> 그리고 **검사하는 척하는 규칙은 지켜진다고 착각하게 만든다** — 더 나쁘다.

---

## 1. 항상 참인 단언

`tests/console/test_package_boundary.py` (Codex 작성):

```python
assert "app.console" in "\n".join(Path("app/console").glob("*.py").__str__() for _ in [0]) \
       or Path("app/console").is_dir()
```

- 앞 항: `glob()` 은 제너레이터고 `__str__()` 은 `<generator object ...>` 를 만든다 → **항상 거짓**
- 뒤 항: 폴더가 있으면 **항상 참**

즉 `assert True` 다. 패키징이 어떻게 깨져도 통과한다.

★**실행해서 확인했다.** 단언을 눈으로 읽는 것으로는 못 잡는다:

```
생성된 문자열: '<generator object Path.glob at 0x...>'
app.console in it? -> False
Path(app/console).is_dir() -> True
=> 단언은 두 번째 항만으로 항상 참
```

**교훈**: 단언이 `or` 로 이어져 있으면 각 항을 따로 평가해 보라.

---

## 2. 껍데기 분리

"콘솔을 별도 패키지로 분리했다" 는 결과가 이랬다:

```
app/console/console.py            4줄   ← from app.presentation.ui.console import *
app/presentation/ui/console.py  390줄   ← 진짜 코드
```

`pyproject.toml` 은 `app.console*` 만 제외하는데 **실제 코드는 `app.presentation.ui` 에 있고
그 패키지는 제품에 포함된다.** 이름만 옮기고 코드는 그대로 실렸다.

★**내 1차 검증도 틀렸다.** `find_packages` 로 패키지 **이름**만 보고
"제품에 콘솔 없음 OK" 라고 판정했다. 코드가 어디 있는지는 안 봤다.

**교훈**: 분리를 검증할 때는 **줄 수**를 세라. 이름은 옮기기 쉽고 코드는 안 옮겨진다.

---

## 3. 설치할 수 없는 설치 대상

```toml
[project.optional-dependencies]
console = []                                   # 비어 있음
exclude = ["app.console*", ...]                # 전면 제외
```

요구는 둘이었다 — (1) 제품에 콘솔이 없다 (2) 점검할 때 붙일 수 있다.
(1)만 하고 (2)를 안 만들었다. **어떤 설치 대상도 `app.console` 을 담지 않는다.**

**교훈**: 요구가 둘이면 **둘 다** 검사한다. 하나만 통과해도 초록불이 켜진다.

## 4. 조용한 절삭

대시보드가 평가 리포트를 **6개만** 보여주면서 그 사실을 말하지 않았다.
전체 23개인데 화면만 보면 "이게 전부" 로 읽힌다.

지금은 이렇게 적는다:

```
최근 6개만 표시했다. 전체 23개 중 17개는 화면에 없다.
```

**교훈**: 상한을 두면 **상한을 뒀다고 말한다.** 말 없는 절삭은 거짓말이다.

## 5. ★분업 방식 자체의 결함 — Codex 가 한글 파일을 못 읽는다

introspection 발주가 **두 번 연속 아무 산출 없이** 끝났다. 로그 236KB 를 보니
파일만 읽다 끝났고, 읽은 내용이 이랬다:

```
"?꾩닔 ?섍꼍蹂?섍? ?녾굅???섎せ?먮떎. .env.example 瑜?.env 濡?蹂듭궗?댁꽌..."
```

PowerShell 을 거쳐 읽으면 **한글 주석이 mojibake 로 들어간다.**
이 저장소는 주석이 거의 전부 한글이라, **읽을 파일이 많은 작업일수록 무너진다.**

- 성공한 발주(IA 검토·P4~P6)는 읽을 파일이 적었다
- 실패한 발주(introspection·코드 이동·패키징)는 넓게 읽어야 했다

★**내 실수도 겹쳤다.** 1차 때 로그를 `docs/reports/` 안에 쓰게 해서
Codex 가 **자기 로그를 읽는 순환**이 났다. 2차에 밖으로 뺐지만 근본 원인은 남아 있었다.

**교훈**: Codex 에 넘길 때는 **읽을 파일을 명시**하고 범위를 좁힌다.
넓게 읽어야 하는 교차 작업은 이 환경에서 Codex 에 맞지 않는다
(`docs/handoff/05_분업_규칙.md` 에 반영).

## 공통 교훈

네 건 모두 **"했다" 와 "된다" 를 구분하지 않아서** 생겼다.

| 했다 | 된다 |
|---|---|
| 테스트를 만들었다 | 그 테스트가 **실패할 수 있다** |
| 패키지를 나눴다 | 제품 artifact 에 **코드가 없다** |
| 설치 대상을 선언했다 | 실제로 **설치된다** |
| 목록을 보여준다 | **전부** 보여주거나 아니라고 말한다 |
| 발주했다 | 산출물이 **나왔다** |

★오른쪽을 **실행해서 출력으로** 확인하지 않으면 왼쪽만 쌓인다.
