# 제작 단계 모듈 구성기(Composer) GUI 설계 검토

## 검토 결론

현재 `/ui/admin`은 제작 구성이 아니라 운영 조회 화면이다. 화면은 `composition.build_registry()`를 호출해 manifest를 읽고(`app/presentation/ui/routes.py:81-84`), 포트 구현체와 상태·guardrail을 표시할 뿐(`app/presentation/ui/routes.py:87-121`), 선택을 저장하거나 배포 구성을 만들지 않는다. 따라서 Composer가 필요하다면 1차 산출물은 **선언 파일 + 검증기**여야 하며, 코드 생성은 검증을 통과한 선언에 한해 별도 명령으로 제한하는 것이 맞다.

다만 MVP에 즉시 추가하는 것은 권하지 않는다. 현재 저장소는 고정된 `composition.py`가 두 Team과 여러 adapter를 조립하고(`app/composition.py:39-68`), v5 범위 밖 기능은 구현하지 말라는 규칙이 있다(`RULE.md:88-92`, `RULE.md:98-99`). Composer를 추가하려면 먼저 “구성 선언이 실제 배포 조립의 단일 입력”이 되도록 composition 경계를 바꾸는 작업이 필요하다.

## 1. 현재 코드의 모듈 분류

### 1.1 필수 — 뺄 수 없음

| 항목 | 판정 근거와 지금 제거하면 깨지는 곳 |
|---|---|
| Case lifecycle과 `transition_case()` | API의 Case 생성·분류가 `CREATED`, `CLASSIFIED`/`CLASSIFICATION_FAILED` 전이를 직접 호출한다(`app/presentation/api/cases.py:65-91`). Controller도 routing, resume, 결과 반영을 이 함수로 처리한다(`app/application/controller.py:103-156`). 함수는 projection update, event append, outbox insert를 한 트랜잭션에서 수행한다(`app/core/transition.py:6-13`, `app/core/transition.py:153-203`). 제거하면 API와 Controller가 상태를 진행시키지 못하고 append-only event/projection 일관성이 깨진다. |
| 계약 모델 `TeamTask`·`TeamResult`·`TeamManifest`·`TeamModule` | Controller는 `TeamTask`를 만들고(`app/application/controller.py:66-79`), executor 결과를 `TeamResult`로 받아 전이를 결정한다(`app/application/controller.py:137-176`). `TeamModule`은 `manifest`와 `async execute()`를 요구한다(`app/core/contracts.py:315-325`). 모델 검증은 답변 근거, approval, wait/handoff/escalate 형식을 강제한다(`app/core/contracts.py:239-290`). 빼면 Team 실행 경계와 결과 전이 계약이 사라진다. |
| Registry와 active Team 해석 | `build_registry()`가 두 기본 Team을 생성·등록한다(`app/composition.py:39-45`). Registry는 contract 호환성·중복 ID를 검사하고(`app/core/registry.py:38-46`), active이며 case type이 정확히 하나인 Team만 resolve한다(`app/core/registry.py:54-79`). Controller의 routing은 resolve 실패를 `ROUTING_FAILED`와 failed run으로 기록한다(`app/application/controller.py:105-116`). Registry를 빼면 라우팅 자체가 불가능하다. |
| Context Broker와 정책 retrieval 경계 | Controller는 Team manifest의 `knowledge_scope`로 정책을 검색하고(`app/application/controller.py:66-75`), ContextPack을 만든다. `ContextPack`은 12,000 token 및 `degraded`/`omissions` 신호를 검증한다(`app/core/contracts.py:117-152`). retrieval 예외는 빈 결과로 조용히 대체되지 않고 `retrieval_failed=True`로 전달된다(`app/application/controller.py:59-64`). 이 경계를 제거하면 Team이 요구하는 근거·scope·예산 계약이 깨진다. 단, 특정 검색 adapter 자체는 교체 가능하다. |
| DB repository/session 및 outbox 원자성 | composition은 repository, connection factory, broker를 Controller에 주입한다(`app/composition.py:60-68`). Case 전이는 outbox 메시지를 동일 트랜잭션에 넣고(`app/core/transition.py:6-13`, `app/core/transition.py:190-203`), worker는 pending 메시지를 claim·deliver·dead-letter 처리한다(`app/infrastructure/messaging/worker.py:12-39`). 이를 빼면 Case 상태와 비동기 발행의 원자성이 깨진다. |
| Case resume/approval 계약 | `CaseService`는 active run 중복을 막고 `agent_runs`를 기록한다(`app/application/case_service.py:29-48`). Controller는 approval proposal을 action request로 저장하고(`app/application/controller.py:167-172`), resume token 검증 후 다시 실행한다(`app/application/controller.py:178-199`). Team이 proposal만 내고 side effect를 하지 않는 계약도 명시돼 있다(`app/core/contracts.py:196-201`). 이 부분을 빼면 대기·승인·재개 Case가 끝나지 않는다. |

|---|---|

| A2A Executor | 현재 production composition은 `LocalTeamExecutor`를 반환한다(`app/composition.py:48-50`). Controller는 concrete Team이 아니라 주입된 executor의 `execute()`만 호출한다(`app/application/controller.py:137-140`). `A2ATeamExecutor`는 transport와 capability resolver가 별도로 있어야 한다(`app/core/remote_team/a2a_executor.py:10-26`). 따라서 A2A 구현체를 제거해도 Local 경로는 동작하지만 A2A port tests/import 및 원격 실행 선택은 깨진다(`tests/unit/ports/test_team_ports.py:7-9`, `tests/unit/ports/test_team_ports.py:51-57`). |
| VOC 분류·일일 배치 | inline 분류는 `feedback.classify()`가 불완전한 결과를 명시적으로 실패시킨다(`app/modules/customer_ops/feedback.py:83-103`). 일일 집계는 별도 함수와 CLI로만 연결된다(`app/application/feedback_job.py:30-78`, `scripts/run_daily_feedback.py:7-19`). 운영 UI의 VOC 페이지는 report table을 읽는다(`app/presentation/ui/routes.py:72-78`, `app/presentation/ui/routes.py:207-213`). 배치를 제거하면 일일 report·VOC 화면이 사라지지만 Case 생성·Team routing은 직접 깨지지 않는다. inline 분류까지 제거하면 API의 분류 단계가 `CLASSIFICATION_FAILED`로 간다(`app/presentation/api/cases.py:80-91`). |
| MCP | MCP 모듈은 세 read-scoped tool만 등록한다(`app/presentation/api/mcp.py:3-20`), 각 호출은 cases helper를 거친다(`app/presentation/api/cases.py:148-180`). 제거하면 MCP client와 MCP scope 테스트가 깨지지만 REST와 Controller의 일반 경로는 유지된다. 단, `mcp:read` 계약을 사용하는 외부 소비자는 명시적으로 deprecation해야 한다. |
| Vector RAG adapter | `search_policy()`는 tenant/scope가 없으면 빈 결과를 반환하고, API key가 없으면 “fallback 없음”을 명시적으로 오류낸다(`app/infrastructure/rag/retriever.py:15-24`, `app/infrastructure/rag/retriever.py:37-46`). Controller가 이를 호출한다(`app/application/controller.py:59-75`). 따라서 “RAG 기능”은 선택 가능하지만 현재 활성 Team의 manifest가 `policy`를 요구하고(`app/modules/customer_ops/billing.py:17`, `app/modules/customer_ops/technical.py:11`), Team도 `read.policy`를 호출한다(`app/modules/customer_ops/billing.py:60-67`, `app/modules/customer_ops/technical.py:46-54`). RAG를 빼려면 이 Team/manifest를 비활성화하거나 정책 Port를 구성에서 제거하고, 호출 시 명시적 오류를 내야 한다. 조용한 빈 답변 폴백은 현재 코드와 규칙에 어긋난다. |

### 1.3 교체 가능 — Port가 있음

| Port/교체 지점 | 근거와 제약 |
|---|---|
| `TeamExecutorPort`: Local ↔ A2A | Port는 `execute(TeamTask) -> TeamResult` 한 메서드다(`app/core/remote_team/executor.py:8-10`). Local은 Registry module을 호출한다(`app/core/remote_team/executor.py:12-19`); A2A는 transport로 submit/poll하고 원격 결과를 TeamResult로 매핑한다(`app/core/remote_team/a2a_executor.py:17-26`, `app/core/remote_team/a2a_executor.py:46-68`). Controller는 이 Port만 호출하므로 교체면은 실재한다. 다만 A2A에는 endpoint resolver·transport 설정이 추가로 필요하다(`app/core/remote_team/a2a_executor.py:13-21`). |
| 정책 검색 함수 | `build_controller()`가 `policy_search_fn`을 주입한다(`app/composition.py:52-64`). Controller는 호출 실패를 명시적 degraded 신호로 바꾼다(`app/application/controller.py:59-64`). 따라서 pgvector 구현체는 교체 가능하지만 반환 의미와 실패 신호는 유지해야 한다. |
| Message broker | `MessageBrokerPort`의 계약은 `publish/ack`이다(`app/core/contracts.py:333-341`). MVP adapter는 `OutboxBrokerAdapter`이고 Redis adapter는 만들지 말라는 계약이다(`app/core/contracts.py:334-338`). 다만 현재 Controller에는 broker가 주입되지만(`app/composition.py:60-68`) 이 파일에서 broker를 직접 호출하는 경로는 확인되지 않는다. 그러므로 “교체 가능한 경계”이지, 현재 Case 실행을 즉시 대체해도 되는 독립 기능이라는 뜻은 아니다. |

### 1.4 개수 가변 — Agent Team

Team 수는 Registry에 등록된 active Team의 수와 일치해야 한다. `TeamRegistry`는 리스트를 받아 각 Team을 등록한다(`app/core/registry.py:32-46`), manifest의 `accepted_case_types`와 capability로 정확히 하나를 선택한다(`app/core/registry.py:54-89`). 테스트도 기본 두 Team을 확인한 뒤 외부 Team을 `registry.register()`로 추가한다(`tests/unit/test_composition_root.py:25-32`). 따라서 2개/3개/4개는 구조적으로 가능하지만, 같은 case type에 active Team이 둘 이상 매칭되면 `RegistryError`가 나고 routing failed가 된다(`app/core/registry.py:77-79`, `app/application/controller.py:112-116`). GUI는 단순히 개수를 늘리는 것이 아니라 “case type별 정확히 하나” 검사를 해야 한다.

## 2. 구성 산출물 3안 비교와 권고

| 안 | 장점 | 단점/이 저장소에서의 실제 위험 |
|---|---|---|
| 1. 선언 파일(`config/project.yaml`) + composition이 읽음 | 변경 이력이 작고 되돌리기 쉽다. 현재 조립 책임이 한 곳에 모여 있으므로(`app/composition.py:39-68`) Registry/adapter 선택을 선언으로 검증하기 좋다. GUI와 runtime의 차이를 schema·contract test로 잡을 수 있다. | 선언만 바꾸고 Python 구현이 없으면 실행 시 import/Registry 오류가 난다. 활성화 전에는 반드시 manifest 구현·adapter factory가 존재해야 한다. |
| 2. 코드 생성(scaffold) | 팀 담당자가 바로 디렉터리·manifest·테스트 뼈대를 받아 작업할 수 있다. | 생성 파일이 실제 `build_registry()`에 자동 등록된다는 보장이 현재 없다(`app/composition.py:42-45`는 두 클래스를 고정 import). 방치된 파일, 충돌하는 team_id, 빈 prompt/tool이 “등록된 것처럼” 남을 위험이 크다. |
| 3. 선언 + scaffold | 선언은 배포 구성의 기록이고 scaffold는 작업 착수점을 제공한다. | 두 산출물의 drift가 가장 크다. 생성물과 선언, 실제 Registry 세 곳을 동기화·검증해야 하며, v5 MVP 경계를 넘는 새 생성 시스템이 된다. |

### 권고: 1안을 기본으로 하고, 검증 통과 후에만 제한적 scaffold를 부가

권고 산출물은 `config/project.yaml` 같은 **선언 파일 하나**다. 다만 사용자가 지정한 소유 범위상 이번 검토에서는 만들지 않는다. 향후 구현 시 `composition.py`가 선언을 읽어 registry와 adapter를 조립하도록 바꾸고, 선언의 각 ID를 실제 factory/manifest와 대조하는 검증기를 둔다. 이유는 현재 runtime 조립이 `composition.py`에 집중되어 있고(`app/composition.py:39-68`), 현재 admin은 조회만 하기 때문이다(`app/presentation/ui/routes.py:81-121`).

코드 생성은 `active=false` Team의 디렉터리·manifest·contract test만 만들고 자동 production 등록은 하지 않는 2단계로 미룬다. 선언 파일에는 `implementation_ref`, `active`, `required_ports`, `team_id`, `accepted_case_types`, `capabilities`를 기록하고, build 시 “선택됨 + active인데 구현 없음”, “중복 라우팅”, “선택 기능 호출 경로 없음”을 실패시켜야 한다.

## 3. Team 추가 시 최소 뼈대와 미구현 안전장치

### 실행 가능한 Team의 최소 계약

- `TeamManifest` 필수값: `team_id`, `display_name`, `contract_name`, `supported_contract_versions`, `capabilities`, `accepted_case_types`, `required_context`, `allowed_tools`, `knowledge_scope`, `implementation_revision`; `max_steps`는 기본 6, `active`는 기본 true다(`app/core/contracts.py:298-312`). 실제 built-in 예시는 이 모든 필드를 채운다(`app/modules/customer_ops/billing.py:17`, `app/modules/customer_ops/technical.py:11`).
- `TeamModule`은 `manifest` 속성과 `async execute(task: TeamTask) -> TeamResult`가 필요하다(`app/core/contracts.py:315-325`).
- `TeamRegistry.register()` 호출이 필요하고, contract major 호환성·중복 `team_id`를 통과해야 한다(`app/core/registry.py:38-46`).
- `allowed_tools`의 모든 이름은 `ReadToolbox.call()`의 known function이고 허용 목록에 있어야 한다(`app/tools/read_tools.py:99-116`).
- prompt·knowledge scope는 Team 구현이 실제로 사용해야 한다. Billing은 세 read tool과 `billing.answer` 계열 prompt를 호출한다(`app/modules/customer_ops/billing.py:28-39`, `app/modules/customer_ops/billing.py:60-78`). Technical도 네 read tool과 `technical.answer` 계열 prompt를 호출한다(`app/modules/customer_ops/technical.py:16-27`, `app/modules/customer_ops/technical.py:46-62`). prompt 파일은 등록 시 hash와 version을 기록하는 구조다(`app/tools/read_tools.py:119-137`).

### 안전한 “등록됐지만 미구현” 상태

`active=False`를 사용해야 한다. Registry의 `resolve()`는 active Team만 후보로 삼는다(`app/core/registry.py:65-68`). 따라서 scaffold는 다음만 제공한다.

1. 모든 manifest 필드를 채운다. 특히 `active=False`, `implementation_revision`에 scaffold revision을 넣는다.
2. `execute()`는 호출될 경우 `NotImplementedError`를 던지지 말고, `TeamResult(outcome="failed", next_action=ESCALATE, failure_code="team_not_implemented")`를 반환한다. `TeamResult`는 실패 결과에 failure code 또는 warning을 요구한다(`app/core/contracts.py:263-265`). 이렇게 하면 직접 호출돼도 예외가 삼켜지지 않고 계약적인 실패로 남는다.
3. 더 중요한 방어선으로 Composer/build 검증에서 `active=False` Team은 Registry에 등록하되 production routing 후보에서 제외한다. `active=True`인데 구현이 scaffold이거나 required prompt/tool/port가 없으면 build 자체를 실패시킨다.
4. GUI는 case type별 active 후보 수가 정확히 1인지 검사한다. 0개/2개 이상은 Controller가 실제로 `ROUTING_FAILED`로 처리하는 상태이므로(`app/core/registry.py:77-79`, `app/application/controller.py:112-116`) 배포 전에 거부해야 한다.

이 설계는 “미구현 Team이 라우팅된 뒤 Case가 죽는” 문제를 build 단계에서 막고, 우회 폴백도 만들지 않는다. `NotImplementedError`는 호출자가 예외를 처리하지 못하는 외부 경로에서 500으로 뭉개질 수 있어 scaffold runtime의 기본 동작으로는 부적절하다. 단위 테스트에서 직접 호출해 “실패 결과”를 확인하는 용도로만 허용한다.

## 4. 선택 기능 제외 시 실패 설계

원칙은 **선택 기능을 빼면 그 Port를 `None`으로 조용히 바꾸지 않고, 호출 시 식별 가능한 예외를 발생시키는 것**이다. 프로젝트 규칙도 fallback 금지와 명시적 오류를 요구한다(`RULE.md:81-86`). RAG도 API key 부재 시 fallback이 없다고 명시한다(`app/infrastructure/rag/retriever.py:15-18`).

권고하는 공통 구조는 다음과 같다.

- 선언에는 기능의 `enabled`와 Port 구현 ref를 함께 둔다.
- build 시 `enabled=false`이면 해당 adapter를 조립하지 않는다.
- 선택 기능을 요구하는 Team/서비스가 그 Port를 호출하면 `OptionalFeatureDisabled(feature="graphstore")` 같은 명시적 예외를 낸다. 예외에는 feature id, 호출 operation, project config revision을 포함한다.
- HTTP 경계에서는 이를 일반 500으로 숨기지 말고 `feature_disabled` 같은 4xx/5xx 계약 오류로 변환한다. 내부 runtime에서는 feature id가 로그·Case failure code에 남아야 한다.
- GraphStore의 경우 현재 호출자는 admin의 snapshot뿐이고(`app/presentation/ui/routes.py:87-112`), 업무 실행 경로의 호출은 확인되지 않았다. 따라서 GraphStore를 뺀 구성에서는 admin에 “disabled”를 표시하고 GraphStore 조회 버튼 자체를 노출하지 않는다. 나중에 ContextBroker나 Team이 GraphStore를 요구하도록 선택되면 build 검증이 `graphstore required but disabled`로 실패해야 한다.

조용한 빈 리스트는 금지한다. `search_policy()`의 빈 리스트는 tenant/scope에 문서가 없는 정상 의미(`app/infrastructure/rag/retriever.py:37-46`)와 retrieval 예외의 degraded 신호(`app/application/controller.py:59-64`)가 구분되어 있기 때문이다. 같은 방식으로 disabled와 empty result를 섞으면 운영자가 “기능을 뺐다”와 “데이터가 없다”를 구별할 수 없다.

## 5. 반대 의견과 위험

### 만들지 않는 편이 나은 이유

1. **구성-코드 drift**: 현재 `build_registry()`는 두 클래스를 Python 코드에 고정한다(`app/composition.py:39-45`). 선언 파일만 추가하면 GUI 선택과 실제 runtime이 서로 다른 시스템이 된다. 이 drift를 막으려면 composition refactor, schema validation, contract test, CI check가 함께 필요하다.
2. **뼈대 방치**: `TeamManifest.active` 기본값은 true다(`app/core/contracts.py:310-312`). scaffold가 active를 생략하면 미구현 Team이 routing 후보가 된다. Registry는 정확히 하나의 active Team을 요구하므로(`app/core/registry.py:65-79`) 기존 Team과 충돌하거나 routing failure를 만든다.
3. **운영 화면과 제작 도구의 혼동**: 현재 admin은 read-only라고 스스로 표시하고(`app/presentation/ui/routes.py:81-89`), Case/Trace/Approval/VOC 운영 메뉴를 제공한다(`app/presentation/ui/routes.py:33-35`). 여기에 write 기능을 덧붙이면 운영 권한·감사·승인과 제작 구성을 섞게 된다.
4. **MVP 범위 초과**: 규칙은 v6 In만 구현하고 Out/Phase 2 본체는 만들지 말라고 한다(`RULE.md:88-92`, `RULE.md:98-99`). handoff 계획도 Redis adapter 본체를 금지하고 Port만 허용한다(`app/core/contracts.py:334-338`). Composer GUI는 선언 schema, 저장·검증, 생성·preview·권한까지 추가하므로 v5 §3의 최소 Case/Trace/Approval/VOC 운영 UI 경계를 넘어설 가능성이 높다. v5 원문은 저장소 외부 기준선으로 보존되어 있으며, 저장소 안의 실행계획은 그 §3을 읽기 전용 기준으로 취급한다(`docs/plans/2026-08-12_1507_A-COP_실행계획서_v1.md:1-10`, `docs/handoff/_prompts/S-UI.md:9-21`).
5. **잘못된 구성의 비용**: active Team을 빼면 기존 case type이 0개 후보가 되어 Case가 `ROUTING_FAILED`로 간다(`app/application/controller.py:105-116`). 반대로 새 Team을 넣었는데 같은 case type을 수용하면 정확히 하나 조건을 위반한다(`app/core/registry.py:77-79`). GUI의 편의성이 런타임 안전성보다 앞서면 회의 중 변경이 곧 장애가 된다.

따라서 “팀 수를 자주 바꾸고 기능을 선택한다”는 요구만으로 GUI를 승인하지 않는다. 먼저 선언을 runtime 조립의 단일 source로 만들고, build-time 검증으로 위 실패를 잡을 수 있을 때만 다음 단계로 간다.

## 6. 만든다면 최소 범위(MVP) 제안

MVP는 제작 화면 전체가 아니라 다음 네 기능으로 제한한다.

1. **구성 편집**: Team 목록, `active`, `team_id`, accepted case type, capability, required port, tool allowlist, prompt key, knowledge scope를 편집한다. 운영 DB·Case·VOC 데이터는 읽거나 쓰지 않는다.
2. **정적 검증**: TeamManifest Pydantic 검증, contract version, 중복 ID, case type별 active Team 정확히 하나, allowlist의 tool 존재, 선택 Port의 enabled/required 일관성을 검사한다. Registry의 실제 규칙을 그대로 재사용한다(`app/core/registry.py:38-79`).
3. **선언 export와 preview**: `config/project.yaml`을 export하고, 실제 composition이 만들 객체/비활성 기능/라우팅 표를 preview한다. export만으로 production 파일을 자동 수정하지 않는다.
4. **검증 명령**: 선언을 읽어 `build_registry()`와 동일한 factory 조립을 dry-run하고, 미구현 active Team·disabled required feature·ambiguous routing이면 실패한다. 통과 후에만 별도 승인된 scaffold 생성 명령을 제공한다.

MVP에서 제외할 것: production `app/**` 자동 수정, DB migration 생성, 권한·배포·원격 A2A endpoint provisioning, prompt 본문 자동 작성, Graph DB 설치, 운영 admin 화면에 Composer 쓰기 기능 통합. 이 경계를 지키지 못하면 이번 GUI는 모듈 구성기가 아니라 새로운 배포 플랫폼이 되며, 현재 저장소의 contract-first·fallback 금지·In/Out 경계를 동시에 위반할 위험이 있다.

## 근거 범위와 판정 한계

이번 판정은 저장소에 실제 존재하는 Python import·호출 관계와 테스트를 기준으로 했다. `v5 §3` 원문 자체는 이 저장소 파일 목록에 없으므로 그 세부 문구를 직접 인용하지 않았고, 저장소 안에서 확인 가능한 실행계획·handoff와 `RULE.md`의 In/Out 규칙만 근거로 사용했다. GraphStore가 현재 Controller에서 호출되지 않는다는 판정도 “호출 import가 없다”는 저장소 검색 결과와 admin/test의 실제 참조(`app/presentation/ui/routes.py:14`, `app/presentation/ui/routes.py:87-112`, `tests/integration/graph/test_sql_graph_adapter.py:8`)에 한정한다. 향후 미검색 외부 배포 스크립트가 있다면 이 결론은 재검증해야 한다.
