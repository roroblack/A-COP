# Composer 배포 경계 분리 계획

> 배경: Claude·Codex 설계 자문(`docs/handoff/_prompts/S-COMPOSER-DEPLOYMENT-TOPOLOGY-CONSULT.md`)
> 결론 — 고객 API(`/v1/cases`)와 Composer 쓰기 API(`/composer/*`, `/auth/token`)가
> 지금 **같은 FastAPI 프로세스·같은 포트**에 있다. `docs/handoff/13`의 "VPN/SSH
> 전제"는 코드가 아니라 운영 약속일 뿐이라 인프라가 그걸 강제하지 않으면
> 종이 위의 약속이다. 실제로 `infra/aws/main.tf`의 ALB ingress 가
> `0.0.0.0/0`(전체 공개)이어서 그 전제와 이미 모순된다는 것도 확인했다.
> 사용자 지시: 1단계(문서·배포설정) → 2단계(두 프로세스 분리) 순서로 진행.

## 0. 지금 상태 (사실관계, 2026-08-18)

- `app/presentation/api/app.py`의 `create_app()`이 고객 API·운영 UI·
  `/introspection`·`/composer/*`·`/auth/token`을 **한 `FastAPI` 앱**에
  전부 등록한다.
- `app/application/composer_service.py`의 `_WRITE_LOCK`은 프로세스 로컬
  `threading.Lock`이다 — 다중 인스턴스·다중 워커에서 동시성 보장이 깨진다.
- `infra/aws/main.tf`(Codex 초안, 2026-08-17, **미검증** — 이 기계엔
  Terraform 없음)의 ALB ingress 는 `0.0.0.0/0`. `aws_ecs_service.desired_count`
  는 이미 `1`이지만, "왜 1이어야 하는지" 배포 설정에 근거가 안 남아 있다.
- Composer 가 `config/project.yaml`을 바꿔도 이미 떠 있는 런타임 프로세스가
  자동으로 재조립된다는 계약이 없다(재시작/reload 절차 미정의).

## 1. basement 원칙과의 정합성

Composer 쓰기 채널 자체는 이미 basement 설계 원칙에 맞게 만들어져 있다 —
`composer_service.py`가 대상 앱의 실제 canonical config loader
(`load_project_config`)를 그대로 재사용해 "검증은 통과했는데 기동은
실패" 문제를 피한다. 이번 분리는 이 원칙을 깨지 않는다: **코드를 복제
하지 않고, 같은 저장소·같은 커밋에서 배포 단위(entrypoint/이미지)만
나눈다.** `final_project_ui`가 대상의 검증 모델을 복사하지 않는다는
원칙(`final_project_ui/CLAUDE.md` §0.2)도 그대로 유지된다 — 쓰기 로직은
여전히 대상(sample/cs) 쪽에 남는다.

## 2. 확인이 먼저 필요한 것

- Composer 적용(`apply`) 후 실제 서비스 런타임에 반영하는 방법 —
  재배포 트리거? 내부 reload endpoint? DB/config-store polling? 이번
  계획에서는 **정의만 하고 구현은 범위에 따라 조정**(2단계 안에서 결정).
  ★2026-08-19 결론: `docs/reports/2026-08-19_Composer_reload_계약_설계검토.md`
  — 지금은 **재기동/재배포 요구** 계약만 채택(자동 폴링·admin-triggered
  reload는 보류). `apply` 성공은 "Composer가 대상 파일을 원자적으로
  교체했다"는 뜻일 뿐 customer-runtime 반영을 뜻하지 않는다고 명시하고,
  `desired_revision`/`active_revision`/`pending_restart` 구분 노출이
  필요하다고 판정(아직 코드로 구현하지 않음 — 노출 자체는 후속 스트림).
- 두 entrypoint의 배포 이미지를 몇 개로 낼지(같은 이미지, 다른 커맨드로
  띄우는 방식 vs 완전히 다른 이미지 빌드) — ★2026-08-19 완료: 두 개의
  Dockerfile(`Dockerfile`/`Dockerfile.customer`)로 확정, §5 참고.

## 3. 1단계 — 문서·배포 설정 정합화 (코드 로직 변경 없음)

계약: `docs/handoff/_prompts/S-COMPOSER-DEPLOY-DOCS-01.md`

- `docs/handoff/13`에 수평 확장 금지·`/auth/token` 민감도·config apply와
  audit append 가 원자적이지 않다는 사실·런타임 반영 미정의를 명시.
- `infra/aws/main.tf`의 ALB ingress 를 VPC 내부/관리 IP 로 좁히거나
  최소한 "프로덕션 전 반드시 좁혀야 한다" 주석을 남긴다. `desired_count=1`
  옆에 이유를 주석으로 남긴다.
- Docker/compose 의 Uvicorn 실행 커맨드에 `--workers 1`을 명시(폴백 금지
  원칙 — 기본값에 암묵적으로 기대지 않는다).
- **코드(`app/`, `config/`, `tests/`)는 건드리지 않는다.**

완료 기준: `pytest -q --ignore=tests/integration/rag` 결과가 이 스트림
전후로 동일. 문서 diff 검수 완료.

## 4. 2단계 — customer-runtime / composer-control 두 진입점 분리

1단계 완료·검수 후 착수. 별도 계약 문서를 새로 작성한다(1단계 리포트
검수 후 확정). 예상 범위(확정 아님, 2단계 착수 시 계약으로 못박는다):

- `app/presentation/api/app.py`의 `create_app()`을 역할별로 나눠, 고객
  API만 등록하는 진입점과 Composer+인증 API만 등록하는 진입점을 각각
  만든다(코드 복제 없이 같은 `build_router`/`composer_write_router` 등을
  재사용, 등록 여부만 다르게).
- 두 진입점을 각각 다른 실행 커맨드/이미지로 빌드 가능하게 한다
  (`Dockerfile`·`docker/compose.yml`·`infra/aws/`에 반영).
- Composer 가 적용한 설정이 customer-runtime 에 반영되는 방법을 명시적
  계약으로 정의한다(§2의 확인 사항 확정).
- `scripts/basement_manifest.py`의 `BASEMENT_COMPONENTS`는 이번엔 안
  쪼갠다 — Codex 자문 권고대로 "export profile/role" 개념만 후속 과제로
  남기고, 지금은 단일 export 유지.
- basement/cs 양쪽에 이미 만든 `tests/architecture` 경계 테스트가 계속
  통과해야 한다.

완료 기준: 두 진입점이 각각 독립적으로 기동, 고객 API 쪽에는 `/composer/*`·
`/auth/token`이 전혀 등록되지 않음을 실측 확인(라우트 목록 또는 실제 HTTP
404 로 증명), 전체 테스트 통과, `docs/evidence/`에 재현 기록.

## 5. 상태

★2026-08-18: 계획 등록. 1단계 착수 승인됨(사용자 지시: "1번하고 2번 하라는
소리야"). 1단계 완료·검수 후 2단계 계약을 작성해 이어서 진행한다.

★2026-08-19: **2단계의 진입점 분리 목표가 별도 경로(pip 패키지 분리,
v0.3.0)로 사실상 달성됐다** — 애초 이 계획이 예상한 "`create_app()`을
역할별로 나눈다"가, 그보다 큰 리팩터(`acop_basement`/`acop_composer`
패키지 분리)의 부산물로 이미 만들어졌다.

- `acop_basement.presentation.api.app:create_app()`은 이제
  `composer_write_router`/`composer_auth_router`를 **옵션 인자**로만
  받는다. 인자를 안 주면(`app = create_app()`, 모듈 레벨 인스턴스가 그
  형태다) `/composer/*`·`/auth/token`이 전혀 등록되지 않는다 — 이게 곧
  고객 전용(customer-runtime) 진입점이다.
- `app/entrypoint.py`(sample 로컬, "관리용 빌드")가 `acop_composer.api`/
  `acop_composer.auth`의 라우터를 가져와 그 인자에 얹는다 — 이게 곧
  composer-control 진입점이다.
- 두 진입점이 **같은 `create_app` 함수를 재사용**하고 코드를 복제하지
  않는다는 점에서 §4가 요구한 조건을 만족한다.

★2026-08-19(같은 날, 후속): **이미지(로컬 Docker) 경계 분리도 완료했다**
(`docs/handoff/_prompts/S-COMPOSER-DEPLOY-STAGE2-LOCAL.md`, Codex 구현 +
Claude 검수). §4가 "실배포 시점까지 보류"라고 판단했던 부분을 사용자가
지금 착수하도록 지시해 진행했다 —

- `Dockerfile.customer`(신규) — `app/`·`acop_basement/`·`config/`만
  COPY, `acop_composer/`는 COPY 안 함, 대상은
  `acop_basement.presentation.api.app:app`.
- 기존 `Dockerfile` — 관리용 이미지로 유지, `acop_composer/` 포함,
  대상은 `app.entrypoint:app`.
- `docker/compose.yml` — `app-customer`(8000)·`app-admin`(8001) 두
  서비스로 분리, `db` 공유.
- Docker 미설치 환경이라 **실제 빌드는 검증 못 했다** — Dockerfile
  정적 확인(COPY 경로 존재, `acop_composer` 미포함, `--workers 1`)과
  YAML 문법 확인까지만 했다. 실제 `docker build`/`docker compose up`
  검증은 Docker가 있는 환경에서 별도로 필요하다.

**아직 달성 안 된 부분**은 그대로다:

- `infra/aws/`는 이번에도 건드리지 않았다 — AWS 배포 대상 분리는
  여전히 "가정일 뿐 사용자 확답 전"(`CLAUDE.md` §5)이다.
- Composer 적용(`apply`) 후 customer-runtime 반영 방법(§2)은 여전히
  미정의.

이 검수 과정에서 별개의 실제 버그 2건도 발견해 고쳤다(같은 세션,
버그헌팅 라운드9 산출물 검수 중): `acop_basement/presentation/api/
app.py`의 `create_app()`이 controller·classifier를 둘 다 주입받아도
무조건 `app.composition`을 import해 basement 단독 설치 계약을 깨던 것,
`setup.py`가 `pyproject.toml`의 패키징 include/exclude를 조용히
무시하고 `tests`/`examples`/`scripts`까지 wheel에 포함시키던 것.
`setup.py`는 삭제했다(이미 기능이 죽어 있던 "개발 콘솔" 특수 처리
코드였다). 자세한 근거는 커밋 메시지와
`docs/reports/2026-08-19_S-COMPOSER-DEPLOY-STAGE2-LOCAL_리포트.md`
참고.

결론: **코드 경계 + 로컬 이미지 경계 모두 분리됐다. 남은 건 AWS/인프라
쪽 실제 배포 반영뿐이며, cs 실제 배포 계획이 나오는 시점에 재검토한다.**
