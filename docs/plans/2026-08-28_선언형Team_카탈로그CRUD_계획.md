## 0. 지금 상태 (실측 2026-08-28)

- `TeamConfig`는 `team_id`/`active`/`implementation_ref` 3개 필드뿐이고
  `extra="forbid"`다 — Team별 설정을 담을 자리가 없다
  (`acop_basement/core/project_config.py`).
- `_instantiate_team()`은 생성자 인자 개수를 보고 `(tools)` 또는
  `(tools, llm)`만 주입한다 — 선언별 파라미터를 넘길 경로가 없다
  (`app/composition.py:95-108`).
- `build_registry()`는 같은 capability를 두 Team이 주장하면 거부한다
  (`app/composition.py:134`). 따라서 **같은 구현체를 다른 이름으로 복제하는
  것은 지금 구조에서 실패한다** — 선언형 Team은 인스턴스마다 자기
  capability를 선언하므로 이 문제를 우회한다.
- Composer는 v2(`/current`·`/validate`·`/apply`)만 있다. `/toggle`도
  sample엔 없다(cs에만 있음).
- `KNOWN_IMPLEMENTATION_REFS`는 2개(`FeedbackAnalyticsTeam`,
  `PlaceholderTeam`).

## 1. 범위

**한다**
- `TeamConfig.parameters` 필드 추가(선언형 Team 전용 설정 자리).
- `DeclarativeTeamRuntime` — 범용 실행기. 한 번 배포하면 이후 새 Team은
  코드 없이 선언(데이터)만으로 만든다.
- `GET /composer/catalog` — UI가 고를 수 있는 구현 종류와 입력 스키마.
- `POST /composer/changes` — 인스턴스 단위 CRUD(create/update/delete/
  enable/disable), `dry_run`, `base_revision`, `reason`, idempotency.
- 응답에 `activation_state: pending_restart`를 **정직하게** 반환.

**안 한다(Phase 2)**
- 자동 재시작·무중단 반영(`/composer/activations`) — supervisor·worker
  구성이 미확정이라 지금 만들면 추측이 된다.
- 서명 플러그인 배포·SBOM·artifact installer.
- drain/tombstone 같은 삭제 안전장치 고도화 — 1차는 `disable` 후
  `delete` 2단계로만 한다.

## 2. 확정 스키마 (두 스트림이 공유하는 계약)

### 2.1 `TeamConfig` 확장

```python
class TeamConfig(BaseModel):
    model_config = ConfigDict(extra="forbid")
    team_id: str = Field(min_length=1)
    active: bool
    implementation_ref: str = Field(min_length=1)
    parameters: dict[str, Any] | None = None   # 선언형 Team 전용
```

`parameters`가 `None`이면 기존 코드형 Team이다(하위호환 — 기존
`project.yaml`이 그대로 유효해야 한다).

### 2.2 선언형 Team 파라미터

```yaml
- team_id: vip_return_review
  active: true
  implementation_ref: acop_basement.teams.declarative:DeclarativeTeamRuntime
  parameters:
    display_name: "VIP 반품 검토"
    capabilities: ["return.vip_review"]
    accepted_case_types: ["return"]
    required_context: ["case_state", "policy"]
    allowed_tools: ["read.policy"]
    knowledge_scope: ["return_policy"]
    max_steps: 4
    prompt_key: "declarative.vip_return_review"
```

### 2.3 ★보안 — grant ceiling (양보 불가)

Codex 교차검증이 지적한 권한 상승 경로를 막는다: `composer:write`를 가진
사람이 `allowed_tools`를 임의로 넓히면 그게 곧 도구 권한 부여가 된다.

- `acop_basement`에 **읽기 전용 tool allowlist 상수**를 둔다. 선언형
  Team의 `allowed_tools`가 이 집합의 부분집합이 아니면 **config 로드
  시점에 거부**한다(런타임이 아니라 로드 시점 — fail-fast).
- 선언형 Team은 1차에서 **`ActionProposal`을 만들지 않는다.** 조회·분류·
  초안 작성까지만이다. side effect가 필요하면 코드형 Team을 써야 한다.
- `prompt_key`는 문자열 참조만 허용한다. 프롬프트 원문을
  `project.yaml`에 넣지 않는다(감사·버전 원칙).

## 3. 두 스트림 (병렬, 파일 소유 분리)

| 스트림 | 소유 파일 | 계약 |
|---|---|---|
| A — 선언형 Team | `acop_basement/core/project_config.py`, `acop_basement/teams/**`, `app/composition.py`, 해당 테스트 | `S-DECLARATIVE-TEAM-RUNTIME.md` |
| B — 카탈로그·CRUD | `acop_composer/**`, 해당 테스트 | `S-COMPOSER-CATALOG-CHANGES.md` |

★B는 A가 아직 안 끝났을 수 있으므로 **선언형 Team 생성 테스트를 쓰지
않는다.** 기존 등록 구현체(`PlaceholderTeam` 등)의 CRUD만 검증한다. 두
스트림이 다 끝난 뒤 Claude가 통합 테스트(선언형 Team을 `/composer/changes`로
만들어 로더 통과 확인)를 직접 추가한다.

## 4. 완료 기준

- `python -m pytest tests/architecture -q` 통과 — 선언형 런타임이 basement
  순수성(도메인 어휘 0)을 지켜야 한다.
- 기존 `config/project.yaml`(parameters 없음)이 그대로 로드된다.

  (같은 구현체를 두 번 쓰는데도 capability 충돌이 안 난다는 게 핵심 증명).
- `allowed_tools`에 읽기 전용 밖의 tool을 넣으면 **로드가 실패**한다.
- `GET /composer/catalog`가 등록 구현체와 선언형 타입을 반환한다.
- `POST /composer/changes`의 `dry_run: true`가 파일을 안 건드린다.
- `base_revision` 불일치 → `409`, 스키마 위반 → `422`.
- 전체 회귀: `python -m pytest -q --ignore=tests/integration/rag`.
