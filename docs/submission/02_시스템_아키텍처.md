## Case 생명주기

Case 상태는 12개 상태를 계약 전이표로 관리하며, 상태 변경의 단일 진입점은 `transition_case()`다. 확인된 핵심 전이는 다음과 같다.

| 현재 상태 | 이벤트 | 다음 상태 | 비고 |
|---|---|---|---|
| classifying | classified | routing | 분류 성공 |
| classifying | classification_failed | escalated | 실패를 조용히 삼키지 않음 |
| routing | routed | running | Team 실행 진입 |
| running | approval_required | waiting_approval | 승인 필요 |
| waiting_approval | approved | resuming | 승인 후 재개 준비 |
| resuming | resumed | running | `completed`를 직접 적용하지 않음 |
| resuming | resume_failed | escalated | 재개 실패 |
| running | completed | resolved | 정상 종결 |
| running | ttl_expired | escalated | TTL 만료 |
| 모든 비종결 상태 | cancelled | cancelled | 종결 상태 |

계약에는 12개 상태 전체와 `cancelled` 종결성이 정의되어 있다. 이 제출본의 근거 파일에서 이름이 직접 확인되지 않는 나머지 상태명은 임의로 보충하지 않았으며, `미측정`으로 둔다. 상태표 전체의 자동 대조 자체는 DoD-02에서 통과했다.

## 불변성과 메시징

- optimistic concurrency는 `expected_version` 조건부 UPDATE로 구현한다. 같은 버전의 두 요청은 1건 성공·1건 `StateConflict`가 된다.
- `case_events`는 append-only이며 `(case_id, aggregate_version)` UNIQUE로 중복 버전을 막는다.
- `replay_case()`는 같은 reducer를 접어 projection의 status·version을 재현한다.
- outbox insert와 projection 변경은 한 transaction에 묶고, `UNIQUE(topic, dedupe_key)`로 중복 전달을 막는다. 따라서 outbox는 이 시스템에서 Message Broker의 영속·재시도 경계로 재정의된다.

## Context Broker

입력 예산은 정확히 12,000 token이며 섹션 예산은 `1800/2400/2400/3600/1200/600=12000`이다. 초과 팩은 거부하고 `degraded`일 때 `omissions`를 요구한다. 절삭 순서는 실제 관측 근거가 확인된 `similar_cases` 우선이며, 전체 절삭 동작의 종단 관측은 `미측정`이다.
