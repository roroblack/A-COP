# 설계 검토 의뢰 — 제작 단계 모듈 구성기(Composer) GUI

## 0. 이건 코드 작성이 아니라 **설계 검토**다

★**코드를 만들지 마라.** 이번 산출물은 **설계 문서 하나**다.
근거는 반드시 **`파일:줄번호`** 로 대라. 추측을 사실처럼 쓰지 마라.

## 1. 요구사항 (사용자 원문 취지)

지금 있는 `/ui/admin` 은 **운영용 조회 화면**이다. 필요한 건 그게 아니라
**제작 단계에서 프로젝트 구성을 짜는 GUI** 다.

- 팀 회의 중 Agent Team 이 **3개였다가 2개로 줄거나 4개**가 될 수 있다
- 모듈을 추가하면 **실제 배포될 프로젝트 구성에 그 자리가 생기고**,
  세부 구현은 나중에 담당 팀이 채운다
- LangGraph·Graph DB·GraphStore 같은 기능이 **필요 없다 싶으면 빼는** 구성
- 즉 **넣을 수 있는 모듈 / 뺄 수 있는 모듈**을 우리가 알고 있으니 그걸 도구로 만든다

## 2. 검토할 것

### 2-1. ★현재 코드에서 "뺄 수 있는 것" 과 "뺄 수 없는 것" 을 가려라

저장소를 실제로 읽고 **근거와 함께** 분류하라.

| 구분 | 무엇이 여기 속하나 (당신이 채워라) |
|---|---|
| **필수 (뺄 수 없음)** | 예: Case lifecycle·`transition_case()`·계약 모델? 왜 뺄 수 없는지 |
| **선택 (뺄 수 있음)** | 예: GraphStore·A2A Executor·VOC 배치·MCP? 빼면 무엇이 깨지나 |
| **교체 가능 (Port 있음)** | 예: LocalTeamExecutor↔A2ATeamExecutor |
| **개수 가변** | Agent Team 모듈 |

★각 항목마다 **"지금 빼면 어디가 깨지는가"** 를 `파일:줄번호` 로 답하라.
빼도 되는지 **실제로 import 관계를 따라가서** 판단하라. 짐작하지 마라.

### 2-2. 구성 산출물의 형태

GUI 가 만들어내야 하는 것은 무엇인가? 후보를 비교하고 **하나를 권고**하라.

1. **선언 파일**(예: `config/project.yaml`)을 만들고 `composition.py` 가 그걸 읽는 방식
2. **코드 생성**(scaffold) — 선택한 모듈의 디렉터리·`__init__.py`·manifest 뼈대를 실제로 만든다
3. 둘 다 (선언 + 뼈대 생성)

각 방식의 **장단점과 이 저장소에 맞는 이유**를 적어라.
★현재 `app/composition.py` 가 하는 일을 먼저 읽고 판단하라.

### 2-3. Team 모듈 추가 시 실제로 필요한 것

새 Team 하나를 추가할 때 **최소 무엇이 있어야 동작하는가?**
- `TeamManifest` 의 필수 필드
- `TeamModule` Protocol 이 요구하는 것
- Registry 등록
- tool allowlist·prompt·knowledge_scope

★GUI 가 **뼈대만 만들고 세부는 팀이 채운다**면, 뼈대에 무엇이 들어가야
"등록은 되지만 아직 미구현" 상태로 안전하게 존재할 수 있나?
(예: `active=False` 로 두기? `NotImplementedError` 를 던지기?)
★**미구현 Team 이 라우팅되어 Case 가 죽는 일이 없어야 한다.** 그 방법을 제안하라.

### 2-4. 선택 기능을 뺐을 때의 안전장치

`GraphStore` 를 뺐는데 어딘가가 그걸 부르면 어떻게 되나?
- Port 가 없을 때 **명시적 오류**인가, 조용한 폴백인가
- ★이 프로젝트는 **폴백 금지**(`RULE.md` §3.2)다. 뺀 기능을 부르면
  명확히 실패해야 한다. 그 설계를 제안하라

### 2-5. 위험과 반대 의견

★**이 GUI 를 만들지 않는 편이 나은 이유**도 적어라.
- 구성이 코드와 어긋날 위험
- 생성된 뼈대가 방치될 위험
- MVP 범위(v5 §3)를 넘는지
