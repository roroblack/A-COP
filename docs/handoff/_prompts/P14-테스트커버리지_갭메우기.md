## 3. 만들 것 — 갭 5개

### 3-1. `console/composer.py:67-73` — 토큰 발급 실패의 5xx/기타, malformed JSON
`tests/test_composer.py`에 추가:
- `/auth/token`이 500을 내는 경우 → 지금 코드가 어떤 `status`를 내는지 확인하고
  그 실제 동작을 단언해라(추측하지 말고 코드를 먼저 읽어라)
- `/auth/token`이 200인데 `access_token` 키가 없는 응답을 보내는 경우
- `/auth/token`이 200인데 본문이 JSON이 아닌 경우

### 3-2. `console/composer.py:88-99` — 401/403/409/422 외의 기타 HTTP 오류
- 예: `/composer/current`가 500·503을 내는 경우 어떤 `status`로 분류되는지

### 3-3. `console/db.py:70-161` — DB 성공/실패 경로
`tests/test_connections.py`에 추가(실제 로컬 Postgres가 없어도 되게, 기존
패턴처럼 연결 실패·잘못된 스키마 케이스는 그대로 하되):
- `tenant_id` 필터가 실제로 SQL WHERE 절에 들어가는지 — 소스 문자열 검사로
  확인해도 된다(`test_trace_joins_case_events_by_case_id_not_run_id`와 같은 패턴)
- `limit` 파라미터가 쿼리에 실제로 전달되는지
- 상태 테이블(`_state_counts`)의 개별 조회가 실패했을 때 `__error__` 키로
  보고되는지(이미 있는 로직 — 실제 실패를 어떻게 흉내낼지는 db.py를 읽고 판단해라.
  예: 존재하지 않는 테이블명으로 SQL을 바꿔치기하는 monkeypatch보다는, 함수
  구조상 단위 테스트 가능한 지점을 찾아라. 어렵다면 최소한 정상 동작 경로라도
  실제 DB 없이 검증 가능한 부분만 다뤄라)
- `read_trace`가 존재하지 않는 run_id(유효한 UUID 형식)에 대해 실제 DB
  연결 실패 시 "연결하지 못했다"로 응답하는지(이미 있는 패턴 재사용)

★**실제 로컬 Postgres 연결이 필요한 부분은 억지로 만들지 마라** — DB 없이도
돌아가는 CI를 깨면 안 된다. 안 되면 그 갭은 "DB 필요"라고 리포트에 남기고 스킵해라.

### 3-4. `console/readers.py:81-250` — 파일 리더 함수
`tests/test_readers.py`에 추가:
- `read_guardrails()` — 정상 파일 읽기, 파일 없음, YAML 파싱 실패 각각
- evidence 파일을 읽을 수 없는 경우(권한 없음 시뮬레이션이 어려우면 존재하지
  않는 디렉터리로 대체해도 된다)

  건너뛴 사실이 카운트에 남는지도 확인해라(이 프로젝트 원칙 — 조용한 스킵 금지)

### 3-5. `console/profiles.py`·`README.md` — CI 토큰 주입
이건 테스트가 아니라 **문서화 갭**이다. `README.md`에 CI(GitHub Actions 등)에서
`CONSOLE_INTROSPECTION_TOKEN`/`CONSOLE_COMPOSER_ISSUER_SECRET`을 어떻게 주입하는지
한 단락 추가해라(예: repository secrets → env). ★실제 `.github/workflows/*.yml`을
만들라는 게 아니다 — 이 저장소엔 아직 CI 파이프라인 자체가 없다. 파이프라인을
새로 만드는 건 이 작업 범위 밖이다. 문서에 "지금은 수동, CI 붙일 때 이렇게 주입한다"
정도만 적어라.
