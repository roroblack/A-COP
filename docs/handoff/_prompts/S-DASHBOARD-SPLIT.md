# 검토 의뢰 — 개발 대시보드를 별도 프로그램으로 분리할 것인가

## 0. 제안

사용자 제안:

> 배포 단계가 될 때 개발 대시보드는 모듈화돼서 **완전히 제거 가능**해야 한다.
> 점검·보수 때만 우리 로컬에서 다시 붙여서 작업한다.
> 즉 Composer 가 있는 이 대시보드를 **별도 프로그램**(`final_project_dashboard`)으로 만들어
> 릴리스가 나가도 붙여서 쓸 수 있는 구조로. cs / sample 분리한 것처럼.

## 1. 현재 상태

```
/ops/**   고객사 대시보드   ops_ui 모듈       — 납품되는 제품
/ui/**    개발 콘솔         console_ui 모듈   — 대시보드·quality·experiments·runs·admin
/ui/composer                composer_ui 모듈  — 제작 구성기
```

★**이미 토글로 완전히 끌 수 있다.** `console_ui: false` → `/ui/*` 전부 404,
`/ops/*` 는 200. 경계 테스트가 강제한다(`tests/e2e/test_audience_boundary.py`).
현재 **311 passed**.

| `docs/evidence/DoD-*.md` | 판정·재현·실제 출력 |
| `eval/reports/*.jsonl` | run·arm·provider·ablation |
| DB | `agent_runs`·`team_tasks`·`llm_calls`·`case_events` |
| `app/composition.py` | 실제 조립 결과(admin) |

## 2. 웹 리서치 요약

**control plane / data plane 분리** — 두 평면을 분리하면 공격 표면이 줄고 장애가 격리된다.
데이터 평면이 뚫려도 제어 평면(메타데이터·과금)으로 못 넘어간다.

**monorepo vs polyrepo** — 여러 곳이 같은 계약에 의존하면 **모노레포가 드리프트를 막는다.**
계약이 한 곳에 있어 깨지는 변경이 리뷰에서 걸린다. 반대로 폴리레포는 모듈성을 주지만
조정 비용이 든다. 최악은 **"분산 모놀리스"** — 저장소는 나뉘었는데 **함께 배포해야 하는** 상태.

## 3. ★쟁점

분리에 찬성하는 근거:
- 릴리스 산출물에서 콘솔 코드가 **아예 없다** (토글 off 는 코드가 남는다)
- 공격 표면 축소 — Composer 는 **선언을 쓰는** 화면이다
- 여러 프로젝트(sample·cs·다음 것)에 **같은 대시보드 하나**를 붙일 수 있다

분리에 반대하는 근거:
- ★대시보드는 위 §1 의 **5가지 내부 형식**에 의존한다.
  `project.yaml` 스키마 · DoD evidence 마크다운 형식 · eval jsonl 필드 ·
  DB 테이블 · composition 함수. 저장소가 갈리면 **이것들이 조용히 드리프트**한다
- 지금 규모에서 **분산 모놀리스** 가 되기 쉽다 — 함께 고쳐야 하는데 저장소만 둘
- 토글로 이미 제거된다. 분리의 **추가 이득이 정확히 무엇인지** 따져야 한다
