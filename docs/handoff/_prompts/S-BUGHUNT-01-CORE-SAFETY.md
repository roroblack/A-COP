# S-BUGHUNT-01-CORE-SAFETY — 안전 핵심부 버그 사냥 (리포트만, 수정 금지)

## 배경 (읽지 않아도 되는 맥락)

CLAUDE.md §0 이 이 저장소에서 가장 무겁게 취급하는 것: 근거 없는 확답, 승인 없는
side effect, 상태를 `transition_case()` 밖에서 바꾸는 것, tenant 격리 누락.
지금 당장 사용자 입력 없이는 못 여는 작업(judge 라벨·파인튜닝·AWS 확정)이 다
막혀 있어서, 그 대신 **이미 있는 코드에서 버그를 찾는다.**

## 이번에도 다르게 한다 — ★고치지 않는다, 보고만 한다

사용자가 자리에 없어 산출물을 대신 검수해야 한다(`RULE.md` §3.6-3). 이 스트림은
**아무 파일도 수정하지 않는다.** 발견한 것을 근거·재현 명령과 함께 리포트로만
낸다. 수정은 Claude 가 검수 후 직접 하거나, 후속 스트림으로 별도 발주한다.

## 스캔 범위 (이번 라운드는 이 다섯 파일만 — 넓게 안 본다)

1. `app/core/transition.py` — 상태 전이 순수 함수. `customer_cases` 를 바꾸는
   유일한 문
2. `app/core/verification.py` — 제안의 식별자·금액을 실행 전 대조하는 순수 로직
3. `app/application/proposal_guard.py` — 승인 직전 재조회 검증
4. `app/infrastructure/messaging/worker.py`, `app/infrastructure/messaging/outbox.py`
   — at-least-once 배달·idempotency
5. `app/presentation/api/cases.py` — tenant/customer 격리가 걸리는 REST 진입점

## 찾을 것 — 진짜 버그만, 스타일 지적 아님

각 후보에 대해 **구체적인 실패 시나리오**를 요구한다:

- 어떤 입력/상태에서
- 무엇을 잘못 하는지 (틀린 값을 반환·상태를 잘못 바꿈·격리를 새게 함·예외를
  삼킴·idempotency 를 깨뜨림 등)
- 왜 기존 테스트가 이걸 못 잡는지 (테스트에 없는 경계값이라거나, mock 이 실제
  분기를 안 태운다거나)

특히 이 패턴을 우선 찾는다 — 이 저장소에서 실제로 여러 번 나왔던 것들이다:
- `except: continue`/`except Exception: pass` 처럼 실패를 조용히 삼키는 코드
  (RULE.md §3.2 폴백 금지 위반)
- 두 tenant 의 데이터가 같은 쿼리에서 섞일 수 있는 조건 누락
- 트랜잭션 경계가 실제로 원자적이지 않은 곳 (일부만 커밋될 수 있는 경로)
- 동시성 가정이 실제로는 깨지는 곳 (lock 없이 read-then-write 하는 패턴)
- 계약(`docs/handoff/01`)과 구현이 조용히 어긋난 필드

**"이렇게 하면 더 나을 것 같다" 류의 스타일 제안은 적지 않는다.** 실제로
틀린 것만 적는다. 확신이 없으면 "의심됨 — 확인 필요"로 표시하고 왜 의심되는지
적는다. 억지로 개수를 채우지 않는다 — 못 찾으면 못 찾았다고 적는다.
