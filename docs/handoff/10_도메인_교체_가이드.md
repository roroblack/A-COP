# 10 — 도메인 교체 가이드 (basement → 다른 CS 플랫폼)

> 이 저장소는 **범용 basement** 다. 어떤 CS 플랫폼 요청이 와도 대응 가능한 것이 목표다.
> 실제 서비스(예: `final_project_cs`)는 basement 를 **`pip install acop_basement`**
> 로 받아서 자기 도메인만 채워 만든다(v0.3.0, 2026-08-19 — 그 전엔 저장소를
> 통째로 복사하는 모델이었다. `docs/handoff/15`가 배포 계약을 규정한다).
>
> Composer 쓰기 채널은 별도 선택 패키지 `acop_composer` 다 — cs 처럼 릴리스
> 대상은 이걸 설치하지 않는다. "관리용 빌드"만 얹는다.
>
> 이 문서는 **무엇을 갈아 끼우면 되는지**만 적는다.
> 여기 없는 파일을 고치고 있다면, 그건 basement 가 도메인을 물고 있다는 뜻이다.

---

## 0. 경계

| 층 | 도메인을 아는가 | 소속 | 복사/설치 후 |
|---|---|---|---|
| `acop_basement/{core,domain,application,infrastructure,presentation,tools,introspection}/**` | ★**모른다** | pip 패키지 `acop_basement` | 손대지 않는다 — `pip install`로 받는다 |
| `acop_composer/**` | 모른다(도메인 값은 안 다루지만 basement 설정을 쓴다) | 별도 pip 패키지 `acop_composer` | 릴리스 대상은 설치 안 함. 관리용 빌드만 설치 |
| `app/modules/**` | 안다 | 이 저장소 로컬(product) | **갈아 끼운다** |
| `app/composition.py`, `app/entrypoint.py` | 안다(조립만) | 이 저장소 로컬 | 참고해서 자기 프로젝트용으로 새로 쓴다 |
| `config/**` | 안다 | 이 저장소 로컬 | 갈아 끼운다 |
| `config/migrations/002_domain_*.sql` | 안다 | 이 저장소 로컬 | 갈아 끼운다 |
| `knowledge/**` · `eval/datasets/**` · `scripts/seed*.py` | 안다 | 이 저장소 로컬 | 갈아 끼운다 |

★이 경계는 **테스트가 강제한다** — `tests/architecture/test_basement_is_domain_free.py`.
`acop_basement/**`에 도메인 어휘가 들어오면 실패한다. 예외 목록은 3개를 넘을 수 없다.

## 1. 갈아 끼우는 것 — 순서대로

### 1-1. 도메인 테이블

```
config/migrations/002_domain_customer_ops.sql
  → 002_domain_<your>.sql
```

현재 4개(`subscriptions`·`payments`·`entitlements`·`incidents`).
쇼핑몰이면 `orders`·`order_items`·`shipments`·`returns` 가 온다.

★`acop_basement/infrastructure/db/migrations/001_schema.sql`(core 14 테이블)은
**손대지 않는다** — 이건 pip 패키지 안에 있다. `acop_basement.infrastructure.db
.migrate`가 core 마이그레이션(패키지 안)과 domain 마이그레이션
(`config/migrations/`, product 쪽)을 파일명 순서로 함께 적용한다. 도메인
마이그레이션이 basement 패키지 **안**에 있으면 안 된다 — 2026-08-19에
바로 이 실수(`002_domain_customer_ops.sql`이 `acop_basement/` 안에
실려 나간 것)를 검수에서 잡아 고쳤다.

### 1-2. 대조 선언 (v7 §9-E)

```
app/modules/customer_ops/verification_policy.py
```

```python
CUSTOMER_OPS_POLICY = VerificationPolicy(
    references={"order_id": "orders", "shipment_id": "shipments"},
    quantities=(QuantityRule("refund_amount", "order_id", "total_cents", scale=Decimal(100)),),
    opaque=frozenset({"coupon_id"}),      # 아직 대조 수단이 없는 것
    ignored=frozenset({"reason", "template"}),
)
FACT_QUERIES = (("orders", "SELECT order_id, total_cents, status FROM orders "
                           "WHERE tenant_id=%s AND customer_id=%s",
                 ("order_id", "total_cents", "status")),)
```

★**`opaque` 에 넣는다는 것은 "확인 못 하니 거부한다" 는 선언이다.**
귀찮다고 빼면 검사 없이 통과한다 — 조용히 새는 쪽이 더 위험하다.

★**선언에 없는 필드는 자동으로 거부된다.** 새 필드를 조용히 흘려보내지 않기 위해서다.
`VerificationPolicy`·`QuantityRule`은 `acop_basement.core.verification`에서
import한다 — basement 는 규칙 엔진만 갖고, 어휘는 이 파일(product 로컬)이 갖는다.

### 1-3. Agent Team

```
app/modules/customer_ops/*.py   (feedback_team.py 가 지금 유일한 production 예시다)
config/project.yaml  →  teams: [...]
```

Team 개수는 가변이다. `implementation_ref`를 import 할 수 없으면 등록이
거부되므로 "선언은 켰는데 기동하면 죽는" 상태가 안 생긴다
(`acop_basement.core.project_config.load_project_config`). ★`/ui/composer`
HTML 폼은 2026-08-18에 인증 부재가 드러나 완전히 제거됐다 — 릴리스 이후
구성 관리는 `acop_composer`(별도 선택 패키지, `docs/handoff/13`)의
`POST /composer/*` API 로만 한다. cs 처럼 Composer 없이 배포하는 대상은
`config/project.yaml`을 직접 편집하고 재배포하거나, 관리용 빌드가 붙는
`/composer/*`를 별도로 켠다.

### 1-4. 지식 코퍼스

```
knowledge/**            현재 25문서 / 300청크
scripts/check_corpus.py 인수 게이트 — ★그대로 쓴다
```

★게이트는 basement 다. 청크 길이·중복률·게이밍 패턴 검사는 도메인과 무관하다.
`python -m scripts.check_corpus` 가 통과해야 적재한다.

### 1-5. 평가 데이터

```
eval/datasets/golden.jsonl          60건
eval/datasets/holdout.jsonl         20건 (★보존 — 프롬프트 수정에 쓰지 않는다)
eval/datasets/attack_fixtures.jsonl 15건 (공격)
```

★`attack_fixtures.jsonl` 은 **도메인 어휘를 담지만 구조는 같다.**
`expect_block` 이 정답이고 판정은 실제 방어를 돌려 구한다 — 순환이 아니다.
새 도메인의 "지어낸 식별자 / 상한 초과 수량 / degraded / 인젝션" 을 채운다.

### 1-6. 시연 데이터

```
scripts/seed.py             기본 시드
scripts/seed_demo_cases.py  발표 시나리오 2건 (case_id 는 uuid5 로 고정)
```

## 2. 갈아 끼우지 않는 것 (basement, `acop_basement` 패키지 안)

| 무엇 | 왜 |
|---|---|
| Case lifecycle · `transition_case()` | 상태 변경의 단일 진입점. 도메인 무관 |
| 계약 모델 (`contracts.py`) | `extra='forbid'`, evidence 의무 |
| Team Registry · `allowed_tools` 강제 | |
| Context Broker (12,000 토큰) | |
| **대조 규칙 엔진** (`acop_basement/core/verification.py`) | 어휘는 선언에서 온다 |
| Controller · WAIT/RESUME · 승인 | |
| Outbox (원자성·dedupe·`unknown`) | |
| Ports 6종 + `project.yaml` 조립 | |
| 운영 UI 4화면(`/ops/**`) | 상태 색·근거 표시는 도메인 무관 |
| A2A (Card·input-required·취소·인증) | |
| 방어 지표 5종 (`eval/defense_metrics.py`) | 분모 규칙은 도메인 무관 |

Composer(`acop_composer`, 별도 패키지)도 도메인을 모른다 — 다만 basement 와
분리 배포되는 이유가 다르다: 관리 기능이라 릴리스 대상엔 안 실린다
(`docs/handoff/13`).

## 4. 이 문서가 생긴 이유

2026-08-16 에 `verification.py`(당시 `app/core/verification.py`, 지금은
`acop_basement/core/verification.py`)가 구독·결제 어휘를 Core 에 박고
있었다. 그 상태로 쇼핑몰에 복사했다면 **`order_id` 가 "확인 불가 → 자동
거부"** 에 걸렸을 것이다. 그 도메인의 가장 중요한 식별자가 basement 의
거부 목록에 있는 정반대 상황이다.

v7 §9-E 표가 `payment_id`·`amount` 를 **예시로** 든 것을 스펙으로 읽은 탓이었다.
계획서의 예시는 그 계획서의 도메인일 뿐이다 —
**basement 에는 메커니즘만 올라가고, 어휘는 선언으로 내려간다.**

★2026-08-19에 같은 실수가 다른 형태로 재발했다 — `002_domain_customer_ops.sql`
(도메인 마이그레이션)이 `app` → `acop_basement` 리네임 과정에서 basement
패키지 안에 그대로 실려 나갔다. `config/migrations/`로 옮겨 고쳤다(§1-1).
**"검사하지 않는 경계는 지켜지지 않는다"**를 이번에도 확인했다 —
`tests/architecture`가 `acop_basement/infrastructure/db/migrations/`
디렉터리 안의 파일명 패턴까지는 보지 않아서, 이 위반은 사람이 직접
`find`로 찾아야 했다.

## 5. basement SemVer 판정 기준

배포 버전은 `pyproject.toml`의 `project.version`을 기준으로 하며, 변경의
호환성에 따라 다음처럼 판정한다.

| 등급 | 판정 기준 |
|---|---|
| patch | 기존 계약을 유지하면서 basement 내부 구현의 버그를 수정한다. |
| minor | 기존 계약과 호환되는 기능·Port·registry ID를 추가한다. |
| major | `contracts.py`의 `TeamTask`·`TeamResult`·`TeamManifest` 필수 필드, Port 인터페이스, registry ID의 제거·재명명, import 경로(패키지명) 변경, 또는 config schema를 호환되지 않게 변경한다. |

`app/modules/**`, `config/**`, `knowledge/**`, 평가 데이터의 변경은 basement SemVer에
자동으로 포함하지 않는다. 이들은 각각 `domain_profile_revision` 또는 데이터셋의 별도
revision으로 기록한다. 즉 `basement_version`과 domain/data revision을 같은 숫자로
올리지 않는다. `acop_composer`는 별도 패키지이므로 자체 버전을 가질 수 있다(아직
버전 분리는 안 함 — basement 와 같은 저장소 버전을 공유한다).

릴리스마다 루트 `CHANGELOG.md`에 실제 `git log --oneline`을 근거로 변경을 기록한다.
Git tag 생성과 배포 메타데이터 발행은 이 문서의 범위가 아니며, 릴리스 담당자가
검토 후 수행한다.
