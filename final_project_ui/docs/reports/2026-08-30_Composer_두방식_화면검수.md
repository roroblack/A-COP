## 결과 — 통과

두 방식 다 화면이 온전히 그려졌다. 같은 화면 코드에 **주소와 헤더만 다르다**:

- 방식 배지 · `revision` · 카탈로그(고를 수 있는 구현 3종) · 지금 선언된 Team ·
  모듈 6종 · Port 3종 · Team 표 · 실행 순서 9단계 · 컴포넌트 7종 전부 표시
- `central` 은 화면 맨 위에 **어느 대상을 바꾸는지**(`demo-customer-42`) 를 밝힌다

### 쓰기가 실제로 되는가 — 통과

화면이 나오는 것과 화면에서 고칠 수 있는 것은 다른 주장이라 따로 확인했다.
중앙 방식 콘솔의 카탈로그 폼으로 선언형 Team `vip_return_review` 를 만들었다:

```
[전] 중앙 revision=ea58fc7efe63 teams=['feedback_analytics']
[전] 대상 project.yaml sha=ab396bceca2c
[후] 중앙 revision=6a5f57824887 teams=['feedback_analytics', 'vip_return_review']
[후] 대상 project.yaml sha=ab396bceca2c      ← ★그대로다
```

★이 설계의 핵심 주장이 여기서 증명된다 — **중앙 방식에서 UI 는 대상 파일을 쓰지 않는다.**
화면은 `create 적용됨 — vip_return_review (revision 6a5f57824887) · ★아직 반영 전입니다 —
대상을 재시작해야 실제로 적용됩니다` 를 정직하게 표시했다.

## ★검수에서 잡은 결함 1건 — 배지의 태그가 글자로 나갔다

`_composer_mode_badge()` 가 `note(f"... 대상 <code>{esc(id)}</code> ...")` 였다.
`note()` 는 **본문 전체를 이스케이프한다**(그게 안전한 기본값이다). 그래서 운영자 화면에
`<code>demo-customer-42</code>` 가 **글자 그대로** 보였다.

★문구 검사(`"demo-customer-42" in body`)는 **통과하고 있었다** — 대상 이름이 문자열로는
들어 있었기 때문이다. 기존 테스트
`test_central_mode_shows_which_deployment_is_being_changed` 도 통과했다.
**눈으로 봐야 잡히는 종류였다.**

고친 뒤 남긴 것:

- `console/web.py` — 배지에서 태그 제거 + 왜 그랬는지 주석
- `tests/test_composer_web.py::test_the_mode_badge_does_not_leak_escaped_markup` —
  배지 구간에 `&lt;` 가 있으면 실패. ★고치기 전 코드로 되돌려 **실제로 실패하는 것을 확인**했다
  (같은 실행에서 옛 단언 2건은 그대로 통과 — 검사하는 척하는 검사가 아니다)
- 캡처 스크립트에도 태그 유출 검사를 넣었다

`console/web.py` 전체를 훑어 `note()` 안에 태그가 남은 곳이 더 있는지 봤다 — 1건
(`/project?path=<프로젝트 경로>`) 은 자리표시 글자라 이스케이프가 맞다.

- 중앙 저장소의 `demo-customer-42` 와 방금 만든 `vip_return_review` 는 **검수용 데이터**다.
  지울 때는 `project_configs` 에서 해당 행을 지운다.
