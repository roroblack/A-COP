## API 오류코드와 재시도 표 운영 장면 1
API 응답은 HTTP 상태와 서비스 고유 오류를 함께 읽는다. 진단은 계정 식별, 실패 시각, 요청 경로를 확인하는 순서로 진행한다. 성공 로그가 있다고 해서 현재 세션도 정상이라고 단정하지 않으며, 토큰 scope와 브라우저 세션을 따로 점검한다. 같은 증상이 2회 재현되면 원인 후보를 좁힌다. 실패 시각이 없는 문의는 서버 로그와 대조할 수 없으므로 먼저 고객이 본 화면의 시간을 확인한다. 종료 시각과 확인자를 남겨 같은 진단을 반복하지 않는다. 확인자를 남긴다. 종료 확인자를 적는다.

## API 오류코드와 재시도 표 운영 장면 2
400 계열은 요청 형식과 입력 범위를 먼저 확인한다. 401은 토큰 만료나 서명 불일치부터 확인하고, 403은 인증 뒤 scope 부족 여부를 본다. 두 응답을 같은 재로그인 안내로 합치지 않으며, 비밀값은 로그나 고객 답변에 남기지 않는다. 새 토큰 발급 뒤에도 동일하면 권한 원장으로 넘긴다. 401과 403을 구분한 뒤에도 비밀값을 요구하지 않고 토큰 만료 시각과 필요한 scope 이름만 확인한다. 진단에 사용한 요청 시각과 결과 코드를 함께 기록한다. 요청 시각을 적는다. 실패 시각을 적는다.

## API 오류코드와 재시도 표 운영 장면 3
401은 토큰 만료나 서명 문제를 점검하고 비밀키 재전송을 요구하지 않는다. 400 오류는 요청 형식, 필수 필드, 값의 범위를 순서대로 검사한다. 서버가 반환한 오류 메시지를 그대로 신뢰하지 않고 trace와 요청 시각을 연결한다. 수정 가능한 입력만 다시 보내며, 유효하지 않은 값을 반복 제출하지 않는다. 입력 수정 후 재호출할 때는 변경한 필드만 표시해 서버가 새 요청을 원래 요청의 반복으로 오해하지 않게 한다. 인증 실패와 권한 부족을 다른 해결 경로로 안내한다. 해결 경로를 나눈다. 응답 유형을 나눈다.

## API 오류코드와 재시도 표 운영 장면 4
403은 인증 성공 뒤 scope나 역할이 부족한 경우로 분류한다. 404는 경로와 tenant 범위를 먼저 확인한다. 자료가 없다는 응답만으로 삭제를 결론내리지 않고, 조회 권한과 최신 이벤트를 대조한다. 다른 고객의 식별자를 시험 요청에 사용하지 않으며, 확인 결과는 90일 감사 범위에 맞춰 보관한다. 404 조사에서는 경로의 철자와 tenant 범위를 각각 확인하며 자료 삭제 여부는 원장 담당자의 확인 뒤에 말한다. 수정한 입력만 재검증해 같은 잘못을 반복하지 않는다. 필드만 수정한다. 수정 필드를 남긴다.

## API 오류코드와 재시도 표 운영 장면 5
404는 경로와 테넌트 범위를 확인하며 자료가 없다고 즉시 삭제로 해석하지 않는다. 409는 동시 수정이나 idempotency 충돌 가능성을 분리해 본다. 현재 상태를 읽은 뒤 필요한 경우에만 새 버전으로 요청하고, 같은 키로 다른 금액을 보내지 않는다. 결제 명령은 상태 조회 없이 자동 재전송하지 않는다. 409가 나면 현재 버전과 요청 버전을 비교하고 충돌 해결 전에는 같은 변경을 여러 번 보내지 않는다. 자료 부재와 접근 거절을 다른 결과로 구분한다. 결과를 구분한다. 조회 결과를 보존한다.

## API 오류코드와 재시도 표 운영 장면 6
409는 동시 수정이나 idempotency 충돌을 나타낼 수 있다. 429 응답에서는 Retry-After 값을 우선 적용한다. 값이 없을 때도 짧은 간격의 무한 반복을 하지 않고 지수형 간격을 사용하며, 재시도 가능 작업과 결제·해지처럼 중복 위험이 있는 작업을 구분한다. 재시도 횟수는 요청별로 세어야 한다. 429 재시도는 응답 헤더의 시간을 넘기지 않으며 사용자가 여러 탭에서 동시에 호출하는 상황도 함께 점검한다. 충돌 해결 전에는 쓰기 요청을 자동 반복하지 않는다. 현재 버전을 읽는다. 현재 버전을 확인한다.

## API 오류코드와 재시도 표 운영 장면 7
429는 Retry-After 값과 호출량을 존중한다. 500 계열은 요청 시각, trace, 서버 응답을 묶어 조사한다. 같은 호출을 무한 반복하지 않고 20초 간격의 제한된 재시도만 허용하며, 쓰기 작업은 idempotency 키가 없으면 자동화하지 않는다. 복구 뒤 실제 결과를 조회해 중복 생성 여부를 확인한다. 500 뒤의 결과가 불명확하면 실패로 단정하지 않고 조회 API로 생성 여부를 확인한 후에만 다시 실행한다. 대기 시간이 끝난 뒤에도 같은 오류면 담당 큐로 넘긴다. 대기 후 재평가한다. 대기 시각을 기록한다.

## API 오류코드와 재시도 표 운영 장면 8
500 계열은 같은 요청을 무한 반복하지 않고 요청 시각과 trace를 남긴다. 브라우저 문제와 서버 문제를 나눌 때는 다른 세션이나 읽기 전용 경로를 비교한다. 캐시 삭제는 마지막 수단으로 두고, 삭제 전에 현재 세션과 토큰 만료 시각을 기록한다. 고객에게 비밀번호나 전체 인증 헤더를 요청하지 않는다. 브라우저와 서버를 비교할 때 고객의 인증 정보를 복사하지 않고 오류 코드와 발생 시각만 전달받는다. 결과가 불명확한 쓰기는 조회로 상태를 확인한 뒤 결론낸다. 조회 뒤 결정한다. 실행 여부를 대조한다.

## API 오류코드와 재시도 표 운영 장면 9
재시도는 읽기 요청이나 안전한 idempotency 키가 있는 쓰기에만 적용한다. 여러 사용자가 같은 오류를 겪으면 incident 후보로 올리고 단일 계정 진단을 중단한다. 오류 코드, 시작 시각, 영향 범위를 묶어 담당 팀에 전달하며, 20초 안에 응답이 없다는 사실만으로 원인을 추정하지 않는다. 공통 오류 후보는 영향 계정 수와 공통 trace 패턴을 묶어 incident 담당자에게 넘긴다. 세션 비교에는 고객 비밀값을 포함하지 않는다. 비밀값은 제외한다. 민감값을 제외한다.

## API 오류코드와 재시도 표 운영 장면 10
결제와 환불 명령을 키 없이 재시도하지 않는다. API 재전송은 읽기 작업과 상태 변경 작업을 구분한다. 읽기는 최신 결과를 다시 조회할 수 있지만 결제나 환불은 승인 여부를 확인한 후 한 번만 실행한다. 응답이 끊긴 경우에도 서버 trace와 idempotency 상태를 먼저 확인한다. 상태 변경 API는 응답 본문보다 원장 결과를 우선 확인해 네트워크 단절 뒤의 중복 실행을 막는다. 공통 trace와 영향 계정 수를 사건 자료에 적는다. trace를 연결한다. trace를 연결한다.

## API 오류코드와 재시도 표 운영 장면 11
20초 권한 반영 지연은 API 오류와 분리해 안내한다. 권한 반영 지연은 토큰 발급 시각과 원장 이벤트 시각의 차이로 확인한다. 20초가 지나면 고객에게 재로그인만 반복 안내하지 않고 동기화 진단으로 전환한다. 해결 전에는 성공으로 보이는 화면 캡처만 근거로 삼지 않는다. 토큰 재발급으로 해결되지 않는 지연은 권한 이벤트와 캐시 만료 시각을 비교해 담당 큐를 정한다. 서버 결과를 확인하기 전에는 성공이나 실패를 확정하지 않는다. 원장 결과를 우선한다. 원장 값을 우선한다.

## API 오류코드와 재시도 표 운영 장면 12
복구 확인은 실제 응답과 원장 이벤트가 맞는지 보고 끝낸다. 재시도 간격은 20초를 넘기지 않는다. 진단을 끝낼 때는 실제 기능 호출, 응답 코드, 관련 이벤트가 서로 맞는지 대조한다. 고객에게 전달할 내용에는 재현 방법과 안전한 다음 시도만 남기고 내부 trace를 노출하지 않는다. 종료 시각과 확인자를 기록해 후속 문의가 같은 절차를 반복하지 않게 한다. 종료 답변에는 재현이 끝난 시각과 사용자가 다시 시도할 조건을 적고 내부 디버그 값은 제외한다. 토큰과 권한 원장의 시각 차이를 비교한다. 시각 차이를 비교한다. 토큰 시각을 비교한다.
