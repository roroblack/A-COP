부트캠프 주제 대응: 다중 에이전트 서빙 기반 고객 피드백 분석 및 맞춤형 응대 자동화 시스템

고객 피드백 분석 + 전문 Agent Team 협업 + 외부 소비자 AI 연동 + 모듈형 Agentic Basement

v10 · 구현계획서 v5 기준 · MVP 범위 확정판

1. 한눈에 보는 핵심 그림

이 프로젝트는 단순 챗봇이 아니라, 고객 피드백을 기반으로 실제 업무 단위의 전문 AI Agent Team이 협업하여 문제를 해결하는 Agentic Customer Operations Platform이다.

핵심 아이디어

  • 고객 피드백을 단순 답변용 입력이 아니라 Customer Case로 관리
  • 업무 책임 단위 Agent Team Module 구성 — 실제 Team 종류와 개수는 요구사항 분석 후 결정
  • RAG, Memory, Shared State를 통해 Agent 협업

차별점

  • 고정 파이프라인이 아니라 동적 분기·재처리·승인
  • 외부 사용자의 개인 AI(ChatGPT/Claude/Gemini)가 우리 서비스 API/MCP로 접속 가능
  • 도메인 확장이 가능한 모듈형 Basement 구조

시연 포인트

  • 구독 해지 후 추가 결제
  • 권한 동기화 오류
  • 반복 VOC 탐지 및 리포트

2. 왜 기존 Pipeline을 Agentic Customer Operations로 확장하는가?

팀에게는 “Agentic AI를 쓰자”부터 설명하는 것이 아니라, 기존 구조가 어떤 문제를 해결하지 못하는지부터 보여준다.

Agent 수를 늘리자는 제안이 아니다. 고정된 처리 단계를 Agent라고 부르는 대신, 실제 고객 업무에서 서로 다른 책임·지식·도구를 가진 업무 단위를 모듈형 Agent Team으로 구성하고, 상위 Agentic System이 이들의 협업과 상태를 관리하도록 만들자는 제안이다.

Team A/B/C는 고정 이름이 아니다. 실제 업무 분석 결과에 따라 필요한 Team Module을 만들고 Registry에 등록한다.

1

Multi-Agent의 이유가 생긴다

검색 Agent, 생성 Agent처럼 단계를 나누는 것이 아니라 서로 다른 업무 목표·권한·Tool·Knowledge를 가진 팀을 분리한다. 따라서 Agent 간 협업 자체가 실제 업무 구조와 연결된다.

2

LangGraph의 이유가 생긴다

한 Case가 한 번에 끝나지 않고 Team 재배정, 추가 정보 대기, Human Approval, 실패 후 재처리, 상태 복원과 같은 분기·순환·중단·재개를 갖는다.

3

기존 과제를 버리지 않는다

고객 피드백, 감성·의도·이슈 분석, RAG, Multi-Agent, 맞춤형 응대는 그대로 유지한다. 단순 답변 Pipeline을 Customer Case 해결 시스템으로 확장한다.

팀 설명용 한 문장: 기존 과제를 없애는 것이 아니라, “고객에게 답변 하나 생성”에서 “하나의 고객 문제를 여러 전문 AI 팀이 협업하여 해결”하는 구조로 한 단계 확장한다.

2-A. v5 확정 범위 — 무엇을 만들고, 무엇을 안 만드는가

v4까지는 "가능성"을 열어 두었다. v5부터는 범위를 잠근다. 아래에 없는 것은 10주 안에 만들지 않는다.

MVP 한 문장: 가상 SaaS 고객 문의 2개 업무 유형을 대상으로, Case 상태를 영속화하고, 서로 다른 권한·도구·지식을 가진 2개 Agent Team이 하나의 Case를 이어서 처리하며, 승인·재개·정책 근거가 모두 기록되는 것을 증명한다.

MVP에 넣는다 (필수)

  • 가상 SaaS 도메인 1개 + seed DB
  • Capability 2개 — subscription_billing, technical_entitlement
  • Agent Team 2개 (내부 역할 최대 2개씩)
  • Case lifecycle + 낙관적 동시성 + checkpoint 기반 WAIT/RESUME
  • 정책 RAG(pgvector) + 구조화 DB 조회 Tool
  • Feedback Analytics 배치 파이프라인(감성·의도·이슈 + 급증 탐지)
  • mock refund + Human Approval
  • REST/OpenAPI 5개 엔드포인트
  • 운영자 3화면 (Case 목록 / trace / 승인)
  • Baseline A · B · Proposed 자동 평가 harness

Phase 2 (여유 있을 때만)

  • MCP read-only 3 tool — 9주차, 쓰기 금지
  • 하이브리드 검색(BM25+Vector) + Rerank
  • OAuth 2.0 Authorization Server
  • Episodic Memory (유사 Case 2건 주입)
  • Redis Streams 어댑터 교체 실증
  • 3번째 Agent Team
Phase 2 항목은 M3 게이트(9주)를 통과한 뒤에만 착수한다. 미착수해도 발표는 성립한다.

만들지 않는다 (제외)

  • Kafka / RabbitMQ
  • 동적 플러그인 설치 런타임
  • 실제 결제·계정 시스템 연동
  • 임베딩 클러스터링 / 토픽 모델링
  • 다중 LLM provider 동시 운용
  • 전체 운영 대시보드
  • 멀티테넌시 실운영 (컬럼만 두고 값은 1개 고정)

3-2. 상세 아키텍처 — 구현 시 실제로 분리되는 컴포넌트

중요: Context Broker와 Message Broker는 같은 것이 아니다. Context Broker는 “판단에 필요한 정보를 구성”하고, Message Broker는 “비동기 Task/Event를 운반”한다. 상세도에서는 둘을 별도 컴포넌트로 배치했다.

3-3. 컴포넌트 사전 — 브리핑만 보고도 역할을 알 수 있게

Agent Gateway

외부 AI/사용자 요청의 Trust Boundary

OAuth Access Token을 검증하고 사용자, 외부 AI Client, Scope, 요청 위험도를 확인한 뒤 내부 Case 요청으로 넘긴다.

입력: REST/MCP 요청 + Token → 출력: 인증·인가된 요청 Context

Customer Case Layer

한 번의 메시지를 장기 실행 가능한 업무 Case로 변환

문의 원문, 현재 상태, 담당 Capability, Event, 승인 대기, 재개 지점 등을 Case 단위로 관리한다.

입력: 승인된 고객 요청 → 출력: case_id + lifecycle state

Context Broker

Agent에게 필요한 Context Pack 구성

RAG, 현재 DB 상태, Case History, Memory 중 필요한 정보만 선택·정규화·압축해 Controller/Team에 공급한다.

메시지를 운반하지 않음. “무엇을 알아야 하는가?”를 담당

Message Broker

비동기 Task/Event 전달

긴 작업, 재시도, Worker 분리, Event Pub/Sub를 담당한다. MVP는 in-process/Redis로 시작하고 필요 시 Redis Streams 또는 RabbitMQ Adapter로 확장한다.

Context를 만들지 않음. “어떤 Task/Event를 어디로 전달할까?”를 담당

Agentic Controller

Case의 상위 의사결정·라우팅

Capability에 맞는 Team을 선택하고 해결 여부를 판단하며 WAIT/RESUME, Human Approval, Replan, 종료를 관리한다.

Top-Level LangGraph가 위치하는 핵심 계층

Agent Team Slot

교체 가능한 Team Module의 실행 경계

Registry가 선택한 Team Module이 여기서 실행된다. 내부가 Single-Agent, Multi-Agent, LangGraph, Rule/ML 혼합이어도 Core는 Team Contract만 본다.

입력: TeamTask/CaseContext → 출력: TeamResult

Shared State

여러 Team이 공유하는 Case의 단일 기준 상태

evidence, decisions, open_tasks, owner, status, version, approval 상태를 저장해 서로 다른 Team이 같은 Case를 이어서 처리할 수 있게 한다.

팀별 Memory와 다름: Shared State는 “현재 Case의 공식 상태”

Tool / Action Layer

실제 외부 시스템을 변경하는 실행 계층

조회·환불 요청·계정 변경·알림 같은 Business Capability API를 제공한다. 권한, idempotency, audit, 승인 여부를 확인한 후 side effect를 실행한다.

Agent가 DB를 직접 만지는 대신 통제된 Tool을 호출

Agent Team Registry

Capability → Team Module 탐색

team_id, capabilities, version, tool_scope, knowledge_scope, 활성 상태를 관리해 Team을 추가·교체해도 Core가 특정 팀 이름에 의존하지 않게 한다.

예: capability=refund_review → 현재 활성 Team Module 반환

4. 핵심 Workflow — Top-Level Graph + Team별 Subgraph

왜 4-1을 단순화해서 표현하나? Level 1/2는 “Case가 어느 Team으로 가고 다시 돌아오는지”를 보여주는 상위 Graph이고, 실제 Team 내부에는 각자 별도의 LangGraph/Subgraph가 존재할 수 있다. 상위 Graph와 내부 Graph를 한 그림에 모두 펼치면 흐름이 오히려 읽히지 않기 때문에 계층을 나눈다.

wait_reason → resume_node ────────────────────────────────────── customer_input → validate_input human_approval → execute_approved_action external_callback → verify_external_result
  • Team 전체 재실행 금지. 처음부터 다시 돌리면 이미 실행된 side effect가 중복된다.

  • callback은 event_id + idempotency_key로 중복을 흡수한다.
  • TTL 만료는 조용히 종료하지 않고 반드시 escalated로 보낸다. "말없이 사라지는 Case"를 금지한다.
상태 전이는 transition_case(case_id, expected_version, event) 단일 함수로만 수행한다. API·Team·Tool이 status를 직접 UPDATE하면 안 된다. 이 규칙 하나가 통합 주의 버그 대부분을 막는다.

4-B. 정합성 3대 규약 — 통합 주에 터지지 않기 위한 최소 조건

Core 담당자와 Team 담당자가 서로 다른 상태 모델을 만들면 마지막 2주에 통합이 불가능해진다. 아래 3개는 1주차에 합의하고 고정한다.

규약 1

낙관적 동시성 (Optimistic Concurrency)

version 컬럼이 있다고 동시성이 해결되지 않는다. 두 worker가 같은 version을 읽고 각자 append하면 나중 저장이 앞선 결과를 덮어쓴다.

UPDATE customer_cases SET status = :status, state_json = :new_state, version = version + 1, updated_at = now() WHERE case_id = :case_id AND version = :expected_version RETURNING version;
영향 행이 0이면 StateConflict → 최신 재조회 후 최대 2회만 재시도. 한 Case의 active run은 항상 1개.
규약 2

append-only 이벤트 + projection

변경의 원본은 case_events이고 state_json은 파생 결과다. 반대로 하면 "왜 이 상태가 됐는지"를 재구성할 수 없다.

  • UNIQUE(case_id, event_version) → 이벤트 누락·중복 즉시 검출
  • UNIQUE(tenant_id, idempotency_key) → 재전송 흡수
  • 상태 변경과 outbox insert는 같은 트랜잭션
검증 방법: 동일 POST를 10회 보내면 Case는 1개여야 한다.
규약 3

LangGraph checkpoint ≠ 업무 상태

checkpoint는 그래프 재개용 런타임 스냅샷이고, customer_cases는 외부에 약속하는 업무 상태다. 한 JSON으로 합치면 그래프 스키마를 바꾸는 순간 과거 Case가 전부 깨진다.

  • thread_id = case_id, PostgreSQL checkpointer
  • checkpoint에는 case_id · run_id · graph_revision · node_name + 최소 상태만
  • 실행 중 graph_revision 고정 — 새 revision은 새 Run에서만
검증 방법: 그래프를 수정한 뒤에도 진행 중이던 Case가 정상 재개되어야 한다.

안전성은 지표가 아니라 게이트다. LLM-as-Judge 루브릭 5항목(correctness · policy_grounding · next_action · safety · personalization)은 각 0~4점이며, 통과 조건은 safety>=3 and correctness>=3 and total>=16이다. 승인 전 side effect 실행이 1건이라도 있으면 그 run은 전체 fail로 처리한다.

11. 6명 팀 역할 분담 — 2개 Core 파트 + Agent Team 3명 + UI/Evaluation 1명

Core를 “아키텍처 담당 vs 백엔드 담당”처럼 겹치게 나누지 않고, 실행 조정과 외부/인프라 통합이라는 서로 다른 책임 경계로 분리한다.

11-1. Core Platform — 2개 파트, 각 1명

Part A · Agentic Runtime & Coordination

  • Customer Case lifecycle / Shared State 모델
  • Top-Level LangGraph: routing, replan, wait/resume, approval
  • Agent Team Contract / Registry
  • Context Broker의 orchestration 측 인터페이스
  • Message task/event envelope와 checkpoint 규칙
하지 않는 것: OAuth endpoint, REST/MCP 구현, DB driver/ORM, UI, Team 내부 RAG/Prompt 구현

Part B · Platform Integration & Execution

  • Agent Gateway: OAuth, Token, Scope, External AI 연결
  • REST/OpenAPI / MCP endpoint
  • Tool / Action Gateway와 외부 Business API Adapter
  • PostgreSQL/Vector/Message/LLM 기술 Adapter
  • Audit/Observability/배포·환경 통합
하지 않는 것: Case 라우팅 의사결정, Team 내부 Workflow, 업무별 Retrieval/Memory 정책

11-2. Agent Team Module 개발 — 3명

요구사항 분석 후 확정된 Agent Team Module에 3명을 배치한다. Team 이름과 개수는 아직 고정하지 않는다.

  • Team 내부 Agent/Subgraph 설계
  • 업무별 Prompt/Tool 조합

13. 심사 예상 질문과 답변

“이거 그냥 LLM 파이프라인에 Agent 이름만 붙인 거 아닌가요?”

아닙니다. 이름이 아니라 실행 책임과 증거가 분리되어 있습니다. Billing은 결제·구독 사실과 환불 정책만 다루고, Technical은 entitlement·계정 상태·장애 이력만 다룹니다. 한 케이스의 trace에서 routing → team run → evidence → action proposal → approval/resume을 확인할 수 있고, 잘못된 팀의 tool 호출은 0건이어야 합니다. Proposed를 단순 LLM 파이프라인으로 ablation했을 때 routing, policy grounding, action safety, resume success를 각각 비교합니다.

두 Team의 허용 capability/tool 목록, 팀별 run trace, 잘못된 tool 호출 카운터, Proposed와 Baseline B의 동일 80건 지표표, approval 후 정확한 재개 노드 로그
case_id=case_approval_01 new ? classifying ? routing ? running ? waiting_approval(resume_node=execute_approved_action) approval.approved ? resuming(checkpoint=cp_17) ? execute_approved_action(side_effect_count=1) ? resolved

“Agent가 2개일 필요가 있나요? 프롬프트 하나로 다 되는 것 아닌가요?”

단일 프롬프트도 답변은 만들 수 있지만, 이 MVP는 서로 다른 데이터 권한과 실패 책임을 검증하는 과제입니다. Billing과 Technical을 하나로 합친 ablation을 같은 60 golden·20 holdout에 실행합니다. ①정답 routing ②필수 사실 recall ③정책 근거성 ④권한 밖 tool 호출 ⑤handoff precision을 비교해, 2개가 비용만 늘리고 개선이 없으면 그 사실도 결론으로 공개합니다.

baseline_single_team 실행기, 팀별 데이터/tool scope, 80건 고정 데이터셋, metric CSV, 2개 Team 유지/폐기 판정 기준(핵심 지표 개선 또는 안전성 개선)

“RAG랑 Multi-Agent 둘 다 하는 이유가 뭔가요?”

둘은 해결하는 오류가 다릅니다. RAG는 정책 문서의 근거를 찾고, Multi-Agent는 업무 책임·권한·다음 행동을 분리합니다. 정책 문서를 잘 찾지만 Technical 계정 정보를 읽지 못하면 실패하고, 팀을 잘 골라도 환불 정책을 인용하지 못하면 실패합니다. 그래서 RAG 제거, Team 제거, 둘 다 적용의 3조건을 비교합니다.

문서 ID가 포함된 evidence trace, 팀별 context scope, RAG on/off·multi-agent on/off 실험 설정, policy groundedness와 action safety 결과

“LangGraph 안 쓰고 그냥 함수 호출로 하면 안 되나요?”

단순 resolved 건만 보면 함수 호출로 충분합니다. 그러나 승인 대기 후 프로세스가 끊겼다가 재개되는 케이스와 Team handoff를 동일 함수 체인으로 안정적으로 재현하려면 상태·재개 지점·실행 trace가 필요합니다. 본 프로젝트의 주장은 LangGraph 자체가 우월하다는 것이 아니라, waiting_approval에서 승인 이벤트 뒤 execute_approved_action부터 재개되는 증거를 보이는 것입니다. 같은 시나리오를 함수 체인으로 구현한 baseline과 resume success·중복 side effect를 비교합니다.

함수 체인 baseline, LangGraph 실행 trace, 강제 프로세스 재시작 테스트, resume success, duplicate side effect 카운터

“정확도가 Baseline보다 얼마나 올랐나요? 비용은 몇 배죠?”

발표 전 실제 측정값으로 답하겠습니다. 80건에 대해 Baseline A/B/Proposed를 같은 model·temperature·fixture·tool budget으로 실행하고, correct routing, required fact recall, policy groundedness, action safety, case cost, p50/p95 latency를 함께 제시합니다. 정확도만 올리고 비용·지연이 폭증하면 성공으로 포장하지 않습니다.

python experiments/runner.py --config ... 실행 결과, config/dataset hash, 모델·토큰·비용 로그, reports/comparison.csv, bootstrap 95% CI, 비용 대비 개선 표

“가상 데이터로 한 실험을 어떻게 믿나요?”

실제 고객 성능을 주장하는 실험이 아니라, 통제된 조건에서 workflow·권한·근거·재개 동작을 검증하는 실험입니다. 25개 정책 문서와 seed DB snapshot으로 재현성을 확보하고, golden 60과 표현·수치·순서를 바꾼 holdout 20을 분리합니다. 한계는 명시하고, 실제 데이터 일반화는 후속 검증 과제로 남깁니다.

seed 생성 명령, corpus/version hash, golden·holdout 분리 파일, 동일 입력 재실행 diff, 데이터 합성 규칙과 한계 문서

“6명이 10주 했는데 결국 챗봇 아닌가요?”

최종 화면은 채팅처럼 보일 수 있지만 성공 단위는 답변이 아닙니다. 케이스가 생성되고, 두 업무 Team 중 하나가 routing되며, 정책·DB 근거가 기록되고, 고위험 action은 승인 전 실행되지 않고, 승인 이벤트 후 중단 지점에서 재개되며, 불확실하거나 타 업무면 handoff/escalation됩니다. 배치에서는 반복 feedback을 묶어 Technical Team 후보 이슈를 냅니다. 이 상태·trace·배치 결과를 화면과 CSV로 함께 공개합니다.

case timeline, team/run/tool/approval trace 화면, 3종 demo 데이터, feedback report, 80건 평가 결과, action safety 100% 목표와 실패 건수

“Handoff와 실패를 임의로 보여주는 것 아닌가요?”

임계값을 발표용으로 조정하지 않습니다. capability 불일치, 필요한 데이터 scope 부재, 재시도 예산 초과, 낮은 근거 점수 중 하나가 발생하면 규칙에 따라 handoff/escalation합니다. 같은 fixture를 다시 실행해 동일한 조건에서 동일한 분기를 보여줍니다.

분기 규칙 버전, 실패 fixture, trace의 reason_code, 재실행 결과, handoff precision/recall 또는 최소한 expected-vs-actual 표
