1. 한눈에 보는 핵심 그림

이 프로젝트는 단순 챗봇이 아니라, 고객 피드백을 기반으로 실제 업무 단위의 전문 AI Agent Team이 협업하여 문제를 해결하는 Agentic Customer Operations Platform이다.

핵심 아이디어

  • 고객 피드백을 단순 답변용 입력이 아니라 Customer Case로 관리
  • 업무 책임 단위 Agent Team Module 구성. Team 종류와 개수는 요구사항 분석 후 정한다.
  • RAG, Memory, Shared State를 통해 Agent 협업

차별점

  • 고정 파이프라인이 아니라 동적 분기·재처리·승인
  • 외부 사용자의 개인 AI(ChatGPT/Claude/Gemini)가 우리 서비스 API/MCP로 접속 가능
  • 도메인 확장이 가능한 모듈형 Basement 구조

시연 포인트

  • 구독 해지 후 추가 결제
  • 권한 동기화 오류
  • 반복 VOC 탐지 및 리포트

2. 기존 Pipeline을 Agentic Customer Operations로 확장하는 이유

먼저 기존 구조가 해결하지 못하는 문제를 확인한다.

Agent 수를 늘리자는 제안이 아니다. 고정된 처리 단계를 Agent라고 부르는 대신, 실제 고객 업무에서 서로 다른 책임·지식·도구를 가진 업무 단위를 모듈형 Agent Team으로 구성하고, 상위 Agentic System이 이들의 협업과 상태를 관리하도록 만들자는 제안이다.

왼쪽은 처리 단계를 Agent라고 부르는 구조, 오른쪽은 업무 책임 단위 Team을 상위 Controller가 조정하는 구조다. 오른쪽에만 되돌아오는 화살표가 있다.

앞의 구조 변경에서 이어지는 개선점
위 비교에서 핵심적으로 바뀐 것은 ① 처리 단계를 Agent라고 부르는 구조에서 실제 업무 책임 단위 Team으로 전환하고, ② 한 번의 답변 생성 대신 Customer Case의 상태를 끝까지 관리하며, ③ 기존 분석·RAG·응대 기능을 이 Case 처리 흐름 안에 그대로 포함한 것이다. 이 변화로 다음 세 가지 개선점이 생긴다.
1

Multi-Agent의 이유가 생긴다

업무 책임 단위로 Team을 분리했기 때문에, 검색 Agent·생성 Agent처럼 처리 단계를 억지로 Agent화하는 문제가 줄어든다. 각 Team이 서로 다른 업무 목표·권한·Tool·Knowledge를 가지므로 Agent 간 협업이 실제 업무 분업과 연결된다.

2

LangGraph의 이유가 생긴다

답변 한 번이 아니라 Customer Case의 상태를 계속 관리하기 때문에, Team 재배정, 추가 정보 대기, Human Approval, 실패 후 재처리, 상태 복원 같은 분기·순환·중단·재개가 실제 요구사항이 된다. 이때 상위 Workflow를 Graph로 관리할 이유가 생긴다.

3

기존 과제를 버리지 않는다

기존 기능을 제거한 것이 아니라 더 큰 Case 처리 구조 안에 배치했기 때문에, 고객 피드백, 감성·의도·이슈 분석, RAG, Multi-Agent, 맞춤형 응대 요구는 그대로 유지된다. 단순 답변 Pipeline을 Customer Case 해결 시스템으로 확장하는 방식이다.

Agent Gateway
외부 요청의 인증·인가 경계

Web·Personal AI·원격 Agent System의 REST/MCP/A2A 요청을 내부 Case로 넘기기 전에 신원·권한·요청 대상을 검증한다.

정확한 역할과 기능

  • Access Token의 유효성·만료·대상을 검증한다.
  • 사용자와 외부 AI Client를 식별한다.
  • 요청 기능이 허용 Scope 안인지 검사한다.
  • 고위험 요청은 추가 승인 정책으로 넘긴다.
  • A2A 요청의 원격 Agent 식별자, 대상 Agent, 요청 Capability와 인증 정보를 검증한다.

Context Broker
판단에 필요한 Context Pack 구성

Vector RAG, Graph 관계 탐색, DB 현재 상태, Case History, Memory에서 필요한 정보만 골라 Controller/Team에 공급한다.

정확한 역할과 기능

  • 현재 작업에 필요한 정보 종류를 결정한다.
  • RAG·DB·Memory 결과를 표준 Context Pack으로 조합한다.
  • 중복/불필요한 정보를 줄여 Context 크기를 관리한다.
  • Team별 Knowledge Scope를 적용한다.
  • Vector Search가 찾은 관련 Entity를 Graph Store에서 1~2 hop 확장해 연결된 Case·Issue·Policy·Action을 보강할 수 있다.

용어 해설

Context Pack여러 원천의 정보를 현재 작업에 맞춰 정리한 표준 입력 묶음.
RAG생성 전에 외부 지식에서 관련 근거를 검색해 입력에 추가하는 구조.
Normalization서로 다른 형식의 정보를 일관된 구조로 맞추는 과정.
GraphRAG벡터 유사도 검색 결과에 지식 그래프의 관계 탐색을 결합해 연결된 근거와 맥락을 확장하는 검색 구조.
핵심 질문: “이 Agent가 지금 무엇을 알아야 하는가?”
Message Broker
Coordination의 비동기 Task / Event 전달

우리 Runtime 내부의 Local Team Worker에 Task/Event를 전달한다. 원격 Agent System과의 협업은 A2A Adapter가 담당한다.

정확한 역할과 기능

  • Controller가 발행한 Task를 Queue에 넣는다.
  • Team Worker가 Task를 소비해 실행하게 한다.
  • 실패 작업의 Retry를 처리한다.
  • 완료/오류 Event를 여러 구독자에게 전달할 수 있다.
  • Message Broker는 내부 Queue/Worker 통신용이며 외부 Agent 간 상호운용 프로토콜 역할을 하지 않는다.

용어 해설

Asynchronous요청자가 작업 종료까지 계속 기다리지 않는 실행 방식.
Queue처리할 작업을 보관하는 대기열.
Retry일시적 실패 작업을 정해진 정책에 따라 다시 실행하는 것.
Pub/SubEvent를 발행하면 여러 구독자가 받아 처리하는 전달 방식.

3-4. Agent/Team 경합과 동시성 처리 책임 계획서 8-C

경합 처리를 “Coordination 정책 담당”과 “Backend CAS 구현 담당”으로 사람을 다시 쪼개지 않는다. 같은 Customer Case의 실행·상태 경합은 Core 1이 정책부터 DB 무결성까지 end-to-end로 담당한다. 반면 실제 환불·계정변경 같은 외부 Action의 중복 실행은 Core 2가 담당한다.

코드의 책임 경계와 사람의 담당 경계를 똑같이 만들 필요는 없다. 코드에서는 Coordination과 State/Tool Layer를 분리하되, 사람은 Core 1이 Case Runtime을 end-to-end로 담당한다.

경합/중복 문제처리 방식담당 영역
두 Team이 같은 Case를 동시에 처리 Ownership, 병렬 허용 여부, 실행 순서, Retry/Replan/Cancel 정책 Core 1 · Case Runtime & Coordination
같은 Shared State를 동시에 UPDATE version, Optimistic Concurrency, CAS, Transaction으로 충돌 감지·차단 Core 1 · Case Runtime & Coordination
State Conflict 발생 후 다음 행동 최신 State 재조회 → 결과 유효성 판단 → Retry 또는 Replan Core 1 · Case Runtime & Coordination
같은 환불/계정 변경 Action이 중복 호출 Idempotency Key, Permission, Approval, Audit로 Side Effect 1회 보장 Core 2 · Access & Action Platform
한 Agent Team 내부 Agent끼리 경합 Team 내부 Subgraph/State/merge/retry 정책으로 해결 각 Agent Team Module
중요: 코드 컴포넌트는 Controller, State Repository, Message Broker, Tool Gateway처럼 분리한다. 하지만 사람 역할은 이 컴포넌트 이름대로 잘게 쪼개지 않고, 하나의 기능 흐름을 끝까지 책임하는 수직 영역으로 묶는다.

4. 핵심 Workflow

왜 4-1을 단순화해서 표현하나? Level 1/2는 “Case가 어느 Team으로 가고 다시 돌아오는지”를 보여주는 상위 Graph이고, 실제 Team 내부에는 각자 별도의 LangGraph/Subgraph가 존재할 수 있다. 상위 Graph와 내부 Graph를 한 그림에 모두 펼치면 흐름이 오히려 읽히지 않기 때문에 계층을 나눈다.

9-B. Graph DB / GraphRAG 활용 계획 계획서 9-D

GraphRAG는 문서에서 LLM이 관계를 추출하는 방식과, 이미 정형화된 관계를 질의하는 방식을 구분한다. 전자는 채택하지 않고 후자를 채택한다. MVP는 PostgreSQL JOIN·재귀 CTE 기반 SqlGraphAdapter로 시작한다. 시나리오 A/B/C의 관계 깊이는 1~2이고 반복 VOC 급증은 집계 질의다. “그거 그냥 JOIN 아니냐”에 대해서는 현재 규모에서는 맞다고 인정한다. 전용 Graph Store는 빼지 않되, MVP에 도입하지 않는다.

Graph가 실제로 유리해지는 지점: Remote Agent 위임 토폴로지는 관계가 외부로 뻗고 깊이가 가변이며 PostgreSQL FK에 없다. Case → Evidence → Document → Policy → Decision → Action 설명 경로도 고정 깊이가 아니다. 현재는 Team 2개와 Remote PoC 1개, 위임 깊이 2이므로 그래프 저장소가 필요하지 않다.

판단이 뒤집히는 조건은 Remote A2A Agent 2개 이상, 정책 계층 상속 도입, SQL 경로의 근거 포함률 미달이다.

10-2. 공식 산출물과 우리 설계가 어긋나는 지점

아래 세 건은 강사 확인이 필요하다. 확인 전까지는 구현 완료로 표기하지 않는다.

전처리 · 학습 산출물 3건

우리 구조의 핵심 실행은 LLM API 호출과 Agent Team orchestration이다. 따라서 LLM API 호출 자체를 학습한 ML/DL 모델이라고 제출하지 않는다. 데이터 전처리 결과서에는 CLAUDE에 있는 PII masking, Case fixture, knowledge documents 25건, knowledge chunks 300건, metadata·embedding 적재와 RAG corpus 품질 게이트를 담는다. 다만 RAG corpus v5가 재작업 중이므로 최종 인수는 확인 필요다. 머신러닝/딥러닝 학습결과서에는 학습 결과 대신 v8 §27의 A/B/Proposed 평가와 Proposed+FT 비교 경로를 구분해 기록한다. 현재 확인된 것은 LLM API 기반 평가 540 관측이며, 파인튜닝 결과는 확인 필요다. 학습한 ML/DL 모델은 자체 학습 모델이 없으면 “해당 없음”으로 제출할지 확인 필요로 남긴다. 강사가 학습 모델을 필수로 요구하면 v8 §27의 파인튜닝 경로를 별도 범위로 확정해야 한다.

sLLM 필수 여부

WBS 원본은 12번 산출물을 “3, 4번 팀”으로 적고, 6팀 행에도 포함한다. 6팀 필수 여부는 원본에서 확정되지 않는다. 필수가 아닌 경우에는 자체 sLLM을 제출 범위에서 제외하고, v8 §27의 파인튜닝 경로를 선택 항목으로 표시한다. 필수인 경우에는 공개 1차 모델과 알파 2차 모델을 같은 golden/holdout에서 비교하는 v8 §27의 경로를 5W 이후 별도 작업으로 확정한다. 어느 갈래가 적용되는지는 강사 확인 필요다.

GraphDB 구축 결과서

5W 마감에 맞춰 “물리적인 외부 GraphDB 구축”으로 확대하지 않는다. v8은 GraphStorePort를 두고 MVP 구현체로 SqlGraphAdapter를 사용하며, PostgreSQL JOIN·재귀 CTE 기반 관계 조회를 계획한다. CLAUDE에는 이 Port와 Adapter가 구현되어 있고 Controller가 Port를 경유하는 상태가 기록되어 있다. 따라서 제출물은 PostgreSQL·pgvector 기반 Vector RAG와 GraphStorePort·SqlGraphAdapter의 구성, Case→Issue→Policy·Issue→Team·Case→Action 관계 질의 fixture 결과다. 외부 AGE·Neo4j Adapter를 5W까지 구축해야 하는지는 원본과 v8만으로 확정할 수 없으므로 확인 필요다. DoD 21의 정확성 판정이 부분 상태로 남아 있으므로 5W 전에 세 관계 질의의 evidence를 완성한다.

11. 6명 팀 역할 분담

Core를 “Coordination 로직 담당”과 “Backend 구현 담당”으로 쪼개지 않는다. 같은 기능 흐름에서 정책과 실제 무결성 구현이 서로 붙어 있기 때문에, Core 1은 Case Runtime을, Core 2는 Access/Action을 각각 end-to-end로 담당한다.

Agent Team은 Tool을 직접 호출하지 않는다. 읽기는 Context Broker가 미리 제공하고, 쓰기는 ActionProposal로 반환한다. 따라서 Team 개발자 3명은 Core 2 인터페이스를 보지 않아도 된다. 두 Core의 접점은 ExecuteAction / ActionResult 한 쌍이다.
