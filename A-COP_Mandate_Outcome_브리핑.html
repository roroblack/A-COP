A-COP / Architecture Extension Brief

Mandate + Outcome
기존 구조를 건드리지 않는 Agent 시대 확장

새 Agent나 새 Platform Component를 더 만드는 계획이 아니다. 기존 A-COP의 실행 구조는 그대로 두고, “사용자가 무엇을 위임했는가”와 “무엇이 되어야 성공인가”를 Customer Case의 공식 의미로 추가한다.

1. 한눈에 보는 결론

가장 먼저 이것만 보면 된다.

KEEP기존 A-COP 그대로Case · Controller · Team · Shared State · Context · Tool · MCP · A2A · Approval · Audit 구조는 변경하지 않는다.
NEW 01MandateAgent가 고객 대신 어디까지 해도 되는가?
목표·허용 행동·금지 행동·금액 제한·재승인 경계를 Case에 명시한다.
NEW 02Outcome무엇이 되어야 Case가 진짜 끝나는가?
Tool 호출 성공이 아니라 검증 가능한 고객 목표 달성을 종료 조건으로 둔다.
Commitment와 Resolution Proof는 MVP 신규 컴포넌트로 만들지 않는다. 기존 case_events / action_result / evidence / audit로 흡수하고 실제 필요성이 생길 때만 승격한다.

3. 업계 흐름과의 정합성

웹 리서치 기준으로 Mandate는 임의로 만든 장식 개념이 아니라 실제 Agentic Commerce가 해결 중인 문제와 맞닿아 있다.

외부 흐름핵심A-COP에서 가져갈 해석
Google AP2typed mandate를 통해 사용자의 의도를 증명하는 계층을 다룸Scope와 사용자 위임 의도를 분리한다.
Google UCPCommerce lifecycle을 typed capability로 표준화하고 REST/MCP/A2A 등과 결합 가능Commerce 때문에 A-COP transport/core를 재설계할 필요 없음.
A2A v1.0Agent Card, identity, skill/capability, auth를 통한 독립 Agent 협업Remote Team은 기존 Registry/A2A 경로 유지.
MCPLLM app과 Tool/Resource 연결 및 authorizationMandate는 transport가 아니라 Case semantics.
Visa / Mastercardagent identity, permissioning, verifiable intent를 별도 trust 문제로 다룸“누구인가”와 “무엇을 위임받았는가”를 나눠 관리.

4. 가장 중요한 경계 — Scope ≠ Mandate ≠ Approval

핵심: Scope는 “호출 가능”, Mandate는 “이번 목표에서 위임됨”, Approval은 “이 실행을 지금 승인함”이다. 셋을 하나로 합치면 권한 모델이 흐려진다.

5. Mandate — 최소 구현

포함할 것

goalallowed_actionsforbidden_actionsconstraintsapproval_rulesstatusversion

복잡한 법률 계약 객체가 아니라, Agent 실행 경계를 판정하기 위한 구조화된 Case 데이터다.

상태

DRAFT ↓ ACTIVE ├→ REVISED → ACTIVE ├→ SUSPENDED → ACTIVE ├→ REVOKED └→ EXPIRED

Action 실행 전 판정

Action Proposal→Scope→Mandate Guard→Approval→Idempotency→Tool

“지난주 산 키보드가 다른 모델로 왔어. 추가 비용 1만원 이하면 알아서 교환하고, 그 이상이면 나한테 물어봐.”

12. 하지 않을 것

NO새 서비스 남발 금지Mandate Service, Outcome Service, Commitment Ledger Microservice를 만들지 않는다.
NO프로토콜 재구현 금지AP2/UCP/MCP/A2A 자체를 만드는 프로젝트로 확장하지 않는다.
NO증명 시스템 과잉 금지블록체인·전자서명·법적 원장 등은 실제 요구가 생길 때만 검토한다.

13. 최종 판단

A-COP을 CS 전용으로 좁히지 않는다. 기존 구조는 범용 Agent Runtime으로 유지하고, Mandate와 Outcome만 범용 Case semantics로 추가한다. 이 두 개는 쇼핑·여행·SaaS·보험 등 “Agent가 사람 대신 현실의 상태를 바꾸는” 모든 도메인에 재사용할 수 있다.
