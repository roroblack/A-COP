# S-OPS-UNKNOWN-RUNBOOK — provider timeout `unknown` 상태 운영 절차서

## 0. 배경

- `docs/release_checklist.md` §2 — provider timeout 을 성공으로 추정하지
  않고 `unknown` 으로 남긴다는 원칙은 구현돼 있으나, 실제로 `unknown` 상태가
  발생했을 때 **사람이 무엇을 봐야 하고 어떻게 해결하는지 절차서가 없다.**
- `CLAUDE.md` §0.2 — "provider timeout 을 성공으로 추정하지 않는다. `unknown`
  으로 남기고 자동 재실행하지 않는다"는 원칙이 이 절차서가 다뤄야 할 상태다.
- 코드를 고치는 작업이 아니라 **문서화** 작업이다. 단, 절차서에 적는 화면
  경로·쿼리·API 는 실제 코드에 존재하는 것만 적어야 한다 — 존재하지 않는
  화면이나 엔드포인트를 지어내지 않는다.

## 1. 할 일

1. 코드베이스에서 `unknown` 상태가 실제로 어디서 만들어지는지 찾아라
   (`app/` 아래 provider timeout 처리 로직, 상태 전이표, `case_events` 기록
   지점). `transition_case()` 진입점과 관련 이벤트 타입을 확인해라.
2. 이 상태가 됐을 때 운영자가 실제로 확인할 수 있는 화면(`/ui/cases`,
   `/ui/trace` 등)이나 API 가 있는지 확인하고, 있다면 정확한 경로를 적어라.
   없다면 "현재 조회 화면 없음"이라고 정직하게 적어라 — 있는 척하지 마라.
3. 다음 내용을 담은 운영 절차서를 작성한다:
   - `unknown` 상태가 무엇을 의미하는지(성공도 실패도 아닌 미확인 상태)
   - 이 상태를 어떻게 찾는지(쿼리, 화면, 로그)
   - 사람이 확인해야 할 것(실제 provider 쪽에서 그 작업이 완료됐는지 수동
     확인하는 방법 — 예: 결제 대행사 콘솔, 배송 조회 등 실제 이 프로젝트
     도메인에 맞는 확인 경로)
   - 확인 후 취할 수 있는 조치(수동으로 `transition_case()` 를 어떤 이벤트로
     호출해 다음 상태로 넘길지 — 자동 재실행이 아니라 사람이 확인 후
     명시적으로 트리거하는 절차여야 한다)
   - 확인이 안 될 때(provider 쪽도 모른다고 하는 경우) 어떻게 하는지
4. 실제 재현 가능한 명령/쿼리 예시를 최소 1개 이상 넣어라(예: `unknown`
   상태인 case 를 찾는 SQL 또는 API 호출). 지어내지 말고 실제 스키마·API
   를 보고 정확하게 적어라.

## 3. 하지 말 것

- 코드 수정 없음 — 순수 문서화 작업이다
- 존재하지 않는 화면·API·쿼리를 있는 것처럼 적지 않는다
- 자동 재시도/자동 복구 로직을 제안하지 않는다(이 프로젝트 원칙과 정면
  충돌 — `CLAUDE.md` §0.2)
