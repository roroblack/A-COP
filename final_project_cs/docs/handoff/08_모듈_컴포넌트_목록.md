# 08 — 모듈 / 컴포넌트 목록 (구성기의 입력 정의)

- 개정 이력: 2026-08-14 최초 작성
- 근거: `git grep` · AST 실측 (문서가 아니라 코드를 셌다)
- 용도: **제작 단계 구성기(Composer)가 무엇을 켜고 끌 수 있는지의 원본 정의**

## 0. 용어를 먼저 나눈다

이 저장소에서 두 말을 다르게 쓴다.

| 말 | 뜻 | 구성기에서 |
|---|---|---|
| **컴포넌트** | 제거하면 시스템이 성립하지 않는 구성물 | **선택 불가** — 항상 포함 |
| **모듈** | 켜고 끌 수 있는 단위. 빼도 나머지가 돈다 | **선택 가능** |
| **Port** | 구현을 갈아 끼우는 지점 | 구현체를 **고른다** |
| **인스턴스** | 같은 계약을 만족하는 것을 **여러 개** 둘 수 있다 | 개수를 **더하고 뺀다** |

★"모듈형 Basement" 의 실체는 **컴포넌트는 고정이고 모듈은 가변**이라는 것이다.

## 1. 컴포넌트 (선택 불가 — 빼면 시스템이 아니다)

| 컴포넌트 | 위치 | 왜 뺄 수 없나 |
|---|---|---|
| **Case lifecycle · `transition_case()`** | `app/core/transition.py`, `app/domain/{case,events}.py` | 상태 변경의 **단일 진입점**. API 의 Case 생성·분류가 이벤트에 직접 의존한다 |
| **계약 모델** | `app/core/contracts.py` | `TeamTask`·`TeamResult`·`TeamManifest`·`TeamModule`·`ContextPack`·`Evidence`. Controller·Team·평가가 전부 이 타입을 주고받는다 |
| **Team Registry** | `app/core/registry.py` | capability 해석의 유일한 경로. 없으면 라우팅 불가 |
| **Context Broker** | `app/core/context.py` | 12,000 토큰 예산·절삭·`degraded` 신호. 근거 조합의 경계 |
| **DB repository / session** | `app/infrastructure/db/` | Source of Truth |
| **Outbox 원자성** | `app/infrastructure/messaging/outbox.py` | projection·event·발행이 한 transaction |
| **Case service (run/resume)** | `app/application/case_service.py` | active run 중복 방지, `agent_runs` 기록 |
| **Controller** | `app/application/controller.py` | 위를 잇는 실행 루프 |
| **설정 · 가드레일** | `app/core/settings.py`, `config/guardrails.yaml` | 수치 단일 출처 |

### ★`voc` 는 이 제품에서 끌 수 없다

위 표에서 `voc` 는 특별하다. **끄면 앱이 기동하지 않는다.**

`CLAUDE.md` §1 이 **"인라인 분류는 선택 기능이 아니다"** 라고 못박았고, 그 분류가
Case 생성 경로에 붙어 있다. 분류를 건너뛰면 `intent` 와 `sentiment` 가 빈 채로 Case 가
만들어지고 그 빈 값이 근거 조합을 거쳐 고객 답변까지 간다. 그래서 조용히 넘어가는 대신
`build_classifier()` 가 그 자리에서 실패한다.

즉 아래 표에서 `voc` 는 **"선택 가능"이 아니다.** 지금까지 끌 수 있는 것처럼 적혀 있던
것이 잘못이었다. 정말로 끄고 싶으면 Case 생성 경로에서 분류를 떼어내는 별도 작업이
먼저 필요하다.

## 4. 인스턴스 — 개수가 가변인 것

| 종류 | 현재 | 추가 방법 |
|---|---|---|
| **Agent Team** | `OrderShippingTeam`, `ReturnExchangeTeam` (2개) | `TeamModule` Protocol 구현 + Registry 등록 |

## 5. ★해결됨 — 구성기가 선언을 읽어 조립한다

이 절이 원래 지적하던 문제(`app/composition.py` 가 Team 을 **하드코딩 import**
해 선언 파일이 실제 조립을 지배하지 못하는 것)는 이후 해결됐다.
`app/composition.py` 는 이제 `load_project_config()` + `importlib` 로
`config/project.yaml` 의 `teams[].implementation_ref` 를 동적으로 읽어
조립한다 — 하드코딩 import 가 없다. `final_project_ui`의 인증된 Composer API로
바꾼 선언이 실제 배포에 반영된다.
→ `docs/reports/2026-08-14_모듈구성기_설계검토.md` (당시엔 미해결이었다는 기록)

## 6. 구성 선언 — 실제 `config/project.yaml` (2026-08-17 기준, 더 이상 권고안이 아니다)

```yaml
# config/project.yaml
modules:
  vector_rag:    { enabled: true }
  graph_store:   { enabled: true }
  a2a_executor:  { enabled: false }
  mcp:           { enabled: true }
  voc:           { enabled: true }
  ops_ui:        { enabled: true }
ports:
  team_executor: local                # local | a2a
  message_broker: outbox              # outbox | redis_streams(Phase 2)
  graph_store: sql                    # sql | age | neo4j(Phase 2)
teams:
  - { team_id: order_shipping,  active: true,  implementation_ref: "app.modules.customer_ops:OrderShippingTeam" }
  - { team_id: return_exchange, active: true,  implementation_ref: "app.modules.customer_ops:ReturnExchangeTeam" }
```

### 빌드 시 실패시켜야 할 것 (검증기)

1. `enabled: true` 인데 **구현이 없다**
2. `active: true` 인데 `implementation_ref` 가 **import 되지 않는다**
3. **중복 `team_id`** 또는 같은 capability 를 두 Team 이 주장
4. 꺼진 모듈을 **부르는 경로가 남아 있다**

★**미구현 Team 은 `active: false` 로 둔다.** 그러면 Registry 에 이름은 있지만
라우팅되지 않아 Case 가 죽지 않는다. "자리만 만들고 세부는 팀이 나중에" 를 안전하게 하는 방법이다.
