## P1. ActionProposal 근거 대조 (DoD-24) ★최우선

### 무엇이 문제인가
`app/application/controller.py:171-178` 이 `proposal.arguments` 를 **대조 없이** 저장한다.
실제 결제액이 30,000원인데 LLM 이 "50,000원 환불" 을 제안하면 **지금은 통과한다.**

지금 있는 `contracts.py:283-289` 는 *제안이 자기 결과 안의 evidence 를 가리키는가* 만 본다.
**현실과 맞는지는 보지 않는다.**

### 만들 것
`app/core/verification.py` — 순수 대조 함수 (Core, DB 접근 없음)
`app/application/proposal_guard.py` — DB 재조회 + 대조 실행 (Application)

v7 §9-E 표 그대로 필드별 대조:

| 필드 | 대조 | 불일치 |
|---|---|---|
| `order_id`·`payment_id`·`subscription_id` | tenant/customer 범위 실재 + 소유권 | 실행 전 거부 |
| `amount` | 최신 결제액·환불 가능 잔액·통화 | 실행 전 거부 |
| `quantity` | line item 취소 가능 수량 | 실행 전 거부 |
| `action_type` | Registry scope·approval matrix | 거부 또는 승인 대기 |
| `evidence_ids` | ContextPack 의 실제 evidence id | 실행 전 거부 |

### 검증은 두 번
1. **approval 전** — proposal 생성 시점 (Controller)
2. **실행 직전 재검증** — 승인 후 (상태가 그 사이 바뀔 수 있다)

### 거부 시 동작 (v7 §9-E)
조용히 무시하지 않는다. proposal 폐기 → **`escalated`** →
감사 로그에 `action_id`·case/run/task·**실패한 필드**·기대값/실제값의 **안전한 hash**·actor·시각.

★기대값·실제값을 **원문으로 남기지 않는다** — 금액·식별자가 감사 로그에 그대로 들어가면
`CLAUDE.md` §1(PII·결제 식별자 원문 금지)을 어긴다. hash 로 남긴다.

### 완료 조건
- 없는 `order_id` → 거부 + `escalated` + 감사 로그
- 불일치 `amount` → 거부 (30,000원 결제에 50,000원 환불 제안)
- 소유권 없는 `subscription_id` → 거부
- 정상 제안 → 통과 (★과잉 차단이 없어야 한다)
- 승인 후 DB 가 바뀐 경우 → 실행 직전 재검증에서 거부

## P2. degraded 를 Core 강제로 (DoD-25)

### 무엇이 문제인가
`billing.py:56` · `technical.py:42` 에서 **두 Team 이 각자 스스로** 검사한다.
★**새 Team 이 빠뜨리면 아무도 막지 않는다.** Team 의 선의에 기대고 있다.

> 검사하지 않는 규칙은 지켜지지 않는다.

### 만들 것
Controller 가 Team 결과를 받은 **직후**, `ContextPack.degraded=true` 인데
`action_proposals` 가 비어 있지 않으면 **제안을 폐기하고 escalated** 로 보낸다.
Team 의 자율 검사는 남겨 둔다 (빠른 실패는 여전히 좋다).

### 완료 조건
- degraded Context + 제안을 내는 **가짜 Team** → 제안이 실행 경로에 들어가지 않음
- 기존 두 Team 의 자율 검사도 그대로 통과
- ★Team 을 하나 더 추가해도 강제가 유지됨을 테스트로 고정

## P3. REST 상한 테스트 교정 (DoD-13)

### 무엇이 문제인가
```python
assert actual == CONTRACT_V1_PATHS      # 집합 완전 일치
```
v7 §0 은 "5는 상한이 아니다", DoD-13 은 "5가 상한이 아님을 **추가 endpoint fixture 로 검증**".
**지금 테스트는 정반대를 강제한다.**

★composer 기본값 때와 같은 실패 유형이다 —
테스트가 검사하는 것이 *지금도 의도한 성질인지* 확인하지 않으면
테스트가 제품을 낡은 방향으로 붙잡는다.

### 만들 것
완전 일치 → **계약 경로가 전부 있다(⊆)** + 새 경로는
`scope`·`idempotency`·`audit`·평가 fixture 를 갖췄는지 검사.
"임의로 늘리지 않는다" 는 의도는 **품질 게이트로** 지킨다.

## P4. 방어 지표 5종 + 공격 fixture (§9-E, §15)

P1·P2 가 **실제로 막는지 재는 수단.** 순서상 뒤여야 한다.

| 지표 | 분자 / 분모 |
|---|---|
| 근거 정합률 | 대조 성공 필드 수 / 모델이 제안한 근거 필드 수 |
| 근거 초과율 | Context 에 없는 필드 주장 수 / 전체 주장 수 |
| 적절한 기권율 | 불충분·불일치 입력에서 escalate 한 비율 |
| 과잉 기권율 | 충분한 근거에서 불필요하게 escalate 한 비율 |
| 스키마 준수율 | parse 성공 수 / 전체 |

★**분모와 fixture 를 함께 기록한다.** 분모를 안 적으면 조용한 스킵이 성공률을 부풀린다.

공격 fixture: 없는 `order_id` · 불일치 금액 · degraded Context · **프롬프트 인젝션**.
