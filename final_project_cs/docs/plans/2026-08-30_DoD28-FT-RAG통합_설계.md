# DoD-28 후속 — 파인튜닝 모델 RAG 통합 경로 설계

- 배경: [`2026-08-30_S-DOD28-FINETUNE-PIPELINE_리포트.md`](../reports/2026-08-30_S-DOD28-FINETUNE-PIPELINE_리포트.md) —
  `Proposed+FT`(파인튜닝 모델 단독 호출)가 golden/holdout 양쪽에서 0% pass. 원인은
  Team 파이프라인 밖에서 호출돼 RAG evidence를 아예 못 받았기 때문.
- 이 문서의 목적: 파인튜닝 모델을 **Team 파이프라인 안**(ContextPack을 실제로 받는
  경로)에 끼워 넣는 설계.
- ★**2026-08-30 같은 세션에서 §2 전체를 실제로 구현·실행까지 했다.** 배선은
  전부 동작한다. 모델 품질은 **채택 불가** — §5(실행 결과) 참고. 아래 §1~§4는
  설계 당시 원문 그대로 보존하고, §5에 실측 결과를 추가한다.

## 0. 결론 먼저 — 단순 배선이 아니라 재학습이 필요하다

가장 중요한 발견: **지금의 파인튜닝 모델은 배선만 바꿔도 못 쓴다.**
`eval/finetune/build_datasets.py`가 만든 SFT 데이터는 입력이 고객 메시지
텍스트 하나뿐이고(`{"case_id","messages":[{"role":"user","content":고객메시지}]}`),
정책 근거·`evidence_id` 인용을 요구하는 출력 스키마를 가르친 적이 없다.
반면 실제 Team(`response_review.py:96-104`)이 OpenAI에 보내는 입력은:

```python
await self.llm.complete(
    "response.generate", task.input_text,
    {"evidence": evidence, "context": task.context.model_dump(mode="json"),
     "retry_count": retry, "tone_profile": tone_profile},
)
```

— evidence 리스트가 통째로 들어있는 dict다. 지금 모델을 이 입력으로 그냥
호출해도 "이 dict에서 evidence_id를 뽑아 인용해야 한다"는 걸 학습한 적이
없으므로 여전히 근거 없이 답할 것이다. **RAG 통합 = 배선(1~4) + 재학습(0)**
두 가지가 다 필요하다.

## 2. 설계

### 2.1 재학습 (stage 3) — 실제 Team 입출력 형태로

- 입력: `{"prompt_key": "response.generate", "input_text": ..., "context": {"evidence": [...], "context": {...ContextPack...}, "retry_count": ..., "tone_profile": ...}}`
  (지금 `OpenAITeamLLM.complete`가 만드는 것과 동일한 JSON)
- 출력 타깃: `rationale_evidence_ids`가 **입력으로 준 evidence의 evidence_id 부분집합**인 답.
  지어낼 필요 없다 — `eval/reports/2026-08-28_reeval_Proposed_v3.jsonl`의 judge-pass
  행이 이미 실제 Team+RAG 파이프라인이 만든, evidence로 근거된 정답 예시다.
  이번에 쓴 "2차 22건"(judge pass golden)을 그대로 재사용하되, 학습 입력을
  golden 메시지 하나가 아니라 **그 행의 `team_result.evidence` 전체를 포함한
  JSON**으로 바꿔야 한다 — `eval/finetune/build_datasets.py`의 stage2 빌더를
  이 형태로 다시 짜는 작업이 필요(현재는 안 되어 있음).
- 데이터가 22건뿐이라 매우 작다 — 알파 실사용 로그가 쌓이기 전까지는
  이 재학습도 "방향성 확인" 수준이지 채택 근거는 아니다(§4 golden 60건 한계와
  동일 성격의 표본 크기 문제).

### 2.2 서빙 — x600에 최소 추론 서버

x600은 지금 SSH로만 닿고 HTTP로 노출된 적이 없다. 최소 구성:

- `venv312` 안에 FastAPI(또는 표준 라이브러리 `http.server`로도 충분한 스코프) 앱 1개,
  `POST /complete` — `{"prompt_key","input_text","context"}` 받아서
  `{"final_response_text", "rationale_evidence_ids", ...}` JSON 반환.
  merged(base+adapter) 모델을 프로세스 시작 시 한 번만 로드(지금 `predict.py`가
  매 실행마다 다시 로드하는 것과 다르게, 서버는 상주 프로세스로 로드 1회 후 재사용).
- 네트워크: x600은 LAN(`10.20.20.x`)에서만 SSH로 닿는 걸 이번 세션에서 확인했다.
  포트를 새로 열어 노출하기보다 **SSH 로컬 포트포워딩**
  (`ssh -N -L 8100:localhost:8100 x600`)으로 cs 쪽 로컬호스트에서만 접근하게
  하는 편이 방화벽 변경 없이 안전하다. 인증은 없더라도 최소 LAN 밖 노출은
  막아야 한다.
- x600은 관리형 서비스가 아니라 사용자가 수동으로 재부팅하는 개발용 GPU
  워크스테이션이다(이번 세션에도 한 번 응답불능→재부팅 있었음). **상시 가동을
  전제로 한 운영 배포는 이 문서 범위 밖** — Phase 2 Docker/AWS 컨테이너화
  단계(CLAUDE.md 루트 표)에서 다시 결정할 문제.

### 2.3 `LocalFTTeamLLM` — 같은 인터페이스로 새 backend

`app/infrastructure/llm/local_ft.py` (신규), `OpenAITeamLLM`과 나란히:

```python
class LocalFTTeamLLM:
    def __init__(self, *, base_url: str, connection_factory=None, timeout=60.0): ...
    async def complete(self, prompt_key: str, input_text: str, context: dict, *, run_id=None) -> dict:
        # 1) prompts 테이블에서 prompt_key의 active 행 조회 (OpenAITeamLLM과 동일 패턴)
        # 2) POST {base_url}/complete 로 {"prompt_key","input_text","context"} 전송
        # 3) record_llm_call(conn, provider="local_ft", model="qwen2.5-3b-ft-stage3", ...) 기록
        # 4) OpenAITeamLLM.complete와 동일한 반환 shape
```

Team 코드(`response_review.py`)는 **한 글자도 안 바뀐다** — `self.llm.complete(...)`
호출부는 그대로고, 어떤 객체가 주입됐는지만 다르다. 이게 지금 인터페이스가
덕타이핑인 이유이자 이 설계가 가능한 이유다.

### 2.4 배선 — 설정으로 전환 가능하게

- `app/core/settings.py`에 `llm_provider: Literal["openai","local_ft"] = "openai"`,
  `local_ft_base_url: str | None` 필드 추가.
- `app/composition.py:171-195` `build_controller()`에서 분기:
  `llm = OpenAITeamLLM(...) if settings.llm_provider == "openai" else LocalFTTeamLLM(base_url=settings.local_ft_base_url, ...)`.
- eval 하네스도 맞춰서: `common.py:101-115`의 `--provider` choices에
  `"local_ft"` 추가, `_team_context()`(`common.py:321` 부근)에서 provider별로
  `_OpenAITeamLLM()` 대신 새 `_LocalFTTeamLLM()` 주입.

### 2.5 검증 순서 (기존 judge/방어지표 파이프라인 재사용)

1. §2.1 재학습 완료 → 새 어댑터(`ckpt_stage3`)
2. §2.2~2.4 배선 완료 → `python -m eval.runners.proposed --dataset eval/datasets/golden.jsonl --provider local_ft --output eval/reports/<날짜>_golden_local_ft.jsonl`
3. 같은 judge rubric(`prompts/judge/judge_v1.txt`)으로 채점 — 이번에 만든
   `eval/finetune/score_ft.py`가 아니라 **`common.py`의 실제 judge 경로**를
   쓴다(이번 것과 달리 이제는 진짜 evidence/citations가 채워지므로).
4. 세 arm 비교: `Proposed`(OpenAI, 27.8%) vs `Proposed+FT-standalone`(이번 결과, 0%)
   vs `Proposed+FT-RAG통합`(신규). **`Proposed`의 27.8%를 못 넘으면 채택하지 않는다** —
   지금 시점의 목표는 OpenAI를 이기는 게 아니라 "RAG 통합이 0%를 유의미하게
   개선하는가"를 보는 것.
5. holdout은 이미 이번 세션에서 최초 실측(16.7%)을 썼으므로, 이 비교에도
   **딱 한 번만** 돌리고 그 수치로 확정한다(만지작거리며 여러 번 돌리면
   holdout이 아니게 된다).

## 5. ★2026-08-30 실행 결과 — 배선은 성공, 모델은 채택 불가

같은 세션 안에서 §2 전체를 실제로 구현·실행했다. 사용자가 자리를 비운
사이 중단 없이 진행하라는 지시에 따라, §0에서 예견한 "재학습 없이는
안 된다"를 실측으로 검증하는 데까지 갔다.

### 5.0 전제조건 결함 발견·수정 — response.generate가 production에서 아예 등록된 적이 없었다

§3의 "미확인 리스크"로 남겨뒀던 `ALLOWED_PROMPT_KEYS` 상태를 DB(`acop_cs`)
직접 조회로 확인하다가, `response.generate`/`response.review_tone` 프롬프트가
**한 번도 등록된 적이 없다**는 걸 발견했다 — 파일 자체가 저장소에 없었다.
`app.composition.build_controller()`의 production 배선
(`OpenAITeamLLM(connection_factory=get_connection)`)으로 재현하니
`RuntimeError: no active prompt registered for response.generate`가
매번 났다. 다만 `config/project.yaml`의 `response_review.enabled: false`
때문에 지금 이 결함이 실 트래픽을 죽이고 있지는 않다 — 켜는 순간
터질 지뢰였다. `prompts/response/generate.v2.md`·`review_tone.v1.md`
신규 작성, allowlist 갱신, DB 재등록, 회귀 테스트 3건으로 고쳤다.
별도 리포트: [`2026-08-30_S-PROMPT-KEY-REGISTRATION-GAP_리포트.md`](../reports/2026-08-30_S-PROMPT-KEY-REGISTRATION-GAP_리포트.md).

### 5.1 golden.jsonl은 이 팀을 단 한 건도 안 거친다 — 데이터 재설계

`app/application/controller.py::_maybe_review()`를 직접 읽어 확인: 이
Team은 primary Team(`return_refund` 등)이 만든 **`result.answer`를 검토·
재작성**하는 사후 처리 단계이지, 고객 메시지를 직접 받는 게 아니다.
golden.jsonl 72건은 전부 `return_refund`/`procurement_order_payment`/
`fulfillment_logistics`(전부 결정론적, LLM 미호출)로만 라우팅된다 —
**이 Team을 훈련할 실제 데이터가 golden/holdout에 전혀 없었다.**

`eval/finetune/build_stage3_dataset.py`(신규)로 우회: golden Proposed
judge-pass 행의 evidence·answer를 가져와 `_maybe_review()`와 동일한
입력 shape을 구성하고, **방금 고친 실제 `response.generate`를 진짜로
호출**해 진짜 grounded completion을 목표값으로 수집했다(지어낸 데이터
아님). 72건 중 judge-pass 22건 → `answer`가 있는 건 12건뿐(나머지 10건은
`waiting_input`/`escalated`라 애초에 이 Team이 안 걸리는 게 맞음, 세어서
기록함) → 9건 학습 / 3건 홀드아웃으로 분리.

### 5.2 배선 — 전부 동작 확인

- `app/infrastructure/llm/local_ft.py` `LocalFTTeamLLM` 신규 — `OpenAITeamLLM`과
  동일한 prompts-table 조회·`record_llm_call` 감사(provider="local_ft")·
  duck-typed `complete()`. httpx로 x600의 `eval/finetune/serve.py`(신규,
  FastAPI 상주 프로세스, 모델 1회 로드 후 재사용)를 호출.
- `app/core/settings.py`에 `local_ft_base_url` 추가, `app/composition.py`의
  `build_controller()`가 `settings.llm_provider`로 `OpenAITeamLLM`/`LocalFTTeamLLM`
  분기(`local_ft`인데 base_url 없으면 fail-closed).
- 회귀 테스트 8건 신규(`tests/integration/llm/test_local_ft_llm_audit_wiring.py`
  4건, `tests/unit/test_composition_llm_provider.py` 4건) — 전부 통과.
- x600에 SSH 로컬 포트포워딩(`ssh -N -L 8100:127.0.0.1:8100 x600`)으로
  LAN 밖 노출 없이 연결. 서버 기동 중 CUDA OOM 1회 발견·수정 — `run_serve.bat`에
  학습 때 썼던 `PYTORCH_CUDA_ALLOC_CONF`를 빠뜨렸던 것, 추가하고 재기동해 해결.

**결론: §2.1~2.4의 배선 설계는 코드 레벨에서 전부 검증됐다.** Team → LLM
인터페이스 → HTTP → 추론 서버 → 모델 → 감사 로그까지 end-to-end로
막힘없이 흐른다.

### 5.3 모델 품질 — 채택 불가, 실측으로 확인

`train.py --stage 3`(9건, 6epoch)의 최종 `train_loss=1.652`,
`mean_token_accuracy=0.6656` — 1차(0.95)·2차(0.91)보다 뚜렷이 낮다.
학습 도중부터 이미 신호였다.

홀드아웃 3건(`sft_stage3_holdout.jsonl`, 학습에 안 쓴 케이스)으로
`eval/finetune/eval_stage3_review.py`(신규)가 OpenAI와 local_ft를 **같은
입력**(같은 draft·같은 evidence)으로 나란히 호출해 비교했다:

| | OpenAI (참조) | local_ft (stage 3) |
|---|---|---|
| 3건 모두 유효 JSON 파싱 | 3/3 | **0/3** |
| grounded(judge, 0~4) | 4, 4, 4 | 채점 불가(파싱 실패) |
| safe(judge, 0~4) | 4, 4, 4 | 채점 불가(파싱 실패) |

local_ft 원시 출력을 직접 열어보면 `{"final_response_text":...}` 형태를
전혀 안 만든다 — 입력으로 준 evidence 청크를 그대로 이어쓰는 식으로
붕괴한다(예: `..."document_id": "doc_14", "chunk_no": 13, "content": "..."`
를 스스로 만들어냄, 학습 타깃에 없던 패턴). **9건으로는 이 태스크
(긴 JSON 컨텍스트 → 근거 기반 JSON 응답)를 배우지 못한다** — 표본
크기의 문제이지 배선이나 서빙의 결함이 아니다.

### 5.4 판단 — 지금 채택하지 않는다, 오늘 밤 더 튜닝해서 될 문제가 아니다

CLAUDE.md §4 "표본이 작으면 작다고 말한다" 원칙 그대로: 9건짜리 학습
결과를 하이퍼파라미터로 더 밀어붙이는 건 근본 해결이 아니다. 필요한 건
**더 많은 실제 review-task 데이터**뿐이다 — 다음 둘 중 하나로만 는다:
(a) `response_review.enabled: true`로 켜서 실 운영에서 transcript가
쌓이길 기다리거나, (b) `build_stage3_dataset.py` 같은 합성-실측 혼합
방식을 더 큰 case 집합(golden 72건보다 큰, 또는 반복 seed를 늘린)에
돌려 후보 수를 늘린다. 지금은 "배선이 되는가"라는 원래 질문에 **예,
되지만 지금 모델은 못 쓴다**로 답이 났다.

### 5.5 ★같은 세션, (b) 시도 — 데이터 12건으로 늘려 재학습, 그러나 재검증은 미완료

바로 (b)를 시도했다. `build_stage3_dataset.py`를 case 데이터셋을
인자로 받게 일반화(`--cases`)해서, golden 12건에 더해
`2026-08-30_holdout_proposed.jsonl`(holdout의 실 Proposed 실측 결과)의
judge-pass 4건도 같은 방식으로 뽑았다 — `h-response-review-01`,
`h-return-01/02/03`. **holdout 점수 재측정에는 안 썼다** — 이미 완결된
실행의 실 evidence·답변을 SFT 원재료로 재사용한 것뿐이라 "홀드아웃을
여러 번 만지는" 것과는 다르다(§3 리스크 항목의 정신은 유지).

합쳐서 16건(train 12 / test 4, `sft_stage3_train_v2.jsonl`/
`sft_stage3_holdout_v2.jsonl`) → `ckpt_stage2`에서 다시 `--stage 3
--epochs 8`로 재학습. 결과: `train_loss` 1.652→**1.475**,
`mean_token_accuracy` 0.6656→**0.7054** — 방향은 개선이지만 여전히
1차(0.95)·2차(0.91)에 한참 못 미친다.

이 v2 어댑터로 서버를 재기동하려던 중 x600이 한동안 SSH 응답 불능이
됐다(연결이 여러 차례 "Connection reset by peer"로 끊김 — 재부팅 없이
자연 복구됨, 이전의 완전 먹통과는 다른 패턴). 복구된 뒤 서버를 다시
띄우고 포트포워딩을 재연결해 **holdout 4건 비교를 실행했다**.

| | OpenAI (참조) | local_ft stage3 v1(9건) | local_ft stage3 v2(16건) |
|---|---|---|---|
| 유효 JSON 파싱 | 4/4 | 0/3 | **0/4** |
| grounded/safe(judge) | 4,4 전건 | 채점 불가 | 채점 불가 |

**v2도 채택 불가 — loss/accuracy 개선이 실제 출력 품질 개선으로
이어지지 않았다.** 다만 실패 양상이 바뀌었다: v1은 서버가 CUDA OOM으로
500 에러를 냈지만(배선 문제), v2는 서버가 정상 응답하되 모델이 유효한
JSON을 생성하지 못했다(`json.JSONDecodeError` — "Expecting value" /
"Extra data" 등, 매 건 다른 위치에서 깨짐). **이건 배선이 아니라 순수
모델 품질 문제라는 뜻**이고, §5.4의 결론(표본 크기 문제, 오늘 밤 더
튜닝해서 될 게 아님)을 16건에서도 다시 확인한 것이다 — golden+holdout을
탈탈 털어도 이 Team의 진짜 review-task 데이터는 16건이 상한이다.
더 늘리려면 §5.4 (a)(`response_review.enabled: true`로 켜서 실 운영
transcript 축적) 말고는 방법이 없다.
