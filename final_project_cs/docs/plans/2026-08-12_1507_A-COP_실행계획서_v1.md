## 0. v5 와 이 문서의 관계

v5 는 **무엇을 만들고 무엇으로 통과를 판정하는가**(범위·계약·DoD)를 정한다. 그것은 바뀌지 않는다.
이 문서는 **누가 어떤 순서로 만들고, 각 단계에서 무엇을 실행해 통과를 증명하는가**를 정한다.

바꾸는 것은 딱 두 가지다.

| v5 전제 | 이 프로젝트의 실제 | 대응 |
|---|---|---|
| 개발자 6명(A~F) 10주 | 1명 + Claude + Codex | 역할 A~F 를 **7개 소유 스트림**으로 재편(§2). 인원이 아니라 **디렉터리 소유권**으로 충돌을 막는다 |
| `docker/compose.yml` 로 PG 기동 | **Docker 미설치**. conda env `pgv` 의 PG 16.14 가 `:5433` 에서 이미 가동 | 로컬 PG 사용. compose 파일은 **재현 문서용으로만** 남기고 실행 경로에서 뺀다 |

그 밖의 v5 결정(12,000 토큰 예산 · 25문서/300~400청크 · MCP read-only 3 tool · outbox=Message Broker ·
60+20 golden/holdout · bootstrap+McNemar)은 **그대로 간다. 축소 금지**(`RULE.md` §3.3, §3.6-3).

### 왜 Core 를 Claude 가 갖는가

`transition_case()`·optimistic concurrency·outbox 원자성·ContextPack 예산 절삭은
**틀려도 테스트가 초록으로 나오는 종류의 코드**다(경합·부분 실패·토큰 경계).
`RULE.md` §3.6-5 대로 계약 테스트를 만든 쪽과 통과시킨 쪽을 분리하기 위해 Core 와 `tests/contract/` 는 Claude 가 쥔다.

### Codex 호출 형식

```powershell
Get-Content docs\handoff\_prompts\<스트림>.md | codex exec -s workspace-write -C <저장소루트> -
```

프롬프트는 계약 문서를 **인용**한다(경로로 가리킨다). 내용을 복사하면 두 벌이 어긋난다.

| 항목 | 내용 |

## 4. 의존 순서와 병렬 실행

```
P0 ──> P1 ──┬──> P2(S-DB) ─────┬──> P5(Claude) ──> P8(S-UI) ──> P10
            │                  │
            ├──> P3(S-RAG)  ───┤
            ├──> P4(S-TEAM) ───┤
            ├──> P6(S-API)  ───┤
            └──> P7(S-VOC)  ───┴──> P9(S-EVAL)
```

- **P1 통과 전 Codex 스트림 없음.** 계약이 확정돼야 병렬이 의미가 있다.
- P2~P7 은 소유 디렉터리가 겹치지 않으므로 **동시 실행 가능**하다.
  다만 P2(DB) 는 다른 스트림이 repository 를 쓰므로 **먼저 끝내는 것이 이득**이다.
- P9 는 P4·P6·P7 이 있어야 Proposed 군을 돌릴 수 있다. baseline A/B 는 먼저 만들 수 있다.

### 이 프로젝트에서 반복된 실패 유형 (다음에 되풀이하지 않기 위해)

1. **건수만 세는 검증은 내용을 보증하지 않는다** — 코퍼스 5회차, seed 미달
2. **계약에 적었지만 게이트에 넣지 않은 요구는 지켜지지 않는다** — 구체 수치·청크 길이
3. **구조 검사와 동작 검사는 다르다** — route 등록 ≠ endpoint 동작, 코드 존재 ≠ 적재 완료, 컬럼 존재 ≠ 값 기록
4. **`passed` 숫자만 보면 안 된다** — `skip` 이 실패를 감춘다
5. **지표를 조이면 지표를 우회한다** — 무작위 토큰 주입(v3)
6. **스트림을 디렉터리로 쪼개면 경계의 배선이 무주공산이 된다** — 분류기 미연결
7. ★**구현 담당 샌드박스는 외부 네트워크를 못 쓴다** — LLM 실행은 검수 담당이 직접 (`docs/handoff/05` §2-1)
