# 경계를 나누며 생긴 틈, 그리고 승인이 막혀 있던 제안 (2026-09-03)

이 밤 작업의 기록. 두 갈래다 — 하나는 **의도한 작업**(v8 §3-A 교정 이행),
다른 하나는 그 과정에서 **드러난 결함**이다.

## 1. 접수 비동기화 (의도한 작업)

`POST /v1/cases` 가 `run_case()` 를 그 자리에서 기다렸다 — 실측 p50 20~34초 ·
p95 32~51초. `BackgroundTasks` 로 응답 뒤로 뺐다.

계약이 바뀐다: 응답에서 `run_id`·`next_action`·`resume_token` 이 빠지고 일곱
필드로 고정된다. 진행은 `GET /v1/cases/{case_id}` 로 본다.
(`docs/handoff/03` §1-1 갱신, 별도 결함 리포트 있음)

★분류는 접수 안에 남겼다. LLM 한 번이라 수 초고, 그 결과가 있어야 응답이
`intent` 를 실어 보낸다. 느린 쪽은 에이전트 실행이었다.

## 2. ★경계를 나눌 때마다 같은 틈이 생긴다

이번 이틀 동안 경계를 두 번 나눴고, **두 번 다 같은 종류의 틈**이 생겼다.

| 무엇을 나눴나 | 생긴 틈 | 막은 것 |
|---|---|---|
| 분류를 Case 생성 트랜잭션 밖으로 | `classifying` 잔류 | `classification_sweeper.py` |
| 실행을 접수 응답 뒤로 | `routing` 잔류 | `routing_sweeper.py` |

패턴이 같다: **"A 와 B 사이에 죽으면 아무도 다시 안 집는다."** 원자성을 포기해
얻은 것(응답 속도·문의 유실 방지)에는 항상 이 대가가 따른다. 그래서 경계를
나눌 때마다 되잡는 손을 같이 만들어야 한다.

★두 sweeper 모두 **후보 조회 트랜잭션을 작업 전에 닫는다.** 외부(LLM·에이전트)를
기다리는 동안 조회 트랜잭션을 붙들지 않는다 — 이번에 고친 결함이 바로 그것이라
같은 실수를 반복하지 않는다.

### 실패를 한 칸에 뭉치지 않는다

`classification_sweeper` 는 Codex(gpt-5.6) 가 만들었고 구현이 탄탄했다. 검수에서
고친 것은 **실패 분류**다.

    failed   CLASSIFICATION_FAILED 를 **적는 데 성공**했다.
             Case 는 escalated 로 나아가고 다음 회차에 다시 안 걸린다.
    errored  아무것도 못 적었다(전이·DB 오류). Case 는 `classifying` 에 그대로
             남아 **다음 회차에 또 걸린다.**

합쳐 세면 "실패했지만 처리는 됐다" 와 "아무 일도 못 했다" 를 구분할 수 없다.
운영자가 할 일이 다르다. `routing_sweeper` 도 같은 이유로 `started`/`errored` 를
나눴다.

### 가짜 conn 테스트가 못 보는 것

두 sweeper 의 테스트는 DB 없이 `transition_case` 를 monkeypatch 하고 가짜 conn 을
쓴다. 빠르고 절차를 잘 보지만 **SQL 문법과 컬럼 이름을 검사하지 못한다.**
그래서 두 SQL 을 실제 DB 에 걸어 도는 것을 따로 확인했다.

## 3. ★드러난 결함 — 제안 다섯 종류가 승인 단계에서 막혀 있었다

환불 계산을 손보다 발견했다. `verify_proposal` 은 선언되지 않은 필드를
"검사 규칙이 없으면 실행하지 않는다" 로 막는다. 그런데 Team 들이 실제로 싣는
필드 여럿이 정책에 없었다.

| 제안 | 막던 필드 |
|---|---|
| `refund.calculate` | `calculation_basis` |
| `order.create` | `request` |
| `order.modify` | `changes` · `fulfillment_status` |
| `order.cancel` | `scope` · `seller_fault` · `warehouse_handoff` · `fulfillment_status` |

즉 **환불과 주문 변경·취소는 승인 자체가 되지 않는 상태였다.**

### 왜 아무도 못 잡았나

제안을 **만드는 쪽**과 승인 직전 **재검증하는 쪽**을 이어서 보는 검사가 없었다.
각자의 테스트는 전부 초록이었다 — 제안 생성 테스트는 제안이 나오는지만 봤고,
검증 테스트는 **손으로 만든 arguments** 를 썼다. 그 사이에서 새는 것을 아무도
안 봤다.

★2026-08-17 에 `evidence` 로 똑같이 한 번 샜다(그때는 실 브라우저 승인 클릭으로
발견). **그때 검사를 안 만들어서 같은 구멍으로 또 샜다.** 이번엔 만들었다:
`tests/contract/test_proposal_fields_are_declared.py`.

### 전부 `ignored` 로 밀어 넣지 않았다

정책 파일이 스스로 적어 둔 원칙이 있다 — "귀찮다고 빼면 검사 없이 통과한다".

- **`ignored`(설명용, 값을 바꾸지 않는다)**: `calculation_basis` · `request` ·
  `fulfillment_status` · `scope` · `seller_fault` · `warehouse_handoff`
- ★**`opaque`(확인 못 하니 거부)**: `changes` — 고객이 준 변경 요청 **그대로**라
  금액·수량이 들어올 수 있는데 대조할 규칙이 없다.

`order.modify` 는 계속 막힌다. 다만 이제 **의도적 거부**다 — 사고로 막히는 것과
알고 막는 것은 다르다. 푸는 방법(변경 내용을 구조화하고 주문 사실과 대조하는
규칙을 만든 뒤 `quantities` 로 옮긴다)도 주석과 테스트에 적었다.

## 남은 것

- **스케줄러 없음.** 두 sweeper 는 함수와 테스트까지다. 언제 어떤 주기로 돌릴지는
  배치 운영 결정이라 따로 정한다
- **`order.modify` 를 실제로 풀려면** `changes` 대조 규칙이 필요하다
- Codex 는 이 작업 끝에 사용량 한도에 걸렸다(재개 08:43)
