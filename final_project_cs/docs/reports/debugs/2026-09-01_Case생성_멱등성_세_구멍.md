## 3. 구멍 (1) — 동시 요청에서 Case 가 두 개 생기고 감사 기록이 하나 사라진다

`create` 는 `SELECT ... FROM action_requests WHERE idempotency_key=%s` 로
확인하고 없으면 만든다. 그 사이가 열려 있다. 두 요청이 모두 "없다" 를 보면
둘 다 진행한다.

`UNIQUE(tenant_id, idempotency_key)` 가 있으니 뒤엣것이 걸려서 500 이 날 줄
알았는데 아니었다. `create_action_request` 가 충돌을 삼킨다.

```sql
INSERT INTO action_requests (...) VALUES (...)
ON CONFLICT (tenant_id, idempotency_key)
DO UPDATE SET idempotency_key=EXCLUDED.idempotency_key   -- 아무것도 안 바꾸는 갱신
RETURNING action_id
```

그래서 실제로 일어나는 일은 이렇다.

1. 두 요청이 각각 `customer_cases` 행을 만든다. **Case 가 두 개다.**
2. 뒤엣것의 `action_requests` INSERT 는 충돌해서 아무 일도 안 하고,
   **먼저 들어간 행(= Case A 를 가리킴)의 `action_id` 를 돌려준다.**
3. 두 요청 모두 201 로 성공하고, 클라이언트는 서로 **다른 case_id** 를 받는다.
4. 결과적으로 Case B 는 감사 기록이 없다.

멱등성 가드가 조용히 실패한다. 실패했다는 신호가 어디에도 없다.
`ON CONFLICT DO UPDATE` 는 잠금을 얻으려고 쓴 것으로 보이는데, 그 결과가
"충돌을 감지하고 되돌린다" 가 아니라 "충돌을 모른 척한다" 가 되어 있다.

같은 저장소의 `app/application/case_service.py:46` 은 정확히 같은 상황을
`psycopg.errors.UniqueViolation` 으로 잡아 `ActiveRunError` 로 올리고,
왜 그렇게 하는지 주석까지 달아 두었다. `create` 만 그 처리가 없다.

### 고칠 방향 (택일)

- **A.** `create_action_request` 를 `ON CONFLICT DO NOTHING` + `RETURNING` 으로
  바꾸고, 0행이면 이미 있는 것이므로 `create` 가 그 행의 `case_id` 로
  기존 Case 를 돌려주고 **자기가 만든 Case 는 롤백**한다.
- **B.** `create` 를 뒤집어서 `action_requests` 를 먼저 잡고(`case_id` 를 나중에
  채우거나 별도 예약 표를 두고) 성공한 쪽만 Case 를 만든다.
- **C.** 최소 조치로 `SELECT ... FOR UPDATE` 대신 advisory lock 을
  `hashtext(idempotency_key)` 로 잡는다.

어느 쪽이든 **동시 2회 회귀 테스트**가 함께 들어가야 한다. 지금은 없다.

## 4. 구멍 (2) — `CreateCase.idempotency_key` 와 `tenant_id` 가 죽은 필드다

```python
class CreateCase(BaseModel):
    model_config = ConfigDict(extra="forbid")
    request_id: str
    idempotency_key: str | None = None   # ← 어디서도 안 읽는다
    tenant_id: str | None = None         # ← 어디서도 안 읽는다
    ...
```

`grep -n "request.idempotency_key\|request.tenant_id" app/presentation/api/cases.py`
가 아무것도 못 찾는다. 키는 언제나 서버가 `request_id` 로 계산한다.

`extra="forbid"` 라서 오타는 막지만, 이건 오타가 아니라 **받아 놓고 무시하는
필드**다. 클라이언트가 `idempotency_key` 를 보내면 존중될 것이라 믿는다.
실측 표 3행이 그 결과다. `tenant_id` 는 더 위험하다. 만약 나중에 누군가
이 필드를 쓰게 만들면 인증으로 정해진 테넌트를 몸통이 덮어쓰는 길이 열린다.

### 고칠 방향 (택일)

- **A.** 두 필드를 지운다. `extra="forbid"` 이므로 보내던 쪽은 422 로 즉시 안다.
- **B.** `idempotency_key` 를 실제로 존중한다. 오면 그것을 쓰고, 없을 때만
  `request_id` 로 계산한다. `tenant_id` 는 지운다(인증이 정본이다).

B 가 낫다고 본다. HTTP 멱등성 관례는 클라이언트가 키를 주는 쪽이다.
다만 그때는 "같은 키에 다른 몸통이 오면 409" 규칙이 함께 필요하다.

## 5. 구멍 (3) — 판단이 필요함: 같은 뜻, 다른 문장은 별개 Case 가 된다

키의 재료가 `tenant_id + request_id + action_type + business_subject` 이고
`business_subject = f"{customer_id}:{message}"` 다. **문의 원문이 글자 그대로
들어간다.** 그래서 이렇게 오면 Case 가 셋 생긴다.

```
1. "배송 언제와?"
2. "배송 언제오냐고?"
3. "배송 오는 거 언제냐고?"
```

세 번 분류하고, 세 번 팀을 고르고, 세 번 LLM 을 부르고, 세 개의 답이 나간다.
같은 고객의 열려 있는 Case 에 이어 붙이는 로직은 없다(`repository.list_cases`
에 그런 조회가 없고, 이어 붙이려면 클라이언트가 `case_id` 와 resume 토큰을
알고 `POST /v1/cases/{case_id}/messages` 를 불러야 한다).

이건 결함이 아닐 수도 있다. 멱등성은 "같은 요청의 재시도"를 막는 장치이지
"같은 뜻의 다른 요청"을 묶는 장치가 아니다. 다만 **CS 도메인에서는 이게 실제로
자주 일어나고**, 비용과 고객 경험에 바로 닿는다. 지금 어디에도 이 결정이
적혀 있지 않아서 남긴다.

### 결정이 필요한 것

- 같은 고객의 열린 Case 가 있으면 새 Case 대신 그쪽에 이어 붙일 것인가?
  붙인다면 어떤 상태까지를 "열림" 으로 볼 것인가(`resolved` 전 전부? `waiting` 만?).
- 붙이지 않는다면, 중복 문의를 **어디서** 걸러낼 것인가.
  접수 앞단인가, 분류 뒤인가, 아니면 아예 안 거르고 답을 세 번 내보내는가.
- 이 결정을 `docs/handoff/` 어디에 적을 것인가.

## 6. 학습 자료 쪽

`program/onboarding/trace/steps.py:63` 의 문장은 앞뒤를 나눠 보면
뒷문장만 사실이다. 앞문장은 "클라이언트가 같은 `request_id` 를 보낼 때만" 참이고,
지금 저장소에 REST 로 Case 를 만드는 화면이 없어서(`app/presentation/ui`,
`web` 어디에도 `request_id` 를 만드는 코드가 없다) 그 계약을 지키는 주체가 없다.

MCP 경로(`cases.py:247`)는 다르다. 서버가
`sha256("mcp:{customer_id}:{message}")` 로 직접 만들기 때문에 클라이언트가
무엇을 하든 진짜로 한 번이다. 이 차이도 자료에 없다.

자료 문구는 이 리포트의 3~5번이 정리된 뒤에 맞춰 고친다.
