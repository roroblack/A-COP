# 결함 리포트 — 낙관적 동시성 가드가 두 겹이고, 파이썬 쪽을 풀면 결과가 비결정적이 된다

- 발견: 2026-08-31
- 상태: **코드는 고치지 않았다.** 판단이 필요한 사안이라 기록만 남긴다.
- 발견 경위: 테스트 사각지대 회귀 테스트 작업 중 `INV-STATE-001` 이 실행마다
  결과가 갈리는 원인을 추적하다 나왔다.

## 1. 위치

- `app/core/transition.py:143` — 파이썬 쪽 검사 `if current.version != expected_version:`
- `app/core/transition.py:66` — SQL 쪽 검사 `AND version = %(expected_version)s`
- `app/core/transition.py:169` — 0행이면 `StateConflict`

## 2. 무엇을 봤나

같은 규칙이 두 곳에서 강제된다. 파이썬에서 한 번 대조하고, UPDATE 문에서 또 대조한다.
그래서 **파이썬 검사를 풀어도 동작은 대체로 보존된다.** 지난 상태로 덮어쓰려 하면
UPDATE 가 0행을 반환하고 거기서 `StateConflict` 가 난다.

## 3. 재현

`acop_dojo` 의 `INV-STATE-001` 결함(파이썬 검사를 `!=` 에서 `<` 로 바꾼다)을 적용한다.

```
cd acop_dojo
python -c "import sys;sys.path.insert(0,'.');
from acop_dojo.sandbox import Sandbox; from acop_dojo import defects
from acop_dojo.config import target_root
..."   # 전체 스크립트는 docs/evidence/2026-08-31_테스트_사각지대_회귀테스트_검증.md §4
```

## 4. 실측

| 방식 | 결과 |
|---|---|
| 결함 적용 + 전체 테스트 (2026-08-30, 3회) | 2회 통과, 1회 실패 |
| 결함 적용 + 전체 테스트 (2026-08-31) | 실패 1건 |
| 결함 적용 + `test_same_expected_version_has_one_success_and_one_state_conflict` 단독 5회 | **4회 통과, 1회 실패** |
| 결함 적용 + 이번에 추가한 결정적 테스트 3건 | 전부 통과 (동작이 보존되므로 정상) |

단독으로도 갈린다. 처음 세운 "전체 테스트가 같은 PostgreSQL 을 공유해서 생기는
테스트 격리 문제" 가설은 **틀렸다.** 그 가설을 리포트에 적었던 것을 여기서 정정한다.

## 5. 왜 갈리나 — 2026-09-01 확인 완료

**추정이었던 부분을 실측으로 대체한다.** 실패 회차의 traceback 을 붙잡았다.

```
InvalidTransition: 허용되지 않은 전이: running --routed--> ?
  (이 상태에서 가능한 이벤트: ['missing_input', 'approval_required',
   'async_provider', 'completed', 'retry_exhausted', 'guardrail_escalated'])
app/core/transition.py:151  →  app/domain/case.py:63
```

기제는 이렇다. 두 스레드가 같은 `expected_version=2` 로 ROUTED 를 시도한다.

1. 이긴 쪽이 ROUTED 를 적용한다. 상태가 `routing → running`, version 이 3 이 된다.
2. 진 쪽이 projection 을 읽는다. **여기서 갈린다.**

| 진 쪽이 읽은 시점 | 본 값 | 파이썬 검사(`<`) | 그 다음 | 결과 |
|---|---|---|---|---|
| 이긴 쪽 커밋 **전** | version 2, `routing` | `2 < 2` 거짓 → 통과 | `routing --routed-->` 는 유효 → SQL 이 0행 | `StateConflict` → 테스트 **통과** |
| 이긴 쪽 커밋 **후** | version 3, `running` | `3 < 2` 거짓 → 통과 | `running --routed-->` 는 전이표에 없음 | **`InvalidTransition`** → 테스트 **실패** |

`InvalidTransition` 은 테스트의 `except StateConflict` 에 걸리지 않아 스레드 밖으로
튀어나가고, `pool.map` 이 그대로 다시 던져 테스트가 깨진다.

## 5-1. ★앞선 서술을 정정한다

이 리포트의 초판(2026-08-31)에 "파이썬 검사를 풀어도 동작은 대체로 보존된다" 고 썼다.
**절반만 맞았다.** 정확히는 이렇다.

- **상태는 보존된다.** SQL 의 `AND version = %(expected_version)s` 가 지난 상태로
  덮어쓰는 것을 막는다. 이 부분은 초판이 맞다.
- **오류의 종류는 보존되지 않는다.** 진 쪽이 받는 예외가 경합 타이밍에 따라
  `StateConflict`(409, 다시 읽고 재계산) 와 `InvalidTransition`(상태표 위반) 사이에서
  달라진다. 호출자는 이 둘을 다르게 처리한다.

따라서 파이썬 검사는 SQL 과 **중복이 아니다.** 이것이 하는 일은 진 쪽에게
`StateConflict` 를 **결정적으로** 주는 것이다. 이걸 지우면 같은 동시 전이가
어떤 날은 409 로, 어떤 날은 전이 위반으로 보고된다.

## 6. 위험도

**낮음 — 지금 코드에서는 안전하다.** 두 겹이라 하나가 풀려도 상태가 덮어써지지 않는다.
다만 세 가지가 걸린다.

1. 파이썬 검사의 실제 값은 "빠르게 실패시켜 **결과를 결정적으로 만드는 것**"이다.
   중복이라고 판단해 지우면 동시 전이의 결과가 실행마다 달라진다.
2. `docs/handoff/` 계약에는 이 이중 방어가 적혀 있지 않다. 다음 사람이 둘 중 하나를
   중복으로 보고 지울 수 있다.
3. 파이썬 검사가 사라지면 **동시 전이의 오류 종류가 비결정적이 된다.** 같은 상황이
   `StateConflict` 로도 `InvalidTransition` 으로도 보고된다. API 경계에서 전자는
   "다시 읽고 재시도" 이고 후자는 "이 상태에서 할 수 없는 일" 이라 안내가 달라진다.

## 7. 제안

- 코드는 그대로 둔다.
- `app/core/transition.py:143` 주석에 "SQL 에도 같은 조건이 있다. 이 검사는 중복이 아니라
  경합 결과를 결정적으로 만드는 장치다" 를 한 줄 남긴다. (Claude-Core 소유)
- `acop_dojo` 결함 카탈로그에서 `INV-STATE-001` 은 **학습 문제로 쓰지 않는다.**
  잡히는지가 실행마다 달라 같은 문제를 두 번 풀면 다른 답이 나온다.

---

## 8. 해결 — 2026-09-01

**결정적으로 잡는 테스트를 찾았다.** 이 리포트가 "잡히는지가 실행마다 갈린다" 로
남겨 뒀던 문제가 닫혔다.

열쇠는 **예외의 종류**였다. 상태가 이미 지나간 Case 에 낡은 version 으로 쓰면

| | 파이썬 가드 있음 | 가드 풀림(`<`) |
|---|---|---|
| 하는 일 | version 을 먼저 대조 | 그대로 진행 |
| 나는 예외 | `StateConflict` | `InvalidTransition` (전이표에서 걸림) |

둘 다 쓰기를 막지만 호출자에게는 뜻이 다르다. 앞은 "다시 읽고 재계산해라" 이고
뒤는 "이 상태에서 할 수 없는 일" 이다. 그래서 `pytest.raises(StateConflict)` 로
**예외 종류를 고정**하면 단일 스레드에서 결정적으로 갈린다.

- 테스트: `tests/integration/db/test_stale_write_conflict.py`
  `::test_stale_write_on_an_advanced_case_is_a_conflict_not_a_transition_error`
- 실측: 결함을 적용하고 5회 반복 — **5회 모두 실패(=잡음)**
- 그동안 갈리던 동시성 테스트는 두 조회가 모두 끝났음을 보장하지 않아서였다.
  같은 파일의 barrier 테스트가 그 부분을 결정적으로 만든다(§SQL 가드).

이에 따라 `acop_dojo` 카탈로그에서 `INV-STATE-001` 의 제외를 풀었다.
남은 제외는 `INV-CLASS-002` 하나이고 그것은 중복 방어 제거라 잡을 대상이 없다.
