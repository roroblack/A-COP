## 곁들여 — §8-D 「쓰기 계약」 표는 이제 코드와 맞는다

이식해 지금은 맞는다 — 계약 **1.1**, scope `ops:reload`.

살아 있는 프로세스 실측:

```
[1] 시작       active=6cca23ee13b8 desired=6cca23ee13b8 state=active 계약=1.1
[2] 토글       200 · a2a_executor False → True
[3] 토글 직후  active=6cca23ee13b8 desired=2b89b5f40370 state=stale   ← 전에는 여기서 active 라고 답했다
[4] reload     200 {active: 2b89b5f40370, state: active}
[5] reload 후  active=2b89b5f40370 state=active · a2a_executor 실제로 True
```

즉 §8-D 는 **두 문장 중 하나만 고치면** 코드와 완전히 일치한다.

# 두 번째 — §0 「남은 것 둘」이 **둘 다 해소됐다**

§0 「v8 재판정」 끝의 문단이다. 두 항목 다 코드로 재 보니 이미 닫혀 있다.

## (가) 결함 2 — "절반만 고쳐졌다" → **전부 고쳐졌다**

계획서가 적은 것:

> `Controller.run_case()`가 같은 병을 그대로 갖고 있다 — `app/application/
> controller.py:119`에서 트랜잭션을 열고 `:155`에서 Team 실행(LLM 네트워크
> 호출)을 `await`한다. "트랜잭션 안 LLM은 고쳤다"고 말하면 절반만 맞다.

지금 `run_case()` 는 **3단으로 나뉘어 있다**(`controller.py:156~220`).

```
A. 시작·라우팅·재개   with conn.transaction(): ...   → conn.commit()   (195행)
B. Team 실행          ★트랜잭션 밖                     await ...        (205행)
C. 결과 반영          with conn.transaction(): ...   → conn.commit()
```

★**코드를 읽고 판단하지 않았다.** `await` 가 `with self.connection_factory()`
안에 있는 것은 맞다 — 그래서 정적 검사(AST)로는 여전히 "트랜잭션 안" 으로 보인다.
**커넥션을 쥔 것과 트랜잭션을 쥔 것은 다르다.** 실행 중에 쟀다:

```
Team 실행 순간의 실측:
   트랜잭션 상태 : IDLE     (INTRANS 가 아니다 — 열려 있지 않다)
   advisory lock : 0 개
```

`team_executor` 자리에 프로브를 앉혀 `execute()` 가 불린 그 순간의
`conn.info.transaction_status` 와 `pg_locks` 를 읽었다.

★각 단계가 **명시적으로 commit** 하는 이유도 코드에 적혀 있다 — 안 하면 psycopg3
가 다음 `conn.transaction()` 을 새 트랜잭션이 아니라 **SAVEPOINT** 로 열어
(앞선 읽기가 이미 암묵 트랜잭션을 열어 놓으므로) 경계를 좁힌 효과가 통째로
사라진다.

## (나) 결함 3 — "중간발표(9/15) 이후로 미룬다" → **이미 했다**

계획서가 적은 것:

> `run_case` 호출처가 접수 라우트 하나뿐이라 접수가 에이전트 실행 전체를
> 기다린다(실측 p50 20~34초). §21 API 계약 변경과 outbox 트리거 신설이 함께
> 필요하므로 중간발표(9/15) 이후로 미룬다.

지금은 떼어져 있다 — `app/presentation/api/cases.py`:

| 것 | 어디 |
|---|---|
| 떼어낸 실행 | `_run_case_detached()` (`:77`) |
| 배선 | `background.add_task(_run_case_detached, ...)` (`:166`) |
| 실패해도 접수는 산다 | `test_a_failing_detached_run_does_not_break_the_intake` (`:468`) |
| 기다리지 않는다 | `tests/integration/api/test_api_runtime.py:425` |

그리고 호출처는 하나가 아니라 **셋**이다(`check_drift.py` 가 세어 준다):
`controller.py:415`(내부 resume) · `cases.py:93`(접수, 떼어냄) ·
`routing_sweeper.py:81`(되잡기).

★sweeper 가 필요해진 이유가 바로 이 분리다. 접수 응답 뒤로 실행을 빼면 그 사이에
죽은 Case 가 `routing` 에 남는다 — 그걸 되잡는 장치가 `routing_sweeper` 다.
**결함 3을 고치면서 생긴 틈을 같이 막았다는 사실**이 계획서에 없다.

## 제안

§0 「남은 것 둘」 문단을 **「해소됨」 으로 바꾸거나 삭제**한다. 남긴다면 두 항목이
언제 어떻게 닫혔는지와 함께 남긴다 — 지금 상태로는 **끝난 일을 남은 일로**
읽게 한다.

## 이 측정에서 실제로 일어난 일 (숨기지 않는다)

(가)를 재려고 진짜 Controller 를 돌렸다. demo 테넌트의 `routing` Case 1건이
실제로 실행돼 **`resolved` 로 바뀌었고 LLM 호출이 나갔다.** 프로브는 상태만
읽고 실행은 원래 executor 에 그대로 넘겼다 — 그래야 "실제 실행 순간" 을 재는
것이기 때문이다.

## 곁들여 — (나)는 **다른 방법으로** 풀렸다

§25 는 "outbox에 `case.created`를 넣고 worker가 Controller를 깨워" 풀라고 적는다.
실제로는 **`BackgroundTasks` 로 떼어내서** 풀었다. 결과(접수가 안 기다린다)는
같지만 방법이 다르고, outbox 트리거는 안 만들었다.

§25 를 고칠 때 이 차이도 함께 적는 편이 낫다 — 안 적으면 나중에 "outbox 트리거가
어디 갔지" 를 찾게 된다.

## 제안
