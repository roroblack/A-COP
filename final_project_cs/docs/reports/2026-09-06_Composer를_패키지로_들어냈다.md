# Composer 를 패키지로 들어냈다 — 사본이 이미 갈라져 있었다 (2026-09-06)

세 저장소에 걸친 작업이다. sample 커밋 `43d3f09`·`f0e6bad`, 루트 커밋 `f2319aa`.

## 0. 무엇을 하려던 일이었나

v9 §8-D(D-006): **cs 소스 안에 Composer 구현을 두지 않는다.** 중앙 저장 방식이면
UI 프로젝트로, pip 방식이면 관리용 빌드가 `acop_composer` 를 설치·주입하고
릴리즈 때 뺀다. 어느 형태든 구현은 cs 밖이다.

시작할 때 파악한 범위는 "cs 사본 ~400줄 삭제" 였다. 실제로는 그보다 컸다 — 아래
§3 이 왜인지 말한다.

---

## 1. ★사본은 이미 갈라져 있었다 (몰랐던 사실)

"한쪽만 고쳐지는 날이 온다" 는 예상이 아니라 **이미 일어난 일**이었다.

| | sample | cs (2026-09-06 이전) |
|---|---|---|
| `/composer/current` | 있음 | 있음 |
| `/composer/validate` | 있음 | 있음 |
| `/composer/apply` | 있음 | 있음 |
| `/composer/toggle` | 있음 | 있음 |
| `/composer/catalog` | 있음 | **없음** |
| `/composer/changes` | 있음 | **없음** |
| `/composer/revisions` | 있음 | **없음** |
| `/composer/restore` | 있음 | **없음** |

`final_project_ui` 콘솔은 `/composer/catalog` 와 `/composer/changes` 를 부른다
(`console/composer.py`·`console/web.py`). **cs 대상에 붙이면 그 카드가 404 로
안 떴다.** 릴리스 대상에서 안 되는 기능을 참고 구현체에서만 확인하고 있던 것이다.

이 프로젝트에서 되풀이된 무늬 그대로다 — **한 진입점을 고치면 다른 진입점에
같은 결함이 남는다**(REST 고치고 MCP 남김, cs 고치고 sample 남김). 이번엔
"같은 기능의 두 사본" 판이었다.

## 1-1. 그리고 쓰기 채널이 고객 릴리즈에 실려 있었다

`create_app()` 이 composer 라우터를 **무조건** 붙였다. 즉 고객이 닿는 프로세스에
설정 쓰기 표면이 항상 존재했고, 방어가 scope 하나뿐이었다.

지금은 안 붙인다. 실측 — `sys.meta_path` 로 `acop_composer` import 를 막고 기동:

```
차단 확인: acop_composer 는 이 빌드에 설치돼 있지 않다
경로 18개로 기동 · Composer 표면: 없음
/health 200 · /introspection 401(살아 있음) · /composer/current 404
```

**403 이 아니라 404 다.** "권한이 없다" 와 "그런 표면이 없다" 는 다르다.

## 2. 고친 결함 — 1차 분리가 예외 이음매를 끊어 놓았다

sample 커밋 `43d3f09` 로 `service.py` 를 패키지 Protocol 로 옮기면서, 잡는 예외와
던지는 예외가 **다른 클래스**가 됐다.

```
패키지가 잡는 것 : acop_composer.stores.RevisionMismatch
호스트가 던지는 것: acop_basement.core.config_store.RevisionMismatch
하위 클래스인가   : False
→ except 가 조용히 빗나간다
```

결과: 저장소 CAS 가 진 경우 **409 가 아니라 500** 이 나간다.

### 왜 안 보였나

1. `apply_candidate` 가 락 아래에서 revision 을 **먼저** 대조해 대부분 그 전에
   409 로 걸린다
2. 파일 모드(`FileConfigStore`)는 애초에 CAS 를 하지 않는다 — 단일 writer 전제다
3. 남는 것은 **중앙 모드의 진짜 경합** 하나뿐이라 테스트가 안 밟았다

★타입 검사도 못 잡는다. Protocol 은 메서드 모양만 보지 **예외는 안 본다.**

### 고친 방향

예외도 계약으로 보고 **어댑터가 경계에서 옮긴다**(`_TranslatingStore`). 호스트
예외 4종이 패키지 예외로 옮겨지는 것을 실측했다.

| 던진 것 | 잡힌 것 |
|---|---|
| 호스트 `RevisionMismatch` | 패키지 `RevisionMismatch` (`current_revision` 보존) |
| `ConfigStoreError` | `StoreError` |
| `RevisionStoreError` | `StoreError` |
| `AuditStoreError` | `StoreError` |

## 3. ★범위가 예상보다 컸던 이유 — cs 에 없던 것들

"사본 삭제" 로 끝나지 않았다. cs 가 갖고 있지 않아 새로 만들어야 했던 것:

| 것 | 왜 필요했나 |
|---|---|
| `config_from_declaration()` | cs 의 검증은 **파일 경로**로만 됐다. `/validate` 가 후보를 임시 파일로 쓴 뒤 그 파일을 로더에 먹였다 |
| 파일 저장소 3종 | cs 에 저장소 추상이 없었다. `composer_service` 가 직접 파일을 쓰고 JSONL 을 append 했다 |
| 이력 저장소 | cs 에는 **선언 이력이 아예 없었다** — 되돌리기가 불가능했다 |
| scope `composer:admin` | cs 에 없었다 |

★그리고 **`/introspection` 이 `composer_service.revision` 을 import 하고 있었다.**
introspection 은 Composer 를 안 깐 릴리즈 빌드에서도 떠야 하는 코드다 — **선택
기능의 모듈에 필수 경로가 의존**하고 있었다. `config_revision()` 을 코어
(`app/core/project_config.py`)로 옮겼고, 어댑터 codec 도 같은 함수를 쓴다.
두 벌 만들면 `/introspection` 이 말하는 revision 과 Composer 가 말하는 revision 이
갈리는 날이 온다.

이 셋(`config_store` 사정, `introspection` 의존, 이력 부재)은 전부 **찾아보고 나서야**
드러났다. 처음의 "400줄 삭제" 추정은 지운 줄만 세고 **그 줄이 하던 일**을 안 센
것이었다.

## 4. 호스트 계약을 정리하며 뺀 것

패키지가 호스트에게 무엇을 요구하는지가 곧 결합의 크기다. 늘어나면 그 자체가 신호다.

| 뺀 것 | 왜 |
|---|---|
| `settings` · `guardrails` 통짜 콜러블 | 패키지가 `settings().composer_jwt_secret` 처럼 **속성 이름**에 의존한다. 계약이 어디에도 안 적힌 채 생긴다 → 필요한 것을 이름으로 묻는 `AuthPolicy` 로 |
| `config_store_for` · `revision_store_for` | 파일이냐 중앙이냐를 고르는 판단 자체가 **호스트 설정의 일**이다 → `StoreProvider` 하나로 |
| `connection_factory` · `validate_parameters` | 아무도 안 썼다(죽은 필드) |

필드 10 → 8. `audit_dir` 은 이제 실제로 쓰인다(감사·이력 기본 경로).

★`aud` 도 호스트가 준다. 상수로 박으면 sample 용 토큰이 cs 에서 그대로 통과한다 —
대상 격리는 서명만으로 되는 것이 아니다.

★비밀은 **값이 아니라 함수**로 받는다. 프로세스가 뜬 뒤 설정이 바뀌어도 따라가고,
`ComposerHost` 를 로깅해도 비밀이 안 샌다.

## 5. 안 맞춘 것 — revision 형식

sample 은 12자, cs 는 sha256 64자다. **맞추지 않았다.**

맞추면 기존에 발급된 `base_revision` 이 전부 어긋나 저장이 409 로 튕긴다.
revision 은 그 대상 안에서만 비교되므로 형식이 달라도 되고, 굳이 맞출 이유가 없다.
"통일" 은 그 자체로 가치가 아니다.

## 6. 숨기지 않는 계약 변경

- `/apply`·`/restore` 가 `composer:write` → **`composer:admin`**(D-011).
  콘솔이 `/apply` 를 부르지 않는 것을 확인했다(`acop_composer_ui` 클라이언트에는
  메서드가 있지만 콘솔이 안 쓴다)
- 토글 감사 이벤트 모양이 바뀌었다. `target_type`/`previous_active` →
  `resource_type`/`operation` + **`changed_fields`**. 옛 기록은 옛 모양 그대로 남는다
- 토글 거부 코드가 나뉘었다. "그런 대상이 없다"(`invalid_change`) 와 "토글할 수
  있는 종류가 아니다"(`validation_error`) 는 운영자가 할 일이 다르다.
  옛 cs 구현은 둘을 `invalid_declaration` 하나로 뭉갰다

## 7. 게이트 — 없으면 되돌아간다

| 저장소 | 파일 | 막는 것 |
|---|---|---|
| sample | `tests/architecture/test_composer_package_boundary.py` | 패키지가 제품을 import · 코어가 선택 패키지를 import · 조립부 밖 사용 |
| cs | `tests/architecture/test_composer_stays_out_of_this_repo.py` | 사본 3종 부활 · 조립부 밖 사용 · 릴리즈 진입점 오염 · 카탈로그↔등록표 불일치 |

★**양쪽 다 일부러 위반을 넣어 실제로 실패하는 것을 확인한 뒤 되돌렸다.**
통과만 보고 믿지 않는다 — 이 프로젝트에서 "검사하는 척하는 검사" 를 이미 겪었다.

★이 게이트가 필요한 이유는 위반이 **sample 안에서는 아무 증상도 안 내기**
때문이다. 전부 설치돼 있으니 `from acop_basement...` 한 줄은 그냥 동작한다.
증상은 cs 에 pip 로 깐 뒤에야 나온다.

## 10. 남은 것

- **`POST /admin/reload`** 가 cs 에 없다. sample 에는 있다(계약 1.1). cs 는 저장
  뒤 재기동이 필요하고, 응답의 `pending_restart` 가 그 사실을 숨기지 않는다.
  콘솔의 [반영] 버튼은 cs 대상에서 "계약 1.0 이라 미지원" 으로 뜬다
- **중앙 설정 저장소** — cs 범위 밖이다(D-007). `_Stores` 가 중앙 요청을 조용히
  파일로 떨어뜨리지 않고 거부한다
- **콘솔을 cs 관리용 빌드에 실제로 붙여 화면으로 확인** — 이번엔 서버 쪽 왕복까지만
  했다. `CLAUDE.md` §4 는 "UI 가 있으면 실제로 열어서 확인한다" 고 요구한다
