# VISION-08 — Commerce Ops Pack (운영 자동화)

상태: 보류. 10주에는 Runtime 계약과 제한된 Commerce 표면만 검증한다.

## 3. 도입 트리거 (이 조건이 만족되면 재검토한다)

다음 중 하나가 4주 연속 관측되면 도입을 재검토한다.

- 운영자가 직접 처리하는 재고·가격·발주·배송·정산 Case가 월 100건 이상이고, 그중 30% 이상이 반복 workflow다.
- Commerce 운영 Action 종류가 8개 이상이고, 월 50건 이상이 동일 계약으로 실행된다.
- 제한 Commerce 표면의 주문·배송·CS 연결 Case가 월 200건 이상이며, 95% 이상에 구조화된 상품·주문 식별자가 있다.

## 2. 지금 하지 않는 이유

현재 근거 문서는 Commerce를 A-COP 위의 Reference Vertical과 제한 표면으로 정의하며, 상품·주문·결제·배송·정산 전체는 별도 canonical contract와 Adapter가 필요하다고 한다. 10주에 전면 구현하면 Runtime·CS·평가 범위를 잠식한다. 실제 발주·정산·재고 변경은 돈과 운영 상태를 바꾸므로 승인·감사·unknown까지 검증해야 한다.

## 4. 도입 시 예상 비용

| 구분 | 실소요 일수 | 내용 |
|---|---:|---|
| 생성 | 8~12일 | 운영 Team 계약, 재고·가격·발주·배송·정산 상태, Adapter stub, 승인 정책 |
| 검증·통합 | 5~8일 | mismatch·중복·timeout·재처리·권한·trace·운영자 화면 통합 |
| 대기 | 2~4일 | 외부 API sandbox/fixture, 운영자 정책 승인, 데이터 준비 |

병목은 실제 외부 운영 시스템의 계약·sandbox·정책 승인이다. 정확한 비용은 실제 연동 대상 확인 필요.

## 6. 폐기 조건 (이 조건이면 이 비전을 버린다)

위 트리거가 12개월 동안 한 번도 발생하지 않고, 고객이 Commerce Ops를 요구하지 않으며, 제한 표면만으로도 운영 목표를 달성하면 전면 Pack은 폐기하고 기존 팩·Adapter만 유지한다.
