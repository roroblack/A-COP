## 4-A. 멈춘 Case 되잡기 (sweeper, 2026-09-03)

접수·분류·실행을 나누면서 그 **사이에 죽으면 Case 가 중간 상태에 남는다.**
그걸 주기적으로 훑어 다시 처리한다.

| 무엇 | 임계값 | 한 번에 |
|---|---|---|
| `classifying` 잔류 | `classification_stuck_after_seconds: 300` | 100건 |
| `routing` 잔류 | `routing_stuck_after_seconds: 600` | 50건 |

**실행 주기: 60초.**

```bash
python -m scripts.run_sweepers --interval 60
```

★**임계값과 주기는 다른 것이다.** 임계값은 "얼마나 오래 멈춰 있어야 멈춘 것으로
보는가" 이고 이게 **안전**을 정한다 — 짧으면 정상 처리 중인 Case 를 되잡는다.
주기는 "얼마나 자주 확인하는가" 이고 이게 **복구 지연**을 정한다. 그래서 주기를
짧게 잡아도 안전이 나빠지지 않는다. 60초면 복구 지연이 임계값과 거의 같아진다
(분류 5~6분, 실행 10~11분).

★`routing` 임계값을 길게 잡은 이유: 에이전트 실행은 원래 수십 초 걸린다
(실측 p50 20~34초 · p95 32~51초). 짧게 잡으면 **정상 실행을 되잡아** 같은 Case 를
둘이 돌린다.

★**둘 이상 띄워도 된다.** 같은 Case 를 집으면 `expected_version` 낙관적 동시성이
하나만 통과시키고 나머지는 `conflicted` 로 센다. 다만 굳이 여럿 띄울 이유는 없다.

★질의는 부분 인덱스 `cases_stuck_sweep_idx` 를 탄다(마이그레이션 009). 인덱스가
없으면 테넌트의 Case 를 **매분 전부** 읽는다 — EXPLAIN 으로 확인하고 넣었다.

★출력의 `errored` 는 **아무것도 기록하지 못한** 수다. `failed`(분류 실패를
기록함)와 다르고, 다음 회차에 또 걸린다. **0 이 아니면 사람이 본다.**

## 5. Scope (v5 §12)

```
case:read  case:write  order:read  return:read  action:approve  mcp:read
```

| 경로 | 요구 scope |
|---|---|
| `POST /v1/cases` | `case:write` |
| `GET /v1/cases`, `GET /v1/cases/{id}` | `case:read` |
| `POST /v1/cases/{id}/messages` | `case:write` |
| `POST /v1/cases/{id}/actions/{aid}/approve` | `action:approve` |
| MCP 3 tool 전부 | `mcp:read` |

★**MCP 에는 `mcp:read` 외 어떤 scope 도 부여하지 않는다.** 쓰기는 REST + Human Approval 경로만.
