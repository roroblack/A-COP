# 반품 제한을 안 보고 "정책 근거상 검토할 수 있습니다"라고 답한다

## 해결됨 (2026-09-03) — 세 단계를 순서대로

아래 "고치려면" 에 적은 순서 그대로 갔다. **1 없이 2·3 만 하면 "제한 없음"을
사실처럼 단정하게 된다**는 경고를 지켰다.

| 단계 | 한 것 |
|---|---|
| 1 데이터 | `008_products_return_restriction.sql` — `products.return_restriction` 신설. **NULL = 모름**(007 `returns.order_item_id` 와 같은 규약) |
| 2 도구 | `read.catalog` 가 그 컬럼을 반환하도록, `return_refund.allowed_tools` 에 `read.catalog` 추가 |
| 3 판단 | 반품 대상 품목의 상품 제한을 조회해 **세 갈래**로 나눔 |

### 세 갈래

```
제한 있음(made_to_order 등)  → escalated · failure_code=return_restricted_product
                               사유를 warnings 에 담아 사람에게 넘긴다
제한 없음이 확인됨('none')    → 기존대로 "정책 근거상 검토할 수 있습니다"
모름(NULL)                   → **"정책 근거상" 이라고 말하지 않는다.**
                               실제로 확인한 것(기간·이력)만 말하고,
                               상품 제한은 확인되지 않았다고 밝힌다
```

★모름 갈래가 이 수정의 핵심이다. NULL 을 "제한 없음"으로 읽으면 결함이 자리만
옮긴다 — 그래서 **하나라도 모르는 품목이 있으면 주문 전체를 "모름"으로** 둔다
(`_restriction()`).

### 시드에 세 상태가 다 있다

```
NULL(모름)      9  ← 실주문 이력에서 온 상품. 판매자 반품 정책을 우리가 모른다
none            5  ← 데모 상품. 우리가 정의하므로 단정해도 된다
made_to_order   1  ← SKU-CST-06 "Custom engraved tumbler" (제한 경로를 실제로 밟게 하려고 넣음)
```

제한 경로를 데이터로 한 번도 안 밟으면 코드가 있어도 도는지 알 수 없어서
일부러 하나 넣었다.

### 검증

회귀 테스트 4건(`tests/unit/teams/test_return_refund.py`) — 제한 있음 / 제한
없음 확인 / 모름 세 갈래 + allowlist. **622 passed.**

★내 변경이 다른 테스트 하나를 깼고(카탈로그 행이 4-튜플 → 5-튜플),
`tests/integration/db/test_procurement_catalog.py` 를 함께 고쳤다.

★**남은 것**: 청약철회 제한 사유 중 "사용·일부 소비로 가치가 감소한 경우"
같은 것은 **배송 후 물건 상태**에 달렸지 상품 속성이 아니다. 이 컬럼으로
판정하지 않으며, 그건 사람이 본다. 마이그레이션 주석에도 적었다.

---

- 발견 경위: capability 선택 정확도를 측정하다가, 라벨과 어긋난 유일한 케이스
  `g-return-08` 이 **"주문제작 상품인데 반품하고 싶습니다"** 였다. 라벨이
  `return.check_eligibility` 인 이유가 "주문제작이라 반품 대상이 아닐 수
  있어서"인데, **그럼 Team 은 그 제한을 실제로 보는가**를 확인했다.
- 판정: **실재, 미수정.** 데이터 모델까지 걸려 있어 한 줄로 못 고친다.

## 무엇이 문제인가

`ReturnRefundTeam.execute()` 가 `return.check_eligibility` 에서 내는 답:

```python
answer="제공된 주문·반품 이력·정책 근거상 반품 요청을 검토할 수 있습니다."
```

**"정책 근거상"이라고 말한다.** 그런데 실제로 검사하는 것은 둘뿐이다.

| 검사 | 위치 |
|---|---|
| 이미 진행 중인 반품이 있는가 | `active_history = {"approved","processing","completed"}` |
| 반품 기간이 지났는가 | `_policy_days(policy, reason)` 와 `ordered_at` 비교 |

**반품 제한 사유는 하나도 안 본다.** 코퍼스에는 있다:

```
knowledge/documents/13_return_restrictions.md
  "법이 정한 청약철회 제한 사유는 소비자 책임으로 재화가 멸실·훼손된 경우,
   사용이나 일부 소비로 가치가…"
knowledge/documents/08_order_cancel-timing.md
  "주문제작 상품이나 이미 제작에 들어간 맞춤 상품은 일반 취소 절차로
   처리되지 않을 수 있다."
```

즉 **정책 청크는 evidence 로 받아 오지만 판단에 쓰지 않는다.** 기간 계산에
쓰는 `return_period_days` 하나만 꺼내 쓴다.

## 왜 한 줄로 못 고치나 — 볼 데이터가 없다

`products` 테이블에 반품 제한을 나타내는 컬럼이 **없다.**

```
product_id · tenant_id · sku · name · unit_cents · status · updated_at
```

`status` 는 판매 상태(active 등)이지 반품 가능 여부가 아니다. 게다가
`return_refund` 의 `allowed_tools` 에 `read.catalog` 가 없어서 **상품을
조회할 수단 자체가 없다**(`read.order`·`read.order_items`·`read.return`·
`read.policy` 뿐).

즉 이 Team 은 지금 구조에서 "이 상품이 주문제작인가" 를 알 방법이 없다.

## 실제 위험

`CLAUDE.md` §0.1 — "정책 근거를 못 대면 확정 답변을 만들지 않는다."
지금은 반대다: **정책 근거를 댔다고 말하면서 제한 조항은 안 봤다.**

- `return.check_eligibility` → 고객에게 "검토할 수 있습니다" 라고 답한다.
  반품 불가 상품이면 **틀린 확정 답변**이다.
- `return.request` → `ActionProposal` 을 만든다. 다만 여기엔 사람 승인이
  걸려 있고, 승인 화면이 정책 청크를 근거로 함께 보여주므로 **사람이 잡을
  기회는 있다**(2026-09-02 스크린샷에서 확인). 실행 위험보다 **답변 위험**이 크다.

## 고치려면 (셋 다 필요, 순서대로)

1. **데이터** — `products` 에 반품 제한을 표현할 자리를 만든다(예:
   `return_policy` 또는 `is_made_to_order`). 없는 값을 코드로 지어낼 수 없다.
   실제 쇼핑몰 연동 전이면 mock seed 에 넣는 것부터다.
2. **도구** — `return_refund.manifest.allowed_tools` 에 `read.catalog` 를 넣는다.
   지금 Registry 가 막고 있다(2026-09-01 `read.order_items` 를 더할 때와 같은
   상황이다 — 툴은 있는데 allowlist 에 없어 못 썼다).
3. **판단** — 제한에 걸리면 "검토할 수 있습니다" 대신 제한 사유를 근거와 함께
   답하고, 애매하면 `escalated` 로 보낸다. 지어내지 않는다.

★**1 없이 2·3 만 하면 안 된다.** 볼 데이터가 없는데 판단 코드를 넣으면
"제한 없음"을 사실인 것처럼 단정하게 된다 — 지금과 같은 종류의 결함이 자리만
옮기는 셈이다.
