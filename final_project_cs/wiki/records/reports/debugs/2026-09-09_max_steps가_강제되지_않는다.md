# `max_steps` 가 선언만 되고 아무도 강제하지 않는다

## 미해결

- 발견: 2026-09-09, 2026년 다중 에이전트 설계 패턴 연구와 우리 구조를 대조하다
- 판정: **실재.** 기제를 넣었으나 **기존 Team 6개에는 배선하지 않았다**(아래 §결정)
- 위험도: **지금은 낮음 · 여행 도메인에서 높음** — cs Team 6개는 LLM 을 안 부르고
  분기가 유한해서 무한 반복 경로가 없다. 여행 Team 은 **③ 재계획이 LLM 을 쓰므로
  후보를 계속 만드는 경로**가 생긴다

## 어떻게 발견했나

`arXiv:2601.03328`(LLM-Enabled Multi-Agent Systems, 2026-01)이 정리한 설계 패턴
다섯을 우리 구조와 맞춰 보다 나왔다. 그 조사가 함께 말한 실패 모드 중 하나:

> 제약이 약한 에이전트는 같은 문제를 무한히 되풀이한다(loop divergence).
> **최대 반복 횟수나 명시적 종료 조건을 강제하라.**

우리에겐 `TeamManifest.max_steps` 가 있다. **그래서 지켜지는 줄 알았다.**

데였다(선언만 있고 안 쓰는 도구 · 라벨과 정반대를 출력하던 검사 스크립트 등).

## 지금 무엇이 반복을 막고 있나 — 절반만 막는다

```python
# app/tools/read_tools.py:169
signature = name + ":" + json.dumps(arguments, sort_keys=True, ...)
if signature in seen:
    raise ToolLoopExceeded(f"repeated tool request: {name}")
seen.add(signature)
```

| | 막나 |
|---|---|
| 같은 도구를 **같은 인자로** 다시 부른다 | **막는다** — `ToolLoopExceeded` |
| 같은 도구를 **다른 인자로** 계속 부른다 | **안 막는다.** 상한이 없다 |

`seen` 은 **중복 차단기이지 예산이 아니다.** 그런데 그 크기가 곧 호출 횟수라,
예산으로 쓰기에 딱 맞는 값이 이미 손에 있었는데 아무도 안 봤다.

## 왜 지금까지 안 터졌나

cs Team 6개는 **LLM 을 한 번도 안 부른다**(5/6 = 83%, 유일한 예외
`response_review` 는 도구를 안 쓴다). 분기가 유한한 순수 함수라 도구 호출 수가
코드로 정해져 있다 — 실측 최대가 `return_refund` 의 6회다.

★**여행에서는 다르다.** v10 §5 가 각 Team 에 **③ 재계획 후보 생성(LLM)** 을 준다.
LLM 이 후보를 내고 그 후보를 다시 검증하는 구조에서는 **"다른 인자로 계속 조회"**
경로가 자연스럽게 생긴다. 상한이 없으면 한 Case 가 API 예산을 태울 수 있다.

## 넣은 기제

`ReadToolbox.call()` 에 **선택 인자 `budget`** 을 더했다.

```python
def call(self, name, context, arguments, allowed_tools, seen, budget=None):
    if budget is not None and len(seen) >= budget:
        raise ToolBudgetExceeded(f"tool budget {budget} exhausted before '{name}'")
```

- **기본값 `None` 이라 기존 동작이 안 바뀐다** — 호출부를 안 고쳐도 된다
- `seen` 의 크기를 그대로 쓴다. 새 카운터를 만들지 않았다
- `ToolBudgetExceeded` 는 `ToolLoopExceeded` 와 **다른 예외**다 —
  "같은 걸 또 불렀다" 와 "너무 많이 불렀다" 는 원인이 달라 로그에서 갈려야 한다

회귀 테스트 `tests/unit/tools/test_tool_budget.py` 4건:
예산 안 / 예산 소진 / `budget=None` 이면 무제한 / 중복 차단은 그대로.

## ★결정 — 기존 Team 6개에는 배선하지 않았다

배선하려면 도구 호출 지점 **18곳**에 `budget=self.manifest.max_steps` 를 더해야 한다.
하지 않은 이유:

1. **그 여섯은 교체 대상이다.** 도메인이 여행으로 바뀌면서 Team 모듈은 전량 신규다
   (v10 §0-2). 지금 배선하면 버려질 코드에 손대는 것이다
2. **지금 위험이 없다.** 위 §"왜 지금까지 안 터졌나" — LLM 을 안 부르고 호출 수가
   코드로 정해져 있다

★**그래서 이 리포트를 「미해결」로 둔다.** 기제는 있으나 **아무도 안 쓰는 상태**이고,
그건 이 리포트가 지적한 바로 그 문제와 같은 모양이다. **여행 Team 이 이걸 쓰는 것을
보고 나서야 닫는다.**

여행 Team 제작 지침
(`program/briefing/A-COP_Team모듈_제작_브리핑.html`)에 넣었다 —
manifest 표의 `max_steps` 줄과 §4 「연구가 짚은 것 중 안 지키는 것」.

## 다음에 확인할 것

1. 여행 Team 첫 구현이 `budget=` 을 실제로 넘기는지 — **테스트로 고정**한다
2. 상한에 걸렸을 때 무엇으로 끝낼지 — `escalated` 가 맞는지, 아니면 부분 결과를
   내고 `warnings` 에 남길지. **지금은 예외만 던지고 그 뒤 처리가 안 정해졌다**
3. `max_steps` 의 뜻 — 지금은 「도구 호출 횟수」로 해석했다. 원래 의도가
   「추론 단계 수」였다면 다른 값을 세야 한다. **계약 문서에 정의가 없다**
