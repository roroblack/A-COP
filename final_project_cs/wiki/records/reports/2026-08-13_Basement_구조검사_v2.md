결론: “Team을 갈아 끼울 수 있는 Core 골격”은 일부 성립하지만, 현재 저장소는 아직 “무엇이든 올릴 수 있는 Basement”라고 판정할 수 없다. 2차 수정은 capability 하드코딩과 Core→presentation 격리를 개선했지만, 실행 조립·port 연결·도메인/LLM 결합을 제거하지는 않았다(근거: `app/application/controller.py:39-43`, `tests/contract/test_core_isolation.py:5-26`).

## 2-1. Team 교체 가능성

### 실제 추가 파일 수

- Core Registry 자체를 수정할 파일: **0개**. `TeamRegistry`는 생성자에 Team 목록을 받고, `register()`는 `TeamModule`의 `manifest`만 읽는다(`app/core/registry.py:29-46`). Team 이름을 Registry에 하드코딩하지 않는다.
- 새 Team의 manifest/allowed-tools는 별도 등록 파일이 아니라 구현 클래스의 `manifest`에 들어간다(`app/modules/customer_ops/billing.py:16-20`, `app/modules/customer_ops/technical.py:10-14`). 따라서 구현 파일만 추가하면 Protocol 구조상 등록 가능하다.
- 현재 패키지 export 관례까지 유지하는 실제 최소치는 **2개 파일**이다: 새 Team 구현 파일 1개 + `app/modules/customer_ops/__init__.py` export 1개(`app/modules/customer_ops/__init__.py:1-4`). 단, 직접 import하여 `TeamRegistry([NewTeam(...)])`에 주입하면 export 파일은 생략 가능하다(`app/core/registry.py:32-38`).
- Prompt 파일은 Team 계약상 필수가 아니며, 현재 Billing/Technical도 prompt key를 구현 내부에서 호출한다(`app/modules/customer_ops/billing.py:28-39`, `app/modules/customer_ops/technical.py:16-27`). 외부 prompt를 추가하는 경우에만 prompt 파일과 로딩/배선이 추가로 필요하다.
- **생산 실행 경로에는 등록 지점이 없다.** 저장소에서 `TeamRegistry(...)`의 실제 생성은 테스트에만 존재한다(`tests/integration/controller/test_controller_integration.py:131-147`, `tests/integration/controller/test_controller_integration.py:203-204`). API app은 Controller/Registry를 조립하지 않고 feedback router만 연결한다(`app/presentation/api/app.py:16-26`). 따라서 “최소 2개 파일”은 테스트/외부 조립을 포함한 최소치이며, production에서 새 Team을 실제 서비스에 노출하려면 별도 composition root를 만들어야 한다.

### Core의 이름 결합

- `git grep -n "Billing\|Technical" app/core/` 결과: **0건**. Core Registry는 모듈을 import하지 않는다고 명시하고 generic Team 목록만 받는다(`app/core/registry.py:29-36`).
- `TeamModule`만 만족하면 되는 계약은 있다: `manifest`와 `execute(TeamTask) -> TeamResult`가 전부다(`app/core/contracts.py:315-325`). Registry는 contract version, 중복 ID만 검증한다(`app/core/registry.py:38-46`).
- 그러나 실제 Team 클래스는 `ReadToolbox`에 의존하고(`app/modules/customer_ops/billing.py:8-20`, `app/modules/customer_ops/technical.py:6-14`), tool allowlist와 업무 vocabulary를 각 클래스에 직접 둔다(`app/modules/customer_ops/billing.py:17`, `app/modules/customer_ops/technical.py:11`). Protocol만으로 내부 구현의 독립성이 보장되는 것은 아니다.

### 제거 시험의 구조적 결과

- Core에서 Billing/Technical을 제거해도 Core 자체는 깨지지 않는다. Core에는 해당 이름 import가 없고 Registry가 빈 목록도 허용한다(`app/core/registry.py:32-36`).
- 반대로 전체 `customer_ops` 패키지를 제거하면 API app이 `feedback`를 직접 import하므로 깨진다(`app/presentation/api/app.py:5-8`). 개별 Team 제거도 package export와 Team 계약 테스트의 직접 import를 깨뜨린다(`app/modules/customer_ops/__init__.py:1-4`, `tests/contract/test_team_contract.py:3-10`). 즉 **Core 제거 독립성은 성립하지만 서비스 전체 제거 독립성은 성립하지 않는다.**

## 2-2. 도메인 교체 가능성

- Controller의 routing 자체는 `intent`를 `case_type`으로 Registry에 전달하는 generic 코드다(`app/application/controller.py:39-43`, `app/application/controller.py:91-105`). 따라서 HR/물류 Team을 Registry에 넣는 것만으로 이 부분은 재사용 가능하다.
- Core Context는 `customer_id`를 현재 상태에 넣고(`app/application/controller.py:54-60`), read tool은 `customer_id`와 `customers/subscriptions/payments/entitlements` 테이블을 직접 전제한다(`app/tools/read_tools.py:23-34`, `app/tools/read_tools.py:51-89`). HR/물류로 바꾸면 Core orchestration보다 tool/context 및 저장소 경계를 먼저 고쳐야 한다.
- 분류 vocabulary는 customer-ops 종속이다: `feedback.py`가 intent를 `billing|technical|other`로 제한하고 issue code도 결제·권한·로그인 용어로 제한한다(`app/modules/customer_ops/feedback.py:31-40`, `app/modules/customer_ops/feedback.py:61-66`). API의 기본 classifier도 이 모듈을 직접 호출한다(`app/presentation/api/app.py:11-13`).
- 12개 CaseStatus는 `new`, `classifying`, `routing`, `running`, `waiting_*`, `resuming`, `resolved`, `escalated`, `failed`, `cancelled`라는 workflow lifecycle 어휘다(`app/core/contracts.py:53-65`). 일반 업무 Case에도 대체로 적용 가능한 상태이며 고객운영 고유 상태는 아니다. 다만 wait reason에 `customer_input`이 들어가고(`app/core/contracts.py:78-85`, `app/core/contracts.py:243-247`), Evidence source에도 `customer_message`가 들어간다(`app/core/contracts.py:103-109`). 그러므로 완전한 도메인 중립 계약은 아니다.
- guardrail의 reliability/concurrency 수치는 업무 흐름 공통에 가깝다(`config/guardrails.yaml:37-62`). 반면 `security.scopes`에 `subscription:read`, `technical:read`가 있고(`config/guardrails.yaml:89-101`), RAG에 25개 문서·billing/technical corpus 전제가 있으며(`config/guardrails.yaml:64-77`, `knowledge/manifest.json:1-4`, `knowledge/manifest.json:111-129`), feedback surge 설정도 VOC 전용이다(`config/guardrails.yaml:79-87`). 따라서 수치 전체가 도메인 종속은 아니지만 설정 묶음은 종속되어 있다.

## 2-3. 저장소·LLM·전송 교체 가능성

- **Core의 구체 라이브러리 직접 import:** `app/core/transition.py`가 `psycopg.Connection`과 `Json`을 직접 import한다(`app/core/transition.py:19-32`). 또한 Context Core가 `tiktoken`을 직접 import한다(`app/core/context.py:17-25`). Core→`app.infrastructure` import는 0건이지만, DB driver 자체가 Core에 들어와 있어 저장소 교체 경계는 완전하지 않다.
- **OpenAI:** Core에는 `openai` import가 없지만, vector adapter가 OpenAI embedding을 직접 생성한다(`app/infrastructure/rag/retriever.py:6-20`). LLM adapter도 OpenAI를 직접 생성한다(`app/infrastructure/llm/openai.py:11-23`, `app/infrastructure/llm/openai.py:42-53`). 더 나아가 customer feedback가 자체적으로 OpenAI client를 직접 호출한다(`app/modules/customer_ops/feedback.py:47-80`).
- `MessageBrokerPort`는 Core 계약에 선언되어 있으나(`app/core/contracts.py:333-341`), 실제 `OutboxBrokerAdapter`는 infrastructure에 있고(`app/infrastructure/messaging/outbox.py:12-34`), Controller/Case runtime이 이 Port를 주입받아 사용하지 않는다(`app/application/controller.py:27-37`, `app/core/transition.py:116-176`). infrastructure에도 별도 동일 이름 Protocol이 중복 선언되어 있다(`app/infrastructure/messaging/ports.py:6-8`).
- `TeamExecutorPort`는 Controller 생성자에 주입되고(`app/application/controller.py:27-37`), 실행도 Port 형태로 호출된다(`app/application/controller.py:123-134`). 이 Port만큼은 실제 분리가 작동한다.
- `GraphStorePort`는 계약만 있고(`app/core/graph_retrieval/port.py:4-7`), `SqlGraphAdapter`가 실제 구현이지만(`app/infrastructure/graphstore/sql_adapter.py:6-25`), Core/Application에서 주입하거나 호출하는 코드가 없다(저장소 전체 `GraphStorePort` 사용처는 선언부뿐). Graph backend 교체 가능성은 “Port가 존재한다” 수준이다.
- LLM Provider 교체 시 최소 **3개 실행 지점**을 확인해야 한다: Team answer adapter(`app/infrastructure/llm/openai.py:22-51`), vector embedding(`app/infrastructure/rag/retriever.py:6-20`), feedback classifier(`app/modules/customer_ops/feedback.py:47-80`). 설정에 `llm_provider` 필드는 있으나(`app/core/settings.py:39-45`), provider 분기/registry 사용은 없다. 따라서 설정값만 바꿔 Provider가 교체되지는 않는다.

## 2-4. 경계 준수

- `app/core/** -> app/modules/**`: **0건**. `tests/contract/test_core_isolation.py:5-26`가 modules를 금지하고 있으며, 실제 Core import 목록에도 없다.
- `app/core/** -> app/presentation/**`: **0건**. 같은 테스트가 presentation을 금지한다(`tests/contract/test_core_isolation.py:5-26`). 2차 수정의 효과로 이 항목은 유지된다.
- `app/core/** -> app/infrastructure/**`: **0건**. 같은 테스트가 infrastructure를 금지한다(`tests/contract/test_core_isolation.py:5-26`). 단, `app/core/transition.py:26-27`의 `psycopg` 직접 import는 별도 구체 라이브러리 결합이다.
- Team이 `transition_case()`를 직접 부르는 곳: `app/modules`와 `app/tools` 검색 결과 **0건**. Controller/API가 transition을 호출한다(`app/application/controller.py:67-74`, `app/presentation/api/cases.py:76-85`). 이 항목은 지켜진다.
- `customer_cases`를 `transition_case()` 밖에서 UPDATE하는 application code: **0건**. 유일한 projection UPDATE는 `app/core/transition.py:61-66`, 실제 수행도 `app/core/transition.py:151-176` 안이다. `case_service.py:48`은 `agent_runs` UPDATE이며 customer_cases 예외가 아니다.

## 2-5. A2A로 Team 원격 분리

- Controller는 Team을 직접 호출하지 않고 `self.team_executor.execute(task)`만 호출한다(`app/application/controller.py:123-134`). `TeamExecutorPort`의 계약은 `TeamTask -> TeamResult`다(`app/core/remote_team/executor.py:8-9`).
- Local 구현은 Registry에서 Team을 찾아 실행한다(`app/core/remote_team/executor.py:12-19`). A2A 구현은 주입된 transport/resolver로 submit·poll하고 결과를 동일 `TeamResult`로 매핑한다(`app/core/remote_team/a2a_executor.py:10-26`, `app/core/remote_team/a2a_executor.py:46-73`). Local/A2A 계약 테스트도 통과했다: `tests/unit/ports/test_team_ports.py:31-59`, 검사 실행 결과 **46 passed**.
- `LocalTeamExecutor -> A2ATeamExecutor` 교체 시 Controller 본문은 고칠 필요가 없고, 생성 시 `team_executor`를 주입하면 된다(`app/application/controller.py:28-37`). 그러나 production에서 Controller를 생성하는 조립 코드가 없으므로(`app/presentation/api/app.py:16-26`), 현재 서비스 경로에서 교체를 시연할 wiring은 미완성이다.
- Remote 결과는 dict를 `TeamResult.model_validate()`로 검증하지만(`app/core/remote_team/a2a_executor.py:59-67`), 이미 `TeamResult` 객체인 경우에는 `task_id/run_id/team_id`가 현재 task와 같은지 추가 검증하지 않고 그대로 반환한다(`app/core/remote_team/a2a_executor.py:59-60`). 원격 계약의 동일성 보장은 이 경로에서 약하다.

## 2-6. 확장 시 걸림돌

- **가장 먼저 부러질 곳:** 실제 운영 진입점의 조립이다. API app에는 classifier만 연결되어 있고 Controller, Registry, Team executor, Team dependency가 없다(`app/presentation/api/app.py:16-26`). 따라서 새 Team을 추가해도 production request가 이를 자동으로 발견하거나 실행하지 않는다.
- 두 번째 취약점은 도메인 경계다. Controller는 generic routing처럼 보이지만 read tools와 feedback/API가 `customer_id`, subscriptions/payments, billing/technical vocabulary를 직접 전제한다(`app/tools/read_tools.py:23-34`, `app/tools/read_tools.py:51-89`, `app/modules/customer_ops/feedback.py:31-40`, `app/presentation/api/app.py:5-13`). Team 5~10개 또는 HR/물류로 확장하면 이 shared tool/classifier가 충돌 지점이 된다.
- Team 수가 늘면 Registry의 resolve는 `accepted_case_types` 일치 후보를 전부 모아 정확히 하나인지 검사한다(`app/core/registry.py:54-78`). 같은 case type을 여러 Team이 공유하거나 capability namespace가 겹치면 운영 중 충돌한다. 우선순위/버전/tenant별 활성화 정책은 이 코드에 없다(`app/core/registry.py:54-89`).
- 아직 실질적 Port가 없는 지점은 Vector retrieval(`app/application/controller.py:17-19`, `app/infrastructure/rag/retriever.py:30-69`), Message broker(`app/core/contracts.py:333-341`, `app/application/controller.py:27-37`), Graph retrieval(`app/core/graph_retrieval/port.py:4-7`, 사용처 부재), feedback classifier(`app/presentation/api/app.py:11-13`)다.
- `app/core/transition.py`의 DB SQL/psycopg 결합(`app/core/transition.py:26-32`, `app/core/transition.py:61-66`)은 저장소를 바꿀 때 Core를 수정하게 만드는 가장 직접적인 구조적 걸림돌이다.

## ★가장 먼저 부러질 곳

**production composition root 부재**가 1순위다. Controller는 Registry/TeamExecutor를 주입받도록 설계되어 있지만(`app/application/controller.py:27-37`), API app은 그 객체를 만들지 않는다(`app/presentation/api/app.py:16-26`). 따라서 현재 코드는 테스트에서 `TeamRegistry([DemoTeam()])`를 조립할 수는 있어도(`tests/integration/controller/test_controller_integration.py:131-147`), 서비스에서 “새 Team을 등록하면 자동으로 Case lifecycle에 들어간다”는 주장을 입증하지 못한다.

그 다음은 Graph가 실제 Context 경로에 연결되지 않은 점이다. Graph adapter는 SQL JOIN/recursive CTE를 수행하지만(`app/infrastructure/graphstore/sql_adapter.py:25-56`), `ContextInputs`에는 policy/similar cases만 있고 Graph 입력이 없다(`app/core/context.py:69-83`). 따라서 “Vector는 유사성, Graph는 연결 관계”라는 4축 설명이 실행 흐름으로 완성되지 않았다.

## 1차 대비 2차 수정 효과

- 개선됨: 1차의 Controller capability 하드코딩 지점은 제거되었고, 지금은 Registry resolve/capability 선택을 사용한다(`app/application/controller.py:39-43`, `app/application/controller.py:91-97`). 새 Team capability를 Core Controller에 별도 case문으로 추가할 필요는 없다.
- 개선됨: Core 격리 테스트 금지 목록이 modules, presentation, infrastructure, application까지 포함한다(`tests/contract/test_core_isolation.py:5-10`). 실제 Core의 해당 import는 0건이다.
- 여전히 부분: `app/core/transition.py`가 `psycopg`를 직접 import한다(`app/core/transition.py:26-27`), Graph/Message Port가 runtime에 연결되지 않는다(`app/core/graph_retrieval/port.py:4-7`, `app/core/contracts.py:333-341`), production Registry/Controller wiring이 없다(`app/presentation/api/app.py:16-26`).
- 새 Team 추가 파일 수 재검산: **Core 변경 0개, 최소 1개(구현 파일), 현재 package export 관례까지 포함하면 2개**(`app/modules/customer_ops/__init__.py:1-4`). 다만 production 실제 등록 지점이 없으므로, 운영 배선까지 요구하면 별도 composition 파일을 추가하고 그곳을 수정해야 한다.

## 확인하지 못한 것
