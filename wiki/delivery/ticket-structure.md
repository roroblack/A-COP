# 티켓 구조

`[실측]` `A-COP_티켓구조_재편_계획.md`에서 이관. **원본은 그대로 있다.**

TeamFlow(`SKN32_FINAL_TEAM4`, 프로젝트 id 84)에서 관리한다.

`[실측]` **프로젝트 이름이 TEAM4지만 우리 팀은 6팀이다.** TeamFlow 쪽 이름이 잘못 붙은 것이고 id 84는 그대로 쓴다.

## 세 층

```
에픽 (epic)          몇 주짜리 성과 단위.  스프린트·날짜 없음
 └ 스토리 (story)     1~3일.  스프린트와 날짜는 여기에 붙는다
    └ 작업 (task/bug) 몇 시간. 부모 스토리 없이는 만들지 않는다
```

**스프린트는 이 층에 끼지 않는 별개의 축이다.**

## 층별 규칙

| 층 | 타입 | 스프린트 | 시작·마감일 | 담당자 | 부모 |
|---|---|---|---|---|---|
| **에픽** | `epic` | **없음** | **없음** | 총괄 1명 | 없음 |
| **스토리** | `story` | 있음 | 스프린트 범위 안 | 실제 작업자 | 에픽 |
| **작업** | `task` `bug` | 스토리와 같게 | 실제 작업일 | 실제 작업자 | **스토리** |

## ★ 에픽에 기간을 안 적는다

> **그 아래 스토리들이 걸친 범위가 곧 에픽 기간이다.**

**에픽에 날짜를 박으면 스토리가 밀릴 때마다 두 곳을 고쳐야 한다.** 한 곳만 관리한다.

## 작업은 부모 없이 못 만든다

**스토리 없는 작업은 어느 성과에 속하는지 모른다.**

급한 일이 생겨도 스토리를 먼저 만든다.

## 스프린트

`[실측]` 공식 기간을 **4개 스프린트 + 보완 구간**으로 나눈다.

**9개 주차·6개 수행단계 안을 버렸다.** 발표와 자연 경계에 맞췄다.

→ [timeline.md](timeline.md)

## 티켓 작성 규칙

`[실측]` 루트 `CLAUDE.md`가 정한 것.

> **티켓에 내부 코드·줄임말을 쓰지 않는다. 용어 풀이를 붙인다.**

**처음 보는 사람 기준으로 쓴다.**

## API 제약

`[실측]` `.env.teamflow`의 토큰으로는 **이슈 생성만 된다.**

```
조회 · 수정 · 스프린트 생성  →  화면에서 사람이 한다
```

**형식은 `.env.teamflow.example`을 본다.** 실제 파일은 커밋하지 않는다.
