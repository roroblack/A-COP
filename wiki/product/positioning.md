# 포지셔닝

`[실측 2026-09-09]` 근거는 v11 §0-1·§1·§4-A·§11.

## 원라이너

> 여행 계획을 **만드는** 건 이미 여럿이 합니다. 그 계획이 **실제로 성립하는지**, 그리고 **여행이 끝날 때까지 계속 성립하는지**는 아무도 안 봅니다.

## 제품 정의

**가고 싶은 곳과 예약을 주면 전체 여행이 성립하는지 검증하고, 여행이 끝날 때까지 상황 변화를 먼저 감지해 남은 일정을 조정하는 여행 CS 플랫폼**(v11 §0-1).

| | |
|---|---|
| 1순위 고객 | **처음 한국에 자유여행 오는 외국인 개인·친구 그룹**(인바운드) |
| 판매 형태 | **팀당 여행 이용권.** 기준 상품 7일·4인·2도시 59,000원 |
| 접점 | **둘이다** `[결정 2026-09-10 오후]` — ①**개인 에이전트 API** ②**여행계획서 링크**(여행별 토큰, 로그인 없음). 자체 앱·음성은 만들지 않는다 |

★**쇼핑몰 판에서 이 문서는 B2B 였다** — 기업 CS 조직에 파는 플랫폼이었다. v10 은 **여행팀 본인에게 이용권을 판다.** 사는 사람이 바뀌었으므로 아래 모든 논거의 상대도 바뀐다. → [personas.md](personas.md)

## 말하지 않는 것

**"AI 가 여행 일정을 짜 준다"로 설명하면 시장의 기존 제품과 구분되지 않는다.**

★**계획 생성은 우리 일이 아니다**(v11 §4-A). 외부 개인 에이전트나 LLM 이 만든 일정을 **받아서** 검증하고 지켜본다. 생성을 우리 기능으로 말하는 순간 트리플·Mindtrip 과 같은 칸에 들어간다.

그래서 자동화율을 앞세우지 않는다. 대신 세 가지를 함께 제시한다.

| | |
|---|---|
| **성립 판정** | 이동 시간·영업시간·동행 조건까지 맞춰 **전체가 되는가**를 코드가 판정한다 |
| **선제 감지** | 고객이 알기 전에 우리가 알아채고 조정한 뒤 통지한다 |
| **잘못 실행하지 않는 지점** | 업체 예약은 승인 없이 건드리지 않고 **변경 링크로 넘긴다** |

## 겨냥하는 공백

`[실측]` v11 §11.

| 질문 | 답 |
|---|---|
| "일정 생성 앱과 뭐가 다른가" | 생성을 하지 않는다. **성립 검증과 종료까지의 지속 관리**가 제품이다 |
| "트리플·Mindtrip 도 하지 않나" | 일정 생성·수정·여행 중 추천은 한다. 우리가 겨냥하는 공백은 **외부 개인 에이전트의 맥락을 받아 여행 종료까지 선제 관리 루프를 운영하는 것**이다 |

★**그 공백 주장의 근거 등급을 낮춰 적는다.** `[실측]` v11 §11 — 사용자 직접 관찰에서 Mindtrip 의 자동 추적·외부 에이전트 연동은 **확인되지 않았다.** 다만 **기능 부재가 입증된 것은 아니다.**

★**"성능이 더 낫다"고 말하지 않는다.** v11 §11 — **비교 시험을 수행하지 않았다.** MVP 통과 기준은 §8 이고 그건 경쟁 비교가 아니다.

`[미확보]` **여행 시장의 경쟁 격차표가 없다.** 쇼핑몰 판에는 G1~G7·E3~E5·H1~H5 로 정리된 표가 있었는데(아래) 그건 Intercom Fin 등 CS 자동화 제품을 겨냥한 것이다. **여행 쪽 대응 조사는 안 했다.**

## 양면 구조

**고객 면.** 고객은 **자기 개인 에이전트를 통해서만** 우리를 만난다. 우리 출력이 그대로 고객에게 옮겨지므로 근거와 확인 시각이 형식의 일부다.

**운영자 면.** human-on-the-loop 다. 고위험 Action 만 사람이 승인하고, 나머지는 자동 처리하되 운영자는 넘어온 건과 이상 신호를 본다. `[결정 2026-09-10]` **언어는 한국어 한 벌이다** — 고객 통지도 운영자용도 같다(v11 §5-A). **번역은 고객 에이전트 몫이고 그 품질을 우리가 보증하지 못한다.**

**감독이 성립하려면 "이상"이 정의돼 있어야 한다.** 이상은 절대값이 아니라 **기준선 대비 정해진 변화가 생긴 상태**로 정의한다. 임계값은 실제 분포 측정 후 확정한다. `[미확보]`

## 시연과 실제 동작을 섞어 말하지 않는다

★**이게 이 제품에서 가장 조심할 자리다.** v11 §10 리스크 — **"시뮬레이터를 실적으로 오해"**.

| | 지금 무엇인가 |
|---|---|
| 우리 DB 의 일정 조정 | **실제 동작.** 먼저 고치고 통지한다 |
| 업체 예약 변경 링크 | **실제 동작** |
| 협약사 자동 실행 | **시연이다.** Mock 공급자(`tier == 'simulated'`)에서만 |

**"예약 자동화가 된다"고 말하면 거짓이 된다.** 기본 규칙은 승인 필수이고, 자동 실행은 협약이 됐을 때의 모습을 보여주는 것이다. 산출물마다 시연임을 표시한다.

★**게이트를 문서가 아니라 아키텍처 테스트로 막는다**(DoD-14·15). 자동 실행 분기가 Mock 밖으로 새면 고객 돈이 나간다.

## 데이터를 어떻게 말하나

`[실측]` v11 §11 — 국내 기본 정보와 액티비티 규정·기상은 공개다. **예약·현장 데이터는 합성이며 그렇게 표시한다.**

★**"실데이터로 검증했다"고 말할 수 있는 범위가 좁다.** 공개 API(기상·관광정보)와 규정 문서까지다.

## 제공 형태는 구조적 성질이다

Team 은 Registry 등록형이라 **도메인을 갈아 끼워도 Core 가 거의 안 바뀐다.** 2026-09-08 에 커머스 → 여행으로 실제로 한 번 갈았다.

★**단 "Core 를 하나도 안 고친다"는 문자 그대로는 안 지켜졌다** — `app/core/project_config.py` 의 구현 참조 허용 목록과 `app/core/settings.py` 의 외부 소스 칸을 손으로 고쳐야 했다(`[실측 2026-09-09]`). 상세와 갈래 셋은 [../architecture/pack-model.md](../architecture/pack-model.md).

★**이건 아키텍처 성질이고 판매 논거가 아니다.** v10 은 "기업이 자기 Team 을 꽂아 쓰는 플랫폼"을 판매 형태로 쓰지 않는다 — 판매는 여행팀당 이용권이다. **둘을 섞어 말하면 심사에서 무엇을 파는지 흐려진다.**

## 가격

`[실측]` v11 §1 — 기준 상품 7일·4인·2도시 **59,000원**(VAT 포함).

`[미확보]` **수용 여부를 안 검증했다.** v11 §0-3 — 유료 파일럿 20~30팀으로 확인하며 그건 MVP 이후다. 그리고 **인바운드 전제의 손익 재계산**(해외 카드 수수료·환율·영어 채널 획득비)도 결제 수단 결정 뒤로 미뤄져 있다.
