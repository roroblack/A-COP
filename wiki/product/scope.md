# 범위

## 타깃 도메인

★**[2026-09-08 판올림] 1차 도메인은 여행 CS다.** 커머스 CS에서 교체됐다(계획서 v10). 아래 「옛 도메인」 절에 이전 판을 남긴다 — 지우면 그때 왜 그렇게 판단했는지가 사라진다.

> **가고 싶은 곳과 예약을 주면 전체 여행이 성립하는지 검증하고, 여행이 끝날 때까지 상황 변화를 먼저 감지해 남은 일정을 조정한다.**

| | |
|---|---|
| 1순위 고객 | **처음 한국에 자유여행 오는 외국인 개인·친구 그룹** (인바운드) |
| 접점 | **둘** `[결정 2026-09-10 오후]` — ①개인 에이전트(OpenClaw·Hermes 등) **API** ②**여행계획서 링크**(여행별 토큰, 로그인 없음) |
| 언어 | **한국어 하나** `[결정 2026-09-10]` **고객 언어로 옮기는 것은 개인 에이전트가 한다.** 우리는 다국어를 지지 않고 **번역 품질을 보증하지 못한다** |
| 지역 | **서울** 1도시 `[실측]` 사용자 결정 2026-09-10 |

### ★ 둘을 좁히는 이유가 다르다

`[실측]` 사용자 결정 2026-09-09 → [../decisions/D-016-scope-narrowing-reasons.md](../decisions/D-016-scope-narrowing-reasons.md)

| | 왜 좁히나 | 안 좁히면 |
|---|---|---|
| **도시** | **검증 편의성.** 공개 API 를 부르면 전국이 들어오므로 **기술 제약이 아니다** | 시스템은 돈다. **"우리가 다 검증했다"고 말할 분모가 없다** |
| | ★**서울로 정해졌다**(2026-09-10). "서울에서 검증했다"이지 **"서울만 된다"가 아니다** | |
| **언어** | **책임 경계.** 고객은 자기 에이전트를 통해 들어오고 그 에이전트가 번역한다 | 다국어가 우리 층의 일인 것처럼 읽힌다 |

★**언어는 MVP 절삭이 아니다.** 아래 「이번엔 뺀다」에 중국어·일본어가 있으면 나중에 넓힐 것처럼 읽히는데, **넓힐 일이 아니다.**

`[미확보]` **개인 에이전트가 실제로 번역을 해 주는지 확인하지 않았다.** 시연에서 붙일 에이전트 1종으로 직접 확인해야 한다.

**계획 생성은 우리 일이 아니다.** 외부 에이전트·LLM이 만든 일정을 받아 검증하고 감시한다 → v11 §4-A.

대표 시나리오 여섯.

```
일정 수신·검증 · 예약 시간 충돌 · 이동 여유 부족
휴무·운영 변경 감지 · 기상 변화로 재계획 · 업체 예약 건 인계
```

`[실측]` **골든셋 72건은 쇼핑몰 시나리오다.** 평가 하네스는 승계하되 정답 시나리오를 교체해야 한다 → v11 §8.

## In Scope — MVP 7주

`[실측]` v11 §9-A. 구현 단계 1(**계획·검증·지속관리**)까지가 MVP다. ★`[정정 2026-09-10]` 초판은 「계획과 검증」이라고만 불렀는데 **감시·조정·통지가 단계 1 안에 있다** — 이름이 범위를 줄여 읽히게 했다.

| 영역 | 포함 |
|---|---|
| 수집·분류 | 인라인 분류 라벨 다섯 — **일정 제출 / 사건 신고 / 확인 요청 / 조정 거부 / 그 외** |
| Trip | 최신 일정 버전 + 잠긴 예약 + 필수 조건 + 다음 확인 시점 + **통지·재요청 이력** + 제시했던 다른 안 |
| Case | 상태 12종 승계. **시스템도 Case를 만든다** — `trigger_source`(customer·schedule·supplier) |
| Team | **Activity**·**Booking Handoff** 둘이 MVP 필수. Dining·Mobility는 그다음, Lodging/Flight는 등록만 |
| 검증 API | 엔드포인트 하나 — 코드 검증 / 확인 수준·시각 / 불가능 사유·완화 조건. 결과는 `ActionProposal` |
| 지속 관리 루프 | 로컬 주기 작업. 최소 주기 = 출발 전날 / 매일 아침 / 각 예약 2시간 전 |
| **일정 안내** `[2026-09-10 오후]` | 세 시점 — ①변경(**생성 포함**) ②여행·하루 시작 ③**각 항목 출발 시각**(이동 시간에서 역산). ③은 **어디로·언제 나서나·어떻게 가나(경로)** 를 담고 **그때 조회한다**. Case 를 만들지 않고 LLM 을 안 부른다 → [../architecture/notifications.md](../architecture/notifications.md) |
| 선제 조정 | 변화 감지 → 재계획 → 재검증 → **최고 안 하나 적용** → 통지 → **재요청 시** 되돌림·교체 |
| 업체 건 인계 | 바꿀 항목·대안·차액을 정리한 **변경 링크**. 우리 일정은 먼저 고쳐 두고 업체 건만 넘긴다 |
| Action | **장소·운영 조회 / 이동 시간 조회 / 기상 조회** 세 개 (Mock 허용) |
| 외부 연결 | 텍스트 API + 여행별 토큰. 개인 에이전트 1종 연결 시연 |
| 인프라 | **로컬 실행 + 외부 LLM API** |

**인라인 분류는 선택 기능이 아니다.** 이 규칙은 도메인이 바뀌어도 그대로다 — 분류가 실패하면 `classification_failed`를 남기고 `escalated`로 전환한다.

### ★ 실행 경계 — 업체 예약은 승인 없이 실행하지 않는다

`[실측]` v11 §4-C. 승인 게이트(D-005)는 승계하되 적용 범위를 나눈다.

| | 어디에 |
|---|---|
| **Pre-CS**(먼저 조정하고 통지) | **우리 DB의 일정 버전에만** |
| 협약사 자동 실행 | **`supplier.tier == 'simulated'` 일 때만.** 시연 범위이지 운영 규칙이 아니다 |
| 비협약사·위임 범위 밖 | 실행하지 않고 변경 링크로 넘긴다 |

일정 버전은 **불변(append-only)**이다. 되돌리기는 이전 버전을 복사해 새 버전을 만드는 것이지 버전을 지우는 것이 아니다.

## Out of Scope

**이게 In Scope보다 중요하다.** 7주에 아무것도 못 끝내는 이유는 늘 범위다.

| 제외 | 왜 |
|---|---|
| **계획 생성기** | 외부 에이전트·범용 LLM과 정면으로 겹친다. 우리는 검증·감시다 |
| 다도시·가족·한국인 해외여행 | 1도시·인바운드 개인·친구로 통제한다 |
| 중국어·일본어 | **우리 층의 일이 아니다.** 개인 에이전트가 옮긴다 — 「다음 후보」가 아니다 |
| **실제 업체 계약·연동·실결제** | 협약사 자동 실행은 Mock 공급자 시연까지 |
| 링크 클릭 이후 추적 | 변경 링크 생성까지가 MVP |
| OR-Tools 최적화·보행·피로 모델 | 코드 판정과 규칙 재계획까지 |
| 동시 수정 충돌 처리·백업·복구 | 단일 인스턴스 전제 |
| 업체 웹훅·클라우드 스케줄러 | 로컬 주기 작업 |
| 자체 앱·음성(STT/TTS) | **여행계획서 링크는 자체 앱이 아니다** — 토큰 붙은 주소 하나이고 고객이 일정을 직접 편집하지 않는다 |
| Cloud Run·Supabase 배포 | 로컬 실행 |
| OCR·영상 분석 | 입력을 텍스트로 고정한다 |

## Team 범위

`[실측]` v11 §5. Team은 지역 상품이 아니라 **여행을 구성하는 객체 종류**로 나눈다. 도시를 늘리는 것은 데이터 추가이고, Team을 늘리는 것은 객체 종류 추가다.

| Team | 상태 |
|---|---|
| **Activity** | **MVP 필수.** 취소·변경 규정이 문서로 존재해 판정 규칙을 바로 쓸 수 있고 예약금이 걸려 실패 비용이 크다 |
| **Booking Handoff** | **MVP 필수** (2026-09-08 등록만에서 승격). 감지해서 우리 일정을 고쳐도 업체 예약을 못 바꾸면 고객이 직접 처리하게 된다 |
| Dining · Mobility | 그다음 |
| Lodging / Flight | 등록만. 잠긴 예약으로 취급 |

각 Team은 셋을 갖는다 — 검증 규칙 · 감시 소스 · 재계획 후보 생성. **전체 일정 정합성(시간 충돌·예산·이동 여유)은 Team이 아니라 코어 검증 층이 본다.** Team 안에서도 판정(코드)과 대안 생성(LLM)을 나누고, 생성한 대안은 판정을 다시 통과해야 통지된다.

## 옛 도메인 — 커머스 CS (2026-08-18 ~ 2026-09-08)

지우지 않는 이유는 골든셋·평가·사업성 숫자가 아직 이 범위에서 나왔기 때문이다.

| | |
|---|---|
| 도메인 | 온라인 커머스 고객운영. 그전에는 가상의 SaaS Customer Operations였다 |
| 대표 시나리오 | 주문 확인 · 배송 예외 · 반품 요청 · 반품 가능 여부 · 환불 금액 산정 · 반복 불만 탐지 |
| Pack | CS Pack(VOC & Store Manager, Response Generation & Review) + Commerce Ops Pack(Procurement+Order&Payment, Fulfillment&Logistics, Return&Refund, Catalog&Verification) |
| v10 처리 | 커머스 Team 4종과 VOC & Store Manager는 **MVP 경로에서 제외.** 등록은 남겨도 호출되지 않는다 |
| 남는 것 | 코어 계약·생명주기·동시성·감사·평가 하네스 → v11 §0-2·§6 |

## 지연이 만드는 범위 제약

`[실측]` Case 한 건 p50 20~34초, p95 32~51초다(쇼핑몰 경로 실측이라 여행 경로에서 다시 재야 한다).

여행에서는 이 수가 다르게 걸린다. **접점이 API 하나**라 채팅 자동응답 문제는 사라지지만, 대신 두 자리가 걸린다.

| 쓰임 | 지금 지연으로 되나 |
|---|---|
| 일정 검증 API 응답 | `[미확보]` 에이전트가 기다릴 수 있는 상한을 안 정했다. **코드 판정만 하는 경로는 LLM을 안 부르므로 훨씬 빠를 것**이다(v11 §4-D) — 재야 한다 |
| 지속 관리 루프 (출발 전날·매일 아침·예약 2시간 전) | 가능. 주기 작업이라 초 단위 지연이 문제가 아니다 |
| 변화 감지 → 재계획 → 재검증 → 통지 | 가능. 다만 예약 2시간 전 감지에서는 통지까지의 총 시간이 상한이다 |

★**v11 §4-D가 이 자리를 나눈다** — 계산으로 판정 가능한 것(시간 충돌·이동 여유·예산·필수 조건)은 코드가 하고 LLM을 부르지 않는다. 지연이 붙는 곳은 대안 생성뿐이다.

`[실측]` 옛 서술: 골든셋 채널 분포가 web 23 / chat 23 / email 17 / phone 9이라 chat 23건(32%)이 지연으로 어렵고, 제품이 "실시간 자동응답"이 아니라 "상담원 보조"로 좁혀진다고 적혀 있었다. **쇼핑몰 판의 판단이고 여행에는 채널 개념 자체가 없다.**

## Vision — 지금 안 하는 것

나중에 할 수 있지만 MVP 7주에는 안 한다.

- 거래 실행 — 계약된 업체부터 결제·변경·취소 (구현 단계 4)
- 데이터·지역 확장 (구현 단계 3)
- Graph Store 도입 (채택 게이트 통과 시에만)
- 자체호스팅 실제 배포

## 범위 통제 방법

범위 과대가 이 프로젝트의 1번 리스크다. 다음 기준선으로 통제한다.

```text
도메인          1개 (여행)
도시            1개 (서울)   ← 검증 주장의 분모. 기술 제약이 아니다
언어            1개 (한국어) ← 책임 경계. 고객 언어는 에이전트가 옮긴다
MVP 필수 Team   2개 (Activity · Booking Handoff)
```

★**위 넷 중 셋만 "좁힌 것"이다.** 언어는 좁힌 게 아니라 **그 일이 우리 층에 없는 것**이다(D-016).

**Team 수는 아키텍처 상한이 아니다.** Registry 등록으로 확장되는 값이고, 확장 여부는 일정과 평가 여력(골든셋·라우팅 평가 축 증가)으로 판단한다.

`[미확보]` v10에 `A2A`·`MCP`·`Docker`·`AWS` 문자열이 0회다. 쇼핑몰 판의 외부 연동 범위를 뺀 것인지 빠뜨린 것인지 안 정해졌다.
