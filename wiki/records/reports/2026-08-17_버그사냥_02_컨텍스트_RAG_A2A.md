# S-BUGHUNT-02-CONTEXT-RAG-A2A — 컨텍스트·RAG·A2A·라우팅 버그 사냥

스캔 범위: `app/core/context.py`, `app/infrastructure/rag/retriever.py`,
`app/core/remote_team/executor.py`, `app/core/remote_team/a2a_executor.py`,
`app/core/registry.py`.

코드 수정은 하지 않았다.

### app/core/remote_team/executor.py:18-19 — Local executor가 manifest의 allowed_tools를 task 값과 대조하지 않음
- 시나리오: 호출자가 `team_id="billing_subscription"`인 `TeamTask`를 만들면서 `allowed_tools=["read.account"]`처럼 manifest의 `allowed_tools` 밖 값을 넣는다. `LocalTeamExecutor.execute()`는 Registry에서 module만 꺼내 곧바로 `module.execute(task)`를 호출하므로, module이 task의 목록을 신뢰하는 구현이면 Billing Team이 원래 manifest에 없는 tool을 호출할 수 있다. 반대로 악성/오류 Team 구현이 toolbox를 우회해 직접 tool을 호출해도 이 경계에서 차단하지 않는다.
- 왜 기존 테스트가 못 잡는가: 기존 테스트는 정상 manifest 목록을 task에 그대로 넣거나(`tests/unit/teams/test_team_scenarios.py`), `ReadToolbox.call()` 자체가 전달받은 `allowed_tools` 밖을 거부하는지만 검사한다. Registry/Local executor가 task 목록을 manifest와 비교하지 않는 입력은 검사하지 않는다.
- 재현 시도: 코드 읽기로 판단. `LocalTeamExecutor.execute()`에 manifest와 task의 목록을 비교하는 검사가 없고, `TeamTask.allowed_tools`는 호출자가 설정할 수 있다. 재현 안 해봄, 코드 읽기로만 판단.
- 위험도: 높음

### app/core/remote_team/a2a_executor.py:17-25 — deadline이 지난 A2A task도 submit/poll을 먼저 무기한 대기하고 원격 취소하지 않음
- 시나리오: 이미 `deadline_at`이 지난 task 또는 원격 transport의 `submit()`이 응답하지 않는 task를 실행한다. executor는 deadline을 확인하기 전에 `await self._submit(endpoint, task)`를 끝낼 때까지 기다린다. submit이 끝나서 polling 단계에 들어간 경우에도 `await self._poll(remote, task)`가 먼저 실행되므로 poll 하나가 hang하면 deadline 검사가 실행되지 않는다. deadline에 도달한 뒤에는 로컬 `failed` 결과만 반환하며 `transport.cancel()`을 호출하지 않아 원격 작업이 계속 실행될 수 있다.
- 왜 기존 테스트가 못 잡는가: `tests/unit/ports/test_team_ports.py`의 running 시나리오는 `poll()`이 즉시 failed를 반환하고, timeout/deadline 전에 정상적으로 응답한다. hanging submit/poll, 이미 만료된 deadline, timeout 뒤 원격 cancel 여부를 검사하는 테스트가 없다.
- 재현 시도: 재현함. 만료된 `deadline_at`과 `submit()`에서 `asyncio.sleep(1)`하는 transport를 넣고 executor를 `asyncio.wait_for(..., 0.05)`로 감쌌다. 0.05초 안에 executor의 실패 결과가 나오지 않고 외부 `TimeoutError`가 발생했다(`a2a_external_timeout_before_executor_failure`). 코드상 deadline을 지난 뒤에도 submit을 먼저 await하는 경로와 일치한다.
- 위험도: 높음

### app/core/registry.py:54-79 — capability→Team resolve에 tenant 경계가 없음 (의심됨 — 확인 필요)
- 시나리오: 하나의 프로세스에서 tenant A와 tenant B의 Team manifest/configuration이 함께 등록되어 있고 두 tenant가 같은 `case_type`/capability namespace를 사용한다. `TeamRegistry.resolve()`는 `case_type`과 `intent`만 받아 active Team을 고르며 tenant를 받거나 검사하지 않는다. Controller도 `registry.resolve(case_type=intent, intent=intent)`만 호출한다. 따라서 tenant A case가 tenant B용으로 등록된 동일 capability Team을 선택하거나, 두 tenant의 동일 capability가 함께 등록되어 라우팅이 ambiguous/실패할 수 있다.
- 왜 기존 테스트가 못 잡는가: `TeamManifest`와 `TeamRegistry`에 tenant 식별자가 없고, 기존 registry 테스트는 단일 전역 registry 안의 case type/capability만 검증한다. 두 tenant의 동일 capability와 tenant별 manifest를 동시에 등록하는 fixture가 없다.
- 재현 시도: 재현 안 해봄, 코드 읽기로만 판단. 현재 기본 구성은 전역 Team manifest만 사용하므로 실제 tenant별 등록 방식은 확인 필요하다. 다만 현재 resolve 계약 자체에는 tenant를 전달할 자리가 없다.
- 위험도: 높음

## 확정적으로 찾지 못한 항목

- `app/infrastructure/rag/retriever.py`: 본 스캔 경로의 문서 존재 확인과 실제 검색 모두 `tenant_id=%s`, `scope = ANY(%s)` 파라미터 바인딩을 사용하고, 최종 검색에도 동일 조건이 있다. 문자열 결합으로 tenant/scope를 넣는 확정 경로는 찾지 못했다.
- `app/core/context.py`: 각 입력 섹션의 token 계산은 `tiktoken`을 사용하고, section별 탈락은 `omissions`에 기록된다. `retrieval_failed`와 무결과도 `degraded`/`omissions`로 표시된다. 이 파일만으로 신호 없는 축소의 확정 사례는 찾지 못했다.
