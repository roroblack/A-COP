# 버그사냥 06 — Controller WAIT/RESUME·전이표

범위: `app/application/controller.py`, `app/core/transition.py`, `app/domain/events.py` 및 REST 호출 경로. 코드 수정은 하지 않았다.

### app/presentation/api/cases.py:116-126 — REST 메시지 경로가 Controller.resume()·진짜 resume token 검증과 완전히 분리되어 있다
- 시나리오: `waiting_input` Case에 `case:write` 권한으로 `POST /v1/cases/{case_id}/messages`를 보내면 `MessageRequest`는 `request_id`, `message`, `expected_version`만 받고 token 필드가 없다. 핸들러는 `request.message`의 SHA-256을 `resume_token_hash`로 만들어 `VALID_INPUT`을 직접 발행한다. 실제 발행 시 사용한 24시간 TTL token을 모르더라도 message를 바꾸어 전이를 시도할 수 있으며, `CaseService.validate_resume()`의 hash·만료·single-use 검사가 실행되지 않는다.
- 왜 기존 테스트가 못 잡는가: Controller 통합 테스트는 `CaseService.validate_resume()`와 `Controller.resume()`를 별도로 확인하지만, REST messages 테스트는 token을 전달하거나 대기 중 Case의 실제 token 검증을 연결하지 않는다. 전체 호출 검색에서도 `Controller.resume()` 호출자는 정의부 외에 없고, REST/MCP/스케줄러 경로에서 호출되지 않는다.
- 재현 시도: 재현 안 해봄, 코드 읽기로만 판단. `MessageRequest` 정의와 `cases.py:121-123`의 직접 `VALID_INPUT` 발행, `controller.py:265`의 유일한 `validate_resume()` 호출, 프로젝트 전체 `resume(` 검색 결과를 대조했다.
- 위험도: 높음

### app/application/controller.py:140-161 — case_wall_clock_seconds가 실행 전체에 강제되지 않고 팀 결과를 초과 시간에도 반영한다
- 시나리오: `run_case()` 시작 시각부터 `case_wall_clock_seconds`를 재지만, routing·`_task()`의 policy/context 구성·checkpoint 뒤 팀 실행 직전에 한 번만 검사한다. 그 검사 통과 후 context 구성 또는 team 실행이 남은 Case wall-clock 예산을 초과해도 `asyncio.wait_for()`가 team timeout 안에서 끝나면 곧바로 `_apply_result()`와 성공 run 종료가 실행된다. 특히 team timeout(90초)과 case wall clock(180초)이 독립적으로 적용되어 팀 실행 시작 시점에 이미 전체 예산이 거의 소진된 경우에도 팀이 계속 수행된다.
- 왜 기존 테스트가 못 잡는가: 기존 Controller 통합 테스트는 정상 실행·전이·replay를 확인하지만, context 구성 지연 또는 team 실행 중 `case_wall_clock_seconds` 초과를 주입하지 않는다. `case_wall_clock_seconds` 문자열은 현재 `controller.py:140` 한 곳에서만 검사된다.
- 재현 시도: 재현 안해봄, 코드 읽기로만 판단. `started = time.monotonic()`의 시작점과 단일 검사 위치, 이후 `wait_for()`·`_apply_result()` 순서를 확인했다.
- 위험도: 보통

### app/application/case_service.py:29-44, app/infrastructure/db/migrations/001_schema.sql:15 — max_active_runs_per_case 가드가 동시 최초 실행 경합에서 뚫릴 수 있다
- 시나리오: 같은 Case에 두 `run_case()` 또는 `resume()` 요청이 동시에 들어오고 해당 Case에 active/running/resuming `agent_runs` 행이 아직 없으면, 각 트랜잭션의 `SELECT ... WHERE status IN (...) ... FOR UPDATE`가 모두 빈 결과를 본다. 잠글 기존 행이 없으므로 두 트랜잭션이 각각 `agent_runs` INSERT를 수행할 수 있다. 설정의 `max_active_runs_per_case: 1`은 읽히지 않고, `agent_runs` 테이블에도 `(tenant_id, case_id)`에 대한 active 상태 partial UNIQUE 제약이 없다.
- 왜 기존 테스트가 못 잡는가: 기존 동시성 테스트는 같은 `expected_version`으로 `transition_case()`를 호출해 한 건만 성공하는 경우를 검증한다. `start_run()`을 동시에 호출해 빈 상태에서 두 INSERT가 경합하는 테스트는 없고, 단일 요청의 이미 존재하는 active 행만 검증해도 이 race는 드러나지 않는다.
- 재현 시도: 재현 안해봄, 코드 읽기로만 판단. `start_run()`의 빈 결과 후 INSERT와 migration의 `agent_runs` 정의에 active-run uniqueness가 없는 것을 확인했다.
- 위험도: 높음

### app/application/controller.py:107-147 — public run_case()가 WAITING_INPUT/WAITING_APPROVAL Case를 token 없이 실행할 수 있는 경로를 남긴다
- 시나리오: 내부 호출자가 `run_case()`를 대기 상태 Case에 직접 호출하면 `start_run()` 후 `case["status"]`가 `ROUTING`이 아니므로 team entry를 가져오고, `RESUMING`일 때만 `RESUMED`를 발행한다. `WAITING_INPUT` 또는 `WAITING_APPROVAL`에서는 resume token/승인 이벤트 없이 team 실행으로 진입한다. 현재 REST create 경로는 routing Case에만 `run_case()`를 호출하지만, Controller API 자체에는 대기 상태 직접 실행을 거부하는 guard가 없다.
- 왜 기존 테스트가 못 잡는가: 기존 resume 테스트는 정상적으로 `VALID_INPUT`/`APPROVED` 뒤 `RESUMING` 상태를 만든 후 실행한다. 대기 상태에서 `run_case()`를 직접 호출하는 negative test가 없다.
- 재현 시도: 재현 안해봄, 코드 읽기로만 판단. `controller.py:132`의 `RESUMING` 특수 처리와 그 외 상태를 거부하지 않는 분기를 확인했다. 실제 외부 REST/MCP/스케줄러에서 이 직접 호출이 노출되는지는 확인되지 않아 호출 표면은 확인 필요하다.
- 위험도: 보통

## 버그 아님으로 확인한 항목

- `app/domain/case.py:59-66`의 `apply_event()`가 `REQUIRED_PAYLOAD_KEYS`와 `next_status()`를 모두 검사하므로 전이표에 없는 `(status, event_type)` 조합은 `InvalidTransition`으로 막힌다. `transition_case()`는 이 리듀서를 사용한다. 전이표 밖 이벤트가 조용히 통과하는 경로는 이번 코드 범위에서 확인하지 못했다.
- `app/core/transition.py:215-227`의 `replay_case()`는 `case_events`를 `tenant_id`, `case_id`로 조회하고 `aggregate_version` 오름차순으로 모든 반환 행을 `fold_events()`에 전달한다. 중간 이벤트를 선택적으로 건너뛰는 코드 경로는 확인하지 못했다. 다만 aggregate version의 gap 자체를 별도 검출하지는 않으므로, 저장소가 append-only 불변성을 깨뜨리는 경우의 진단 한계는 남는다.
- `app/domain/events.py:16-44`의 `EventType`는 `REQUIRED_PAYLOAD_KEYS`에 모두 등록되어 있고, contract test에도 EventType 누락 검사가 있다. 전이표에 사용되지 않는 이벤트도 현재 확인 결과 없다.
