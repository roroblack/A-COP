# 알림 — 세 시점과 확인할 수 있는 것

`[결정 2026-09-10 오후]` 정본은 v11 §6-A·§6-B. 여기는 **왜 이 모양인지**를 적는다.

★**한 줄로**: 알림은 **신호**이고 **여행계획서 링크가 사실**이다. 그래서 "통지가
닿았나"를 제품 조건으로 두지 않는다.

★`[2026-09-10 오후 개정]` **이 문서는 같은 날 두 번 고쳐졌다.** 초판은 시점을
「전날·아침·2시간 전」으로, 내용을 「새로 조회하지 않는다」로 적었다. **둘 다
바뀌었다** — 시점은 **역산**으로, 내용은 **③에서 경로를 조회하는 것**으로.
바뀐 이유는 각 절에 적었다.

## 세 시점

| # | 언제 | 무엇을 알리나 |
|---|---|---|
| **①** | **변경이 생겼을 때** | 무엇이 왜 바뀌었나 · 적용 안 한 다른 안 · 링크 |
| **②** | **여행계획서를 수행할 시간이 됐을 때** | 여행이 시작된다 · 오늘 무엇을 하나 · 첫 항목으로 언제 나서나 |
| **③** | **각 일정을 수행할 시간에** | ★**어디로 · 언제 나서야 하나 · 어떻게 가나** |

★★**①에 「생성」이 들어간다.** 일정을 **처음 받아 검증을 통과한 것도 변경**이다.
그때가 **여행계획서 링크가 처음 나가는 자리**이기도 하다 — 링크를 언제 주는지 앞 판이
말하지 않았다.

| ① 이 걸리는 경우 | |
|---|---|
| **생성** | 외부 일정을 받아 검증을 통과했다. **링크를 여기서 처음 준다** |
| **조정** | 감시가 변화를 잡아 우리가 고쳤다 |
| **재요청 반영** | 고객이 다시 요청해 되돌리거나 다른 안으로 바꿨다 |

## ①과 ②·③은 성질이 다르다

| | **① 변경 통지** | **②·③ 일정 안내** |
|---|---|---|
| 왜 | 일정이 바뀌었다 | **지금 무엇을 하면 되나** |
| Case 를 만드나 | **만든다** — 판정·재계획이 필요하다 | ★**안 만든다** |
| LLM 을 부르나 | 부른다 (분류·대안 생성) | ★**문구틀·언어마다 처음 한 번만** — 고객 언어로 생성해 재사용한다 |
| 변화가 없어도 가나 | 안 간다 | **간다** |

★★**②·③이 Case 가 아닌 것이 이 설계의 핵심이다.** 안내는 **이미 검증을 통과해
저장된 일정을 읽어 알리는 것**이라 판정할 것이 없다. Case 로 만들면 7일 여행에
안내만 수십 건이 쌓이고 **그만큼 LLM 을 부른다** — [비용 계산](../business/unit-economics.md)이
흔들린다.

★**②·③은 앞 판에 없던 것이다.** v11 §0-1 의 한 줄 정의에 "때가 되면 무엇을 하면
되는지 알려주는"을 더한 이유가 이것이다. **범위가 늘었다는 것을 숨기지 않는다.**

## 무엇은 확인할 수 있고 무엇은 못 하나

★**질문을 정확히 나눠야 답이 나온다.** "알림을 확인할 수 있나"는 네 개의 다른
질문이다.

| | 알 수 있나 | 어떻게 |
|---|---|---|
| 알림을 **발행했나** | **된다** | 바깥함(outbox)이 행으로 남긴다. 지우지 않는다 |
| 알림이 **채널에 닿았나** | **된다** | 웹훅 응답. ★`[실측]` **일반 예외는 최대 3회 뒤 `dead_letter`, 타임아웃·연결 오류는 1회 뒤 `unknown`이고 자동 재시도가 없다**(`worker.py:50~57`) — 후자가 채널이 안 될 때 나는 오류다 |
| 고객이 **알림을 봤나** | ★**안 된다** | 디스코드·텔레그램·메일 어느 것도 읽음을 우리에게 주지 않는다 `[외부]` |
| 고객이 **최신 계획서를 봤나** | ★**된다** | **링크가 우리 것이다.** 열린 시각을 남긴다 |

★★**셋째 줄이 없다고 넷째 줄까지 없는 것이 아니다.** 못 재는 것(알림 열람)과
재야 하는 것(**고객이 최신 안을 봤나**)이 다르다. **제품이 약속하는 것은 뒤쪽**이고
그건 잴 수 있다 — [DoD-25](../delivery/dod.md) 가 그것을 판정한다.

★**안 열어 봤다고 실패가 아니다.** 여행자가 계획서를 안 봐도 일정은 이미 맞게
고쳐져 있고, 나중에 열면 그때 본다. **열람 시각은 「고객이 알고 있나」를 아는
운영 정보이지 통과·실패 조건이 아니다.**

`[미확보]` 열람이 오래 없을 때 다시 알릴지는 안 정했다. **다음 안내에 「아직 안
보신 변경이 있습니다」를 얹는 것**이 가장 싸 보이지만 확인하지 않았다.

## 왜 수신 확인 없이도 성립하나

```
알림   변화가 있었다 / 때가 됐다는 신호      못 봐도 상태는 이미 맞다
링크   ★상태의 정본. 언제 들어와도 최신
재요청 마음에 안 들면 API 나 웹으로 다시 요청
```

★**우리가 먼저 고치기 때문에 성립한다.** 알림을 **승인 요청**으로 쓰면 그때는 도달이
조건이 된다 — 답이 안 오면 아무것도 못 하니까. **통지로 쓰면** 유실돼도 **우리 일정
버전은** 이미 고쳐져 있다.

★★`[2026-09-10 정정]` **초판은 "고객이 틀린 일정을 들고 다니지 않는다"였다 — 과했다.**
**업체 예약은 승인 전이면 그대로다.** 계획서만 보면 있지도 않은 항공편을 타러 간다.
그래서 계획서는 **「업체 변경 필요·미확정」과 기존 확정 예약을 같이** 보여준다(v11 §6-A).

★★**업체 예약은 다르다.** 먼저 고치는 것은 **우리 DB 의 일정 버전**뿐이고, 업체
예약은 [D-005 승인 경로](../decisions/D-005-write-gate.md)를 그대로 지난다.
이 둘을 섞어 읽으면 "승인 없이 다 바꾼다"가 된다.

## ③의 시각은 ★역산한다 — 「2시간 전」이 아니다

```
출발해야 할 시각 = 항목 시작 시각 − 이동 시간 − 여유
```

★**고정값이면 매번 틀린다.** 앞 판은 「각 예약 2시간 전」이었는데, 그건 **걸어서
5분인 곳과 한 시간 반 걸리는 곳을 같게 취급한다.**

★★`[실측 2026-09-10 정정]` **초판은 "이동 시간은 이미 검증이 계산했다"였다 — 틀렸다.**
`read_tools.py:252,256` 의 `read.route`·`read.transit` 는 **항상 `None`**(`[미구현]`)이다.
**Routes 연결이 이 역산의 선행 조건**이다. 여유를 얼마로 두나는 `config/` 설정이다.

★★**낡은 값으로 발행 시각을 정하면 이미 늦다.** 이동이 30분→60분으로 늘었으면 조회
결과를 받는 순간 30분 늦은 것이다. **예상 출발보다 이르게 사전 조회로 이동 시간을
갱신하고 발행 시각을 다시 계산한다**(v11 §6-B). 「이르게」가 얼마인지는 `[미확보]`.

★**②는 여행·하루 시작이다.** 첫 항목 출발 시각에서 역산하되 **전날 저녁에 한 번 더
보낸다** — 준비물·이동 수단은 당일 아침에 알면 늦다. 여행 둘째 날 아침도 *"오늘
계획서를 수행할 시간"* 이라 ②가 매일 돈다.

## 안내에 무엇을 담나 — ★③에서는 새로 조회한다

★★**이 문서의 초판은 "새로 조회하지 않는다"였다. 뒤집혔다.**
*"지금 무엇을 하면 되나"* 를 알리면서 **어떻게 가는지를 안 주면 알림의 값이 없다.**

| 담는 것 | 어디서 오나 | 새로 조회하나 |
|---|---|---|
| 시작 시각 · 장소 | 최신 일정 버전 | 아니다 |
| **다음에 어디로 가나** | 다음 항목의 장소 | 아니다 |
| **언제 나서야 하나** | 위 역산 | 아니다 |
| ★**어떻게 가나 — 경로** | **이동 시간 조회 Action** | ★**③에서는 조회한다** |
| 취소 기한이 남았으면 그 시각 | Activity 판정이 아는 값 | 아니다 |
| 이 항목에 걸린 필수 조건 | `scope=item` 조건 | 아니다 |
| **여행계획서 링크** | 늘 붙인다 | — |

★**왜 ③에서만 조회하나.** 출발 안내의 값은 *"지금 나가면 된다"* 인데 **낡은 경로면
그 값이 없다.** 지연·운행 중단·막차는 **바로 그 시각에 걸린다.** ①·②는 저장된 값으로
충분하다 — 그때는 "어떻게 가나"가 아직 질문이 아니다.

★**호출 수가 통제된다.** 항목 하나에 한 번이므로 **여행 한 건에 항목 수만큼**이다
(7일 기준 20~40회 `[추정]`). 감시 주기마다 부르는 것이 아니다.

★★**「사실과 생성을 분리한다」를 지키는 방법이 달라진다.** 조회하지 않는 것이 아니라
**조회한 것에 확인 시각을 붙이는 것**으로 지킨다.

| | |
|---|---|
| **조회가 되면** | 경로와 **조회 시각**을 같이 적는다 |
| **조회가 안 되면** | ★`[결정 15]` **대체 소스로 바꿔 조회한다.** 대체까지 안 되면 **치명 결함 — 서버를 끈다.** 「모름」으로 보내지 않는다. 앞 판은 「모름으로 적고 링크로 보낸다」였다 |
| **저장된 값을 쓸 때** | 언제 계산한 것인지 적는다 — 어제 것이면 **어제 것임을 적는다** |

★★**안내가 그 규칙을 깨는 가장 쉬운 길이 「그럴듯한 경로 문장」이다.** 실제로 안 본
환승 정보를 적으면 그 순간 이 제품이 파는 것의 반대가 된다.

## 두 번 보내지 않는다

★**중복은 이미 DB 가 막는다** — 바깥함의 `UNIQUE(tenant_id, topic, dedupe_key)`.
안내의 `dedupe_key` 를 **여행 · 대상 · 안내 종류**로 만들면, 되잡기 작업이 같은
시점에 두 번 돌아도 **한 번만 나간다.**

★**새 안전장치를 만드는 것이 아니라 있는 것을 쓰는 것이다.** 되잡기 작업은
설계상 다시 돌 수 있어야 하므로(그래서 "되잡기"다) **막을 자리는 실행이 아니라
발행이다.** [DoD-26](../delivery/dod.md) 이 이것을 본다.

## 언어

`[결정 2026-09-10 — 세 번 바뀌었다]` ★**알림은 보낼 때 고객 언어로 생성한다**(v11 §0-4 결정 14). **언어 목록을 미리 정하지 않는다** — 고객이 고른 언어가 곧 출력 언어다. 대만 고객이면 번체로 생성한다.
에이전트가 API 로 받아 가는 경로는 **에이전트가 옮긴다** — 두 경로의 책임이 다르다.

★**문구틀·언어마다 처음 한 번 생성하고 재사용한다.** 안내(②·③)는 고정 문장에 값을 채우는 것이라
그 문장을 **고객 언어로 한 번 생성해 두면** 같은 언어의 다음 안내는 모델을 안 부른다. **변경 통지(①)의
대안 설명은 매번 생성 문장**이다 — 그건 이미 Case 라 LLM 을 부르는 경로다.

★★**번역하지 않는 칸** — 시각·날짜·금액·장소 고유명사·예약번호는 **원값을 그대로
싣는다.** 틀린 번역이 틀린 시각·틀린 장소로 이어지면 판정이 맞아도 고객이 잘못 읽는다.

## 채널

`[결정 2026-09-10]` **무료 채널 중 구현이 가장 간단한 것 하나** — 디스코드 웹훅.
주소 하나에 POST 이고 **받는 사람 쪽 준비가 없다.**

★**세 채널을 다 만들지 않는다.** 보내는 함수를 갈아 끼우면 된다고 해도 **오류·
재시도·중복 처리까지 공짜는 아니다.** 나머지 둘은 **같은 자리에 함수 하나를 더
얹는 일**로 남는다.

`[외부]` 채널 성질은 각 서비스 공개 문서에서 아는 것이고 **이 저장소에서 붙여
확인한 것이 아니다.**

## 이것을 깨뜨리는 것

| | 무엇 | 왜 |
|---|---|---|
| **안내 문구를 LLM 으로 다듬기 시작하면** | 위 표의 "LLM 을 안 부른다"가 깨진다 | 안내는 자주 나간다. 원가가 Case 수가 아니라 **안내 수**에 붙기 시작한다 |
| **안내를 승인 요청으로 쓰기 시작하면** | 수신 확인이 다시 제품 조건이 된다 | 답을 기다려야 하는 순간 도달이 필수가 된다 |
| **링크 열람을 통과 조건으로 쓰면** | 고객이 안 열면 실패가 된다 | 열람은 운영 정보다 |
| **①·②에까지 새 조회를 넣으면** | 외부 API 호출이 안내 수만큼 는다 | ③만 조회하기로 한 것이 호출을 항목 수로 묶어 둔다 |
| **경로를 못 얻었는데 그럴듯하게 적으면** | 판정의 신뢰성이 무너진다 | **대체 소스로 바꾸고, 안 되면 서버를 멈춘다**(결정 15) |
