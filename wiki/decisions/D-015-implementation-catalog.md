# D-015 구현 카탈로그를 손으로 유지하지 않는다

`[실측 2026-09-09]` 계기는 여행 Team 여섯을 붙이는 작업이다.

## 무엇이 일어났나

`config/project.yaml` 을 여행 여섯으로 갈았는데 **조립은 멀쩡히 뜨고 Composer 로는 그 선언을 저장할 수 없는 상태**가 됐다.

원인은 코어에 손으로 유지하는 목록이 **둘** 있어서다.

| 어디 | 무엇 | 없으면 |
|---|---|---|
| `app/core/project_config.py` | `KNOWN_IMPLEMENTATION_REFS` (frozenset 12개) | `/composer/apply` 가 **422 로 거부** |
| `app/composer_host.py` | `IMPLEMENTATIONS` (튜플 12개 — id·ref·display_name·description) | 콘솔 카탈로그에 안 뜬다 |

**둘은 같은 집합이어야 하고 아키텍처 테스트가 센다**(`test_composer_stays_out_of_this_repo.py:95`). 조립 경로는 이 표를 안 보기 때문에 **pytest 로도 e2e 하나에서만 터졌다.**

★**그래서 「Team 을 늘리는 일은 Registry 등록만으로 끝난다」가 문자 그대로는 안 지켜졌다.** → [../architecture/pack-model.md](../architecture/pack-model.md)

## 왜 그 목록이 있나

**`implementation_ref` 는 `module:Class` 문자열이고 조립이 그것을 import 한다.**

```
임의의 ref 를 허용  =  임의의 모듈을 import  =  서버 프로세스에서 임의 코드 실행
```

★**목록은 편의 장치가 아니라 코드 실행 경계다.** 이 사실이 아래 모든 갈래를 제약한다.

## 갈래 넷

| # | 무엇 | 판정 |
|---|---|---|
| ① | 지금처럼 코어에 손으로 둔다 | **문제가 재발한다.** 이번에 실제로 재발했다 |
| ② | 목록을 `config/` 선언 파일로 뺀다 | **코어는 안 고치게 되지만 UI 관리는 안 된다.** 그 파일에 쓰면 코드 실행이므로 결국 배포 권한이 필요하다 |
| ③ | **콘솔 UI 에서 ref 를 직접 등록하게 한다** | **기각.** 아래 |
| ④ | **배포된 `app/modules/` 를 스캔해 카탈로그를 계산한다** | **권고** |

### ③을 기각하는 이유 — D-013 이 이미 판정했다

[D-013](D-013-declarative-team.md) 이 네 방식을 비교하며 이렇게 적었다.

> **임의 파일 import 는 원격 코드 실행과 같다.**
>
> **UI 에서 만든 걸 UI 에서 실행하면 그 순간 임의 코드 실행이다.**

★**그리고 ③은 애초에 원하는 걸 주지 못한다.** ref 를 등록해도 **그 모듈 파일이 서버에 없으면 import 가 안 된다.** 즉 배포가 선행돼야 하고, ③은 "배포는 됐는데 목록에 안 넣은 상태"만 풀어 준다. **그건 ④가 아예 발생하지 않게 만든다.**

### ④를 권고하는 이유 — D-013 이 기각한 것과 다르다

D-013 이 조건부로 남긴 것은 **「플러그인 디렉터리 스캔」**이다. ④는 그것이 아니다.

| | D-013 이 조건부로 둔 것 | **④** |
|---|---|---|
| 무엇을 스캔 | **임의 디렉터리** (외부에서 파일을 놓을 수 있는 곳) | **저장소 안 고정 경로 `app/modules/`** |
| 파일이 어떻게 들어오나 | 놓으면 된다 | **배포를 통과해야 한다** — 코드 리뷰·테스트·빌드 |
| 새 코드 실행 위험 | **있다** | 배포 절차가 이미 그 경계다 |

★**핵심은 이것이다** — `app/modules/` 안의 코드는 **이미 실행되도록 배포된 코드**다. 그것을 카탈로그에 올리는 일이 새로운 권한을 만들지 않는다. **손으로 유지하는 목록은 그 코드가 이미 거기 있다는 사실을 두 번 적는 것일 뿐이다.**

`[실측]` 지금 12개 ref 가 **전부 `app.modules.` 접두사**다. 예외가 하나도 없다.

`[실측]` `TeamManifest.display_name` 이 이미 계약에 있다(`app/core/contracts.py:307`). **카탈로그의 표시 이름을 Team 이 스스로 말한다.** `description` 은 계약에 없다 — 추가할 자리는 manifest 다.

### ④의 안전 조건

| 조건 | 왜 |
|---|---|
| **스캔 범위를 `app/modules/` 로 고정** | 코어·인프라 경로를 스캔하면 경계가 사라진다 |
| **`TeamManifest` 를 노출하는 클래스만** | 형태가 안 맞는 것은 카탈로그에 안 올린다 |
| **스캔 범위 자체는 선언에 둔다** | 나중에 패키지로 배포된 Team 이 생기면 범위를 넓혀야 한다. **코어를 고치지 않고 넓히려면 범위가 데이터여야 한다** |
| 스캔 실패는 조용히 넘기지 않는다 | import 오류를 삼키면 "왜 안 뜨는지 모르는" 상태가 된다 |

`[미확보]` **스캔 시점에 import 를 하는가.** manifest 를 읽으려면 import 가 필요한데, 그건 기동 시 어차피 하는 일이다. **다만 기동 시 전량 import 는 아직 안 하고 있다** — 등록된 것만 한다. 전량으로 넓힐지 정해야 한다.

## UI 프로젝트가 맡을 것

★**목록을 UI 로 옮기는 것이 아니다. 목록이 없어지고, UI 는 다른 걸 맡는다.**

`[실측]` 콘솔은 이미 카탈로그를 읽고 켜고 끈다 — `read_catalog()`·`toggle_target()`·`apply_candidate()`·`submit_change()`·`restore`(`final_project_ui/console/composer.py`). **④가 되면 이 화면들이 그대로 새 Team 을 다룬다.**

UI 가 새로 가져야 할 것은 셋이다.

| # | 화면 | 무엇을 푸나 |
|---|---|---|
| **1** | **드리프트 보기** | **배포됐는데 선언에 없는 구현** · **선언에 있는데 파일이 없는 구현**. ★2026-09-09 사고가 정확히 첫째였고 **아무 화면에도 안 보였다** |
| 2 | 표시 문구 편집 | `display_name`·`description` 은 **데이터인데 지금 cs 코드에 박혀 있다.** 운영자가 고칠 것이지 배포할 것이 아니다 |
| 3 | 카탈로그 출처 표시 | 각 항목이 **스캔으로 발견된 것인지 선언에 적힌 것인지** 보여준다. 출처를 안 보이면 드리프트를 못 읽는다 |

`[미확보]` **2번이 어디에 저장되는지 안 정했다.** manifest(코드)냐 Composer 선언(데이터)냐 — 운영자가 고치려면 데이터여야 하지만, 그러면 Team 이 자기 이름을 말하지 못한다.

## 이 결정이 안 하는 것

| | |
|---|---|
| **배포 없이 Team 을 추가하게 만들지 않는다** | 코드는 배포를 거친다. ④는 배포된 것을 **두 번 적지 않게** 하는 것이다 |
| 선언형 Team 을 대체하지 않는다 | [D-013](D-013-declarative-team.md) 이 권고한 선언형은 **범용 실행기 하나를 배포**하는 방식이다. ④와 같이 쓴다 |
| Port 교체 방식을 건드리지 않는다 | Port 셋은 `Literal` 열거형이라 ref 가 아니다 |

## 상태

`[미확보]` **결정 대기.** 사용자가 "UI 에서 관리 가능하게" 방향을 지시했고(2026-09-09), 이 문서는 그 방향을 **④ + UI 셋**으로 구체화한 안이다. **코드 변경은 담당 세션 몫이다.**
