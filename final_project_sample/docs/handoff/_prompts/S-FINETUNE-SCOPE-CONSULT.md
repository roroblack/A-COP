# S-FINETUNE-SCOPE-CONSULT — DoD-28 파인튜닝 범위 설계 검토

## 0. 이건 코드 작성이 아니라 **설계 검토**다

★**코드를 만들지 마라. 모델을 실제로 학습시키지 마라. 데이터를 실제로
내보내지 마라.** 이번 산출물은 **설계 문서 하나**다. 근거는 반드시
`파일:줄번호` 또는 `docs/reports/` 실측 수치로 대라. 추측을 사실처럼
쓰지 마라.

## 1. 배경

`docs/plans/A-COP_구현계획서_v8.md` §28(★"파인튜닝 파일럿 로우드맵 방어
지표")은 5종 방어 지표(할루시네이션 억제·유해 지시 거부·과금 오류
회피·PII 유출 차단·정책 준수)를 **완료**로 판정했지만, "파인튜닝 자체는
미착수"다(`scripts/verify_dod.py` DoD-28, evidence
`docs/evidence/28_*.md`를 먼저 읽어라 — 정확한 경로는 실제로 확인해라).

지금 이 프로젝트는:
- Proposed 파이프라인(프롬프트+RAG+검증)이 golden 60건 기준 grounding
  3.98/4점대(`eval/reports/` 실측 — 정확한 수치는 최신 리포트에서
  확인해라)까지 도달했다.
- 방어 지표 5종은 이미 별도 테스트/평가로 측정된다
  (`eval/defense_metrics.py` 또는 해당 모듈 — 실제 파일 확인).
- OpenAI API 키만 있고, GPU·전용 학습 인프라·라벨링 인력은 없다
  (`CLAUDE.md` §5 환경 표 참고).

"파인튜닝 착수"가 이 프로젝트에서 실제로 무엇을 의미해야 하는지가 정의된
적이 없다 — 이번 스트림의 목적은 **착수 여부를 결정하는 게 아니라,
착수한다면 정확히 무엇을 해야 하는지 범위를 정의하는 것**이다.

## 2. 검토할 것

### 2-1. 지금 프롬프트 기반 파이프라인의 한계를 먼저 실측으로 확인해라

파인튜닝이 풀어야 할 문제가 실제로 있는지부터 봐라. `eval/reports/`의
실제 실행 결과(A/B/Proposed 비교, ablation)를 읽고:
- Proposed가 여전히 실패하는 케이스 유형이 무엇인가(golden/holdout
  실패 사례를 실제로 찾아 분류해라).
- 그 실패가 **프롬프트/RAG로 더 고칠 수 있는 것**인지, 아니면
  **파인튜닝이 아니면 안 되는 것**(예: 특정 톤을 일관되게 내는 것,
  긴 프롬프트 없이도 정책을 내재화하는 것, latency/비용 절감)인지
  구분해라.
- ★"그냥 더 좋아 보여서" 는 이유가 아니다. 이 프로젝트는 근거 없는
  확정을 금지한다(`CLAUDE.md` §0.1).

### 2-2. 무엇을 파인튜닝할 것인가 — 후보 비교

- **분류기(intent/sentiment/issue_code)**: 지금은 프롬프트 기반 LLM
  호출이다(`app/modules/customer_ops/feedback.py` 또는 실제 분류 모듈
  확인). 작은 모델을 분류 전용으로 파인튜닝하면 비용·지연 이득이 있는가?
- **REV(검수) 규칙의 톤 판정**: `response_review.py`의 톤 REV가 지금
  LLM 호출인데, 결정론 규칙(`decide_tone`)과 얼마나 자주 불일치하는가 —
  불일치가 잦다면 파인튜닝 후보다.
- **GEN(응답 생성)**: 가장 비용이 크고 위험도도 크다(할루시네이션·PII
  회귀 위험) — 지금 방어 지표 5종이 프롬프트 기반 GEN에 대해 측정된
  것이므로, GEN을 파인튜닝하면 그 5종 지표를 **다시** 측정해야 한다는
  것을 명시해라.

각 후보마다 **데이터 소스**(어디서 학습 데이터를 구하는가 — 지금 golden
60건·holdout 20건뿐이라는 게 진짜 제약이다), **평가 방법**(파인튜닝 전후
비교를 무엇으로 하는가 — 기존 eval 하네스 재사용 가능한지), **비용**
(OpenAI 파인튜닝 API 요금·데이터 준비 인력)을 표로 비교해라.

### 2-3. 데이터 부족 문제를 정면으로 다뤄라

★이 프로젝트가 반복해서 강조하는 원칙 — **"표본이 작으면 작다고
말한다"**(`CLAUDE.md` §4). golden 60건은 파인튜닝 학습셋으로 쓰기엔
너무 작다(일반적으로 분류기 파인튜닝도 수백~수천 건이 필요하다 — 이
숫자가 맞는지 실제로 근거를 대라, OpenAI 공식 문서 기준 최소 권장
건수를 인용해라). **데이터가 부족하면 "지금은 파인튜닝 착수 부적절"이라는
결론도 정당한 산출물이다** — VISION 문서들의 "보류 판정" 관행과 같다.

### 2-4. 위험과 반대 의견

★**지금 파인튜닝에 착수하지 않는 편이 나은 이유**도 반드시 적어라:
- 학습 데이터가 golden/holdout과 겹치면 평가가 무의미해진다(오염).
- 파인튜닝된 모델은 버전 관리·재현성 부담이 프롬프트보다 크다
  (`prompts` 테이블의 `(prompt_key, version)` 불변 원칙과 같은 수준의
  장치가 파인튜닝 모델에도 필요한가?).
- 이 프로젝트는 아직 RC가 아니다(`docs/release_checklist.md` §5-1,
  judge agreement 미측정) — 더 근본적인 신뢰성 검증이 안 끝난 상태에서
  파인튜닝에 자원을 쓰는 게 우선순위가 맞는지.
