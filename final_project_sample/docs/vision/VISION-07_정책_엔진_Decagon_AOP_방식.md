# VISION-07. 정책 엔진 (Decagon AOP 방식)

| 항목 | 내용 |
|---|---|
| 상태 | 검토중 |
| MVP 포함 | 아니오 |
| 최종 갱신 | 2026-08-13 |

## 1. 무엇인가

정책을 프롬프트 문장에만 두지 않고 설정·룰 테이블로 분리해 결정적으로 실행한다. Agent Operating Procedures와 결정적 실행 계층으로 정책을 다루는 Decagon 방향을 참고한다. 현재는 환불 판정만 룰 테이블로 분리하는 최소 버전을 검토 중이며 전체 정책 DSL은 미착수다.

## 2. 지금 하지 않는 이유

- 전체 정책 DSL은 문법·우선순위·충돌·버전·승인·시뮬레이션을 함께 정해야 하는 별도 프로젝트다.
- 현재 정책 문서와 Team 계약이 MVP 범위에서 관리되고 있어 모든 정책을 DSL로 옮길 관측 근거가 부족하다.
- 프롬프트와 룰 테이블이 동시에 같은 결정을 담당하면 판정 출처가 모호해질 수 있다.

## 3. 도입 트리거 (이 조건이 만족되면 재검토한다)

- 정책 문서가 50건 이상이 되면 정책 catalog와 DSL 범위를 재검토한다.
- 정책 변경이 월 5회 이상 발생하는 상태가 3개월 지속되면 프롬프트 외부화 우선순위를 검토한다.
- 최근 3개월 동안 프롬프트를 수정하지 않고 정책만 변경하려는 요구가 월 3건 이상이면 결정적 정책 계층을 검토한다.
- 동일 정책에 대한 Team 판정 불일치가 100건 중 5건을 초과하면 룰 테이블 적용 범위를 확대한다.

## 4. 도입 시 예상 비용

전제: 6인 팀이 AI 코딩 도구를 상시 사용한다. 아래는 인·일이 아니라 실소요 일수(wall-clock)다.
단축률은 이 저장소 실측(2026-08-12, 2시간 21분에 18,390줄·테스트 107건)에 근거한 추정이며 정밀한 값이 아니다.

| 구분 | 내용 | 실소요 | AI 단축 정도 |

| 생성 | 정책 schema·버전·우선순위, DSL/룰 평가기, 시뮬레이션·승인·감사 UI와 테스트 골격 생성. 병목은 정책 표현의 초기 배선이다. | 1.5~2.5일 | 큼 |

병목: DSL을 만드는 속도보다 정책 의미의 보존과 회귀·shadow 결과 승인 검증이 지배적이다.

## 5. 선행 조건 (이게 먼저 있어야 도입 가능)

- 정책 문서와 결정 결과의 version·evidence 연결
- 환불 룰 테이블 최소 버전의 회귀 테스트와 shadow 비교 자료
- 정책 충돌·우선순위·예외·유효기간의 명시적 계약
- 프롬프트 경로와 결정적 경로를 분리 집계하는 평가 하네스

## 6. 폐기 조건 (이 조건이면 이 비전을 버린다)

- 12개월 동안 정책 변경이 월 2회 이하이고 정책만 변경하려는 요구가 월 1건 이하이면 전체 DSL을 폐기한다.
- 환불 룰 테이블을 100건 회귀 평가했을 때 프롬프트 기준선과 일치율이 98% 미만이면 전체 확장을 폐기하고 최소 룰만 유지한다.
- DSL 도입 후 3개월 동안 정책 판정의 출처·버전 추적률이 99% 미만이면 DSL 운영을 폐기한다.
