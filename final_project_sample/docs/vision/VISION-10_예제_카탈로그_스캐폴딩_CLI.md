# VISION-10 — 예제 카탈로그·스캐폴딩 CLI·UI 선택 생성 (데이터 기반 자동 개선 포함)

상태: 1층 완료(2026-08-19), 2층 보류, 3층 신규 등록(2026-08-24). `examples/`(케이스 유형별 Team·A2A 예시 카탈로그)와 그걸 골라
새 릴리스 프로젝트 뼈대를 떠주는 CLI는 `acop_basement`/`acop_composer`
분리가 끝난 지금 언제든 착수해도 되는 크기지만, "실제 프로젝트 데이터가
쌓일수록 생성 품질이 좋아지는" 부분은 착수하지 않는다.

## 1. 하려는 것

두 층으로 나눈다.

1. **카탈로그 + 스캐폴딩 CLI**(작다, 지금 착수 가능) — `examples/`를
   케이스 유형(구독·결제, 커머스, 기술 지원 등)·구성 요소(Team·Port·A2A
   조합)별 메타데이터를 가진 카탈로그로 정리하고, `pip install
   acop_basement` + 고른 예시 모듈 복사 + `config/project.yaml` 초안
   생성까지 자동으로 해 주는 CLI 도구를 만든다.
2. **데이터로 점점 좋아지는 생성기**(크다, 지금 보류) — 실제 릴리스
   프로젝트들(cs 다음에 나올 프로젝트들)의 진짜 Team·인스턴스·config
   가 쌓이면, 그 데이터를 근거로 카탈로그 자체를 자동으로 넓히거나
   추천 품질을 높이는 구조.
3. **UI에서 고르고 바로 만들기**(2026-08-24 등록) — 지금은 카탈로그 조회와
   프로젝트 뼈대 생성이 CLI에서만 된다. 운영 UI에서 예제 목록을 보고 하나를
   골라 이름과 설정을 입력하면 그 자리에서 Team 인스턴스가 만들어지는 흐름을
   말한다. 사용자 표현으로는 "팀 모듈 셈플 중에서 선택해서 바로 생성"이다.

## 3. 도입 트리거 (이 조건이 만족되면 재검토한다)

- **1층(카탈로그+CLI)**: 사용자가 명시적으로 요청하면 바로 착수 —
  데이터 의존성이 없어 트리거를 따로 안 둔다.
- **2층(자동 개선)**: 다음 중 하나가 충족되면 재검토한다.
  - `cs` 이후 실제로 완성된 릴리스 프로젝트가 2개 이상 쌓여, 서로 다른
    도메인의 Team·config 인스턴스를 최소 3세트 이상 비교할 수 있다.
  - 같은 카탈로그 예시를 참고했는데 실제 요구와 안 맞아 처음부터 다시
    짠 사례가 3건 이상 기록된다(카탈로그가 "실제로 재사용되는지" 자체를
    먼저 증명해야 한다).

- **3층(UI 선택 생성)**: 선행조건이 트리거다. 데이터가 아니라 기능 의존이다.
  - 선언형 Team 실행기가 배포돼 있다. 코드 배포 없이 Team을 데이터로 만들 수 있어야 한다.
  - Composer 인스턴스 CRUD 계약이 확정돼 있다. UI가 생성·삭제를 보낼 통로가 있어야 한다.
  - 카탈로그가 HTTP로 조회 가능하다. 지금은 CLI에서만 읽는다.

  세 가지가 모두 갖춰지면 착수한다. 하나라도 없으면 UI만 먼저 만들어도 동작하지 않는다.

## 2. 지금 하지 않는 이유(2층·3층)

지금 완성된 릴리스 프로젝트는 `cs` 하나뿐이다. 데이터 포인트 1개로
"점점 좋아지는" 자동화 구조를 설계하면, 그 하나의 프로젝트가 우연히 가진
특성을 일반 패턴으로 오인해 설계하게 된다 — 이 프로젝트가 이미 여러 번
겪은 실수(v7 §9-E 표의 예시를 스펙으로 잘못 읽어 `app/core/verification.py`
가 구독·결제 어휘를 basement 에 박았던 사례, `docs/handoff/10` §4)와 같은
종류다. 예시가 하나뿐일 때는 "그 예시를 일반화하는 자동 장치"보다
"사람이 직접 예시를 늘리는 것"이 더 정확하고 싸다.

3층은 선행조건이 아직 없어서 하지 않는다. 선언형 Team 실행기가 없으면 UI에서 고를
대상이 "이미 코드로 있는 구현체"뿐이고, 그것들은 이미 `project.yaml`에 다 선언돼 있다.
같은 구현체를 다른 이름으로 하나 더 선언하면 지금 구조에서는 capability 중복으로
조립이 실패한다. 근거는 `program/plan/A-COP_Composer_범위재검토.md` §2.3이다.

즉 UI 화면을 먼저 만들어도 만들 수 있는 것이 없다. 순서가 바뀌면 화면만 있고 동작하지
않는 기능이 된다.

## 4. 도입 시 예상 비용

| 구분 | 실소요 일수 | 내용 |
|---|---:|---|
| 1층 카탈로그+CLI | 3~5일 | `examples/` 메타데이터 스키마, 카탈로그 조회, `acop_basement` 설치+예시 복사+`project.yaml` 초안 생성 CLI, 최소 2개 예시(현재 billing/technical) 등록 |
| 3층 UI 선택 생성 | 4~7일 | 카탈로그 HTTP 조회, 인스턴스 생성 마법사 화면, 설정 입력 폼, 미리보기와 dry-run, 실패 시 되돌리기. 선언형 Team 실행기와 인스턴스 CRUD 계약은 별도 비용 |
| 2층 자동 개선(재검토 시점 기준 재추정 필요) | 미상 | 실제 프로젝트 N≥3 데이터 확보 후, 무엇을 "자동으로 좋아진다"로 정의할지부터 다시 정해야 한다(추천 랭킹? 패턴 자동 추출? LLM 기반 합성?) — 지금은 산정 근거 자체가 없다 |

1층 병목은 카탈로그 메타데이터 스키마 설계(케이스 유형을 어떻게 분류할지)
다. 3층 병목은 설정 입력 폼이다. Team마다 필요한 설정이 다른데 그 스키마를
카탈로그가 제공해야 화면을 자동으로 그릴 수 있다. 2층은 "무엇을 자동화 대상으로 삼을지"가 아직 정의되지 않아 비용
산정이 불가능하다 — 이게 지금 착수하지 않는 또 다른 이유다.

## 6. 폐기 조건 (이 조건이면 이 비전을 버린다)

1층: 카탈로그를 만들었는데 실제 새 프로젝트 착수 때 아무도 참고하지
않으면(착수 후 3건 연속 미사용) 폐기하고 `docs/handoff/10` 문서 하나로
충분하다고 판정한다.

3층: 선언형 Team이 실제로 쓸 만한 Team을 못 만든다고 판정되면 폐기한다. 구체적으로는
선언형으로 만든 Team이 3건 연속 품질 문턱을 넘지 못하고 결국 코드로 다시 구현된 경우다.
그때는 "UI에서 고르고 바로 만들기" 대신 "개발자가 CLI로 뼈대를 뜨고 코드를 채운다"로
영구 대체한다.

2층: 프로젝트가 3개 이상 쌓여도 서로 도메인이 너무 달라 공통 패턴을
추출할 근거가 없다고 판단되면, "자동 개선" 대신 "사람이 분기별로 카탈로그
직접 갱신"으로 영구 대체하고 이 항목은 폐기한다.
