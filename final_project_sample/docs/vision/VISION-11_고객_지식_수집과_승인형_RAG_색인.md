# VISION-11 — 고객 지식 수집과 승인형 RAG 색인

상태: 보류(2026-08-24 등록). 새 고객사를 붙일 때 그 회사의 문서를 사람이 손으로 정리해
지식으로 넣는다. 이것을 제품이 대신하게 만드는 방향이다.

## 1. 하려는 것

지금은 도입할 때마다 사람이 `knowledge/**`를 손으로 채운다. `docs/handoff/10_도메인_교체_가이드.md`
가 그 대상을 명시한다(현재 25문서 300청크).

바꾸려는 흐름은 이렇다.

```
고객사 문서(사규·약관·FAQ·매뉴얼)
   → 수집
   → 잘라서 정리 (청크)
   → 검사 (중복·길이·개인정보·유효기간)
   → staging 에 보관
   → 업무 담당자가 표본 검토·승인
   → 색인 (검색 가능한 상태로)
```

핵심은 **승인 단계다.** 자동으로 넣고 끝내지 않는다. 사람이 확인한 것만 검색 대상이 된다.

여기서 "청크"는 문서를 검색하기 좋은 크기로 자른 조각을 말한다. "색인"은 그 조각들을
찾을 수 있게 정리해 두는 것을 말한다.

## 2. 지금 하지 않는 이유

고객사가 아직 없다. 도입 사례가 하나도 없는 상태에서 수집 자동화를 설계하면, 우리가
가진 하나의 예시(현재 cs 프로젝트의 지식 구조)를 일반 패턴으로 오인한다.

이 프로젝트가 같은 실수를 이미 겪었다. v7 §9-E 표의 예시를 스펙으로 잘못 읽어
`app/core/verification.py`가 구독·결제 어휘를 basement에 박았던 사례다
(`docs/handoff/10` §4).

또 하나. 문서 형식이 고객사마다 다르다. PDF·워드·위키·이미지 스캔이 섞인다. 어떤 형식을
지원해야 하는지는 실제 고객사를 봐야 정해진다. 지금 정하면 안 쓰는 변환기를 만든다.

## 3. 도입 트리거 (이 조건이 만족되면 재검토한다)

다음 중 하나가 충족되면 재검토한다.

- 실제 도입 고객사가 2곳 이상이고, 각각 문서 50건 이상을 지식으로 넣어야 한다.
- 한 고객사의 지식 문서가 200건을 넘어 사람이 손으로 정리하는 데 3일 이상 걸린다.
- 지식 갱신 요청이 월 10건 이상 들어와 수작업 반영이 병목이 된다.

VISION-06(지식·메모리 확장)의 트리거가 "문서 200건 이상"이다. 이 항목과 함께 검토한다.

## 4. 도입 시 예상 비용

| 구분 | 실소요 일수 | 내용 |
|---|---:|---|
| 생성 | 6~9일 | 수집기(형식별 변환), 청크 분할, 검사 규칙, staging 저장소, 승인 화면, 색인 반영 |
| 검증·통합 | 4~6일 | 검색 품질 평가, 개인정보 검사 테스트, rollback 절차, 고객사 격리 확인 |
| 대기 | 3~5일 | 업무 담당자의 표본 검토 시간. 사람이 봐야 하므로 줄일 수 없다 |

병목은 **형식별 변환기**다. PDF 하나만 해도 표·이미지·다단 편집이 섞이면 정확도가
크게 떨어진다. 어떤 형식까지 지원할지 범위를 먼저 못 박아야 비용이 산정된다.

## 5. 지켜야 할 제약

### 5.1 데이터가 고객사 밖으로 나가면 안 된다

계획서에 **자체 호스팅**과 **데이터 외부 반출 방지**가 목표로 적혀 있다. 규제 산업에
들어가려면 이 조건이 필수다.

따라서 수집·변환·임베딩을 **고객사 배포 경계 안에서** 실행한다. 외부 OCR·LLM·embedding
API는 기본 금지한다. 예외는 고객의 명시적 승인이 있고 무엇을 보냈는지 목록으로 남길
때만 허용한다.

이 제약을 못 지키면 이 기능 자체가 제품 가치를 잃는다.

### 5.2 자동 생성 지식의 품질을 사람이 보증한다

잘못 잘린 청크나 오래된 문서가 색인에 들어가면 답변 근거 전체가 오염된다.

- 출처와 변환 이력을 보존한다. 어느 문서의 몇 쪽에서 왔는지 남긴다.
- 중복·길이·개인정보·유효기간을 검사한다.
- 업무 담당자가 표본을 검토하고 승인한 것만 색인한다.
- 색인 후에도 검색 품질을 측정하고 되돌릴 수 있게 한다.

## 6. 폐기 조건 (이 조건이면 이 비전을 버린다)

고객사 문서가 대부분 이미 구조화돼 있어(예: 기존 헬프센터 시스템에서 API로 가져올 수
있어) 수집·변환 단계가 필요 없다고 판정되면 폐기한다. 그때는 "형식별 변환기"가 아니라
"기존 시스템 연동 어댑터"로 방향을 바꾼다.

또는 도입 고객사 3곳을 겪었는데 매번 문서 구조가 너무 달라 공통 변환 규칙을 뽑을 수
없다고 판단되면, 자동화 대신 "도입 시 컨설팅으로 사람이 정리"로 영구 대체한다.
