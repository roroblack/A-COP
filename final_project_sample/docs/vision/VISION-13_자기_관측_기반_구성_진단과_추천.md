# VISION-13 — 자기 관측 기반 구성 진단과 추천

상태: 보류(2026-08-28 등록). 배포 자신의 운영 기록을 세어 "무엇이 없어서 실패했는지"를
보여주고, 그것을 메울 모듈이나 Team 인스턴스를 제안한다.

## 1. 하려는 것

지금은 어떤 Team을 더 놓을지 사람이 판단한다. 판단 근거는 감이거나 고객 요청이다.

바꾸려는 것은 이렇다.

```
운영 기록 (case_events)
   → 실패 유형별로 센다
   → "이 문의 유형 47건이 처리할 Team이 없어 떨어졌다"
   → "Payment Team 인스턴스를 추가하면 이 47건을 처리할 수 있다"
   → 근거가 된 Case 47건을 함께 보여준다
```

**제안까지만 한다.** 적용은 사람이 누른다. Team이 side effect를 직접 실행하지 않고
제안만 반환하는 기존 원칙과 같은 구조다.

## 2. 근거가 되는 신호는 이미 기록되고 있다

추측이 아니라 코드에서 확인했다.

`TeamRegistry.resolve()`는 처리할 Team을 못 찾으면 오류를 던진다
(`app/core/registry.py:78`). Controller가 그것을 잡아 이벤트로 남긴다
(`app/application/controller.py:128-130`).

```python
except RegistryError as exc:
    self._transition_with_retry(..., event_type=EventType.ROUTING_FAILED,
                                payload={"failure_code": "no_team"}, ...)
```

즉 "이 문의를 처리할 Team이 없었다"가 `case_events` 테이블에 그대로 쌓인다.

쓸 수 있는 이벤트는 더 있다. `app/domain/events.py`에 정의돼 있다.

| 이벤트 | 무엇을 뜻하나 | 추천에 쓰는 것 |
|---|---|---|
| `routing_failed` | 처리할 Team이 없었다 | 어떤 Team이 없는지 |
| `classification_failed` | 문의 유형을 못 정했다 | 분류 지식이 부족한 영역 |
| `missing_input` | 필요한 정보가 없었다 | 어떤 조회 도구가 없는지 |
| `retry_exhausted` | 재시도를 다 썼는데 실패했다 | 어떤 연동이 불안정한지 |
| `guardrail_escalated` | 안전장치가 사람에게 넘겼다 | 자동화 여지가 있는 영역 |

**따라서 추천용 데이터를 새로 만들 필요가 없다.** 이미 쌓이는 것을 세기만 하면 된다.

여기서 "이벤트"는 Case에 일어난 일을 시간순으로 남긴 기록을 말한다.

## 3. 지금 하지 않는 이유

운영 기록이 쌓이지 않았다. 실제 운영 배포가 아직 없다.

실패 이벤트가 몇 건 없는 상태에서 추천 규칙을 만들면 우연을 패턴으로 오인한다. 이
프로젝트가 이미 겪은 실수다. 예시 하나를 일반 패턴으로 읽어 basement에 도메인 어휘를
박았던 사례가 `docs/handoff/10` §4에 있다.

또 하나. 기록은 있으나 그것을 **기간·유형 단위로 세는 조회**가 없다.
`get_case_events()`는 Case 하나의 이벤트를 시간순으로 읽을 뿐이다
(`app/infrastructure/db/repository.py:36-39`).

이것은 "기록 추가"가 아니라 "집계 조회 추가"다. Core를 건드리지 않고 읽기 전용 질의만
더하면 된다.

## 4. 도입 트리거 (이 조건이 만족되면 재검토한다)

다음을 **모두** 충족해야 한다.

- 운영 중인 배포에서 `routing_failed` 또는 `classification_failed` 이벤트가 30일 동안
  50건 이상 쌓인다.
- 그중 같은 case type이 10건 이상 반복된다. 한 유형에 몰려야 "그 Team이 없다"고 말할 수
  있다. 흩어져 있으면 Team 부족이 아니라 분류 문제다.
- 이벤트를 기간·유형으로 세는 집계 조회가 구현돼 있다.

세 번째는 이 항목의 선행 작업이기도 하다.

## 5. 도입 시 예상 비용

| 구분 | 실소요 일수 | 내용 |
|---|---:|---|
| 생성 | 3~5일 | 이벤트 집계 조회, 진단 규칙, 추천 산출, 근거 Case 목록 연결 |
| 검증·통합 | 2~4일 | dry-run 검증 연동, 추천 정확도 확인, 화면 표시 |
| 대기 | 0일 | 사람 검토 대기가 없다. 제안까지만 하기 때문이다 |

병목은 **진단 규칙**이다. "몇 건부터 Team이 없다고 볼 것인가"를 정해야 한다. 너무 낮으면
잡음이 되고 너무 높으면 늦게 알려준다.

## 6. 지켜야 할 제약

### 6.1 추천에는 근거가 함께 나와야 한다

계획서는 "모든 판단은 근거와 함께 기록되어 재생·감사할 수 있다"를 표방한다. 추천도 같은
기준을 지켜야 한다.

"이 모듈을 추천합니다"만 뜨고 왜인지 모르면 이 제품이 스스로 내세운 원칙을 어기는 것이다.
**"47건"이라는 수치와 그 47건이 무엇인지 볼 수 있어야 한다.**

### 6.2 적용 가능한 추천만 보여준다

같은 구현체를 다른 이름으로 또 선언하면 capability 중복으로 조립이 거부된다. 근거는
`program/plan/A-COP_Composer_범위재검토.md` §2.3이다.

추천 시점에 dry-run 검증을 함께 돌려 실제로 적용 가능한 것만 보여준다. 따랐는데 실패하는
추천은 없느니만 못하다.

### 6.3 제안까지만 한다

추천이 운영자 판단을 대체하면 구성이 근거 없이 부풀기만 한다. 적용은 사람이 누른다.

## 7. 교차 프로젝트 추천과의 관계

이 항목은 **자기 배포의 기록만** 쓴다. 프로젝트가 하나뿐이어도 성립한다.

여러 배포의 구성을 비교해 "보통 A와 B를 같이 쓴다"를 뽑는 것은 다른 문제다. 그것은
`VISION-10` 2층에 속한다. 릴리스 프로젝트 2개 이상이라는 조건이 필요하다.

교차 프로젝트 추천에는 위험이 하나 더 있다. 다른 고객사의 구성 정보가 새어나갈 수 있다.
계획서의 자체 호스팅과 데이터 외부 반출 방지 목표와 충돌한다. 개별 구성을 공유하지 않고
익명 집계만 쓰거나, 자체 호스팅 배포에서는 그 기능을 끈다.

## 8. 폐기 조건 (이 조건이면 이 비전을 버린다)

추천을 3회 연속 운영자가 무시하면 폐기한다. 추천이 쓸모없다는 뜻이다.

또는 추천대로 Team을 추가했는데 실제 처리율이 오르지 않는 경우가 3회 반복되면 폐기한다.
그때는 "추천" 대신 "실패 통계만 보여주기"로 축소한다. 통계만으로도 사람이 판단할 수 있다면
추천 로직은 불필요하다.

## 개정 이력

- 2026-08-28 최초 작성. 사용자가 "구조가 확장되는 것에 따라 어떤 모듈과 인스턴스를 더
  놓으면 좋다고 추천"하는 방향을 제안했다. 검토 결과 추천 근거를 자기 관측과 교차
  프로젝트로 나눌 수 있고, 앞의 것은 지금 구조에서 이미 성립한다고 판단해 독립 등록했다.
  검토 근거는 `program/plan/A-COP_확장추천_검토.md`다.
