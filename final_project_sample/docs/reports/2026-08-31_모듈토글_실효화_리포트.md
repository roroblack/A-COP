# 2026-08-31 — 모듈 토글 실효화 리포트 (cs 에서 이식)

## 1. 작업 목표

`docs/plans/2026-08-31_모듈토글_실효화_설계.md` 전체.

`final_project_cs` 에서 2026-08-30 에 고친 결함을 이 저장소로 옮겼다.
선언에서 모듈을 꺼도 아무 일이 일어나지 않던 상태다.

이 저장소는 cs 가 가져다 쓰는 참고 구현체다(루트 `CLAUDE.md`). 코드가
sample → cs 방향으로 흐르므로, 여기를 안 고치면 다음 이식 때 cs 의 수정이 덮인다.

## 2. 무엇이 잘못돼 있었나

`require_module` 과 `module_enabled` 호출처를 전부 세어 확인했다(2026-08-31 실측).

| 모듈 | 발견 당시 |
|---|---|
| `vector_rag` · `graph_store` · `ops_ui` · `a2a_executor` | 게이트 있음 |
| **`mcp`** | **게이트 없음.** 꺼도 tool 3종이 그대로 동작 |
| **`voc`** | **게이트 없음.** 꺼도 인라인 분류·일일 배치·VOC 화면이 그대로 |

`mcp` 가 제일 무겁다. 도입 기업이 개인 AI 접근을 안 열기로 하고 껐는데 실제로는
열려 있었다. 선언과 실제가 다르면 운영자가 선언을 믿고 잘못 판단한다.

## 3. cs 와 달랐던 점

### 3.1 ★graph_store 는 여기서 결함이 아니었다

cs 에서는 운영 화면이 `build_graph_store()` 를 우회해 `SqlGraphAdapter` 를 직접
만들고 있었다. 계획서를 쓰면서 **여기도 같을 것이라 짐작하고 그렇게 적었다.**

실제로 세어 보니 아니었다. `acop_basement/presentation/ui/routes.py` 에 import 는
있는데 **쓰는 곳이 없다.** 파일 전체에서 `SqlGraphAdapter` 출현이 import 줄 1회뿐이었다.
관리자 화면이 `final_project_ui` 로 나가면서 남은 죽은 import 다.

계획서를 그 자리에서 고쳤다. **짐작으로 결함을 적으면 없는 결함을 고치게 된다.**
죽은 import 는 지웠다 — 남겨 두면 다음 사람이 조립 경계를 건너뛰고 그것을 쓴다.
cs 에서 실제로 그렇게 됐다.

### 3.2 게이트 다는 자리가 다르다

`acop_basement` 는 cs 가 설치하는 pip 패키지라 product(`app`)를 **최상위에서**
import 할 수 없다. 그래서 basement 안의 게이트는 basement 자신의 로더
(`acop_basement.application.config_source.load_active_config`)로 묻는다.
중앙 설정 저장소 모드도 이 로더가 알아서 따라가므로 따로 다룰 것이 없다.

### 3.3 메뉴를 기동 시점에 한 번 정한다

cs 는 `_nav()` 가 요청마다 선언을 다시 읽는다. 여기서는 그렇게 하지 않았다.

라우터 등록은 기동 시점에 끝나는데 메뉴만 나중 선언을 보면 둘이 어긋난다 —
메뉴에는 VOC 가 있는데 누르면 404 인 상태가 만들어진다. 중앙 저장소 모드에서는
매 요청이 DB 읽기가 되기도 한다. 그래서 `configure_nav(config)` 를 만들어
`mount_ui()` 가 라우터를 등록하는 **그 선언, 그 시점**에 메뉴를 정하게 했다.

★cs 쪽도 이 방식이 낫다. 다음 작업으로 넘긴다(§6).

## 5. `voc` 를 끄면 앱이 기동하지 않는다 — 단 이 저장소엔 구멍이 있다

cs 와 같은 판단을 했다. 근거도 같다 — 이 저장소의 `CLAUDE.md` §1 에도
"인라인 분류는 선택 기능이 아니다" 가 있다.

```
===== VOC 끔 — 기동 자체가 거부된다   (voc: false)
기동 -> ProjectConfigError | module 'voc' is disabled; cannot assemble inline classifier
```

★단 cs 와 다른 점이 하나 있다. **이 저장소는 분류기를 주입할 수 있다.**
`create_app(classifier=...)` 로 넘기면 `build_classifier()` 를 거치지 않는다.
도메인을 갈아 끼우는 저장소라 그 구멍은 의도적으로 열려 있다.

그러니 정확히는 **"기본 조립으로는 `voc` 를 못 끈다"** 이고, 자기 분류기를 주입하는
product 는 여전히 끌 수 있다. 이 차이를 코드 주석에 적어 두었다.

## 7. 이번에 내가 틀렸던 것

★계획서에 **"운영 화면이 `SqlGraphAdapter` 를 직접 만든다"** 라고 적었다. 틀렸다.
cs 에서 그랬으니 여기도 그럴 것이라 짐작하고 쓴 것이다. 실제로는 쓰지도 않는
import 하나였다. 세어 보고 계획서를 고쳤다.

★회귀 방지 테스트를 처음에 **"basement 는 `app` 을 아예 import 하지 않는다"** 로 짰다.
6건이 걸렸는데 전부 **의도된 지연 import** 였다(`presentation/api/app.py` 주석이
그 이유를 적어 두었다). 규칙을 "최상위 import 금지" 로 고쳤다. 검사기가 규칙을
잘못 적으면 멀쩡한 코드를 결함으로 만든다.

★테스트 고정값(fixture)을 cs 에서 그대로 옮겨 오다 `teams: []` 로 두어
`ValidationError` 를 봤다. 이 저장소의 선언 스키마는 Team 을 최소 하나 요구한다
(`min_length=1`). 저장소가 다르면 스키마도 다르다.

## 8. 미해결 이슈 · 다음 작업 제안

1. **cs 의 `_nav()` 를 이 저장소 방식으로 바꾸는 것이 낫다.** cs 는 요청마다 선언을
   다시 읽어서, 기동 뒤에 선언이 바뀌면 메뉴와 라우터가 어긋날 수 있다.
   여기서 쓴 `configure_nav(config)` 가 그 문제를 없앤다.
2. **`mcp` 모듈은 지금 아무 데서도 서빙되지 않는다.** cs 와 같다. tool 정의와
   권한 검사는 있지만 실행하는 코드가 없다. 실제로 열 때 그 진입점에도 게이트가 필요하다.
3. **`voc` 를 정말 끌 수 있게 만들지는 결정이 필요하다.** 지금은 분류기를 주입해야만
   끌 수 있다. 주입 없이 끄려면 Case 생성 경로에서 분류를 떼고, 분류 없이 만들어진
   Case 를 어떻게 다룰지(`escalated` 로 보낼지) 먼저 정해야 한다.
