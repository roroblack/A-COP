## 고친 것 1건

### `app/application/case_service.py:start_run()` — max_active_runs_per_case 가드가 동시 최초 실행 경합에서 뚫릴 수 있었다
- **재현 확인**: `SELECT ... FOR UPDATE` 는 **이미 있는 행만** 잠근다. 어떤
  Case 에 active/running/resuming 행이 하나도 없을 때 두 `start_run()` 이
  동시에 들어오면 **둘 다 빈 결과**를 보고 **둘 다 INSERT** 할 수 있다.
  `agent_runs` 테이블에 이걸 막는 제약이 전혀 없었다(직접 확인:
  `001_schema.sql` 에 `(tenant_id, case_id)` 관련 UNIQUE 없음). 별도
  커넥션 두 개로 실제 재현: 첫 커넥션이 커밋한 뒤에도 두 번째 커넥션이
  raw SQL 로 두 번째 active 행을 넣으면 (고치기 전에는) 조용히 성공했다.
- **왜 심각한가**: `config/guardrails.yaml` 의 `concurrency.max_active_runs_per_case: 1`
  이 문서·설정에는 있는데 실제로 강제하는 DB 제약이 없었다 — "설정에 숫자가
  있다"와 "그 숫자가 지켜진다"의 차이(이 저장소가 여러 번 겪은 패턴).
  경합이 실제로 일어나면 같은 Case 에 대해 LLM 호출·제안 생성이 중복돼
  낭비가 생기고, 두 실행이 서로 다른 `expected_version` 기준으로 전이를
  시도하면서 예측 못한 재시도 연쇄가 날 수 있다.
- **고침**: `migrations/004_agent_runs_active_uniqueness.sql` — partial
  unique index(`(tenant_id, case_id) WHERE status IN ('active','running','resuming')`).
  `start_run()` 의 기존 `SELECT` 검사는 흔한 경로(이미 활성 run 있음)를 빠르게
  거부하는 용도로 남기고, `UniqueViolation` 을 잡아 같은 `ActiveRunError` 로
  번역해 DB 가 최종 방어선이 되게 했다.
- **테스트**: `tests/integration/controller/test_active_run_uniqueness.py`
  (신규, 3건) — DB 제약 자체가 raw SQL 로 두 번째 삽입을 막는지, 별도
  커넥션 두 개로 만든 진짜 경합이 막히는지 확인.

## 문서화만 하고 고치지 않은 것 3건

### 1. `POST /v1/cases/{case_id}/messages` 가 resume token 을 검증하지 않는다
이건 **라운드 04 에서 이미 발견하고 보류한 것과 같은 항목**이다
(`docs/reports/debugs/2026-08-17_버그사냥_04_4건_발견_2건_수정_1건_보류_1건_해소.md`).
이번 라운드가 다시 확인해 같은 결론(REST 계약 변경 필요, 사용자 결정 대기)에
도달했다 — 중복 수정은 안 했다.

### 2. `case_wall_clock_seconds` 가 context 구성·team 실행 시간을 합쳐 재지 않는다
- **재현 확인(코드 사실)**: `controller.py:140` 에서 **한 번만** 검사한다 —
  team 실행 직전. 그 뒤 context 구성이나 team 실행이 남은 예산을 넘겨도
  재검사가 없다.
- **왜 지금은 안 고치는가**: `team_timeout_seconds`(90초) 가 실제 team 실행
  단계는 이미 `asyncio.wait_for()` 로 확실히 상한을 두므로, 이 gap 때문에
  실행이 무한정 도는 일은 없다 — 총 wall-clock 예산(180초)을 정확히 지키지
  못할 뿐이다(돈·승인과 무관한 자원/SLA 가드레일). 위험도가 낮아 이번엔
  문서화만 한다.

### 3. `run_case()` 를 대기 상태(WAITING_INPUT/WAITING_APPROVAL) Case 에 직접 호출하면 resume 절차 없이 team 을 실행할 수 있다
- **재현 확인(코드 사실)**: `controller.py` 에 이 상태들을 거부하는 guard 가
  없다 — `RESUMING` 상태만 특별 취급하고 나머지는 그냥 통과시킨다.
- **왜 지금은 안 고치는가**: `grep` 으로 확인한 결과 `Controller.run_case()`
  를 부르는 프레젠테이션 계층 호출부는 `cases.py:95` **하나뿐**이고, 그마저
  `status == "routing"` 조건에 걸려 있다 — 지금은 도달 불가능하다(라운드
  02 의 `outbox.publish()`, 라운드 06 자체의 finding #1 과 같은 유형: 내부
  메서드가 유일한 호출자를 신뢰하는 경우). 향후 내부에서 이 메서드를
  다른 방식으로 부르기 시작하면 재확인이 필요하다.
