# 2026-08-18 — 버그사냥 라운드 08 (전체 점검)

Codex에게 저장소 전체를 "리포트만, 수정 금지" 계약(`docs/handoff/_prompts/
S-BUGHUNT-08-전체점검.md`)으로 발주하고, 나온 4건을 전부 직접 재현·검증했다.
1건은 실제 결함으로 확인해 재현 테스트를 먼저 작성(실패 확인) → 수정 →
재실행(통과) 순서로 고쳤다. 2건은 코드를 다시 읽어 보니 이미 올바르게
설계된 안전장치였다(결함 아님). 1건은 실제로 진단 정보 손실은 있지만
안전한 동작 자체는 맞아서 이번 라운드에서는 고치지 않고 보류했다.

## 1. [실제 결함, 수정함] `app/presentation/api/cases.py:89-97` — CLASSIFIED 전이 버그가 "분류 실패"로 둔갑

`POST /v1/cases`의 `try` 블록이 `classifier()` 호출뿐 아니라 뒤이은
`transition_case(...CLASSIFIED...)` 호출까지 감싸고 있었다. classifier
자체는 정상 값을 반환했는데, **CLASSIFIED 전이 자체가 실패**(예:
`StateConflict`·`InvalidTransition` — 리듀서/버전 불일치 등 진짜 시스템
버그)해도 같은 `except Exception:` 이 잡아 `classification_failed` 로
기록했다. CLAUDE.md §3 이 이미 이 정확한 실수를 경고한다: "오류 메시지가
사실을 잘못 전하지 않게 한다 (상태 충돌을 'LLM 실패'로 보고하면 한참
헤맨다)."

**재현**: `tests/integration/api/test_api_runtime.py::
test_create_does_not_relabel_a_transition_bug_as_classification_failure`.
`transition_case`를 몽키패치해 두 번째 호출(CLASSIFIED)에서만
`StateConflict`를 던지게 하고, classifier는 정상 값을 반환하게 했다.
수정 전: `201` + `classification_failed`로 조용히 성공 처리됨(진짜 원인이
사라짐). 수정 후: `500`(정직하게 실패), 트랜잭션 전체 롤백(반쪽 상태로
남지 않음).

```powershell
python -m pytest tests/integration/api/test_api_runtime.py::test_create_does_not_relabel_a_transition_bug_as_classification_failure -q
```
```text
# 수정 전: assert 201 == 500  → FAILED
# 수정 후: 1 passed
```

**수정**: `try`를 `classifier()` 호출만 감싸도록 좁혔다. classifier가
실패하면(또는 필드가 부족하면) `result = None`으로 두고 `CLASSIFICATION_FAILED`
로 전이한다. classifier가 성공했으면 `CLASSIFIED` 전이는 `try` 밖에서
호출해, 그 전이 자체의 버그는 있는 그대로 드러나게 했다(500 → FastAPI
`internal_error` 핸들러).

## 2. [결함 아님, 확인 완료] `app/introspection/contract.py:113,119` — `except Exception: pass`

`_port_implementations()`가 message_broker/graph_store 조립 실패를
`pass`로 넘기고 `None`을 남긴다. 코드 자체의 docstring이 이미 이유를
말한다: "★얻지 못하면 `None`(모름)이다. 지어내지 않는다." — 이 함수는
읽기 전용 introspection 엔드포인트(`GET /introspection`)가 "실제로 무엇이
조립됐는지"를 보여주는 용도이고, 한 컴포넌트의 조립 실패로 전체 introspection
응답이 500이 되는 것보다 "이 항목은 모른다"로 표시하는 게 CLAUDE.md §1
"지어내지 않는다" 원칙에 맞다. 결함 아님.

## 3. [결함 아님, 확인 완료] `app/application/proposal_guard.py:33-52,77-84` — 대조용 재조회 실패

`load_facts()`/`recheck_before_execution()`의 `except Exception:` 은
docstring에 이미 이 결정의 배경이 적혀 있다: "savepoint 없이 짰다가
컬럼명을 하나 틀렸고, 그 한 번의 실패가 트랜잭션을 aborted 로 만들어
뒤따르는 전이까지 전부 무너졌다." — 즉 **이번 라운드에서 `cases.py`에서
발견한 것과 정확히 같은 종류의 트랜잭션 오염 버그를 이미 겪고 고친
자리**다. `with conn.transaction():`로 savepoint 를 만들어 조회 실패가
호출자의 트랜잭션을 죽이지 않게 막았고, 실패 시 `Facts(loaded=False)`로
표시해 `verify_proposal()`이 **전건 거부**하게 만든다(CLAUDE.md §0.1
"확인 불가 → 거부"). 결함 아님 — 오히려 이 라운드가 고친 문제의 올바른
해법이 이미 적용된 예시다.

## 4. [진단 정보 손실은 있으나 안전 동작은 맞음, 보류] `app/application/controller.py:68-73` — RAG 검색 실패를 조용히 degraded 처리

`_policy()`가 `policy_search()`의 모든 예외를 `retrieval_failed=True`로
바꾼다. **동작 자체는 안전하다** — 일반 지식으로 조용히 메우지 않고
`ContextPack.degraded=true`로 남긴다(CLAUDE.md §0.1이 요구하는 그대로).
다만 "RAG가 실제로 죽었다"와 "검색 코드 자체에 버그가 있다"를 구분할 방법이
없다 — 둘 다 같은 `degraded` 신호로만 남는다. `proposal_guard.py`(항목 3)
처럼 이미 트랜잭션 오염 문제를 겪은 자리도 아니고(별도 커넥션으로 검색하는
구조), 잘못된 결과를 진짜인 것처럼 내보내는 것도 아니라서 이번 라운드의
"진짜 재현 가능한 결함" 기준에는 못 미친다. 다음 라운드에서 예외 타입/메시지를
구조화 로그나 `ContextPack.omissions`에 남기는 관측성 개선으로 검토할 것 —
이번엔 고치지 않았다.
