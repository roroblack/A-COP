# 버그사냥 03 — 환불 제안이 검증에서 매번 거부되고 있었다 (지금까지 3라운드 중 최고 위험도)

Codex 에 리포트만(수정 금지) 발주(`docs/handoff/_prompts/S-BUGHUNT-03-TEAMS-VOC.md`,
`docs/reports/2026-08-17_버그사냥_03_Teams_VOC.md`)한 뒤 직접 재현·수정했다
(RULE.md §3.6-3). Codex 는 "코드 읽기로만 판단, DB 통합 재현은 안 해봄"이라고
정직하게 적었는데, 직접 실행해서 **실제로 재현했다** — 아래 참조.

## 무엇이 잘못됐는가

`app/modules/customer_ops/billing.py:72`(수정 전) — `BillingSubscriptionTeam`
이 만드는 환불(`refund.request`) 제안은 `arguments={"customer_id": ...}` 뿐이었다.

`app/modules/customer_ops/verification_policy.py` 의 `CUSTOMER_OPS_POLICY` 는
`payment_id`(참조)·`amount`/`amount_cents`(수량)만 대조 대상으로 선언한다.
`customer_id` 는 `references`·`quantities`·`opaque`·`ignored` 어디에도 없다.

## 재현 (실제로 돌렸다)

```python
from app.core.verification import Facts, verify_proposal
from app.modules.customer_ops.verification_policy import CUSTOMER_OPS_POLICY

arguments = {"customer_id": "cust-123"}
facts = Facts(collections={"payments": {}, "subscriptions": {}, "entitlements": {}},
              evidence_ids=frozenset({"ev-1"}))
verify_proposal(arguments=arguments, rationale_evidence_ids=["ev-1"], facts=facts,
                policy=CUSTOMER_OPS_POLICY)
```
실제 출력:
```
customer_id - 선언되지 않은 필드다 — 검사 규칙이 없으면 실행하지 않는다
TOTAL: 1
```

`app/application/controller.py:_reject_unverified()` 는 `WAIT_FOR_APPROVAL` 을
내는 **모든** 제안에 대해 이 검증을 돈다(`verification_policy.references` 가
비어있지 않으면 스킵하지 않음). 즉 **`BillingSubscriptionTeam` 이 만드는 환불
제안은 옳고 그름과 무관하게 매번 `GUARDRAIL_ESCALATED` 로 튕겨나가고,
실제 사람 승인 화면(`WAIT_FOR_APPROVAL`)에 도달한 적이 실제로는 한 번도
없었다.**

## 왜 지금까지 아무도 못 잡았는가

- `tests/unit/teams/test_team_scenarios.py::test_billing_cancelled_subscription_waits_for_refund_approval`
  는 **Team 을 단독으로만** 돌려 `outcome == "waiting"` 인지만 봤다 —
  `verify_proposal()` 을 통과시키지 않았다.
- `tests/unit/core/test_proposal_verification.py` 는 검증 로직 자체는 잘
  테스트하지만, **손으로 만든** `{"payment_id": ..., "amount": ...}` 류의
  arguments 만 넣어봤다 — 실제 Team 이 무엇을 만드는지는 안 봤다.
- 두 테스트 파일이 서로 다른 손으로 만든 입력만 검사해서, **실제 Team 출력을
  실제 검증기에 통과시켜 보는 테스트가 아예 없었다.** 통합의 이가 빠진
  자리였다.
- 발표용 시나리오(`scripts/seed_demo_cases.py`)는 이 흐름을 실행하지 않고
  Case 를 곧바로 `waiting_approval` 상태로 심는다 — 그래서 발표에서도
  드러나지 않았다.

## 고침

`app/modules/customer_ops/billing.py` — 환불 대상 결제를 하나 특정해
(`charged_payment = next((p for p in payments if p.get("status") in
{"paid","succeeded"}), None)`), 제안 arguments 를
`{"payment_id": ..., "amount_cents": ...}` 로 바꿨다. `customer_id` 는
검증할 방법이 없고 필요하지도 않아 제안에서 뺐다.

`tests/unit/teams/test_team_scenarios.py` 의 기존 테스트에 **실제 Team 출력을
`verify_proposal()` 에 통과시키는 단언**을 추가했다 — 이번에 발견한 것과 같은
"두 테스트가 서로 다른 입력만 본다" 유형의 결함이 다시 조용히 들어오면 여기서
잡힌다.

## 남은 것 — 새로 드러난, 아직 손대지 않은 관찰

`payments` 를 여러 건 반환하는 결제 이력에서 **어떤 결제를 환불 대상으로
고를지가 결정적이지 않다.** `FACT_QUERIES` 의 SQL(`verification_policy.py:46-49`)
에 `ORDER BY` 가 없어 `paid`/`succeeded` 상태의 결제가 여러 건이면 DB 가
돌려주는 순서에 의존한다. 지금 고침은 "그 중 하나를 확정적으로 고른다"만
보장한다 — **"가장 최근 결제를 고른다"는 보장은 아직 없다.** 이건 별도
확인이 필요한 관찰이라 이번엔 손대지 않았다(범위를 넓히지 않는다, RULE.md §2).

## 위험도 및 왜 이게 지금까지 3라운드 중 가장 심각한가

이건 "새는 경계"가 아니라 **핵심 데모 시나리오가 실제 실행 경로로는 한 번도
작동한 적이 없었다**는 뜻이다. DoD-24("ActionProposal 근거 대조·실행 차단")
가 "통과"로 기록돼 있는데, 그 판정은 **손으로 만든 fixture 로 검증기 자체가
옳게 도는지**만 쟁였지 **실제 Team 이 검증기를 통과하는 제안을 만드는지**는
안 쟁었다 — "코드가 있다"와 "그 경로가 밟힌다"의 차이(`RULE.md` 가 이미 여러
번 겪었다고 적어 둔 바로 그 패턴)다.
