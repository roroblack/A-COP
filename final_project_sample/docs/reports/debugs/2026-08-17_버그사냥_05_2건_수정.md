## 고친 것 2건

### 1. `app/infrastructure/graphstore/sql_adapter.py:117-119` — `subgraph()` 가 DoD-21 세 축을 빠뜨렸다
- **재현 확인**: `subgraph()` 는 `neighbors()` 를 부르면서 자기만의 고정
  `edge_types` 목록(`["owns","has_event","proposed","approved","contains","in_document"]`)
  을 썼다 — `has_issue`/`governed_by`/`handled_by`(DoD-21 이 v7 §27-21 로
  지정해 추가한 세 축)가 빠져 있었다. `neighbors()` 를 그 타입으로 직접
  부르면 나오는데(`test_graph_v7_axes.py` 가 이미 증명) `subgraph()` 경로만
  조용히 뺐다.
- **왜 지금은 안 뚫리는가(그런데도 고친 이유)**: `subgraph()` 를 부르는
  프로덕션 코드가 없다(`grep` 확인) — 지금은 도달 불가능하다. 그런데 "이
  노드 주변 전체"를 낸다는 이름의 함수가 실제로는 DoD-21 이 추가한 축들을
  빼고 냈다 — 나중에 trace UI 나 MCP 가 이 함수를 쓰기 시작하면 조용히
  절반만 보여줄 뻔했다.
- **고침**: `neighbors()`/`subgraph()` 가 공유하는 `EDGE_TYPES` 상수를 만들어
  세 축을 포함시켰다.
- **테스트**: `tests/unit/infrastructure/test_graph_v7_axes.py::test_subgraph_includes_the_v7_axes`
- **문서**: `docs/evidence/DoD-21_Graph_관계질의.md` 에 addendum 추가 — 판정
  자체는 안 바뀐다(`neighbors()` 의 관계 질의 정확성은 원래도 맞았다).

### 2. `app/infrastructure/db/repository.py:26-30` — Case 목록 정렬이 동률에서 결정적이지 않다 (의심됨 → 확인 후 고침)
- **재현 확인(코드 사실)**: `ORDER BY created_at DESC LIMIT %s` 뿐, 2차
  정렬키가 없다. `created_at` 이 같은 행이 여러 개면 PostgreSQL 이 순서를
  보장하지 않는다.
- **실제 영향은 낮게 평가한다**: 이 API 는 offset/cursor 기반 페이지네이션이
  아예 없다 — 매번 "최근 N개"를 통째로 다시 낸다. 그래서 Codex 가 지적한
  "반복 요청에서 경계 항목이 바뀐다"는 클라이언트가 체감할 페이지네이션
  버그가 아니라, **동률일 때 어느 게 "최근 N개 중 N번째"인지가 안정적이지
  않다**는 좁은 의미의 결정성 문제다. `timestamptz` 는 보통 마이크로초
  정밀도라 실제 동률은 드물지만(시드 스크립트의 대량 삽입 등에서는 발생
  가능), 고치는 비용이 거의 없어 그냥 고쳤다.
- **고침**: `case_id` 를 2차 정렬키(`DESC`)로 추가했다.
- **테스트 추가 안 함**: 정확히 같은 `created_at` 을 강제로 만드는 건 DB
  타이밍에 의존적이라 신뢰할 만한 단위 테스트로 만들기 어렵다 — 코드
  변경 자체가 명백히 옳고(2차 정렬키 추가는 부작용이 없다) 기존 테스트가
  전부 그대로 통과하는 것으로 충분하다고 판단했다.
