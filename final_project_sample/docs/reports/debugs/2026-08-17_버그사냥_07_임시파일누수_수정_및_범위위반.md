## 고친 것 1건

### `app/application/composer_service.py:apply_candidate()` — `os.replace()` 실패 시 staged 임시 파일이 안 지워졌다
- **재현 확인**: `os.replace` 를 `OSError` 를 던지도록 주입해 재현. 후보
  파일(`candidate_path`)은 `finally` 에서 지워지지만 `staged` 파일은 그
  `finally` 블록의 정리 대상이 아니었다 — 디스크 오류·권한 문제가 반복되면
  `.project.write.<uuid>.yaml` 파일이 계속 쌓인다.
- **고침**: `staged` 도 `finally` 에서 `unlink(missing_ok=True)` — 성공
  경로에서는 이미 `os.replace()` 로 옮겨져 없으므로 조용히 넘어간다.
- **테스트**: `tests/unit/application/test_composer_service.py`(신규) —
  `os.replace` 를 monkeypatch 로 실패시키고 임시 파일이 하나도 안 남는지,
  원본 revision 이 안 바뀌었는지 확인.

## 이미 알려진 제약으로 확인한 것 1건

### `_WRITE_LOCK` 이 프로세스 로컬이라 다중 워커에서 동시성이 원자적이지 않다
이건 **새로 발견한 게 아니라 이미 코드 자체의 주석에 적혀 있던 제약**이다
(`composer_service.py:35-37`, 이번 세션에서 만들 때 이미 명시함): "★단일
프로세스 안에서만 동시 쓰기를 막는다. 여러 워커·여러 인스턴스에 걸친 잠금은
아직 없다 — 지금은 로컬 단일 개발자 도구다." Codex 가 코드를 안 읽고
독립적으로 같은 결론에 도달한 것 자체는 검증 가치가 있지만, 이미 설계
문서(`docs/handoff/13_Composer_쓰기채널_계약.md` "경계 / 아직 없는 것")에도
있는 항목이라 새 조치는 안 한다.

## 버그 아님으로 확인한 것 3건 (eval/stats)

Codex 가 직접 재현해 확인했고, Claude 는 그 재현 방법과 결과를 코드 대조로
재검증했다:
- `bootstrap.py`: 같은 seed 로 두 번 돌리면 정확히 같은 결과 — `random.Random(seed)`
  를 함수 내부에서 새로 만들어 전역 상태에 안 얽힌다.
- `mcnemar.py`: discordant 0건, 정확히 threshold(25) 경계 양쪽 모두 올바른
  분기(exact ↔ chi-square)로 처리된다.
- `agreement.py`: 카테고리가 하나뿐일 때(`expected==1.0`)의 상수 분기가
  표준 Cohen's kappa 공식과 일치한다.
