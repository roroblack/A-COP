## 1. resume token 미검증 (라운드 04·06) — ★수정

`POST /v1/cases/{case_id}/messages` 가 `Controller.resume()`(실제 토큰
hash·만료·일회성 검증)을 완전히 우회하고 있었다.

### 조사 중 추가로 발견한 것 — Controller.resume() 자체에 죽어 있던 버그 2건

`Controller.resume()` 은 이 세션 전까지 **어떤 테스트에도 호출된 적이 없었다**
(REST/MCP 어디서도 안 부르고, `test_controller_integration.py` 도
`validate_resume()` 만 단독으로 테스트했다). 실제로 처음 통합 테스트를
붙이면서 두 개를 더 찾았다:

- **에러 escalate 가 롤백으로 사라짐**: `resume()` 이 `ResumeTokenError` 를
  잡아 `WAIT_EXPIRED` 로 escalate 하고 예외를 다시 던지는데, 이 커넥션은
  그 앞의 `get_case()` 조회 때문에 이미 ambient 트랜잭션이 열려 있어서
  `with conn.transaction():` 가 진짜 커밋이 아니라 savepoint 로 동작했다.
  예외가 바깥 커넥션 컨텍스트 밖으로 나가며 전체가 롤백돼 escalate 기록이
  사라졌다 — 실제 테스트로 재현: 틀린 토큰으로 resume 한 뒤에도 Case 가
  `waiting_input` 에 그대로 남아 있었다. **고침**: escalate 트랜잭션이
  정상 종료된 뒤 명시적으로 `conn.commit()`.
- **이미 완료된 Case 에 재사용 토큰이 들어오면 두 번째 오류가 첫 번째를
  가림**: 이미 `resolved` 인 Case 에 만료/재사용 토큰이 들어오면
  `WAIT_EXPIRED` 자체가 그 상태에서 전이표에 없는 조합이라
  `InvalidTransition` 이 나서 원래 문제(토큰 재사용)가 안 보이게 됐다.
  **고침**: escalate 시도를 `InvalidTransition` 으로 감싸 실패해도 원래
  `ControllerError` 만 낸다.
- **`resume()` 자신이 이미 내부에서 `run_case()` 를 부른다**(controller.py:280,
  처음 읽을 때 놓쳤었다) — REST 핸들러에서 또 부르면 이미 resolved 된 Case 에
  완료 이벤트를 두 번 적용하려다 `InvalidTransition` 이 난다. REST 핸들러는
  `resume()` 한 번만 부르면 된다.

### 고침
- `MessageRequest` 에 `token: str` 필드 추가, `expected_version` 제거(더

  `ControllerError` → `401 invalid_resume_token`

## 3. 재검증-승인 트랜잭션 경계 (라운드 01) — ★부분 개선, 완전한 원자성은 범위 밖

### 시도했다가 psycopg3 API 제약에 막힌 것
재검증과 승인 write 를 하나의 `with conn.transaction():` 로 합치고 그
**안에서** `conn.commit()` 을 불러 실패 시 즉시 커밋 후 raise 하려 했다.
psycopg3 가 이를 명시적으로 막는다: `ProgrammingError: Explicit commit()
forbidden within a Transaction context` — 직접 재현해 확인했다.

### 되돌린 것과 그 이유
원래 구조(재검증은 트랜잭션 밖, 실패 시 escalate 는 자기만의 트랜잭션 +
명시적 commit + raise, 성공 시 별도 트랜잭션으로 승인 write)로 되돌렸다.
이 구조가 이미 **psycopg3 하에서 정확한 유일한 형태**라는 걸 이번에
확인했다 — 예전 코드 주석("안에서 하고 409를 던졌더니 방금 쓴 escalated
이벤트가 롤백돼 사라졌다")이 말하는 게 정확히 이 API 제약이었다는 것도
이번에 원인까지 명확히 밝혔다(ambient 트랜잭션 + savepoint + 외부 커넥션
컨텍스트의 rollback-on-exception 조합).

### 실제로 좁힌 것
재검증(`recheck_before_execution()`)과 승인 write 사이에 별도 함수 호출이나
불필요한 지연 없이 곧바로 이어지도록 정리했고, idempotent 재시도는 재검증
전에 조기 반환하도록 앞당겨 불필요한 재검증을 줄였다.

### 정직하게 남기는 한계
**완전한 원자성(그 사이 다른 트랜잭션이 끼어들 수 없음을 보장)은 여전히
없다.** 재검증의 SELECT 와 승인의 write 가 서로 다른 트랜잭션인 이상, 그
경계에 낀 아주 좁은 창(같은 HTTP 요청 처리 안, 사람이 기다리는 구간이
아니라 DB 왕복 몇 번 사이)은 이론적으로 남는다. 완전히 없애려면 재검증이
참조하는 payment/subscription 행에 `SELECT ... FOR UPDATE` 를 걸어 승인
커밋까지 잠금을 유지해야 하는데, 이건 `proposal_guard.py` 의 fact 조회
SQL 구조를 바꾸는 별도 작업이라 이번 범위 밖으로 남긴다.
