# 리뷰 스팸/가짜 리뷰 탐지의 VOC 파이프라인 편입 논의

작성일: 2026-08-20  
대상: A-COP 국내 쇼핑몰 고객운영(CS) AI 플랫폼  
범위: 설계 논의. 자동 삭제·차단·제재 등 side effect 실행은 범위에 포함하지 않는다.

## 결론 요약

현재 상태에서 “가짜 리뷰 탐지 기능”을 분류기로 출시하는 것은 권하지 않는다. 가짜 리뷰 라벨도, 한국어 리뷰용 검증된 사전학습 모델도 없으므로 임의 임계값을 정해 리뷰를 가짜라고 분류하면 근거 없는 확정과 높은 오탐 위험을 만든다.

다만 즉시 시작할 수 있는 안전한 최소 기능은 있다. 이름을 `review_integrity_review` 또는 `review_spam_triage`처럼 제한적으로 붙이고, 리뷰를 가짜라고 판정하지 않고 **검토가 필요한 이상 징후 묶음**을 ActionProposal로 제안한다. 이 제안은 복수의 관측 가능한 신호, 각 신호의 범위와 한계, 데이터 품질 상태를 Evidence로 함께 반환해야 한다. 최종 상태는 `waiting_input` 또는 `escalated`가 기본이며, 사람의 확인 전에는 정상/가짜의 이분류 상태를 확정하지 않는다.

첫 단계는 다음의 순서가 가장 현실적이다.

1. 네이버쇼핑 리뷰와 AI Hub 리뷰에서 라벨 없는 신호를 계산하는 오프라인 프로파일링을 한다.
2. 매장·상품·시간·카테고리별 정상 변동을 먼저 추정한다. 전역 임계값은 사용하지 않는다.
3. 설명 가능한 약한 신호를 2개 이상 묶어 “검토 제안”만 생성한다.
4. CS/운영자가 제안을 검토하고 `정상`, `의심 유지`, `오탐`, `추가 확인 필요`를 기록하는 작은 휴먼 라벨링 루프를 만든다.
5. 충분한 운영 라벨과 비용 함수가 생긴 뒤에만 준지도 학습 또는 지도 모델을 검토한다.

## 1. 지금 당장 가능한 시작점과 선택지 비교

### A. 규칙 기반 약한 신호: 첫 단계로 적합

중복 텍스트, 짧은 시간 내 비정상적인 리뷰 집중, 계정·상품 간 반복 패턴 등 관측 가능한 특징을 계산하고, 각 특징을 별도의 Evidence로 제시한다. 규칙은 “스팸”을 결정하는 것이 아니라 “검토 우선순위”를 정하는 데 사용한다.

장점:

- 라벨과 사전학습 모델 없이 시작할 수 있다.
- 왜 제안되었는지 설명하기 쉽다.
- 신호별 오탐 사례를 운영자가 바로 교정할 수 있다.
- ActionProposal과 `waiting_input`/`escalated` 흐름에 자연스럽게 맞는다.

단점:

- 공격자가 규칙을 피할 수 있다.
- 정상적인 프로모션·신상품 출시·공동구매도 이상 패턴으로 보일 수 있다.
- 단일 신호의 판별력은 낮다.

권장 방식은 규칙 점수를 하나의 진실값으로 취급하지 않고, “관측된 신호의 목록”과 “검토 우선순위”로만 사용하는 것이다.

### B. LLM-as-judge: 보조적인 텍스트 검토에만 사용

LLM에게 리뷰 내용만 보고 가짜 여부를 맞히게 하는 방식은 현재의 첫 모델로 적합하지 않다. 문체가 광고 같거나 과도하게 칭찬하는 것만으로는 가짜라고 볼 수 없고, 한국어 쇼핑 리뷰의 카테고리별 정상 문체도 다양하다. 모델의 확신도 역시 근거 있는 확률로 해석하기 어렵다.

사용한다면 다음처럼 제한해야 한다.

- LLM은 최종 판정자가 아니라, 이미 계산된 구조화 신호를 사람이 읽기 쉬운 요약으로 정리한다.
- 입력에 포함된 Evidence만 사용하게 하고, 계정 활동·구매 여부·시간 정보 등을 추측하지 못하게 한다.
- 결과 필드는 `textual_consistency_observation`처럼 관찰/요약으로 명명한다.
- 반드시 원문과 신호를 함께 보존하고, LLM 출력만으로 ActionProposal을 만들지 않는다.
- 모델 버전, 프롬프트 버전, 실행 시각을 Evidence 메타데이터로 남긴다.

장점은 텍스트의 반복성·광고성·상품과의 관련성 같은 정성적 검토를 보조할 수 있다는 점이다. 단점은 재현성·설명 가능성·언어 및 카테고리 편향이 있고, 라벨 없는 상황에서 성능을 검증하기 어렵다는 점이다. 따라서 초기에는 선택적 보조기로 두는 편이 안전하다.

### C. 준지도 학습/부트스트래핑: 휴먼 루프 뒤의 두 번째 단계

현재 가진 감성 라벨은 가짜 리뷰 라벨이 아니다. 긍정 리뷰를 가짜로, 부정 리뷰를 정상으로 간주하는 식의 부트스트래핑은 타깃을 잘못 정의한다. 먼저 중복·폭증·계정 집중 등 고정밀에 가까운 후보를 사람이 검토해 소량의 신뢰 라벨을 만든 뒤, 그 라벨과 라벨 없는 리뷰를 이용해 모델을 학습하는 순서가 필요하다.

장점은 수작업 라벨 비용을 줄이고 여러 신호의 조합을 학습할 수 있다는 점이다. 단점은 초기 규칙의 편향을 모델이 확대할 수 있고, “규칙으로 뽑힌 후보”만 학습해 놓치기 쉬운 스팸을 보지 못할 수 있다는 점이다. 부트스트랩 라벨에는 `human_confirmed`, `rule_candidate`, `unverified`를 구분해야 하며, 서로 다른 시간·상품·판매자 단위로 검증 세트를 분리해야 한다.

## 2. 유용할 수 있는 약한 신호와 정상 오탐 사례

아래 신호는 단독으로 가짜를 의미하지 않는다. 신호는 가능하면 상품·판매자·카테고리·기간별 기준선과 비교해야 한다.

| 신호 | 관측 방법 | 정상적으로 오탐할 수 있는 경우 |
|---|---|---|
| 동일/근사중복 텍스트 | 정규화한 문장, 형태소/문자 n-gram, 임베딩으로 리뷰 간 유사도와 동일 문구 군집을 계산 | 가족·지인이 비슷한 사용 경험을 남김, 판매자가 제공한 사용 가이드가 여러 리뷰에 반영됨, 옵션/사이즈만 다른 상품, 짧은 후기 템플릿 사용 |
| 같은 문구의 상품 간 반복 | 한 계정·여러 계정이 서로 다른 상품에 동일하거나 거의 동일한 문장을 남기는지 확인 | 브랜드가 여러 상품을 함께 구매한 고객, 체험단 공통 안내 문구, 동일 제조사의 상품군 |
| 짧은 시간 내 리뷰 폭증 | 상품·판매자·계정군의 시간별 리뷰 수를 과거 기준선 및 유사 상품과 비교 | 배송 지연 후 일괄 도착, 프로모션/라이브커머스, 신상품 출시, 명절·시즌성 수요, 구매확정 정책에 따른 일괄 작성 |
| 평점-텍스트 감성 불일치 | 별점과 텍스트의 긍정/부정 표현이 충돌하는 비율 및 대표 문장 추출 | 별점은 배송/포장, 텍스트는 상품 품질을 평가함, 별점 입력 실수, “좋지만 재구매는 안 함” 같은 복합 의견, 비꼼/구어체 |
| 극단 별점 집중 | 특정 시간·계정군·상품에서 5점 또는 1점이 비정상적으로 집중되는지 확인 | 팬덤/브랜드 충성 고객, 품질 사고에 따른 실제 집단 불만, 이벤트 보상, 경쟁 상품 비교 후 집단 행동 |
| 신규 계정/활동 이력 집중 | 새 계정 비중, 짧은 기간의 활동량, 여러 상품에 대한 반복 행동을 확인 | 플랫폼 가입 이벤트, 신규 고객 유입 캠페인, 가족 구성원의 별도 계정, 개인정보 보호로 계정 연계가 제한됨 |
| 계정-상품 네트워크 반복 | 계정-상품-시간 그래프에서 동일 계정군이 여러 상품을 유사 순서로 평가하는지 확인 | 재구매, 정기배송, 한 판매자의 여러 옵션 구매, 공동구매·대량구매 |
| 리뷰 작성 간격/행동 패턴 | 계정별 비현실적으로 일정한 간격, 짧은 시간의 다상품 작성, 동일 기기/접속 정보가 있다면 군집 확인 | 업무상 리뷰를 한 번에 작성, 주문 일괄 처리, 가족·회사·기숙사 등 공유 네트워크 |
| 상품과 무관한 문장/광고성 | 상품 속성·카테고리와의 관련성, 외부 연락처·반복 홍보 문구 확인 | 짧은 배송 후기, 선물 수령자 리뷰, 카테고리 특성상 상품 설명이 적은 후기, 판매자 안내에 따른 표현 |
| 언어·문체 이상 반복 | 같은 비정상 오탈자, 기계적 표현, 번역투가 계정군 사이에서 반복되는지 확인 | 외국인 고객, 모바일 키보드/음성 입력, 특정 커뮤니티의 공통 말투, 장애·접근성 도구 사용 |

실무적으로는 `근사중복 + 짧은 시간 집중 + 계정/상품 네트워크 반복`처럼 서로 다른 종류의 신호가 함께 나타나는 경우를 우선 검토 대상으로 삼는 편이 낫다. 반대로 “긍정적이고 길다”, “문법이 어색하다”, “사진이 없다” 같은 단순 문체 특징은 독립 신호로 강하게 사용하지 않는 것이 좋다.

## 3. A-COP의 ActionProposal/Evidence에 얹는 방식

핵심 명칭은 `fake_review`가 아니라 `review_integrity_concern` 또는 `review_spam_review_request`가 적절하다. 시스템이 보고하는 것은 리뷰의 진위가 아니라, 운영자가 확인할 이유가 있는 관측 패턴이다.

### 제안의 의미

예시 문구:

> “이 리뷰는 가짜입니다”가 아니라, “이 리뷰와 동일 상품의 다른 리뷰 17건에서 동일/근사 문구가 관찰되었고, 해당 군집의 12건이 18분 안에 작성되었습니다. 프로모션·일괄 배송 등 정상 사유를 확인해 주세요.”

권장 상태 전이는 다음과 같다.

`observed_signals` → `review_requested` 또는 `escalated` → 사람의 `confirmed_concern`/`normal_explanation`/`insufficient_evidence`

초기에는 `confirmed_fake` 같은 상태를 만들지 않거나, 최소한 사람의 명시적 확인과 확인 주체·시각·근거가 있을 때만 사용할 수 있게 제한한다. Team이 side effect를 실행하지 않으므로 제안의 action은 삭제나 숨김이 아니라 “운영자 검토 요청”, “주문/프로모션 맥락 확인 요청”, “추가 데이터 요청”이어야 한다.

### Evidence에 반드시 포함할 내용

- `source_type`: 예를 들어 `review_record`, `derived_metric`, `cluster_analysis`, `order_context`, `human_review`.
- `source_id`: 리뷰 ID, 분석 실행 ID, 군집 ID, 운영 검토 티켓 ID 등 재조회 가능한 식별자.
- `observed_at`: 원천 리뷰 작성 시각 또는 파생 분석이 실행된 시각. 둘이 다르면 둘 다 구분해 보존한다.
- 관측값: 유사도, 군집 크기, 시간 창, 기준선, 별점-텍스트 충돌 여부, 신규 계정 비율 등 원래 값을 포함한다.
- 비교 기준: “17건”만이 아니라 어떤 상품/기간/카테고리 기준과 비교했는지 포함한다.
- 한계/대안 설명: 배송 일괄 도착, 이벤트, 재구매 등 정상 설명 가능성을 함께 기록한다.
- 데이터 상태: 계정 식별자·주문·기기·프로모션 정보가 없으면 “확인 불가”라고 적는다.

예시 형태(개념 스키마):

```json
{
  "proposal_type": "review_integrity_concern",
  "status": "waiting_input",
  "target": {"review_id": "review-123", "product_id": "product-45"},
  "summary": "검토 우선순위가 높은 리뷰 군집이 관찰됨; 가짜로 확정하지 않음",
  "evidence": [
    {
      "source_type": "cluster_analysis",
      "source_id": "run-2026-08-20-cluster-7",
      "observed_at": "2026-08-20T09:30:00+09:00",
      "observation": {
        "cluster_size": 18,
        "near_duplicate_similarity": 0.96,
        "time_window_minutes": 18
      },
      "comparison": "동일 상품의 최근 30일 시간당 리뷰 분포",
      "caveat": "프로모션 및 일괄 배송 여부는 현재 데이터로 확인되지 않음"
    }
  ],
  "proposed_action": "운영자가 프로모션·배송·주문 맥락을 확인하고 결과를 기록"
}
```

`confidence: 0.93` 같은 숫자는 실제 라벨로 보정되지 않았다면 사용하지 않는 편이 좋다. 필요하면 `signal_strength: low|medium|high`를 쓰되, 이것은 가짜일 확률이 아니라 “검토 우선순위에 기여하는 관측 신호의 강도”라고 명시해야 한다.

## 4. 현재 데이터로 검증할 것과 새로 확보할 것

### 현재 데이터로 가능한 검증

네이버쇼핑 리뷰 약 199,908건과 AI Hub 속성기반 감성분석 약 25만건으로 다음을 검증할 수 있다.

- 카테고리·별점·감성·리뷰 길이·작성 시각의 분포와 결측률.
- 동일/근사중복 텍스트 비율과 텍스트 군집의 크기 분포.
- 상품 단위의 시간별 리뷰량, 계절성, 상위 폭증 사례.
- 별점과 텍스트 감성의 불일치율. 단, 이는 스팸 라벨이 아니라 불일치 현상 검증이다.
- 카테고리별 정상 문체 차이와 신호별 기준선 후보.
- 텍스트-only 환경에서 계정·주문 정보가 없을 때 어떤 신호가 계산 불가능한지.
- 두 데이터셋의 중복·도메인 차이·수집 시점 차이·라벨 정의 차이.

검증 결과는 “스팸 탐지 성능”이 아니라 `signal coverage`, `stability`, `explainability`, `candidate review cost`로 보고해야 한다. 감성 라벨을 가짜 리뷰 정답으로 사용해 정확도나 F1을 산출하면 안 된다.

### 새로 확보해야 하는 데이터

가짜 리뷰 여부를 실제로 평가하려면 최소한 다음이 필요하다.

- 리뷰 ID와 작성 시각, 상품/판매자/카테고리 ID.
- 가능하다면 주문·구매확정·반품·재구매 여부. 단, 접근권한과 개인정보 보호를 먼저 확인한다.
- 계정의 익명화된 생성 시각, 활동량, 리뷰 작성 이력. 원문 개인정보나 불필요한 식별자는 수집하지 않는다.
- 프로모션·체험단·리워드·공동구매·배송 일괄 처리 이벤트 정보.
- 운영자가 검토한 사례의 라벨, 판정 이유, 검토자, 시각, 반론/정상 설명.
- 신고·제재·이의제기 결과. 이것도 자동 진실값이 아니라 라벨 품질과 편향을 함께 기록한다.
- 시간에 따라 변하는 사전/규칙 및 모델 버전.

라벨은 이분류보다 `정상`, `스팸 의심`, `스팸 확인`, `정상 사유 확인`, `정보 부족`의 다중 상태가 낫다. 특히 `스팸 확인`은 플랫폼 정책과 검토 절차가 정의된 뒤에만 사용해야 한다. 휴먼 라벨은 상품·판매자·기간이 서로 겹치지 않는 검증 분할을 만들 수 있을 만큼 확보해야 한다.

## 5. 손대지 않는 것이 맞는 조건

다음 조건이라면 탐지 기능을 제품 기능으로 노출하지 않고, 데이터 수집·관측 설계만 하는 것이 더 낫다.

- 리뷰 ID 외에 상품·시간·판매자 단위의 맥락도 안정적으로 연결되지 않는다.
- 운영자가 검토 결과를 기록할 수 있는 담당자·절차가 없다.
- 제안이 삭제·노출제한·판매자 경고로 오해될 가능성이 크다.
- 정상 이벤트를 설명할 프로모션·배송 데이터가 없어 오탐 원인을 조사할 수 없다.
- “가짜 리뷰”의 정책적 정의와 증거 기준이 조직 내 합의되지 않았다.
- 테스트할 독립 라벨이 없는데도 임계값·정확도·탐지율을 약속해야 한다.

이 경우의 정직한 제품 상태는 “현재 가짜 리뷰를 판정하지 않음”이다. 대신 VOC에서 `review_pattern_observation`을 내부 분석용으로 계산하고, 사람이 검토할 수 있도록 후보와 Evidence를 축적하는 정도가 적절하다. 그 데이터가 쌓인 뒤에도 신호가 안정적이고 오탐 비용이 감당 가능한지 확인한 후에만 범위를 넓힌다.

## 권장 의사결정

이번 단계의 승인 범위는 **자동 탐지/자동 조치가 아니라, 설명 가능한 이상 징후 관찰과 검토 제안의 내부 파일럿**으로 제한한다. 최초 릴리스의 성공 기준도 “가짜 리뷰를 얼마나 맞혔는가”가 아니라 다음으로 둔다.

- 제안마다 재현 가능한 Evidence가 붙는가.
- 운영자가 정상 사유와 오탐을 기록할 수 있는가.
- 어떤 신호가 카테고리별로 안정적인가.
- 검토 한 건의 비용과 실제 운영 가치가 맞는가.
- 근거 부족 시 `waiting_input`/`escalated`로 멈추는가.

이 기준을 충족할 라벨링 루프와 맥락 데이터가 당장 준비되지 않았다면, 지금은 기능을 만들지 않는 결론이 정당하다. A-COP의 신뢰성을 지키는 관점에서는 탐지 공백을 솔직히 표시하는 것이, 검증되지 않은 가짜 판정을 제공하는 것보다 우선한다.
