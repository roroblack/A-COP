# 네이버 주문 이력 데이터셋

## 한 줄 요약

네이버페이 결제내역에서 본인의 쇼핑 주문 기록을 모아 정리한 데이터다.

## 왜 만들었나

A-COP은 "제 주문 어떻게 됐나요?" 같은 문의에 답해야 한다.

그러려면 **실제 주문 기록이 어떤 모양인지** 알아야 한다. 가상의 예시 데이터로는 실제 상황을 재현할 수 없다. 그래서 진짜 쇼핑몰에서 실제 주문 기록을 받아왔다.

쿠팡(`../coupang_order_history/`)과 함께 **서로 다른 쇼핑몰 두 곳**의 기록을 확보해, 한 곳에만 맞춰진 구조가 되지 않게 했다.

## 어떻게 받아왔나

네이버페이 결제내역 페이지를 브라우저로 열어 화면을 읽는 방식이다.

로그인은 사람이 직접 한다. 프로그램이 아이디와 비밀번호를 다루지 않는다. 사람이 로그인한 브라우저 상태를 프로그램이 이어받아 쓴다.

쇼핑 주문만 골라내기 위해 `serviceChannel=SHOPPING` 조건을 쓴다. 이걸 안 쓰면 송금이나 충전 같은 결제 기록까지 섞인다.

조회와 조회 사이에는 무작위 대기를 넣는다. 기계가 일정한 간격으로 두드리면 차단 대상이 되기 때문이다.

## 알려진 문제 — 첫 수집분에서 4건 누락

아래는 **cyw 제출본 68건에 대한 것이다.** 나머지 세 명의 제출본은 각자의 실제 주문 수와
대조하지 않았으므로, 270건 전체가 "전량"인지는 확인되지 않았다.

**cyw 계정의 실제 주문은 72건인데 68건만 수집됐다.** 다음 4건이 빠져 있다.

```
2022043085163701
2023051853027171
2023090698394101
2024032354706671
```

★**2026-09-01 정정 — 여기 적혀 있던 원인 진단이 틀렸다.**

전에는 "크롤러가 카드마다 주문을 하나씩만 읽었다"고 적혀 있었다. 코드를 읽어 보니
그렇지 않다. `naver_order_crawler.py` 는 카드 안의 **모든** 상세 링크를 순회한다
(`for link_index in range(detail_links.count())`). 수집 당시 로그
(`raw/_crawl_log.txt`)도 같은 것을 말한다 — 모든 페이지에서 **카드 수와 주문 링크
수가 같았다.**

```
1페이지: 카드 15개, 주문 링크 15개
2페이지: 카드 14개, 주문 링크 14개
3페이지: 카드 12개, 주문 링크 12개
```

즉 크롤러가 링크를 빠뜨린 게 아니라 **화면이 그 카드에 상세 링크를 하나만
내줬다.** 그리고 이 크롤러는 주문번호를 **상세 URL 에서만** 얻는다
(`orders.pay.naver.com/order/status/(\d+)`). 그래서 자기 상세 링크가 없는 주문은
식별할 방법 자체가 없어 **구조적으로 보이지 않는다.** 이게 진짜 원인이다.

★이 정정이 중요한 이유: 옛 진단대로 "카드 대신 링크 단위로 순회하도록" 고치면
**이미 그렇게 돼 있는 코드를 다시 고치는 것**이라 한 세션을 헛되이 쓴다.

고치려면 로그인한 상태에서 **주문이 둘 이상 든 카드의 DOM 을 실제로 떠서** 나머지
주문이 어떤 요소로 그려지는지 봐야 한다. 그 전에는 `DETAIL_LINK_SELECTOR` 를 바꿀
근거가 없다. 세션 파일이 지워져 있어 이 작업은 로그인부터 해야 한다.

그동안 이 손실이 **조용히** 일어나지는 않게 해뒀다(2026-09-01):

- 상세 링크가 하나도 없는 카드는 전에는 아무 기록 없이 사라졌다(안쪽 for 문이 0회
  돈다). 이제 `상세 링크 없는 카드` 로 세어 완료 통계에 낸다
- 모든 카드에서 링크가 정확히 1개면 완료 시 주의 문구를 남긴다 — 위 로그가 바로
  그 상태였다

아래 표는 사람이 화면을 직접 세어 만든 것이다.

| 페이지 | 화면의 카드 수 | 실제 주문 수 | 차이 |
|---|---|---|---|
| 1 | 15 | 15 | 0 |
| 2 | 14 | 15 | +1 |
| 3 | 12 | 14 | +2 |
| 4 | 15 | 15 | 0 |
| 5 | 12 | 13 | +1 |
| 합계 | 68 | **72** | **+4** |

이 문제는 **아직 고쳐지지 않았다.** 다만 고치는 방향은 위 정정대로 "링크 단위로 읽기"가
아니다 — 그건 이미 그렇게 돼 있다. 링크가 없는 주문을 화면에서 어떻게 식별할지를
정해야 하고, 그러려면 로그인 상태의 실제 DOM 이 필요하다.
같은 크롤러로 받은 나머지 세 제출본에도 같은 누락이 있을 가능성이 높다.

270건으로 구조 파악과 스키마 검증에는 충분하다. 다만 "전량 수집"이라고 말할 수는 없다.

## 다시 수집하려면

로그인 세션 파일(`naver_state.json`)은 개인정보라 저장소에서 삭제했다. 다시 수집하려면 로그인부터 해야 한다.

```bash
python scripts/crawler/save_session.py      # 브라우저가 열리면 직접 로그인
python scripts/crawler/naver_order_crawler.py
python scripts/normalize.py
```

## A-COP에서 어디에 쓰나

계획서의 Core 1(Case Runtime & Coordination)이 쓴다.

Core 1의 Context Broker는 문의에 답하기 위해 필요한 정보를 모아 조립하는 부분이다. 그때 "이 고객의 주문 기록"이 재료로 들어간다.

## 개인정보

다음은 저장하지 않는다.

- 받는 사람 이름
- 전화번호
- 상세주소

배송지는 시·도와 시·군·구까지만 남긴다. `서울특별시 서초구`까지는 남기고 그 뒤는 버린다.

원본 데이터(`raw/`)와 정리 결과(`processed/`)는 git에 올리지 않는다. 본인의 실제 구매 기록이기 때문이다.
