01 · Why a Chrome extension

왜 파이썬 크롤러가 아니라
Chrome 확장 프로그램이었나

처음부터 확장 프로그램을 만들기로 정한 것은 아니었다. Python과 Playwright로 로그인 브라우저를 띄우는 방식부터 시험했지만, 쿠팡 로그인 단계에서 자동화 브라우저로 식별되어 Access Denied가 발생했다.

1

전용 브라우저 프로필로 로그인 시도

Playwright가 새 Chrome 프로필을 열어 사용자가 직접 로그인하도록 했다. 그러나 로그인 페이지에서 Akamai 봇 차단이 발생했다.

2

기존 Chrome 프로필 재사용 시도

평소 사용하던 프로필을 연결해도 브라우저가 “자동화 제어 중”인 사실은 남았고 같은 지점에서 차단됐다. QR 로그인과 로그인 페이지 직접 접근도 해결책이 아니었다.

3

탐지 우회 대신 실제 Chrome 안으로 이동

자동화 표시를 숨기는 우회는 하지 않았다. 사용자가 직접 로그인한 실제 Chrome에서 동작하고, 이미 열린 쿠팡 페이지만 읽는 확장 프로그램을 선택했다.

비전공자용 설명

Playwright 방식은 ‘로봇이 새 브라우저를 몰고 쿠팡에 입장하는 것’에 가깝다. 확장 프로그램은 ‘사용자가 이미 정상적으로 입장한 브라우저 안에 작은 도구를 설치하는 것’이다. 확장은 비밀번호를 받아 로그인하지 않고, 사용자가 보고 있는 주문 페이지의 정보만 로컬 파일로 저장한다.

확장 내부를 세 부분으로 나눈 이유

UI

popup.js · 조작판

수집 범위와 대기 시간을 받고 시작·중단·상태 확인·JSON 저장 버튼을 제공한다. 팝업은 닫힐 수 있으므로 긴 작업 자체를 맡기지 않는다.

눈

content.js · 현장 조사원

현재 탭의 목록 JSON, 상세 HTML, 배송 HTML을 읽는다. 이동을 직접 지휘하지 않고 “읽은 결과와 다음에 할 일”을 짧게 반환한다.

BG

background.js · 작업 관리자

탭 이동, 체크포인트 저장, 중단·재개를 담당한다. Chrome이 백그라운드 직원을 잠시 종료해도 저장된 작업 위치에서 다시 이어 간다.

따라서 background.js는 “팝업을 닫아도 계속 수집”하려면 필요하다. 다만 계속 살아 있는 무한 루프로 쓰지 않고, 한 단계씩 실행하고 작업 위치를 저장하는 Manifest V3 방식으로 바꿨다.

02 · Before the visible stall

“첫 주문 뒤 정지” 이전에도
이미 여러 번 실패하고 고쳤다

처음 요청은 배송정보를 못 읽는 문제 하나를 고치는 일이었다. 그러나 실제 HTML과 수집 결과를 대조하면서 목록 카드 인식, 클릭 위치, 페이지 복귀, 작업 재개가 각각 독립된 문제라는 사실이 드러났다.

초기 접근

화면의 주문 카드와 버튼을 선택해 클릭

목록 카드에서 상품을 읽고, “주문 상세보기”와 “배송 조회”를 눌러 정보를 보강하려 했다. 상세·배송 정보가 목록 화면에 모두 보이지 않았기 때문에 당시에는 자연스러운 선택이었다.

당시 판단: 화면에 없으면 실제 화면을 열어 읽는다
카드 경계

주문 6건이 상품 66행으로 불어남

주문 카드의 바깥 컨테이너까지 카드로 오인하면서 카드 하나가 다른 카드들을 삼켰다. “상세보기 표지가 정확히 하나인 가장 작은 블록”만 카드로 인정해 실제 HTML에서 7카드·8상품 행으로 맞췄다.

확인법: 화면 건수와 JSON 행 수를 직접 대조
클릭 대상

버튼처럼 보이지만 실제로는 span

“주문 상세보기”는 HTML의 <button>이나 링크가 아니었다. 잘못된 바깥 헤더를 눌러 이벤트가 실행되지 않았다. 가장 안쪽 글자 요소부터 부모 방향으로 클릭 재시도를 추가했다.

발견: 보이는 모양과 HTML 역할은 다를 수 있다
소스 유실

커밋되지 않은 content.js와 popup.js가 이전 상태로 돌아감

디버깅 변경을 되돌리는 과정에서 그날 작업분이 유실됐다. 다행히 남아 있던 테스트 976행이 동작 명세 역할을 해 구현을 재작성했고, 이후 큰 변경 전에는 별도 백업을 남겼다.

교훈: 되돌리기 전에 백업하고 테스트를 행위 명세로 유지
페이지 이동

페이지를 이동하면 주입된 수집 함수도 사라짐

탭 안에 임시로 넣은 함수가 상세 페이지 이동과 함께 파괴되어 결과가 undefined로 끝났다. 이동 제어를 background로 옮기고 content는 현재 문서 한 번만 읽도록 분리했다.

구조 변경: 장시간 루프를 페이지 안에 두지 않는다
시간차

주소는 바뀌었지만 화면은 아직 이전 페이지

URL이 먼저 바뀌고 React 화면은 뒤늦게 갱신됐다. 코드가 그 사이 이전 목록을 읽어 상세 클릭을 반복하거나 페이지 끝으로 오판했다. “뭔가 바뀜”이 아니라 “원한 문서가 준비됨”을 확인하도록 바꿨다.

핵심: 주소 변경과 데이터 준비 완료는 같은 사건이 아니다
호출 인자

undefined 하나 때문에 상태 확인이 전부 실패

Chrome에 전달한 함수 인자 배열에 직렬화할 수 없는 undefined가 들어 있었다. 시험 버튼은 항상 값을 넘겨 성공했지만 실제 수집의 무인자 호출만 실패했다. 가짜 Chrome 테스트도 이제 같은 값을 거부하도록 강화했다.

오류: Value is unserializable
문서 판정

Document의 빈 textContent와 script 속 문자열

한 번은 문서 전체 글자가 빈 값이어서 상세를 목록으로 봤고, 수정 뒤에는 JSON 스크립트 안의 단어까지 화면 글자로 오인했다. 화면 요소만 검사하고 script/style/template은 제외했다.

확인: ‘소스에 존재’와 ‘화면에 표시’는 다르다
재개 경합

수집 시작 후 “지금 상태”를 눌러야 움직임

서비스워커가 깨어날 때의 자동 재개와 새 작업 시작이 겹쳐 둘 다 끝나는 경쟁 상태가 있었다. 재개 요청을 기억했다가 기존 실행 종료 직후 다시 시작하도록 수정했다.

증상: START는 저장됐지만 실제 실행자가 없음

03 · The symptom that remained

그 많은 수정 뒤에도
“첫 주문 뒤 정지”가 남았다

앞선 문제들을 해결하고도 목록과 상세·배송 수집을 한 상태 기계에 섞어 둔 구조는 그대로였다. 그래서 상세 또는 배송 한 건의 실패가 전체 페이지 진행을 계속 붙잡았다.

대표 증상 — 상세, 목록 복귀, 배송, 목록 복귀 순서를 반복한 뒤 진행률이 0/5 또는 1/5에서 멈추고, 보조 탭이 사라지면 No tab with id가 누적됐다. 직접 요청은 HTTP 406 또는 Failed to fetch로 거부됐다.

04 · First evidence

네트워크에서 페이지 루프의 단서를 찾았다

“다음 목록으로 끝까지” 모드인데도 두 번째 요청부터 requestYear=2026이 붙었다. 연도 경계에서 서버가 준 nextYear와 nextPageIndex를 제대로 보존하지 않아 2026년과 2021년의 0·1페이지 사이를 왕복할 수 있었다.

05 · Root cause

멈춤을 만든 원인은 네 층에 걸쳐 있었다

1

잘못된 운반 방식

정상 브라우저 문서 탐색용 상세·배송 URL을 페이지 내부 fetch로 호출했다. 쿠팡은 이를 406으로 거부했고, 모든 주문에서 같은 실패를 먼저 기다렸다.

2

오래된 보조 탭을 새 문서로 오인

탭 갱신 직후 목표 URL·주문번호·배송박스를 확인하지 않고 이전 DOM을 읽을 수 있었다. 탭이 닫힌 뒤에도 폴링은 최대 30초 계속됐다.

3

목록 수집과 보강 작업의 결합

한 주문의 상세와 배송이 모두 끝나야 커서가 증가했다. 그래서 한 번의 네트워크 실패가 페이지 수집 전체를 멈춘 것처럼 보였다.

4

페이지 좌표의 의미 손실

정확한 orderPagination 대신 JSON 전체의 첫 hasNext를 찾고, 무연도 모드에도 현재 연도를 붙였다. 그 결과 페이지 수만 증가하는 순환이 만들어졌다.

사용자 화면에 나타난 버전별 단서

06 · Fetch and document navigation

fetch를 왜 썼고,
왜 결국 버렸나

fetch는 JavaScript가 현재 화면을 다른 페이지로 바꾸지 않고 서버에 자료를 요청하는 표준 기능이다. 처음에는 상세·배송 화면을 매번 열고 돌아오는 비용을 없앨 수 있어 가장 단순하고 빠른 해결책처럼 보였다.

fetch · 뒤에서 내용만 요청

const response = await fetch(detailUrl, {
  credentials: "include"
});
const html = await response.text();
  • 현재 탭 화면을 바꾸지 않는다.
  • 같은 로그인 쿠키를 보내 HTML만 받을 것으로 기대했다.
  • 성공했다면 상세 페이지에서 목록으로 복귀하는 과정이 필요 없었다.

문서 탐색 · 실제 페이지로 이동

chrome.tabs.update(tabId, {
  url: detailUrl
});
  • Chrome 주소창이 해당 상세·배송 URL로 이동한다.
  • 서버가 일반 페이지 방문으로 처리한 완성 HTML을 받는다.
  • 로드 완료 뒤 목표 주문·배송박스가 맞는지 검증한다.
비전공자용 비유

fetch는 방을 옮기지 않고 직원에게 “저 서류만 복사해 주세요”라고 부탁하는 방식이다. 문서 탐색은 사용자가 그 방으로 직접 들어가 서류를 보는 방식이다. 쿠팡은 주소창으로 들어간 방문에는 문서를 줬지만, 뒤에서 같은 문서만 요청하면 실제 관찰에서 HTTP 406으로 거절했다.

정확히 무엇이 실패했나

목록·상세·배송 URL은 브라우저의 최상위 화면에 표시되는 Document 요청이다. 이를 top-level document navigation, 즉 “현재 탭의 주소 자체를 바꿔 새 HTML 문서로 이동하는 것”이라고 한다. 같은 URL이라도 fetch로 부르면 화면 이동이 아닌 하위 리소스 요청이 된다. 요청 목적, 헤더와 브라우저 보안 문맥이 달라진다. 서버 내부의 정확한 차단 규칙까지 확인한 것은 아니지만, 실제 결과는 모든 주문에서 406 또는 Failed to fetch였고 주소창 탐색은 성공했다. 따라서 재시도 횟수를 늘리는 대신 운반 방식을 바꿨다.

“문서 탐색”으로 읽는 세 문서와 데이터 형태

문서주소 형태안에 있는 정보와 읽는 방식
주문목록/ssr/desktop/order/listHTML 안의 script#__NEXT_DATA__ JSON에서 주문번호, 상품, 금액, 배송 요약, 송장번호, shipmentBoxId, 다음 페이지·연도 좌표를 읽는다.
주문상세/ssr/desktop/order/{orderId}서버가 그린 HTML의 결제 표와 상품 영역에서 총상품금액, 할인, 배송비, 복합 결제수단, 배송지역·요청사항을 읽고 개인정보 필드는 내보내지 않는다.
배송조회/ssr/desktop/shiptrack?orderId=…&shipmentBoxId=…HTML의 배송 단계와 이력 영역에서 송장번호, 택배사, 상태, 상태별 시각을 읽는다. 송장번호가 없는 박스는 탐색 대상에서 제외한다.

문서를 잘못 읽지 않기 위한 확인 순서

1. 로드 완료 / 2. 목표 URL 일치 / 3. orderId 일치 / 4. shipmentBoxId 일치 / 5. 전용 영역 준비 / 6. 파싱

이 확인이 없으면 탭 주소만 먼저 바뀐 순간 이전 주문의 화면을 새 주문 결과로 저장할 수 있다. 이것이 stale-page race, 즉 “새 페이지가 오기 전에 옛 페이지를 너무 빨리 읽는 경쟁 문제”다.

reco.coupang.com/viewed-products는 최근 본 상품 추천용이고, destination-address/receiver는 수령지 보조 데이터다. 둘 다 주문 결제와 전체 배송 이력의 원본이 아니다. 실시간으로 받은 정적 JS 번들 역시 화면 동작 설명서일 뿐 사용자별 주문 데이터 목록이 아니므로 운영 데이터 원본으로 선택하지 않았다.

Scrapling과 XHR 캡처도 검토했다

Scrapling은 Python 기반 적응형 스크래핑 도구이고, capture_xhr은 페이지가 로드되는 동안 발생한 XHR·fetch 응답을 잡는 기능이다. 여기서 XHR은 “화면 전체를 바꾸지 않고 페이지가 뒤에서 서버와 주고받는 작은 요청”이다. 수령지 보조 API 같은 실제 XHR을 조사할 때는 유용하지만, 이번 상세·배송 URL은 XHR이 아니라 탭 전체가 이동하는 Document였다. 더구나 Scrapling은 별도 Python/Playwright 브라우저와 로그인 세션 공유가 필요해 앞서 확인한 자동화 로그인 차단 문제로 되돌아간다. 그래서 운영 수집기에 넣지 않고, 실제 Chrome의 정상 문서 탐색을 유지했다.

07 · Why the reference won

왜 extension_nextdata_ref 구조를 기준으로 삼았나

작업 폴더에는 같은 주문목록을 별도 방식으로 읽는 참고 구현 scripts/extension_nextdata_ref가 있었다. 이 구현은 상세·배송은 수집하지 않았지만, 목록만큼은 사용자의 추가 조작 없이 다음 페이지까지 안정적으로 진행했다. 따라서 “멈추지 않는 이유”를 현재 확장과 나란히 비교했다.

관찰 01

버튼을 찾지 않았다

ref는 화면의 “다음” 글자나 난수형 CSS 클래스를 찾지 않고, 서버가 문서에 넣어 둔 페이지 좌표로 다음 URL을 만들었다.

관찰 02

목록 원본을 직접 읽었다

화면에 그려진 카드들을 역으로 해석하지 않고 desktopOrder.orderList의 주문 데이터를 그대로 사용했다.

관찰 03

한 페이지가 원자적이었다

페이지를 로드하고 JSON을 읽어 결과를 저장한 다음, 다음 URL로 이동하는 단순한 흐름이라 상세 한 건의 실패가 목록 진행을 막을 일이 없었다.

선택한 것은 ref의 코드 전체가 아니라 핵심 원리였다. ref는 목록 전용이므로 그대로 복사하면 결제정보와 배송 이력을 얻을 수 없다. 우리는 “정확한 NextData 경로로 목록을 먼저 완주하고 서버 좌표로 이동한다”는 뼈대를 채택하고, 상세·배송은 별도의 문서 탐색 단계로 확장했다.

__NEXT_DATA__는 무엇인가

<script id="__NEXT_DATA__" type="application/json"> … </script>

쿠팡 주문목록은 Next.js로 만들어졌다. 서버는 첫 화면 HTML을 보낼 때 화면을 다시 구성할 수 있는 JSON 상태를 위 스크립트 태그에 함께 넣는다. 브라우저가 이 값을 이용해 화면을 이어서 활성화하는 과정을 hydration이라고 한다. 주문목록 페이지에서는 그 JSON 안의 props.pageProps.domains.desktopOrder.orderList에 주문 목록이, orderPagination에 다음 페이지·연도 좌표가 있었다.

__NEXT_DATA__는 별도의 비밀 API나 정적 JS 번들이 아니다. 사용자가 이미 받은 주문목록 문서 안에 포함된 구조화 데이터다. 따라서 목록에서는 화면 텍스트를 재조립하는 것보다 정확하고, 사용자별 데이터가 없는 정적 JS 파일을 뒤질 필요도 없다. 단, 상세·배송 문서까지 모두 같은 구조라는 보장은 없으므로 페이지별 스키마 검증과 전용 파서를 유지했다.

요소 선택·클릭 방식은 왜 버렸나

판단 기준요소 선택·클릭NextData + 문서 좌표
선택 안정성쿠팡의 난수형 CSS 클래스, 버튼 문구, DOM 계층 변경에 민감하다.서버 데이터의 주문 ID와 명시적인 페이지 좌표를 사용한다.
로드 시점hydration 전에는 카드가 없거나 일부만 있고, 숨은 중복 요소를 잡을 수 있다.JSON 존재와 문서 준비 상태를 함께 검증한 뒤 한 번만 읽는다.
상태 재현“어느 버튼까지 클릭했는가”가 탭의 순간 DOM에만 남는다.현재 좌표·주문 커서·목표 URL을 storage 체크포인트로 복원한다.
실패 범위상세에서 목록으로 못 돌아오면 전체 순회가 멈춘다.목록 완주와 상세·배송 보강을 분리해 한 항목의 실패를 격리한다.
검증 가능성클릭 성공과 올바른 주문 문서를 읽었다는 사실이 같지 않다.목표 URL, orderId, shipmentBoxId가 모두 일치해야 파싱한다.

결론: 클릭 자동화가 항상 나쁜 것은 아니다. 데이터가 클릭 뒤에만 나타날 때는 필요하다. 하지만 이 목록은 동일한 정보와 다음 좌표가 이미 문서 JSON에 있었으므로, 클릭은 필요한 상호작용이 아니라 불안정성만 추가하는 우회 경로였다.

08 · Architecture change

페이지를 클릭하는 크롤러에서
문서 좌표를 따라가는 수집기로

이전 구조

  • DOM 카드·버튼을 찾아 클릭
  • 상세마다 목록으로 복귀
  • 직접 fetch 후 보조 탭 폴백
  • 영구 while 루프와 keepalive
  • 실패한 한 건이 전체 진행 차단

최종 구조

  • 정확한 desktopOrder JSON 파싱
  • 서버의 다음 페이지 좌표 그대로 사용
  • 상세·배송은 정상 문서 탐색
  • 저장된 체크포인트에서 한 단계씩 재개
  • 항목별 제한 재시도 후 다음 건 진행
STEP 1

목록 완주

orderList와 orderPagination만 읽어 모든 주문과 다음 좌표를 저장한다.

STEP 2

상세 탐색

/order/{orderId}로 정상 이동하고 목표 주문번호와 문서 준비 상태를 검증한다.

STEP 3

배송 탐색

송장번호가 있는 박스만 shiptrack으로 이동해 단계와 배송 이력을 읽는다.

STEP 4

체크포인트

매 단계 상태를 로컬 저장한다. 서비스워커가 쉬어도 이벤트·알람이 다음 한 걸음을 재개한다.

09 · Real interface

실제 쿠팡 주문목록 위에서 검증했다

아래 화면은 재현용 목업이 아니라 당시 설치된 확장과 쿠팡 주문목록에서 직접 촬영한 원본 캡처다. 캡처 당시 표시는 5.4.4이며, 이후 송장번호 필터와 정규화 규칙을 확정해 최종 버전은 5.4.6이 됐다.

10 · Verification

“돌아간다”가 아니라 산출물로 확인했다

{

    "order_rows": 9,

회귀 테스트 45개 통과과거에 발견한 문제가 코드 변경 뒤 다시 생기지 않았는지 한 명령으로 반복 검사했다.

“자동 회귀 테스트”란?

회귀는 이미 고친 버그가 다른 수정 때문에 되살아나는 현상이다. 테스트는 입력 HTML과 작업 상태를 준비하고, 기대한 주문 수·다음 URL·중단 결과가 나오는지 프로그램이 자동 비교한다. 사람이 45번 버튼을 눌렀다는 뜻이 아니라 node scripts/extension/tests/index.js 한 번으로 45개 시나리오를 확인했다는 뜻이다.

테스트 묶음개수무엇을 다시 망가뜨리지 않는지
content11NextData 주문 변환, 상세·배송 파싱, 개인정보 제거, 송장번호 없는 배송 제외
real-page15실제 쿠팡 HTML을 개인정보 치환한 fixture로 저장해 상품·결제·배송 단계와 페이지 좌표 검증
background9탭 이동, 체크포인트 재개, 중단, 타임아웃, 사라진 탭 처리
wiring10manifest 권한, 팝업 버튼, 파일 연결, 불필요한 예전 클릭 코드가 다시 들어오지 않았는지 확인

자동 테스트는 저장된 입력에 대해 코드가 약속을 지키는지 확인한다. 쿠팡 실사이트가 바뀌지 않았다는 보장은 아니므로, 마지막에는 실제 로그인 Chrome에서 전체 페이지 완주와 다운로드 JSON 건수를 별도로 확인했다. 테스트 45개와 실제 스크린샷·Raw 9/4 검증은 서로 보완 관계다.

11 · Final policy

배송 건수 4개가 맞는 이유

최종 포함 기준: 송장번호가 있으면 포함, 없으면 제외

구매 상품 행은 9개지만 배송 JSON은 4건이다. 나머지 1건은 결제 완료·배송 전 상태여서 아직 송장번호가 없었다. 이를 누락으로 취급하거나 가짜 배송 행으로 만들지 않고, 배송조회 대상에서 명시적으로 제외했다. 송장번호가 발급되면 다음 수집에서 자동으로 포함된다.

왜 처음에는 5건이라고 생각했나

화면에 보인 배송 관련 주문 묶음은 5개였기 때문에 처음에는 배송조회 결과도 5개여야 한다고 판단했다. 그러나 주문 상품 행, 고유 주문번호, 배송박스, 실제 송장 발급 건은 서로 다른 단위다. 결과를 다시 대조하니 상품은 9행, 고유 주문은 8건, 배송 관련 박스는 5개였고 그중 송장번호가 발급된 박스만 4개였다. 따라서 4건은 크롤링 누락이 아니라 최종 포함 규칙에 맞는 결과다.

12 · What we learned

성공을 만든 것은 재시도 횟수가 아니라 경계의 명확화였다

A

정적 JS 번들은 데이터 원본이 아니다

번들에는 요청·렌더링 코드만 있다. 사용자별 주문과 배송 이력은 목록 NextData와 상세·shiptrack 문서에서 읽어야 했다.

B

문서 URL은 문서 탐색으로 읽는다

브라우저 상단 탐색에서는 성공하는 URL이 하위 fetch에서는 거부될 수 있다. 실제 브라우저의 정상 문서 이동을 데이터 운반 계층으로 삼았다.

C

서비스워커 종료는 오류가 아니다

영구 루프로 억지로 살리지 않고, 작업 ID·대기 URL·커서를 먼저 저장한 뒤 이벤트마다 멱등한 한 단계를 수행하도록 만들었다.

D

진행률과 정확성은 같은 상태에서 나와야 한다

표시용 숫자와 실제 큐를 분리하지 않았다. 주문·배송 완료 여부와 현재 탐색 문서를 체크포인트에서 바로 진단할 수 있게 했다.

13 · Plain-language audit

비전공자를 위한 용어 해설과
채팅 요구사항 최종 점검

본문에서 사용한 핵심 용어를 일상적인 표현으로 다시 정리했다. 이 표만 읽어도 어떤 문제가 있었고 왜 최종 구조가 달라졌는지 따라갈 수 있다.

용어쉬운 뜻이번 작업에서의 의미
DOM브라우저가 화면의 제목·버튼·표를 나무 구조로 정리한 설계도보이는 요소를 찾아 클릭하는 초기 방식이 이 구조와 CSS 변경에 민감했다.
__NEXT_DATA__화면과 함께 배달된 정리된 주문 장부화면 카드에서 글자를 다시 긁지 않고 주문목록 원본과 다음 좌표를 읽었다.
hydration서버가 보낸 정적인 화면에 브라우저가 버튼 동작을 붙이는 준비 과정주소는 바뀌었는데 화면이 아직 옛 상태인 시간차가 생기는 이유였다.
HTTP 406서버가 “이 방식의 요청에는 원하는 문서를 줄 수 없다”고 거절한 응답상세·배송 URL을 fetch로 요청한 접근이 실제 환경에서 성립하지 않는 증거였다.
서비스워커팝업이 닫혀도 뒤에서 작업 순서를 관리하는 임시 직원Chrome이 이 직원을 쉬게 할 수 있어 작업 위치를 매번 저장해야 했다.
체크포인트“현재 몇 페이지·몇 번째 주문까지 했음”이라고 남기는 작업 메모워커가 종료되거나 탭 로딩이 늦어도 같은 위치에서 재개하게 했다.
