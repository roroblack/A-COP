# 쿠팡 주문내역 수집 확장 — 작업 리포트

작성일 2026-08-21 · 확장 5.4.1 · 빌드 2026-08-21b

## 결과

이미 로그인된 Chrome의 쿠팡 주문내역을 로컬 JSON으로 저장한다. 로그인과 인증은 자동화하지
않고, 브라우저 식별 정보를 바꾸거나 수집 결과를 외부 서버로 보내지 않는다.

| 범위 | 데이터 원천 | 얻는 것 |
|---|---|---|
| 목록만 | 주문목록 `__NEXT_DATA__` | 주문번호, 상품, 금액, 주문·배송 요약, 송장 요약 |
| 목록 + 상세 | 위 목록 + 주문상세 정상 문서 | 상품 금액, 할인, 배송비, 복합 결제, 배송 요청 |
| 목록 + 상세 + 배송조회 | 위 데이터 + shiptrack 정상 문서 | 배송 단계와 배송 이력 |

## 현재 구조

| 파일 | 책임 |
|---|---|
| `content.js` | 정확한 NextData 경로 파싱, 상세·배송 문서 검증과 파싱, 다음 상태 결정 |
| `background.js` | 저장 체크포인트, 같은 탭 문서 이동, 로드·알람 재개, 중단 세대 관리 |
| `popup.js` | 설정, 상태·구조 진단, JSON 내려받기 |

수집은 두 단계다.

1. `__NEXT_DATA__.props.pageProps.domains.desktopOrder`의 `orderList`와
   `orderPagination`을 따라 목록을 끝까지 먼저 저장한다.
2. 목록이 끝나면 같은 로그인 탭을 `주문상세 → 배송조회 → 다음 주문상세` 주소로 이동한다.
   주문마다 목록으로 돌아가지 않는다.

상세와 배송은 `fetch`나 비활성 보조 탭으로 요청하지 않는다. 쿠팡이 정상 문서 탐색이 아닌
요청을 406으로 거부하고, 재사용 보조 탭이 이전 DOM을 새 주문으로 읽는 경합을 만들었기 때문이다.

서비스 워커는 영구 keepalive 루프를 유지하지 않는다. 상태를 `chrome.storage.local`에 먼저
저장하고 한 묶음의 전이 뒤 반환한다. 탭 로드 완료 이벤트와 알람이 저장된 작업을 다시 깨운다.

## 정체 원인과 제거한 것

이전 구현은 목록 수집과 상세·배송 보강을 섞어서 다음 흐름을 반복했다.

`목록 → 상세 → 목록 복귀 → 배송 → 목록 복귀 → 다음 주문`

그 결과 한 번의 상세·배송 실패가 페이지네이션 전체를 막았다. 추가로 다음 문제가 겹쳤다.

- 정상 문서 전용 상세·배송 주소를 하위 `fetch`로 호출해 406/Failed to fetch가 반복됐다.
- 보조 탭의 목표 URL과 주문번호를 검증하지 않아 이전 문서를 성공으로 읽을 수 있었다.
- 닫힌 보조 탭을 30초 동안 계속 호출하며 `No tab with id`를 누적했다.
- DOM 카드 해시와 버튼 클릭 결과에 페이지 진행을 맡겨 hydration 시점에 따라 달라졌다.
- “다음만” 모드에도 `requestYear`를 강제로 붙여 수집 범위를 바꿨다.
- 팝업과 서비스 워커의 두 구동자 호환 분기가 같은 걸음을 중복 실행할 여지가 있었다.

5.4.1에서는 다음 레거시를 삭제했다.

- DOM 주문 카드 수집기와 카드 해시
- 상세·배송·다음·연도 버튼 클릭기와 4단계 클릭 재시도
- 상세→목록 복귀와 목록 위치 복원 상태
- 직접 fetch, helper 탭, popup driver 호환 분기
- `performAction`, `pageFacts`, `collectOrders` 등 사용하지 않는 공개 API
- 팝업의 “다음 누르기 시험”, “상세 열기 시험”
- `activeTab`, `tabs`, `www.coupang.com` 확장 권한
- 레거시 통합 테스트와 DOM 목록 fixture

현재 런타임이 내는 행동은 `none`, `navigate`, `done`뿐이다.

## 정확성 장치

- 목록은 DOM이 아니라 JSON 주문 키와 서버 페이지 좌표로 중복 판정한다.
- “다음 목록으로 끝까지” 모드는 URL에 `requestYear`를 붙이지 않는다.
- 상세는 정확한 `/ssr/desktop/order/{orderId}`와 페이지 주문번호를 함께 검증한다.
- 배송은 정확한 `orderId`와 `shipmentBoxId`가 있는 shiptrack URL만 파싱한다.
- 같은 배송박스의 모든 `vendorItemIds`를 조회 URL에 넣는다.
- 16자리 이상 식별자는 JSON 파싱 전에 문자열로 보존한다.
- 상세·배송 실패는 항목별 최대 세 번 뒤 경고와 함께 건너뛴다.
- 배송 JSON은 송장번호가 있는 건만 포함하고 `(orderId, shipmentBoxId)`로 분리 배송을 구분한다.
- 수취인, 전화번호, 상세주소, 우편번호를 결과에서 제거한다.

## 검증

`node scripts/extension/tests/index.js`

현재 엔진만 대상으로 한 테스트 45개가 통과한다.

| 검증 범위 | 포함 내용 |
|---|---|
| 실측 상세 fixture | 상품 1개, 할인, 배송비, 복합 결제, 지역·요청 |
| 실측 배송 fixture | 단계 진행, 송장, 상대 시각, 배송 이력 |
| NextData fixture | 주문번호, 페이지 좌표, 무연도/연도별 모드, 큰 정수 |
| 연속 흐름 | 목록 완료 후 상세→배송→완료, 이전 DOM 거부 |
| 워커 | 재주입, 재기동, 중단, 저장 경쟁, 탭 로드·알람 재개 |
| 장애 | 호출 timeout, discarded 탭만 reload, 닫힌 탭 안전 중단 |

브라우저 실계정에서 확인할 항목은 전체 페이지 완주, 주문별 상세·배송 채움, 팝업 재개와 최종
JSON의 개인정보 부재다. 팝업의 `지금 상태`와 `구조 진단`은 NextData·페이지 좌표·목표 문서
상태를 보여준다.

설치와 사용법은 `scripts/extension/README.md`를 따른다. 과거 `docs/`의 클릭 관련 문서는
폐기된 방식의 원인 분석 기록이며 현재 실행 구조가 아니다.

## 전처리

최신 확장 출력은 `python scripts/normalize.py`로 정규화한다. 스크립트는 같은
타임스탬프의 주문 JSON과 배송 JSON을 자동으로 짝지어 다음 파일을 만든다.

- `processed/orders.jsonl`: 상품 행 단위 Commerce Ops 정규화 주문
- `processed/tracking.jsonl`: `(order_id, shipment_box_id)` 단위 배송조회 결과
- `preprocess_stats.json`: 입력 SHA-256과 행 수 검증 통계

원본과 처리 결과에는 개인의 구매 이력이 포함되므로 외부 배포 압축에서는 제외한다.
