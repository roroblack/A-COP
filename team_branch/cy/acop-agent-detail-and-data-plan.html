01
기존 팀

주문·반품·환불 팀

주문, 결제, 반품 기간, 판매자 정책을 확인해 처리안을 제시하는 팀. 이 팀의 기능은 리뷰 데이터가 아니라 "주문 스키마"가 필요하므로, 실제 기업 데이터가 없는 대신 자체 설계한 Mock 주문 DB로 구현합니다.

ORDORDER OPS
01
반품 기간 D-day 자동 판정

수령일 기준으로 반품 가능 기간이 며칠 남았는지 자동으로 계산합니다.

소스
MOCK자체 설계 주문 DB
필요 필드주문일, 수령일(delivered_at), 상품 카테고리별 반품기간(정책값)
수집 방법실제 주문 데이터가 없으므로 order_id, delivered_at 등을 가진 가상 주문 테이블을 직접 설계·생성. 반품기간은 실제 전자상거래법 기준(수령 후 7일)을 규칙으로 반영
02
다중상품 주문 부분반품 자동 분리

한 주문에 여러 상품·수량이 있을 때, 반품 대상 상품만 따로 분리해 처리합니다.

소스
MOCK자체 설계 주문 DB
필요 필드order_id, order_item_id, product_id, quantity, unit_price
수집 방법주문 1건에 order_item이 여러 개 붙는 1:N 스키마로 Mock 데이터 생성. 실제 판매 데이터 없이 상품 카테고리 분포는 AI Hub 데이터의 카테고리 비율을 참고해 현실감 있게 구성
03
환불 금액 자동 계산 (결제수단 분기 포함)

배송비 포함·제외, 부분반품 시 상품별 비례 금액을 계산하고, 카드·포인트·쿠폰 혼합결제일 때 결제수단별로 환불 방식을 나눠 제안합니다. 별도 "결제·정산 에이전트"를 새로 만들지 않고 이 기능 안에서 분기 처리합니다.

소스
MOCKRULE
필요 필드결제금액, 배송비, order_item 단가·수량, 결제수단 분할내역(카드/포인트/쿠폰)
수집 방법Mock 주문 DB에 결제수단 분할 필드를 추가해 사용. 계산 자체는 학습이 필요 없는 규칙(비례식) 로직이라 별도 데이터 수집 불필요
04
반품사유 ↔ 판매자정책 자동 매칭

반품 사유(단순변심/하자 등)에 따라 반품비 부담 주체를 정책과 대조해 자동 판정합니다.

소스
MOCKAPI
필요 필드반품사유 코드, 판매자 정책 테이블(사유별 부담주체)
수집 방법판매자 정책 규칙은 자체 정의(표준 이커머스 약관 형식 참고)하고, 법적 최소 기준은 소비자24·전자상거래법 공개 자료로 검증
05
반품회수 vs 환불선처리 판단

상품 가액이 낮으면 회수 없이 환불부터 진행하는 게 더 합리적인지 비교해 제안합니다.

소스
MOCKRULE
필요 필드상품 단가, 평균 왕복 택배비(고정값)
수집 방법택배비는 공개된 택배사 요금표 기준 평균값을 상수로 사용. 상품 단가는 Mock 주문 DB에서 조회
06
VOC 접수시 환불가능여부 안내

처리가 끝나기 전, 고객에게 먼저 환불 가능 범위를 안내해 대기 중 정보 공백을 줄입니다.

소스
RULE
수집 방법별도 수집 없음. 위 01·03·04번 기능의 계산 결과를 접수 시점에 미리 보여주는 조합 로직
07
교환·재배송 처리

반품(돈을 돌려주는 흐름)과 달리 새 배송을 다시 만드는 흐름이라 상태 전이가 다릅니다. 판단은 ORD 팀이 그대로 하고, 실행 단계에서 새 송장 발급이 필요하면 LOG 팀과 협업(기존 복합 Case 패턴 재사용)합니다. 별도 팀을 만들지 않고 ORD의 새 기능 항목으로 둡니다.

소스
MOCK
필요 필드교환 가능 재고 수량(product_id 단위)
수집 방법데이터 갭: 실제 재고 데이터가 없어 소규모 Mock 재고 테이블을 별도로 설계해야 함. 재고 스키마가 확정되기 전까지는 후순위 기능
02
기존 팀

배송·물류 팀

송장과 배송 상태를 조회하는 팀. 실시간 배송 API는 실제 기업 권한이 없어 못 쓰므로, 배송 이벤트 로그를 Mock으로 시뮬레이션하고 파손·분실 판단에는 리뷰 텍스트를 함께 활용합니다.

LOGLOGISTICS OPS
01
SLA 초과 사전 예측

배송 이력 패턴을 보고 지연 가능성이 높은 건을 미리 찾아내 선제 안내합니다.

소스
MOCK
필요 필드발송일, 단계별 스캔 시각(집화/간선/배송출발/완료)
수집 방법실제 택배사 API 연동이 불가능하므로 배송 이벤트 로그를 자체 생성. 정상/지연 케이스 비율은 참고 가능한 공개 통계(국토부·택배업계 평균 배송일수)를 반영해 현실감 있게 구성
02
반복 파손 배송사 탐지

특정 택배사·구간에서 파손 신고가 몰리는지 집계해 알려줍니다.

소스
REALMOCK
필요 필드파손 언급 리뷰(속성=포장/배송, 감성=부정), 배송사 필드
수집 방법파손 여부는 AI Hub 속성기반 데이터의 "포장/배송" 속성 라벨을 그대로 활용. 실제 데이터엔 배송사 정보가 없어, 주문 Mock DB에 배송사 필드를 임의 배정해 연결
03
분실 의심 자동 감지

마지막 배송 스캔 이후 오래 업데이트가 없으면 자동으로 확인 요청을 생성합니다.

소스
MOCKRULE
필요 필드마지막 스캔 시각
수집 방법01번의 Mock 배송 이벤트 로그를 재사용. "마지막 업데이트 후 N일 경과"는 별도 학습 없는 임계값 규칙
04
배송완료 후 미수령 신고 처리

시스템상 배송완료인데 고객이 못 받았다고 하는 경우를 별도 흐름으로 처리합니다.

소스
MOCK
필요 필드배송상태(완료), VOC 접수 텍스트
수집 방법Mock 배송 로그의 "완료" 상태와, 골드셋 Case(직접 라벨링한 한국어 Case 150건) 중 미수령 사례를 매칭해 시연용 시나리오로 구성
03
기존 팀

판매자·상품 품질 및 VOC 팀

가장 핵심 데이터셋(AI Hub 속성기반 감정분석 데이터)의 혜택을 그대로 받는 팀입니다. 판매자 단위 정보만 데이터셋에 없어 일부 Mock 매핑이 필요합니다.

SELSELLER QUALITY
01
속성별 리뷰 요약 카드

"배송 만족, 사이즈 불만족"처럼 상품을 속성 단위로 쪼개 보여줍니다.

소스
REAL
필요 필드속성명, 속성별 감성라벨(긍정/부정/중립)
수집 방법AI Hub 속성기반 감정분석 데이터(dataSetSn=71603)를 그대로 다운로드해 사용. 별도 라벨링 불필요 - 이미 속성 단위로 라벨링돼 있는 게 이 데이터셋을 고른 이유
02
사이즈·핏 자동 배지

사이즈 관련 부정 리뷰가 몰리면 "실측보다 크게/작게 나옴" 배지를 자동으로 붙입니다.

소스
REAL
필요 필드패션 카테고리 중 "사이즈" 속성 라벨 + 원문 텍스트(크다/작다 방향성 추출용)
수집 방법AI Hub 데이터의 패션 카테고리 서브셋 사용. "크다/작다" 방향은 속성 라벨에 없어 원문에서 키워드(크다/작다/넉넉/타이트) 규칙 기반 추출을 추가로 적용
03
반복 불만 클러스터링

비슷한 내용의 리뷰를 자동으로 묶어서 같은 불만이 몇 건 반복됐는지 계산합니다.

소스
REAL
필요 필드리뷰 원문, 부정 라벨
수집 방법AI Hub + Naver Shopping 리뷰(bab2min/corpus) 텍스트를 한국어 임베딩 모델(예: KoSimCSE)로 벡터화 후 K-Means/HDBSCAN으로 클러스터링. 두 데이터셋 다 이미 공개돼 있어 추가 수집 불필요
04
안전·리콜 키워드 즉시 에스컬레이션

리뷰에서 위험 관련 표현이 감지되면 바로 최우선 검토 대상으로 올립니다.

소스
REALAPI
필요 필드위험 키워드 사전, KC 인증·리콜 정보
수집 방법리뷰 텍스트에서 자체 구축한 위험 키워드 사전(화재/유독/감전 등)으로 1차 필터링하고, Safety Korea(제품안전정보센터) 공개 API로 실제 리콜 여부를 교차 확인
05
판매자 신뢰도 스코어링

불만 건수, 파손율 등을 종합해 판매자별 신뢰도 점수를 산출합니다.

소스
MOCK
필요 필드판매자 ID, 상품별 불만·파손 집계값
수집 방법데이터 갭: AI Hub 데이터엔 판매자 단위 구분이 없음. 상품 카테고리를 여러 개의 가상 판매자에게 임의 배정하는 Mock 매핑을 거쳐야 판매자 단위 집계가 가능
06
기획·마케팅 인사이트 리포트

최근 리뷰에서 가장 많이 언급된 개선 요청 키워드를 정리해 리포트로 제공합니다.

소스
REAL
필요 필드리뷰 원문, 작성일(트렌드 파악용)
수집 방법AI Hub + Naver 리뷰 텍스트에 TF-IDF/토픽모델링 적용. 다만 두 데이터셋 모두 스냅샷 데이터라 실시간 "이번 달" 트렌드는 아니고, 데모에서는 데이터 내 기간대별 비교로 대체
07
리뷰 기반 연관 상품 추천

같은 리뷰에서 함께 언급된 상품을 기준으로 연관 상품을 제시합니다.

소스
REALMOCK
필요 필드리뷰 원문 내 상품명 동시언급
수집 방법데이터 갭: 데이터셋에 개별 상품명이 명확히 분리돼 있지 않아, 카테고리 레벨 동시언급으로 범위를 낮추거나 소규모 Mock 상품 카탈로그를 만들어 텍스트에 매핑해야 함
04
신규 제안

응답 생성 에이전트

이 팀은 원본 기획서에 없던 팀입니다. 다른 팀의 출력(구조화 데이터)을 입력으로 받아 LLM이 문장을 생성하는 구조라, 리뷰 데이터 수집과는 성격이 다릅니다.

GENRESPONSE GENERATION · 신규
01
근거 기반 응답 초안 생성

주문상태·정책조항·환불금액 등을 받아 고객용 문장으로 자동 변환합니다.

소스
LLM
수집 방법별도 데이터 수집 없음. 각 팀의 Action Proposal(구조화 출력)을 프롬프트 입력으로 넣어 LLM이 바로 문장을 생성. 다만 톤 품질 검증용으로 골드셋 Case 150건 내 예시 응답 스타일을 참고 프롬프트에 활용
02
개인화 톤·채널 반영

선호 채널, 감성·긴급도, 이전 미해결 이력에 맞게 안내 순서와 톤을 조정합니다.

소스
MOCK
필요 필드고객 프로필(선호채널), 이전 Case 이력
수집 방법실제 고객 데이터가 없으므로 Mock 고객 프로필 스키마(customer_id, preferred_channel, case_history)를 자체 설계
03
FAQ 자동 매칭

반복되는 단순 질문은 표준 답변을 재사용해서 처리 속도와 비용을 줄입니다.

소스
REALMOCK
수집 방법리뷰·VOC 텍스트에서 반복되는 질문 패턴을 추출해 초기 FAQ셋을 구성하고, 골드셋 Case 150건 작성 시 자주 나오는 유형을 함께 반영
04
요약형·상세형 응답 자동 선택

단순 문의는 짧게, 복합 케이스는 상세하게 응답 분량을 자동으로 조정합니다.

소스
RULE
수집 방법별도 수집 없음. 배정된 팀 개수·risk_level 등 Case 메타데이터 기준의 규칙 로직

06

데이터 수집 전략 요약

왜 아마존이 아닌가: 아마존 리뷰 데이터/API는 접근성은 좋지만 영어·해외 소비 패턴 데이터라, 한국 고객 VOC 처리 능력을 증명하지 못합니다. 프로젝트의 핵심 가치(한국어 응대 품질)와 맞지 않아 제외했습니다.
왜 네이버·쿠팡 직접 크롤링이 아닌가: 이용약관 위반이자 저작권 문제로 법적 리스크가 있습니다. 대신 이미 적법한 절차로 공개된 AI Hub 속성기반 감정분석 데이터와 bab2min/corpus(Naver Shopping 리뷰)를 사용해 같은 목적을 우회 달성합니다.
남은 데이터 갭: 판매자 단위 구분, 실시간 주문·배송·재고 정보는 공개 데이터에 없어 Mock으로 채워야 합니다. 이 갭이 있다는 걸 발표에서 숨기지 말고, "실제 기업 연동 시에는 해당 기업이 권한을 부여한 데이터로 교체한다"는 원칙으로 명시하는 게 좋습니다.
데이터 최신성 문제: AI Hub 속성기반 감정분석 데이터는 2022년 구축(2023년 갱신) 데이터입니다. "지금 이 순간의 트렌드"를 보여주는 용도로 쓰기엔 오래됐다는 게 실제 한계입니다. 다만 이 문제는 기능별로 영향이 다릅니다.
  • 영향 적음 — 속성별 리뷰요약, 사이즈배지, 반복불만클러스터링, 안전키워드탐지, 톤적합성검사: "사이즈가 작다", "포장이 부실하다" 같은 불만 패턴 자체는 연도가 바뀌어도 거의 그대로입니다. 모델이 배우는 건 "패턴을 알아보는 능력"이라, 학습 데이터가 2022년이어도 2026년 리뷰를 넣으면 여전히 잘 분류합니다.
  • 영향 큼 — 기획·마케팅 인사이트 리포트("이번 달 트렌드"): 이건 실제로 오래된 데이터의 한계를 그대로 받습니다. 데모에서는 "실시간 트렌드"라고 과장하지 말고, "이 기간 데이터 기준 분석 예시"로 명확히 라벨링하는 게 안전합니다.
최신성 보완 방법 (법적으로 가능한 것만):
  • 네이버 데이터랩(DataLab) 오픈 API — 개별 리뷰 텍스트가 아니라 검색어·쇼핑 카테고리 트렌드를 실시간 집계로 제공하는 공식 API입니다. 리뷰 원문은 2022년 데이터를 쓰더라도, "요즘 어떤 카테고리가 뜨는지"는 이 API로 현재 시점 데이터를 붙일 수 있습니다.
  • 통계청 온라인쇼핑동향조사(KOSIS) — 분기별로 갱신되는 공식 이커머스 카테고리별 거래액 통계. 마케팅 인사이트 리포트에 "실제 시장은 이렇게 움직이는데, 우리 VOC 신호와 비교하면" 식으로 현재성을 보강할 수 있습니다.
  • Safety Korea 리콜 API는 이미 실시간 데이터라 안전·리콜 기능은 최신성 문제가 없습니다.
구조적으로 인정할 부분: "실시간으로 계속 갱신되는 국내 대형 쇼핑몰 리뷰 데이터"는 사실 실제 기업들도 자체 데이터로만 갖고 있는 자원입니다. 학교 프로젝트 수준에서 이걸 완전히 해결하는 건 원래 불가능한 문제이고, 실제 산업에서도 이래서 리뷰 분석 스타트업들이 각 쇼핑몰과 개별 제휴를 맺습니다. 발표에서는 "지금 데이터로 파이프라인과 판단 로직이 정확히 작동함을 증명했고, 실제 서비스화 시에는 기업 제휴를 통해 데이터를 실시간으로 교체한다"는 흐름으로 설명하는 게 설득력 있습니다.
