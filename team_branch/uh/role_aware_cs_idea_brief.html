Idea Brief · Personal Draft · 2026-08

로그인한 사람이 누구냐에 따라
구매자의 CS 창구가 되고, 판매자의 파트너가 되는 챗봇

하나의 엔진(피드백 분석 + Case 처리) 위에서, 인증된 역할에 따라 시스템이 다른 얼굴을 보여준다. 구매자에게는 문의부터 분쟁까지 층을 타고 오르는 응대 퍼널을, 판매자에게는 입점 온보딩부터 소명 지원까지의 운영 파트너를. "고객 대상이 모호하다"는 지적을 역할 인식 설계로 답한다.

MODE A · BUYER LOGIN

구매자 모드 — 응대 퍼널

조회·안내·처리형 문의를 즉시 해결하고, 실패한 건만 분쟁 사다리로 격상. 상담에서 구매 완결까지.

MODE B · SELLER LOGIN

판매자 모드 — 운영 파트너

대화형 입점 온보딩, 내 스토어 VOC 요약, 분쟁 소명 지원. 응대에서 배운 것을 입점 단계로 환류.

SAME ENGINE · SAME DATA · DIFFERENT FACE — 분기점은 Supervisor 진입점의 role 판별 하나
01 · Core Structure

구매자 쪽 뼈대 — 문의 퍼널 위에 분쟁 사다리

CS의 대부분은 분쟁이 아니라 평범한 문의다. 대량의 문의를 아래층에서 싸고 빠르게 끝내고, 해결에 실패했거나 불만으로 번진 소수만 위층으로 올린다. 분쟁은 별개 기능이 아니라 "문의 처리가 실패했을 때의 다음 상태"다.

L0

문의 층 — 넓고 얇게

조회형(배송·주문·적립금: tool call로 DB 조회) / 안내형(정책·FAQ: config+RAG) / 처리형(주소 변경·취소·교환 접수: 자동 승인 한도 내 경량 트랜잭션). 챗봇 상담 → 상품 탐색 → 구매 완결까지 포함.

volume ████████
LLM cost ▁ 소형모델+캐시
L1

판매자 레벨 응대

테넌트 config로 자동 생성되는 스토어별 1차 응대. 스토어 정책 안에서 처리 + 분쟁 성립 여부 판정. 의도적으로 얇게 유지.

volume ████
LLM cost ▂
L2

플랫폼 중재 — 좁고 깊게

SLA 초과·소명 부적절·불복 시 자동 격상. 증거 수집 → 법정 기준(전자상거래법·분쟁해결기준) 조항 인용 판정 → 유사 결정례 제시 → 운영자 승인 후 환불/페널티 트랜잭션.

volume ██
LLM cost ▅ 고성능 모델
L3

외부 절차 연계

중재 실패·고액 분쟁이면 케이스 파일을 소비자원 피해구제 신청 서식으로 자동 패키징 + 절차 안내. 시스템의 한계를 시스템이 알고 출구를 책임진다.

volume ▏
문서 생성
비용 전략이 구조와 일치: 아래층은 소형 분류기·tool call·FAQ 캐시로 LLM 호출을 최소화하고, 위로 갈수록 비싼 모델을 쓴다. "좋은 성능 · 적은 비용"이 그림 한 장으로 설명됨. 핵심 지표는 자동 해결률(전체 문의 중 L0~L1 종결 비율) — 실무 CS가 실제로 쓰는 지표.
02 · Role-Aware Routing

역할 인식 — 로그인 주체가 라우팅의 첫 입력

아키텍처상 추가되는 것은 Supervisor 진입점의 분기 하나. 그 아래 인프라(정책 RAG, 분석 결과, 테넌트 config, mock DB)는 전부 공유된다. 기능이 늘어나는 게 아니라 같은 자산에 접근하는 관점이 늘어나는 것.

ROLE = BUYER

구매자로 로그인하면

위의 퍼널 전체가 이 사람의 창구가 된다.

  • 문의·처리·구매 상담 (L0)
  • 분쟁 접수와 진행 상태 확인 (L1~L3)
  • 다국어 유입 시 해당 언어로 응대 지속
ROLE = SELLER

판매자로 로그인하면

같은 챗봇이 운영 파트너로 바뀐다. MVP는 딱 세 기능.

  • 대화형 입점 온보딩 (아래 04 참고)
  • 내 스토어 VOC 요약 조회 — 분석 팀 산출물을 판매자 관점으로 필터링할 뿐이라 추가 비용 ≈ 0
  • 진행 중 분쟁의 소명 작성 지원
03 · Buyer Journey

과정 ① 구매자 모드 — 한 케이스가 퍼널을 오르는 과정

1
문의 접수·분류"2주째 미배송이에요" → 소형 모델이 감성(분노)·이슈(미배송)·의도 분류, role=buyer 확인, 케이스 생성. 판매 주체(직매입/위탁/오픈마켓)를 판별해 책임 경로 결정.
2
L0~L1 시도배송조회 tool call → 실제 지연 확인 → 테넌트 봇이 스토어 정책 기반 안내 + 판매자에게 소명 요청. SLA 24h 타이머 가동.
3
자동 격상판매자 무응답 → 타이머 초과 → 조건부 엣지가 L2로 전이. 상태와 시간이 그래프를 움직인다 — LangGraph를 쓰는 이유가 여기서 증명됨.
4
L2 중재 판정증거 수집(주문·결제·배송 이력, 필요 시 파손 사진 VLM 판독) → 리스크 스코어 산정 → 저위험이면 즉시 환불 경로, 고위험이면 소명 절차 경로 → 법 조항 인용 판정 초안 → 운영자 승인 → 환불 트랜잭션 + 판매자 페널티.
판매자 불복 분기: 이의제기 접수 → 심사 팀이 반품 검수 결과·소명 대조 → 인용/기각. 구매자↔판매자 외에 판매자↔플랫폼이라는 두 번째 분쟁 전선까지 다룬다.
5
L3 출구 (필요 시)중재 실패 → 케이스 파일을 소비자원 피해구제 신청 서식으로 패키징 + 절차 안내.
04 · Seller Journey

과정 ② 판매자 모드 — 온보딩이 데모 몰을 채운다

가상 쇼핑몰의 스토어들을 팀이 수작업으로 만드는 대신, 온보딩 에이전트를 통해 판매자가 입점하는 과정으로 만든다. 콜드스타트 비용이 기능 시연으로 전환되는 구조.

1
판매자 가입·로그인role=seller 인식 → 챗봇이 온보딩 모드로 진입. "어떤 상품을 팔 예정이세요?"
2
시장 벤치마크 제공"캠핑 랜턴 팔려고요" → 우리 몰의 해당 카테고리 데이터를 집계 레벨로 요약: 상품 분포, 가격대, 구매율 평균, 리뷰에서 추출한 주요 이슈. 개별 경쟁 스토어의 내부 수치는 노출하지 않음(집계·익명화 원칙) — 플랫폼이 자기 데이터를 쓰는 것이라 크롤링 불필요.
3
정보 수집판매 결정 후, 에이전트가 필요한 것을 능동적으로 요구: 상품 이미지, 상세설명 자료, 배송·환불 정책, 응대 톤. 부족한 항목을 판단해 되묻는 능동성이 포인트.
4
초안 생성 + 자동 검수상품 페이지 샘플 생성 → 상품정보제공고시 필수 항목 누락·표시광고법상 금지 표현(효능 과장 등)을 정책 RAG로 자동 검수 → "이 카테고리는 사이즈 분쟁이 많으니 실측표를 넣으세요" 같은 VOC 기반 가이드 첨부. 분쟁을 처리하며 배운 것이 분쟁을 예방하는 입점 단계로 환류.
5
수정 → 등록판매자가 단순 편집 화면에서 수정 → 확정 시 상품 등록 + 테넌트 config 자동 생성 → 이 스토어의 L1 응대 봇이 즉시 가동. 온보딩의 끝이 곧 CS 시스템의 시작.
05 · Key Mechanisms

고유 메커니즘

M-0리스크 기반 하이브리드 환불

소명 우선(네이버식: 공정하나 느림)과 선환불(쿠팡식: 빠르나 악용 리스크)을 케이스 단위로 동적 선택. 금액·증빙 수준·고객 환불 이력·판매자 분쟁률로 리스크 스코어를 산정해 경로를 결정한다. 어느 플랫폼도 하지 않는 지점이며, "분석 결과가 시스템 동작을 바꾼다"는 주제 요건의 가장 강한 증명.

M-1판매자 = 테넌트 config

스토어 하나 = config 하나(정책·SLA·자동 승인 한도·톤). 등록하면 L1 봇 자동 생성. 판매자 온보딩 = config 추가를 라이브 데모로.

M-2판매 주체 판별 라우팅

직매입/위탁/오픈마켓에 따라 책임 주체와 정책 경로가 달라짐. 케이스의 첫 질문은 "누가 판매자인가".

M-3SLA 자동 격상

소명 기한을 타이머로 걸어 초과 시 그래프 자동 전이. 현행 플랫폼의 수동 기한 관리를 상태 기계로 명시화.

M-4판매자 이의제기 심사

선환불의 부작용(부당 환불 주장·블랙컨슈머)을 다루는 두 번째 분쟁 전선. 사진 재사용 등 반복 어뷰징 패턴 감지 포함.

06 · Feature Extensions

기능 확장 카드

EXT-2

직접 학습 없음. VLM에 판정 루브릭(상품 일치 / 파손 유형·부위 / 훼손 등급 3단계)을 줘 zero-shot 판독 → 환불 제안(전액/부분/반품 후 판단)의 입력값으로. 팀 제작 평가셋 수십 장으로 판정 일치율 측정. 증거 판독 모듈 하나로 범위 고정.

07 · Principles

지키는 선 — 주객전도 방지

7 : 3

코어 7 : 확장 3. 심장은 Case 처리·분석·평가 파이프라인. 온보딩·구매·VLM은 남는 힘으로 감싸는 주변 기관. 발표에서도 확장은 마지막 2~3분 슬롯으로 고정.

DEP →

의존 방향 규칙. 확장 기능은 코어 산출물(분석 결과·정책 RAG·테넌트 config)을 소비만 한다. 온보딩이 없어도 config 수동 등록으로 데모가 돌아가야 함 — 일정이 밀리면 확장부터 잘라도 본체가 안 다친다.

HITL

돈·페널티는 AI 단독 확정 금지. 환불·제재·이의제기 인용은 조항 인용 + 운영자 승인 필수. 구매 확정도 사용자 명시 확인 필수.

SCOPE

판매자 모드는 3기능까지. 온보딩(초안+검수+config 등록) · VOC 요약 · 소명 지원. 페이지 빌더, 이미지 생성, 광고·프로모션 설정은 명시적 아웃 — 판매자용 SaaS라는 두 번째 프로젝트가 되는 것을 방지.
