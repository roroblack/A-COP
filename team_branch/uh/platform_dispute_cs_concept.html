Concept Brief · 2026-08 · Draft for Team Review

오픈마켓 분쟁조정 멀티에이전트 CS
"해결 단계로 층을 쌓는 에스컬레이션 사다리"

종합 몰(플랫폼) 아래 입점 판매자들의 CS를 3층 구조로 처리한다. 업무 종류가 아니라 해결 단계로 시스템을 조직하는 것이 아키텍처 시그니처. 판매자는 config 테넌트로 정의되어 플러그인처럼 추가된다.

L1

판매자 레벨 응대

테넌트 config로 자동 생성되는 스토어별 1차 응대 봇. 단순 문의 해결 + 분쟁 성립 여부 판정까지만 담당(얇게 유지).

↑ 판매자 무응답(SLA 초과) / 소명 부적절 / 구매자 불복 시 자동 전이
L2

플랫폼 레벨 중재

증거 수집 → 법정 기준(전자상거래법·분쟁해결기준) RAG 판정 → 유사 결정례 제시 → 환불/페널티 트랜잭션. 운영자 승인(HITL) 필수.

↑ 중재 실패 / 고액 분쟁 / 판정 불복 시 자동 전이
L3

외부 절차 연계

케이스 파일을 소비자원 피해구제 신청 서식으로 자동 패키징, 절차 안내. 시스템의 한계를 시스템이 알고 출구를 책임진다.

01 · Why this shape

왜 이 구조인가

에스컬레이션 자체가 에이전틱함의 증거. 상태(소명 유무, 판정 결과, 불복 여부)와 시간(SLA 타이머)에 따라 그래프가 전이하는 구조라, LangGraph의 조건부 엣지가 장식이 아닌 핵심 메커니즘이 된다. "왜 단일 LLM이 아닌가"에 대한 답이 아키텍처 그 자체.

판단 근거가 전부 공개 법정 문서. 전자상거래법 청약철회 규정, 전자상거래 표준약관, 소비자분쟁해결기준 — 판정이 약관 해석이 아니라 조항 인용으로 검증된다. 플랫폼 약관들도 판매자 조건보다 관계법령을 우선 규범으로 명시하고 있어 현실 정합성이 있다.

기존 논의가 전부 흡수됨. 피드백 분석 팀 → 판매자 리스크 스코어링(마케팅/운영 인사이트 방향), 소비자 지원 방향 → L3 층, 분쟁조정 아이템(Top10 #9) → L2 층, 도메인 교체 프레임워크 → 테넌트 config로 진화. 141개 기존 프로젝트에 이 형태는 없음.

02 · Seller as Tenant

아래 몰을 채우는 방법 — 판매자 = 테넌트 config

입점 스토어 하나가 config 파일 하나. 등록하면 그 스토어의 L1 응대 봇이 자동 생성된다. "판매자 온보딩 = config 추가"를 라이브로 보여주는 것이 확장성 데모의 핵심.

# tenant: store_012.yaml
store: "한라봉농원 직영몰"
category: 신선식품
sale_type: marketplace  # 직매입|위탁|오픈마켓
policy:
  ship_deadline_days: 2
  refund: 단순변심 7일, 왕복배송비 6,000
  auto_refund_limit: 30,000원 이하 즉시
sla:
  reply_hours: 24   # 초과 시 L2 자동 전이
tone: 친근체

데이터 겹 — mock 스토어 5~10개(카테고리·정책 다양화) + 주문·배송·결제 mock DB. AI Hub 쇼핑몰 리뷰를 스토어별 배정해 분쟁률·이슈 집계 재료로.

행동 겹 — 판매자 페르소나 LLM 시뮬레이터(협조형·지연형·비협조형·공격형). 에스컬레이션 트리거 시나리오를 자유롭게 재현.

화면 겹 — 판매자 소명 입력 콘솔(간단 UI). 시연 때 팀원이 판매자 역할로 직접 개입하는 인터랙티브 데모 가능.

03 · Agent Teams

에이전트 팀 구성

ROUTE
Supervisor / 판매주체 판별

케이스 접수 → 감성·이슈·의도 분류(소형 모델) → 판매 유형(직매입/위탁/오픈마켓) 판별이 첫 라우팅. 유형에 따라 책임 주체와 정책 그래프가 달라짐 — 쿠팡 구조에서 가져온 현실 반영.

L1
테넌트 응대 봇 (스토어별 자동 생성)

스토어 정책 config 기반 1차 응대. 자동 승인 한도 내 처리 + 분쟁 성립 판정. 의도적으로 얇게.

L2
증거 수집 에이전트

판정에 필요한 증빙(주문번호·사진·배송조회·대화 이력)을 판단해 능동적으로 요구, 구조화된 케이스 파일 생성.

L2
중재·판정 에이전트

법정 기준 RAG 조회 → 조항 인용 판정 초안 + 유사 피해구제·분쟁조정 결정례 제시 → 운영자 승인 후 환불/페널티 트랜잭션.

NEW
판매자 이의제기 심사 팀

선환불 케이스에서 판매자↔플랫폼 분쟁(부당 환불 주장) 심사. 반품 검수 결과 + 소명 대조. 구매자↔판매자 외의 두 번째 분쟁 전선 — 쿠팡 셀프환불 구조에서 도출한 고도화 팀.

NEW
리스크 스코어링 팀

케이스 위험도(금액·증빙 수준·고객 환불 이력·판매자 분쟁률) 산정 → 처리 경로 결정의 입력값. 블랙컨슈머 반복 패턴 감지 포함.

INSIGHT
피드백 분석 팀

스토어별 리뷰·분쟁 데이터로 이슈 유형/분쟁률 집계, "특정 스토어 위생 이슈 급증" 시그널을 운영 대시보드로. 선제 개입의 근거.

L3
외부 절차 연계 에이전트

케이스 파일 → 소비자원 피해구제 신청 서식 자동 패키징 + 절차 안내.

04 · vs Naver · Coupang

현행 플랫폼 대비 포지션

네이버는 "소명 먼저"(공정하지만 느림), 쿠팡은 "환불 먼저"(빠르지만 악용 리스크). 우리는 케이스 단위로 두 정책을 동적 선택한다.

네이버 (스마트스토어)쿠팡본 시스템
접수폼 기반 신고폼/버튼 기반대화형 접수 + 증거 자동 구조화
환불 시점소명·판정 후선환불(집화 스캔 자동환불, 일부 회수 없는 셀프환불) 후 판매자 이의제기리스크 스코어로 경로 선택: 저위험=즉시 환불, 고위험=소명 절차
판정사람 CS 재량사람 CS + 규정 체크법정 조항 인용 판정 초안 + 유사 결정례 제시 + 운영자 승인(HITL)
에스컬레이션소명 기한 관리(수동성)24h 답변 SLA + 페널티SLA 타이머 기반 그래프 자동 전이 (상태 기계로 명시화)
외부 출구기관 안내 수준기관 안내 수준소비자원 신청 서류 자동 패키징까지
판매자 지원——소명 작성 지원 에이전트 (양측을 돕는 플랫폼)
선제 감지—반품률 지표 관리리뷰·분쟁 분석 기반 스토어 리스크 스코어 → 분쟁 전 개입 시그널
05 · Upgrades

고도화 포인트

UP-0리스크 기반 하이브리드 환불 (핵심 차별화)

네이버식 소명 우선과 쿠팡식 선환불을 케이스 단위로 동적 선택. 금액·증빙·이력 기반 리스크 스코어가 경로를 결정 — 어느 플랫폼도 하지 않는 지점이며, "분석 결과가 시스템 동작을 바꾼다"는 주제 요건의 가장 강한 증명.

UP-1유사 결정례 RAG

소비자원 피해구제 사례·분쟁조정 결정례를 검색해 "비슷한 사례의 결정"을 양측에 제시 → 합의 유도.

UP-2판매자 이의제기 심사

선환불의 부작용(부당 환불·블랙컨슈머)을 다루는 두 번째 분쟁 전선. 반복 환불 패턴 감지 포함.

UP-3판매자 소명 지원

분쟁은 판매자가 소명을 못 써서 커지기도 함. 소명 초안 작성을 돕는 에이전트를 판매자 콘솔에 제공.

UP-4선제 개입 시그널

스토어별 이슈 급증 감지 → 운영 대시보드 알림. 마케팅/운영 인사이트 확장이 여기 흡수됨.

06 · Key Scenario

대표 시나리오 — 한 케이스가 세 층을 타고 오른다

1
접수"2주째 미배송인데 판매자가 답이 없어요" → 감성(분노)·이슈(미배송)·판매유형(오픈마켓) 판별, 케이스 생성.
2
L1 → 판매자 소명 요청테넌트 봇이 배송조회 + 판매자에게 소명 요청. SLA 24h 타이머 가동.
3
자동 에스컬레이션판매자 무응답(비협조형 페르소나) → 타이머 초과 → L2 자동 전이.
4
L2 중재증거 수집 완료 → 청약철회·계약불이행 조항 인용 판정 초안 + 유사 결정례 제시 → 리스크 스코어 저위험 → 운영자 승인 → 환불 트랜잭션 + 판매자 페널티.
5
판매자 불복 (분기)이의제기 접수 → 심사 팀이 소명·검수 결과 대조 → 기각/인용 판정.
6
L3 출구 (분기)중재 실패 시 케이스 파일을 소비자원 피해구제 신청 서식으로 패키징 + 절차 안내.
07 · Data Sources

데이터 소스

법정 문서

전자상거래법(청약철회) · 전자상거래 표준약관 · 소비자분쟁해결기준L2 판정의 근거 코퍼스. 전부 공개, 조항 단위 인용 가능.

공공데이터

한국소비자원 품목별 피해구제 사례(Q&A) · 분쟁조정 결정례유사 사례 RAG + 합성 문의의 근거. 전자상거래 품목이 최다라 궁합 최상.

AI Hub

쇼핑몰 리뷰(속성기반 감성분석) · 상담형 대화 데이터분류 모델 학습 + 상담 문체 참고. 리뷰는 mock 스토어별 배정해 분쟁률 집계 재료로.

직접 생성

테넌트 config 5~10개 · 주문/배송/결제 mock DB · 판매자 페르소나 시뮬레이터 · 합성 분쟁 골든셋피해구제 사례의 실제 이슈 분포를 근거로 합성 — 골든셋(문의·정답 판정·모범 응대)이 자동 구축됨.

08 · Guardrails & Scope

설계 원칙 · 범위 통제

HITL

돈과 페널티는 AI 단독 확정 금지. L2 판정·환불·페널티·이의제기 인용은 조항 인용 + 운영자 승인 필수. 설계 성숙도 어필 지점.

SCOPE

L1은 얇게. 판매자 응대 층에 공들이면 프로젝트가 둘이 됨. 무게는 L2 중재 + 에스컬레이션 로직에.

SCOPE

config 동적 그래프 빌드는 첫 주에. "테넌트 하나를 config로 추가하는 데모"를 최우선 마일스톤으로. 리팩토링으로 나중에 넣기 어려움.

EVAL

평가는 판정 정확도 중심. 골든셋 대비 이슈 분류 정확도, 판정(환불 가/불가·귀책) 일치율, 인용 조항 정확성, 에스컬레이션 트리거 정확도. 법정 기준이라 정답 검증이 깔끔함.
