A-COP INTEGRATION MAP · PIPELINES → ARCHITECTURE · 2026-08

안착 지도 — P1~P5가 A-COP의 빈칸을 채운다

A-COP 브리핑은 "Team 종류와 개수는 요구사항 분석 후 결정한다"고 비워두었다. 우리 파이프라인이 그 요구사항 분석의 답이다. 새 아키텍처를 만드는 것이 아니라, A-COP의 각 레이어에 우리 기능이 꽂히는 자리를 지정한다.

01 · Layer Mapping

레이어별 안착 — 왼쪽 A-COP 스택, 오른쪽 우리 기능

칩의 접두어는 출처 파이프라인(P1~P5) 또는 시스템 요소. 굵은 테두리는 그 레이어의 존재 이유를 증명하는 핵심 매핑.

ENTRY
접점 (Web UI · MCP · A2A · Operator UI)
사용자·외부 AI·파트너 에이전트·운영자의 진입 채널
P1구매자 챗 (Web UI) P2판매자 콘솔 (Web UI) HITL운영자 승인 콘솔 + 맥락 승계 브리핑 (Operator UI) EXT구매자의 개인 AI 문의 (MCP) SIM판매자 페르소나 시뮬레이터 (A2A Remote)
CORE 2
Agent Gateway
인증 · 권한 · Scope · Identity
MAP역할 이중 모드 (role=buyer/seller) = Identity·Scope 그 자체 P4원가 조회 권한 — 판매자 본인 Scope 제한
CORE 1
Customer Case Layer
모든 요청을 Case lifecycle로 정규화
MAP퍼널 L0~L3 = Case 상태 정의 (new→…→resolved) P1SLA 타이머 = 기한 있는 WAIT 상태 P5미충족 수요 = Case Event 로깅
CONTEXT
Context Broker (4원천 → Context Pack)
Vector RAG · Graph 관계 · DB State · Memory
P1법령·약관·유사 결정례 (Vector RAG) P2고시 항목·금지 표현 (Vector RAG) P1주문·배송·결제 (DB State) P1과거 Case·환불 이력 (Memory) P3어뷰징 관계 탐색: 고객—이미지—판매자—청구 연결 (GraphStorePort)
CORE 1
Agentic Controller
Routing · Replan · WAIT/RESUME · 경합 정책
MAPSupervisor 라우팅 (역할·이슈·판매주체 판별) P1SLA 초과 → 자동 격상 = WAIT 만료 후 Replan P1리스크 분기 (즉시환불 vs 소명절차) = 동적 경로 선택
REGISTRY
Agent Team Registry
Capability · execution_type · endpoint 등록
MAP테넌트 config = Registry 등록 항목 P2온보딩의 "config 등록 → L1 봇 가동" = Registry 등록 행위의 UI화
EXEC
Agent Team Slots (Local / A2A)
"Team A/B/C — 요구사항 분석 후 결정"
TEAM판정·중재 팀 (P1·P3의 심장) TEAM증거 수집 팀 (+VLM tool) TEAM이의제기 심사 팀 TEAM온보딩 팀 (P2) TEAMWhat-if 팀 (P4) TEAM피드백 분석 팀 (P5 집계 소비) SIM판매자 시뮬레이터 = A2A Remote Slot
STATE
Shared State
Case·Task 상태 · Evidence · Conflict
P1케이스 파일 (증거·판정 근거 누적) HITL맥락 승계 브리핑 = Shared State의 요약 뷰
CORE 2
Tool / Action Layer
ActionProposal · Human Approval · Idempotency · Audit
P1판정 초안 = ActionProposal 형식 그대로 P1환불·페널티 집행 (승인 후) P3차액 지급 (승인 후) P1L3 소비자원 서식 패키징 (문서 생성 액션) P4손익 계산 엔진 (내부 tool)

03 · Heavy Parts, Real Jobs

무거운 부품 3개의 실사용처 — 장식에서 기능으로

A-COP에서 가장 야심찼던(그래서 부담이었던) 세 부품에, 우리 파이프라인이 각각 실제 일감을 준다.

A2A 막연한 "파트너 에이전트 위임" 판매자 페르소나 시뮬레이터

협조형·지연형·비협조형 판매자 봇을 독립 Agent System으로 세우고 소명 요청을 A2A Task로 위임. 에스컬레이션 트리거 재현 도구이자 A2A 프로토콜의 실데모.

PHASE 2 · 데모 가치 높음
GRAPH 막연한 "관계 탐색으로 근거 확장" 어뷰징 관계 그래프

고객—증빙 이미지—판매자—청구 건을 그래프로 연결해 반복 환불·이미지 재사용·연쇄 청구 패턴 탐지. 리스크 스코어링(P1 분기·P3 체크)의 입력이 되어 판정 경로를 실제로 바꾼다.

PHASE 2 · 차별화 핵심
MCP 막연한 "외부 AI 연동" 개인 AI의 대리 문의

구매자의 ChatGPT/Claude가 MCP로 우리 Case API에 접속해 "내 환불 어떻게 됐어?"를 대신 묻는 시나리오. 같은 Case Layer로 정규화되므로 추가 개발이 아니라 채널 추가.

PHASE 3 · 여력 시 옵션
04 · Phasing

단계 배치 — 어디까지가 코어 7인가

PHASE 1 · MVP (코어 7)
  • Case Layer + Controller — 퍼널 상태·SLA 격상·리스크 분기
  • Local Team Slot 3~4개 — 판정·증거·L1 봇·분석
  • Context Broker 축소판 — Vector RAG + DB State (Graph·Memory 없이 시작)
  • Tool/Action + Operator UI — ActionProposal·HITL·맥락 브리핑
  • Registry 최소형 — 테넌트 config 로딩
PHASE 2 · 확장 (3)
  • P2 온보딩 — Registry 등록의 UI화
  • P3 최저가 보상 — VLM + 판정 재사용
  • P4 What-if — 계산 tool + 시뮬레이션
  • Graph 어뷰징 — 리스크 입력 강화
  • A2A 시뮬레이터 — 격상 데모용
PHASE 3 · 옵션
  • MCP 개인 AI 채널
  • Memory 원천 — 과거 Case 경험 활용
  • P5 입고 알림 루프 완성
  • 다국어 응대
읽는 법: A-COP의 모든 상자를 만드는 게 아니라, Phase 1은 A-COP 스택의 세로 한 줄(접점→Gateway→Case→Broker축소→Controller→Slot→State→Action)을 얇게 관통시키는 것. 이후 Phase는 그 줄에 팀·원천·채널을 옆으로 꽂는다 — "모듈형 Basement"라는 A-COP의 약속이 실제로 지켜지는 방식.
