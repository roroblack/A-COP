PROJECT BRIEF - 2026.08

A-COP Commerce
"한 건의 요청을, 근거를 갖춘 처리로 바꾸는 플랫폼"

구매자 요청을 주문, 상품, 배송, 정책 데이터와 연결해 Case로 관리하고, 고객 피드백을 분석해 반복 문제를 조기 탐지하는 마켓플레이스형 멀티에이전트 고객운영 플랫폼입니다. 단순 답변 생성이 아니라 개인화된 안내, 상태 확인, 외부 확인 요청, 승인 기반 실행, 감사 로그까지 다룹니다.

PROJECT TOPIC
다중 에이전트 서빙 기반 고객 피드백 분석 및 맞춤형 응대 자동화

01 - DOMAIN DEFINITION

이 프로젝트는 "쇼핑몰 챗봇"이 아니라 마켓플레이스 운영 자동화다

플랫폼 기업은 거래를 중개하고, 구매자는 상품을 구매하며, 판매자는 상품과 정책을 제공하고, 택배사는 배송을 수행합니다. 고객 요청의 책임 주체가 하나가 아닐 수 있으므로 단일 챗봇보다 Case 중심 협업 구조가 필요합니다.

BUYER - 소비자 고객

구매자

상품 문의, 리뷰, 배송 문의, 교환, 반품, 환불, 판매자 신고를 플랫폼에 요청합니다.

→
PLATFORM - A-COP

이커머스 플랫폼

주문과 정책의 공식 접점입니다. 요청을 Case로 만들고, 근거를 확인하고, 승인된 조치를 실행합니다.

↔
PARTNERS - B2B

판매자와 배송사

상품 정보, 재고, 판매자 정책 또는 배송 추적 정보를 제공합니다. 필요한 경우 확인 요청을 받고 응답합니다.

역할을 분명히 구분한다. 구매자는 소비자 고객, 판매자는 플랫폼의 입점 파트너, 배송사는 외부 운영 파트너입니다. 플랫폼은 구매자에게 1차 응대 책임을 지고, 판매자·배송사에는 확인 또는 클레임을 요청합니다. 따라서 "누가 답해야 하는가"가 아니라 "누가 확인하고, 누가 최종 실행 권한을 갖는가"를 분리해야 합니다.
02 - REQUEST INTAKE

챗봇과 폼은 둘 다 필수가 아니라, 교체 가능한 입력 채널이다

두 입력 방식이 떠오른 이유는 타당합니다. 그러나 MVP에서 중요한 것은 어떤 화면으로 받느냐보다, 서로 다른 입력을 동일한 Case 구조로 바꾸는 것입니다.

MVP RECOMMENDED

통합 요청 폼

반품·환불·배송신고처럼 주문번호, 사유, 첨부 증거가 필요한 공식 요청에 적합합니다. 데이터 누락이 적고 테스트가 쉽습니다.

OPTION

대화형 챗봇

고객의 자연어 설명을 받기에 좋습니다. 다만 주문 식별, 필수 사유, 사진 등 누락 정보를 재질문하는 흐름이 필요합니다.

LATER COMBINATION

챗봇에서 폼으로 전환

챗봇은 안내와 사전 분류를 담당하고, 환불·반품 같은 공식 처리는 입력값이 채워진 폼으로 넘깁니다.

통합 요청 폼의 최소 입력

request_type
상품 문의 / 배송 / 반품 / 환불 / 신고 / 리뷰 order_id
주문 연결 - 없으면 상품 ID 또는 추가 확인 order_item / quantity
반품·환불 대상 상품과 수량 선택 message
고객 설명과 요청 내용 evidence
파손 사진, 배송 화면 등 첨부자료 channel
폼 / 챗봇 / 리뷰에서 생성된 VOC customer_id
권한 확인을 위한 구매자 식별자 service_context
선호 언어·채널 등 최소 개인화 신호 consent / notice
개인정보 처리 고지와 동의 기록
리뷰는 공식 처리 요청과 다르다. 리뷰는 기본적으로 공개 평가이므로 모든 리뷰를 상담 Case로 만들지 않습니다. 저평점, 파손, 가품, 안전, 사기 의심처럼 정해진 위험 규칙에 해당하는 리뷰만 VOC Case로 전환합니다.
03 - CASE ORCHESTRATION

요청은 한 번 접수되지만, 처리는 여러 팀이 이어받는다

A-COP의 핵심은 메시지를 곧바로 답변으로 끝내지 않는 것입니다. 접수된 요청을 공식 상태와 근거를 가진 Case로 만들고, 팀 결과와 외부 확인을 같은 상태에 기록합니다.

분류는 최소 일곱 가지 축으로 수행한다

분류 축값 예시라우팅 또는 처리에 미치는 영향
요청 의도상품 문의반품환불배송신고담당 팀과 필요한 RAG 코퍼스를 선택합니다.

주문 연결 수준주문 확인상품만 확인추가정보 필요바로 처리할지, 주문번호·사진을 재요청할지 결정합니다.
위험도일반금전 처리안전사기 의심사람 승인, 즉시 에스컬레이션, 민감정보 접근 여부를 결정합니다.
감성·긴급도중립부정강한 불만긴급처리 우선순위와 사람 개입 필요 여부를 정합니다.
응대 맥락신규재구매선호 채널이전 Case같은 정책 안에서 안내 순서·언어·톤을 조정합니다.
처리 상태runningwaiting_externalwaiting_approvalresolved외부 파트너 응답과 사람 검토를 잃지 않고 재개할 수 있습니다.

Case는 상태 전이와 감사 로그를 함께 가진다

new→classified→gathering_evidence→proposed→waiting_approval→resolved

정보가 부족하면 needs_more_info, 배송사·판매자 확인이 필요하면 waiting_external으로 이동했다가 같은 Case를 재개합니다. 모든 전이에는 시각, 담당 주체, 근거, 다음 행동을 이벤트로 남깁니다.

05 - FEEDBACK ANALYTICS AND PERSONALIZATION

개별 요청을 처리하는 동시에, 누적 피드백에서 다음 문제를 먼저 찾는다

주제의 “고객 피드백 분석”은 Case 처리의 부가 기능이 아닙니다. A-COP은 고객에게는 현재 건의 해결을, 운영자에게는 반복 문제와 우선 대응 대상을 제공하는 두 가지 산출물을 만듭니다.

REACTIVE OUTPUT - CASE RESPONSE

이번 요청에 대한 근거 기반 응대

주문·정책·배송 상태를 확인하고, 고객 상황에 맞는 안내와 처리안을 만듭니다. 금전·제재 등 고위험 조치는 사람 승인을 거칩니다.

PROACTIVE OUTPUT - FEEDBACK INSIGHT

다음 문제를 막기 위한 운영 인사이트

리뷰와 VOC를 판매자·상품·원인·감성·기간 기준으로 집계합니다. 반복 불만, 급격한 부정 감성 증가, 안전 키워드를 운영자 검토 대상으로 올립니다.

ALERT EXAMPLE

반복 불만 조기 경보

최근 7일 동안 특정 판매자의 특정 상품에서 “파손”, “포장 불량”으로 분류된 부정 피드백이 기준선보다 증가하면, Seller Quality 팀에 근거 묶음과 함께 검토안을 생성합니다. 이는 자동 제재가 아니라 사람이 확인할 운영 신호입니다.

PERSONALIZED RESPONSE

정책은 같게, 안내는 상황에 맞게

재구매 여부, 선호 언어·채널, 이전 문의의 미해결 여부처럼 최소화된 신호를 사용해 안내 순서·톤·에스컬레이션 우선순위를 조정합니다. 고객별로 환불 권리나 금액을 임의로 다르게 판단하지 않습니다.

예시: 강한 부정 감성 + 최근 미해결 Case → 운영자 우선 검토
예시: 선호 채널이 앱 알림 → 같은 처리 상태를 앱 알림 문구로 제공
개인화의 경계: 민감정보나 불필요한 상세 행동 이력은 사용하지 않으며, 개인화 신호는 응대 경험과 우선순위에만 사용합니다. 법·정책상 권리, 환불 가능 여부, 제재 판단은 모든 고객에게 동일한 규칙과 승인 절차를 적용합니다.
06 - KEY SCENARIOS

대표 시나리오 - "상품이 파손됐고 배송도 너무 늦었어요. 반품하고 싶어요."

한 요청에 주문, 배송, 판매자 품질 이슈가 함께 있는 경우로, 멀티에이전트 구조가 왜 필요한지 가장 잘 보여줍니다.

1

구매자가 통합 요청 폼을 제출한다

주문번호, 반품 사유, 파손 사진, "배송이 늦었다"는 설명을 받습니다. 이 단계에서는 단지 접수일 뿐, 환불이나 책임을 확정하지 않습니다.

2

Supervisor가 복합 Case로 분류한다

주요 의도는 반품/환불, 관련 책임 주체는 배송사와 판매자, 위험도는 금전 처리로 분류합니다. Order Ops와 Logistics Ops를 차례로 배정합니다.

3

주문·반품 팀이 정책과 거래 사실을 확인한다

수령일, 반품 가능 기간, 결제금액, 판매자 반품 정책을 근거로 환불 가능 범위와 반품비 부담 주체를 제안합니다. 한 주문에 여러 상품·수량이 있으면 order item과 수량 단위로 부분 반품 가능 여부를 판단합니다.

4

물류 팀이 배송 증거를 확인하고 배송사에 요청한다

송장 이력에서 지연 여부를 확인하고, 파손 사진을 포함한 배송 클레임 요청을 생성합니다. 배송사 응답을 기다리는 동안 Case는 waiting_external 상태가 됩니다.

5

필요할 때 판매자 품질 팀이 반복성을 점검한다

같은 판매자·상품에서 파손과 저평점이 반복되는지 확인합니다. 반복된다면 판매자 주의 또는 상품 검수의 운영자 검토안을 추가합니다.

승인 분기: 시스템은 “반품 대상 1개 회수 후 환불 제안”, “경미한 파손에 대한 부분 환불 제안” 또는 “반품 회수 후 전액 환불 제안”을 만들 수 있습니다. 세트·묶음 상품은 판매 정책을 확인하며, 실제 금전 처리와 판매자 제재는 운영자가 승인한 뒤에만 Mock 실행됩니다.
6

최종 응답과 VOC가 함께 남는다

구매자에게 처리 상태와 근거를 안내하고, 이 사건의 익명화된 유형·원인·결과는 VOC 집계에 반영됩니다. 이후 반복 불만 탐지의 근거가 됩니다.

SCENARIO B - FEEDBACK ANALYTICS

리뷰 누적 → 품질 이슈 검토

동일 판매자의 상품에서 “포장 불량” 부정 리뷰가 일정 기간 급증합니다. 분석기는 유사 리뷰 묶음, 증가 추이, 연결 주문 수를 근거로 제시하고 Seller Quality 팀은 판매자 확인·검수 강화 여부를 운영자 검토안으로 만듭니다.

SCENARIO C - PERSONALIZED RESPONSE

미해결 이력이 있는 고객의 배송 지연

배송 지연 자체의 보상·처리 기준은 모든 고객에게 동일합니다. 다만 최근 미해결 Case와 강한 부정 감성이 함께 확인되면, 시스템은 빠른 사람 연결과 현재 단계·다음 예정 시점을 먼저 안내하도록 응대 순서를 조정합니다.

07 - DATA AND POLICY RAG

거래 구조, 한국어 피드백, 정책 근거를 구분해 조합한다

공개 데이터로 데모 흐름을 검증하되, 출처·언어·라이선스의 한계를 숨기지 않습니다. 실제 기업 연동 단계에서는 해당 기업이 권한을 부여한 주문·상품·배송·문의 데이터만 사용합니다.

데모에 바로 쓰는 데이터

REAL / ANON
Olist Brazilian E-Commerce

주문, 상품, 결제, 배송, 판매자를 연결하는 거래 골격으로 사용합니다. 리뷰는 포르투갈어이고 텍스트 공란이 있어, 한국어 응대 품질을 직접 증명하는 데이터로는 사용하지 않습니다.

KOREAN VOC
허용된 한국어 리뷰·VOC 또는 통제된 골드셋

라이선스와 접근 조건을 확인한 한국어 데이터만 사용합니다. 확보가 어려운 Case는 사실과 다름을 명시한 통제된 합성 VOC로 만들고, Olist 주문 ID에 매핑해 한국어 시연을 구성합니다.

OFFICIAL
정책 RAG 코퍼스

소비자분쟁해결기준, 전자상거래 소비자보호 관련 법령, 표준약관, 소비자24 상담사례를 출처·시행일·검토일과 함께 저장합니다.

PUBLIC API
Safety Korea 제품 안전인증·리콜 정보

KC 인증과 국내외 리콜 정보를 조회해 위험 상품 또는 안전 이슈 Case를 에스컬레이션합니다.

CONTROLLED MOCK
가상 주문·판매자·배송사 API

환불 실행, 배송사 확인 요청, 판매자 경고는 통제된 Mock Action으로 구현해 상태 변경과 승인 흐름을 안전하게 검증합니다.

데이터를 쓰는 위치

RAG
정책·상품 근거 검색

공식 정책, 상품 사양, 판매자 정책, 리콜 정보를 팀별 코퍼스로 분리하고, 답변에는 근거 문서와 검토일을 남깁니다.

DB
공식 상태 조회

주문, 결제, 배송, 반품, 승인 상태는 벡터 검색이 아니라 트랜잭션 DB에서 정확하게 조회합니다.

MODEL
분류·감성·반복 VOC 분석

요청 의도, 감성, 책임 주체, 위험도를 분류하고 반복 불만 패턴을 집계합니다.

AUDIT
실행 전후 기록

어떤 근거로 누가 어떤 조치를 제안·승인·실행했는지 Case 이벤트와 감사 로그에 남깁니다.

실제 기업 도입 시의 데이터 원칙: 경쟁사 페이지의 리뷰를 대량 수집하는 것이 아니라, 해당 기업이 권한을 부여한 주문·상품·문의 데이터와 공식 API를 연결합니다. 고객명·주소·연락처 같은 개인정보는 RAG 코퍼스에 넣지 않고, 권한 통제된 운영 DB에 최소 범위로 보관합니다. 고객 메시지·리뷰는 신뢰할 수 없는 입력으로 취급해 모델 지시가 아닌 분석 대상 텍스트로만 처리합니다.
08 - AGENT SERVING DESIGN

상태를 잃지 않고 멈추고 재개하는 에이전트 서빙 구조

“서빙 기반”은 여러 에이전트를 그려 놓는 것에 그치지 않습니다. 요청을 API로 받고, 외부 확인·사람 승인을 거치는 동안 Case 상태를 영속화하며, 처리 과정과 비용을 관측할 수 있어야 합니다.

ENTRY API폼·챗봇 요청을 받는 FastAPI 계층. 인증, 입력 검증, Case 생성 담당.
ORCHESTRATORLangGraph 기반 Supervisor 그래프. 팀 라우팅, interrupt, 재개 조건을 관리.
STATE STOREPostgreSQL과 Checkpointer에 Case·이벤트·승인 상태를 영속화.
ASYNC WORKER배송사 확인, 알림, 분석 집계처럼 오래 걸리는 작업을 이벤트·큐로 분리.
OBSERVABILITY트레이싱으로 모델·도구 호출, 지연, 토큰, 오류, 승인 경로를 기록.
WHY MULTI-AGENT

한 모델이 모든 일을 하는 방식과 다른 이유

  • 주문·정책, 물류, 판매자 품질은 조회 데이터와 판단 기준이 다릅니다.
  • 배송사 확인처럼 외부 대기를 별도 흐름으로 두어야 합니다.
  • 팀마다 허용 도구와 승인 경계가 달라 최소 권한을 적용할 수 있습니다.

단, MVP는 Supervisor와 3개 팀으로 제한해 멀티에이전트가 목적이 되는 것을 피합니다.

09 - MVP AND EXTENSIBILITY

처음에는 한 기업의 운영 흐름을 재현하고, 이후 기업별로 이식한다

이식 가능성은 "모든 쇼핑몰에 즉시 연결된다"는 뜻이 아닙니다. Case 엔진은 공통으로 두고, 기업별 데이터 연결, 정책, 승인 기준만 설정 가능한 구조를 만든다는 뜻입니다.

PHASE 1

Case·골드셋 MVP

통합 요청 폼, 주문 Mock DB, 3개 팀 라우팅, 상태 화면과 라벨링된 한국어 Case 150건을 구성합니다.

PHASE 2

근거·승인 처리

정책 RAG, 배송 추적 Mock, Action Proposal, 사람 승인과 감사 로그를 연결합니다.

PHASE 3

피드백 분석·개인화

반복 불만 대시보드, 감성·긴급도 우선순위, 최소 신호 기반 응대 순서 조정을 구현합니다.

PHASE 4

기업 이식 구조

주문, 카탈로그, 물류, 결제 Action을 Port/Adapter로 분리하고 기업별 정책 config를 적용합니다.

COMMON ENGINE

모든 기업에 공통인 부분

Case Lifecycle, 분류, Agent Team 계약, Context Pack, 승인, 감사 로그, 평가 포맷

TENANT CONFIGURATION

기업별로 바뀌는 부분

주문/상품/물류 API, 반품·환불 정책, SLA, 승인 금액, 판매자 제재 규칙, RAG 문서

10 - EVALUATION AND BOUNDARIES

"답변을 잘했다"보다 "안전하게 처리했고, 문제를 발견했는가"를 평가한다

문장 품질뿐 아니라 정확한 팀 배정, 근거 포함, 승인 경계 준수, Case 상태 전이와 반복 불만 탐지를 함께 측정합니다. 멀티에이전트 구조의 효용은 반드시 비교 실험으로 확인합니다.

ROUTING분류·팀 배정 정확도

의도·책임 주체·위험도 F1. 목표: 골드셋 기준 0.85 이상.

EVIDENCE근거 적합성

거래 사실과 정책 근거를 올바르게 참조하는 비율과 LLM 루브릭 평가.

SAFETY승인 경계 준수

환불·제재 등 고위험 조치의 승인 위반율. 목표: 0%.

OPERATIONSCase·경보 완결성

외부 대기·재개·해결·감사 로그 및 반복 불만 경보가 누락 없이 이어지는 비율.

평가 프로토콜

GOLD SET

한국어 Case 150건에 의도, 책임 주체, 위험도, 기대 Action, 승인 여부를 라벨링합니다.

BASELINE

단일 LLM + 도구 호출과 Supervisor + 3개 팀을 같은 골드셋에서 비교합니다.

ABLATION

RAG 제거, 승인 게이트 제거 시 근거 품질과 안전 위반이 어떻게 달라지는지 확인합니다.

IN SCOPE

구현으로 증명할 것

요청 접수부터 복합 Case 분류, 팀 협업, 정책 근거, 승인 후 Mock 실행, 피드백 분석과 개인화된 안내까지의 완결된 운영 흐름

OUT OF SCOPE

MVP에서 하지 않을 것

실제 카드 환불, 실제 판매자 제재, 택배사 계약 시스템 연동, 파손 사진 자동 판독, 경쟁사 대규모 크롤링

추가 가드레일: 고객 텍스트와 리뷰는 신뢰할 수 없는 입력으로 분리하고, 도구 조회는 구조화된 권한 범위에서만 수행합니다. Case별 최대 단계·도구 호출·토큰 예산을 두며, 반복 호출 또는 무진전 상태는 Supervisor가 사람에게 에스컬레이션합니다. LLM에는 필요한 개인정보만 마스킹해 전달합니다.
11 - ONE SENTENCE

최종 프로젝트 정의

기업별 주문·상품·배송·정책 시스템과 연동하여 구매자 문의, 반품·환불, 배송 이슈, 판매자 VOC를 Case 단위로 안전하게 처리하고, 누적 피드백에서 반복 문제를 조기 탐지하며, 고객 맥락에 맞는 안내를 제공하는 멀티에이전트 이커머스 Customer Operations Platform.
