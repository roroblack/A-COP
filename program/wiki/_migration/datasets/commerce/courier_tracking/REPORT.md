# 택배 배송 이력 데이터셋

## 한 줄 요약

송장번호를 넣으면 그 택배가 언제 어디를 거쳐 갔는지 기록을 받아오는 도구와, 그 결과 데이터다.

## 왜 만들었나

A-COP은 고객 문의에 답하는 시스템이다. "제 물건 어디쯤 왔나요?"는 가장 흔한 질문이다.

이 질문에 답하려면 **택배가 지금 어느 단계인지** 알아야 한다. 그 정보를 실제로 받아오는 통로가 이 폴더다.

## 무엇이 들어 있나

| 파일 | 내용 |
|---|---|
| `courier_codes.json` | 국내 택배사 111곳의 이름과 코드 |
| `scripts/track.py` | 송장번호를 넣으면 배송 이력을 받아오는 실행 파일 |
| `scripts/naver_parcel_api.py` | 실제 조회를 수행하는 부분 |
| `scripts/merge_incoming.py` | 팀원 제출본(`raw/_incoming_*/`)을 `processed/` 로 합치는 실행 파일 |
| `raw/tracking_*.jsonl` | 조회한 결과 원본. 실행한 날짜별로 쌓인다 |
| `raw/_incoming_*/` | 팀원이 각자 자기 계정에서 모아 보낸 제출본 |
| `processed/tracking.jsonl` | 네이버 API 조회분을 하나로 합치고 송장번호 기준 중복을 제거한 것 |
| `processed/tracking_coupang.jsonl` | 쿠팡 화면 수집분. ★위와 **다른 스키마**다 |
| `tracking_schema.json` | 네이버 조회 결과의 규격 |
| `tracking_coupang_schema.json` | 쿠팡 수집 결과의 규격. 왜 따로인지도 여기 적혀 있다 |
| `legacy/` | 택배사 홈페이지를 직접 읽던 이전 방식. 지금은 안 쓴다 |

## 어떻게 받아오나

택배사마다 홈페이지가 다르고 화면 구조도 제각각이다. 111곳을 각각 대응하는 것은 현실적이지 않다.

그래서 **네이버 택배조회를 통로로 쓴다.** 네이버는 이미 모든 택배사를 하나의 형식으로 정리해 두었다.

```
송장번호 + 택배사 코드  →  네이버 택배조회  →  통일된 형식의 배송 이력
```

이 방식의 장점은 택배사가 홈페이지를 바꿔도 영향을 받지 않는다는 것이다. 단점은 네이버가 지원하지 않는 택배사는 조회할 수 없다는 것이다.

## A-COP에서 어디에 쓰나

계획서의 Core 2(Access & Action Platform)가 쓴다.

Core 2는 실제로 외부에 무언가를 요청하고 결과를 받아오는 층이다. "배송 조회"라는 행동을 수행할 때 이 도구를 호출한다.

**주의**: 이 폴더는 학습용 데이터가 아니다. 모델을 훈련시키는 재료가 아니라, 실행 시점에 호출하는 도구다.

`processed/tracking.jsonl`은 그래서 "전처리한 학습 데이터"가 아니라 **날짜별
원본을 합치고 중복만 제거한 것**이다(2026-08-28에 만들었다 — 그 전까지는
`processed/`가 비어 있었고, 그게 정상이라고 이 문서에 적혀 있었다).
정규화·토큰화 같은 학습용 전처리는 여전히 하지 않는다.

## 사람처럼 보이게 하는 장치

조회와 조회 사이에 무작위 대기를 넣는다. 기계가 일정한 간격으로 두드리면 차단 대상이 되기 때문이다.

자세한 사용법과 옵션은 `README.md`에 있다.

## 개인정보

조회 결과에서 다음은 저장하지 않는다.

- 받는 사람 이름
- 전화번호
- 상세주소

배송 경로에 나오는 물류센터 이름은 개인 식별성이 없으므로 남긴다.
