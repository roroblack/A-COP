# 문서 작성 표준

## 하면 안 되는 것

**1. 코드를 문장으로 옮겨 적지 않는다.**

```markdown
❌ TeamRegistry 클래스는 register 메서드를 가지고 있습니다.
   register 메서드는 team을 등록합니다.
```

에이전트가 코드를 읽으면 바로 아는 내용이다. 대신 이렇게 쓴다.

```markdown
⭕ ## 책임
   capability를 Agent Team 구현으로 해석한다.

   ## 경계
   Controller는 Team을 직접 생성하지 않는다. 반드시 Registry를 거친다.

   ## 왜
   Team을 추가·교체할 때 Core 코드가 바뀌지 않게 하려고.
```

**2. 한 파일에 두 개 이상의 개념을 넣지 않는다.**

줄 수가 기준이 아니다. 다음 중 하나가 달라지면 다른 문서다.

- 소유자
- 변경 주기
- 승인·폐기 단위
- 독립적으로 링크할 필요
- `type`

**3. 자동 생성 문서를 손으로 고치지 않는다.**

생성물에는 front matter에 명시한다.

```yaml
automation:
  command: python dojo.py report
  manual_edit: false
```

손으로 고치면 다음 생성 때 사라진다. 고쳐야 하면 생성 스크립트를 고친다.

**4. 같은 사실을 두 문서에 적지 않는다.**

한쪽이 소유하고 다른 쪽은 링크한다. 값을 복사하면 한쪽만 갱신됐을 때 어느 쪽이 맞는지 알 수 없다.

여러 문서에 반복되는 값은 루트 `CLAUDE.md`의 기준 사실 표가 단일 출처다.

**5. `CLAUDE.md`에 지식을 넣지 않는다.**

`CLAUDE.md`는 **라우터**다. "어디를 봐야 하는가"만 적는다. 여기에 설명을 쌓기 시작하면 다시 거대 문서가 되고 계층 탐색이 무너진다.

예외는 기준 사실 표 하나다. 이건 검증된 관행이라 유지한다.

## 반드시 하는 것

**1. 주장에 근거 등급을 붙인다.**

`[실측]` `[외부]` `[추정]` `[미확보]` 넷 중 하나. 규칙은 [evidence-grades.md](evidence-grades.md).

**2. 불변식은 ID와 테스트 경로를 함께 적는다.**

```markdown
| ID | 불변식 | 판정 | 실행 위치 |
|---|---|---|---|
| `INV-CS-ACT-001` | Team은 side effect를 실행하지 않는다 | automated | `tests/architecture/test_team_has_no_side_effect.py` |
```

**3. 인접 문서로 링크를 건다.**

링크 없는 문서는 찾아지지 않는다. 모든 개념 문서에 `## 관계` 절을 둔다.

**4. 결정에는 기각한 대안을 함께 적는다.**

이유 없이 결정만 적으면 나중에 누군가 "이거 왜 이렇게 했지, 고쳐야겠다" 하고 되돌린다.

**5. 모르는 것은 `[미확보]`로 적는다.**

빈칸으로 두지 않는다. 무엇이 있어야 채워지는지 함께 쓴다.

## 문서 골격

### 개념 문서 (`type: concept`)

```markdown
## 책임      무엇을 담당하는가. 3줄 이내
## 경계      무엇을 하지 않는가. 책임보다 중요할 때가 많다
## 불변식    ID·판정·테스트 경로 표
## 관계      인접 문서 링크와 한 줄 설명
## 결정      왜 이렇게 설계했는가. 기각안 포함
## 구현      코드 위치만. 코드를 옮겨 적지 않는다
## 실패 사례  무엇이 잘못될 수 있고 그때 어떻게 되는가
```

### 결정 문서 (`type: decision`)

```markdown
## 맥락           어떤 상황에서 이 판단이 필요했는가
## 결정           한 문장
## 선택지와 이유   표. 채택 여부와 이유
## 결과           무엇이 바뀌는가. 무엇을 못 하게 되는가
## 근거           [실측] 코드 위치 · [외부] 출처
```

### `index.md`

목차가 아니다. **읽는 사람이 어디로 갈지 판단할 재료**를 준다. 최소한 이것들.

```markdown
## 읽기 순서    처음 오는 사람이 따라갈 순서
## 각 문서      문서별 "답하는 질문" 또는 "건드리면 위험한 것"
## 불변식       이 영역에 걸린 규칙
## 인접 영역    옆 영역으로 가는 링크
## 구현 위치    (코드 저장소인 경우)
```

## 문서가 커질 때

문서는 반드시 커진다. 규칙이 없으면 v8 계획서(1,466줄)와 같은 상태로 돌아간다.

### 예방 — 애초에 안 커지게

가장 효과가 큰 것 넷.

| 하지 말 것 | 대신 |
|---|---|
| 코드를 문장으로 옮겨 적기 | 위치만 가리킨다. `app/runtime/state/` |
| DDL·JSON·설정 전문 붙여넣기 | 실제 파일을 링크한다 |
| 긴 데이터 표를 손으로 유지 | 생성물로 빼고 `automation`을 붙인다 |
| 시점별 기록을 개념 문서에 쌓기 | 개념 문서엔 결론만. 기록은 `report` 문서로 |

**제일 큰 건 첫 줄이다.** 코드 설명을 빼는 것만으로 대부분의 비대화가 사라진다.

### 분할 트리거

줄 수만으로 자르지 않는다. 다음 중 하나라도 해당하면 자른다.

| 신호 | 판정 |
|---|---|
| 소유자가 둘로 갈린다 | **자른다** |
| 변경 주기가 다르다 (한쪽은 매주, 한쪽은 분기) | **자른다** |
| 독립적으로 링크하고 싶은 절이 생긴다 | **자른다** |
| `type`이 섞인다 (개념 + 결정 + 일정) | **자른다** |
| 목차를 봐야 원하는 절을 찾는다 | **자른다** |

줄 수는 보조 지표로만 쓴다.

```text
~300줄   정상
300~500  분할 검토. 위 신호 확인
500줄~   분할한다. 목록형이 아니면 예외 없음
```

300줄이 기준인 이유는 그 이상이면 에이전트가 한 번에 읽어야 할 양이 커져서 "필요한 것만 싸게 가져온다"는 목적이 깨지기 때문이다.

### 폴더 승격

파일 하나가 폴더가 된다. 이게 기본 패턴이다.

```text
business/unit-economics.md          (600줄이 됨)
        ↓
business/unit-economics/
   ├─ index.md          ← 결론과 지도. 원래 문서의 요약이 여기 남는다
   ├─ human-cost.md     ← 사람 원가 적산
   ├─ acop-cost.md      ← A-COP 원가
   └─ comparison.md     ← 비교와 결론
```

**`index.md`에 결론을 남기는 게 핵심이다.** 쪼갠 뒤 index가 목차만 되면 읽는 사람이 4개를 다 열어야 한다. 결론은 index에 두고 근거를 하위 문서로 보낸다.

승격할 때 지킬 것 셋.

1. **링크를 고친다.** `unit-economics.md`를 참조하던 문서를 전부 찾아 `unit-economics/index.md`로 바꾼다. CI 링크 검사가 잡아준다
2. **`log.md`에 적는다.** 파일이 사라지면 남의 링크가 깨진다
3. **미리 알린다.** 남이 같은 문서를 고치는 중일 수 있다

### 길어도 되는 문서

목록형은 쪼개면 오히려 불편하다. 예외로 둔다.

| 문서 | 왜 예외인가 |
|---|---|
| `glossary.md` | 용어를 찾을 때 한 파일에서 검색하는 게 빠르다 |
| `quality/invariants.md` | 불변식 카탈로그. 전체를 훑어야 의미가 있다 |
| `delivery/dod.md` | DoD 29항목. 체크리스트는 통으로 본다 |
| 자동 생성물 | 사람이 유지하지 않는다 |

예외는 front matter에 표시한다.

```yaml
size_exempt: true
size_exempt_reason: 용어 카탈로그. 검색 대상이므로 한 파일로 유지
```

**이유 없는 예외는 허용하지 않는다.** 예외 목록이 늘어나면 그 자체가 신호다.

### CI 검사

```text
300줄 초과 + size_exempt 없음  → 경고
500줄 초과 + size_exempt 없음  → 실패
size_exempt 있는데 이유 없음    → 실패
```

## 링크

저장소 안에서는 상대경로를 쓴다.

```markdown
[shared-state.md](shared-state.md)
[../quality/invariants.md](../quality/invariants.md)
```

저장소를 넘을 때도 상대경로를 쓴다. 워크스페이스 안에 나란히 있기 때문이다.

```markdown
[cs의 계약](../final_project_cs/wiki/teams/team-contract.md)
```

**예외는 `gPUteer` 하나다.** 별도 워크스페이스에 있어서 상대경로가 안정적이지 않다. GitHub 절대 URL을 쓴다.

## 언어

| 대상 | 언어 |
|---|---|
| 제목·본문 | 한국어 |
| 파일명·폴더명 | 영어 소문자 kebab-case |
| `tags` | 영어 소문자 kebab-case |
| 코드 식별자 | 영어 (코드 그대로) |

파일명을 영어로 하는 이유는 링크에 한글 URL 인코딩이 끼면 읽기 어려워지기 때문이다. 태그를 영어로 하는 이유는 조사·띄어쓰기 변형 없이 안정된 키가 필요해서다.

## OKF에서 뺀 것

이 표준은 OKF v0.2를 기반으로 하되 다음을 뺐다. 필요해지면 그때 넣는다.

| 항목 | 뺀 이유 |
|---|---|
| `stale_after` (문서 만료 시각) | 이관 직후 수백 개가 한꺼번에 만료로 뜬다 |
| `type` 13개 → 8개 | 늘리기는 쉽고 줄이기는 어렵다. 붙인 문서를 다 고쳐야 하므로 |
| 전역 ID 스킴 | 저장소 간 링크가 지금 수십 개다. 상대경로로 충분하다 |
| `attestation` | 공인 계산·receipt 구조가 이 프로젝트에 아직 없다 |
| OpenWiki CLI 자동 생성 | 이 저장소 가치의 상당 부분이 "미결정"과 "왜"인데 코드에서 안 나온다 |
