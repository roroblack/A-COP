그리고 2026년 7월 OpenWiki 0.2부터 Google Cloud 쪽에서 제안한 OKF(Open Knowledge Format) 를 채택하면서 이 아이디어가 꽤 명확한 규칙으로 정리됐다. GitHub +1

4. 결국 AI 문서는 Description 이 엄청 중요하다
사람용 문서에서는 제목이 중요했다면,
AI 문서에서는
Title + Description + Tags
가 매우 중요해진다.
안 좋은 예:
YAML
title: Controller
description: Controller 설명
거의 정보가 없다.
좋은 예:
YAML
title: Agentic Controller
description: Routes customer cases to Agent Teams, controls retry/replan and WAIT/RESUME, and coordinates Shared State updates.
tags:
- orchestration
- routing
- langgraph
- case-runtime
Agent가 검색할 때:
"I need to change retry behavior after state conflict"
라고 하면
retry , routing , case-runtime , Shared State
같은 의미적 연결이 생긴다.

여기서 중요한 건:

6. Source Code를 다시 적는 문서는 가치가 낮다
예를 들어 코드가:
Python
실행됨
class TeamRegistry :
def register ( self , team ):
...
인데 문서에:
Markdown
# TeamRegistry
TeamRegistry 클래스는 register 메서드를 가지고 있습니다.
register 메서드는 team을 등록합니다.
이건 AI한테 거의 쓸모 없다.
Agent가 코드 읽으면 바로 알 수 있으니까.
좋은 문서는:
Markdown
# Agent Team Registry
## Responsibility
Maps capabilities to Agent Team implementations.
## Architectural rule
The Controller must never instantiate a Team directly.
All Team resolution must pass through TeamRegistry.
## Why
This allows Agent Teams to be added or replaced
without modifying the Core Runtime.
## Invariants
- Team IDs must be unique.
- Team versions must be explicit.
- Disabled Teams must never receive new Cases.
- Registry lookup must not mutate Case State.
## Related
- /architecture/agentic-controller.md
- /architecture/team-contract.md
이런 것이다.
즉 AI 문서는:
What the code does
보다
Why it is designed this way / What must remain true
가 훨씬 중요하다.
7. 특히 Invariant 가 AI Coding Agent에게 엄청 중요하다
이건 실무적으로 상당히 가치가 있다.
예를 들어:
Markdown
## Invariants
1. Shared State is the source of truth for a Case.
2. Agent Teams may propose state changes but may not bypass CAS.
3. External actions must be idempotent.
4. Human-required actions must enter WAIT before execution.
5. Team modules must not directly depend on other Teams.
이런 규칙을 적는다.
그러면 Claude Code / Codex / Gemini CLI 등이 코드를 수정할 때:
refund-team에서 DB 직접 update 해버림
같은 실수를 할 가능성을 줄일 수 있다.
AI한테 필요한 것은 단순 구조 설명보다:
절대 깨면 안 되는 것
이다.

10. index.md 가 단순 목차가 아니다
OpenWiki/OKF에서 index.md 는 꽤 중요한 역할을 한다.
예:

This directory describes the runtime architecture.
## Core Runtime
- [Agentic Controller](agentic-controller.md)
Controls Case routing, retry, replan and lifecycle.

- [Context Broker](context-broker.md)

- [Team Contract](team-contract.md)
Defines the interface required by Agent Teams.
Agent는 이 파일 하나만 보고:

14. 코드가 바뀌면 Wiki도 업데이트된다

처음:
Bash
openwiki --init
하면 repository를 분석해서:
openwiki/
를 만든다.
그 뒤:
Bash
openwiki --update
하면 최근 변경사항을 확인한다.
개념적으로:
git diff
↓
변경된 코드
↓
영향받는 concept 확인
↓

↓

이런 구조다.
공식 OpenWiki는 Git 변경사항을 기준으로 관련 문서를 갱신할 수 있고, GitHub Actions/GitLab CI/Bitbucket Pipelines 등을 통해 자동 업데이트하는 흐름도 제공한다. GitHub +1

16. 최신 OKF는 여기서 한 단계 더 간다
이건 2026년 8월 기준 알아둘 만하다.
현재 Google Cloud의 OKF spec은 이미 v0.2 까지 나와 있고 단순 title/tag 수준을 넘어서 다음 같은 개념을 중요하게 본다.
Provenance
이 지식은 어디서 왔나?
Trust
얼마나 믿을 수 있나?
Freshness
아직 최신인가?
Lifecycle
현재 사용되는 지식인가?
Attestation
정해진 방식으로 검증됐는가?
왜냐하면 AI가 AI용 문서를 계속 작성하기 시작하면:
“이 Markdown이 사실이라는 보장이 뭐지?”
라는 문제가 생기기 때문이다. OKF v0.2는 바로 이 provenance, trust, freshness, lifecycle, attestation 을 보다 명시적인 지식 속성으로 다루고 있다. GitHub
이게 꽤 중요한 방향이다.

# Shared State
## Purpose
Customer Case의 공식 상태를 저장한다.
## Responsibility
- Case status
- owner
- evidence
- decisions
- open tasks
- approval state
- version
## Architectural Boundary
Agent Team은 Shared State를 직접 우회하여
별도의 공식 Case 상태를 만들 수 없다.
## Invariants
- Shared State is the Case source of truth.
- Every mutation increments `version`.
- Concurrent updates must use CAS.
- Conflict must return `CONFLICT`.
- Failed updates must never partially mutate state.
## Lifecycle
CREATED
→ RUNNING
→ WAITING
→ RUNNING
→ COMPLETED
## Relationships
- [Agentic Controller](agentic-controller.md)
- [Agent Team Contract](team-contract.md)
- [Case Lifecycle](../concepts/case-lifecycle.md)
## Implementation
- `src/runtime/state/`
- `src/runtime/repository/`
## Decision
Optimistic concurrency is used instead of global locking
because independent Agent Teams may operate concurrently.
## Failure Cases
### Version Conflict
Team A: version=12
Team B: version=12
Team A commit → version=13
Team B commit → CONFLICT
Controller reloads version=13 and performs retry/replan.
이걸 보면 인간도 이해하고, AI도 굉장히 잘 이해한다.
19. 결국 좋은 AI 문서 작성법을 한 문장으로 정리하면
기존 문서는:
“사람에게 시스템을 설명한다.”
였다면 AI용 문서는:
“Agent가 필요한 지식을 스스로 발견하고, 관계를 따라가고, 설계 의도를 보존하면서 행동할 수 있도록 지식 구조를 만든다.”
라고 보는 게 더 정확하다.
그래서 좋은 AI 문서는 단순히 글을 잘 쓰는 게 아니라:
Atomic Knowledge
+
Metadata
+
Hierarchy
+
Links
+
Invariants
+
Decisions
+
Provenance
+
Freshness
를 설계하는 작업이 된다.
그리고 나는 이 흐름이 RAG 다음 단계에서 꽤 중요한 Context Engineering 패턴 이라고 본다. RAG가 “필요한 원문을 어떻게 찾느냐”를 해결했다면 OpenWiki/OKF 계열은 “Agent가 지속적으로 사용할 지식을 어떤 형태로 보존할 것이냐” 를 다루기 시작한 셈이다. GitHub +1
특히 너처럼 여러 컴포넌트·Agent Team·Runtime 규칙이 얽힌 프로젝트 에서는 그냥 README를 잘 쓰는 것보다, AGENTS.md → index.md → concept 문서 → source code 식으로 계층을 만드는 방식이 훨씬 효과적이다.

맞아. 네가 말한 영상은 정확히 이거야. 제목도 **「사람이 아닌 에이전트를 위한 문서 작성법: OpenWiki 내부 공개」**로 확인된다. YouTube
그리고 내가 아까 설명한 방향이 큰 틀에서는 맞긴 했는데 , 네가 물은 건 일반적인 OpenWiki/OKF 철학보다 이 영상에서 말하는 “에이전트를 위한 문서를 어떻게 써야 하느냐”의 구체적인 방법론 쪽이 더 중심이야. 그러니까 아까 답변은 범위를 좀 넓게 잡았다.
영상의 핵심을 네 질문에 맞춰 더 정확히 잡으면 이렇다.
사람용 문서는 “읽기 편한 설명”이 중요하지만, Agent용 문서는 탐색성·구조·경계·연결성 이 더 중요하다.
문서를 하나의 긴 README로 쓰지 않고, 작은 주제 단위 + 명확한 index + 링크 구조 로 만든다.
Agent가 모든 문서를 처음부터 읽는 게 아니라 상위 index → 필요한 하위 문서 → 관련 코드 순으로 스스로 파고들게 한다.
코드에 이미 드러난 내용을 다시 설명하기보다는 설계 의도, 제약, 컴포넌트 간 관계, 무엇을 건드려야 하는지 를 적는 게 중요하다.
결국 OpenWiki는 그냥 “문서를 생성”하는 게 아니라 코드베이스 위에 Agent가 탐색할 수 있는 지식 지도(knowledge map)를 만드는 것 에 가깝다.
그래서 네가 영상 제목 보고 생각한 “AI가 잘 이해하도록 문서를 쓰는 새로운 작성법” 이라는 이해가 맞아. OpenWiki 자체가 그 방법을 실제 repo 문서화 시스템으로 구현한 사례고.
원하면 내가 이 영상 내용 자체를 처음부터 끝까지 기준으로
① 영상 핵심 주장 → ② 기존 README/CLAUDE.md와 차이 → ③ OpenWiki 실제 구조 → ④ AI 문서를 잘 쓰는 규칙 10개 → ⑤ A-COP에 그대로 적용하면 어떤 폴더/문서 구조가 되는지
순서로 다시 제대로 분석해줄게.

① Self-contained fragments

metadata

가 중요하다.
③ Documentation = Memory
OpenWiki 팀은 애초에 documentation 자체를 최종 목표로 보는 게 아니야.
발표 시작에 말했듯이 그들의 더 큰 thesis는:
General-purpose memory가 Agent의 다음 중요한 영역이다.
이고,
Codebase Wiki는 그걸 실험하기 좋은 첫 번째 domain이라는 거야.
즉 개념적으로:
Codebase
↓
OpenWiki
↓
persistent structured memory
↓
Coding Agent
다.
그리고 이 관점에서 보면 OpenWiki는 “자동 문서화 CLI”라기보다 Coding Agent용 외부 장기기억 계층의 초기 형태 라고 보는 게 훨씬 정확해.
