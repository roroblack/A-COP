# 구현 지시 — A-COP 파트별 진행 브리핑 문체·UI 정리

## 0. 대상 파일

`program/briefing/A-COP_파트별_진행_브리핑.html` (단일 파일, HTML+인라인 CSS,
외부 리소스·폰트·스크립트 없음 — 그대로 유지).

## 1. 하지 말 것 (절대 금지)

- 이 파일이 보고하는 **사실·수치·팀 이름·상태(완료/진행중/보류)를 바꾸지 않는다.**
  이 파일은 실제 작업 상태를 그대로 반영한 문서다 — 문장을 다듬다가 의미를
  바꾸면 안 된다. 애매하면 원문 의미를 그대로 두고 표현만 다듬는다.
- 다른 파일은 건드리지 않는다. 이 파일 하나만.
- 색상 토큰(`--bg`/`--accent`/`--done`/`--warn`/`--critical`/`--idle` 등)의
  값 자체는 바꾸지 않는다 — 라이트/다크 테마 양쪽에 이미 맞춰 둔 값이다.

## 2. UI 버그 — 찾아서 고친다

레이아웃이 좁은 화면(모바일 폭 375px 안팎)에서 박스를 뚫고 나오는 문제가
최소 1건 있었다(`ul.flow li` 안의 연속된 `<code>` 인라인 요소) — 이미
`overflow-wrap:anywhere`로 1차 조치했지만 **같은 종류의 문제가 다른 곳에도
있는지 전체를 다시 훑어라.** 특히:

- 표(`.stats` 그리드), 카드(`.team`), 콜아웃(`.callout`) 안에 긴 문자열
  (`code.inl` 여러 개 연속, 긴 URL, 긴 영문 식별자)이 있는 자리
- `overflow-x` 가 body 전체로 새는 곳이 없는지(가로 스크롤은 개별 컨테이너
  안에서만 나야 한다)
- 라이트/다크 두 테마 모두에서 대비가 충분한지(특히 `.pill--*`, `.callout`)

실제로 뷰포트를 좁혀서(375px, 768px, 1280px 상당) 렌더링을 확인하고 고쳐라
(브라우저 도구가 없으면 CSS 로만 방어적으로 처리 — `overflow-wrap`,
`min-width:0`, `word-break` 를 필요한 곳에 일관되게 적용).

## 3. 문체 — ★사람이 읽기 편하게 다듬는다 (최우선)

이 문서는 팀/이해관계자에게 보여줄 **진행 상황 브리핑**이다. 지금 문체가
군데군데 실행 로그·커밋 메시지를 그대로 붙여넣은 것처럼 딱딱하고,
코드베이스를 잘 모르는 사람은 바로 이해하기 어려운 부분이 있다.
**목표 독자는 이 코드를 직접 안 본 사람이다** — 함수명·파일 경로를
아는 게 전제가 아니라, "그래서 뭐가 됐고 뭐가 남았는지"가 한 번 읽고
바로 들어와야 한다. (참고: 같은 폴더의 `A-COP_브리핑_v8_쉬운설명.html`
이 이런 "쉬운 설명" 버전의 기존 사례다 — 같은 정신으로 다듬어라. 단,
그 파일을 읽거나 베끼지는 않는다 — 이 문서 자체를 그 수준으로 고치는 것이다.)

다음 기준으로 다듬어라:

- 같은 문장 구조(예: "~을 확인했다", "~를 추가했다")가 리스트 안에서
  기계적으로 반복되면 자연스럽게 변주한다.
- 한 문장에 정보가 과하게 몰려 있으면(쉼표로 3개 이상 절이 이어지는 경우)
  나눈다.
- 약어·코드 식별자(`voc_store_manager` 등)는 처음 등장할 때는 그대로 두되,
  주변 설명 문장이 매끄럽게 읽히도록 조사·어미를 다듬는다.
- 존댓말/반말 톤은 지금처럼 평서형(개조식·보고체)으로 통일 유지한다 —
  갑자기 존댓말이 섞이지 않게 한다.
- 각주(★ 표시, 콜아웃)의 어조도 나머지 본문과 톤이 어긋나지 않게 맞춘다.

## 4. 완료 조건

- [ ] 375px/768px/1280px 상당 폭에서 가로 스크롤·요소 잘림·박스 이탈이 없다
- [ ] 라이트/다크 두 테마 모두 텍스트가 배경과 대비되어 읽힌다
- [ ] 사실·수치·팀명·상태값이 원본과 동일하다(비교해서 확인)
- [ ] 문체가 리스트 안에서 기계적으로 반복되지 않는다
- [ ] 결과를 이 파일에 그대로 덮어쓴다(새 파일 만들지 않는다)

작업 끝나면 무엇을 고쳤는지 3~5줄로 짧게 요약해서 출력해라(별도 리포트
파일은 안 만들어도 된다 — 이 작업은 너무 작아서 리포트가 과하다).
