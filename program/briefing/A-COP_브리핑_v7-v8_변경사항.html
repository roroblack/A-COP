1. Team 구조 개편 — 이름만 바뀐 게 아니다

Local Team 3개 + Remote 1개 구조가, "CS Pack 확정축 2개 + Commerce Ops 연계축 4개" 구조로 바뀌었다.

v7 — Local 3 + Remote 1
  • Billing Team
  • Technical Team
  • VOC Team
  • (Remote) Catalog & Verification Team
v8 — 확정축 2 + 연계축 4
  • CS Pack (10주 확정 착수)
    VOC & Store Manager
    Response Generation & Review
  • Commerce Ops 연계축 (일정 따라 조정)
    Procurement + Order & Payment
    Fulfillment & Logistics
    Return & Refund
    Catalog & Verification (A2A Remote)
본문 내 "VOC Team 경계" 설명, pill 목록, 위임 예시 문장 전부 새 이름으로 일괄 교체됨
💬 쉬운 설명 v7은 "Billing(요금)·Technical(기술)·VOC(피드백)" 3개 팀이 CS 문의만 나눠 처리하는 구조였습니다. v8은 이걸 두 그룹으로 다시 나눕니다. ① CS Pack(무조건 10주 안에 만드는 것) — 문의를 받아 분류·집계하는 "VOC & Store Manager"와, 답변을 실제로 만들고 근거를 검증하는 "Response Generation & Review". ② Commerce Ops 연계축(검증 쇼핑몰이 정해지는 대로 맞춰 넣는 것) — 발주, 배송, 반품·환불, 상품 검증까지 총 4개 팀. 즉 "CS만 하던 팀"에서 "CS는 확정하고, 쇼핑몰 실무(주문·배송·반품)는 상대가 정해지는 대로 붙이는" 구조로 바뀐 겁니다. ※ Response Generation & Review가 새 정식 Team으로 승격된 것으로 보이는데, 이건 DoD가 28→29개로 늘어난 것과 맞물려 보입니다(29번이 "Response Generation & Review 검증" 항목).

2. 도메인 팩 다이어그램·쉬운설명 재정의

"10주 구현 vs vision(나중 계획)"이라는 이분법이, "CS Pack 확정축 vs Commerce Ops 연계축(검증 쇼핑몰 일정에 맞춰 조정)"으로 바뀌었다.

v7 "지금 10주에 만드는 것은 고객센터용 묶음(CS Pack)이고, 쇼핑몰 운영용 묶음(Commerce Ops Pack)은 나중 계획(vision)입니다."
v8 "고객 문의를 맡는 VOC & Store Manager와 답변을 만들고 검토하는 Response Generation & Review를 CS Pack의 확정축으로 삼습니다. 발주·주문·결제, 물류, 반품·환불, 상품 검증은 Commerce Ops 연계축으로 나누어 검증 쇼핑몰과 일정에 맞춰 조정합니다."
"나중에 할 수도 있는 것" → "검증 쇼핑몰 연계 여부에 따라 조정되는 것"으로 위상이 바뀜
💬 쉬운 설명 v7의 표현은 "Commerce Ops Pack은 vision(먼 미래 계획)"이라 심사 자리에서 "그럼 지금은 왜 얘기하냐"는 질문을 받기 쉬운 표현이었습니다. v8은 이걸 "검증 쇼핑몰(우리와 실제로 연동할 파트너 쇼핑몰)이 정해지는 시점과 범위에 맞춰 진행한다"로 바꿨습니다. 똑같이 "지금 당장은 안 만든다"는 뜻이지만, "언제·왜 만들지 조건이 이미 정해져 있다"는 느낌으로 바뀐 겁니다 — 계획이 없는 게 아니라 외부 변수(파트너 확정)에 달려있다는 걸 명확히 한 것으로 보입니다.

4. "버리는 순서"(fallback) 갱신

일정이 빠듯할 때 뭘 먼저 포기할지의 순서도, 새 팀 구조에 맞춰 다시 짜였다.

v7 ① Graph 비교 실험 → ② A2A Remote PoC → ③ MCP tool 축소

지키는 것: Team 2개 + 평가 하니스
v8 ① Graph 외부 Adapter 비교 → ② A2A Remote 확장 시나리오 → ③ MCP tool 추가와 Commerce Ops 확장 → ④ 화면 장식과 추가 Team

지키는 것: CS Pack 확정축 + 운영 UI + 평가 harness
💬 쉬운 설명 "버리는 순서"는 시간이 부족해질 때 뭐부터 포기할지 미리 정해둔 우선순위입니다. v7에서는 "MCP tool 축소"가 마지막 카드였는데(이미 만든 기능을 줄인다), v8에서는 "MCP tool 추가와 Commerce Ops 확장 자체를 안 한다"로 바뀌었습니다. 즉 v7은 "만든 걸 줄인다"는 방어였고, v8은 "애초에 확장축(Commerce Ops) 쪽은 여유 있을 때만 손댄다"는 더 보수적인 방어로 바뀐 겁니다. 대신 반드시 지키는 것도 명확해졌습니다 — CS Pack 확정축, 운영 UI, 평가 harness 이 세 가지는 무슨 일이 있어도 끝까지 지킵니다.
