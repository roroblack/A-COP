Team 하나의 내부 — 여섯 팀이 똑같이 돈다

가드 셋을 다 본다. 하나라도 걸리면 그 결과를 그대로 돌려주고, 셋 다 통과하면 _guard() 가 None 을 돌려줘 execute() 가 이어진다. 순서에 뜻이 있다 — 남의 일이면 판단하기 전에 넘기고, 못 하는 일이면 시작하지 않으며, 근거가 깎였으면 확정 답을 만들지 않는다.

TravelTeamBase는 execute를 가로채지 않으며, 각 Team이 공통 부품을 직접 호출한다. 가드는 순서대로 검사하고 첫 실패에서 반환한다. 제공 원문이 _result 구현 중간에서 끝나므로, 판정 뒤 네 갈래는 과제에 명시된 계약을 표시한다. 도구 예외를 특정 반환 분기로 연결하는 처리는 원문에서 확인할 수 없어 생략한다.

팀별 — 실제 구현은 이렇게 다르다

Activity

Activity만 기상 민감 활동에 read.weather를 호출하며, 전용 _weather_note()는 46줄이다. 취소·실행 가능 여부는 RESPOND로 답하고 변경 제안은 WAIT_FOR_APPROVAL로 반환한다.

Dining

예약의 place_id로 장소를 조회하고 확인 시각을 검증한다. check_conditions는 아이 동반·할랄·채식 등 동행 조건을 대조하며, 모르는 조건은 모름으로 남긴다.

Mobility

Mobility만 select_capability(intent, input_text) 훅으로 사건 표지를 검사한다. 세 capability는 같은 실행 경로에서 여유 시간과 이동 시간을 계산하고 RESPOND로 답한다.

Booking Handoff

verify는 공급자 상태와 내부 기록을 대조하며, 불일치하면 사람의 확인이 필요하다고 답한다. 변경·취소 준비는 제안을 만들고 WAIT_FOR_APPROVAL을 반환한다.

Lodging / Flight

LodgingTeam과 FlightTeam은 _LockedBookingTeam의 실행 구현을 공유한다. read.booking만 호출하고 예약을 잠긴 상태로 취급하며, 일정 조정 대상이 아니라고 RESPOND로 답한다.
