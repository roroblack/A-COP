01

공유 인프라와 6개 팀의 데이터 흐름

모든 팀이 같은 파이프라인(Controller → Registry → Team → ActionProposal → 승인)을 통과한다. 갈라지는 지점은 "무엇을 근거로 쓰는가"다 — 정책 RAG를 쓰는 팀, 케이스 유사도 검색을 쓰는 팀, DB 사실조회만 쓰는 팀, 아직 데이터가 없는 팀으로 나뉜다.

03

임베딩 모델 — 팀마다 다른가?

아니다. 플랫폼 전체가 임베딩 모델 하나를 공유한다.

지금 구조에서 팀별로 다른 임베딩 모델을 쓰는 건 선택지가 아니라 위반이다 — pgvector DDL이 vector(1536)로 고정돼 있고, 다른 차원의 모델을 섞으면 같은 테이블에서 코사인 유사도 계산 자체가 깨진다. 모델을 바꾸려면 DDL과 기존 적재분을 전부 함께 다시 만들어야 한다.

모델
OpenAI text-embedding-3-small
차원
1536
정책 코퍼스
25문서 · 306청크 (Return&Refund, Procurement, Fulfillment, Response Review가 knowledge_scope로 필터링해 공유)
케이스 유사도 인덱스
같은 모델, 별도 벡터 공간 (VOC 전용)
임베딩이 필요 없는 팀 기능
DB 사실 조회(read.order 등), 분류기(fine-tuned 모델은 임베딩이 아니라 분류 헤드를 씀)

즉 "팀마다 다른 임베딩 모델이 필요한가"의 답은 — 아니다, 필요한 건 팀마다 다른 knowledge_scope 필터와 다른 데이터 소스이지, 다른 임베딩 모델이 아니다. VOC의 감성분류·GEN의 톤 생성은 애초에 임베딩을 안 쓴다(LLM 완결·분류기 완결이다) — 이걸 "임베딩이 필요"라고 뭉뚱그리면 안 된다.
