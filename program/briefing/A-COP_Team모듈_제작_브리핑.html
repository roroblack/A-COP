Team 모듈 아키텍처 — 무엇으로 이루어지고 어떻게 만드나

2026-09-09 · 골격은 코드 AST 실측 · 규칙은 계획서 v10 §5 · 2026년 다중 에이전트 설계 패턴 연구와 대조

한 줄

Team 은 선언(manifest) · 주입(도구) · 단일 진입점(execute) · 근거(evidence) 넷으로 이루어진다. 이 넷은 협상 대상이 아니다 — 여섯 팀 전부가 100% 갖고 있고, Registry·Controller·평가 하네스가 전부 이 모양을 전제로 돈다.

1. Team 하나의 해부

class XxxTeam:
    manifest = TeamManifest(...)            # ① 선언 — 코드 밖에서 읽는 계약
    def __init__(self, tools): ...          # ② 주입 — 도구를 스스로 만들지 않는다
    async def execute(task) -> TeamResult:  # ③ 단일 진입점
        ...
    def _evidence(...): ...                 # ④ 근거를 붙이는 자리

① 선언 — manifest 가 하는 일

Team 의 능력과 권한을 코드 밖에서 읽을 수 있게 만든다. Registry 가 이걸 보고 라우팅하고, 도구 호출을 막고, 화면에 표시한다.

필드무엇을 정하나누가 읽나
team_id이 팀의 식별자Registry 등록 · config/project.yaml
capabilities이 팀이 할 수 있는 일의 목록 Registry 가 task 의 capability 가 여기 있는지 본다
accepted_case_types어떤 Case 를 맡나 Registry 라우팅. 비우면 Case 를 직접 안 받는 팀이 된다
allowed_tools쓸 수 있는 도구 — 권한 반경 Registry 가 이 밖의 호출에 ToolNotAllowed
knowledge_scopeRAG 가 어느 문서군을 넘기나Context Broker
required_context무엇이 있어야 판정할 수 있나Context Broker
max_steps반복 상한 ★지금은 아무도 안 읽는다 — §5 참조
default_capability고를 수 없을 때의 기본Registry

② 주입 — 도구를 스스로 만들지 않는다

Team 은 DB 커넥션도 LLM 클라이언트도 직접 만들지 않는다. 조립 지점(app/composition.py)이 만들어서 __init__ 으로 넣어 준다.

def __init__(self, tools: ReadToolbox, llm: Any | None = None) -> None:
    self.tools, self.llm = tools, llm

이래서 Team 을 테스트할 때 가짜 도구를 넣을 수 있고, 원격(A2A)으로 뺄 수도 있다.

③ 단일 진입점 — execute() 의 다섯 칸

1. 가드    if task.team_id != self.manifest.team_id:      → handoff
           if task.capability not in ...capabilities:     → escalated
           if task.context.degraded:                      → escalated

2. 준비    seen: set[str] = set()                  # 같은 도구·같은 인자 재호출 차단
           evidence = list(task.context.evidence)  # 근거 누적 시작

3. 조회    self.tools.call(name, task.context, args, task.allowed_tools, seen)
                                                   ↑ 여기서 권한이 강제된다

4. 판단    ★도메인 규칙은 여기에만 있다.
           계산으로 판정한다 — 시간 충돌·기한·인원·조건 누락에 LLM 을 부르지 않는다

5. 반환    TeamResult(outcome, next_action, evidence, decisions, [ActionProposal])

★가드 셋을 다 넣는다. 실측하면 지금 이게 균일하지 않다 — degraded 5/6 = 83% · capability 4/6 = 67% · team_id 1/6 = 17%. 잘못 배선된 task 가 와도 다섯 팀은 조용히 처리한다.

④ 근거 — 왜 이게 4대 요소인가

여섯 팀 전부가 _evidence 를 갖는다(6/6 = 100%). 답을 만드는 함수보다 근거를 붙이는 함수가 먼저 공통이 됐다.

Evidence(evidence_id, source_type, source_id, claim, value, confidence, observed_at)

모든 핵심 주장에 붙는다. 근거를 못 대면 답을 만들지 않고 waiting_input 이나 escalated 로 간다.

2. Team 이 반환하는 것 — TeamResult

outcome            completed · escalated · handoff · failed
next_action        respond · wait_for_input · wait_for_approval · call_tool
                   · handoff · escalate · continue
answer             판정 결과. ★고객 문장이 아니라 판정이다
evidence           [Evidence]  — 무엇을 근거로 그렇게 판정했나
decisions          [{...}]     — 판정의 구조화된 형태
action_proposals   [ActionProposal] — ★제안까지만. 실행하지 않는다
failure_code       왜 못 했나
warnings           사람이 봐야 할 것

★ActionProposal 이 이 아키텍처의 안전 장치다. Team 은 환불·예약변경·취소를 실행하지 않는다. 제안을 만들고, 사람 승인 (action:approve scope)을 거쳐 코어가 실행한다. 제안에는 idempotency_key 가 붙어 같은 요청 10회 → side effect 1회가 테스트로 증명된다.

3. 여행 Team 이 갖는 셋 — 검증 · 감시 · 재계획

무엇어디서 도나LLM
① 검증 규칙이 예약이 지금 성립하는가 Team — execute() 4칸 안 쓴다. 계산으로 판정
② 감시 소스무엇이 바뀌었는지 본다 코어 스케줄러 — 다음 확인 시점에 Case 를 연다 (TriggerSource.SCHEDULE). Team 은 폴링하지 않는다 안 쓴다
③ 재계획 후보대신할 것을 찾는다 Team 여기서만 쓴다. 생성물은 ①을 다시 통과해야 통지된다

★ 후보의 공통 형태 — 이것만 맞추면 코어가 조립한다

{
  "kind":         "activity" | "dining" | "mobility",  # ★코어는 이걸 안 본다
  "start":        ISO8601,
  "end":          ISO8601,
  "place":        {"name", "lat", "lon"},
  "cost":         {"amount", "currency"},
  "locked":       bool,            # 잠긴 예약이면 코어가 안 건드린다
  "evidence":     [Evidence],
  "confirmed_at": ISO8601 | null   # null 이면 "미확인"으로 표시된다
}

코어는 시간이 겹치는지 · 이동 여유가 되는지 · 예산을 넘는지만 본다. "골프인지 식당인지" 를 알 필요가 없어서 도메인을 모른 채 조립할 수 있다.

★이 형태가 정해져야 ③을 만들 수 있다. 지금은 초안이지 계약이 아니다.

4. 2026년 다중 에이전트 설계 패턴과의 대조

2026-01 arXiv 논문(2601.03328)이 정리한 다섯 패턴을 우리 구조와 맞춰 보면 다섯 중 넷이 이미 구현돼 있다. 우연이 아니라 같은 실패를 피하려다 같은 모양이 된 것이다.

연구가 말하는 패턴막는 실패우리 구조상태
Role/Capability Declaration
역할·능력을 명시 선언		 에이전트가 자기 범위 밖 일을 한다 TeamManifest.capabilities · accepted_case_types 6/6 = 100%
Tool Permission Scoping
도구 접근을 좁힌다		 의도치 않은·위험한 동작 allowed_tools + Registry 의 ToolNotAllowed. 팀 쌍 14/15 = 93% 가 서로 다른 도구 집합 강제됨
Orchestration vs Autonomy
조정자가 흐름을 쥔다		 에이전트가 서로를 부르며 흐름을 잃는다 Controller 가 시작·실행·반영을 쥔다. Team 은 서로를 호출하지 않는다 — 넘길 때도 outcome="handoff" 로 코어에 돌려준다 구현됨
Human Approval Boundaries
사람 승인 경계		 되돌릴 수 없는 실행 ActionProposal + action:approve scope + 승인 직전 DB 재대조(proposal_guard) 구현됨
Output Verification
출력을 검증하고 쓴다		 환각 · 사실 오류 제안의 식별자·금액을 DB 와 대조해 실행 전 차단. 인용 없는 주장 금지 부분 — 아래

★ 연구가 짚은 것 중 우리가 아직 안 지키는 것 둘

1. 반복 상한(loop divergence)이 강제되지 않는다. 연구는 "제약이 약한 에이전트는 같은 문제를 무한히 되풀이한다 — 최대 반복 횟수나 명시적 종료 조건을 강제하라" 고 한다. 우리는 max_steps 를 선언은 하는데 실행 경로에서 아무도 읽지 않는다(실측: contracts.py 정의 · routes.py 화면 표시 · introspection 뿐).

지금 막는 것   seen 집합 — 같은 도구를 같은 인자로 다시 부르면 ToolLoopExceeded
안 막는 것     같은 도구를 다른 인자로 계속 부르는 것. 상한이 없다

여행에서는 ③ 재계획이 LLM 을 쓰므로 후보를 계속 만들어 내는 경로가 생긴다. Team 을 만들 때 단계 수를 세고 max_steps 를 넘으면 escalated 로 끝낸다.

2. 검증 단(Reflection)이 파이프라인에 안 붙어 있다. 연구의 Output Verification 은 "생성한 것을 다른 주체가 검증한다" 인데, 우리 검증 팀은 설정에서 꺼져 있고 평가 경로에도 안 탄다. 그 결과 평가에서 답변이 216행 중 9종(4.2%) 뿐이고 47.2% 가 빈 문자열이었다 — Team 의 내부 판정 문구가 그대로 고객 답변 자리로 나갔다.

★여행에서 이 자리를 각 Team 안의 ③ 뒤에 둔다(v10 §5 — 생성한 대안은 판정을 다시 통과해야 통지된다). "통과했다"를 테스트로 증명하지 않으면 같은 일이 반복된다.

5. 팀별 — 무엇을 만드나

ActivityMVP 필수

대상 — 골프(티타임) · 한강 수상 액티비티 · 겨울 스키·눈썰매. 우천 위약금 규정이 문서로 있고 예약 시각이 고정인 레저.

manifest

                     "refund.calculate"]
accepted_case_types ["activity"]
allowed_tools       ["read.booking", "read.policy", "read.place", "read.weather"]

default_capability  "activity.check_cancelable"

① 검증 (계산)

  • 취소 기한 — 예약 시각 − 현재 시각 대 규정 시간
  • 인원이 정원을 넘는가 · 운영일·운영시간 안인가
  • 날씨 조건 — 규정에 기준 시각이 있는 경우만(예: 티타임 2시간 전 강수량)
  • 위약금율 — 남은 시간 구간별 표. 모르면 금액을 만들지 않는다

② 감시 · ③ 재계획

기상청 초단기예보 · 운영 공지(코어 스케줄러가 Case 를 연다) / 같은 시간대 대체 · 날짜 이동 · 환급 안내(LLM → ① 재통과)

6. 만드는 순서

  1. 후보 공통 형태를 계약으로 확정 (§3) — 없으면 ③을 만들 수 없다
  2. manifest 를 먼저 쓰고 config/project.yaml 에 등록 — 로직 없이 Registry 해석이 되는지 먼저 본다
  3. 골격 다섯 칸 (§1 ③) — 가드 셋을 다 넣는다
  4. ① 검증 규칙만 구현. LLM 없이 계산으로. 여기까지가 뼈대
  5. 테스트 — 판정 갈래마다 하나씩. 「모름」 갈래를 반드시 포함한다
  6. ③ 재계획(LLM) → 생성물이 ①을 다시 통과하는지 테스트로 증명
  7. ② 감시 — 코어 스케줄러 쪽이라 Team 코드 변경이 없다

★4번까지 하면 팀 하나가 돈다. ③·②가 없어도 검증은 성립한다.

7. 자주 밟는 함정

함정어떻게 나타나나어떻게 피하나
「모름」을 「없음」으로 읽는다 제한을 확인 못 했는데 "정책 근거상 가능합니다" 라고 답한다 NULL = 모름. 확인 못 한 것은 확인 못 했다고 답한다. 하나라도 모르면 전체를 「모름」으로 둔다
문구 판정이 너무 넓다 "취소해야 하나요?"(고민)를 취소 요청으로 잡는다 요청을 분명히 밝히는 문구만. 신호 없으면 None → 기본 동작
답변을 하드코딩한다 내부 판정 문구가 그대로 고객 답변이 된다 Team 은 판정을 내고, 고객 문장은 통지 단계에서 만든다
선언만 하고 안 쓰는 도구 allowed_tools 에 있는데 호출이 0회 실제로 쓰는 것만 적는다. 안 쓰면 지운다
선언만 하고 안 지키는 상한 max_steps 를 아무도 안 읽는다 단계를 세고 넘으면 escalated. §4 참조
테스트가 실제 경로를 안 탄다 검증 단계를 건너뛴 채 통과한다 두 단계가 실제로 두 번 불렸는지를 단언한다

8. 시작 전에 정해야 하는 것

  • 후보 공통 형태 — §3 은 초안이다. 확정 전에는 ③을 만들지 않는다
  • 반복 상한 강제 — max_steps 를 실행 경로에서 읽게 한다. 지금은 선언만 있다
  • 검증 단을 어디에 두나 — 각 Team 의 ③ 뒤. 탔는지를 테스트로 고정한다
  • 계약 포장을 공용 기반으로 뺄지 — 빼면 가드가 6/6 으로 균일해진다. 지금은 같은 코드가 315줄 복붙돼 있다
  • Activity 의 경계 — 실내 티켓류를 넣으면 감시 소스가 둘로 갈린다 (기상청 vs 공연 취소 공지). [미확보] 수요 비교가 없다

Reliability without Validity: A Systematic, Large-Scale Evaluation of LLM-as-a-Judge Models
arXiv:2606.19544 · 2026-06		 9개 제공사 21개 채점자 · 118회 · 약 54만 판정. ① 정확일치와 Cohen's kappa 사이 격차가 보편적(MT-Bench 기준 33~41%p) ② 일관성–편향 역설 — 재현성 0.95 이상인 채점자가 위치 편향 0.10 이상을 함께 가진다 ③ 장황함 편향은 이제 작다(21개 전부 0.011 미만) ★내 가설 하나가 약해졌다 — 아래

★ 논문이 내 설명 하나를 지웠다 — 그게 더 좋은 소식이다

평가에서 고정 워크플로 군이 우리 군을 모든 축에서 이겼다. 나는 두 설명을 놓고 있었다.

가설 A  채점자가 긴 산문을 선호한다 (장황함 편향)
가설 B  우리 군이 내부 판정 문구를 그대로 답변 자리에 냈다 — 파이프라인 마지막 단이 빠졌다

논문이 A 를 약하게 만든다 — 2026년 채점자들의 장황함 편향은 0.011 미만으로, 2023년 연구 대비 한 자릿수 낮다. 그리고 우리 실측이 B 를 직접 지지한다:

서로 다른 답변    216행 중 9종 = 4.2%
빈 문자열         102행 = 47.2%
평균 길이         19자

이건 "짧아서 진 것" 이 아니라 고객 답변이 아예 안 만들어진 것이다. Team 은 판정을 내고, 고객 문장은 그다음 단계가 만든다 — 그 단계를 빼면 평가가 그것을 정직하게 잡아낸다.

일치도를 잴 때 미리 알아 둘 것. 위 논문 ①이 말하는 정확일치와 kappa 의 격차 33~41%p 는 우리 일치도 측정에도 그대로 온다. "몇 % 가 같았다" 는 높게 나오고 kappa 는 훨씬 낮게 나온다 — 그게 정상이고, 낮다고 채점자를 버릴 이유가 아니다.

★그리고 분산이 0 인 축은 kappa 를 못 만든다. 채점자가 한 축에 늘 같은 값을 주면 그 축의 kappa 는 1.0 아니면 0.0 두 값만 나온다 — 축을 만들 때 변별하는지부터 확인한다.
