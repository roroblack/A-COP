A-COP 아키텍처 브리핑

2026-09-09 · 코드 AST 실측 + 계획서 v10 · 숫자는 문서가 아니라 코드를 세어 냈다

한 줄

이 시스템의 뼈대는 「선언 · 경계 · 근거」 셋이다. 도메인이 쇼핑몰에서 여행으로 바뀌어도 코어는 그대로인 이유가 이 셋이 도메인을 모르기 때문이다.

1. 두 층으로 나뉜다

┌─────────────────────────────────────────────────────────────┐
│  코어 (basement) — 도메인을 모른다                            │
│  app/core · app/domain · app/application                    │
│                                                              │
│   계약        TeamManifest · TeamTask · TeamResult           │
│   생명주기    상태 12종 · 전이 25 · transition_case() 한 문   │
│   Registry    누가 어떤 Case 를 맡는지, 어떤 도구를 쓸 수 있는지│
│   Context     12,000 토큰 예산 · 넘치면 degraded 를 켠다       │
│   Controller  시작(커밋) → Team 실행 → 결과 반영(새 트랜잭션)  │
│   Outbox      발행 중복 방지 · at-least-once                  │
└───────────────────────┬─────────────────────────────────────┘
                        │  ↑ Team 은 코어를 안다 (6/6 = 100%)

┌───────────────────────┴─────────────────────────────────────┐
│  모듈 (도메인 자리) — 여기서만 업무 어휘를 안다                 │
│  app/modules/**  ·  config/project.yaml                     │
│                                                              │
│   Team 6종     manifest 선언 → Registry 등록 → execute()      │
└─────────────────────────────────────────────────────────────┘

★이 경계는 말이 아니라 테스트가 지킨다.

  • tests/contract/test_core_isolation.py — 코어가 app.modules 를 import 하면 실패
  • tests/architecture/test_basement_is_domain_free.py — 코어에 업무 어휘가 들어오면 실패
  • tests/contract/test_team_tool_discipline.py — Team 이 인프라를 직접 부르면 실패

도메인을 여행으로 갈아끼울 때 코어를 다시 검증하지 않아도 되는 근거가 이 셋이다.

2. Team 의 공통 골격 — 6개를 AST 로 세었다

manifest 선언6/6100% — 코드 밖에서 읽는 계약
도구 주입 __init__6/6100% — 스스로 만들지 않는다
단일 진입점 execute()6/6100% — 전부 async
_evidence 누적6/6100% — 근거를 붙이는 자리

★_evidence 가 100% 인 게 이 도메인의 성격을 그대로 보여준다. 답을 만드는 함수보다 근거를 붙이는 함수가 먼저 공통이 됐다 — "근거 없으면 답하지 않는다"가 코드 모양으로 굳은 것이다.

execute() 의 표준 흐름

1. 가드    capability ∈ manifest.capabilities ?      4/6 = 67%
           context.degraded ?                        5/6 = 83%
               → 걸리면 outcome="escalated"
2. 준비    seen: set()  (같은 도구 재호출 차단)        5/6 = 83%
           evidence = list(task.context.evidence)     6/6 = 100%
3. 조회    self.tools.call(name, …, task.allowed_tools, seen)
4. 판단    순수 분기 — 여기서만 도메인 규칙을 쓴다
5. 반환    TeamResult(outcome, next_action, evidence, [ActionProposal])

★가드가 팀마다 다르다. team_id 가드는 1/6 = 17% 뿐이다 — 잘못 배선된 task 가 와도 다섯 팀은 조용히 처리한다. 계약 포장을 app/core/team_base.py 로 올리면 이게 6/6 으로 균일해진다. 지금은 같은 코드가 315줄 복붙돼 있어, 여행으로 옮기면 그대로 복제된다.

6개 중 5개(83%)가 LLM 을 한 번도 부르지 않는다. DB 를 읽고 if/else 하는 순수 함수다. "Agent Team" 이라는 이름이 실제보다 크게 들리고, 새 도메인을 설계할 때 "여기도 에이전트를 만들어야 하나" 하는 착각을 부른다.

그럼 왜 나누나 — 지능이 아니라 권한 반경 때문이다.

allowed_tools 가 서로 다른 팀 쌍     14/15 =  93%
knowledge_scope 가 서로 다른 팀 쌍   15/15 = 100%
7개 도구 중 한 팀만 쓰는 것          3개 (read.account · read.return · read.shipment)

합치면 모든 팀이 도구 7종과 전체 지식범위를 갖는다. 이 도메인에서 그건 "환불됩니다"를 잘못 말할 경로가 6배로 늘어난다는 뜻이다. 그래서 경계는 유지하고, 이름과 계약 포장만 고친다.

규칙코드에서 무엇이 강제하나
근거 없으면 답하지 않는다 모든 핵심 주장에 Evidence. RAG 가 죽으면 조용히 메우지 않고 degraded=true + omissions
side effect 는 제안까지만 Team 은 ActionProposal 만 반환. 실행은 사람 승인 뒤 코어가 한다. MCP 는 read-only
상태는 한 문으로만 바뀐다 transition_case() 가 유일한 진입점. UPDATE customer_cases 직접 호출은 0건(정적 검사)

5. 계획은 어디서 만들어지나 — 셋으로 갈린다

무엇어디근거
① 초안 생성빈 상태에서 일정을 짠다 우리 밖 — 외부 에이전트 v10 §4-A — "계획 생성기를 만들면 트리플·Mindtrip 과 정면으로 겹친다"
② 대안 생성변화가 생겼을 때 바꿀 후보 모듈단 — 각 Team 의 ③ v10 §5 — Team 은 ①검증 ②감시 ③재계획 셋을 갖는다
③ 조립 · 정합성후보를 모아 시간충돌·예산·이동여유를 본다 코어단 v10 §5 — "전체 일정 정합성은 Team 이 아니라 코어 검증 층이 본다"

③ 이 코어인 이유: 전체 일정은 여러 Team 을 가로지르는데 어느 Team 도 남의 객체를 못 본다(allowed_tools 가 100% 팀 쌍에서 다르다). 그리고 코어는 도메인을 몰라도 조립할 수 있다 — 후보가 {시작, 끝, 장소, 비용, 잠김여부} 같은 공통 형태로 오면 "골프인지 식당인지" 를 알 필요가 없다.

★ 여기가 비어 있다 — 일정이 들어오는 경로

v10 §9-A   계획 생성 | 만들지 않는다 | 자체 추천·생성기 ← 뺀다
v10 §9-A   검증 API  | 엔드포인트 하나 (코드 검증 / 확인 수준·시각 / 불가능 사유)
v10 §5-A   코어 1 분류 라벨에 "일정 제출" 이 있다

"일정 제출" 이라는 라벨은 있는데 그 일정이 어떤 형태로 들어오는지가 없다. 입력 스키마도 가져오기 경로도 정의가 없다.

★「생성」과 「가져오기」는 다른 문제인데 v10 이 하나로 묶어 뺐다. "생성기를 만들면 경쟁사와 겹친다"는 판단은 생성에 대한 것이지 가져오기에 대한 게 아니다. 가져오기가 없으면 검증할 대상이 없다.

단계도 둘로 갈린다 — 초기엔 LLM·외부 API 로 흉내 낼 수 있지만, 결국 우리가 만들어야 하는 것이라면 그건 처음부터 자리를 잡아 둬야 한다. 가져오기는 코어단(도메인 무관 정규화), 생성은 나중에 모듈단 또는 별도 층이다.

★ 그럼 「생성」은 어디에 넣나 — 새로 만들 게 거의 없다

재계획      변화 감지  →  Team 이 후보를 낸다(②)  →  코어가 조립·검증(③)  →  통지
초안 생성   빈 일정    →  Team 이 후보를 낸다(②)  →  코어가 조립·검증(③)  →  제공
                          ↑ 같은 부품              ↑ 같은 부품

입력만 다르고 파이프라인이 같다. v10 이 "계획 생성은 안 한다" 고 뺀 것이, 실은 이미 가진 두 부품을 빈 일정에서 한 번 돌리는 일이다. 새 Team 도 새 코어 부품도 만들지 않는다.

단계어디왜
가져오기 (정규화)코어 도메인 어휘가 필요 없다 — {시작,끝,장소,비용,잠김여부} 로 바꾸는 일뿐. §5-A 의 "일정 제출" 라벨이 이미 코어 1 에 있다
후보 생성 (LLM)모듈 골프 티타임·식당 영업시간을 알아야 한다. 코어에 두면 v10 §6 "Core 는 도메인 어휘를 모른다" 에 걸린다
조립 · 정합성코어 여러 Team 을 가로지른다. 어느 Team 도 남의 객체를 못 본다
재검증모듈 v10 §5 — "생성한 대안은 판정을 다시 통과해야 통지된다"

★LLM 이 Team 안에 있어야 하는 이유가 하나 더 있다. 생성한 후보를 그 Team 이 바로 판정할 수 있다. 코어에서 생성하면 후보를 다시 Team 으로 보내야 하고, 그때 "누가 판정하나" 가 또 문제가 된다. v10 §5 가 "각 Team 안에서 판정(코드)과 대안 생성(LLM)을 분리한다" 고 한 것이 이 뜻이다 — 분리하되 같은 Team 안에서.

단계로 나누면:

지금       외부 에이전트가 초안을 만든다 → 가져오기 만 있으면 된다
다음       우리가 LLM 으로 후보를 낸다   → Team 의 ② 를 빈 일정에서도 부를 수 있게
나중       전량 자체 생성                → 같은 부품. 바뀌는 건 품질이지 구조가 아니다

★지금 정해 둬야 할 것은 하나뿐이다 — 후보의 공통 형태. 그것만 계약으로 못박으면 ②를 누가 만들든(외부 LLM · 우리 Team · 나중의 자체 모델) ③은 안 바뀐다.

6. 계획이 "결과 한 방"이 아니라 상태인 이유

v10 §4-B   Trip 집합체 신설 — "Case 는 여러 번 생기고 끝나지만 Trip 은 여행 끝까지 산다"
v10 §4-C   "우리 DB 안의 일정 버전"
v10 §5-A   Context Broker 가 여행 상태(최신 일정·잠긴 예약·다음 확인 시점)를 싣는다

상태로 두면 「상태는 한 문으로만 바뀐다」가 그대로 적용된다 — 낙관적 잠금 · 이벤트 순서 · 감사 추적을 새로 만들 필요가 없다. 쇼핑몰에서 이미 검증된 장치를 그대로 쓴다.

7. v9 → v10 에서 무엇이 남고 무엇이 바뀌나

무엇왜
승계 계약 · 생명주기 · 낙관적 동시성 · Idempotency · 이벤트 순서 · Outbox · Registry · Context Broker · 평가 하네스 코어가 도메인을 모르기 때문. 바꾸면 코어를 다시 검증해야 한다(v10 §6)
교체 Team 6종 → 여행 객체 Team · 분류 라벨 · Context 적재 내용 · Action 3종 · Composer 소재(영어 통지) 도메인 어휘는 전부 app/modules/ 안에 있다
신설 Trip 집합체 · TriggerSource(시스템이 Case 를 만든다) · 감시 소스 · 재계획 후보 생성 v9 의 Case 는 전부 고객 요청에서 시작했다. 여행에서는 감시가 Case 를 만든다

8. 아직 계약이 감당 못 하는 것 — 감시

지금 Team 계약        execute(task) → TeamResult      요청-응답 한 번
"기상청 예보를 감시한다"                                주기 실행

지금 주기로 도는 것    outbox worker · 일일 배치       ← 둘 다 Team 이 아니다

v10 §4-B 가 TriggerSource.SCHEDULE 을 만들어 절반은 답했다 — "다음 확인 시점이 오면 시스템이 Case 를 만든다". 그러면 감시는 코어 스케줄러가 하고 Team 은 여느 Case 처럼 판정만 받는다. 이 그림이면 지금 계약이 그대로 산다.

정해야 할 것: 감시를 코어 스케줄러에 둘지, Team 계약에 두 번째 진입점을 낼지. 전자면 계약 무변경, 후자면 Registry·Executor·A2A 가 전부 걸린다. 전자를 권한다 — §4-B 가 이미 그 방향이다.

9. 결정 대기 — 순서대로

  1. 일정 「가져오기」를 범위에 넣는다 — v10 §9-A 의 "계획 생성 · 만들지 않는다"를 「생성은 안 하지만 가져오기는 한다」로 가른다. 이게 없으면 루프의 입구가 없다
  2. 감시를 코어 스케줄러로 확정 (§8) — 계약이 걸리는지 여기서 갈린다
  3. ③ 조립 층의 입력 형태를 계약으로 못박기 (§5) — {시작, 끝, 장소, 비용, 잠김여부}. 이게 있어야 코어가 도메인을 모른 채 조립한다
  4. 계약 포장을 app/core/team_base.py 로 (§2) — 호환 안 깨진다. 여행으로 옮기기 전에 해야 315줄 복붙이 복제되지 않는다
  5. 그다음 팀별 세부 아키텍처
