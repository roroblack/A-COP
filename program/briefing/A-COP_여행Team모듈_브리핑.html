처음에는 쇼핑몰 팀 셋(Procurement · Fulfillment · Catalog)을 버리는 것으로 봤다. 주제 비교 문서도 “안 쓰게 되는 것”으로 적어 뒀다. 그런데 코드를 열어 보니 셋 다 여행에 같은 모양의 자리가 있었다.

왜 자리가 남아 있나. 우리가 만든 것은 “쇼핑몰 기능”이 아니라 판정하고 · 근거를 붙이고 · 사람에게 넘기고 · 기록을 남기는 틀이기 때문이다. 반품 기한을 판정하던 코드가 액티비티 취소 기한을 판정하는 데 그대로 쓰인다. 바뀌는 것은 규칙의 내용이지 규칙을 다루는 방식이 아니다.

1 Team을 무엇으로 나누나

여행을 구성하는 객체 종류별로 나눈다. 지역·상품·고객군으로 나누지 않는다.

나누는 기준도시를 늘리면언어를 늘리면도메인을 넓히면
객체 종류별 채택 데이터만 추가응답 문구만 추가Team 추가
지역별 기각 Team 추가Team 추가Team 추가

객체 종류로 나누면 서울에서 부산으로 늘릴 때 코드를 안 건드린다. 지역으로 나눴다면 도시마다 Team이 하나씩 생긴다.

Team 하나가 갖는 세 가지

  1. 검증 규칙 — 코드. 이 객체가 성립하는 조건(예: 액티비티 취소 기한이 지났나)
  2. 감시 소스 — 이 객체가 바뀌었는지 어디서 아나(예: 기상청 초단기예보)
  3. 재계획 후보 — LLM. 바뀌었을 때 무엇으로 대체하나

전체 일정이 맞는지(시간 충돌·예산·이동 여유)는 Team이 보지 않는다. 그건 코어 검증 층의 일이다. Team은 자기 객체만 보면 된다.

각 Team 안에서 판정(코드)과 대안 생성(LLM)을 분리한다. LLM이 만든 대안은 판정을 다시 통과해야 고객에게 나간다. 지금 Response Generation & Review 팀이 “쓰는 쪽과 검수하는 쪽을 다르게 둔” 원칙과 같고, 계획서 v10은 이 원칙을 별도 팀 대신 모든 Team의 내부 규칙으로 넣었다.

영업시간·휴무·동행 조건(아이·할랄·채식)을 본다. 쇼핑몰에 “영업시간”이라는 개념이 없어 새로 쓴다.

Lodging · Flight 등록만

계약만 등록, 구현하지 않음

잠긴 예약으로만 취급한다. 바꾸지 않고, 다른 일정을 짤 때 “이건 고정”으로 쓴다.

“이어받는다”는 코드를 복사한다는 뜻이 아니다. 판정 3단 구조 · 감시 소스 연결부 · 결과를 코어에 돌려주는 모양을 뼈대로 쓰고, 판정 규칙과 어휘는 전부 새로 쓴다.

3 그대로 · 갈아 끼우기 · 새로 쓰기

도메인 교체는 이 저장소가 이미 한 번 해 본 일이다 — 구독·결제 → 커머스. 이번이 두 번째다.

지난 교체가 남긴 증거. 그때 대조 규칙 엔진은 한 줄도 안 바뀌었다. 바뀐 것은 verification_policy.py라는 어휘 파일 하나였다 (payment_id → order_id 같은 이름 대응). 이번에는 order_id → booking_id로 간다.

새로 쓴다

Team의 판정 규칙(취소 기한·위약금율·기상 판단 시점·영업시간·막차), 감시 소스 연결(기상청·운영 공지·지도 API), 여행 데이터. 그리고 하나 더 —

선제 조정 루프가 진짜 신규다. 나머지는 어휘 교체에 가깝지만 이것만은 지금 구조가 없다.

지금 Case는 고객이 문의해야 시작한다. 여행은 우리가 감시하다가 시작해야 한다. 여행별로 다음 확인 시점을 저장해 두고, 주기 작업이 감시 소스를 다시 조회해 변화가 잡히면 Case를 우리가 연다.

다행히 routing_sweeper가 이미 주기 작업으로 돌고 있어 그 자리에 붙일 수 있다.

4 MVP는 둘

최종발표까지 7주. Activity와 Booking Handoff 둘만 필수다.

Team순위이유
Activity MVP 취소·환급 규정이 문서로 존재해 판정 규칙을 바로 쓸 수 있다. 예약금이 걸려 실패 비용이 크고, 시연에서 사건이 한눈에 보인다.
Booking Handoff MVP 계획서 v10의 “협약사 위임 실행”이 제품이 팔려는 것이다. 이게 없으면 “고객이 방해받지 않고 보고만 받는다”를 보여줄 수 없다.
Dining2순위변화가 잦아 시연 가치는 높지만, Activity로 루프가 증명되면 같은 틀의 반복이다.
Mobility3순위앞의 둘이 바뀌면 늘 영향을 받지만, 늦게 붙여도 코어 검증이 시간 충돌은 잡는다.
Place Verification3순위A2A 시연이 부트캠프 요구사항이라 발표 전에는 필요하다. 기능 가치보다 요구사항 충족이 이유다.
Lodging · Flight등록만잠긴 예약으로만 취급.

Booking Handoff가 MVP로 올라온 이유

★이름이 Execution 이 아니라 Handoff 인 것이 핵심이다 — 기본 동작은 인계이고, 예약을 실제로 바꾸는 것은 시연 모드 한정이다(계획서 v10 §5). Team 은 side effect 를 실행하지 않는다는 규칙(§6)은 그대로다.

처음 초안에서는 “공급자 계약이 없으니 나중에”로 미뤘다. 그 판단은 틀렸다.

계획서 v10은 실행을 세 층으로 나눈다. 1층 우리 일정(먼저 바꾸고 알린다) · 2층 협약사 예약(미리 받은 위임 범위 안이면 묻지 않고 실행하고 알린다) · 3층 비협약사(실행하지 않고 바로 누를 수 있는 링크로 넘긴다).

2층이 제품이다. 고객은 일정만 짜고, 문제가 생기면 알아서 고쳐지고, 바꾸고 싶을 때만 말한다. 계약이 없다는 문제는 커넥터를 Mock으로 풀었다.

계약이 없다는 건 Team을 미룰 이유가 아니라 증명 범위를 좁힐 이유였다 — Mock으로 증명하는 것은 업체 연동이 아니라 경계와 루프가 설계대로 도는가다. 그 사실은 산출물에 표시한다.

MVP 둘로 보여주는 것

  1. 액티비티 취소를 우리가 먼저 감지한다 (고객은 아직 모른다)
  2. 재계획안을 만든다
  3. 잠긴 예약과 필수 조건을 지켰는지 다시 검증한다
  4. 고객이 미리 위임한 범위 안인지 대조한다
  5. 범위 안이면 협약사(Mock) 예약을 실행한다
  6. 통지 문구를 검수한다 (확정 단정·확인 시각 누락)
  7. 고객 에이전트에 선제 통지한다
  8. 고객이 거부하면 되돌린다

이 여덟 단계가 제품의 주장 전부다. Team을 더 붙이는 것은 같은 루프에 객체를 추가하는 일이지 새로운 증명이 아니다.

Team을 늘리는 것보다 루프를 한 번 끝까지 도는 것이 먼저다. Activity 하나만 있어도 위 여덟 단계가 전부 돈다. Dining을 먼저 붙이면 Team은 둘인데 루프는 반쪽인 상태가 된다.

5 확인이 필요한 것

계획서 v10에 부트캠프 요구사항 대응표가 없다. v9에는 「주제 요구사항 ↔ 구현」 11행 표가 있었는데 v10에는 통째로 빠졌고, A2A·MCP라는 말도 한 번도 나오지 않는다.

그중 셋은 여행에서 갈 자리가 바로 보이지 않는다.

요구사항v9에서는v10에서는
감성 분석Case 분류할 때 같이 판정코어 1 라벨이 의도만 남았다
다중 에이전트 서빙Team 6종 + A2A 원격 팀 1종Team은 있으나 A2A 시연 대상이 없다
개인 AI 연동REST 5개 + MCP 도구 3개“에이전트 API + 토큰”으로만 서술

이건 기능 판단이 아니라 채점 항목이다. 셋 다 v9에서 산출물과 검증 방법까지 정해 뒀던 것이라, 여행으로 옮기면서 자리를 안 만들면 구현 여부와 상관없이 대응표가 빈다.

제안 — Place Verification을 A2A 자리로 쓴다. catalog_verification이 지금 그 자리이고, 여행의 장소·운영 정보 검증이 같은 모양이다. Team을 더 만들지 않고 A2A 시연 대상이 생긴다. 감성 분석과 MCP는 코어 몫이라 계획서에서 정할 일이다.
