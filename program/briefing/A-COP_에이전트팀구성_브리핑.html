A-COP / TEAM MODULE BRIEFING

A-COP 에이전트팀 구성 브리핑

업무 하나를 통째로 맡는 Team Module과 외부 Agent에게 일을 맡기는 A2A Module을 구분하고, 슬롯 자격·LLM 사용·평가 가능성을 따로 판정한다.

착수 축을 구분한다. VOC & Store Manager와 Response Generation & Review는 이번 프로젝트 주제인 CS Pack에 속하므로 10주 착수를 확정한다. Procurement + Order & Payment, Fulfillment & Logistics, Return & Refund, Catalog & Verification은 검증 쇼핑몰을 실제로 운영하기 위한 Commerce Ops Pack 범위이며, 해당 프로젝트의 진행 상황과 일정에 따라 조정될 수 있다. 6명 팀 전체가 이 구성으로 고정된다는 뜻은 아니다.

3. 팀 모듈 슬롯 조건 4가지

쉬운 풀이: 네 조건을 모두 만족해야 Team Module이다. 내부에서 LLM을 쓰는지는 별도 결정이다.

1

Capability·책임·권한·지식·Tool 경계가 독립된다.

2

TeamTask(capability + ContextPack)를 입력으로 받는다.

3

TeamResult(answer / warnings / decisions / action_proposals / need_more_context)를 반환한다.

4

side effect를 직접 실행하지 않고 ActionProposal만 반환한다.

쉬운 풀이: 팀은 “이렇게 하자”고 제안만 한다. 돈이 오가는 실행은 Controller가 승인 받고 한다.

내부 구현은 LLM 다중 호출, SQL 집계, 임계값 규칙 중에서 선택할 수 있다. Core는 TeamManifest와 표준 Contract만 본다.

쉬운 풀이: 각 Team은 맡은 업무와 권한 경계가 다르다. 실측 상태는 설계 문서와 따로 적었다.

5. VOC와 Response를 Team Module로 두는 이유

쉬운 풀이: VOC는 반복되는 문제를 세고 알림을 제안한다. Response는 모든 Team의 결과를 같은 기준으로 문장화하고 검사한다.

VOC & Store Manager

집계·시계열·임계값이라는 고유 지식과 관측·알림 tool 경계를 가진다. 배치는 실행 형태일 뿐 슬롯을 결정하지 않는다.

Response Generation & Review

응답 생성과 검증이라는 독립 Capability를 가진다. GEN과 REV는 별도 Team이 아니라 한 모듈 안의 두 호출이다.

Response는 문장 생성·검증의 기준을 모듈 하나에 모으고, 자기 출력을 자기가 채점하는 문제를 줄인다.

6. A2A Module — Catalog & Verification

쉬운 풀이: A2A Remote는 우리 서버 밖에 있는 남의 AI에게 일을 맡기는 것이다. 중간에 “자료가 더 필요하다”고 되물어올 수 있다.

Catalog & Verification은 SKU·Variant·가격·규제 증거를 확인하고 Quote artifact를 만든다. 구매·등록 side effect는 하지 않는다.

쉬운 풀이: Customer Operations는 여러 업무를 처음 받는 입구다. 개별 계산은 독립된 업무가 아니라 해당 Team의 도구다.

8. 착수 판정

쉬운 풀이: 슬롯 자격이 있다고 바로 착수하는 것은 아니다. 팀을 늘리면 채점표도 같이 늘어난다. 그게 진짜 한계다.

정답셋 존재 AND 임의 배정 비의존 AND Core loop 필요 AND 평가 여력

슬롯 자격과 착수 시점은 다른 축이다. VOC & Store Manager와 Response Generation & Review는 CS Pack의 10주 확정 축이고, 나머지 Commerce Ops Pack 모듈은 검증 쇼핑몰 프로젝트의 진행 상황과 일정에 따라 조정되는 연계 축이다. 모듈마다 golden/holdout 라벨, 라우팅 평가, Registry record, contract test, prompt version, Context Pack 예산이 늘어난다.

11. 사람 6명의 역할 분담

여기부터는 앞의 1~10절과 다른 축이다. 1~10절은 시스템이 Registry에 등록하는 Agent Team 모듈 이야기이고(Commerce Ops Pack 슬롯, 대부분 vision·미착수), 이 11절은 실제로 사람 6명이 무엇을 하는지다. 사람의 담당 경계는 코드의 컴포넌트 경계와 같지 않다 — 한 사람이 수직 기능 하나를 끝까지 본다.

Core를 "Coordination 로직 담당"과 "Backend 구현 담당"으로 쪼개지 않는다. 같은 기능 흐름에서 정책과 실제 무결성 구현이 서로 붙어 있기 때문에, Core 1은 Case Runtime을, Core 2는 Access/Action을 각각 end-to-end로 담당한다.

Agent Team은 Tool을 직접 호출하지 않는다. 읽기는 Context Broker가 미리 제공하고, 쓰기는 ActionProposal로 반환한다. 따라서 Team 개발자 3명은 Core 2 인터페이스를 보지 않아도 된다. 두 Core의 접점은 ExecuteAction / ActionResult 한 쌍이다.

11-1. Core Platform

Core 1 · Case Runtime & Coordination

  • Customer Case lifecycle / Case Event / owner
  • Shared State / checkpoint / version
  • State Repository / Transaction
  • CAS / Optimistic Concurrency / Conflict 감지
  • Agentic Controller / Top-Level LangGraph
  • Team routing / parallel 여부 / ownership / retry / replan / cancel
  • WAIT / RESUME / Case-level approval state
  • Agent Team Registry / Team Contract
  • Message Broker / MessageBus Port + Adapter
  • Local/A2A 실행 분기, RemoteTeamPort, A2A Task → Case State 매핑
  • Graph Context Port / GraphRAG orchestration
  • Context Broker 공통 orchestration Port
한 사람이 끝까지 보는 흐름: "Team 간 경합 발생 → State CAS로 충돌 감지 → CONFLICT 반환 → Controller가 최신 State 기준 Retry/Replan"

Core 2 · Access & Action Platform

  • Agent Gateway / Trust Boundary
  • OAuth / Access Token / Scope / External AI Client
  • REST/OpenAPI / MCP endpoint
  • A2A ingress / outbound HTTP·Auth Adapter / Agent Card endpoint
  • Tool / Action Gateway
  • Business Capability API
  • 고위험 Action 권한/승인 검증
  • Idempotency — 동일 Side Effect 중복 실행 방지
  • Audit Log
  • 결제/계정/알림 등 외부 시스템 Integration
한 사람이 끝까지 보는 흐름: "외부 AI 인증 → Scope 검증 → Action 요청 → 승인/Idempotency 확인 → 외부 시스템에 실제 1회 실행 → Audit"

11-2. Agent Team Module 개발 — 모델 3명

착수 시점에는 VOC & Store Manager · Response Generation & Review를 CS Pack의 확정 축으로 두고 3명을 배치한다. Procurement + Order & Payment · Fulfillment & Logistics · Return & Refund · Catalog & Verification은 검증 쇼핑몰 프로젝트를 운영하기 위한 Commerce Ops Pack 연계 축이며, 그 프로젝트의 진행 범위와 일정에 따라 배치가 달라질 수 있다. 6명 팀 전체가 이 구성으로 고정되는 것은 아니다. Team 하나가 무거우면 2명을 붙이고, 가벼우면 한 사람이 둘을 본다.

  • Team 내부 Agent / Subgraph 구조
  • Team 내부 Agent 간 병렬 실행·merge·retry 정책
  • 업무별 Prompt / Tool 사용 전략
  • Team 전용 Knowledge Scope / Retrieval / Rerank
  • Team 전용 Episodic Memory 정책
  • Team 단위 테스트 / 실패 / 재처리 시나리오
  • PoC 대상 Team 1개는 독립 프로세스로 배포하고 A2A Remote Team으로 연결 가능
예: Team 3개면 각 1명, Team 2개면 2명+1명. 내부 경합은 해당 Team이 책임하고, Team 간 경합은 Core 1이 책임한다.

11-3. UX / Observability / Evaluation

  • 사용자 / 운영자 Web UI
  • Case 상태 / Agent Trace / Shared State 시각화
  • Local vs A2A Remote Task 상태와 Graph 근거 경로 시각화
  • Human Approval 화면
  • Baseline vs Agentic Evaluation Harness
  • Case 해결률 / 재처리 / latency / cost / Tool 호출 지표
  • 통합 데모 / 평가 리포트
Core나 Agent Team의 내부 로직을 다시 구현하지 않고, 시스템을 보이게 만들고 품질을 측정하는 역할로 고정한다. 검증이 앞이고 프론트가 뒤다 — 이 1명의 1순위는 화면이 아니라 "좋아졌다"를 숫자로 증명하는 것이다.
