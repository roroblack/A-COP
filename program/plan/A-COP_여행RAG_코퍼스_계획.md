## 0. 결론 먼저

**RAG 에 넣을 것은 「판단 기준」이지 「지금 값」이 아니다.**

| | 무엇 | 어디 | 예 |
|---|---|---|---|
| **API** | 지금 값. 오늘 바뀐다 | 외부 호출 (Mock 허용) | 영업시간 · 잔여 좌석 · 이동 시간 · 강수확률 |
| **RAG** | 판단 기준. 문서에 적혀 바뀌면 개정된다 | `knowledge_documents` | 언제 취소로 보나 · 누가 위약금을 무나 · 무엇을 근거로 판정하나 |
| **코드·설정** | 결정론적 계산 | `config/guardrails.yaml` · Team 코드 | 시간 충돌 · 기한 일수 산술 · 위약금율 × 금액 |

★**셋을 가르는 질문은 하나다 — "이걸 검색해서 근거로 인용할 것인가."**
인용할 것이면 RAG, 계산에 쓸 값이면 설정, 지금 확인해야 할 것이면 API.

## 1. 지금 코퍼스가 어떤 모양인지

`[실측 2026-09-09]` 쇼핑몰 25문서 / 306청크. 표본
`01_shipping_delivered-but-not-received.md`.

```yaml
---
document_id: doc_01
title: 배송완료 표시와 미수령 신고 처리
scope: shipping            # ← Team 의 knowledge_scope 와 맞물린다
version: "1.0"
pii_class: none
effective_from: 2026-01-01
source_uri: internal://nimbus-mall/policy/shipping/not-received
---

## 표시와 실제의 어긋남
운송장에 배송 완료로 찍혀 있는데 … 상담원은 시스템에 찍힌 완료 표시만을
근거로 미수령 주장을 반려해서는 안 된다. … 판단 기준은 자료의 유무이지
고객의 태도가 아니다.
```

★**절 하나가 「판단 하나」다.** 사실 나열이 아니라 **무엇을 근거로 어떻게
판정하는지를 산문으로 쓴 것**이다. 여행판도 같은 모양으로 만든다.

`[실측]` Team 은 `knowledge_scope` 로만 검색한다 — 지금 값:

```
return_refund            order · return · refund · exchange · policy
fulfillment_logistics    order · shipping · warehouse · delivery_exception
catalog_verification     catalog
```

## 2. 출처 — 다시 찾을 필요 없다

`[실측]` `wiki/research/legal-basis.md` 가 **법제처 Open API 조회식**을 남겼고,
같은 문서가 이렇게 적어 뒀다.

> `domain_note: 전자상거래법 근거 조사다. **여행업은 별도 법령이라 다시 조사해야 한다**`

즉 **방법은 그대로 쓰고 대상 법령만 바꾼다.**

```text
GET law.go.kr/DRF/lawSearch.do?OC={OC}&target=law&type=XML&query={법령명}   → MST
GET law.go.kr/DRF/lawService.do?OC={OC}&target=law&MST={MST}&type=XML       → 조문
```

`[미확보]` 재현에 필요한 `OC`(이용자 식별자)가 문서에 안 남아 있다. **팀이 가진
값을 찾아야 한다.**

### 여행에서 볼 것

| 출처 | 무엇이 들었나 | 쓰는 Team |
|---|---|---|
| **소비자분쟁해결기준**(공정위 고시) | **업종별 위약금·환급 기준.** 쇼핑몰 때 쓴 것과 같은 고시이고 **업종 절만 다르다** | 셋 다 |
| 관광진흥법 · 국내여행표준약관 | 여행업 취소·변경의 일반 기준 | 셋 다 |
| 체육시설의 설치·이용에 관한 법률 | 골프장·스키장 등 체육시설 이용 | **Activity** |
| 식품위생법 · 알레르기 유발물질 표시 | 동행 조건 판정의 근거 | **Dining** |
| 여객자동차 운수사업법 · 철도사업법 | 환불·지연 배상 | **Mobility** |

★**소비자분쟁해결기준이 가장 값어치가 크다.** 한 고시 안에 체육시설업·외식업·
여객운송업 절이 **각각 있어서**, 세 Team 의 판단 기준이 **같은 출처에서 나온다.**
쇼핑몰 때 이미 그 고시를 다뤄 봤으므로 방법도 안다.

`[미확보]` 그 고시의 여행 관련 절이 실제로 우리가 필요한 판정(우천 취소·노쇼·
지연)을 다 덮는지 **원문을 안 봤다.** 조회부터 해야 한다.

## 3. Activity — 레저 활동

**성격**: 시각이 고정돼 있고(티타임·입장 시각) **날씨에 걸린다.** 예약금이 있어
취소 비용이 크다.

### RAG 에 넣을 것

| 문서 후보 | 무엇을 판정하나 | 왜 RAG 인가 |
|---|---|---|
| **우천·기상 악화 취소 기준** | 어느 정도 강수·풍속이면 「취소 사유」인가. 업체 재량인가 자동인가 | 업체 약관에 문장으로 적혀 있다. **숫자 하나가 아니라 조건 서술**이다 |
| **취소 시점별 위약금 단계** | 며칠 전 취소면 몇 %인가, 당일 취소는 어떻게 되나 | 소비자분쟁해결기준 체육시설업 절. **단계 표 + 예외 서술** |
| **노쇼 처리** | 연락 없이 안 오면. 재예약 제한이 붙나 | 규정 문장 |
| **기상 취소 vs 개인 사정 취소** | **부담 주체가 갈리는 지점** | 이게 판정의 핵심이고 산문으로만 표현된다 |
| **예약금·잔금 환급 순서** | 무엇부터 돌려주나, 카드 취소는 언제 | 절차 서술 |

### API 로 갈 것 (RAG 아님)

```
지금 강수확률 · 풍속        기상청 초단기예보
그 시각 잔여 슬롯           업체 조회
오늘 운영 여부              운영 공지
```

### 실제로 어떻게 쓰이나

```
sweeper 가 14:00 강수확률 80% 를 본다        ← API
    ↓
Case 생성 → Activity Team 판정
    ↓
read.policy("우천 취소 기준")  →  RAG 청크    ← "강수확률 70% 이상이면 업체가
    ↓                                            취소를 통지할 수 있다" 같은 문장
판정: 취소 사유에 해당 → 위약금 부담은 업체
    ↓
Evidence 로 그 문장을 붙여 통지한다           ← 근거 없는 문장 금지 규칙
```

★**RAG 가 없으면 "비가 오니 취소하세요" 밖에 못 한다.** 있으면 **"강수확률 70%
이상은 업체 귀책이라 위약금 없이 취소됩니다" 를 근거와 함께** 말한다. 그게 제품이다.

## 4. Dining — 요식업

**성격**: 시각이 있지만 **날씨와 무관**하고, **동행 조건**(아이·할랄·채식·알레르기)이
판정에 들어온다. 취소 비용은 Activity 보다 작다.

### RAG 에 넣을 것

| 문서 후보 | 무엇을 판정하나 | 왜 RAG 인가 |
|---|---|---|
| **예약 취소·노쇼 위약금** | 몇 시간 전까지 무료인가. 예약보증금은 언제 떼나 | 소비자분쟁해결기준 외식업 절 |
| **동행 조건 표기 의무** | 알레르기 유발물질을 어디까지 표시해야 하나 | 식품위생법. **"표시가 없으면 없다고 볼 수 있나" 가 판정** |
| **할랄·채식 판정 기준** | 무엇을 근거로 「가능」이라 말할 수 있나 | 인증 여부 · 업체 자체 표기 · 미표기. **셋의 신뢰도가 다르다** |
| **인원 변경 처리** | 몇 명까지 당일 변경이 되나 | 업체 약관 서술 |
| **대체 식당 제안 기준** | 어떤 조건이 맞아야 「대체 가능」인가 | 우리 판정 규칙 |

### API 로 갈 것

```
오늘 영업 여부 · 브레이크타임    Places 영업시간
예약 가능 시간대                업체 조회
```

★**여기가 RAG 를 가장 조심해야 할 자리다.** `[미확보]` **"이 집 할랄 되나요" 는
판단 기준이 아니라 사실이다.** 사실을 RAG 에 넣으면 낡는다 — 업체가 인증을 잃어도
문서는 그대로다. **RAG 에는 「무엇을 근거로 할랄이라 말할 수 있나」를 넣고, 그 집이
실제로 인증을 갖고 있는지는 조회한다.**

이 구분이 흐려지면 **근거 초과율**(v9 부터 재던 지표)이 오른다 — 있지도 않은
사실을 정책 문서에서 끌어다 쓰게 된다.

## 5. Mobility — 이동

**성격**: **다른 둘을 잇는다.** Activity 나 Dining 이 바뀌면 항상 영향을 받는다.
지연·결항이 잦고 배상 기준이 법으로 정해져 있다.

### RAG 에 넣을 것

| 문서 후보 | 무엇을 판정하나 | 왜 RAG 인가 |
|---|---|---|
| **지연 판정 기준** | 몇 분부터 「지연」인가. 수단마다 다르다 | 철도·버스·항공이 각각 다른 고시 |
| **환불 수수료 단계** | 출발 몇 분 전이면 얼마인가 | 철도사업법·여객자동차법. 단계 표 + 예외 |
| **연결 실패의 책임** | 앞 편 지연으로 뒤 편을 놓치면 누가 무나 | **여행에서 제일 중요한 판정**이고 산문으로만 있다 |
| **막차·최소 환승시간 기준** | 얼마를 여유로 봐야 「가능」인가 | 판정 규칙. 우리가 정하는 부분도 있다 |
| **대체 경로 제안 기준** | 어떤 조건이면 대체로 인정하나 | 우리 판정 규칙 |

### API 로 갈 것

```
지금 운행 상태 · 지연 여부      운행 정보
구간 소요 시간 · 환승           Routes
막차 시각                       노선 정보
```

★**「연결 실패의 책임」이 Mobility RAG 의 핵심이다.** 액티비티가 우천으로 밀리면
그 뒤 이동과 식당이 연쇄로 깨진다. **누구 귀책인지가 위약금 부담을 가르고**, 그
기준은 계산이 아니라 규정 해석이다.

## 6. scope 를 어떻게 나누나

`[실측]` 지금은 Team 마다 `knowledge_scope` 목록을 갖고 그 범위만 검색한다.
여행판 제안:

| Team | `knowledge_scope` 후보 |
|---|---|
| Activity | `activity` · `cancellation` · `weather` · `policy` |
| Dining | `dining` · `cancellation` · `dietary` · `policy` |
| Mobility | `mobility` · `delay` · `cancellation` · `policy` |
| Booking Handoff | `booking` · `cancellation` · `payment` |

★**`cancellation` 과 `policy` 를 공유 scope 로 둔다.** 소비자분쟁해결기준처럼
**한 문서가 여러 Team 에 걸치는 것**이 있고, 그때 문서를 복사하면 개정 때 갈린다.

`[미확보]` 공유 scope 를 두면 검색 결과에 남의 업종 절이 섞여 들어올 수 있다.
**문서를 업종별로 쪼개서 각각 scope 를 줄지, 한 문서에 공유 scope 를 줄지**
정해야 한다. 쪼개는 쪽이 검색 정확도는 높지만 개정 추적이 번거롭다.

## 7. 몇 개나 만드나

`[실측]` 쇼핑몰이 25문서 / 306청크였고 `python -m scripts.check_corpus` 게이트를
통과했다. 여행도 **같은 게이트를 쓴다.**

| Team | 문서 수 (제안) |
|---|---:|
| Activity | 8 |
| Dining | 6 |
| Mobility | 7 |
| 공유(취소·약관·법령) | 4 |
| **합계** | **25** |

★**수를 맞추려는 것이 아니다.** 25는 쇼핑몰에서 **306청크가 나와 검색이 되던
규모**라 출발점으로 쓴다. `[미확보]` 여행 판정이 더 복잡하면 더 필요할 수 있다.

★**만드는 방법은 쇼핑몰 때 정해졌다** — 코덱스 재작성이 조사 오손 3,401건을 내서
**직접 작성으로 전환**했다(cs `CLAUDE.md` RAG corpus 줄). 여행도 같은 판단이 선다.
