# A-COP 여행 MVP — 설계 질문 5건

`[초안 2026-09-09]` 사용자가 제기한 다섯 가지에 답한다. 기준선은
`A-COP_구현계획서_v10.md` 이고, **답은 전부 코드를 열어 확인한 위에 쓴다.**

★**이 문서는 제안이다.** 계획서를 고치는 것은 별건이며, 결정된 것만 v10 으로 올린다.

---

## 이 문서에 나오는 말

`[2026-09-10 추가]` 처음 읽는 사람이 막히는 말들이다. **코드에만 있는 이름을
설명 없이 쓰지 않는다** — 실제로 그렇게 써서 지적받았다.

| 말 | 쉬운 뜻 | 왜 이 이름인가 |
|---|---|---|
| **되잡기 작업** (`sweeper`) | **빠뜨린 일을 주워 담는 주기 작업.** 접수는 됐는데 뒷일이 안 돌아간 건을 찾아 다시 돌린다 | 코드 파일 이름이 `routing_sweeper.py` 다. 빗자루로 쓸어 담는다는 뜻 |
| **바깥함 ** (`outbox`) | **내보낼 것을 쌓아 두는 표.** 여기 넣으면 배달 담당이 가져가 보낸다 | 우편함처럼 "나갈 것" 을 모아 두는 자리 |
| **중복 방지 키** (`idempotency key`) | 같은 요청이 두 번 와도 **한 번만 실행되게** 하는 표식 | 두 번 눌러도 환불이 두 번 나가면 안 되니까 |
| **대상 객체 칸** (`business_subject`) | 그 작업이 **무엇을 바꾸는지** 적는 칸. 예약 하나, 주문 하나 | 중복 방지 키를 만들 때 쓰는 재료 |
| **선언표** (`manifest`) | Team 이 **자기가 무엇을 할 수 있는지 적어 두는 목록** | 화물 적하목록에서 온 말 |
| **등록소** (`Registry`) | Team 을 이름으로 찾아 주는 곳 | 전화번호부 |
| **A2A** | Agent to Agent. **에이전트끼리 말을 주고받는 규약** | 표준 이름 |
| **MCP** | Model Context Protocol. **외부 AI 가 우리 기능을 호출하는 규약** | 표준 이름 |
| **덧붙이기만** (`append-only`) | 기록을 **고치거나 지우지 않고 뒤에 붙이기만** 한다 | 그래야 되돌린 이력도 남는다 |
| **지하층** (`basement`) | 도메인을 몰라야 하는 공통 부분. 여행이든 쇼핑이든 안 바뀌는 층 | 건물 지하처럼 위에 뭘 올려도 같다 |
| **팀 결과** (`TeamResult`) | Team 이 판정하고 돌려주는 정해진 모양의 답 | — |
| **중복 키** (`dedupe key`) | 같은 알림을 두 번 보내지 않게 하는 표식 | de-duplicate |

★**이 표는 이 문서 안에서만 쓰는 번역이 아니다.** 코드 파일 이름은 영어
그대로이므로(`routing_sweeper.py`), 파일을 가리킬 때는 영어를, 개념을 말할 때는
한국어를 쓴다. 처음 나올 때 둘을 같이 적는다.

## 1. 계획서 생성 — "우리 일이 아니다" 와 충돌하지 않는다

### 지금 상태

v10 §4-A 가 **「계획 생성은 우리 일이 아니다」**로 못박았다. 외부 에이전트가 만든
일정을 받아 검증하고 여행 끝까지 지켜보는 것이 제품이다.

그런데 **지금은 받을 일정이 없다.** 시연도 평가도 입력이 있어야 시작한다.

### 갈라서 보면 충돌이 아니다

```
계획을 만드는 일        제품 아님    ← v10 §4-A 가 말하는 것
계획을 만들어 넣는 일    시연 준비    ← 지금 필요한 것
```

**둘은 다른 일이다.** 골든셋을 만든 것과 같다 — 우리가 답을 만들지 않지만
평가하려면 입력이 있어야 하므로 만들어 넣었다.

### 그래서 이렇게 나눈다

| | 무엇 | 어디 | 제품인가 |
|---|---|---|---|
| **생성기** | LLM 으로 일정 초안을 만든다 | `scripts/seed_trip.py` (제품 밖) | **아니다** |
| **입구** | 일정을 받아 검증하고 저장한다 | `POST /v1/trips` | **그렇다** |
| 가져오기 | 외부 에이전트·파일에서 받는다 | 같은 입구 | 그렇다 (나중) |

★**핵심은 입구가 하나라는 것이다.** 생성기든 외부 에이전트든 나중의 가져오기든
**같은 문으로 들어온다.** 그래야 "우리가 만든 것" 과 "받은 것" 이 코드에서
구분되지 않고, `[미확보]` 로 남을 여지가 없다.

### 우리 데이터로 어떻게 바뀌나

들어오는 것은 **자유 형식 일정**이고, 우리 데이터는 **검증 가능한 구조**다.
그 사이에 변환이 하나 있다.

```
외부 일정 (자유 형식)
    ↓  ① 정규화 — 항목마다 {시작, 끝, 장소, 비용, 잠김여부} 로 만든다
    ↓  ② 대조   — 장소·운영시간·이동시간을 실제로 조회해 확인한다
    ↓  ③ 판정   — 시간 충돌 · 예산 · 이동 여유. 불가능하면 이유와 완화 조건
    ↓
Trip 의 일정 버전 (우리 데이터)
```

★**①의 다섯 칸이 계약이다.** 이게 정해지면 코어가 도메인을 몰라도 조립할 수 있다
(액티비티인지 식당인지 알 필요가 없다). 이 다섯 칸을 계약으로 못박는 것이
[여행Team모듈 구성안](A-COP_여행Team모듈_구성안.md) 에서 말한 **조립 층의 전제**다.

`[미확보]` 다섯 칸이 충분한지 안 봤다. 동행 조건(아이·할랄·채식)이 Dining 판정에
필요한데 이 다섯에 없다. **넣을지, 아니면 `constraints` 한 칸을 더 둘지 정해야 한다.**

## 2. 지속 관리 — 팀을 돌리지 않는다

### 사용자 판단이 맞다

> "각 팀모듈을 계속 돌게? 이건 좀 소모적일 듯"

**소모적인 정도가 아니라 계약상 안 된다.** `[실측 2026-09-09]`

```
TeamModule 프로토콜의 진입점        async def execute(task) -> TeamResult   ← 하나뿐
TeamManifest 필드 13개 중 주기 관련   없음
```

Team 은 **불러야 도는 것**이다. 주기 실행을 넣으려면 계약에 두 번째 진입점을
내야 하고, 그러면 Registry·Executor·A2A·평가 하네스가 다 걸린다.

### 코어에서 도는 것은 이미 셋 있다 — **되잡기 작업**(sweeper)이라 부른다

`[실측 2026-09-09]` 주기 실행은 전부 `app/application/` 에 있다. **Team 이 아니다.**

| 무엇 | 줄수 | 무엇을 되잡나 |
|---|---:|---|
| `classification_sweeper.py` | 90 | 분류를 트랜잭션 밖으로 뺀 뒤 남은 `classifying` 잔류 |
| `routing_sweeper.py` | 92 | 실행을 응답 뒤로 뺀 뒤 남은 `routing` 잔류 |
| `feedback_job.py` | 107 | 일 1회 집계 |

실행기도 있다 — `scripts/run_sweepers.py`.

```
--once      한 번 돌고 끝난다 (cron 용). errored 있으면 exit 1
--interval  N 초마다. 죽지 않는다
```

★**돌리는 주기를 코드가 정하지 않는다.** 임계값은 `config/guardrails.yaml` 이고
얼마나 자주 부를지는 운영이 정한다. 그 파일 주석이 이유를 적어 뒀다 —
*"상주 루프를 기본으로 두면 언제 도는지가 코드에 숨는다."*

### 그래서 넷째 되잡기 작업을 붙인다

**새 구조를 만들 필요가 없다. 같은 자리에 하나 더 놓는다.**

```
trip_watch_sweeper.py       다음 확인 시점이 지난 Trip 을 집는다
    ↓  변화 감시 (기상·운영 공지·운행 정보)
    ↓  변화 있으면 → Case 를 만든다  ← 여기서부터 기존 경로 그대로
    ↓                                  분류 → Team 판정 → 재계획 → 재검증
    ↓  변화 없으면 → 다음 확인 시점만 갱신
```

★**Team 은 여전히 불려서 돈다.** 바뀌는 것은 "누가 부르느냐" 뿐이다 —
전에는 고객 메시지가, 이제는 sweeper 도 부른다. **v10 §5 의 「② 감시 소스」는
Team 의 능력이 아니라 sweeper 가 무엇을 볼지의 목록**으로 읽어야 한다.

`[미확보]` 감시 소스 설정을 어디 두는지 안 정했다. Team manifest 에 두면 계약
변경이고, `config/` 에 두면 Team 과 떨어진다. **Team manifest 에 선언만 두고
읽는 것은 sweeper 가 하는 쪽**이 계약을 안 건드린다 — 확인 필요.

## 3. 알림 — MCP·A2A 로는 못 민다

### 방향이 반대다

`[실측 2026-09-09]` MCP 도구는 셋이고 **전부 `mcp:read`** 다.

```
list_cases · get_case_detail · open_support_case
```

★**MCP 도 A2A 도 「들어오는 문」이다.** 남이 우리를 부른다. 알림은 **우리가
남을 부르는 것**이라 방향이 반대다. 프로토콜에 그 기능이 없는 게 아니라
**우리 쪽 구현이 서버(불리는 쪽)** 라서다.

### 나가는 문은 이미 있다 — **바깥함**(`outbox`)

`[실측 2026-09-09]` `outbox` 테이블(14열)과 발행 포트가 있다.

```python
MessageBrokerPort.publish(topic, payload, dedupe_key)
outbox  UNIQUE (tenant_id, topic, dedupe_key)   ← 중복 발행을 DB 가 막는다
```

`mock_payment_publisher.py` 가 **실제 공급자와 같은 경계**를 쓰는 Mock 이다.
알림도 같은 자리에 붙인다.

```
trip_watch_sweeper  →  변화 감지  →  Case  →  재계획·재검증
                                                  ↓ 통과
                                          outbox.publish("trip.notice", …)
                                                  ↓
                                          worker  →  전달 어댑터
```

### 전달 어댑터는 무엇으로 하나

| 방법 | 되나 | 비고 |
|---|---|---|
| **이메일·웹훅** | 된다 | 어댑터 하나. MVP 에 맞다 |
| **고객의 개인 에이전트가 폴링** | 된다 | `GET /v1/trips/{id}/notices` — **MCP 로 열면 지금 구조 그대로다** |
| MCP 서버가 먼저 밀기 | **안 된다** | 우리가 MCP 서버다. 클라이언트를 못 부른다 |
| A2A 로 밀기 | **조건부** | 우리가 A2A **클라이언트**가 되어야 한다. v10 에 A2A 언급이 **0회**라 범위 밖 |

★**권하는 것은 「폴링 + 웹훅」 둘이다.** 고객 에이전트는 MCP 로 읽어 가고
(지금 구조 그대로), 급한 건은 웹훅으로 민다. **MCP 를 밀기 용도로 바꾸려 하면
안 된다** — read-only 경계(v9 부터 지킨 것)가 무너진다.

`[미확보]` 알림 수신 주체가 사람인지 고객의 에이전트인지 안 정했다. 사람이면
이메일·푸시가 필요하고, 에이전트면 폴링으로 충분하다. **v10 §0-1 은 "개인
에이전트가 만든 일정을 받는다" 고 했으니 에이전트 쪽이 자연스럽다.**

## 4. 대표 시나리오 하나 — 이미 틀이 있다

`[실측]` `scripts/seed_demo_cases.py` 가 쇼핑몰 시나리오 둘을 심는다. 여행판은
**그 자리를 갈아 끼우면 된다.**

### 권하는 시나리오 — 「비 와서 액티비티가 깨진다」

이유 셋. **v10 이 MVP 필수로 고른 Team 둘을 한 번에 보여준다**(Activity ·
Booking Handoff). **감시 소스가 기상청이라 변화를 만들어 내기 쉽다.**
그리고 **승인 경계가 자연스럽게 등장한다.**

```
1  일정 등록      한강 수상 액티비티 14:00 · 근처 식당 17:00 · 이동 30분
2  검증 통과      시간 충돌 없음 · 이동 여유 있음 → Trip 저장, 감시 시작
3  변화 감지      sweeper 가 기상 조회 → 14:00 강수확률 80%
4  Case 생성      "사건 신고" 로 분류 (v10 §5-A 라벨)
5  Team 판정      Activity — 우천 취소 규정 적용, 대체 후보 생성
6  재검증         대체안이 시간·예산·이동을 다시 통과해야 통지된다
7  인계           Booking Handoff — 예약 변경 링크 + 차액 정리
8  통지·거부      고객이 거부하면 이전 일정 버전으로 되돌린다
```

★**8번이 이 시연의 핵심이다.** 되돌림이 되는 것을 보여야 "먼저 조정한다" 가
위험하지 않다는 것이 증명된다. v10 DoD 8·9(되돌림 + append-only 이력)가 그것이다.

`[미확보]` 기상 API 를 실제로 붙일지 Mock 으로 할지 안 정했다. **시연 재현성을
생각하면 Mock 이 낫다** — 발표날 비가 안 오면 시연이 안 된다.

## 5. 데이터 구분 — 셋으로 나눈다

### 지금 있는 것

`[실측 2026-09-09]`

```
DB 테이블 19개
RAG 코퍼스 25문서 / 306청크    ← 전부 쇼핑몰
datasets/                       commerce · voc · mt   ← 여행 없음
```

### 셋으로 나눈다

| 구분 | 무엇 | 어디 | 여행에서 |
|---|---|---|---|
| **API** | 실시간으로 조회하는 것 — 장소·운영시간·이동시간·기상 | 외부 호출 (Mock 허용) | **신규** |
| **RAG** | 잘 안 변하는 규정 — 취소·환급 규정, 위약금율, 동행 조건 | `knowledge_documents` | **전량 교체** |
| **합성** | 시험용 — 일정·예약·고객 | `scripts/seed_*.py` | **신규** |

★**가르는 기준은 "얼마나 자주 바뀌나" 다.** 운영시간은 오늘 바뀔 수 있으니 API,
우천 취소 규정은 계약서에 적힌 것이라 RAG. **이 기준을 안 정하면 규정을 API 로
조회하려 들거나 운영시간을 RAG 에 넣게 된다.**

### DB 는 19표 중 5표만 갈아낀다

`[실측 2026-09-09]` 지금 19표를 성격으로 가르면:

| | 표 | 여행에서 |
|---|---|---|
| **코어 — 그대로** | `customer_cases` · `case_events` · `agent_runs` · `team_tasks` · `action_requests` · `action_approvals` · `outbox` · `llm_calls` · `prompts` · `customers` · `tenants` · `knowledge_documents` · `knowledge_chunks` · `feedback_analytics_reports` | **14표 손 안 댐** |
| **도메인 — 갈아낌** | `orders` · `order_items` · `products` · `returns` · `shipments` | **5표 교체** |

여행 쪽 후보:

```
trips                여행 하나. Case 여럿을 가로지른다
itinerary_versions   일정 버전 (append-only). 되돌림이 여기서 나온다
itinerary_items      항목. {시작, 끝, 장소, 비용, 잠김여부} + constraints
bookings             예약. 잠긴 것과 안 잠긴 것
watch_schedule       다음 확인 시점 — sweeper 가 읽는다
```

★**`trips` 가 `customer_cases` 와 다른 이유** — v10 §4-B 가 적었다:
*"Case 는 여러 번 생기고 끝나지만 Trip 은 여행 끝까지 산다."* 사건마다 Case 가
생기고 닫히는 동안 Trip 하나가 계속 산다.

★**`itinerary_versions` 를 append-only 로 두면** 되돌림·이벤트 순서·감사 추적을
새로 안 만들어도 된다. `case_events` 가 이미 그 모양이다(`UNIQUE(case_id,
aggregate_version)`).

`[미확보]` `business_subject` 규칙이 안 정해져서 `bookings` 의 id 를 무엇으로
쓸지 못 정한다 → [구성안 §2-A](A-COP_여행Team모듈_구성안.md). **여행은 Trip 하나에
예약이 여럿이라 이게 먼저다.**

## 6. 화면 초안 — 넷이면 된다

MVP 범위(v10 §9-A)가 "계획과 검증" 까지이므로 화면도 거기 맞춘다.

| # | 화면 | 무엇을 보여주나 | 왜 필요한가 |
|---|---|---|---|
| 1 | **일정** | 최신 버전 · 잠긴 예약 표시 · 다음 확인 시점 | 제품의 상태 그 자체 |
| 2 | **사건** | 감지된 변화 · 무엇이 깨졌나 · 대체안 | 재계획이 왜 일어났는지 |
| 3 | **승인** | 대기 중인 제안 · 근거 · 차액 | **승인 경계가 있다는 증거** |
| 4 | **추적** | 일정 버전 이력 · 되돌림 · 판정 근거 | 되돌릴 수 있다는 증거 |

★**3·4 가 시연의 값어치다.** 1·2 는 어느 여행 앱에도 있다. **"자동으로 하되
경계를 지킨다" 를 보여주는 것은 승인 화면과 추적 화면**이고, v10 DoD 8·9·10·14 가
그것을 판정한다.

★기존 운영 UI(`/ui/approvals`, trace 화면)가 이미 3·4 의 뼈대다. `[미확보]`
그대로 쓸 수 있는지는 화면을 열어 확인해야 한다.

## 6-A. 「검증·감지·재계획 에이전트」는 코어인가 Team 인가

`[2026-09-09]` 강사 의견은 **셋을 에이전트로 세우라**는 것이고, 팀 내부 의견은
**셋 다 코어 기능**이라는 것이다.

★**의견으로 가를 문제가 아니다. 판정 기준이 이미 코드에 있다.**
`tests/architecture/test_basement_is_domain_free.py` 가 **basement 다섯 층
(`core`·`domain`·`application`·`infrastructure`·`presentation`)에 업무 도메인
어휘가 들어오는 것을 막는다.** 도메인을 알아도 되는 곳은 `app/modules/**` 뿐이다.

> 그래서 질문은 "이건 코어 일인가"가 아니라
> **"이걸 하려면 여행 어휘를 알아야 하나"** 가 된다.

### 그 기준으로 가르면 셋 다 쪼개진다

| 일 | 여행 어휘가 필요한가 | 어디 |
|---|---|---|
| 언제 볼지 정하고 주기로 도는 것 | 아니오 — 시각 비교 | **코어** sweeper |
| 무엇을 볼지 (기상청? 운영 공지?) | **예** | Team 선언 |
| 바뀌었는지 비교 | 아니오 — 값 비교 | **코어** |
| **항목 검증** (우천이면 취소되나, 티타임 규정, 할랄 가능한가) | **예** | **Team** |
| **전체 검증** (시간 충돌·예산·이동 여유) | 아니오 — 다섯 칸으로 계산 | **코어** |
| **재계획 후보 생성** (무엇으로 대체하나) | **예** | **Team** |
| 후보 조립·재검증·통지 | 아니오 | **코어** |

★**쪼개지는 선이 기능 이름이 아니라 어휘다.** "재계획 에이전트" 를 통째로
코어에 넣으려면 우천 취소 규정을 `app/core/` 에 써야 하는데, **그러면 빌드가
깨진다** — 의견이 아니라 `pytest tests/architecture` 가 판정한다.

`[실측]` 이 검사가 실제로 사고를 잡았다. 2026-08-16 에 `app/core/verification.py`
가 구독·결제 어휘를 코어에 박았고, 그 결과 **쇼핑몰의 `order_id` 가 basement 의
"확인 불가 → 거부" 목록에 올라 있었다.** 가장 중요한 식별자가 거부 대상이 된
정반대 상황이었다.

### 둘 다 맞는 말을 하고 있다

| | 맞는 부분 |
|---|---|
| **팀 내부 의견** | **루프·조립·전체 검증은 코어다.** Team 을 주기로 돌리는 것은 계약상 안 된다(§2) |
| **강사 의견** | **판단은 에이전트가 해야 한다.** 항목 검증과 대안 생성은 도메인 어휘가 필요해 코어에 못 넣는다 |

**충돌이 아니라 분업이다.** 코어가 루프를 돌리고 조립하며, Team 이 도메인 판단을 한다.
v10 §5 가 각 Team 에 준 셋(① 검증 규칙 ② 감시 소스 ③ 재계획 후보)이 정확히
**도메인 어휘가 필요한 세 자리**다.

### 다만 부트캠프 요구사항 쪽은 실제로 구멍이다

`[실측 2026-09-09]` 부트캠프 주제가 **"다중 에이전트 서빙 기반 …"** 이다(v9 §169).
v9 §3-A 에 「부트캠프 주제 요구사항 ↔ 구현 대응표」가 있어 이 요구를 Team 다섯에
매핑해 뒀는데, **v10 에는 그 표가 통째로 없다.**

그리고 v10 §9-A 는 `다중 에이전트` 를 **"이번엔 뺀다"** 칸에 넣었다(`v10:301`).
★**그 줄은 「외부 연결」 행이라 외부 개인 에이전트를 여럿 붙이는 것을 뺀다는 뜻**
이지 내부 Team 을 줄인다는 뜻이 아니다. 하지만 **읽는 사람은 그렇게 안 읽는다.**

**강사가 걱정하는 것이 이 자리일 가능성이 높다.** 대응은 Team 을 늘리는 것이 아니라
**대응표를 되살리는 것**이다 — 어느 Team 이 어느 요구를 맡는지 한 표로 보이면
"에이전트가 없다" 는 오해가 안 생긴다.

`[미확보]` 강사가 말한 "에이전트" 가 우리가 말하는 Team 과 같은 것인지 확인 안 했다.
**같은 말을 다르게 쓰고 있으면 이 논의 자체가 헛돈다.** 먼저 물어볼 것.

## 6-B. 그 셋은 각 Team 이 하나, 새 모듈이 하나

`[2026-09-09]` **각 Team 이 각자 갖는다. 새 모듈은 필요 없고, 기존 한 팀에 몰지도
않는다.** 다만 **셋의 상태가 다르다** — 하나는 이미 있고, 하나는 없고, 하나는
한 팀에만 있다.

`[실측 2026-09-09]` 지금 Team 여섯의 내부를 열어 보면:

| v10 §5 가 준 것 | 지금 상태 | 여행에서 할 일 |
|---|---|---|
| **① 검증 규칙** | **이미 각 팀에 있다** — `execute()` 안의 판정 로직 (`return_refund` 125줄 · `fulfillment_logistics` 62줄) | **규칙만 갈아낀다.** 자리는 그대로 |
| **② 감시 소스** | **없다** — `TeamManifest` 13필드에 주기·감시 관련이 하나도 없다 | **선언만 팀에 둔다.** 부르는 것은 sweeper |
| **③ 재계획 후보 생성** | **한 팀만 한다** — `response_review._generate` 가 유일하게 `self.llm.complete` 를 부른다 | **4팀이 각자 갖는다.** 본은 이미 있다 |

### ② 는 "선언" 만 팀에 둔다 — 실행을 넣으면 계약이 깨진다

Team 은 `execute(task)` 로만 불린다(§2). **감시를 팀이 직접 돌면 두 번째 진입점이
필요하고 그건 계약 변경**이다. 그래서 이렇게 가른다.

```
Team manifest   watch_sources: ["weather.short_term", "operator.notice"]   ← 선언
sweeper(코어)    그 목록을 읽어 실제로 조회하고 변화를 비교한다              ← 실행
```

★**이러면 계약을 안 건드린다.** `TeamManifest` 에 필드 하나가 느는 것은
`allowed_tools`·`knowledge_scope` 가 이미 그런 모양이라 같은 성격이다.

`[미확보]` 그래도 필드 추가는 계약 변경이다. `config/` 에 두는 안과 견줘 정해야 한다.

### ③ 은 본이 이미 있다 — 다만 네 곳 복붙이 된다

`response_review._generate()` 가 그 모양이다.

```python
if self.llm is None:            # LLM 없으면 생성 안 한다
    return 원문 그대로
response = await self.llm.complete("response.generate", …)
return self._decode(response)
```

v10 §5 가 이 팀을 Team 자리에서 내리고 **원칙을 각 Team 안으로 흡수**했으므로,
Activity·Dining·Mobility·Booking Handoff 넷이 각자 `_generate` 를 갖게 된다.

★**그러면 네 곳에 같은 뼈대가 복붙된다.** 지금 `_result`·`_evidence`·`_escalate`
80줄이 이미 그 상태다 → [구성안의 계약 포장](A-COP_여행Team모듈_구성안.md).
**③ 을 넣기 전에 그 포장을 `app/core/team_base.py` 로 빼는 편이 낫다** — 넣고 나서
빼면 네 곳을 고쳐야 한다.

### 경고 하나 — "선언만 하고 안 쓰는" 상태가 실제로 있다

`[실측 2026-09-09]` `voc_store_manager` 는 `llm` 을 **주입받고도 `execute()` 에서
한 번도 안 쓴다.** 분기는 `similar_case_count >= 2` 고정 임계값 하나다.

★**②·③ 도 같은 꼴이 되기 쉽다.** manifest 에 `watch_sources` 를 적어 두고 sweeper 가
안 읽거나, `_generate` 를 만들어 두고 안 부르는 상태. **선언과 동작이 갈리면
문서만 보고는 못 알아챈다.** 검사로 막아야 한다 —

```
manifest 에 watch_sources 가 있는데 sweeper 가 안 읽는 Team 이 있으면 실패
```

`tests/contract/test_module_toggles.py::test_every_declared_module_has_a_gate` 가
이미 같은 성격의 검사다. 그 옆에 붙인다.

## 7. 순서

앞의 것이 뒤의 전제라 순서가 있다.

| # | 무엇 | 왜 먼저인가 |
|---|---|---|
| 1 | **`business_subject` 규칙** | 계약이다. `bookings` id 설계가 여기 걸린다 |
| 2 | **정규화 다섯 칸 확정** | 조립 층의 전제. `itinerary_items` 스키마가 이것이다 |
| 3 | DB 5표 설계 | 위 둘이 정해져야 쓸 수 있다 |
| 4 | 입구(`POST /v1/trips`) + 생성기 | 입력이 있어야 나머지가 돈다 |
| 5 | `trip_watch_sweeper` + 알림 | 지속 관리 루프 |
| 6 | 시연 시나리오 심기 | 위가 다 돌아야 시연이 된다 |
| 7 | 화면 넷 | 마지막 |

**1·2 를 건너뛰고 3 부터 하면 두 번 만든다.** 둘 다 계약이라 나중에 바꾸면
그 위에 쌓은 것이 전부 따라 바뀐다.
