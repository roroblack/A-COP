# A-COP 다이어그램 근거

현재 다이어그램 8종은 `A-COP_구현계획서_v8.md`의 계약, 런타임, 데이터 구조를 기준으로 한다.

## 다시 만들기

같은 폴더의 `render_all.py`로 8종을 SVG로 렌더링한 뒤 `build_showcase.py`로 `A-COP_다이어그램_모음.html`을 만든다. 두 스크립트 모두 PlantUML 서버 접속이 필요하다.

상태 다이어그램의 영문 라벨은 §19 mermaid 초안에 명시된 이벤트명이다. 한글 라벨은 §19 표에는 있으나 이벤트명이 없는 전이에 붙인 설명용 라벨이다. 이 구분은 다이어그램 범례에도 표시한다.

## archive 안내

- `A-COP_UML_다이어그램_v2.html`은 초기 3종만 담고 있어 8종판으로 대체하면서 옮겼다.
- `render_new.py`와 `render_new2.py`는 일부 다이어그램만 렌더링하던 스크립트라 8종 일괄 렌더링용 `render_all.py`로 통합하면서 옮겼다.
- `acop_plan_basis_v2.txt`는 초기 3종의 근거·검증 보고서라 핵심 사실과 계획서 절 대조 내용을 이 문서에 흡수하면서 옮겼다.

## 유스케이스 다이어그램

외부 주체와 업무 기능의 범위는 §1-2, §9, §9-C, §16을 근거로 한다. Core Runtime, CS Pack, Commerce Ops Pack, MCP, A2A, 승인 경계와 운영자 기능을 반영했다.

## 클래스 다이어그램

핵심 계약과 실행 경계는 §7-B, §8, §8-B, §9-E, §21을 근거로 한다. `TeamTask`, `TeamResult`, `ContextPack`, `Evidence`, `TeamModule`, Registry, Controller, Action 경계를 반영했다.

Local과 A2A 실행은 `TeamExecutorPort` 뒤에서 동일한 `TeamResult`로 정규화하며, Team은 side effect를 실행하지 않고 `ActionProposal`만 반환한다.

## 시퀀스 다이어그램

Case 생성부터 분류, Context Pack, Team 실행, WAIT/RESUME, 승인, 결과 반환까지의 흐름은 §8, §8-A, §8-B, §9, §9-C, §9-E, §19를 근거로 한다.

## 상태 다이어그램

Case 생명주기와 허용 전이는 §19를 직접 근거로 한다. 상태 변경의 단일 진입점, `StateConflict`, WAIT reason, resume node, Resume token, TTL 만료 처리도 같은 절의 구현 명세를 반영했다.

## ERD

PostgreSQL 테이블, ENUM, 외래 키, 이벤트 소싱과 중복 방지 제약은 §22를 직접 근거로 한다. `knowledge_chunks.embedding`은 §22의 pgvector 확장과 `vector(1536)` 선언을 반영했다.

## 컴포넌트 다이어그램

Basement(Core)의 전체 구성은 §7-B와 §8-1~§8-8을 근거로 한다. Agent Gateway, Customer Case Layer, Team Registry/Contract, Context Broker, Message Broker, Shared State, Tool/Action Layer, Agentic Controller의 경계를 반영했다. Core 1은 Case Runtime & Coordination을, Core 2는 Access & Action Platform을 담당한다.

Message Broker는 Task/Event 전달을 맡고 Context Broker는 판단용 ContextPack을 구성한다. 두 Broker는 합치지 않으며 계층 경계는 §8-A-1의 Application/Coordination과 Infrastructure 분리를 따른다.

## A2A 시퀀스 다이어그램

A2A 외부 소비자 AI 연동 구조는 §9를 근거로 한다. MCP는 도구·Resource 접근이고 A2A는 장기 실행 업무 위임이라는 역할 분리를 §9-C에서 반영했다. Agent Card, A2A Task 생명주기, input-required 왕복, Artifact 반환, A2A Task와 Case 상태 매핑을 포함한다.

Catalog & Verification을 A2A Remote Team 후보로 정한 판단은 §9-C-1을 근거로 한다. Agent Card, 진행 상태, 추가 입력, Artifact, 장기 추적, 서비스 간 인증, 실패·timeout·취소를 모두 검증할 수 있는 후보라는 점을 반영했다.

## 배포 다이어그램

기술 스택과 Phase 2 배포 경계는 §12를, 소스 트리와 패키지 배치는 §13을, 엑셀 입력용 요약의 배포·기술 기준은 §28을 근거로 한다. `A-COP_Composer_v3_설계_토글전용_UI이관.md` §8의 패키징 원칙도 함께 반영했다.

배포 단위는 `acop_basement`, 선택 설치하는 `acop_composer`, 패키지가 아닌 독립 서비스 `final_project_ui`로 나눈다. 고객용 빌드는 `acop_basement`만 설치하고 컴포저를 배제하며, 관리용 빌드에서만 `acop_composer`를 선택 설치한다.
