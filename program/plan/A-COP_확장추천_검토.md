# A-COP 확장 추천 검토

작성 2026-08-28. Codex는 파일 쓰기에 실패해 산출물을 내지 못했다. 코드 확인과 판단은
직접 수행했다.

## 1. 결론

등록할 만하다. 다만 하나로 묶으면 안 된다. 추천의 근거를 어디서 얻느냐에 따라 난이도가
완전히 다르기 때문이다.

**자기 관측 기반 추천**은 지금 구조에서 이미 성립한다. 필요한 신호가 코드에 이미 있다.
프로젝트가 하나뿐이어도 가능하다. 새 `VISION-13`으로 독립 등록한다.

**교차 프로젝트 기반 추천**은 여러 배포의 구성을 비교해야 한다. `VISION-10` 2층과 같은
조건이 필요하므로 거기에 흡수한다.

## 2. 추천 근거 두 종류

여기서 "추천"은 "이 모듈을 켜세요", "이런 Team 인스턴스를 추가하세요"를 시스템이 먼저
제안하는 것을 말한다.

| 종류 | 근거 | 필요한 프로젝트 수 | 예시 |
|---|---|---|---|
| 자기 관측 기반 | 그 배포 자신의 운영 기록 | 1개 | "결제 오류 문의 47건이 처리할 Team이 없어 떨어졌다" |
| 교차 프로젝트 기반 | 여러 배포의 구성 비교 | 3개 이상 | "보통 A Team과 B Team을 같이 쓴다" |

둘은 나눌 수 있다. 앞의 것이 뒤의 것을 기다릴 이유가 없다.

## 3. 자기 관측 기반은 지금 구조에서 성립한다

필요한 신호가 이미 기록되고 있다. 추측이 아니라 코드에서 확인했다.

### 3.1 라우팅 실패가 이벤트로 남는다

`TeamRegistry.resolve()`는 처리할 Team을 찾지 못하면 `RegistryError`를 던진다.
근거는 `final_project_cs/app/core/registry.py:78`이다.

```
raise RegistryError(f"case must resolve to exactly one active team: {case_type}")
```

Controller가 그것을 잡아 이벤트로 남긴다. 근거는
`final_project_cs/app/application/controller.py:128-130`이다.

```python
except RegistryError as exc:
    self._transition_with_retry(..., event_type=EventType.ROUTING_FAILED,
                                payload={"failure_code": "no_team"}, ...)
```

즉 **"이 문의를 처리할 Team이 없었다"가 `case_events` 테이블에 그대로 쌓인다.**
`failure_code`가 `no_team`이다.

### 3.2 다른 신호도 이미 있다

`final_project_cs/app/domain/events.py`에 다음 이벤트 종류가 정의돼 있다.

| 이벤트 | 무엇을 뜻하나 | 추천에 쓸 수 있는 것 |
|---|---|---|
| `routing_failed` | 처리할 Team이 없었다 | 어떤 Team이 없는지 |
| `classification_failed` | 문의 유형을 못 정했다 | 분류 지식이 부족한 영역 |
| `missing_input` | 필요한 정보가 없었다 | 어떤 조회 도구가 없는지 |
| `retry_exhausted` | 재시도를 다 썼는데 실패했다 | 어떤 연동이 불안정한지 |
| `guardrail_escalated` | 안전장치가 사람에게 넘겼다 | 자동화 여지가 있는 영역 |
| `approval_required` | 승인이 필요했다 | 승인 적체 구간 |

`case_events`는 `event_type`, `payload_json`, `created_at`을 가진다. 근거는
`final_project_cs/app/infrastructure/db/repository.py:36-39`다.

**따라서 추천의 근거 데이터는 별도로 만들 필요가 없다.** 이미 쌓이고 있는 것을 세기만
하면 된다.

### 3.3 다만 집계 경로가 없다

기록은 있으나 그것을 case 단위가 아니라 **기간·유형 단위로 세는 조회**는 없다.
`get_case_events()`는 case 하나의 이벤트를 시간순으로 읽을 뿐이다.

그래서 선행 작업은 "기록 추가"가 아니라 "집계 조회 추가"다. 이 차이가 크다. 전자는
Core를 건드리지만 후자는 읽기 전용 질의만 더하면 된다.

## 4. 위험과 관리 방법

| 위험 | 실제 판단 | 관리 방법 |
|---|---|---|
| 추천을 따랐는데 조립이 실패한다 | 실제 위험이다. 같은 구현체를 다른 이름으로 또 선언하면 capability 중복으로 조립이 거부된다 | 추천 시점에 dry-run 검증을 함께 돌린다. 적용 가능한 추천만 보여준다 |
| 추천이 운영자 판단을 대체한다 | 실제 위험이다. 근거 없이 따르면 구성이 부풀기만 한다 | 추천은 제안까지만 한다. 적용은 사람이 누른다. Team이 side effect를 직접 실행하지 않는 기존 원칙과 같은 구조다 |
| 다른 고객사 구성이 새어나간다 | 교차 프로젝트 추천에서 실제 위험이다 | 개별 구성을 공유하지 않는다. 익명 집계만 쓰거나, 자체 호스팅 배포에서는 이 기능 자체를 끈다 |
| 추천 근거를 설명하지 못한다 | 실제 위험이다. 계획서가 "모든 판단은 근거와 함께 기록"을 표방한다 | 추천마다 근거 수치와 해당 Case 목록을 함께 낸다. "47건"과 그 47건이 무엇인지 볼 수 있어야 한다 |

네 번째가 특히 중요하다. 근거 없는 추천은 이 제품이 스스로 내세운 원칙을 어기는 것이다.

## 5. 등록 형태 제안

### 5.1 VISION-13 신규 등록 — 자기 관측 기반 구성 진단

**하려는 것**

배포 자신의 운영 기록을 세어 "무엇이 없어서 실패했는지"를 보여주고, 그것을 메울 모듈이나
Team 인스턴스를 제안한다.

**지금 하지 않는 이유**

운영 기록이 쌓이지 않았다. 실패 이벤트가 몇 건 없는 상태에서 추천을 만들면 우연을
패턴으로 오인한다. 또 집계 조회 경로가 아직 없다.

**도입 트리거** (다음을 모두 충족)

- 운영 중인 배포에서 `routing_failed` 또는 `classification_failed` 이벤트가 30일 동안
  50건 이상 쌓인다.
- 그중 같은 case type이 10건 이상 반복된다. 한 유형에 몰려야 "그 Team이 없다"고 말할 수
  있다.
- 이벤트 집계 조회가 구현돼 있다.

**예상 비용**

| 구분 | 실소요 일수 | 내용 |
|---|---:|---|
| 생성 | 3~5일 | 이벤트 집계 조회, 진단 규칙, 추천 산출, 근거 Case 목록 연결 |
| 검증·통합 | 2~4일 | dry-run 검증 연동, 추천 정확도 확인, UI 표시 |
| 대기 | 0일 | 사람 검토가 필요 없다. 제안까지만 하기 때문이다 |

병목은 **진단 규칙**이다. "몇 건부터 Team이 없다고 볼 것인가"를 정해야 한다.

**폐기 조건**

추천을 3회 연속 운영자가 무시하거나, 추천대로 추가한 Team이 실제 처리율을 올리지 못하면
폐기한다. 그때는 "추천" 대신 "실패 통계만 보여주기"로 축소한다.

### 5.2 VISION-10 2층 갱신 — 교차 프로젝트 추천

기존 2층은 "실제 프로젝트 데이터가 쌓이면 카탈로그 품질을 높인다"였다. 여기에 "여러
배포의 구성을 비교해 함께 쓰이는 조합을 추천한다"를 포함한다고 명시한다.

트리거는 기존 2층과 같다. 릴리스 프로젝트 2개 이상, 인스턴스 3세트 이상이다.

## 6. 확인하지 못한 것

- Codex 검토를 완료하지 못했다. 파일 쓰기 실패로 산출물이 없다. 이 문서는 직접 확인한
  코드 근거와 판단으로 작성했다.
- 실제 운영 배포가 없어 이벤트가 얼마나 쌓이는지 확인하지 못했다. 트리거 수치는 제안이다.
- `case_events`를 기간·유형으로 집계하는 조회가 다른 곳에 이미 있는지 전수 확인하지
  못했다. `repository.py`에서는 확인되지 않았다.
- 추천 결과를 어디에 보여줄지 정하지 못했다. Composer 화면인지 별도 진단 화면인지는
  UI 설계에서 정한다.
