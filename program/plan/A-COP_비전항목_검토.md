# A-COP 비전 항목 검토

## 1. 결론

항목 A는 비전 TODO에 넣을 만하다. 다만 새 Team 아이디어가 아니라 기존 예제 라이브러리, 선언형 Team, Composer 인스턴스 CRUD를 사용자가 한 흐름에서 쓰게 만드는 Phase 2 제품 기능으로 적어야 한다. 계획서 §8-B의 예제 Team 확충 자체는 기존 구현 계획에 남겨야 한다. 항목 B는 하나의 TODO로 넣으면 안 된다. 고객 문서를 RAG 지식으로 바꾸는 기능은 Phase 2 제품 후보로 넣을 가치가 있다. 공개 데이터셋 정리는 개발 도구로 관리해야 한다. 고객사 평가셋 생성은 독립 채점 원칙을 갖춘 품질관리 도구로 별도 검토해야 한다.

## 2. 항목 A 검토

### 판단

사용자는 업무에 맞는 Team 예제를 찾는 시간을 줄일 수 있다. 운영자는 Python 경로와 `project.yaml`을 직접 다루지 않아도 된다. 도입 담당자는 검증된 시작점을 복제한 뒤 이름과 허용 범위만 조정할 수 있다.

이 방향은 기존 계획과 맞는다. `A-COP_예제Team모듈_확충설계.md`는 §8-B의 6개 Team을 예제 후보로 구체화했다. `A-COP_Composer_범위재검토.md`는 카탈로그 기반 인스턴스 CRUD와 `DeclarativeTeamRuntime`을 권고했다. `A-COP_Composer_v3_설계_토글전용_UI이관.md`는 `final_project_sample/examples/`를 예제 라이브러리로 정했다. 구현계획서도 Team 추가가 Core 변경이 아니라 Registry 등록이 되도록 요구한다. 따라서 항목 A는 흩어진 계획 세 개를 하나의 사용자 흐름으로 잇는다는 판단이 맞다.

현재 저장소에는 `examples/catalog.py`와 스캐폴딩 CLI가 있다. 그러나 카탈로그에는 Billing과 Technical 예제 두 개만 있다. UI 선택 생성도 확인되지 않았다. §8-B의 6개 Team을 다루는 예제 확충 계획과 현재 카탈로그는 아직 이어지지 않았다.

### 권고 형태와 시점

비전 항목명은 `검증된 Team 예제 카탈로그와 선택 생성`이 적절하다. “바로 생성”은 활성화 완료가 아니라 검증된 인스턴스 초안 생성으로 정의해야 한다. 생성 뒤에는 설정 검증, 평가, 승인, 재시작 또는 Registry 재적재가 남을 수 있다.

MVP에서는 §8-B의 착수 Team과 계약 테스트를 완성해야 한다. 예제를 늘리기 위해 MVP 범위를 추가로 넓히면 안 된다. Phase 2에서는 다음 흐름을 제공한다.

1. UI가 서버의 서명된 예제 카탈로그를 조회한다.
2. 사용자가 capability, 필요한 지식, 허용 Tool, 위험 수준을 확인한다.
3. 사용자가 예제를 골라 `instance_id`와 설정을 입력한다.
4. 서버가 선언과 권한을 검증하고 새 revision을 저장한다.
5. 평가지표와 승인 문턱을 통과한 인스턴스만 활성화한다.
6. 실패하면 이전 revision으로 되돌린다.

단순 분류, 정책 검색, 사실 조회, 답변 초안은 선언형 Team으로 만드는 편이 자연스럽다. 새 외부 프로토콜, DB transaction, 복잡한 계산, side effect가 필요한 예제는 코드형 Team으로 유지해야 한다. 같은 구현을 복제할 때 capability 충돌을 막을 namespace와 라우팅 정책도 먼저 필요하다.

## 3. 항목 B 검토

“전처리 자동화”에는 목적과 책임이 다른 세 작업이 섞여 있다. 공통 파이프라인 하나로 합치지 말아야 한다.

| 구분 | 산출물 | 성격 | 비전 판단 | 시점 |
|---|---|---|---|---|
| 공개 데이터셋 정리 | `datasets/**/processed/`, 통계, 재현 스크립트 | 연구·개발 도구 | 제품 TODO에 넣지 않는다. 데이터 엔지니어링 백로그로 둔다 | 현재부터 필요할 때 수행 |
| 고객 문서의 RAG 지식화 | 승인된 문서, 청크, 임베딩, 출처와 버전 | 고객 온보딩 제품 기능 | 별도 비전 항목으로 넣는다 | Phase 2 |
| 고객사 평가셋 작성 | golden 후보, 사람 확정 라벨, 봉인된 holdout | 품질관리·검증 도구 | 완전 자동화는 넣지 않는다. 보조 생성과 독립 검증으로 한정한다 | Phase 2 이후 |

### 공개 데이터셋 정리

이 작업은 모델 개발자와 평가 담당자의 반복 작업을 줄인다. `datasets/README.md`의 `raw`, `processed`, `scripts`, `REPORT.md`, `preprocess_stats.json` 규칙과 자연스럽게 이어진다. 각 데이터셋의 스키마, 라이선스, 개인정보, 라벨 의미가 달라 범용 자동 변환을 제품에 넣을 근거는 부족하다. 공통 실행 규약과 검증 리포트 생성은 자동화할 수 있다. 개별 `normalize.py`와 `validate.py`의 도메인 판단은 데이터셋별 도구로 남겨야 한다. 전처리 전 VOC 데이터는 이 개발 백로그의 우선순위를 높이지만 제품 기능의 근거가 되지는 않는다.

### 고객 문서의 RAG 지식화

이 기능은 고객사 관리자와 도입 담당자에게 가치가 있다. 새 고객사를 붙일 때 `knowledge/**`를 사람이 직접 만드는 비용을 줄인다. 현재의 `knowledge_documents`, `knowledge_chunks`, pgvector, `scripts/check_corpus.py`를 확장할 수 있다. Core 계약을 바꿀 필요는 없다. 다만 업로드, 파싱, 개인정보 탐지, 청크 후보 생성, 검토 대기, 승인, 색인, 버전 전환, 롤백을 다루는 수집 관리 계층은 새로 필요하다.

완전 자동 게시를 목표로 삼으면 안 된다. 제품 범위는 “자동 변환 후 사람 승인”이어야 한다. 원문 출처, 적용 기간, tenant, 해시, 변환기 버전, 승인자를 모든 청크에 연결해야 한다.

### 고객사 평가셋 작성

이 작업은 도입 담당자와 품질 담당자의 초기 비용을 줄일 수 있다. 그러나 시스템이 문제와 정답을 함께 만들고 같은 계열 모델이 채점하면 성능 증거가 약해진다. 따라서 자동화 대상은 문항 후보 생성, 중복 제거, 민감정보 마스킹, 형식 검사, 라벨링 화면 제공까지로 제한해야 한다.

golden은 업무 전문가가 독립적으로 확정해야 한다. 계획서의 두 명 독립 라벨링과 제3자 조정 원칙을 유지해야 한다. holdout은 별도 표본에서 만들고 개발자와 생성기가 보지 못하게 봉인해야 한다. 이 기능은 RAG 지식 수집보다 늦게 두는 편이 맞다.

## 4. 위험과 관리 방법

| 위험 | 실제 판단 | 관리 방법 |
|---|---|---|
| 자동 생성 지식의 품질 | 실제 위험이다. 잘못된 청크는 답변 전체의 근거를 오염시킨다 | 자동 결과를 staging에 둔다. 출처와 변환 이력을 보존한다. 중복, 길이, 개인정보, 유효기간을 검사한다. 업무 전문가의 표본 검토와 승인 뒤 색인한다. 검색 평가와 rollback을 운영한다 |
| 자동 평가셋의 자기 채점 | 실제 위험이다. 생성기와 채점기가 같은 편향을 공유할 수 있다 | 생성과 라벨 확정을 분리한다. 사람 독립 라벨과 실제 Case 표본을 사용한다. 합성 데이터만으로 성능을 주장하지 않는다. judge 모델과 prompt 버전을 고정하고 사람 일치도를 확인한다 |
| 고객 데이터의 외부 반출 | 자체 호스팅 목표와 직접 충돌할 수 있는 실제 위험이다 | 수집과 임베딩을 고객사 배포 경계 안에서 실행한다. 외부 OCR, LLM, embedding API는 기본 금지한다. 예외는 고객의 명시적 승인과 전송 목록 기록이 있을 때만 허용한다. tenant 격리, 암호화, 접근 로그, 보존·삭제 정책을 검증한다 |
| holdout 보존 원칙 훼손 | 자동화가 holdout을 검색, prompt 수정, 추천 학습에 사용하면 실제 충돌이다 | holdout 저장소와 권한을 분리한다. checksum과 접근 로그를 남긴다. 생성기, RAG, prompt 개선 입력에서 제외한다. 정해진 평가 실행만 읽게 한다. 노출되면 폐기하고 새 표본을 봉인한다 |

## 5. 의존 관계와 순서

```text
Team Contract와 Registry
          |
          +--> §8-B Team 구현·계약 테스트 --> 예제 Team 확충 --> 카탈로그 등록
          |                                                |
          +--> DeclarativeTeamRuntime ----------------------+
                                                           v
인스턴스 CRUD --> revision·감사·검증 --> 재시작/재적재·rollback --> UI 선택 생성

원문 반입 정책 --> tenant·PII·출처 규칙 --> 지식 staging·품질 게이트
                                                   |
                                                   v
                                      사람 승인 --> RAG 색인·rollback

실제 Case 표본 --> 라벨링 규칙 --> golden 후보 보조 생성 --> 독립 사람 확정
                                               |
별도 표본 -------------------------------------+--> holdout 봉인 --> 평가 전용 실행
```

항목 A에서는 Registry와 Team Contract가 가장 먼저 안정되어야 한다. 그다음 선언형 Team 범용 실행기와 인스턴스 CRUD가 필요하다. 예제 Team은 계약 테스트와 최소 평가 fixture를 통과한 뒤 카탈로그에 올라가야 한다. UI는 마지막 소비자다.

항목 B에서는 데이터 반입 정책이 기능보다 먼저다. 지식 자동화는 staging과 사람 승인까지 검증한 뒤 RAG 색인에 연결해야 한다. 평가셋 보조 생성은 실제 Case와 라벨링 규칙이 확보된 뒤 시작해야 한다. holdout은 생성과 개선 경로에서 처음부터 분리해야 한다.

## 6. 비전 TODO 문서 형태 제안

현재 작업 트리에는 이미 `final_project_sample/docs/vision/TODO_VISION.md`와 개별 `VISION-01`부터 `VISION-10` 문서가 있다. 따라서 `program/plan/`에 두 번째 비전 TODO를 만들면 정본이 둘이 된다. `program/plan/`은 구체적 설계와 이번 검토 문서를 유지해야 한다. 비전 정본은 기존 `final_project_sample/docs/vision/`을 계속 쓰는 편이 충돌이 적다.

기존 `TODO_VISION.md`는 한 줄짜리 인덱스로 유지한다. 각 항목은 상태, MVP 포함 여부, 제품 사용자, 도입 트리거, 선행조건, 검증 기준, 폐기 조건, 관련 설계 문서를 가져야 한다. 구현계획서 §12와 맞추려면 상태를 `MVP`, `Phase 2`, `Phase 2 이후`, `보류`, `폐기`로 제한하는 편이 좋다.

항목 A는 기존 `VISION-10`을 갱신하는 것이 맞다. 이미 완료로 적힌 카탈로그·CLI와 아직 없는 UI 선택 생성, 선언형 Team, 인스턴스 CRUD를 서로 다른 단계로 표시해야 한다. §8-B의 6개 Team 확충은 `A-COP_예제Team모듈_확충설계.md`를 참조하게 한다.

항목 B는 두 문서로 나누는 편이 맞다. 하나는 `고객 지식 수집과 승인형 RAG 색인`이다. 다른 하나는 `평가셋 작성 보조와 독립 검증`이다. 공개 데이터셋 전처리는 비전 인덱스에 넣지 않는다. 그 작업은 `datasets/README.md` 아래의 개발 백로그와 데이터셋별 `REPORT.md`에서 관리한다.

## 7. 확인하지 못한 것

현재 작업 트리에는 미커밋 변경이 많다. `A-COP_예제Team모듈_확충설계.md`의 “`voc_store_manager` 하나만 구현·등록”이라는 기록과 달리 현재 `final_project_cs/config/project.yaml`에는 6개 Team이 활성 선언되어 있다. 현재 카탈로그에는 §8-B의 6개 Team이 아니라 Billing과 Technical 두 예제만 있다. 이 차이 때문에 어느 상태를 배포 기준으로 볼지는 확인하지 못했다.

- Composer의 인스턴스 CRUD와 `DeclarativeTeamRuntime`이 다른 브랜치나 외부 저장소에 구현됐는지 확인하지 못했다.
- 실제 고객사의 문서 형식, 문서량, 갱신 빈도, 업무 전문가 승인 절차를 확인하지 못했다.
- 자체 호스팅 배포에서 OCR, embedding, LLM이 모두 로컬로 실행되는지 확인하지 못했다.
- 고객사 데이터의 보존 기간, 삭제 요구, 국외 이전 금지 조건을 확인하지 못했다.
