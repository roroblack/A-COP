# 여행 전환 현황 — 어디까지 됐고 무엇이 남았나

`[실측 2026-09-09]` 문서가 아니라 **코드·DB·테스트를 직접 세었다.**

---

## 0. 결론 먼저

**Team 층은 붙었다. 그런데 여행 Case 가 지금 라우팅되지 않는다.**

분류기 어휘가 아직 쇼핑몰이라, 여행 Team 여섯이 받는 `case_type` 을
**분류기가 하나도 만들어 내지 못한다.** 실행해서 확인했다.

```
여행 라벨 → ClassificationFailed: classifier returned an invalid intent or sentiment
```

★**2026-08-17 에 한 번 겪은 사고와 같은 모양이다.** 그때는 옛 구독 어휘가
남아 쇼핑몰 Case 가 전부 분류 실패로 떨어졌다. 재발 방지로 만든 불변식
테스트가 있는데 **지금 통과한다** — 그 테스트가 등록조차 안 된 팀 하나만 보기 때문이다.

## 2. 왜 552개가 통과하는데 여행이 안 도나

### 막으라고 만든 가드가 안 막는다

`tests/unit/voc/test_feedback_intent_alignment.py` 는 2026-08-17 사고의
**재발 방지로 만든 테스트**다. 그런데 이렇게 돼 있다.

```python
from app.modules.customer_ops import VocStoreManagerTeam

def test_every_routable_case_type_is_a_classifiable_intent():
    routable = set(VocStoreManagerTeam.manifest.accepted_case_types)
    missing = routable - INTENTS
```

★**등록표가 아니라 팀 하나를 본다.** 그 팀은 지금 `config/project.yaml` 에
**등록조차 안 돼 있다.** 도메인이 바뀌어도 이 테스트는 계속 통과한다 —
없어진 팀을 계속 검사하기 때문이다.

**고정된 예시를 보는 가드는 예시가 사라지면 가드가 아니게 된다.**
등록표(`load_project_config()`)를 읽어야 한다.

### 실제로 대 보면 이렇다

`[실측]`

```
INTENTS                order · shipping · return · exchange · other
여행 Team 이 받는 것    activity · booking · mobility · dining · lodging · flight

INTENTS 에 없는 case_type: 6개 전부
```

분류기는 `intent not in INTENTS` 이면 `ClassificationFailed` 를 던진다
(`feedback.py:118`). 그러면 Case 는 `classification_failed` 를 남기고
`escalated` 로 간다 — **여섯 팀 중 아무도 안 불린다.**

## 3. 여행으로 돌리려면 무엇을 고쳐야 하나

순서가 있다. **앞의 것이 뒤의 전제다.**

### 1순위 — 이것만 고치면 루프가 돈다

| 무엇 | 어디 | 왜 먼저 |
|---|---|---|
| **`INTENTS` 교체** | `app/modules/customer_ops/feedback.py:48` | 이거 하나가 여섯 팀을 전부 막고 있다 |
| **`ISSUE_CODES` 교체** | 동 `:51` | 통과해도 여기서 또 막힌다 (실행해 확인) |
| **가드 테스트를 등록표 기준으로** | `tests/unit/voc/test_feedback_intent_alignment.py` | 안 고치면 다음 도메인에서 또 같은 사고 |

★**분류기가 `customer_ops` 에 있는 것도 정리 대상이다.** 여행으로 갈아끼우면
`travel_ops` 의 어휘를 `customer_ops` 파일이 들고 있게 된다.
`[결정 2026-09-10]` **`config/` 로 뺀다** — 다만 `INTENTS` 만 빼면 부족하다.
**프롬프트에도 커머스 어휘가 리터럴로 박혀 있다**(`feedback.py:81`).
**선언 하나에서 프롬프트·검증·라우팅 셋이 나와야 한다**
→ [설계결정 6건 §6](A-COP_여행MVP_설계결정_6건.md).

### 2순위 — 데이터가 있어야 판정이 돈다

★**코어 14표는 손 안 댄다.** 19표 중 5표만 도메인이다.

## 4. ★정정 — Team 이 넣는 `business_subject` 는 **저장되지 않는다**

`[실측 2026-09-10]` 앞 판에서 *"`travel_ops/_base.py:136` 의 3단 폴백
(`booking_id → trip_id → case_id`)이 문제다"* 라고 적었다. **그 분석의 전제가 틀렸다.**

### 서버가 Team 의 키를 버리고 다시 만든다

`app/application/controller.py:358~366`

```python
for proposal in result.action_proposals:
    # The Team value is advisory. The server owns the final key at the write boundary.
    server_key = idempotency_key(
        tenant_id=..., request_id=request_id_for_case(case),
        action_type=proposal.action_type,
        business_subject=str(case["case_id"]),      # ← 항상 case_id
    )
```

★**Team 이 `booking_id` 를 넣든 폴백으로 `case_id` 를 넣든 결과가 같다.**
그 값은 DB 에 닿지 않는다. **그러니 `_base.py` 의 폴백을 고쳐도 아무것도 안 바뀐다.**

### 충돌하면 두 번째가 사라진다

`app/infrastructure/db/repository.py:44`

```sql
INSERT INTO action_requests (...) VALUES (...)
ON CONFLICT (tenant_id, idempotency_key)
DO UPDATE SET idempotency_key = EXCLUDED.idempotency_key
RETURNING action_id
```

`[실측 2026-09-10]` 살아 있는 DB 에 넣어 확인했다(트랜잭션 롤백, 남긴 것 없음).
한 Case·같은 `action_type`·예약만 다른 제안 둘 —

```
두 제안의 action_id 가 같은가 : True
남은 행 1개 · 인자 ['{"booking_id": "bk-001"}']      ← bk-002 가 없다
```

두 번째 제안의 `arguments_json` 이 **저장되지 않고**, 호출부는 첫 행의 `action_id` 를
받아 `action_ids` 에 같은 값을 두 번 넣는다.

★`DO UPDATE` 는 값을 안 바꾸지만 **`DO NOTHING` 이 아닌 이유가 있다** —
`DO NOTHING` 은 충돌 행을 `RETURNING` 하지 않는다. 기존 `action_id` 를 돌려받으려는
의도적 관용구다.

### 이건 결함인가 — **지금은 잠재 결함이다**

`[검토 2026-09-10]` 이 주장을 적대적 검토에 부쳤고, **내가 과하게 말한 곳이 잡혔다.**

| 내가 적은 것 | 검토가 짚은 것 |
|---|---|
| "두 번째 예약 변경이 **사라진다**" | 지금 여행 Team 은 **전부 `[proposal]` 하나씩** 돌려준다. 저장 경계의 결함은 증명됐지만 **정상 경로가 거기 닿는 것은 증명 안 됐다** |

**그래도 잠재 결함은 실재한다.** `TeamResult` 계약은 제안 여럿을 허용하고 같은
종류의 중복을 막지 않는다. 그리고 **승인 화면도 실행 직전 재검증도 「저장된 행」을
읽으므로, 사라진 것을 되살리지 못한다.**

### 왜 이렇게 만들어졌나 — 근거가 있다

`wiki/records/reports/2026-08-14_S-IDEMKEY_리포트.md` 가 이유를 적어 뒀다.

> 해지 후 결제 환불의 `business_subject` 는 `case_id` 를 선택했다. (…) 동일 Case 를
> 다른 run 에서 재실행해도 같은 환불 행위로 식별해야 하기 때문이다. **결제 식별자가
> 별도 계약 필드로 제공되지 않는 현재 모델에서** case ID 가 감사·승인 흐름의 대상과
> 일치한다.

★**당시엔 옳은 선택이었다.** 환불은 Case 당 하나였고, 결제 식별자를 담을 계약 필드가
없었다. **여행이 그 전제를 둘 다 깬다** — Trip 하나에 예약이 여럿이고, `booking_id` 는
있다.

### 고치는 방향

**서버가 검증한 대상 객체 id 를 키의 `business_subject` 에 넣는다.** 그리고 같은 키에
**다른 인자**가 오면 조용히 넘기지 말고 명시적으로 처리한다.

★`[결정 2026-09-10]` **②를 권한다 — 서버가 대상 객체 id 를 키에 넣는다.**

①("한 Case 에 같은 종류는 하나" 를 사양으로)을 안 고르는 이유 셋.

| | |
|---|---|
| **여행의 사건이 그 모양이 아니다** | "비가 온다" 사건 하나가 액티비티·식당·이동을 한꺼번에 흔든다. Case 를 쪼개면 **한 사건을 여러 Case 로 나눠 놓고 고객에게 따로 통지**하게 된다 |
| **되돌림이 어려워진다** | v10 DoD 8 이 "거부하면 이전 일정 버전으로 되돌린다" 인데, 한 사건이 여러 Case 면 **어디까지 되돌릴지**가 애매해진다 |
| **계약이 이미 여럿을 허용한다** | `TeamResult.action_proposals` 가 목록이다. 사양이 "하나" 라면 계약이 먼저 그렇게 말해야 한다 |

②를 고르면 **조용한 병합이 사라진다.** 지금은 두 번째가 소리 없이 없어지는데,
객체 id 가 키에 들어가면 서로 다른 행이 된다.

★`[결정 2026-09-10]` **`action_type` 접두가 어느 인자에서 id 를 꺼낼지 정한다.**
서버가 규칙표를 갖고, **인자에서 꺼낸 뒤 실재·소유를 확인한 값**만 키에 넣는다.

| `action_type` 접두 | 꺼낼 인자 | 무엇인가 |
|---|---|---|
| `activity.*` · `dining.*` · `booking.*` | `booking_id` | 예약 한 건 |
| `mobility.*` | `item_id` | 일정 항목 한 구간 |
| `trip.*` | `trip_id` | 여행 전체 |

★**없으면 폴백하지 않고 거부한다.** 대상을 특정 못 한 채 실행하면 무엇을 바꾸는지
모르는 작업이 된다. `fulfillment_logistics` 가 이미 그렇게 한다
(`shipment_identity_unknown` 으로 escalate).

★**Team 이 준 값을 그대로 쓰지 않는다.** 서버가 인자에서 꺼내 **실재하는지·이 여행의
것인지 확인한 뒤** 쓴다. 안 그러면 지금 주석이 경계한 자리로 돌아간다 —
*"The Team value is advisory."*

`[미확보]` 규칙표를 코드에 둘지 `config/` 에 둘지는 안 정했다. **어휘를 설정으로
빼기로 했으므로(결정 6) 같이 가는 것이 자연스러워 보이지만, 이건 계약에 더 가깝다.**

## 5. 곁들여 — `_base.py` 의 「315줄」

그 파일 머리말이 커머스 복붙을 **315줄**이라고 적었다. `[실측 2026-09-09]`
직접 세면 팀 안의 `_` 헬퍼 전체가 **327줄**이고, 그중 도메인 규칙
(`_refund_amount` · `_policy_days` · `_sku` 등)이 대부분이라 **공통 성격은
80줄**(`_result` 4곳 · `_evidence` 6곳 · `_escalate` 2곳)이다.

★**결정은 안 바뀐다.** 공용 기반을 만든 것은 옳다. 다만 **이유가 줄 수가 아니라
균일함**이다 — 팀마다 반환 모양이 달랐던 것이 문제였고, 그건 그 파일 머리말도
같이 적고 있다.
