# 아키텍처 브리핑 재설계안 — 무엇이 낡았고 어떻게 다시 그리나

`[2026-09-10]` 대상은 [`program/briefing/A-COP_여행Team모듈_아키텍처.html`](../briefing/A-COP_여행Team모듈_아키텍처.html)
(2026-09-09 작성). **이 문서는 계획서가 아니라 그 브리핑을 다시 그리기 위한 작업
지시서**다. 기준선은 [v11](A-COP_구현계획서_v11.md).

★**교차검증 상태.** 코덱스(gpt-6-astra)로 **범위를 제한한 대조 두 건을 완주했다** —
①브리핑 대 코드 ②논문 대조와 재설계 검토. 아래 ★표는 코덱스가 독립적으로 같은
값을 낸 항목이고, **§2 와 §2-A 는 코덱스가 내 판정을 뒤집은 것**이다.

★`[기록]` **첫 시도는 실패했다.** 범위 제한 없이 던져 저장소를 통째로 읽다가
(로그 466KB) 쿼터를 태우고 중단됐다. **열 파일을 명시하고 「저장소를 훑지 마라」를
넣자 완주했다.** 코덱스에 대조를 시킬 때는 **볼 파일을 세어서 주는 것**이 조건이다.

## 0. 결론 — 다시 그려야 한다

**대조한 16개 중 8개가 어긋난다(50%).**

## 2. ★논문 인용이 틀렸다 — 이게 이번 검증에서 제일 큰 것

논문: **LLM-Enabled Multi-Agent Systems: Empirical Evaluation and Insights into
Emerging Design Patterns & Paradigms** (arXiv:2601.03328, 2026-01).

우리는 이 논문의 **「설계 패턴 다섯」**과 우리 구조를 대조했다고 적어 왔다
([`A-COP_Team모듈_제작_브리핑.html`](../briefing/A-COP_Team모듈_제작_브리핑.html) §4).
**그 다섯은 논문이 제시한 패턴 목록이 아니다.**

`[실측 2026-09-10]` **독립적으로 두 번 확인했다** — 코덱스(gpt-6-astra)가 arXiv HTML 을
받아 §4.2 Table 1 을 읽었고, 나도 따로 원문을 받아 같은 표를 확인했다.

| | 다섯 항목 |
|---|---|
| **논문 §4.2 Table 1 의 분류 차원** | Control Flow(explicit·dynamic) · Interaction Styles(handoff·tool flow) · History Sharing(전체 추론 이력·최종 결과만) · Network Configurations(supervisor·swarm·hierarchical·SIE) · Human Interaction(in-the-loop·on-the-loop) |
| **우리 브리핑이 「논문이 정리한 다섯 패턴」이라 적은 것** | 역할·능력 선언 · 도구 권한 좁히기 · 조정 대 자율 · 사람 승인 경계 · 출력 검증 |

**겹치는 것은 사실상 둘뿐이다** — 「조정 대 자율」이 Control Flow·Network
Configurations 에, 「사람 승인 경계」가 Human Interaction 에 대응한다.
**역할·능력 선언 · 도구 권한 좁히기 · 출력 검증은 Table 1 의 차원이 아니다.**

### 더 나쁜 것 — 논문에 없는 문장을 직접 인용으로 적었다

제작 브리핑이 이렇게 적었다 —

> *"연구는 「제약이 약한 에이전트는 같은 문제를 무한히 되풀이한다 — 최대 반복
> 횟수나 명시적 종료 조건을 강제하라」고 한다"*

`[실측 2026-09-10]` **두 조회 모두 논문 본문에서 이 주장을 찾지 못했다.**
반복 상한·종료 조건 요구는 논문에 없다. **Reflection 이나 「다른 주체가 검증한다」는
정의도 없다** — 논문이 강조하는 것은 **사람의 관여**다(*"all case studies reaffirm
the necessity of human involvement, either in-the-loop or on-the-loop"*).

★**「못 찾았다」와 「없다」는 다르다.** 둘 다 arXiv HTML 판을 봤고 PDF 본문 전체를
줄 단위로 훑은 것은 아니다. **그러나 Table 1 의 차원이 우리가 적은 다섯과 다르다는
것은 확정이다.**

### 그래서 무엇을 고치나

★**대조를 버리는 것이 아니다. 출처를 정직하게 바꾸는 것이다.**

| 지금 | 고칠 것 |
|---|---|
| "논문이 정리한 다섯 패턴" | **"논문의 논의를 우리 점검 항목 다섯으로 재구성했다"** |
| 반복 상한 직접 인용 | **우리 설계 요구사항**으로. 논문 인용을 떼고 우리가 왜 필요하다고 봤는지 적는다 |
| Reflection 정의 인용 | 동. 논문은 **사람 관여**를 말한다 |
| 논문 대조표가 다른 브리핑에만 | 아키텍처 브리핑에도 **P1~P5 앵커**로 (§3 5장) |

★**심사에서 논문을 열면 바로 걸린다.** 그리고 이건 전역 작업 규칙이 경계하는 바로
그 사고다 — **「규정·계약·근거 문서는 검색하지 말고 읽는다」.** 요약만 보고 패턴
이름을 지어 붙였다.

## 2-A. ★내 앞 판정을 철회한다 — 「여섯 중 여섯」은 틀렸다

이 문서 초판에 **"논문이 짚은 구멍 둘이 다 메워졌다 · 다섯 중 넷이 아니라 여섯 중
여섯"** 이라고 적었다. **코덱스 검토가 그것을 반박했고 맞는 지적이다.**

| 내가 적은 것 | 반박 | 내 최종 |
|---|---|---|
| `max_steps` **강제된다** | `_base.py:78` 이 예산을 **전달**하고 `read_tools.py` 에 예외가 **정의**돼 있는 것은 맞다. 그러나 그것은 **도구 호출 예산이 연결됐다**는 증거이지 반복이 멈춘다는 증거가 아니다. **예외가 실제로 나는 조건 · 카운터 수명 · 도구를 안 부르는 LLM 반복**은 확인 안 됐다 | **정정.** "도구 호출 예산이 연결됐다" 까지만 말한다 |
| 출력 검증 **켜졌다** | `build_verification()` 이 여행 정책을 물고 `controller.py:332` 가 `check_proposal` 을 부르는 것은 맞다. 그러나 **①제안 사실 대조**와 **②고객 답변·생성 대안 검증**은 다른 일이다. ②는 확인 안 됐고 `response_review` 는 여전히 `enabled: false` 다 | **정정.** "제안 사실 대조는 붙었다" 까지만 |

★**같은 실패를 또 했다.** 두 자리를 열어 보고 "구멍이 메워졌다"로 넓게 단정했다.
**연결됐다는 것과 막힌다는 것은 다르다.**

★**그래서 「검증」을 세 가지로 갈라 적어야 한다** — 코덱스 제안 그대로다.

| | 무엇 | 지금 |
|---|---|---|
| **도메인 판정** | 영업 여부·이동 가능·취소 조건 | 각 Team 이 한다 |
| **제안 사실 대조** | 실행할 제안을 정책·사실과 대조 | `check_proposal` 로 **붙었다** |
| **고객 전달 전 검증** | 답변·생성 대안이 근거와 맞나 | **확인 못 했다.** `response_review` 는 꺼져 있다 |

**지금 브리핑은 Team 의 「도메인 판정」을 자세히 설명하면서 그것이 뒤의 둘까지
한다는 인상을 준다.** 그 셋을 갈라 그리는 것이 §3 4장이다.

## 3. 다시 그린다면 — 장 여섯

★**축을 바꾼다.** 지금은 「무엇이 있나」인데, **「누가 판단하고 누가 실행하나 → 그
경계를 어떤 계약과 검사로 지키나」** 로 간다. 팀별 소개는 그 뒤다.

★**모든 도해에 같은 표식을 쓴다.** 점검 항목 **P1 역할·능력 / P2 도구 권한 /
P3 조정·자율 / P4 사람 승인 / P5 출력 검증** (§2 대로 **논문 패턴이 아니라 우리
점검 항목**이라고 적는다).

★★**상태를 색으로만 칠하지 않는다.** 글자로 병기한다 —
**코드 확인 · 문서 기재 · 미확인 · 미구현/미등록.** 지금 `6 LIVE`·`STUB`·`OPEN` 이
**등록 여부·기능 범위·검증 수준을 한 종류처럼 섞어** 놓아 무엇이 안 된 건지 안 보인다.

| 장 | 도해에 무엇이 들어가나 | 왜 |
|---|---|---|
| **1. 누가 판단하고 누가 실행하나** | 외부 요청 · Controller · 여섯 Team · 읽기 도구 · **제안 대조** · **승인자** · Action Layer. 화살표에 `TeamTask`·`TeamResult`·`ActionProposal`. **답변 반환 경로와 변경 제안 경로를 갈라 그린다** | 지금 전체도는 **승인자와 대조 단계가 없다.** P3=Controller · P2=도구 경계 · P4=승인자 · P5=제안 대조 |
| **2. Team 이 받을 수 있는 일과 돌려줄 수 있는 것** | 왼쪽 `manifest`(team_id·capabilities·**accepted_case_types**·max_steps) → 가운데 `TeamTask` → 오른쪽 `TeamResult`. **선언과 실행 시 검사를 선으로 잇는다** | **`accepted_case_types` 가 지금 브리핑에 0회다.** 「역할을 적었다」와 「범위를 검사한다」는 다르다. P1·P2 |
| **3. Team 하나의 실행과 중단 조건** | 가드 셋 → 조회(허용목록·중복·예산 **세 항목을 갈라서**) → 근거 누적 → 판정 → 반환. **`_unknown` 은 독립 종료가 아니라 「모름 사유를 가진 ESCALATE」로** 그린다 | `[실측]` `_base.py:154` 의 `_unknown` 이 실제로 `_escalate()` 를 부른다. 지금 도해는 넷을 나란히 놔 따로인 것처럼 보인다 |
| **4. ★검증 셋을 갈라 그린다** | 두 판. **제안 판**: 제안 → 사실 대조 → 승인/거부 → 실행 직전 재대조 → Action. 옆에 `build_verification → 여행 정책 → check_proposal`. **답변 판**: 판정·생성 대안 → 검증 여부 → 고객. **확인 못 한 연결은 점선에 「미확인」** | §2-A 의 셋(도메인 판정·제안 대조·전달 전 검증)을 안 가르면 **Team 판정이 전부를 보증하는 것처럼 읽힌다** |
| **5. 여섯 Team 은 무엇이 다른가** | 공통 가드 도해를 **반복하지 않는다.** `대상 / capability / 조회 / 판정 / 응답·제안 / 기능 제한` 표 먼저, 팀별 **고유 분기만** 작은 도해로 | 지금은 팀마다 같은 뼈대를 다시 그려 자리를 먹고 차이가 안 보인다 |
| **6. 아직 보장 못 하는 것** | `항목 / 지금 근거 / 사용자에게 생기는 제한 / **완료 확인 기준**` 표 | ★**「완료 확인 기준」이 핵심이다** — 무엇을 보이면 상태가 바뀌는지 적어야 다음 사람이 닫을 수 있다 |

### 6장 표는 이렇게 시작한다

| 항목 | 지금 상태 | 완료 확인 기준 |

### ★근거가 어디서 와서 어디로 가나 — 도해에 반드시 넣는다

## 5. v2 를 만들었고 검토를 거쳤다

`[2026-09-10]` [`../briefing/A-COP_여행Team모듈_아키텍처_v2.html`](../briefing/A-COP_여행Team모듈_아키텍처_v2.html)
로 새 파일을 만들었다. **v1 은 안 건드렸다** — 다른 세션의 미커밋 변경이 있었다.

★**코덱스(gpt-6-astra) 검토가 내가 새로 넣은 오류 다섯을 잡았다.** 전부 코드를 열어
확인하고 고쳤다.

| 코덱스가 잡은 것 | 실제 | 고침 |
|---|---|---|
| 가드 줄 번호 `56·60·62` | **`57·61·63`** — 56은 독스트링 끝, 60은 HANDOFF 인자, 62는 capability 실패 반환 | 셋 다 교체 |
| `_result → RESPOND` | **`_result` 는 네 갈래를 다 만드는 공용 함수다.** `_guard` 의 HANDOFF 도 이걸 쓴다(`:58`) | 상자 다시 씀 |
| `_proposal → WAIT_FOR_APPROVAL` | **`_proposal` 은 `ActionProposal` 만 돌려준다.** `approval_required=True` 는 붙이지만 `next_action` 은 안 정한다 — `_result:127` 이 `wait_reason` 을 채운다 | 갈라서 적음 |
| 02장 대응선이 `accepted_case_types → capability` 로 이어짐 | **뜻이 다른 칸을 이었다.** `_guard` 는 `case_type` 을 안 본다 — Controller 가 이미 팀을 골라서 보낸다 | 선을 다시 긋고 「팀은 이미 정해져서 온다」를 적음 |
| 「검증은 세 가지」인데 표는 넷 | 도메인 판정 · 제안 대조 · **실행 직전 재대조** · 전달 전 검증 | 넷으로 |

★**과장도 잡혔다.** 「제안 사실 대조 — 코드 확인」은 **호출이 있다는 것까지만** 정당하다
(대조 규칙의 내용과 실제 차단 경로는 확인 못 했다) → **「호출 확인」으로** 좁혔다.
「실행 직전 재대조」는 본문이 「미확인」인데 도해가 **실선으로** 이어 단정하고 있었다 →
**점선으로** 바꾸고 레인 제목에 「실선은 확인한 것, 점선은 확인 못 한 것」을 적었다.

★**빠진 것도 채웠다** — 여섯 팀 모두 `default_capability` 가 있다는 것(고를 장치가
없으면 **못 고르는 게 아니라 항상 같은 것으로 간다**) · `a2a_executor.enabled: false` ·
`team_executor: local` · 팀이 붙인 멱등 키를 **서버가 다시 만든다**는 것 ·
`_evidence` 는 `base` 를 줘야 쌓인다는 것 · Booking Handoff 만 capability 접두가
팀 이름과 다르다는 것.

★**말풀이 절을 앞에 넣었다** — `case_type`·`intent`·`degraded`·`ContextPack`·멱등 키·바깥함.
그리고 v1 변경 이력을 **뒤로 옮겼다** — 구조를 먼저 읽게.

### 검토를 세 번 돌렸다 — 매 바퀴 진짜가 나왔다

★**한 번으로는 안 끝났다.** 고치면서 새 오류가 들어갔고, 그것을 다음 바퀴가 잡았다.

|---|---|
