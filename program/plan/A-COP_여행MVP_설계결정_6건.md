## 1. 조건 — ★뒤집는다. 다섯 칸에 넣지 않되 **버리지도 않는다**

### 내가 틀렸다

처음엔 *"동행 조건은 Trip 수준 속성이라 항목 칸에 안 넣어도 된다"* 고 적었다.
근거는 `dining.py:83` 하나였다 — 조건을 `task.context.current_state` 에서 읽는다.

**구현 하나를 보고 설계를 단정했다.**

`[실측 2026-09-10]` 같은 저장소에 **항목 수준 조건이 이미 있다.**

```python
# app/modules/travel_ops/activity.py:129
party = booking.get("party_size")       # ← 예약(항목)에서 온다
capacity = booking.get("capacity")
if party is not None and capacity is not None and party > capacity:
    ...  "인원이 정원을 넘습니다"
```

| 조건 | 어디서 읽나 | 수준 |
|---|---|---|
| `dietary` (할랄·채식) | `context.current_state` | **Trip/Case** |
| `party_size` | `booking` | **항목** |

**둘 다 있다.** 액티비티마다 인원이 다를 수 있고, 저녁마다 동행이 다를 수 있다.

### 그래서 이렇게 한다

**다섯 칸은 그대로 두되, 조건을 별도로 보존하고 연결한다.**

```
itinerary_items   {시작, 끝, 장소, 비용, 잠김여부}      ← 다섯 칸 유지
trip_constraints  Trip 수준 조건 (할랄·채식·아이 동반)
item_constraints  항목 수준 조건 (인원·연령 제한 등)
```

★**정규화하면서 조건을 버리면 검증 자체가 틀린다.** 조건을 못 본 채
"성립한다" 고 판정하면 **필수 조건을 위반한 일정을 정상으로 통과시킨다.**
그게 이 제품이 파는 것의 반대다.

★`[결정 2026-09-10]` **한 표에 「무엇에 붙는가」 칸을 둔다.** 두 표로 나누면
같은 종류의 조건을 두 곳에서 찾게 되고, 조건이 하나 늘 때마다 어느 표인지 먼저
정해야 한다.

```
trip_constraints(가칭)
    scope       trip | item        ← 무엇에 붙는가
    ref_id      trip_id 또는 item_id
    kind        dietary · party_size · age_limit …
    value
```

★**Trip 조건이 항목 조건을 덮지 않는다.** 둘 다 만족해야 통과다 — 여행 전체가
채식인데 이 액티비티는 인원 초과면 그건 여전히 불가다.

`[미확보]` 표 이름과 칸 이름은 DB 설계에서 확정한다. **한 표로 간다는 것이 결정이다.**

## 2. 감시 소스 설정 — `config/` 에 두되 검증을 붙인다

**유지한다.** `TeamManifest` 에 칸을 더하면 계약 변경이고 Registry·A2A·평가
하네스가 다 걸린다. `config/project.yaml` 은 이미 Team 등록·모듈 토글을 담는다.

### 검토가 짚은 것 — 지금 검증이 그것까지 안 본다

`load_project_config()` 가 기동 때 `_validate_active_team_implementations` 로
`implementation_ref` 를 실제로 import 해 본다. **그런데 새로 넣을 감시 설정은
그 검사 대상이 아니다.**

★**같은 자리에 검사를 하나 더 붙인다** — *"선언한 감시 소스가 등록된 Team·
capability 를 가리키나."* 안 붙이면 오타 하나가 **조용히 감시 안 됨**으로 끝난다.

★**"두 군데를 뒤져야 한다" 는 지적도 맞다.** 감시 실행은 Team 밖(되잡기 작업)에
두되, **"어느 Team 이 무엇을 보는가" 를 한 번에 조회할 수 있게** 한다.

## 3. 알림 수신 주체 — 에이전트 우선. 다만 **전달 책임을 생략하지 않는다**

**유지한다.** 그리고 근거가 내가 든 것보다 강하다.

`[실측 2026-09-10]` v10 §1 —

> **접점** | 고객의 개인 에이전트. 우리는 **API 로만** 만난다. 자체 앱·음성
> (STT/TTS)은 만들지 않는다

★**"제출자가 수신자" 라는 내 추론은 약했다.** 진짜 근거는 이것이다 —
**계획서가 접점을 에이전트로 못박았고 자체 앱을 안 만든다고 했다.**

### 검토가 짚은 것 — 웹훅 성공은 인지가 아니다

**보냈다** 와 **여행자가 알았다** 는 다르다. 사람을 부차로 두는 것과
사람에게 닿을 책임을 없애는 것은 다르다.

**정해야 하는 것 셋** — 긴급 통지의 **전달 기한** · **수신 확인** · **실패 시 처리**.
그리고 그것은 **우리와 외부 에이전트 사이의 계약**이다.

`[미확보]` 그 셋이 안 정해졌다. 다만 **누가 정해야 하는지는 정해졌다** — 우리가
혼자 정할 수 없고 에이전트 쪽과 맞춰야 한다.

## 4. 시연 기상 — Mock 기본. **재생임을 표시한다**

**유지한다.** 발표날 비가 안 오면 시연이 안 된다.

### 검토가 짚은 것 — 과거 재생은 별도 경로다

`[실측 2026-09-10]` `open_meteo.py:94`

```python
ahead = (target.date() - datetime.now().date()).days
if ahead < 0 or ahead >= MAX_FORECAST_DAYS:
    return None          # ← 과거 날짜는 "모름"
```

**과거 날짜를 넣어도 안 된다.** "지난주 폭우를 재생하자" 는 지금 어댑터로 안 된다.

★**더 중요한 지적** — 사후 **관측값**을 당시 **예보**처럼 쓰면 안 된다.
그 어댑터가 반환값을 `kind="forecast"` 로 표시하는 이유가 그것이다.

**그래서 재생은 이렇게 한다** — 저장해 둔 **예보 응답**과 **시뮬레이션 시각**을 쓰고,
**재생이라는 것을 표시한다.** 관측을 예보로 둔갑시키지 않는다.

★그리고 **실물 조회도 따로 한 번은 보여야 한다.** v10 이 기상을 직접 쓴다고
했으므로, Mock 시연만 하면 그 주장을 증명 못 한다.

## 5. 알림 채널 — 디스코드 하나만. **셋 다 만들지 않는다**

**유지하되 범위를 줄인다.**

### 검토가 짚은 것 — 두 가지

**하나.** 결정 3의 **에이전트 웹훅**과 디스코드 **시연 출력**은 목적이 다르다.
전자는 제품 경로이고 후자는 발표장에서 보이게 하는 것이다. 섞어 적었다.

**둘.** *"콜러블 하나만 갈아 끼우면 된다"* 고 적었지만 **오류·재시도·중복 처리까지
공짜는 아니다.** 7주에 세 채널을 만들 이유가 없다.

★**디스코드 하나만 만든다.** 실제 인바운드 여행자가 디스코드를 쓰느냐는
질문은 맞는데, **이건 제품 기본 채널이 아니라 시연 출력이다.** 제품 경로는
결정 3의 에이전트 API 다.

## 6. 분류 어휘를 `config/` 로 — **프롬프트도 같은 선언에서 나와야 한다**

**유지한다.** 다만 내가 *"다음 도메인부터 코드를 안 고친다"* 고 한 것은 과장이었다.

### 검토가 짚은 것 — 프롬프트에 커머스 어휘가 박혀 있다

`[실측 2026-09-10]` `app/modules/customer_ops/feedback.py:81`

```python
"intent is order|shipping|return|exchange|other; sentiment is "     # ← 리터럴
...
"issue_code must be one of: " + ", ".join(sorted(ISSUE_CODES))      # ← 상수에서
```

★**`issue_code` 는 상수에서 만드는데 `intent` 만 문자열로 박혀 있다.**
`INTENTS` 만 설정으로 빼면 **프롬프트는 여전히 커머스를 말한다.**

### 그래서 규칙을 하나 더 붙인다

> **선언 하나에서 셋이 나온다 — 프롬프트 · 출력 검증 · 라우팅.**

지금은 프롬프트(문자열)와 검증(`INTENTS`)이 **따로 있어서 갈라질 수 있다.**
실제로 `intent` 가 그렇게 갈라져 있다.

★검증할 것도 늘어난다 — `intent`·`issue_code` 의 **조합**이 말이 되나,
그 `issue_code` 접두가 **등록된 Team** 을 가리키나, **기존 Case 의 어휘 버전**은
어떻게 되나.

★**같은 검사를 CI 와 기동 때 둘 다 돌린다.** 그러면 오타가 배포 전에 잡힌다.
설정으로 빼는 대가가 "런타임 실패" 가 되지 않게 하는 방법이 이것이다.

## 7. 검토에서 배운 것

★**가장 위험했던 것은 결정 1이었다.** 검토자의 말 그대로 —
*"입력 조건을 잃으면 필수 조건을 위반한 일정을 정상 판정한다.
MVP 의 핵심인 검증 신뢰성을 직접 무너뜨린다."*

**내가 그걸 「안 넣어도 된다」로 결론 냈던 이유**는 `dining.py` 한 줄을 보고
전체를 단정했기 때문이다. 같은 폴더의 `activity.py` 에 반례가 있었다.

**좁게 확인하고 넓게 단정했다.** 여섯 중 하나에서 그랬고, 나머지 다섯도
"조건부" 였다 — 전부 **내가 안 본 것**이 하나씩 있었다.
