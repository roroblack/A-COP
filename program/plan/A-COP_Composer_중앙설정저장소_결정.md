# A-COP Composer — 중앙 설정 저장소 결정 (2026-08-29)

이 문서는 Composer 의 **설정 저장 위치**에 대한 결정 기록이다. 이 주제에서
다른 문서와 충돌하면 **이 문서를 따른다.**

## 1. 결정

**설정을 대상 서버의 파일이 아니라 우리가 운영하는 중앙 저장소에 둔다.**
Composer(쓰기 코드)는 **중앙 설정 서비스 한 곳에만** 설치한다. 릴리즈되는
대상(cs) 수천 개에는 설치하지 않는다.

## 2. 왜 — 두 요구가 지금 구조에서 충돌했다

이 결정 전까지 다음 두 요구가 동시에 성립하지 않았다. 그 사실을 여기 남긴다
— 적어두지 않으면 다음 사람이 또 "관리용 빌드로 하면 되죠" 라고 답하고 같은
자리로 돌아온다(이번 세션에서 실제로 반복됐다).

| 요구 | 근거 | 지금 구조에서의 결과 |
|---|---|---|
| 컴포저가 고객 릴리즈에 딸려나가면 안 된다 | 보안. 쓰기 가능한 구성 관리 API 가 고객 대면 프로세스에 있으면 취약점 하나가 서비스 전체에 닿는다 | 고객 빌드에서 `acop_composer` 제거 |
| 릴리즈 이후에도 관리할 수 있어야 한다 | 운영. 모듈·Team 을 켜고 끄고 인스턴스를 만든다 | 관리하려면 대상 안에 쓰기 코드가 있어야 한다 |

설정이 **대상마다의 로컬 파일**(`config/project.yaml`)이라 쓰기 코드가 그
파일 옆에 있어야 했다. 그래서 "고객 빌드엔 빼고, 관리할 땐 다시 넣는다" 가
되는데, 대상이 수천 개면 이건 성립하지 않는다.

★이 충돌은 **설정을 파일로 두는 한** 해소되지 않는다. 배포 기법(사이드카,
빌드 분리)으로 완화할 수는 있어도 근본은 저장 위치 문제다.

## 3. 어떻게 바뀌나

### 3.1 지금

```
고객사 1 서버:   cs + config/project.yaml(파일)   ← 고치려면 여기 안에 composer 필요
고객사 2 서버:   cs + config/project.yaml(파일)   ← 여기도
...
고객사 3000:    cs + config/project.yaml(파일)   ← 여기도
```

### 3.2 결정 후

```
        [우리 회사]                              [고객사 3000곳]

  UI 화면 ──▶ 설정 서비스 1개 ──▶ 설정 저장소       cs #1  ──┐
             (여기에만 composer)     (중앙 DB)      cs #2  ──┼─ 기동 시 자기 설정을
                                        ▲          ...     │  중앙에서 **읽는다**
                                        └──────────cs #3000┘  (쓰기 없음)
```

- Composer 는 **1곳에만** 설치된다. 3000번 설치하지 않는다.
- 대상은 설정을 **읽기만** 한다. 쓰기 코드가 필요 없으므로 고객 빌드에
  `acop_composer` 가 없다 — 보안 요구가 지켜진다.
- 설정을 바꿀 때 **고객 서버에 접속하지 않는다.** 중앙만 고친다 — 운영
  요구가 지켜진다.
- 재설치·재임포트가 발생하지 않는다.

## 4. 용어 (이 문서에서 쓰는 뜻)

| 말 | 뜻 |
|---|---|
| 대상 | 고객사에 배포된 cs 인스턴스. 수천 개 |
| 설정 | 어떤 모듈·Port·Team 이 켜져 있는지의 선언. 지금은 `config/project.yaml` |
| 중앙 설정 저장소 | 우리가 운영하는 DB. 모든 대상의 설정이 여기 있다 |
| 설정 서비스 | 그 DB 앞의 서비스 1개. `acop_composer` 가 여기 설치된다 |
| UI | `final_project_ui`. 우리가 운영하는 관리 화면 하나 |
| `acop_composer_ui` | UI 가 HTTP 호출에 쓰는 클라이언트 라이브러리 |

## 5. ★UI 에서 모듈·인스턴스 CRUD 가 되는가 — 된다

**계약과 화면은 그대로 쓴다.** 2026-08-28~29 에 만든 것이 이 구조에서
그대로 유효하다. 부르는 주소가 "대상" 에서 "설정 서비스" 로 바뀔 뿐,
요청·응답 모양은 같다.

| 이미 만든 것 | 이 결정 후 |
|---|---|
| `GET /composer/catalog` | 그대로 |
| `POST /composer/changes`(create/update/delete/enable/disable, dry_run, idempotency) | 그대로 |
| `POST /composer/toggle` | 그대로 |
| UI 화면(인스턴스 만들기 카드, 지우기) | 그대로 |
| `acop_composer_ui` 클라이언트 | 그대로 |
| 선언형 Team 실행기(`acop_basement/teams/`) | 그대로 — 대상에서 돈다 |
| grant ceiling(읽기 전용 tool 강제) | 그대로 |

즉 **UI 에서 모듈·인스턴스 CRUD 는 이미 되고, 이 결정으로 수천 대상까지
확장된다.**

## 6. 무엇을 고쳐야 하나

바꿔야 할 것은 **저장 계층 하나**다. 나머지는 위 표대로 유지된다.

| 지점 | 지금 | 바꿀 것 |
|---|---|---|
| `acop_composer/service.py` | 로컬 YAML 파일 + `os.replace()` 원자 교체 | 중앙 DB 행(row) 조건부 쓰기 |
| 동시성 | 프로세스 로컬 `threading.Lock` | DB 조건부 쓰기(CAS). ★`base_revision` 낙관적 동시성은 **이미 있다** — 그대로 쓴다 |
| 대상의 설정 읽기 | `load_project_config()` 가 로컬 파일을 읽음 | 중앙에서 자기 설정을 받아옴(부트스트랩 + 캐시) |
| 대상 식별 | 없음(파일 하나뿐이라 필요 없었다) | **필요하다** — 어느 대상의 설정인지 구분할 키 |
| 감사 로그 | `var/audit/composer_events.jsonl`(파일) | append-only DB 테이블. ★계약(actor·revision·changed_fields·reason)은 그대로 |

★`_WRITE_LOCK` 이 프로세스 로컬이라 다중 인스턴스에서 깨진다는 것은 이미
`docs/handoff/13` 이 한계로 적어둔 사항이다. 중앙 저장소로 가면 그 한계가
자연히 해소된다.

## 7. 이 결정이 바꾸지 않는 것

- **저장됐다고 반영된 것이 아니다.** 대상은 기동 시 설정을 읽으므로 변경
  후에도 재시작(또는 별도 reload 계약)이 필요하다. `/composer/changes` 가
  `activation_state: pending_restart` 를 돌려주는 것은 중앙 저장소에서도
  그대로다. 화면은 이 사실을 계속 정직하게 표시한다.
- **유효성 판정은 서버가 한다.** UI 는 판정하지 않는다.
- **선언형 Team 의 grant ceiling** — 읽기 전용 tool 만 허용하는 규칙은
  저장 위치와 무관하게 유지된다.

## 8. 아직 정하지 않은 것

정직하게 적는다. 이 결정은 **방향**이고, 아래는 착수 시 정해야 한다.

- 중앙 저장소의 구체 형태(기존 PostgreSQL 재사용 vs 별도 서비스)
- 대상 식별 방식(배포 ID·테넌트 ID·인증서 중 무엇으로 자기를 증명하나)
- 대상이 중앙에 못 붙을 때의 동작 — ★**마지막으로 성공한 설정을 캐시해
  계속 도는가, 아니면 기동을 거부하는가.** 조용한 폴백을 만들지 않는다는
  원칙상 어느 쪽이든 명시적으로 정해야 한다
- 설정 변경의 대상 반영 방법(재시작 / reload endpoint / polling) — 기존
  `docs/reports/2026-08-19_Composer_reload_계약_설계검토.md` 가 남긴 숙제와
  같은 문제다
- 마이그레이션 경로(지금 파일 기반으로 도는 sample·cs 를 어떻게 옮기나)
- 이 작업을 이번 10주 안에 하는가, 이후로 미루는가

## 9. 이 결정이 틀릴 수 있는 조건

실제 배포 대상이 수천이 아니라 **수십 개 이하로 확정**되는 경우다. 그
규모에서는 중앙 저장소의 운영 부담(가용성·백업·마이그레이션)이 얻는 것보다
클 수 있고, 사이드카나 대상별 관리용 빌드로도 충분하다.
