# 지속 관리 루프와 알림 — 설계

`[초안 2026-09-09]` "계속 돌면서 일정 변경 있나 체크하다가 결과를 소비자에게
알림" 을 어떻게 만드는가. **답은 전부 코드를 열어 확인한 위에 쓴다.**

---

## 0. 결론 먼저

**루프는 하나가 아니라 둘이다. 둘 다 이미 있는 패턴이다.**

```
① 감시 루프    trip_watch_sweeper      변화가 있나 본다        ← 새로 만든다
② 배달 루프    OutboxWorker            알림을 실제로 보낸다     ← 이미 있다
```

★**둘을 하나로 합치면 안 된다.** 감시가 막히면 배달도 멈추고, 배달이 실패하면
감시가 다시 안 돈다. 지금 코드가 이미 나눠 놨다.

---

## 1. ★먼저 — 라우팅 축이 어긋나 있다

`[실측 2026-09-09]` 루프를 만들기 전에 이게 먼저다. **지금 여행 Case 는
Team 에 도달하지 못한다.**

### 실행해서 확인한 것

등록된 여섯 팀에 라벨을 넣어 봤다.

| 넣은 값 | 결과 |
|---|---|
| `activity` · `booking` · `dining` | **라우팅 됨** → `activity` · `booking_handoff` · `dining` |
| `사건 신고` · `일정 제출` · `확인 요청` | **전부 라우팅 실패** |

★**v10 §5-A 가 정한 코어 1 분류 라벨로는 라우팅이 안 된다.**

### 왜 그런가

`app/application/controller.py:71`

```python
entry = self.registry.resolve(case_type=intent or "", intent=intent)
                              ^^^^^^^^^^^^^^^^^^^^^^  같은 값을 둘 다에 넘긴다
```

레지스트리는 **두 축**을 받는다 — `case_type` 은 어느 Team 인지, `intent` 는
그 Team 의 어느 capability 인지. 그런데 컨트롤러가 **하나로 뭉개서** 넘긴다.

그래서 `intent` 가 곧 Team 선택 값이 되고, Team 이 받는 것은 **객체 종류**
(`activity` · `booking` · …)이므로 `intent` 도 객체 종류여야 한다.

**v10 §5-A 의 다섯(일정 제출 / 사건 신고 / 확인 요청 / 조정 거부 / 그 외)은
객체 종류가 아니라 "고객이 무엇을 원하나" 다. 다른 축이다.**

### 그래서 셋 중 하나를 정해야 한다

| 안 | 무엇 | 대가 |
|---|---|---|
| **A. 두 축을 다 쓴다** | 분류기가 **객체 종류**와 **요청 종류**를 **둘 다** 낸다. `case_type` = 객체, `intent` = 요청 | 컨트롤러 한 줄과 `Classification` 한 칸. **레지스트리는 이미 두 축을 받는다** |
| B. 객체 종류만 쓴다 | `INTENTS` 를 객체 여섯으로 바꾸고 v10 §5-A 라벨은 버린다 | v10 이 정한 것을 버린다. "조정 거부" 를 표현할 자리가 없어진다 |
| C. 요청 종류만 쓴다 | Team 의 `accepted_case_types` 를 다섯 라벨로 바꾼다 | **여섯 팀을 다섯 라벨로 못 가른다.** 성립하지 않는다 |

★**A 를 권한다.** 레지스트리가 이미 `resolve(case_type, intent)` 로 두 축을
받게 만들어져 있다 — **설계는 이미 A 다. 컨트롤러가 그걸 안 쓰고 있을 뿐이다.**

`Classification` 은 지금 넷이다 — `sentiment` · `intent` · `issue_code` · `severity`.

★`[실측 2026-09-10]` **칸을 더하는 것은 코어 계약 변경이 아니다.** `Classification` 은
`app/modules/customer_ops/feedback.py:41` 의 frozen dataclass 이고 `app/core/` 에는
**없다**. 쓰는 곳도 그 파일 하나다. Registry·A2A·평가 하네스가 안 걸린다.

★**그래도 더하지 않는다.** `issue_code` 가 이미 객체 종류를 접두로 달고 있어
(`order_payment_failed` · `shipping_delayed`) **거기서 `case_type` 을 뽑으면 된다.**
칸을 안 늘리는 쪽이 항상 싸다 → [분류어휘 명세](A-COP_여행_분류어휘와_라우팅_명세.md).

## 2. 감시 루프 ① — `trip_watch_sweeper`

### 이미 있는 자리에 넷째로 놓는다

`[실측 2026-09-09]` 주기 실행은 전부 `app/application/` 에 있고 **Team 이 아니다.**

| 있는 것 | 줄수 |
|---|---:|
| `classification_sweeper.py` | 90 |
| `routing_sweeper.py` | 92 |
| `feedback_job.py` | 107 |

실행기 `scripts/run_sweepers.py` 도 있다 — `--once`(cron) / `--interval`(상주),
`errored` 가 있으면 **exit 1**.

### 무엇을 하나

```
trip_watch_sweeper
  1  다음 확인 시점이 지난 Trip 을 집는다      watch_schedule 에서 읽는다
  2  감시 소스를 조회한다                     기상 · 운영 공지 · 운행 정보
  3  변화 없으면 → 다음 확인 시점만 갱신하고 끝
  4  변화 있으면 → Case 를 만든다             ← 여기서부터 기존 경로 그대로
```

★**4번이 핵심이다.** sweeper 는 **Case 를 만들기만 한다.** 판정도 재계획도
안 한다 — 그건 기존 경로(분류 → Team → 재검증)가 이미 하는 일이다.
**sweeper 가 판정까지 하면 Team 을 두 벌 만들게 된다.**

★**Team 은 여전히 불려서 돈다.** v10 §5 의 「② 감시 소스」는 Team 의 능력이
아니라 **sweeper 가 무엇을 볼지의 목록**으로 읽어야 한다.

### 주기는 코드가 정하지 않는다

기존 sweeper 가 그렇게 돼 있고 이유가 주석에 있다 —
*"상주 루프를 기본으로 두면 언제 도는지가 코드에 숨는다."*

임계값은 `config/guardrails.yaml`, 부르는 주기는 운영이 정한다.
v10 §9-A 가 최소 주기를 이미 적었다 — **출발 전날 / 매일 아침 / 각 예약 2시간 전.**

## 3. 배달 루프 ② — 이미 있다

`[실측 2026-09-09]` `OutboxWorker` 가 이렇게 생겼다.

```python
OutboxWorker(connection_factory, publisher: Callable[[dict], Any], *,
             max_attempts=3, tenant_id=None)
```

★**`publisher` 가 그냥 콜러블 하나다.** 텔레그램이든 디코든 이메일이든
**함수 하나를 주면 끝난다.** 어댑터를 위한 자리가 이미 열려 있다.

이미 들어 있는 것 — 재시도 `max_attempts=3` · 죽은 워커의 잠금 회수
(`status='unknown'` 으로 사람이 보게) · tenant 별 분리 실행 ·
`UNIQUE(tenant_id, topic, dedupe_key)` 로 **중복 발행을 DB 가 막는다.**

```
재계획·재검증 통과
   ↓  outbox.publish("trip.notice", payload, dedupe_key)
outbox 행 (pending)
   ↓  OutboxWorker.process_once()
publisher(...)  →  텔레그램 / 디코 / 이메일
   ↓  성공하면 status='delivered'
```

★**행을 지우지 않는다**(`worker.py` 첫 줄: *"without deleting them"*).
무엇을 언제 보냈는지가 남는다 — 알림은 "보냈다" 를 증명해야 하는 일이다.

## 4. 알림 채널 — 무료 셋 비교

`[외부]` 아래 성질은 각 서비스의 공개 문서에서 아는 것이고, **이 프로젝트에서
실제로 붙여 확인한 것은 아니다.** 붙일 때 확인해야 한다.

| | 붙이는 비용 | 받는 사람이 할 일 | 시연에 좋은가 |
|---|---|---|---|
| **디스코드 웹훅** | **가장 싸다** — URL 하나에 POST | 없음 (채널만 있으면 됨) | **가장 좋다** |
| **텔레그램 봇** | 봇 토큰 + `chat_id` | **먼저 봇에게 말을 걸어야** `chat_id` 가 생긴다 | 보통 |
| **이메일(SMTP)** | 계정 + 앱 비밀번호 | 없음 | 스팸함 위험 |

★**시연에는 디스코드 웹훅을 권한다.** 받는 사람 쪽 준비가 **없다** — 발표장에서
채널 하나 열어 두면 알림이 뜬다. 텔레그램은 시연 직전에 봇을 시작시켜야 하고,
이메일은 스팸으로 빠지면 시연이 안 된다.

★**어느 것을 골라도 코드는 같다.** `publisher` 함수 하나이므로 **셋을 다 만들어
두고 설정으로 고르는 것**도 된다. 그게 v10 §6 의 "Ports" 성질과 맞는다.

★`[결정 2026-09-10]` **비밀은 `.env`, 나머지는 `config/`.** 이 저장소에
**관례가 이미 있다** — `.env` 는 커밋하지 않고(`ACOP_OPENAI_API_KEY` 등), 형식만
`.env.example` 로 올린다. 루트에도 `.env.teamflow` / `.env.teamflow.example` 이
같은 모양이다. **웹훅 URL·토큰은 비밀이므로 `.env`**, 어느 채널을 쓸지·재시도
횟수는 설정이므로 `config/`.

`[미확보]` **실제로 붙여 보지는 않았다.** 위 채널 성질은 공개 문서에서 아는 것이고
이 저장소에서 확인한 것이 아니다.

## 5. 전체 그림

```
                      ┌─────────────────────────────────────────┐
                      │  ① 감시 루프 (--interval 또는 cron)      │
                      │     trip_watch_sweeper                  │
                      └───────────────┬─────────────────────────┘
                                      │  변화 감지
                                      ↓
                            Case 생성  (기존 경로 진입)
                                      ↓
             분류  →  Team 판정  →  대안 생성  →  ★재검증
                                      ↓ 통과한 것만
                            outbox.publish("trip.notice")
                                      ↓
                      ┌─────────────────────────────────────────┐
                      │  ② 배달 루프                             │
                      │     OutboxWorker(publisher=디코/텔레/메일)│
                      └───────────────┬─────────────────────────┘
                                      ↓
                              고객이 알림을 받는다
                                      ↓
                        거부하면 → 이전 일정 버전으로 되돌림
```

★**「재검증」 을 빼면 안 된다.** v10 §5 가 못박았다 — 생성한 대안은 판정을
**다시 통과해야** 통지된다. 안 그러면 "고쳤다" 고 알리고 그 고친 것이 또 깨진다.

## 6. 순서

| # | 무엇 | 왜 이 순서인가 |
|---|---|---|
| 1 | **라우팅 축 결정** (§1 의 A/B/C) | 이게 안 되면 Case 가 Team 에 못 간다. 루프를 만들어도 아무 일이 안 일어난다 |
| 2 | 분류 어휘 교체 | 1 이 정해져야 무엇을 넣을지 안다 |
| 3 | `watch_schedule` 표 | sweeper 가 읽을 것 |
| 4 | `trip_watch_sweeper` | 감시 루프 |
| 5 | `publisher` 어댑터 하나 | 디코 웹훅부터 |
| 6 | 시연 시드 | 위가 다 돌아야 시연이 된다 |

★**1 을 건너뛰고 4 부터 하면 sweeper 가 Case 를 만들어도 아무도 안 받는다.**
