# 여행 RAG — 꼭 필요한 대상 재점검

`[실측 2026-09-10]` 어제 쓴 [코퍼스 계획](A-COP_여행RAG_코퍼스_계획.md)은 **Team 코드가
없던 때**의 추정이다. 그 뒤 `app/modules/travel_ops/` 5개가 붙었으므로
**코드가 실제로 정책에서 무엇을 꺼내려 하는지**로 다시 추린다.

★**어제보다 짧아졌다.** 16개 문서 후보로 넓게 잡았던 것을 **4자리**로 좁힌다.

---

## 0. 결론 먼저

| | |
|---|---|
| **RAG 를 실제로 부르는 팀** | **2/5** — Activity · Booking Handoff |
| 선언만 하고 안 부르는 팀 | 2 — Dining · Mobility (`read.policy` 가 `allowed_tools` 에 있는데 호출이 없다) |
| 아예 안 쓰는 팀 | 1 — Lodging/Flight (`allowed_tools` 에도 없다. **맞다**) |
| **꼭 필요한 RAG 자리** | **4** (아래 §2) |
| ★**막고 있는 것** | **지금 구조로는 RAG 가 그 값을 못 준다** (아래 §3) |

## 1. 실측 — 누가 정말 부르나

`[실측 2026-09-10]` `app/modules/travel_ops/` 를 AST 로 훑었다.

| 파일 | 줄수 | `read.policy` 선언 | **실제 호출** |
|---|---:|:---:|:---:|
| `activity.py` | 274 | O | **O** — `execute()` · `_weather_note()` |
| `booking_handoff.py` | 94 | O | **O** — `_prepare()` |
| `dining.py` | 96 | O | **X** |
| `mobility.py` | 80 | O | **X** |
| `locked_bookings.py` | 73 | X | X |

### Dining 이 안 부르는 것은 결함이 아니다

`_conditions()` 는 **장소 데이터**로 판정한다 — `place.dietary`(있다) ·
`place.dietary_absent`(없다) · 그 외는 **「모름」**.

```python
unknown = [item for item in wanted if item not in known and item not in absent]
if unknown:
    return self._unknown(task, f"조건 {', '.join(unknown)}", evidence)
```

★**이게 옳은 설계다.** 「이 집이 할랄인가」는 **사실**이라 조회할 것이고,
RAG 에 넣으면 업체가 인증을 잃어도 문서가 안 바뀌어 낡는다. 어제 문서에서
`dietary` 를 RAG 후보로 올렸던 것은 **틀렸다** — 코드가 더 정확했다.

`[미확보]` 다만 `knowledge_scope` 에 `dietary`·`opening_hours` 가 **선언돼 있다.**
안 쓰는 scope 는 지우는 편이 낫다 — 나중에 누가 채워 넣는다.

### Mobility 가 안 부르는 것은 **미구현**이다

`execute()` 가 `capability` 로 갈라지지 않는다. `select_capability()` 는
`mobility.exception` 을 골라 주는데 **`execute()` 에 그 갈래가 없다** — 셋 다
같은 경로(구간·운행 조회 → `have >= need` 계산)로 간다.

```python
fits = have >= need          # ★여유 시간은 계산이다. LLM 을 부르지 않는다.
```

★**계산으로 끝나는 부분은 RAG 가 필요 없다. 맞다.** 다만 `exception`(지연·결항 뒤
**누구 귀책이고 환불이 얼마인가**)은 계산이 아니라 규정 해석이고, **그 갈래가
아직 없다.** 만들 때 RAG 가 필요해진다.

## 2. 꼭 필요한 자리 — 넷

**코드가 이미 정책에서 값을 꺼내려 하고, 못 꺼내면 「모름」으로 떨어지는 자리**만 센다.

| # | 자리 | 코드가 찾는 것 | 못 찾으면 |
|---|---|---|---|
| 1 | `activity._check_cancelable` | **취소 기한** `cancel_deadline_hours` | `_unknown("취소 기한")` — 판정 자체를 못 한다 |
| 2 | 〃 | **구간별 위약금율** `penalty_by_hours` | 취소 가능만 답하고 **금액을 안 만든다** |
| 3 | `activity._weather_note` | **기상 취소·순연 기준** | **「불가」를 못 만든다.** 예보를 사실로만 전한다 |
| 4 | `booking_handoff._prepare` | 변경·취소 인계에 담을 규정 | 인계 문서가 빈약해진다 |

★**3번은 코드 주석이 직접 요구하고 있다.**

> ★★**여기서 「불가」를 만들지 않는다.** 강수확률이 얼마부터 취소·순연인지는
> **운영 규정**이 정할 일이고, 그 규정은 `read.policy` 가 대야 한다. 가드레일의
> 수치는 판정 기준이 아니라 **주의 문구 기준**이며, 측정이 아니라 우리가 고른
> 값이다. 그걸로 확정 답을 만들면 근거 없는 확정이 된다.

**즉 「비가 오니 취소됩니다」를 말할 수 있게 하는 것이 RAG 의 값어치다.**
지금은 "강수확률 80%입니다" 까지만 말한다.

### 이 넷을 덮는 문서는 셋이면 된다

| 문서 | 무엇을 담나 | 쓰는 자리 |
|---|---|---|
| **활동 취소·환급 규정** | 취소 기한 · 시점별 위약금율 · 환급 순서 | 1 · 2 · 4 |
| **기상 사유 취소·순연 기준** | 어느 조건이 「업체 귀책」인가 · 순연과 취소의 갈림 | 3 |
| **변경·취소 인계 규정** | 무엇을 고객에게 알려야 하나 · 차액 산정 | 4 |

★**어제 16개 후보를 적었지만 지금 코드가 실제로 쓰는 것은 이 셋이다.**
나머지(노쇼·인원 변경·대체 제안 기준 등)는 **그 갈래가 코드에 없다.**
만들 때 같이 만든다.

## 3. ★그런데 지금 구조로는 RAG 가 그 값을 못 준다

`[실측 2026-09-10]` 이게 이번 점검의 핵심이다.

**코드가 기대하는 모양**

```python
def _policy_hours(policy, key):
    for chunk in policy if isinstance(policy, list) else []:
        if isinstance(chunk, dict) and chunk.get(key) is not None:   # ← dict 를 본다
            return float(chunk[key])
    return None
```

**RAG 가 실제로 주는 모양**

```python
@dataclass(frozen=True)
class PolicyChunk:
    document_id: str
    chunk_no: int
    content: str      # ← 산문
    score: float
    scope: str
```

★**`PolicyChunk` 는 `dict` 가 아니다.** `isinstance(chunk, dict)` 가 항상 거짓이라
`_policy_hours` 와 `_penalty_rate` 는 **어떤 문서를 넣어도 `None` 을 돌려준다.**

즉 **취소 기한과 위약금율은 지금 어떤 코퍼스를 만들어도 안 채워진다.**

`[미확보]` 실행으로 재현하지는 않았다. `isinstance` 판정과 dataclass 선언을
읽어 낸 결론이다. **코드 세션이 한 번 돌려 확인해야 한다.**

★커머스에도 같은 모양이 있다 — `return_refund._policy_days` 가 똑같이
`isinstance(value, dict)` 로 거르고 **`90 if reason == "defective" else 7` 로
떨어진다.** 여행 쪽은 폴백이 `None`(모름)이라 **거짓 확정은 안 만든다.**
그 점은 여행 쪽이 낫다.

### 갈래 셋

| 안 | 무엇 | 대가 |
|---|---|---|
| **① 구조화 정책을 따로 둔다** | 수치는 `config/` 또는 전용 표에서 읽고, RAG 는 **문장 근거**만 댄다 | 수치와 문장이 두 곳. **개정 때 갈릴 수 있다** |
| **② 문서 front matter 에 수치를 넣고 청크에 실어 보낸다** | `PolicyChunk` 에 `attributes` 한 칸 추가 | **계약 변경.** Context Broker·Evidence 까지 번진다 |
| ③ 산문에서 LLM 이 뽑는다 | 문서는 산문 그대로 | **판정에 생성이 끼어든다.** 「판정은 코드」 원칙과 부딪힌다 |

★**①을 권한다.** 「판정은 코드가, 근거는 RAG 가」라는 지금 구조를 안 건드린다.
수치는 계산에 쓰는 값이므로 애초에 검색 대상이 아니다 — 어제 문서에서 세운
가르는 기준(**"이걸 검색해서 근거로 인용할 것인가"**)이 그대로 적용된다.

**그러면 RAG 문서는 「왜 그 수치인가」와 「어떤 경우가 예외인가」를 담는다.**
수치 자체는 안 담는다.

`[미확보]` ①을 고르면 수치를 어디 둘지 정해야 한다. `config/guardrails.yaml` 은
**운영 임계값**이지 도메인 규정이 아니다 — 섞으면 「가드레일 단일 출처」 규칙이
흐려진다. 별도 파일이나 표가 필요해 보인다.

## 4. 그래서 지금 할 것

| # | 무엇 | 왜 |
|---|---|---|
| 1 | **`_policy_hours`·`_penalty_rate` 가 정말 `None` 만 내는지 실행 확인** | 코퍼스를 만들기 전에 확인한다. 맞으면 만들어도 안 쓰인다 |
| 2 | **수치를 어디서 읽을지 결정**(위 ①②③) | 문서 구조가 여기서 갈린다 |
| 3 | 문서 셋 작성 — 활동 취소·환급 / 기상 사유 / 변경·취소 인계 | 2 가 정해진 뒤 |
| 4 | Dining·Mobility 의 안 쓰는 `knowledge_scope` 정리 | 안 쓰는 선언은 나중에 잘못 채워진다 |
| 5 | `mobility.exception` 갈래를 만들 때 RAG 를 같이 본다 | 지금은 갈래가 없다 |

★**1·2 를 건너뛰고 3 부터 하면 만들어도 안 쓰인다.** 어제 문서가 코퍼스 25개를
제안했는데, **지금 코드가 읽을 수 있는 것은 0개**다.
