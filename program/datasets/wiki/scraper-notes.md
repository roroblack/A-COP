# 스크래퍼 관측 기록

`[실측]` `datasets/commerce/coupang_order_history/docs/` 2건에서 이관. **원본은 그대로 있다.**

**바깥 화면을 관측한 기록이다.** 우리가 만든 게 아니라 상대가 바꾸면 낡는다.

## ★ PII — 수집하지 않는다

받는사람 정보 표에 다음이 있다. **마스킹돼 있어도 수집하지 않는다.**

```
받는사람 : 최*우
연락처   : 010****7059
받는주소 : (06725) 서울특별시 서초구 남부순환로339길 ** ***호
```

### 주소가 필요하면 시·구만

```regex
(서울특별시|...)\s+([가-힣]+(시|군|구))
```

**앞부분만 취하고 나머지는 버린다.**

**우편번호·번지·동호수는 저장하지 않는다.**

`[실측]` **마스킹된 값도 안 받는 게 규칙이다.** `010****7059`도 다른 데이터와 붙이면 좁혀진다. → [`auth-boundary.md`](../../final_project_cs/wiki/external/auth-boundary.md)의 join key 분리

## 수집이 새던 원인 2가지

### 원인 1 — 취소완료 주문에는 상품 링크에 `href`가 없다

**기존 selector 가 주문을 통째로 놓쳤다.**

**대안** — `주문 상세보기` 텍스트와 주문일로 카드 루트를 찾고 거기서 상품명을 뽑는다.

### 원인 2 — 마지막 페이지인데 "다음"을 눌렀다

**`disabled` 버튼을 눌러 10초 timeout 이 났다.**

**대안** — `disabled` 속성 유무로 판정한다.

## 추출은 클래스가 아니라 텍스트로

`[실측]` **클래스명은 바뀐다. 텍스트는 덜 바뀐다.**

| 대상 | 방법 |
|---|---|
| 다음 버튼 | 모든 `button` 중 텍스트가 `다음`으로 끝나거나 포함 |
| 이전 버튼 | 같은 방식으로 `이전` |
| **비활성 판정** | **`disabled` 속성 유무** |

**SVG 가 버튼 안에 있으므로 `textContent` 를 쓰되 공백을 정리해 비교한다.**

## ★ [2026-09-02 추가] 선택자는 해시 클래스를 안 쓴다

`[실측]` `docs/실제HTML_주문카드.md` 에서 이관. 실측 outerHTML 1건에서 확인한 것이다.

**쿠팡 클래스명은 해시라 배포 때마다 바뀐다.** 구조와 속성으로 잡는다.

| 무엇 | 어떻게 |
|---|---|
| 카드 | `td` 중 `a[href*="MyCoupang_my_orders_list_product_title"]` 를 포함하는 것 |
| **상품명** | **`img[alt]` 의 alt** — 가장 안정적. 또는 링크 내 span 텍스트 |
| 금액 | `span[translate="yes"]` 텍스트에서 숫자 추출 |
| 수량 | 금액 span 의 **다음 형제** span 중 `N개` 패턴 |
| 상태 | 카드 내 `span[style*="font-size:1.25rem"]` |
| vendorItemId | href 에서 정규식 |

**`img[alt]` 가 가장 안정적인 이유는 그게 접근성 속성이라서다.** 화면 개편에도 잘 안 바뀐다.

`[미확보]` **금액과 상태는 여전히 취약하다.** `translate="yes"` 와 인라인 `font-size` 는 스타일 변경에 깨진다.

### 목록 카드에 없는 것

```
주문번호 · 주문일시 · 판매자명 · 배송비 · 총액
택배사 · 송장번호 · 배송지
```

**주문 상세로 들어가야 한다.** → 아래 [주문 상세에는 택배사·송장번호가 없다](#주문-상세에는-택배사송장번호가-없다)

## 배송 화면 세 형태

| 형태 | 상태 | 송장번호 | 이력표 |
|---|---|---|---|
| A | 상품준비중 | **빈 문자열** | 없음 |
| B | 배송중 | 있음 | 있음 |
| C | 배송완료 | 있음 | 있음 + 도착안내 |

### 결론 — 이력표 부재는 오류가 아니다

**배송 전에 이력이 없는 건 정상이다.** 아직 발송 전이라 데이터 자체가 없다.

`[실측]` **이걸 오류로 처리하면 정상 주문을 수집 실패로 센다.**

### 축을 둘로 나눈다

```
발송 여부      ×    배송 완료 여부
```

**하나의 상태값으로 뭉치지 않는다.**

## 상대 시각 주의

`오늘` · `어제` 같은 표기가 나온다.

```
수집 시점 기준 절대시각으로 변환
+ 원문도 함께 보존
```

**원문을 남기는 게 중요하다.** 변환이 틀렸을 때 되돌릴 수 있다.

## 주문 상세에는 택배사·송장번호가 없다

**목록과 상세의 `sourceType` 이 다르다.** 상세만 보면 배송 정보를 못 얻는다.

## 배송요청사항

**주문별로 값이 다르다.** 고정값으로 가정하지 않는다.

## ★ [2026-09-04] 배송이력 5건 중 4건만 수집 — 원인 확인됨

`[실측]` `preprocess_stats.json` 이 이미 계산해 둔 값이었다. 열어보지 않아서 "미확인"으로 남아 있었다.

```
unique_order_ids: 8
tracking_rows:    4
excluded.cancelled_tracking_boxes:        3   (취소 주문 — 배송 자체가 없다)
excluded.tracking_number_missing_boxes:   1   (송장번호 미기재)
```

**8건 중 취소 3건은 배송조회 대상이 아니다.** 남은 5건 중 1건은 송장번호가 없어 배송 이력을 못 얻었다. **5건 중 4건 수집**은 이 1건 때문이다 — 스크래퍼 결함이 아니라 원본 화면에 송장번호가 비어 있는 경우([위 배송 화면 A형](#배송-화면-세-형태): 상품준비중은 송장번호가 원래 빈 문자열)다.

**결론 — 추가 조치 불필요.** 데이터 결손이 아니라 정상 동작이다.

## 네이버 주문 4건 누락 — 아직 안 고쳐졌다

`[실측]` `datasets/commerce/naver_order_history/REPORT.md` §"알려진 문제". **cyw 계정 실제 72건 중 68건만 수집.** 나머지 3명 제출본(101·44·57건)도 각자 실제 주문 수와 대조되지 않아 270건 전체가 "전량"인지 확인 안 됨.

**원인 후보 — 링크 없는 주문을 화면에서 식별하는 방법이 안 정해졌다.** 로그인 상태의 실제 DOM이 있어야 진행 가능 — 코드만으로는 못 고친다.
