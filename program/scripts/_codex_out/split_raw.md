# 이 소스들을 고른 이유 (선택 근거)

`REPORT.md`는 "뭘 찾았는지"만 적혀 있고 "왜 이걸 골랐는지"가 없었다. 이 문서가
그 공백을 메운다. 판단 기준은 세 가지였다: ① [`team_branch/cy/화요일_브리핑`](../../../team_branch/cy/)의
데이터 소싱 방침(공공데이터·공식 API·라이선스 명시만, 플랫폼 크롤링 금지) ②
A-COP이 실제로 쓸 지점(VOC 감성분류, REV PII 근거, GEN 톤 프로파일, case_type
라우팅) ③ 승인 대기 시간 동안 파이프라인을 멈추지 않을 것.

## AI Hub를 우선 후보로 삼은 이유

한국어 VOC 데이터라는 게 전제라서 후보군이 처음부터 좁았다. 직접 크롤링(네이버쇼핑·쿠팡
리뷰)은 화요일 브리핑이 이미 법적 문제로 금지한 경로라 검토 대상에서 뺐다.
남는 건 정부기관 공식 데이터셋(AI Hub, 모두의말뭉치)과 라이선스가 명시된
공개 저장소(GitHub, HuggingFace)뿐이었다 — 이 둘을 우선순위로 삼았다.

### AI Hub 71603 (속성기반 감성분석)을 고른 이유

VOC 팀이 실제로 마주칠 문제는 "이 리뷰가 긍정이냐 부정이냐"가 아니라
"배송은 느렸는데 품질은 좋았다"처럼 **한 문장 안에 여러 속성에 대한 감성이
섞여있는 경우**다. 단순 이분류 데이터(예: bab2min naver_shopping)로는 이
케이스를 못 다룬다. 71603은 스팬 단위 BIO 태깅이라 "어느 속성이 부정적인가"를
바로 학습·평가할 수 있다 — case_type 세분류(주문/배송/반품/교환)와
자연스럽게 대응된다. 대안으로 검토했던 단순 긍정/부정 데이터셋들은 이미
naver_shopping으로 확보했으므로, 새로 신청하는 건 이 세분류 능력을
보강하는 것이어야 한다고 판단했다.

### AI Hub 30716 (민원 콜센터 QA)을 고른 이유

세 가지가 일치했다: ① 규모가 110만 쌍으로 압도적으로 크다 ② **K쇼핑 도메인이
55만 쌍**으로 명시적으로 포함돼 있다 — 우리 도메인(쇼핑몰 CS)과 직접
겹치는 유일한 대형 데이터셋이다 ③ 형식이 상담원 질문/답변 + 고객 질문/답변
쌍으로 구성돼 있어 A-COP의 Case(고객 메시지) → Team 응답 구조와 형식이
거의 그대로 맞는다. 질병관리본부·금융보험·다산콜센터 3개 도메인은 우리와
무관하지만, 신청 단위가 데이터셋 전체라 분리 신청이 안 된다 — K쇼핑 55만
쌍을 얻으려면 나머지도 같이 받아야 한다(불필요한 부분은 받은 뒤 필터링).

### AI Hub 71844 (민간 민원상담 LLM Instruction Tuning)을 고른 이유

71603·30716은 분류·QA용이고, 이건 **생성(GEN)에 바로 쓸 수 있는 instruction
tuning 형식**이라는 점이 달랐다. 최소 3턴 이상, 500자 이상 조건이 우리
Case의 실제 대화 길이(단발성 문의가 아니라 왕복이 있는 상담)와 맞는다.
수집처가 카드사·통신사(하나카드·LG유플러스)라 쇼핑몰 도메인은 아니지만,
"상담 응대의 문체·구조"를 배우는 용도로는 도메인이 완전히 겹칠 필요가
없다고 판단했다 — GEN이 배워야 할 건 정책 지식(이건 RAG가 담당)이 아니라
**응대 형식**이기 때문이다.

### 모두의말뭉치 "개체명 분석 말뭉치"(개체 연결 제외)를 고른 이유

REV(응답 검증)의 PII 필터가 지금 손으로 짠 정규식만으로 돌아가고 있다 —
[`법령원문_2026-08-20.md`](../../../program/research/_법령원문_2026-08-20.md)에서 확인한 개인정보보호법
제2조 가목("성명, 주민등록번호 및 영상 등")의 "성명"을 정규식이 놓치는
사례(예: 흔치 않은 성씨, 외국인 이름)가 분명히 있을 것이다. 국립국어원
공식 개체명 태깅 기준으로 만든 말뭉치는 이 정규식의 recall을 실측·개선하는
근거가 된다. "개체 연결"(entity linking, 위키피디아 지식베이스 연결)
버전은 검토했지만 뺐다 — 우리는 "이게 사람 이름인가"만 알면 되지 "이
사람이 누구인가"까지는 필요 없다. 불필요한 라벨 복잡도를 늘릴 이유가
없었다.

### bab2min/corpus (naver_shopping)를 먼저 받은 이유

AI Hub 3종은 전부 승인 대기가 필요하고 대기 기간이 공식 문서에 안 나와
있다 — 얼마나 걸릴지 모른다. bab2min/corpus는 Public Domain이라 **승인
없이 즉시 받을 수 있는 유일한 후보**였다. 그래서 감성분류 베이스라인을
당장 만들 수 있는 이걸 먼저 처리하고, AI Hub 3종은 승인이 나는 대로
따라잡는 순서로 갔다. 라벨 분포가 거의 정확히 50:50인 것도 확인했는데
(REPORT.md 참고), 이건 baseline 평가에는 좋지만 실제 VOC 데이터의 불균형
분포와는 다를 수 있다는 점도 같이 기록해뒀다 — 이 데이터 하나로 끝낼
생각은 아니라는 뜻이다.

### Kaggle Customer Support Tickets를 "참고용으로만" 남긴 이유

화요일 브리핑의 명시적 방침이다: 해외 Kaggle 데이터는 스키마·분류체계
설계 참고용으로만 쓰고 학습 데이터 본체로 안 쓴다. 이유를 추측하면 —
라이선스가 명확히 확인 안 됐고, 언어·문화권이 달라 그대로 학습에 쓰면
도메인 미스매치가 생긴다. 그래도 카탈로그에 남긴 이유는, 이 데이터셋의
**티켓 카테고리 체계**가 우리 `issue_code`/`case_type` 스키마가 놓친
케이스가 없는지 대조하는 데는 쓸모가 있어서다 — 데이터 자체가 아니라
"분류체계 설계 시 대조군"으로 쓴다.

### HuggingFace 파인튜닝 모델 4종을 고른 이유

전부 한국어 특화(다국어 범용 모델 제외), 승인 절차 없이 즉시 접근 가능
(AI Hub 승인 대기 중에도 바로 실험 가능), 그리고 **입도(granularity)가
다른 걸 일부러 섞었다** — 3종 분류(긍정/부정/중립), 5종 감정, 6종 감정.
VOC가 최종적으로 몇 단계 감성/감정 라벨을 쓸지 아직 안 정해졌기 때문에,
결정 전에 각 입도의 실제 성능 차이를 baseline으로 비교해볼 수 있게
일부러 범위를 넓게 잡았다. 실제로 파이프라인에 붙일지는 팀 판단이고,
이 카탈로그의 역할은 "고를 수 있는 선택지를 실측 가능한 상태로
준비해두는 것"까지다.

### 리뷰 스팸 탐지 자료를 "쓸 도구 없음"으로도 남긴 이유

사용자가 명시적으로 물어본 항목이라("리뷰나 이러한 사항들에 대해 VOC
하는 거 우리가 체크할 수 있는 거 있으면") 답이 "없다"이더라도 조사
결과를 남겼다 — 다음에 같은 질문이 나왔을 때 "이미 찾아봤는데 없었다"를
바로 확인할 수 있게 하기 위해서다. 국내 사례(배달의민족)는 기술이
비공개라 그대로 가져다 쓸 수 없고, 오픈소스는 전부 영어 아마존 리뷰
기준이라 구조 참고 이상은 안 된다는 게 이번 조사의 결론이다.

## 검토했지만 최종적으로 카탈로그에 안 넣은 것

- **네이버쇼핑·쿠팡 리뷰 직접 크롤링**: 화요일 브리핑이 법적 문제로 명시
  금지. 검토 자체를 안 했다.
- **범용 오픈 LLM(Qwen3.6, GLM-5.2, Gemma4 등, 2026년 출시)**: VOC
  감성분류용이 아니라 GEN의 생성 베이스 모델 후보라 층위가 다르다.
  이 카탈로그는 VOC 분류 도구·데이터만 다룬다 — GEN 베이스 모델 선택은
  별도 조사 대상으로 남긴다.

# 이 소스들을 고른 이유 (선택 근거)

## 교차검증 리서치 (2026-08-20) — "지금까지 고른 게 최선인가?"를 다시 검증

사용자 요청으로 "Kaggle이나 다른 곳에 더 좋은 자료가 있는지" 오늘자 기준으로
Claude와 Codex(gpt-5.6-luna)가 **서로 독립적으로**(서로의 결과를 안 보고)
같은 범위를 다시 조사했다. Codex의 원본 조사 결과는
[`_codex_independent_research_2026-08-20.md`](_codex_independent_research_2026-08-20.md)에
그대로 남겨뒀다(가공하지 않음). 아래는 둘을 대조해 합의한 결론이다.

### 합의(둘 다 독립적으로 같은 결론에 도달)

- **Kaggle에는 쇼핑몰 VOC에 직접 맞는 한국어 데이터셋이 없다.** 둘 다 영어
  합성 티켓/리뷰 데이터만 찾았고, 결론도 동일했다 — "학습 데이터 본체가
  아니라 스키마·taxonomy 참고용"이라는 기존 방침이 두 번째 독립 조사로도
  뒤집히지 않았다. Codex는 Apache 2.0/MIT/CC BY 4.0 라이선스인 것들까지
  찾았지만("Customer Support Tickets 200K+", "Customer Sentiment Dataset")
  합성·영어 데이터라는 한계는 같았다.
- **AI Hub 71603/71844/71616/619는 이미 정확히 파악돼 있었다.** Codex가
  독립적으로 찾은 규모·구축연도·URL이 기존 카탈로그와 일치했다 — 카탈로그
  정확도가 재확인됐다.
- **HuggingFace 감정분류 모델은 KOTE 계열로 수렴한다.** Claude가 독립적으로
  찾은 KOTE(SNU, 43감정+무감정 25만건)를, Codex가 찾은 파생 모델들
  (`tojoHere/goemotions-ko-xlm-roberta-base`가 "GoEmotions+KOTE 50K로 학습"이라고
  모델카드에 명시, `tobykim/koelectra-44emotions`도 "KOTE + 추가수집"이라고 명시)이
  독립적으로 뒷받침했다 — 여러 파생 모델이 같은 원본을 가리킨다는 건 KOTE
  자체가 사실상 이 분야의 표준 데이터라는 신호로 봤다.

### 불일치 — Codex가 찾고 Claude가 놓친 것 (더 큰 무게를 둠)

두 가지는 Codex 조사에만 있었고, 확인해보니 **기존 카탈로그보다 명백히
낫다.** REPORT.md에 ★표시로 추가했다.

1. **AI Hub 102 (소상공인 고객 주문 질의-응답 텍스트)** — 500만 건. 백화점·
   홈쇼핑·e-commerce 콜센터가 포함되고, 감성(긍/중/부정)+인텐트+개체명이
   동시에 라벨링돼 있다. 기존 카탈로그의 어떤 것보다 크고, 어떤 것보다
   라벨이 풍부하다. Claude가 이걸 놓친 이유: AI Hub 일반 웹검색으로는
   "쇼핑몰 리뷰"·"CS 챗봇" 같은 키워드로 찾았는데, 이 데이터셋은 "소상공인
   고객 주문"이라는 제목이라 검색어에 안 걸렸다 — 키워드 편향의 실패 사례로
   기록해둔다.
2. **공정위 15098340 (온라인 상거래 소비자상담 내역)** — 736,806건, 제목에
   "온라인 상거래"가 명시돼 있다. Claude는 같은 자리(공정위 소비자
   민원학습데이터 시리즈)에서 "위해위험"(129,759건)과 "전문상담"(191,408건)
   만 찾고 이 데이터셋을 놓쳤다 — 같은 시리즈 안에 더 안 맞는 것과 더 맞는
   것이 섞여 있었는데 전자만 찾은 사례다. 승인 없이 즉시 받을 수 있고
   규모도 5.7배 크다.

### 최종 우선순위 합의

1. **1순위(신규, 아직 미다운로드)**: AI Hub 102 (신청 필요) + 공정위
   15098340(승인 불필요, 지금 바로 받을 수 있음).
2. **2순위(이미 확보)**: AI Hub 71603/71844, bab2min naver_shopping — 계속
   유효하다, 교체 대상 아님.
3. **3순위(모델 후보 재검토)**: 기존 카탈로그의 4개 파인튜닝 모델 대신
   또는 함께, KOTE 원본이나 KOTE 기반 파생 모델(GGARA02, tojoHere)을
   베이스라인으로 우선 검토.
4. **변경 없음**: Kaggle은 여전히 참고용 방침 유지, 모두의말뭉치 신청도
   그대로 진행.

### 라이선스 관련 합의된 경고

Codex가 조사 중 스스로 낸 결론에 동의한다 — **"무료 다운로드"와 "학습·재배포
허용"은 다른 말이다.** AI Hub는 신청 승인이 필요하고, Kaggle/HuggingFace는
카드별로 라이선스가 다 다르다. 지금까지 이 카탈로그의 접근상태 표기는
"받을 수 있는지"만 확인한 것이지 "학습에 그대로 써도 되는지"까지 법적으로
확정한 게 아니다 — 실제 학습 투입 전에 재확인이 필요하다.

## 리뷰 스팸 탐지 논의 (2026-08-20) — "쓸 도구 없음"을 어떻게 풀지

사용자가 사실 확인(리뷰 스팸 탐지 데이터·모델 없음)에 이어 "그럼 어떻게
해결할지"를 물었다. 사실 조사가 아니라 설계 판단이 필요한 문제라, Claude가
먼저 판단을 세운 뒤 Codex(gpt-5.6-luna)에게 같은 문제를 독립적으로 맡겨
대조했다. Codex 원본:
[`_review_spam_detection_codex_논의_2026-08-20.md`](_review_spam_detection_codex_논의_2026-08-20.md).

### 결론 — 이번엔 반박이 아니라 수렴, Codex가 더 정교했다

두 판단이 같은 방향으로 수렴했다: **지금 데이터·라벨이 전혀 없는 상태에서
"가짜냐 아니냐"를 확정하는 분류기를 만들면 안 된다.** 대신 다음 셋 중
Codex 쪽이 Claude의 초안보다 명백히 더 구체적이고 실행 가능해서, Codex
안을 그대로 채택한다.

1. **첫 단계는 규칙 기반 약한 신호다** (분류기가 아니라 "검토 우선순위
   산정"). LLM-as-judge는 보조 요약용으로만, 준지도학습은 사람이 검증한
   라벨이 쌓인 다음 단계로 미룬다 — Claude도 같은 결론이었으나 Codex가
   왜 각 단계가 안 되는지(감성 라벨을 가짜리뷰 정답으로 대체하면 타깃
   자체가 틀린다는 지적 등)를 더 명확히 짚었다.
2. **명칭부터 `fake_review`가 아니라 `review_integrity_concern`으로
   가야 한다.** "이 리뷰는 가짜다"가 아니라 "17건에서 근사 문구가
   18분 내 관찰됨, 프로모션·일괄배송 등 정상 사유를 확인해달라"는 식으로
   제안 자체가 비확정적이어야 한다는 게 A-COP의 Evidence 원칙과 정확히
   맞는다. `confidence: 0.93` 같은 보정 안 된 숫자는 아예 쓰지 말라는
   지적도 타당하다.
3. **"지금은 손대지 않는 게 맞다"는 조건까지 명시했다** — 상품/시간/판매자
   맥락이 안 이어지거나, 운영자가 검토 결과를 기록할 절차가 없거나, 제안이
   삭제·판매자 경고로 오해될 수 있으면 기능 자체를 노출하지 않는 게 낫다는
   6가지 조건. Claude는 "일단 약한 두 신호만 붙여보자"는 쪽으로 더
   낙관적이었는데, 이 체크리스트를 보고 생각을 바꿨다 — 지금 우리 데이터
   (naver_shopping, AI Hub 71603)엔 계정·상품·시간 메타데이터가 없어서
   중복 텍스트 신호 하나 말고는 검증할 수 있는 게 사실상 없다. 성급하게
   "탐지 기능 있음"을 내세우는 것보다 이 문서 자체를 "지금은 안 하는 게
   맞다"의 근거로 남기는 게 낫다고 판단을 바꿨다.

### 지금 데이터로 즉시 해볼 수 있는 것 (검증이지 기능 출시가 아님)

- `naver_shopping_sentiment/`·`aihub_71603_aspect_sentiment/` 두 데이터에서
  **근사중복 텍스트 비율**과 **평점-텍스트 감성 불일치율**만 계산해볼 수
  있다 — 계정/시간/상품 메타데이터가 없어서 폭증·계정집중·문체반복 신호는
  지금 데이터로는 계산 불가.
- 이 계산 결과는 "스팸 탐지 성능"이 아니라 "신호가 실제로 얼마나 관측되는지"
  로만 보고해야 한다(Codex 지적 — 감성 라벨을 가짜리뷰 정답으로 오용하면
  안 됨).

## 최종 완결성 점검 (2026-08-20) — "오늘자 기준 이게 끝인가?"

사용자가 지금까지 모은 자료 전체를 놓고 "충분한지, 국내에 더 받을 게
없는지"를 물었다. 이번엔 독립조사가 아니라 **완결성 감사(audit)**다 —
Codex에게 지금까지 확보한 목록 전체를 그대로 보여주고, 그 위에서 빠진
게 있는지 찾게 했다. Codex 원본:

### 답: 대량 수집 관점에서는 충분하다. 남은 건 "더 받기"가 아니라 "가공"이다.

Codex의 판정에 동의한다 — 쇼핑 리뷰 45만+건, 민원·상담 QA/라벨링 수백만
건, 소비자 피해·위해·분쟁 원문까지 갖췄고, 감성·속성·의도·개체명·QA·
FAQ 등 과업 커버리지도 넓다. **여기서 데이터를 더 모은다고 품질이
오르지 않는다.** 진짜 남은 일 둘:

1. **AI Hub 30716·공정위 15098320의 "온라인쇼핑몰만" 필터링에 공식
   코드 매핑표가 없다** — Codex가 직접 찾아봤지만 공개된 코드북이
   없다고 확인했다. 즉 "K쇼핑 55만 쌍만 뽑아내면 된다"가 생각보다
   간단하지 않다 — 기관명/메타데이터 대조 후 내부 매핑표를 직접
   만들고, 사람이 표본 검수해야 한다(Codex가 5단계 절차를 구체적으로
   제시함). 이 작업 전까지는 "K쇼핑 서브셋 확보"를 완료로 세면 안 된다.
2. **외부 공개자료는 A-COP의 실제 상담 로그를 대체하지 못한다** — 사업자
   정책, 상품/주문 시스템, 최신 용어, 답변 SLA는 외부 데이터에 없다.
   holdout 평가셋·intent taxonomy는 결국 A-COP 실 데이터로 만들어야
   한다는 게 Codex의 지적이고, 이건 맞는 말이다 — 지금까지 모은 건
   전부 "사전학습·베이스라인용"이지 "우리 서비스 정답지"가 아니다.

### 새로 확인된 보조 자료 (대형 원문 데이터는 아님 — 참고·평가용으로만)

- **서울·대구 등 지자체 열린데이터광장** — 확인해보니 대부분 월별

- **국가법령정보센터 판례** — 법적 답변 근거 문장 재료로는 유용하지만

- **NIA 2026 신규 AI Hub 데이터 구축 공고** — 공고만 있고 아직 실제
  공개된 쇼핑몰 CS 데이터는 확인 안 됨. 확보 목록에 넣지 않고 분기별
  재점검 대상으로만 추적한다.

### TranslateGemma-4B/12B 참고

### ⚠️ hangul_ratio 자동판정의 함정 — 실제로 걸림

`hangul_ratio`는 "한글 문자가 섞여 있는가"만 재기 때문에, 뜻이 완전히 다른 내용도
한글로만 써있으면 "OK"로 잘못 판정한다. **Seed-X-PPO-7B가 정확히 이 함정에 걸렸다** —
자동판정은 0.776로 "OK"였지만 샘플 3개를 직접 읽어보니 원문과 전혀 상관없는 문장을
출력했다:

```
원문: "O tampo da mesa chegou todo amassado e batido." (테이블 상판이 찌그러지고 훼손된 채 도착했다)
Seed-X-PPO-7B 출력: "그는 자신의 에고이스트ικ 회사에서 해고되었습니다." (그는 자신의 이기적인 회사에서 해고되었다)
```

전혀 다른 내용이고 그리스 문자(ικ)까지 섞여 있다. 자동 지표만 보고 "고쳐졌다"고
결론 냈으면 오보가 될 뻔했다 — **반드시 샘플을 직접 읽고 검증**해야 한다.

## 결과 5 — 2026-08-24 GPU 재검증: MADLAD·NLLB·ke-t5·Seed-X·HY-MT 복구

x600(Windows, RTX 4070 SUPER 12GB)에서 막혔던 모델들을 사용자가 제공한 별도 GPU 서버
(RunPod, **Linux, RTX A4500 20GB VRAM, 시스템 RAM 251GB**)에서 재시도했다. 결론부터:
**x600에서 "포기"로 결론 냈던 원인은 x600이라는 특정 환경(Windows·좁은 VRAM·비공식
torch 빌드) 문제였지 모델 자체의 결함이 아니었다** — 정상적인 Linux+공식 PyPI 환경에서는
아래 항목만 빼고 전부 복구됐다.

### 진짜 원인이었던 것들 (하나씩 확정)

1. **MADLAD-400 계열 완전 무작위 퇴화 출력(`"e e e e e e..."`)의 진짜 원인**: x600에서는
   "GPU 문제인가, transformers 5.x 문제인가, 캐시 손상인가"를 계속 의심만 하고 확정하지
   못했다. GPU 서버에서 **공식 문서 예제(`"<2pt> I love pizza!"` → `"Eu amo pizza!"`)조차
   `transformers` 최신판(5.15.1)에서 깨지고, `transformers==4.46.3`으로 낮추면 정확히
   `"Eu amo pizza!"`가 나오는 것을 직접 재현 확인했다.** 최신 transformers가 MADLAD-400의
   tied-weights(입출력 임베딩 공유) 처리 방식을 바꾸면서 생긴 회귀 버그로 확정. 토큰화
   자체(`<2ko>` prefix 등)는 처음부터 문제없었다 — x600에서의 의심은 방향이 틀렸었다.
2. **Seed-X-PPO-7B / Seed-X-Instruct-7B / HY-MT1.5-1.8B가 GGUF에서 깨졌던 진짜 원인**:
   공식(비양자화) HuggingFace 체크포인트로 직접 재현하니 셋 다 정상 작동했다(위 결과 1
   참조) — **mradermacher/tencent의 GGUF 변환 결함**이었지 모델이나 프롬프트 문제가
   아니었다. Seed-X 계열은 카드에 "chat template 쓰지 말고 raw 문자열 + 끝에 언어 태그"
   라고 명시돼 있었는데, 처음부터 그렇게 쓰고 있었다(`"...{s} <en>"`) — 원래 프롬프트
   설계는 맞았다.
3. **x600에서 "디스크 여유 350TB인데도 다운로드가 죽는다"에 해당하는 문제가 GPU 서버에서도
   재현**: `/workspace`(네트워크 스토리지, `df -h` 기준 350TB 여유)에도 실제로는 계정별
   할당량이 걸려 있어 **47GB 근처에서 `Disk quota exceeded`**가 났다 — `df`가 보여주는
   숫자와 실제 쓸 수 있는 용량이 다를 수 있다는 걸 두 서버에서 연달아 확인. 모델 처리
   후 캐시를 즉시 삭제하는 방식(1개씩 처리 → 삭제 → 다음 모델)으로 우회.
4. **백그라운드 실행이 계속 "이유 없이" 죽던 문제**: `nohup`/`setsid`/`tmux`까지 다 써봤는데
   SSH 세션이 끝나면 프로세스가 통째로 사라졌다 — 원인은 프로세스 분리 실패가 아니라 위 3번의
   디스크 할당량 초과가 반복적으로 겹쳐서 생긴 연쇄 장애였다(할당량 초과 시 로그 파일 쓰기부터
   실패하면서 tmux 서버까지 같이 죽었다). 디스크 문제를 고치자 일반 SSH 연결(도구의
   백그라운드 실행 기능으로 연결을 계속 열어두는 방식)만으로도 안정적으로 끝까지 돌았다.

# 쿠팡 확장 미수집 원인 (실측 HTML 기반)

사용자가 제공한 "다음 페이지" 주문 카드 HTML 분석 결과.

## 원인 1 — 취소완료 주문에는 상품 링크에 href가 없다

현재 확장의 주문 카드 탐색 기준:
`a[href*="MyCoupang_my_orders_list_product_title"]`

그런데 취소완료 주문의 상품 링크는 **href가 아예 없다**:

```html
<a class="sc-5a139ee-12 sc-243c9af9-0 dNRFWT ihxwGs">
  <span class="sc-5c217829-1 sc-243c9af9-1 kgcOMO iIfQoU">헤이맨 아이패드 프로 M1 ...</span>
</a>
```

이미지 링크도 마찬가지로 href가 없다:
```html
<a class="sc-408af0a8-0 hjrnzM">
  <img alt="헤이맨 아이패드 프로 M1 ..." src="...">
</a>
```

배송완료 주문은 href가 있지만(`/ssr/sdp/link?vendorItemId=...`), 취소완료는 상품 페이지
링크 자체가 사라진다. 따라서 href 기반 탐색은 취소 주문을 전부 놓친다.

### 새 탐색 기준

주문 카드의 안정적 앵커는 **`주문 상세보기` 헤더 블록**이다. 모든 주문에 있다.

```html
<div class="sc-2dee486c-0 cXKQoM">          <!-- 주문 카드 루트 -->
  <div class="sc-f52eb281-0 gtEXxx">        <!-- 헤더 -->
    <div class="sc-f52eb281-1 dybnQZ">2021. 8. 27 주문</div>
    <div class="sc-f52eb281-2 gjhiiX">
      <span class="sc-f52eb281-3 dBmYzE">주문 상세보기</span>
    </div>
  </div>
  <div class="sc-5a139ee-0 gCjDaW"> ... 상품 테이블 ... </div>
</div>
```

카드 탐색: 텍스트가 `주문상세보기`인 요소를 찾고, 그 조상 중 **주문일 텍스트
(`YYYY. M. D 주문`)를 함께 포함하는 가장 가까운 블록**을 카드 루트로 잡는다.

이러면 취소완료·배송완료 모두 잡힌다. 그리고 **주문일을 목록에서 바로 얻을 수 있다**
(현재는 상세 진입해야만 얻는데 목록 헤더에 있다).

상품명은 카드 안에서 다음 순서로 찾는다:
1. `img[alt]` 중 뱃지가 아닌 값 (취소 주문도 이미지 alt는 있다)
2. 금액 span 근처의 텍스트 span

## 원인 2 — 마지막 페이지인데 "다음"을 눌렀다

사용자가 준 페이지네이션 HTML:

```html
<button ... disabled=""><svg .../> <!-- -->이전</button>
<button ... disabled="">다음<!-- --> <svg .../></button>
```

**둘 다 `disabled`다.** 즉 이 페이지는 처음이자 마지막 페이지다.

그런데 확장은 "다음 페이지 클릭 후 10초 동안 주문 카드가 바뀌지 않아 중단"이라는
경고를 냈다. `disabled` 판정이 동작하지 않았다는 뜻이다.

원인 후보: 버튼 텍스트에 HTML 주석(`<!-- -->`)이 끼어 있다. `textContent`로는 주석이
제외되지만, 만약 `innerHTML` 기반으로 비교하거나 자식 노드를 순회하면 어긋날 수 있다.
또한 `이전` 버튼의 텍스트는 `<svg/> 이전` 순서라 SVG가 앞에 온다.

### 수정

- `disabled` 확인을 **클릭 전에** 반드시 수행하고, disabled면 즉시 정상 종료로 처리해라.
  "10초 대기 후 중단" 경고를 내지 말고 "마지막 페이지"로 로그를 남겨라.
- 버튼 판정은 `textContent`(주석 자동 제외)를 공백·제로폭 제거 후 비교한다.

## 확인된 추가 정보 — 연도 필터

목록 상단에 연도 탭이 있다.

```html
<div class="sc-6441a31c-1 hdwxWS">최근 6개월</div>
<div class="sc-6441a31c-1 gUoxrz">2026</div>
<div class="sc-6441a31c-1 gUoxrz">2025</div>
... 2024, 2023, 2022, 2021
```

**기본값이 `최근 6개월`이다.** 그래서 3건만 나온 것이다. 전체를 수집하려면 연도 탭을
순회해야 한다. 2021~2026 6개 연도를 각각 클릭하고 그 안에서 페이지네이션을 돌면 된다.

이것이 수집량이 적었던 진짜 이유다.

# 배송조회 화면의 두 가지 형태 (실측)

## 형태 A — 배송 전 (상품준비중)

이력 표가 **없다**. 대신 진행 단계 표시가 있다.

```html
<div class="sc-b55961ed-1 hbKRpw">내일(토) 새벽 7시 전 도착 보장</div>
<div class="sc-69a3001b-0 jGIPAi">고객님이 주문하신 상품이 준비시작되었습니다.</div>

<!-- 진행 단계 (완료된 단계와 미완료 단계의 클래스가 다름) -->
<div>결제완료</div>   <!-- kBFVZh = 완료 -->
<div>상품준비중</div> <!-- kBFVZh = 완료 -->
<div>배송시작</div>   <!-- bphNHp = 미완료 -->
<div>배송중</div>     <!-- bphNHp = 미완료 -->
<div>배송완료</div>   <!-- bphNHp = 미완료 -->

<td class="...">송장번호</td><td class="...ccHVRg"></td>  <!-- 값이 빈칸 -->
```

**송장번호가 빈 문자열이다.** 아직 발송 전이라 데이터 자체가 없다.

## 형태 B — 배송 완료

송장번호와 이력 표가 모두 있다.

```html
<td>송장번호</td><td>10327825750572</td>
<table><thead><tr><th>시간</th><th>현재위치</th><th>배송상태</th></tr></thead>
<tbody>
  <tr><td>어제 23:07</td><td>안양1</td><td>배송완료</td></tr>
  <tr><td>어제 21:32</td><td>안양1</td><td>배송출발</td></tr>
  <tr><td>어제 20:50</td><td>안양1</td><td>캠프도착</td></tr>
</tbody></table>
```

## 결론

"배송 이력 표를 찾지 못했습니다" 경고 4건은 **버그가 아니라 정상**이다.
아직 배송이 시작되지 않은 주문이라 표가 존재하지 않는다.

## 개선할 것

1. 이력 표가 없을 때 **경고 대신 상태로 기록**해라.
   `TrackingStatus: "배송전"` 또는 `DeliveryProgress` 필드를 두고,
   경고 문구는 `배송 이력 표를 찾지 못했습니다` 대신
   `아직 배송이 시작되지 않아 이력이 없습니다`로 구분해라.

2. **진행 단계를 수집해라.** 배송 전 주문도 어디까지 진행됐는지 알 수 있다.
   완료된 단계와 미완료 단계는 클래스가 다르지만(kBFVZh vs bphNHp) 해시라 쓸 수 없다.
   대신 **단계 이름 목록**(결제완료·상품준비중·배송시작·배송중·배송완료)을 수집하고,
   현재 상태(`OrderStatus`)와 대조해 몇 번째 단계인지 계산해라.

3. **도착 예정 안내를 수집해라.**
   `내일(토) 새벽 7시 전 도착 보장`, `어제(목) 도착 완료` 같은 값이 상단에 있다.
   `DeliveryPromise` 필드로 저장한다.

4. 송장번호가 **빈 문자열**이면 `null`로 정규화해라. 지금은 빈 문자열이 들어갈 수 있다.

# 형태 C — 배송중 (실측 추가)

배송 전(A)과 배송 완료(B) 사이에 **배송중** 상태가 있다. 세 형태로 확정.

```html
<div class="sc-b55961ed-1 hbKRpw">오늘 도착 보장</div>
<div class="sc-69a3001b-0 jGIPAi">고객님의 상품을 배송중입니다.</div>

<!-- 진행 단계: 배송중까지 완료(kBFVZh), 배송완료만 미완료(bphNHp) -->
결제완료(kBFVZh) 상품준비중(kBFVZh) 배송시작(kBFVZh) 배송중(kBFVZh) 배송완료(bphNHp)

<td>송장번호</td><td>10327825290451</td>   <!-- 있음 -->

<table><thead><tr><th>시간</th><th>현재위치</th><th>배송상태</th></tr></thead>
<tbody>
  <tr><td>오늘 09:11</td><td>안양1</td><td>배송출발</td></tr>
  <tr><td>오늘 08:36</td><td>안양1</td><td>캠프도착</td></tr>
</tbody></table>
```

## 세 형태 비교

| | A 상품준비중 | C 배송중 | B 배송완료 |
|---|---|---|---|
| 송장번호 | 빈칸 | **있음** | 있음 |
| 이력 표 | 없음 | **있음(2행)** | 있음(3행) |
| 도착 안내 | 내일(토) 새벽 7시 전 도착 보장 | 오늘 도착 보장 | 어제(목) 도착 완료 |
| 설명문 | 준비시작되었습니다 | 배송중입니다 | 배송완료 되었습니다 |
| 마지막 이벤트 | — | 배송출발 | 배송완료 |
| 상품수령방법 행 | 없음 | 없음 | **있음**(문앞 전달) |

## 판정 기준 정정

**"송장번호 유무"로 발송 여부를 가르는 것은 맞다.** A만 빈칸이고 C·B는 있다.

다만 **완료 여부는 별개 축**이다. C는 발송됐지만 완료가 아니다.
- `ShipmentStarted`: 송장번호가 있으면 true (C, B)
- `DeliveryCompleted`: 이력에 `배송완료` 이벤트가 있으면 true (B만)

C 상태의 주문은 나중에 다시 수집하면 이력이 늘어난다. 재수집 시 **같은 송장번호의
이력을 갱신**할 수 있어야 한다.

## 상대 시각 주의

C에서 `오늘 09:11`, B에서 `어제 23:07`이 나온다. 두 표기 모두 처리해야 하며,
**수집 시점 기준**으로 절대 시각을 계산한다. 원문은 반드시 함께 보존한다.
같은 주문을 다른 날 재수집하면 `오늘`이 `어제`로 바뀌므로, 원문만 믿으면 안 되고
절대 시각으로 변환해 저장해야 중복·갱신 판정이 가능하다.

## 배송요청사항 값이 다르다

A/B는 `새벽: 문 앞 (자유 출입가능)`, C는 `문 앞`이다. 주문마다 다르므로 고정값으로
가정하지 마라. 개인 식별성은 없으니 수집해도 된다.

# 네이버 주문 이력 데이터셋

## 한 줄 요약

네이버페이 결제내역에서 본인의 쇼핑 주문 기록을 모아 정리한 데이터다.

## 왜 만들었나

A-COP은 "제 주문 어떻게 됐나요?" 같은 문의에 답해야 한다.

그러려면 **실제 주문 기록이 어떤 모양인지** 알아야 한다. 가상의 예시 데이터로는 실제 상황을 재현할 수 없다. 그래서 진짜 쇼핑몰에서 실제 주문 기록을 받아왔다.

쿠팡(`../coupang_order_history/`)과 함께 **서로 다른 쇼핑몰 두 곳**의 기록을 확보해, 한 곳에만 맞춰진 구조가 되지 않게 했다.

## 무엇이 들어 있나

| 파일 | 내용 |
|---|---|
| `raw/naver_2026-08-20_68건_cyw.json` | 크롤러가 받아온 원본 (첫 수집) |
| `raw/naver_2026-08-21_102건_kjh.json` | 팀원 제출본. ★파일명은 102건인데 실제로는 101건이다 |
| `raw/naver_2026-08-21_44건_syh.json` | 팀원 제출본 |
| `raw/naver_2026-08-21_57건_csw.json` | 팀원 제출본 |
| `processed/orders.jsonl` | A-COP 스키마로 정리한 결과 **270건** (2026-08-29 재생성) |
| `order_schema.json` | 결과가 어떤 모양이어야 하는지 적어둔 규격 |
| `scripts/crawler/` | 주문 기록을 받아오는 프로그램 |
| `scripts/normalize.py` | 원본을 스키마에 맞게 바꾸는 프로그램 |

## 어떻게 받아왔나

네이버페이 결제내역 페이지를 브라우저로 열어 화면을 읽는 방식이다.

로그인은 사람이 직접 한다. 프로그램이 아이디와 비밀번호를 다루지 않는다. 사람이 로그인한 브라우저 상태를 프로그램이 이어받아 쓴다.

쇼핑 주문만 골라내기 위해 `serviceChannel=SHOPPING` 조건을 쓴다. 이걸 안 쓰면 송금이나 충전 같은 결제 기록까지 섞인다.

조회와 조회 사이에는 무작위 대기를 넣는다. 기계가 일정한 간격으로 두드리면 차단 대상이 되기 때문이다.

## A-COP에서 어디에 쓰나

계획서의 Core 1(Case Runtime & Coordination)이 쓴다.

Core 1의 Context Broker는 문의에 답하기 위해 필요한 정보를 모아 조립하는 부분이다. 그때 "이 고객의 주문 기록"이 재료로 들어간다.

## 개인정보

다음은 저장하지 않는다.

- 받는 사람 이름
- 전화번호
- 상세주소

배송지는 시·도와 시·군·구까지만 남긴다. `서울특별시 서초구`까지는 남기고 그 뒤는 버린다.

원본 데이터(`raw/`)와 정리 결과(`processed/`)는 git에 올리지 않는다. 본인의 실제 구매 기록이기 때문이다.

| 2023 | 15 |

한 건은 이런 모양이다.

```json
{
  "order_id": "2026070144299551",
  "order_status": "구매확정완료",
  "seller_name": "하우저스",
  "product": {"name": "엑츠 액츠세제...", "quantity": 1, "unit_price": 8880},
  "payment": {"amount": 11880, "paid_at": "2026-07-01T12:27:48+09:00"},

```

`product`, `payment`, `shipping`, `cs`로 나눈 이유는 문의 유형이 그 단위로 나뉘기 때문이다. 상품 문의, 결제 문의, 배송 문의, 취소·반품 문의가 각각 다른 정보를 필요로 한다.

## 알려진 문제 — 첫 수집분에서 4건 누락

아래는 **cyw 제출본 68건에 대한 것이다.** 나머지 세 명의 제출본은 각자의 실제 주문 수와
대조하지 않았으므로, 270건 전체가 "전량"인지는 확인되지 않았다.

**cyw 계정의 실제 주문은 72건인데 68건만 수집됐다.** 다음 4건이 빠져 있다.

```
2022043085163701
2023051853027171
2023090698394101
2024032354706671
```

★**2026-09-01 정정 — 여기 적혀 있던 원인 진단이 틀렸다.**

전에는 "크롤러가 카드마다 주문을 하나씩만 읽었다"고 적혀 있었다. 코드를 읽어 보니
그렇지 않다. `naver_order_crawler.py` 는 카드 안의 **모든** 상세 링크를 순회한다
(`for link_index in range(detail_links.count())`). 수집 당시 로그
(`raw/_crawl_log.txt`)도 같은 것을 말한다 — 모든 페이지에서 **카드 수와 주문 링크
수가 같았다.**

```
1페이지: 카드 15개, 주문 링크 15개
2페이지: 카드 14개, 주문 링크 14개
3페이지: 카드 12개, 주문 링크 12개
```

즉 크롤러가 링크를 빠뜨린 게 아니라 **화면이 그 카드에 상세 링크를 하나만
내줬다.** 그리고 이 크롤러는 주문번호를 **상세 URL 에서만** 얻는다
(`orders.pay.naver.com/order/status/(\d+)`). 그래서 자기 상세 링크가 없는 주문은
식별할 방법 자체가 없어 **구조적으로 보이지 않는다.** 이게 진짜 원인이다.

★이 정정이 중요한 이유: 옛 진단대로 "카드 대신 링크 단위로 순회하도록" 고치면
**이미 그렇게 돼 있는 코드를 다시 고치는 것**이라 한 세션을 헛되이 쓴다.

고치려면 로그인한 상태에서 **주문이 둘 이상 든 카드의 DOM 을 실제로 떠서** 나머지
주문이 어떤 요소로 그려지는지 봐야 한다. 그 전에는 `DETAIL_LINK_SELECTOR` 를 바꿀
근거가 없다. 세션 파일이 지워져 있어 이 작업은 로그인부터 해야 한다.

그동안 이 손실이 **조용히** 일어나지는 않게 해뒀다(2026-09-01):

- 상세 링크가 하나도 없는 카드는 전에는 아무 기록 없이 사라졌다(안쪽 for 문이 0회
  돈다). 이제 `상세 링크 없는 카드` 로 세어 완료 통계에 낸다
- 모든 카드에서 링크가 정확히 1개면 완료 시 주의 문구를 남긴다 — 위 로그가 바로
  그 상태였다

아래 표는 사람이 화면을 직접 세어 만든 것이다.

| 페이지 | 화면의 카드 수 | 실제 주문 수 | 차이 |
|---|---|---|---|
| 1 | 15 | 15 | 0 |
| 2 | 14 | 15 | +1 |
| 3 | 12 | 14 | +2 |
| 4 | 15 | 15 | 0 |
| 5 | 12 | 13 | +1 |
| 합계 | 68 | **72** | **+4** |

이 문제는 **아직 고쳐지지 않았다.** 다만 고치는 방향은 위 정정대로 "링크 단위로 읽기"가
아니다 — 그건 이미 그렇게 돼 있다. 링크가 없는 주문을 화면에서 어떻게 식별할지를
정해야 하고, 그러려면 로그인 상태의 실제 DOM 이 필요하다.
같은 크롤러로 받은 나머지 세 제출본에도 같은 누락이 있을 가능성이 높다.

270건으로 구조 파악과 스키마 검증에는 충분하다. 다만 "전량 수집"이라고 말할 수는 없다.

# 택배 배송 이력 데이터셋

## 한 줄 요약

송장번호를 넣으면 그 택배가 언제 어디를 거쳐 갔는지 기록을 받아오는 도구와, 그 결과 데이터다.

## 왜 만들었나

A-COP은 고객 문의에 답하는 시스템이다. "제 물건 어디쯤 왔나요?"는 가장 흔한 질문이다.

이 질문에 답하려면 **택배가 지금 어느 단계인지** 알아야 한다. 그 정보를 실제로 받아오는 통로가 이 폴더다.

## 무엇이 들어 있나

| 파일 | 내용 |
|---|---|
| `courier_codes.json` | 국내 택배사 111곳의 이름과 코드 |
| `scripts/track.py` | 송장번호를 넣으면 배송 이력을 받아오는 실행 파일 |
| `scripts/naver_parcel_api.py` | 실제 조회를 수행하는 부분 |
| `scripts/merge_incoming.py` | 팀원 제출본(`raw/_incoming_*/`)을 `processed/` 로 합치는 실행 파일 |
| `raw/tracking_*.jsonl` | 조회한 결과 원본. 실행한 날짜별로 쌓인다 |
| `raw/_incoming_*/` | 팀원이 각자 자기 계정에서 모아 보낸 제출본 |
| `processed/tracking.jsonl` | 네이버 API 조회분을 하나로 합치고 송장번호 기준 중복을 제거한 것 |
| `processed/tracking_coupang.jsonl` | 쿠팡 화면 수집분. ★위와 **다른 스키마**다 |
| `tracking_schema.json` | 네이버 조회 결과의 규격 |
| `tracking_coupang_schema.json` | 쿠팡 수집 결과의 규격. 왜 따로인지도 여기 적혀 있다 |
| `legacy/` | 택배사 홈페이지를 직접 읽던 이전 방식. 지금은 안 쓴다 |

## 어떻게 받아오나

택배사마다 홈페이지가 다르고 화면 구조도 제각각이다. 111곳을 각각 대응하는 것은 현실적이지 않다.

그래서 **네이버 택배조회를 통로로 쓴다.** 네이버는 이미 모든 택배사를 하나의 형식으로 정리해 두었다.

```
송장번호 + 택배사 코드  →  네이버 택배조회  →  통일된 형식의 배송 이력
```

이 방식의 장점은 택배사가 홈페이지를 바꿔도 영향을 받지 않는다는 것이다. 단점은 네이버가 지원하지 않는 택배사는 조회할 수 없다는 것이다.

## A-COP에서 어디에 쓰나

계획서의 Core 2(Access & Action Platform)가 쓴다.

Core 2는 실제로 외부에 무언가를 요청하고 결과를 받아오는 층이다. "배송 조회"라는 행동을 수행할 때 이 도구를 호출한다.

**주의**: 이 폴더는 학습용 데이터가 아니다. 모델을 훈련시키는 재료가 아니라, 실행 시점에 호출하는 도구다.

`processed/tracking.jsonl`은 그래서 "전처리한 학습 데이터"가 아니라 **날짜별
원본을 합치고 중복만 제거한 것**이다(2026-08-28에 만들었다 — 그 전까지는
`processed/`가 비어 있었고, 그게 정상이라고 이 문서에 적혀 있었다).
정규화·토큰화 같은 학습용 전처리는 여전히 하지 않는다.

## 사람처럼 보이게 하는 장치

조회와 조회 사이에 무작위 대기를 넣는다. 기계가 일정한 간격으로 두드리면 차단 대상이 되기 때문이다.

자세한 사용법과 옵션은 `README.md`에 있다.

## 개인정보

조회 결과에서 다음은 저장하지 않는다.

- 받는 사람 이름
- 전화번호
- 상세주소

배송 경로에 나오는 물류센터 이름은 개인 식별성이 없으므로 남긴다.

이 중 **배송 이력이 실제로 나온 것은 12건**이다. 나머지 45건은 조회에
실패했다(`not_found` 44 · `no_history` 1).

실패가 많은 이유는 데이터의 문제가 아니라 **송장번호가 오래됐기 때문**이다. 택배사는 배송이 끝난 뒤 일정 기간이 지나면 기록을 지운다. 대개 6개월에서 1년이다. 그래서 오래된 주문의 송장번호로는 아무것도 나오지 않는다.

배송 이력 한 건은 이런 모양이다.

```json
{"kind": "집화처리", "where": "비앤비솔루션", "timeString": "2026-07-01 10:34:38", "level": 2}
```

`kind`는 무슨 일이 있었는지, `where`는 어디에서, `timeString`은 언제다. `level`은 배송 단계 번호로, 숫자가 클수록 고객에게 가까워진 상태다.

## 목록 대비 sourceType 차이

- 목록: `sourceType=MyCoupang_my_orders_list_product_title`
- 상세: `sourceType=MyCoupang_order_detail_product_title`

두 값을 모두 매칭하도록 `href*="_product_title"` 형태로 느슨하게 잡는 편이 안전하다.

## 중요: 택배사·송장번호가 없다

상세 페이지에도 택배사와 송장번호가 **없다**. `배송 조회` 버튼(`button` 텍스트)이 있고
클릭해야 별도 화면이 뜨는 구조로 보인다. 즉 배송 이력을 얻으려면 한 단계 더 들어가야 한다.

네이버는 상세 페이지의 `배송조회` 버튼을 눌러 `/order/delivery/tracking/...`로 이동해
택배사와 송장번호를 얻었다. 쿠팡도 같은 패턴일 가능성이 높다.

## PII (수집 금지)

- 연락처: 010****7059
- 받는주소: (06725) 서울특별시 서초구 남부순환로339길 ** ***호 ( 서초동 )

# 배송조회 화면 구조 (실측)

`배송 조회` 버튼을 눌렀을 때 나오는 화면. 여기에 **배송 이력 표가 그대로 있다.**

## 얻을 수 있는 필드

| 항목 | 값 예시 | 추출 방법 |
|---|---|---|
| 택배사 | 로켓배송 | 송장번호 라벨과 같은 표 안의 첫 행 |
| 송장번호 | 10327825750572 | `송장번호` 라벨(`td`)의 다음 `td` |
| 배송 요약 | 어제(목) 도착 완료 | 상단 요약 div |
| 배송 상태문 | 고객님이 주문하신 상품이 배송완료 되었습니다. | 요약 아래 div |
| 상품수령방법 | 문앞 전달 | 받는사람 표의 해당 행 |

## 배송 이력 표 (핵심)

```html
<table>
  <thead><tr><th>시간</th><th>현재위치</th><th>배송상태</th></tr></thead>
  <tbody>
    <tr><td>어제 23:07</td><td>안양1</td><td>배송완료</td></tr>
    <tr><td>어제 21:32</td><td>안양1</td><td>배송출발</td></tr>
    <tr><td>어제 20:50</td><td>안양1</td><td>캠프도착</td></tr>
  </tbody>
</table>
```

추출 방법: `thead`에 `시간`·`현재위치`·`배송상태` 3열이 있는 `table`을 찾아
`tbody tr`의 `td` 3개를 각각 매핑한다. 클래스는 쓰지 않는다.

`courier_tracking` 데이터셋의 이벤트 스키마와 대응:
- `시간` -> `timeString`
- `현재위치` -> `where`
- `배송상태` -> `kind`

## 중요한 결론

**네이버와 달리 택배사 조회 API를 따로 붙일 필요가 없다.**

네이버는 송장번호만 얻고 `courier_tracking`으로 별도 조회해야 했다. 쿠팡은 로켓배송
자체 물류라 이 화면에 이력이 직접 나온다. 다만 시간 표기가 `어제 23:07`처럼 상대적이라
주문일 기준으로 절대 시각을 계산해야 한다.

로켓배송이 아닌 판매자배송 주문은 일반 택배사(CJ 등)일 수 있다. 그 경우 택배사명이
`로켓배송` 대신 실제 택배사명으로 나올 것이고, 그때는 `courier_tracking`으로 조회할 수
있다. 표본이 1건뿐이라 확인 필요.

## PII (수집 금지)

이 화면에도 받는사람(최*우), 받는주소, 배송요청사항이 있다. 수집하지 않는다.
`상품수령방법`(문앞 전달)은 개인 식별성이 없어 수집해도 된다.

# 페이지네이션 (실측)

주문목록 하단의 이전/다음 버튼. **`<a>`가 아니라 `<button>`이다.**

```html
<!-- 이전 (첫 페이지에서 비활성) -->
<button class="sc-19a0c88a-0 boBywg sc-7a9dfa59-1 gULjxs" disabled="">
  <svg ...></svg> 이전
</button>

<!-- 다음 -->
<button class="sc-19a0c88a-0 boBywg sc-7a9dfa59-1 gULjxs">
  다음 <svg ...></svg>
</button>
```

## 추출 방법 (클래스 금지)

- 다음 버튼: 모든 `button` 중 텍스트를 정리했을 때 `다음`으로 끝나거나 `다음`을 포함하는 것
- 이전 버튼: 같은 방식으로 `이전`
- **비활성 판정**: `disabled` 속성 유무. `disabled`면 그 방향으로 더 이동할 수 없다.
- SVG가 버튼 안에 있으므로 `textContent`를 쓰되 공백을 정리해서 비교한다.

## 기존 구현의 문제

현재 확장은 `a[rel="next"]`, `a[aria-label="다음"]`, `.pagination a.next`를 찾는다.
셋 다 존재하지 않으므로 **페이지 넘김이 전혀 동작하지 않았다.**

## 종료 조건

- 다음 버튼이 없거나
- 다음 버튼에 `disabled` 속성이 있거나
- 클릭 후에도 수집된 주문번호가 이전 페이지와 동일하면 (네이버에서 겪은 무한 루프 방지)

세 조건 중 하나라도 만족하면 순회를 끝낸다.
