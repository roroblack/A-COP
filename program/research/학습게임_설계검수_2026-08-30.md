# 결론

2026-08-30 기준으로 이 설계는 그대로 구현할 단계가 아니다. 가장 치명적인 문제는 **실행 성공·pytest 통과·호출 순서 정답을 코드베이스 이해의 증거로 간주하는 구성타당도 오류**다. 이 오라클들은 행동의 정오를 검증하지만, 계약·상태·권한·변경 파급효과에 대한 정신모형이 형성됐는지는 검증하지 않는다. 이는 아래 근거를 바탕으로 한 내 추론이다.

또한 5단계 전체가 코드베이스 이해 교육법으로 검증된 사례는 찾지 못했다. 개별 부품에는 근거가 있지만, 특히 뮤테이션·고정 1/3/7일 반복·읽기 전용 의존 그래프는 주장하는 학습 효과보다 근거가 약하다.

## 치명적 약점

### 1. “초보자도 먼저 예측”은 잘못된 일괄 정책이다

예측을 전면 폐기해야 한다는 근거는 없다. 2024년 프로그래밍 교육 실험에서는 코드를 먼저 예측한 집단이 일반적인 설명 후 코딩 집단보다 학습평가와 정서 반응에서 나았다. POE의 정식 형태도 단순히 맞힌 뒤 공개하는 것이 아니라 **예측→관찰→예측과 관찰의 차이 설명**이다. [Prediction versus production for teaching computer programming](https://doi.org/10.1016/j.learninstruc.2023.101871)

그러나 A-COP의 “다음 호출 하나 맞히기”는 productive failure라기보다 prequestion에 가깝다. prequestion 메타분석은 물어본 바로 그 내용에는 중간 효과가 있었지만(g=0.54), 묻지 않은 내용으로의 일반화는 사실상 없었다(g=0.04). 호출 순서 퀴즈 점수가 코드베이스 전체 구조 이해로 전이된다고 볼 수 없다. [Guessing as a learning intervention: meta-analysis](https://doi.org/10.3758/s13423-023-02353-8)

Productive failure 역시 “아무 설명 없이 틀려보게 하기”가 아니다. 53개 연구·166개 비교 메타분석에서 문제 해결 후 수업이 개념·전이에 g=0.36의 이점을 보였지만, 절차 지식에는 차이가 없었고, 효과는 학습자가 여러 해결 표현을 생성하고 뒤의 수업에서 이를 정답 구조와 비교·통합하도록 설계했을 때 컸다. [Sinha & Kapur, 2021](https://doi.org/10.3102/00346543211019105) 오류 자체보다 뒤의 오류 비교·정교화가 중요하다는 실험도 있다. [How to make failure productive](https://www.sciencedirect.com/science/article/pii/S0959475218304997)

따라서 이 상황에서는 둘 중 하나를 고르는 것이 아니라 사전지식에 따라 달라야 한다.

- 완전 초보자: 해설된 실제 실행 사례→일부 단계가 비어 있는 completion→독립 예측
- 해당 서브시스템 경험자: 짧은 예측→즉시 트레이스→불일치 원인 설명
- 고숙련자: 장애·변경 가설을 먼저 세우는 productive-failure형 과제

현재 설계에는 입문 수준 진단, worked example, 단계적 fading이 없다. 56개 앱 모듈 전체를 처음 보는 사람에게 곧바로 예측을 요구하면 탐색 부하를 학습으로 오인할 수 있다. 초보자에게 worked example이 일반 문제풀이보다 유리하고, 숙련도가 올라가면 지도를 줄여야 한다는 근거가 있다. [Worked examples, example-problem and problem-example pairs](https://www.sciencedirect.com/science/article/pii/S0361476X1000055X)

### 2. “예측 후 공개”가 정답 맞히기로 퇴화할 가능성이 높다

A-COP과 정확히 같은 형식이 정답 맞히기 게임으로 퇴화했다는 직접 사례는 찾지 못했다. **정확히 일치하는 근거 없음**이다.

다만 위험을 뒷받침하는 인접 근거는 있다. 2025년 Parsons 문제 연구 검토는 학습자가 과제를 성공시켜도 목표 개념에는 주의를 기울이지 않는 selective-attention 문제가 있다고 정리한다. 정답 선택형·재배열형 과제는 문제 공간을 줄이는 대신 표면 단서로 통과할 길도 만든다. [Parsons problems and computing education learning theories](https://doi.org/10.1145/3769994.3770032)

현재 방식에서는 호출 이름이나 반복 패턴을 암기해도 통과할 수 있다. 다음 호출을 맞힌 뒤 다음을 요구하지 않으면 구조 이해 증거가 되지 않는다.

- 왜 다른 후보 호출은 불가능한가
- 어느 상태나 권한 조건이 이 간선을 활성화했는가
- 입력 조건 하나가 바뀌면 경로가 어디서 갈라지는가
- 같은 원리를 보지 않은 모듈에 적용할 수 있는가

자기설명은 이 구멍을 메울 근거가 있다. 일반 메타분석에서 자기설명 프롬프트의 평균 효과는 대략 g=0.55였고, 특히 개념을 설명하게 하는 프롬프트가 단순 수행 점검보다 강했다. [Self-explanation meta-analysis summary](https://www.clearinghouse.edu.tum.de/wp-content/uploads/2023/09/CHU-KR-25_ENG_Bisra_2018_Selbsterklaerungen.pdf) 소스 코드 이해 연구에서도 자기설명의 양과 학습량 사이에 강한 양의 상관이 보고됐다. [Open self-explanation during source-code comprehension](https://cdn.aaai.org/ocs/18479/18479-79419-1-PB.pdf)

다만 자기설명이 예측 퀴즈보다 직접적으로 우월하다는 코드베이스 규모의 head-to-head 연구는 찾지 못했다. 따라서 “대체”보다 **예측을 자기설명의 입력으로 격하**하는 것이 타당하다.

### 3. 뮤테이션 단계가 가르치는 것은 구조 이해가 아니라 테스트 설계일 가능성이 크다

뮤테이션 교육 연구가 입증한 효과는 주로 테스트 작성, mutation score, mutant-state propagation 이해다. 2025년 FSE 연구에서도 scaffolding과 시각화가 낮은 성취자의 뮤테이션 과제 수행을 개선했지만, 대상은 52~1,010 LOC의 자기완결적 Java 클래스였으며 평가도 테스트 수, 커버리지, mutation score, equivalent mutant 설명이었다. 18k줄 다중 모듈 구조 이해로의 전이는 측정하지 않았다. [Potter et al., FSE 2025](https://doi.org/10.1145/3696630.3727240)

산업 규모 자료는 뮤테이션 피드백이 개발자로 하여금 더 좋은 테스트를 작성하게 하고 실제 결함과 관련된 mutant를 잡는 데 유용함을 보여준다. 하지만 이것 역시 **테스트 품질 향상 근거이지 아키텍처 학습 근거가 아니다**. [Long Term Effects of Mutation Testing](https://research.google/pubs/long-term-effects-of-mutation-testing/)

따라서 “깨진 pytest 결과만 보고 변경 파일과 내용을 맞힌다”는 과제는 다음 편법을 강화할 수 있다.

- 테스트 이름과 assertion 문구에서 파일을 역추론한다.
- 도메인 계약보다 fixture와 mock 배치를 암기한다.
- 자주 깨지는 테스트와 모듈의 통계적 연관을 외운다.
- 여러 변경이 같은 실패 집합을 만드는 경우에도 임의로 하나를 고른다.

이 편법이 실제로 A-COP에서 발생한다는 직접 근거는 없다. **근거 없음, 내 추론**이다. 이를 막으려면 보지 않은 테스트·다른 모듈·새 입력에서의 전이 평가가 필요하다.

### 4. 테스트 60개라는 숫자만으로는 뮤테이션 게임의 성립 여부를 판단할 수 없다

60개/18,165줄은 약 3.3개 테스트/KLOC지만, 테스트 개수는 커버리지나 oracle 강도를 나타내지 않는다. 하나의 parametrized test가 넓게 검사할 수도 있고, 60개가 같은 happy path만 반복할 수도 있다.

뮤턴트가 유효한 실패 신호를 만들려면 최소한 다음 세 조건이 필요하다.

1. 변형된 코드가 테스트에서 실행된다.
2. 변형이 내부 상태를 실제로 감염시킨다.
3. 그 차이가 assertion까지 전파된다.

2025년 FSE 논문도 이 세 번째 state-propagation 문제와 equivalent mutant를 명시한다. [FSE 2025 mutation study](https://doi.org/10.1145/3696630.3727240) Python의 `mutmut`도 기본 생성 범위가 넓어질 수 있어 covered line만 변형하는 별도 옵션을 제공하고, 공통 함수에 수백 테스트가 우연히 매달리면 느리고 해석하기 어려운 실패가 된다고 경고한다. [mutmut 공식 문서](https://github.com/boxed/mutmut/blob/main/README.rst)

Equivalent mutant는 부차적 예외가 아니다. 일반적으로 자동 판정하기 어려운 문제이며, 2024년 3,302개 mutant 쌍 연구도 기존·LLM 기반 탐지법의 일반화 한계를 보고했다. [ISSTA 2024 equivalent-mutant detection](https://doi.org/10.1145/3650212.3680395) 사람이 직접 만든 mutant에서는 equivalent 비율이 10% 미만이었지만, 개발자들이 equivalent 여부를 정확히 판별하는 데 상당히 어려움을 겪었다. [2024/2025 Code Defenders 연구](https://arxiv.org/abs/2404.09241)

그러므로 현재 수치만으로 3단계가 가능하다고 말할 수 없다. 먼저 실제로 다음을 측정해야 한다.

- 라인·분기 커버리지
- 모듈별 reached/killed/survived/timeout 비율
- 실패 테스트 집합이 서로 다른 mutant를 구분하는 정도
- flaky test와 환경 의존 실패
- 전문가 두 명의 equivalent 판정 일치도
- mutant 하나당 실행시간

이 자료 없이 자동 생성 mutant를 게임에 넣으면 “정답 없는 문제”, “아무 테스트도 깨지지 않는 문제”, “여러 정답이 가능한 문제”가 섞인다.

### 5. 고정 1·3·7일 반복은 기억에는 그럴듯하지만 재방문 장치로는 입증되지 않았다

프로그래밍 교육에서도 spacing과 retrieval practice 자체에는 근거가 있다. 입문 Python 강좌에서 학기 중 사용한 spaced/interleaved retrieval 도구가 동기와 학습에 효과적이었다. [ICER 2019 retrieval-practice tool](https://doi.org/10.1145/3291279.3339411) 프로그래밍 객관식 문제를 대상으로 한 distributed-practice 연구도 있다. [Distributed practice for novice programming students](https://doi.org/10.1177/18344909211008264)

그러나 이 사례들은 수업에 포함되거나 참여가 구조적으로 유도된 환경이다. **자발적 CLI 사용자가 1·3·7일 뒤 실제로 돌아왔다는 사례는 찾지 못했다.** 기억 효과와 재방문 행동은 별개다. 알림조차 과의존을 만들 수 있다는 2024년 실험도 있다. [Smartphone-based study reminders can be a double-edged sword](https://www.nature.com/articles/s41539-024-00253-7)

또한 모든 능력에 고정된 1·3·7일을 쓰는 근거도 없다. **근거 없음, 내 추론**이다. 경로 추적, 권한 판단, 패치 작성은 망각 속도와 수행비용이 서로 다르므로 실제 회상 성공도에 따라 간격을 조정해야 한다.

### 6. 읽기 전용 의존 그래프는 장식으로 끝날 가능성이 있다

시각화가 무효인 것은 아니다. 실행 trace 시각화의 통제실험에서는 IDE만 사용한 집단보다 시간이 22% 줄고 정답률이 43% 높았다. [Controlled experiment for trace visualization](https://doi.org/10.1109/TSE.2010.47)

하지만 학습 효과는 시각화의 존재보다 학습자가 그것으로 무엇을 하느냐에 좌우된다. 프로그램 시각화 연구는 단순 viewing보다 질문에 응답하거나 조작하는 높은 engagement가 중요하고, 주제 복잡도와 학습자 특성도 결과를 조절한다고 정리한다. [Active learning using program visualization](https://pmc.ncbi.nlm.nih.gov/articles/PMC6302837/)

2026년 CodeMap 연구도 사용자 선호와 사용행태는 긍정적이었지만, 연구진 스스로 정식 성능 비교가 아닌 15명의 소규모 관찰 연구라고 명시했다. 한 초보자는 정보량 때문에 지도가 압도적이라고 평가했다. [CodeMap, ICPC 2026](https://doi.org/10.1145/3794763.3794822)

A-COP의 지도는 더 약하다. AST 의존 그래프는 import 관계는 보여도 다음을 자동으로 보장하지 않는다.

- 런타임 dispatch와 플러그인 등록
- 설정·환경변수·DB를 통한 결합
- 상태전이와 불변조건
- 권한 검사의 의미
- 호출 빈도와 실제 대표 경로
- 변경 시 함께 수정되는 파일

이 평가는 **Python 정적 import 그래프의 표현력에 관한 내 추론**이다. 사용자가 가설을 세우고 경로를 강조·수정·비교하지 않는 읽기 전용 지도라면 학습도구가 아니라 네비게이션 보조물이다.

### 7. 최종 보스전 하나로 “전체 구조 이해”를 인증할 수 없다

저위험 백로그 하나는 특정 영역에 대한 국소 변경 능력만 보여준다. 테스트 통과와 리뷰 승인도 다른 모듈로의 전이를 증명하지 않는다. **근거 없음, 내 추론**이다.

능력 목록을 인증하려면 학습에 사용하지 않은 모듈에서 지연 평가가 있어야 한다. 예를 들어 “상태전이 설명 가능”은 새 Case 유형의 전이표를 역작성하고 반례를 찾게 해야 하며, “변경 파급 추론 가능”은 보지 않은 커밋의 영향을 예측한 뒤 실제 diff와 비교해야 한다.

## 더 나은 대안

이 18k줄 코드베이스 전체를 대상으로 현재 5단 구성보다 우월하다고 직접 검증된 단일 형식은 찾지 못했다. 가장 근거가 나은 대안은 게임 단계를 유지하는 것이 아니라 **worked example에서 시작해 실제 유지보수 작업으로 fading하는 적응형 견습 과정**이다.

권장 흐름은 다음과 같다.

1. 전문가가 실제 Case 하나를 실행하면서 목표, 상태, 권한, 호출 이유를 subgoal 단위로 설명한다.
2. 학습자가 일부가 빈 trace·상태표·계약표를 복원한다.
3. 결과를 예측하고 실제 trace와 비교한 뒤 불일치 원인을 자기설명한다.
4. 과거의 실제 회귀 버그를 재현하고 최소 원인을 찾는다.
5. 실제 수정 커밋을 가린 채 패치를 제안하고 원래 커밋과 비교한다.
6. 동료와 PR을 리뷰하며 변경 전후의 행동 차이와 위험을 설명한다.
7. 보지 않은 모듈에서 지연 전이 평가를 한다.

부분적으로 이를 지지하는 근거는 다음과 같다.

- Faded Parsons 문제는 237명 수업 연구에서 code tracing·code writing보다 패턴 습득과 일반 코드 작성에 효과적이었다. 이는 완성 예제와 독립 구현 사이의 reconstruction 단계를 지지한다. [Designing Exercises to Teach Programming Patterns](https://www2.eecs.berkeley.edu/Pubs/TechRpts/2022/EECS-2022-257.html)
- 2025년 8주 디버깅 연구에서는 코드별 구체적 worked example을 준 집단이 한 세션 후 80% 정확도에 도달하고 3주 뒤에도 유지했다. 추상 지침이나 비계 없는 시행착오보다 직접적인 대안 근거다. 다만 소규모 코드 조각 연구라는 제한이 있다. [Context-Specific Instruction](https://arxiv.org/abs/2509.22420)
- 2024년 79명 통제실험에서 구조화된 peer code review 집단의 성적이 대조군보다 높았다. [Collaborative Peer Code Review](https://doi.org/10.55612/s-5002-063-007)
- Google의 코드리뷰 사례연구와 324명 설문에서는 근거를 설명하는 리뷰와 표준에 연결된 예시가 학습을 돕고, 얕은 지적과 맥락을 무시한 리뷰는 방해했다. [Effective Teaching through Code Reviews](https://doi.org/10.1145/3660764)
- 코드 change comprehension 연구에서는 학생들이 두 버전의 행동적 유사성을 과대평가하는 문제가 관찰됐다. 따라서 정적 파일 맞히기보다 실제 diff를 놓고 “행동이 동일한가”를 검증하는 과제가 필요하다. [ICSE 2024—Barriers for Students During Code Change Comprehension](https://conf.researchr.org/details/icse-2024/icse-2024-research-track/227/Barriers-for-Students-During-Code-Change-Comprehension)

명세 재구성, 문서 역작성, 커밋 히스토리 기반 학습이 이 코드베이스에서 다른 방식보다 우월하다는 직접 실험은 찾지 못했다. 다만 이들은 산출물을 통해 계약·변경 이유·누락된 지식을 검사할 수 있어, 호출명 맞히기보다 목표 능력과 가까운 과제라는 것이 내 추론이다.

## 설계 변경 권고 5개

### 1. 5단 고정 코스를 “worked example→completion→독립 수행”의 적응형 코스로 바꾼다

가장 먼저 사전진단으로 모듈·테스트·도메인 경험을 측정하고, 초보자에게는 해설된 실제 Case 실행을 제공한다. 이후 trace 일부 복원, 전체 예측, 실제 변경으로 비계를 점차 제거한다. 예측은 모든 사람의 첫 행동이 아니라 이미 최소 정신모형이 있는 사람의 연습 단계로 옮긴다. 이는 초보자의 탐색 부하를 줄이면서 숙련자에게 과도한 설명을 주지 않기 위해서다.

### 2. 통과 기준을 pytest에서 “설명+반례+새 모듈 전이”로 확장한다

pytest는 행동 보존 오라클로만 사용한다. 각 과제에는 호출 이유, 상태·권한 전제, 대안 경로가 불가능한 이유, 입력 변경 시 갈라지는 지점을 구조화된 양식으로 답하게 한다. 학습에 사용하지 않은 모듈에서 같은 원리를 적용하는 지연 평가를 별도로 둔다. 능력 표시는 그 전이 평가를 통과했을 때만 부여한다. 그렇지 않으면 “테스트를 통과시켰다”와 “구조를 이해했다”가 계속 혼동된다.

### 3. 자동 뮤테이션 게임을 폐기하고 검증된 회귀 사례 중심의 결함 실험실로 축소한다

우선 git 히스토리에서 실제 버그 수정 커밋을 골라 수정 전 버전을 재현하고, 실패 관찰→원인 가설→최소 패치→원래 커밋 비교를 수행하게 한다. 뮤테이션은 보조 문제로만 남기고, covered·killed·비등가이며 실패 집합이 다른 후보와 구분되는 mutant만 전문가가 승인해 사용한다. 출시 전 모듈별 mutation baseline과 실행시간을 측정하고, 기준을 못 넘는 모듈에서는 뮤테이션 단계를 제공하지 않는다.

### 4. 읽기 전용 전체 그래프를 작업 중심의 가설 검증 지도으로 바꾼다

처음부터 56개 노드와 135개 간선을 노출하지 않는다. 현재 Case 경로와 직접 관련된 노드만 표시하고, 학습자가 예상 간선·상태·권한 경계를 먼저 그린 뒤 정적 분석과 실행 trace를 겹쳐 비교하게 한다. import, 실제 호출, 상태 접근, 권한 검사, 역사적 co-change를 서로 다른 간선으로 분리한다. 지도 사용 후에는 반드시 지도 없이 경로나 변경 영향을 재구성하게 해 도구 의존과 학습을 구분한다.

### 5. 고정 1·3·7일 복습을 팀 업무에 결합된 적응형 재현 과제로 바꾼다

재방문을 개인 의지에 맡기지 말고 PR 리뷰, 주간 장애 훈련, 페어 세션에 짧은 복습 과제를 삽입한다. 정답 여부뿐 아니라 자신감, 소요시간, 설명 완전도를 기록해 다음 간격과 난도를 조정한다. 같은 호출을 다시 묻지 말고 다른 모듈에서 같은 계약·상태 원리를 회상하게 한다. 1·3·7일은 초기 기본값으로만 사용하고, 실제 재방문율과 지연 전이 성과가 나오기 전에는 교육 효과를 주장하지 않아야 한다.
