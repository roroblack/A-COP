# 컴포저 v3 설계 대비 구현 대조

## 1. 결론

설계와 구현은 부분적으로만 일치한다. `acop_basement`와 `acop_composer` 디렉터리를 나눈 골격, revision 확인, 인증 scope, audit append는 존재한다. 그러나 v3의 핵심인 `POST /composer/toggle` 토글 전용 계약은 구현되지 않았고, 현재 구현은 전체 `ProjectConfig`를 검증·교체하는 v2형 `/composer/validate`·`/composer/apply`다. 또한 두 패키지는 디렉터리상 분리됐지만 하나의 `final-project-sample` 배포 설정에 함께 포함되며, Composer가 basement의 `ProjectConfig`와 설정에 결합돼 있다. 따라서 현재 상태는 v3 설계 대비 **불일치**로 판정한다.

## 3. 검증 항목별 판정표

설계 요구 항목은 설계 문서 §2.2~§2.4, §3, §4, §8.1~§8.2의 내용을 검증 가능한 단위로 나눴다. 설계 근거는 [`program/plan/A-COP_Composer_v3_설계_토글전용_UI이관.md`](../../program/plan/A-COP_Composer_v3_설계_토글전용_UI이관.md:57), 특히 endpoint와 처리 순서는 63~93행, 프로젝트 책임은 99~118행, 패키지 분할은 158~176행이다.

| 검증 항목 | 판정 | 근거와 대조 |
|---|---|---|
| Composer endpoint가 `POST /composer/toggle`이고 `target_type`, `target_id`, `active`, `base_revision`, `reason`을 받는다 | **미구현** | 구현 라우터는 `/composer/current`, `/composer/validate`, `/composer/apply`뿐이다 (`acop_composer/api.py:64-92`). payload도 전체 `config`를 요구한다 (`acop_composer/api.py:48-57`). |
| 대상 ID는 등록 목록에 있는지만 확인한다 | **불일치** | v3는 등록 ID 존재 확인만 요구한다(설계: `...md:75-81`). 구현은 `_validate_http_registry()`에서 team의 `implementation_ref` allowlist를 검사한다 (`acop_composer/service.py:55-69`). |
| Core 계약 모델을 깊이 검증하지 않는다 | **불일치** | `acop_composer`가 `ProjectConfig`, `ProjectConfigError`, `load_project_config`를 import한다 (`acop_composer/service.py:29-32`, `acop_composer/api.py:25-27`). `load_project_config()`는 Pydantic schema와 active team implementation import/class 계약까지 검사한다 (`acop_basement/core/project_config.py:114-177`). |

| append-only 감사 로그를 남긴다 | **불일치** | audit append 자체와 actor/revision/reason은 있다 (`acop_composer/api.py:101-112`, `137-140`). 그러나 v3의 `target_type`, `target_id`, old/new flag 중심 event가 아니라 전체 config의 `changed_fields`를 기록한다 (`acop_composer/api.py:101-106`). |

| `acop_basement`에 Composer 코드가 없어야 한다 | **불일치** | `acop_basement` 안에 `composer` 문자열과 Composer 전용 wiring이 있다 (`acop_basement/presentation/api/app.py:11-17`, `63-68`; `acop_basement/core/settings.py:50-52`). 직접 `from acop_composer` import는 없지만 basement의 app factory가 Composer router 주입을 알고 있고 Composer JWT 설정도 보유한다. |
| `acop_composer`는 선택 설치 패키지이고 고객 빌드에는 빠진다 | **불일치** | 패키지 탐색 설정이 하나의 배포물 `final-project-sample`에 `app*`, `acop_basement*`, `acop_composer*`를 함께 포함한다 (`pyproject.toml:5-8`, `17-22`). `setup.py`와 `setup.cfg`는 없다. 고객 compose 명령은 basement app을 기동하지만 별도 wheel/package artifact의 분리는 확인되지 않는다 (`docker/compose.yml:2-10`). |

판정 분포는 **일치 1, 불일치 8, 미구현 1, 설계에 없음 1**이다.

## 4. 경계 검증 결과

`rg -n -i "composer|acop_composer" acop_basement`로 확인한 결과, `acop_basement`에 `acop_composer`를 직접 import하는 문장은 없었다. 다만 Composer 관련 결합은 남아 있다.

- `acop_basement/presentation/api/app.py:19`는 `create_app()` 시그니처에 Composer router 인자를 둔다.
- `acop_basement/presentation/api/app.py:63-68`은 Composer router를 조건부로 app에 등록한다.
- `acop_basement/core/settings.py:50-52`는 Composer JWT/issuer secret을 basement 설정 모델에 둔다.
- `acop_basement/core/project_config.py:22-38`은 HTTP Composer 후보를 위한 implementation registry를 Core loader 옆에 둔다.

따라서 “Composer 파일을 basement에 넣지 않았다”는 좁은 의미의 파일 배치는 지켜졌지만, “basement가 Composer를 알지 않아야 한다”는 아키텍처 경계는 지켜지지 않았다. 현재 경계는 `acop_basement`가 선택적 router를 주입받는 구조이며, v3가 요구하는 Composer 비소속 경계보다 결합도가 높다.

경계 테스트도 파일 목록을 직접 확인하지 않는다. 현재 테스트는 도메인 단어와 `app.modules` import만 대상으로 한다 (`tests/architecture/test_basement_is_domain_free.py:63-72`, `105-113`).

## 5. 토글 계약 범위 검증 결과

v3가 요구하는 최소 흐름은 등록 ID 확인 → revision 비교 → 해당 flag의 원자적 쓰기 → audit 기록이다(설계: `...md:75-93`). 실제 흐름은 전체 config 입력 → registry 및 `ProjectConfig` 검증 → 전체 YAML staging → 전체 파일 교체 → 변경 필드 audit다.

핵심 위반은 두 가지다.

1. endpoint 이름과 입력 shape가 다르다. `/composer/toggle`와 `target_id`가 없고, `/composer/apply`가 전체 `config`를 받는다 (`acop_composer/api.py:48-57`, `86-100`).
2. Core 계약 검증이 실행된다. candidate를 임시 YAML로 저장한 뒤 `load_project_config()`를 호출하고 (`acop_composer/service.py:88-94`), apply에서도 같은 loader를 호출한다 (`acop_composer/service.py:123-134`). 이 loader는 active team의 module/class 존재와 `manifest`·`execute` 속성까지 확인한다 (`acop_basement/core/project_config.py:133-177`).

따라서 UI가 `ProjectConfig`를 직접 import하지 않는다는 주석은 있지만 (`acop_composer/api.py:9-10`), 서버 측 Composer가 Core 계약 모델과 loader에 강하게 의존한다. v3의 “UI가 Core 계약 모델을 복제하거나 깊이 검증하지 않는다”는 전제는 이 구현으로 보장되지 않는다.

## 6. 설계 문서 갱신 권고

1. 설계 문서에는 현재 구현이 v3가 아니라 v2형 전체 선언 apply를 유지하고 있다는 사실을 명시하고, `POST /composer/toggle`로 전환할 때 제거할 endpoint와 payload를 표로 고정하는 것이 좋다. 근거는 실제 endpoint와 payload가 `acop_composer/api.py:48-57`, `64-100`에 남아 있다는 점이다.
2. `acop_basement` 경계의 정의를 “Composer 파일 부재”에서 “Composer import·설정·router wiring·패키지 metadata 부재”로 구체화하는 것이 좋다. 현재 `app.py`와 `settings.py`가 Composer를 알고 있기 때문이다 (`acop_basement/presentation/api/app.py:11-17`, `63-68`; `acop_basement/core/settings.py:50-52`).
3. §8에 패키징 acceptance criteria를 추가하는 것이 좋다. `final-project-sample` 하나의 배포물에 두 패키지를 함께 넣는 현재 설정(`pyproject.toml:5-8`, `17-22`)으로는 선택 설치와 고객 빌드 제외를 증명할 수 없다. basement와 composer를 별도 build artifact로 만들고, 고객 wheel의 `RECORD` 또는 파일 목록에서 Composer 경로가 0개인지 검사하도록 권고한다.
4. 현재 v2 handoff와 v3 설계가 혼재한다. `docs/handoff/_prompts/S-COMPOSER-DEPLOYMENT-TOPOLOGY-CONSULT.md:7-20`은 `/composer/validate`, `/composer/apply`를 전제로 하고, `:43-49`는 canonical loader 재사용을 전제로 한다. v3를 채택할 경우 이 handoff의 endpoint·loader·배포 경계를 v3 계약으로 갱신하거나 “폐기된 v2 참고 문서”로 표시해야 한다.
5. 구현이 설계보다 앞선 부분은 유지하기보다 먼저 v3 범위로 되돌리는 편이 맞다. 전체 config validation, `implementation_ref` allowlist, Composer JWT 설정을 basement와 공유하는 방식은 v3의 좁은 책임과 직접 충돌하기 때문이다. 단, revision lock과 audit의 안전성은 새 toggle endpoint로 이식할 가치가 있다.

## 7. 이 대조의 한계

- 대조는 정적 파일·문서·read-only git 조회에 기반했다. 테스트 실행과 wheel build는 하지 않았다.
- `final_project_ui`는 sample 저장소의 구현 대상이 아니므로 실제 HTTP client가 Core 모델을 import하지 않는지는 검증하지 못했다.
- `final_project_sample`의 커밋되지 않은 `.pytest-tmp/`가 생성된 경위와 내용은 변경하지 않고 상태만 기록했다.
- 설계 문서와 일부 기존 handoff 문서는 이 환경의 터미널 출력에서 문자 인코딩이 깨져 보이는 구간이 있었으므로, 판정은 사용자 지정 절의 줄번호와 코드의 ASCII 식별자·실제 함수/라우터 정의를 함께 근거로 삼았다.
