# 최종 주제 후보 비교 v4 — 2026-09-08

## 0. 이 문서의 목적과 검토 요청

이 문서는 SKN32 최종 프로젝트 6팀이 주제 후보 다섯 개를 같은 형식으로 비교하고, 팀이 결정한 주제 **여행 전체를 관리하는 AI API 서비스**의 시장·고객·수익·데이터·구현 범위를 정리한 것이다. 멘토님께 세 가지 검토를 요청드린다.

1. 1순위 고객을 **처음 한국에 자유여행을 오는 외국인 개인·친구 그룹(인바운드)** 으로 잡은 판단이 타당한지.
2. 7주 안에 만들 MVP 범위(§3-7)가 "지속 관리·선제 조정"이라는 강점을 보여주기에 충분한지, 혹은 과한지.
3. 팀 모듈을 액티비티 → 요식 → 이동·동선 순으로 만드는 순서가 맞는지.

v3에서 바뀐 점: 2009년 조사 통계를 삭제했고, 손익 수치가 한국인 고객 전제임을 명시했으며, 액티비티 예시를 인바운드 고객에 맞게 바꿨다. 비선정 후보의 상세는 부록으로 옮겼다.

수치에는 출처 등급을 붙였다. 등급이 없는 문장은 정성 판단이다.

### 선정 이유

§2-2 비교표에서 여행 후보는 시장 크기가 가장 크지만 경쟁 공백과 구현 난이도에서는 최고점이 아니다. 팀이 그럼에도 여행을 고른 이유는 다섯 가지다. 앞의 세 가지는 문서의 근거에서 읽히는 것이고, 뒤의 두 가지는 팀 논의에서 중시한 것이다.

- 인바운드 시장이 수치로 뒷받침되는 유일한 후보다. 2025년 방한 외래객이 1~11월 누적 1,741만 명으로 2019년 수준을 회복했고, 개별여행 비중이 82.9%까지 올랐다 [외부, 원문 확인].
- A-COP가 만들어 온 코어(판정의 정직성, 근거 대조, 사람 인계, 감사 기록)를 "예약 검증과 지속 관리"라는 형태로 그대로 옮길 수 있다.
- 인바운드 대상이면 국내 공공 데이터(TourAPI)가 곧 대상 데이터라 데이터 접근이 다른 여행 시장보다 쉽다.
- **시연 효과.** 여행은 발표 자리에서 사건과 결과가 한눈에 보이는 도메인이다. "예약한 액티비티가 취소됐는데 고객이 알기 전에 대안이 도착했다"는 장면은 규정 문서나 판정 로그를 읽지 않아도 무엇이 자동화됐는지 전달된다. 다른 네 후보는 무상·유상 판정이나 과실 비율처럼 결과가 문서 안에 머물러 시연에서 차이가 드러나기 어렵다.
- **확장성.** 팀 모듈을 액티비티·요식·이동처럼 여행을 구성하는 객체 단위로 나누므로, 도메인을 넓힐 때 코어를 바꾸지 않고 Team을 추가하면 된다. 도시를 늘리는 것은 데이터 추가이고, 언어를 늘리는 것은 응답 소재 추가이며, 한국인 해외여행으로 넓히는 것은 데이터 공급자 교체다. 후보 B(액티비티 CS)는 이 구조의 첫 Team으로 흡수되고, 액티비티 판정 규칙은 후보 B 조사를 그대로 쓴다.

## 3. 팀 결정 후보 — 여행 전체를 관리하는 AI API 서비스

정본은 팀 내부 사업 검토서(v2, 2026-09-08, 이하 "v2 검토서")다. 이 절은 그 내용을 이 문서의 형식에 맞춰 요약하고, 국내 자료에 없던 해외 동향과 데이터 접근성만 2026-09-08 웹검색 [외부]로 보탰다. v2 검토서의 수치는 [제안]으로 표시한다. v2 검토서 자체가 "고객 계약·실제 매출·성능 시험·공급자 계약을 수행한 것으로 간주하지 않는다"고 적고 있다.

### 3-1. 한 줄 정의와 제안 내용

**가고 싶은 곳과 예약 내용을 주면 전체 여행을 구성하고, 여행 중 상황이 달라져도 중요한 예약과 원하는 경험을 지키면서 남은 일정을 조정해 주는 여행 CS(고객 지원·여행 수행 관리) 플랫폼.** 개인 에이전트(OpenClaw·Hermes 등, 고객이 쓰는 AI 비서)는 고객과 대화하는 접점이고, 관리 루프와 여행의 최신 상태는 우리 플랫폼이 맡는다. 제품 목표는 상대적으로 신뢰성 높은 정보 제공과 할루시네이션(근거 없는 생성) 축소다. 근거가 없거나 충돌하면 '미확인'으로 돌려주고, 재조회 시각을 현장 관찰 시각처럼 표시하지 않는다.

팀 결정(2026-09-08)으로 두 가지를 정했다. 첫째, **1순위 고객은 처음 한국에 자유여행을 오는 외국인 개인·친구 그룹(인바운드)** 이다. v2 검토서의 조사 범위(한국 소비자의 국내·해외 자유여행)와 다르므로 v2의 고객 근거는 보조 근거로 내려간다. 둘째, **우리 강점은 계획 생성이 아니라 지속 관리다.** 처음 계획은 생성형 AI가 만들고, 우리는 그 계획을 검증하고 여행이 끝날 때까지 지켜본다. 일반적인 CS는 고객이 문제를 알린 뒤 일정을 고쳐 주지만, 우리는 문제를 먼저 감지해 조정하고 고객에게 알린다. 고객은 조정이 마음에 들지 않을 때만 우리에게 말한다.

|---|---|---|---|

### 3-6. 인프라 없이 구현 가능한가, 난이도

**자체 장비·GPU 없이 관리형 클라우드로 MVP 구성 가능. 다만 인프라와 운영이 없다는 뜻은 아니다.** v2 검토서가 공식 문서로 대조한 참조 구성은 외부 LLM API(Gemini) + 관리형 실행(Cloud Run) + DB·인증(Supabase Postgres, 행 단위 권한) + 예약 작업·재시도(Scheduler·Tasks) + 로그·알림(Cloud Logging·Monitoring) + 경로 계산(OR-Tools·Routes API)이다. 여행 검증·권한·루프·복구 로직은 직접 개발한다. 음성 인식·합성(STT/TTS)은 고객 에이전트 몫으로 두고 만들지 않는다.

이 프로젝트의 배포 기준(Docker·AWS는 2단계)과 맞추면, 10주 안에서는 로컬 실행 + 외부 API 호출로 검증하고 클라우드 배포는 다음 단계다 [추정].

| 영역 | 난이도 [제안] | 이유 |
|---|---|---|
| 기본 계획·저장·API | 중간 | 일정 버전, 동의·처리 상태, 다음 확인 시점 저장 |
| 검증·현장 대응 | 높음 | 장소·날짜 식별, 이동·시간대, 조건 충돌, 오래된 정보·동시 변경 처리 |

### 3-7. MVP 최소 범위 (제안)

2026-09-08 기준 최종발표 10-26까지 7주다. v2 검토서의 1단계("한 도시·여행 전체 MVP")를 팀 결정(인바운드 1순위, 지속 관리·선제 조정이 강점, 액티비티 우선)에 맞춰 최소로 잘랐다. 결정은 팀 몫이며 아래는 모두 [추정]이다.

**MVP가 보여줘야 하는 것 세 가지.**

1. **처음 계획은 우리가 만들지 않는다.** 고객의 개인 에이전트(또는 시연용 외부 LLM 1회 호출)가 만든 일정을 받는다. 우리 제품의 가치는 계획을 짜는 데가 아니라 계획이 현실에서 성립하는지 확인하는 데 있다.
2. **검증은 우리가 API로 한다.** 코드로 검사할 수 있는 것(예약 시간 충돌·이동 여유·예산·동행 조건)과 확인 수준을 높일 수 있는 것(오늘 운영·운행 여부와 확인 시각)을 나눠 돌려주고, 불가능한 일정은 이유와 완화할 조건을 붙여 거절한다.
3. **여행이 끝날 때까지 지속 관리하고, 문제는 우리가 먼저 알아채 조정한다.** 일반적인 CS는 고객이 문제를 알린 뒤 일정을 고쳐 주지만, 우리는 반대다. 감시 소스에서 변화가 잡히면 우리가 재계획→재검증→통지하고, 고객은 조정이 마음에 들지 않을 때만 말한다. 거부하면 이전 버전으로 되돌린다. 이것이 A-COP CS의 강점(판정 정직성·근거·인계·감사 기록)이 여행으로 옮겨진 모습이다.

| 항목 | 최소 범위 | 이번엔 뺀다 (2단계 이후) |
|---|---|---|
| 고객·지역 | 처음 한국에 자유여행을 오는 외국인 개인·친구 그룹. 국내 1도시(서울 권장: TourAPI·외국어 안내 자료 밀도가 가장 높음) | 가족·소그룹 2순위, 다도시, 한국인 해외여행 |
| 언어 | 영어 1개 + 운영자용 한국어. **결정 사항으로 명시한다.** 방한 상위 국가는 중국·일본·대만 등으로 알려져 있어(수치 [미확보]) 영어만 지원하면 가장 큰 고객군이 MVP에서 빠진다. 시연 범위를 좁히기 위한 선택이며 시장 판단이 아니다 | 중국어·일본어 등 |
| 계획 생성 | 만들지 않는다. 고객 에이전트가 만든 일정(장소·시간·예약 원문)을 API로 받는다 | 자체 추천·일정 생성기 |
| 검증 API | 엔드포인트 하나. ① 코드 검증(시간 충돌·이동 여유·예산·동행 조건) ② 운영·운행 확인 수준과 확인 시각 ③ 불가능 사유·완화 조건. 결과는 ActionProposal(팀 모듈이 코어에 돌려주는 표준 제안 형식)로 | 최적화(OR-Tools), 보행·피로 모델 |
| 상태 저장 | 여행 1건 = 최신 일정 버전 + 잠긴 예약 + 필수 조건 + 다음 확인 시점 + 통지·거부 이력 | 동시 수정 충돌 처리, 백업·복구 |
| 지속 관리 루프 | 여행별 다음 확인 시점을 저장하고, 로컬 주기 작업이 감시 소스를 재조회한다. 최소 주기: 출발 전날, 매일 아침, 각 예약 2시간 전 | 업체 웹훅 수신, 클라우드 스케줄러, 여행 종료 후 자동 정지 |
| 선제 조정 | 변화(액티비티 취소·기상 조건·식당 휴무)가 잡히면 우리가 재계획안을 만들고 잠긴 예약·필수 조건을 지켰는지 재검증한 뒤 고객 에이전트에 "이렇게 조정했습니다. 원치 않으시면 알려 주세요"로 통지. 거부하면 되돌린다 | 결제·취소 실행, 여러 대안 동시 제시 |
| 사람 인계 | 검증 실패·근거 충돌·거부 후 대안 없음 → 사람 검토 상태로 넘기고 기록 | 사람 지원 운영 시간·상담 상품 |
| 외부 연결 | 텍스트 입출력 API + 여행별 접근 토큰. 개인 에이전트 1종(OpenClaw 또는 Hermes)과 연결 시연 | 여러 에이전트 동시 지원, 음성 |
| 데이터 | TourAPI 장소 + 합성 여행 20~30건 + 사건 시나리오 10개(액티비티 취소·기상·휴무 중심) + 번역 검토 자료. 팀의 데이터셋 폴더 규칙(원본·가공·스크립트·보고서 분리)을 따른다 | 실제 고객 여행 기록, 현장 제보 |
| 인프라 | 로컬 실행 + 외부 LLM API. Places·Routes·기상청은 소량 호출 또는 Mock | Cloud Run·Supabase·Scheduler 배포 |
| 통과 기준 | 선제 조정 시나리오에서 통지 전 재검증 통과율 100%, 필수 조건 위반 0건, 확인 시각 표시율 100%, 감지→통지 시간, 거부→되돌림 성공률 | 실제 유료 결제율, 재구매·환불, 팀당 기여이익 실측 |

#### 팀 모듈 MVP — 무엇부터 만드나

A-COP는 코어(진입·분류, 실행)와 등록형 팀 모듈(Team)로 나뉜다. 코어와 팀 사이의 계약(Controller·TeamExecutorPort·ActionProposal)은 그대로 두고, 팀 모듈만 여행용으로 새로 등록한다. Team은 지역 상품이 아니라 **여행을 구성하는 객체 종류별**로 나눈다. 각 Team은 자기 객체의 ① 검증 규칙 ② 감시 소스 ③ 재계획 후보 생성을 갖고, 전체 일정 정합성(시간 충돌·예산·이동 여유)은 코어 검증 층이 본다. 만드는 순서는 **액티비티 → 요식 → 이동·동선**이다.

| 순서 | Team | 검증 규칙 | 감시 소스 | 재계획 | 왜 이 순서인가 |
|---|---|---|---|---|---|
| **1 · MVP 필수** | **액티비티 (Activity)** | 예약 시간·운영일·인원·날씨 조건·취소·환급 규정 | 운영 공지, 기상청 초단기예보, 예약 확인 | 같은 시간대 대체 액티비티, 날짜 이동, 환급 안내 | 취소·변경 규정이 문서로 있어 판정 규칙을 바로 쓸 수 있다. 후보 B에서 조사한 골프장 우천 취소 규정(취소 기한·위약금율·기상 판단 시점)을 판정 규칙의 틀로 쓴다. 예약금이 걸려 실패 비용이 크다 |
| 2 | 요식 (Dining) | 영업시간·휴무·예약 여부·동행 조건(아이·할랄·채식) | 영업 공지, Places 영업시간(오늘 포함 7일) | 인접 대안, 식사 시간 이동 | 변화가 잦고 대체가 쉽다. v2의 사건 예시("점심 식당이 닫혔다")가 여기다 |
| 3 | 이동·동선 (Mobility) | 구간 이동 시간·환승·막차·여유 시간 | 운행 정보, Routes | 경로·순서 재배열 | 앞의 두 Team이 바뀌면 항상 이동이 영향을 받는다. 늦게 붙여도 코어 검증이 시간 충돌은 잡는다 |
| 등록만 | 숙박·항공 (Lodging/Flight) | 계약만 등록하고 구현하지 않는다 | — | — | 잠긴 예약으로만 취급한다. 결제·취소 실행은 v2 4단계 |

★**예약 인계(Booking Handoff)는 이 표에서 뺐다.** 초안은 「등록만/껍데기」로 두었으나 **2026-09-08 팀 결정으로 MVP 필수로 올라왔다**(계획서 v10 §5). 감지해서 우리 일정을 고쳐도 업체 예약을 못 바꾸면 고객이 결국 직접 처리하므로, 무엇을 어떻게 바꿔야 하는지 정리해 넘기는 것까지가 제품이라는 판단이다. 이름도 `Booking Execution` 이 아니라 `Booking Handoff` 다 — 기본 동작이 **인계**이기 때문이다.


인바운드 고객에 맞는 액티비티 예시는 템플스테이, 한강 수상 액티비티, 공연·뮤지컬, 테마파크, 겨울 스키·눈썰매, 쿠킹 클래스다. 골프는 규정 조사의 출처일 뿐 MVP 시나리오의 주 예시가 아니다.

각 Team 안에서는 판정(코드)과 대안 생성(LLM)을 분리하고, 생성한 대안은 판정을 다시 통과해야 통지된다. 기존 Response Generation & Review 팀에서 생성과 검수를 다른 주체가 하는 원칙과 같다.

**코어에서 바뀌는 것.** 코어 1(진입·분류) 라벨을 "일정 제출 / 사건 신고 / 확인 요청 / 조정 거부 / 그 외"로 교체하고, Context Broker(요청에 필요한 맥락을 모아 싣는 부품)가 주문 정보 대신 여행 상태를 싣는다. 코어 2(실행) Action은 장소·운영 조회, 이동 시간 조회, 기상 조회 세 개(Mock 허용). Composer(응답 문구 소재 저장소)는 영어 통지 문구 소재. 평가 도구의 정답 시나리오를 합성 여행과 사건으로 교체하고, 기권·과잉 기권 분석은 그대로 쓴다.

**안 쓰게 되는 것.** 쇼핑몰용 팀 모듈(Procurement + Order & Payment, Fulfillment & Logistics, Catalog & Verification). 등록은 남겨도 되지만 MVP 경로에서 호출되지 않는다.

**재사용과 신규.** 재사용되는 것은 루프·상태·인계·감사 기록·평가 도구다. Team 세 개의 판정 규칙, 감시 소스 연결, 여행 데이터는 전부 신규다. 7주 배분은 액티비티 Team 2주, 코어 라벨·Action·상태 저장 1주, 요식 Team 1주, 이동 Team과 선제 조정 루프 1주, 평가·발표 2주 정도로 보이나 근거 없는 [추정]이다.

### 3-8. 남은 검증

v2 검토서의 출시 전 검수 7항목은 검수 계획이며 통과한 것이 아니다: ① 잘못된 예약 날짜·장소를 확정하지 않는지 ② 동일 변경의 중복·역순 수신에서 최신 일정이 보존되는지 ③ 외부 조회 실패 때 마지막 확인 시각과 대안을 표시하는지 ④ DB·파일 복원 후 여행이 이어지는지 ⑤ 다른 고객의 여행 접근과 권한 취소가 차단되는지 ⑥ 여행 종료 후 작업이 멈추는지 ⑦ 실제 청구·지원 시간이 손익 가정에 맞는지. MVP 최소 범위에서는 ①②③⑤를 합성 시나리오로 시험하고 ④⑥⑦은 2단계로 둔다 [추정].

## 부록 A. 비선정 후보 상세

### A-1. 임대인·임차인 CS 시스템

**Pain.** 임대인은 월세 입금 확인, 수리 문의, 비용 협의, 업체·방문 일정 조율을 여러 채널에서 반복 처리한다. 임차인은 수리비를 누가 부담하는지 알기 어렵고, 임대인에게 바로 알리기 부담스러운 질문이나 수리 거절·선지출 이후의 대응을 혼자 해결한다.

**Gap.** 비공개 비용 상담 → 선택한 내용만 공유 → 수리·비용 협의 → 승인된 업무 실행 → 당사자 결제 → 선지출 상환·후속 절차를 하나의 사건으로 연결하는 것이 차별점 후보다. 개별 기능은 경쟁 서비스와 겹쳤고, 전체 흐름을 같이 제공하는 제품은 공개 자료에서 확인하지 못했다. 시장 유일성이 입증된 것은 아니다.

**Buyer.** 여러 호실을 관리하는 임대인과 소형 임대관리 사업자. 임대인이 도입하고 임차인을 무료로 초대한다. 임대인이 유료 고객이어도 임차인의 비공개 상담과 개인 자료는 열람할 수 없다.

**Build.** 월세·납부 확인과 수리 사건 관리를 기반으로 비공개 상담·선택 공유·비용 동의·방문 조율·결제·상환·후속 문서 준비를 연결한다. AI는 법령·계약·사실에 근거한 의견을 제시하고 승인된 업무를 처리하며, 작업 승인과 본인 부담 동의·결제는 당사자가 결정한다. 초기 개발은 수리 유형 1종, 검수한 근거 자료, 수동 입금 확인, 테스트 결제로 검증한다.

**Business.** 건물 또는 관리 호실 수 기준 월 구독료. 가격과 지불의사는 가설이며, 운영시간·반복 연락·처리 누락이 얼마나 줄어드는지 확인해야 한다.

**추가 검토.**

- 시장성: 임대인 수는 많지만 한 명이 낼 수 있는 월 구독료가 낮다. 여러 호실을 가진 임대인과 관리업체로 좁히면 고객 수가 줄고 단가가 오른다. 어느 쪽이든 분모 수치는 [미확보].
- 경쟁 대비 이점: 월세 입금 알림·관리 앱은 이미 여럿 있다. 이점은 임차인 비공개 상담과 선지출 상환을 한 사건으로 묶는 흐름 하나다. 이것이 없어도 진입할 이유는 약하다 [추정].
- 확실히 사줄 고객: 다호실 임대인. 그러나 이들이 임차인의 비공개 AI 상담 구조를 받아들일지가 불확실하다 [추정].
- 데이터: 주택임대차보호법·민법 수선의무·분쟁조정 사례는 공개. 실제 수리 사건 기록은 없어 합성해야 한다. 결제는 테스트 결제로 대체 가능.
- 인프라 없는 구현: 가능. 다만 결제·상환·양자 권한 분리(임대인 화면과 임차인 화면의 열람 범위가 다름)는 설계 부담이 크다. 난이도 중~상 [추정].

### A-2. 액티비티 CS 시스템 — 골프 우천 환급 검증

제안 상세가 없어 2026-09-08 웹검색으로 채웠다.

**Pain.** 여름철 국지성 폭우가 잦아지며 골프장 우천 취소 규정 갈등이 매년 되풀이된다. 문체부·소비자원 조사에서 조사 대상의 31.3%인 111곳이 표준약관보다 소비자에게 불리한 약관을 쓰고 있었다. 한국소비자원에 접수되는 골프장 민원 중 가장 많은 유형은 예약 취소와 위약금이며, 기상 악화에도 취소를 거부하거나 과도한 위약금을 부과하는 사례가 꾸준하다. 갈등의 뿌리는 규정 자체보다 "취소 여부를 언제, 어떻게 판단하느냐"다. 대부분의 골프장은 예보만으로는 취소를 받지 않고 당일 현지 강우를 확인한 뒤 결정하며, 골프장마다 규정이 다르다 [외부, 원문 확인 — 한경 매거진 2026-07-11].

**Gap.** 예약 플랫폼은 예약·결제를 하고, 우천 판정은 골프장이 사람 손으로 한다. 규정 문서와 기상 실측치를 대조해 환급 여부를 자동 판정하는 도구는 이번 검색에서 확인하지 못했다 [미확보].

**Buyer.** 골프장 운영사 또는 예약 플랫폼. 그러나 골프장 입장에서는 취소를 받지 않는 쪽이 매출에 유리하므로 판정 자동화를 구매할 유인이 약할 수 있다. 소비자 보호 압력(불량 약관 적발)이 커질 때 도입 유인이 생긴다 [추정].

**Build.** 골프장 약관(취소 기한·위약금율) + 기상청 초단기예보·자동기상관측 실측치 + 소비자분쟁해결기준을 대조해 "환급/부분환급/위약금" 판정과 근거를 낸다. 도메인을 스키·수상레저·캠핑 등 "중도 이용 정산 규칙이 문서로 있는" 액티비티로 확장한다.

**Business.** 미제출 [미확보].

**추가 검토.**

- 시장성: 골프장 수와 취소 분쟁 건수는 분모 [미확보]. 골프 외 액티비티로 넓히면 커지지만 각 도메인의 규정을 새로 넣어야 한다.
- 경쟁 대비 이점: 판정 도구 부재는 확인했으나, 이 공백이 기술 부족 때문이 아니라 골프장이 원하지 않기 때문일 가능성이 있다 [추정].
- 데이터: 다섯 후보 중 가장 좋다. 기상청 API, 골프장 약관, 소비자원 분쟁 사례가 모두 공개다.
- 인프라 없는 구현: 가능. 규정 → 판정 규칙, 기상 데이터 조인. 난이도 하~중 [추정]. A-COP의 판정·근거 대조 구조를 그대로 쓸 수 있다. 이 조사는 여행 후보의 액티비티 Team 판정 규칙(§3-7)으로 이어진다.

### A-3. 세탁 서비스 손상·분실 클레임 자동 판정 CS

**주제.** 비대면 세탁 서비스(세탁특공대·런드리고·크린토피아)에서 고객이 손상·분실을 신고하면, 클레임 텍스트와 세탁 이력·원단 정보·배송 로그를 근거로 책임 소재(세탁 과실/원단 자체 결함/무과실)를 판정하고, 과실 확정 건에 한해 감가상각을 반영한 보상액까지 자동 신청하는 멀티에이전트 CS 시스템.

**Pain.** 한국소비자원 세탁업 분쟁해결기준 3,875건 기준 업체 과실 25.2%, 원단 결함 31.9%, 무과실 42.9% [제안]. 무과실이 42.9%인데도 소비자가 업체 과실을 직접 증명해야 한다. 세탁 공정관리 시스템과 배송 미션 할당 시스템이 분리돼 있고 배송 인력 상당수가 프리랜서라, 세탁이 끝났는지 모른 채 출고되는 사고가 난다(운동화 끈만 세탁 완료 처리된 채 출고된 사례).

**Gap.** 3사 모두 AI를 쓰지만 용도는 케어라벨 인식·공정 자동화·단순 챗봇뿐이다. "손상 책임 판정+보상액 계산" AI는 없고 분쟁은 100% 사람이 처리한다. 인접 스타트업 '매일새옷'(TIPS 선정)은 접수 단계 사진 분석만 하며, 향후 확장 리스크로 본다.

**Buyer.** B2B: 세탁특공대(1순위, 공개 전략이 모듈과 겹치고 적자 축소 중) > 크린토피아(2순위, 흑자·1위, 프랜차이즈 표준 CS 도구) > 런드리고(3순위, 적자 -230억 [제안]). 동네 세탁소는 매일새옷이 선점해 제외. B2C 체감 수요층: 1인 가구·맞벌이, 고가 의류 이용자, 반복 이용자.

**Build.** 손상판정·보상·물류CS 3모듈 멀티에이전트. 판정 에이전트와 검수 에이전트를 분리(같은 주체면 자기 오류를 못 잡는다). 물류CS는 세탁완료시각 vs 배송출고시각을 경계로 로그 기반 구간 판별(고객 진술은 판정 근거 아님).

**Business.** 오케스트레이션 자체는 세일즈포스·Kore.ai가 상품화한 범용 영역이라 가치가 없다. 팔리는 것은 3개 모듈의 "세탁업 특유의 판정 로직"이다. 통계·공식 기준 근거 판정, 프레임워크 비종속, 비전모델 없이 2달 내 구현이 셀링포인트.

**추가 검토.**

- 시장성: B2B 고객이 국내 3곳이다. 한 곳이라도 도입하지 않으면 시장의 1/3이 사라진다. 프랜차이즈 본사 채널(크린토피아 가맹점)로 넓히면 커진다 [추정].
- 경쟁 대비 이점: 다섯 후보 중 "공식 판정 기준표가 이미 있다"는 점이 가장 명확하다. 판정 근거를 통계로 댈 수 있다.
- 확실히 사줄 고객: 세탁특공대의 공개 전략이 겹친다는 근거는 있으나 인터뷰는 없다 [미확보].
- 데이터: 판정 기준은 공개. 클레임 텍스트·세탁 이력·배송 로그는 회사 내부 데이터라 합성해야 한다. 사진 판정을 빼고 텍스트+메타데이터로 한정한 것은 현실적이다.
- 인프라 없는 구현: 가능. 난이도 중 [추정]. 감가상각 계산은 표 기반이라 규칙으로 처리된다.

### A-4. 소형가전 CS 시스템 (세 제안 통합)

세 제안은 대상 품목이 다르지만 구조가 같다. "증상·정책 문서를 대조해 무상/유상(결함/과실)을 판정하고, 애매하면 사람에게 넘긴다."

| 축 | 게이밍기어 AS 판정 | 소형가전 애매한 진단 | IoT 브랜드 CS 운영 도구 |
|---|---|---|---|
| Pain | 총판 9개사가 AS를 전화 1회선+게시판으로 처리. "더블클릭이 불량인지" 판정 혼란 5년째. 로지텍 AS 창구 이관 한 번에 2년 악평 [제안] | 중소 가전사의 CS 인력 인건비 부담. 이상 없음(NFF) 출장 45% [제안] | 매출 1,150억 브랜드가 성수기에 전화를 끊음. 후보 브랜드 앱 평점 전부 2점대. 로봇청소기 피해구제 2년 연속 두 배. CS에 AI 쓰는 기업 4% [제안] |
| Gap | 서비스맨Pro는 접수·정산만. 채널톡은 상충 신호 재조정을 실측 2회 모두 실패 | 채널톡·서비스맨Pro·애니위즈 모두 규칙 판정까지만. 무상/유상 애매 판단은 사람 몫(오아도 미해결) | 기존 도구는 회사 채팅창으로 고객을 불러들이는 모델. 카카오 상담톡은 이력 삭제. 고객 에이전트가 회사 CS 에이전트를 호출하는 자리는 국내외에 없음 |
| Buyer | 총판·수입원 CS 부서(에스라이즈 1,200억~제이웍스 70억) [제안]. 지불의사 미검증 | 자체 브랜드 중소 제조사, 중고가전 셀러, 병행수입업체 | 직원 30~130명 국내 IoT 가전 브랜드 100~300곳 [제안]. 대표·COO 결정 |
| Build | 정책·트러블슈팅은 공개 자료. 반품·물류는 기존 코드(반품 판정 엔진 33테스트, 배송 데이터 10,527행) 재사용. AS는 LLM+규칙 순차 파이프라인, 6~7주 | 무상/유상 기준은 공정위 소비자분쟁해결기준(공개). 1순위 품목 전자동 커피머신으로 10주 MVP. 사전 예방(소모품 주기·보증 만료·계절 가이드, MCP 알림 도구) | 회사 CS 에이전트(A2A) 하나 + MCP 도구 서버 하나를 코어로. 가상 브랜드+합성 데이터로 5단계 시연 |
| Business | 서비스맨Pro가 도입비+유지비로 이미 팔림. 매출 규모는 추정 | Technical(AS 진단)에 집중 후 로봇청소기·무선청소기로 확장 | 채널톡 월 12만 원·외주 월 80~300만 원 위에 월 30~80만 원. 국내 상한 연 5~30억은 작아 대행사·해외 Tuya 브랜드로 확장 [제안] |

**추가 검토.**

- 시장성: 국내 상한 연 5~30억 [제안]은 작다. 세 제안 모두 "국내는 작으니 확장한다"를 전제로 한다.
- 경쟁 대비 이점: 다섯 후보 중 경쟁사 실패를 직접 실측(채널톡 2회)한 유일한 후보다. 판정 레이어 공백은 구조적이다.
- 확실히 사줄 고객: 총판 CS 부서, 제조사 대표. 후보 명단은 있고 지불의사 인터뷰는 없다 [미확보].
- 데이터: 정책·트러블슈팅 문서 공개, 소비자분쟁해결기준 공개, 가상 브랜드 문서 2개로 채널톡 실측까지 완료. 가장 준비된 상태다.
- 인프라 없는 구현: 가능. 난이도 하~중 [추정]. A-COP 기존 코드(반품 판정, 배송 조회)와 가장 가깝다.
