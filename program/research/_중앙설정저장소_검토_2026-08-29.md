# 중앙 설정 저장소 결정 검토 (2026-08-29)

대상 문서: `program/plan/A-COP_Composer_중앙설정저장소_결정.md`
관련 구현: `final_project_sample/acop_basement/core/config_store.py`,
`006_project_configs.sql`, `tests/integration/test_config_store.py`

산출물 문서에 반영하면서 읽었다. 반영은 끝냈고 아래는 검토 의견이다.

## 1. 반영한 곳

| 문서 | 반영 내용 |
|---|---|
| DB, Vector DB 설계서 | 엔터티에 `project_configs` 추가. 6절에 중앙 저장소 절 신설 |
| 시스템 구성도 | 2.1 배포 환경에 중앙 설정 서비스와 현재 진척 서술 |
| 화면설계서 | SCR-03 목적에 부르는 곳이 바뀐다는 사실과 대상 선택 자리 미설계 명시 |

세 문서 모두 **아직 연결되지 않았다**고 적었다. 결정과 저장 계층은 있지만
그것을 부르는 곳이 없기 때문이다.

## 2. 결정 자체는 타당하다

두 요구가 충돌한다는 진단이 정확하다. 설정이 대상마다의 파일이면 그 파일을
고치는 코드가 대상 안에 있어야 하고, 고객 릴리즈에 쓰기 API 를 넣을 수 없다.
"관리용 빌드로 하면 된다"가 수천 대상에서 성립하지 않는다는 것도 맞다.

문서가 이 충돌을 표로 적어 남긴 것도 좋다. 안 적어두면 다음 사람이 또 같은
답을 내고 같은 자리로 돌아온다고 쓴 대로다.

`§9 이 결정이 틀릴 수 있는 조건`을 스스로 적어둔 것도 드물게 정직하다.

## 3. ★가장 큰 문제 — 자체 호스팅 주장과 충돌한다

**결정 문서에 자체 호스팅이라는 말이 한 번도 안 나온다.** 그런데 제출표의
차별화 근거 두 개가 정확히 그것이다.

| 제출표 | 내용 |
|---|---|
| 배포 | 자체 호스팅을 목표로 설계했으며, 고객사 배포와 **데이터 외부 반출 방지**는 별도 검증 항목으로 둔다 |
| 이유 4 | Intercom Fin 은 **자체 호스팅 불가** 근거가 있다 [G2] |
| 이유 5 | 자체 호스팅 수요는 규제가 만든다. 유럽과 중동 기업의 자국 내 워크로드 75% 이상 전망 [F1] |

중앙 저장소로 가면 **대상이 기동할 때마다 우리 서버로 나가야 한다.**
그러면 이런 일이 생긴다.

- 망분리 환경에서는 아예 못 돈다. G2 로 Fin 을 비판한 논리가 우리에게 그대로 돌아온다
- 규제 산업 고객이 "설정이 어디 있냐"고 물으면 "우리 DB"라고 답해야 한다
- 우리 중앙 서비스가 죽으면 고객사 3000곳이 같이 영향을 받는다. 자체 호스팅의 장점이 사라진다

결정 문서 §8 에 "대상이 중앙에 못 붙을 때의 동작"이 미정으로 적혀 있는데,
이건 장애 대응 항목이 아니라 **제품 포지셔닝 문제**다. 그 자리에 있으면
안 된다고 본다.

### 제안

결정을 뒤집자는 것이 아니다. **두 배포 형태를 함께 두는 것**을 검토할 만하다.

| 형태 | 설정 위치 | 대상 |
|---|---|---|
| 관리형 | 중앙 저장소 | 대상이 많고 우리가 운영을 맡는 경우 |
| 자체 호스팅 | 고객사 안의 설정 서비스 | 망분리와 규제 산업 |

`ConfigStore` 가 이미 Protocol 이고 `FileConfigStore` 와 `PostgresConfigStore`
두 구현이 있으니 구조는 이미 그걸 할 수 있게 돼 있다. 결정 문서에 이 갈래를
적어두면 나중에 "자체 호스팅은 어떻게 되나"라는 질문에 답할 수 있다.

## 4. 구현 상태와 문서 서술이 어긋난다

결정 문서 §5 는 이미 만든 것 일곱 가지를 "그대로"라고 적었다. 확인해 보니
대체로 맞다. UI 의 카탈로그 기반 인스턴스 생성 화면도 실제로 있고
`acop_composer_ui` 패키지도 설치돼 있으며 UI 테스트 127건이 통과한다.

다만 **저장 계층은 아직 아무 데서도 안 쓰인다.**

| 항목 | 상태 |
|---|---|
| `config_store.py` | 있음. `ConfigStore` 규약과 두 구현 |
| `006_project_configs.sql` | 있음 |
| 통합 테스트 | 10건, 통과 |
| **호출부** | **없음.** `acop_composer` 도 `app` 도 이 모듈을 쓰지 않는다 |
| 대상이 중앙에서 읽는 경로 | 없음 |

`acop_composer/service.py` 는 여전히 로컬 YAML 을 `os.replace()` 로 바꾼다.
즉 지금 돌아가는 것은 전부 파일 기반이고, 중앙 저장소는 옆에 놓인 상태다.

이건 잘못이 아니다. 골격을 먼저 두고 붙이는 순서는 정상이다.
다만 **문서가 이 사실을 적어야 한다.** 지금 결정 문서는 "바꿔야 할 것" 표로만
적혀 있어서, 읽는 사람이 이미 바뀐 것으로 오해할 수 있다.

## 5. 테스트는 잘 짜였다

`test_config_store.py` 10건이 검사하는 것을 보면 방향이 맞다.

- 낡은 `base_revision` 으로 쓰면 거부되고 아무것도 안 바뀐다
- 같은 `base_revision` 으로 둘이 쓰면 하나만 이긴다
- 없는 배포를 조회하면 빈 값이 아니라 실패한다
- 파일 저장소가 임시 파일을 남기지 않는다

특히 두 번째와 세 번째가 좋다. 조용한 폴백을 만들지 않는다는 이 저장소의
원칙이 테스트로 강제돼 있다.

## 6. 더 물어야 할 것

결정 문서 §8 의 미정 항목 외에 이것들이 더 있다고 본다.

- **감사 로그의 위치.** 표에는 append-only DB 테이블로 옮긴다고 적혔는데
  그 테이블이 중앙에 있는지 대상에 있는지 안 적혀 있다. 승인 기록은 업무
  데이터라 대상에 있어야 할 것 같고, 설정 변경 기록은 중앙이 맞아 보인다.
  둘을 나눌지 합칠지 정해야 한다.
- **`deployment_id` 를 누가 발급하나.** 문서는 배포 인스턴스를 가리키는 키라고만
  적었다. 대상이 자기를 증명하는 방법(§8 에 미정으로 있음)과 함께 정해야 한다.
- **설정 유출.** 중앙 저장소 한 곳이 뚫리면 고객사 3000곳의 구성이 한 번에
  드러난다. 파일 기반에서는 없던 위험이다. 결정 문서에 이 항목이 없다.
- **이번 기간에 할지.** §8 마지막 줄에 있는데, 이건 다른 미정 항목과 성격이
  다르다. 안 할 거면 산출물 문서는 "결정만 있고 착수 안 함"으로 적어야 하고,
  할 거면 스프린트에 에픽이 하나 더 필요하다. 지금 스프린트 설계에는 없다.

## 7. 정리

| 항목 | 판단 |
|---|---|
| 진단 (두 요구의 충돌) | 정확하다 |
| 방향 (중앙 저장소) | 대상이 수천이면 타당하다 |
| 자체 호스팅과의 관계 | **빠져 있다. 가장 먼저 채워야 한다** |
| 구현 상태 | 저장 계층만 있고 연결 안 됨. 문서에 명시 필요 |
| 테스트 | 잘 짜였다 |
| 일정 반영 | 스프린트에 에픽이 없다 |
