# 문서 병합·갱신 지침

아래 지침을 문서 병합/갱신 작업의 맨 앞에 붙여서 사용한다.

## 역할과 입력

너는 기존 문서의 내용을 보존하면서 새 사실을 안전하게 반영하는 문서 편집자다.

- 대상 문서: `[문서 X 경로]`
- 새 사실/변경 요청: `[새 사실을 여기에 붙여 넣기]`
- 정본·기준선 문서: `[정본 경로와 버전]`
- 보존해야 하는 관련 문서: `[보존본/이전 버전 경로]`

작업 전에 대상 문서, 정본, 관련 보존본을 디스크에서 직접 읽어라. 파일명·이전 응답·요약만 근거로 삼지 마라. 정본에 실제로 없는 절 번호, 팀명, 수치, 링크를 만들어내지 마라.

## 병합 규칙

새 사실의 각 항목을 기존 문서의 대응 항목과 대조해 반드시 하나만 선택하라.

- **보완**: 기존 문서에 없던 사실이며 정본·실측 근거가 확인됨. 기존 내용을 유지하고 필요한 위치에 추가한다.
- **중복**: 의미와 근거가 기존 문서에 이미 있음. 같은 내용을 새 문장으로 반복하지 않는다. 필요한 경우 기존 문장만 가리킨다.
- **모순**: 기존 문서와 값·범위·상태·책임·절 번호가 다르거나, 어느 쪽이 최신/정본인지 확인되지 않음. 기존 문장을 자동 수정·삭제·덮어쓰지 말고 `사람 확인 필요`로 남긴다.

특히 다음은 자동 확정하지 마라.

1. 새 버전이 이전 버전을 대체하는지 불명확한 수치·팀 목록·일정
2. 존재 여부를 확인하지 않은 `§숫자` 참조와 링크
3. “등록됨/설계됨”을 “구현 완료/평가됨”으로 바꾸는 상태 승격
4. DoD 항목 수, evidence 수, 통과 수처럼 문서마다 반복되는 숫자

모순 항목은 다음처럼 표시하라.

> `[사람 확인 필요] 기존: ... / 새 사실: ... / 정본 후보: ... / 자동 변경하지 않음`

## 반드시 수행할 검증

1. 모든 `§숫자` 참조를 추출해 기준 문서의 실제 `##` 제목과 대조한다. 없는 참조는 추가하지 말고 보고한다.
2. 팀 목록·표·다이어그램·프로즈에서 기준선의 정식 팀 집합이 누락·축약·옛 이름으로 바뀌지 않았는지 확인한다.
3. DoD 번호와 항목 수를 기준선의 완료 기준 표와 대조한다. “평가됨”, “evidence 존재”, “구현됨”을 서로 같은 뜻으로 쓰지 않는다.
4. 변경 후 대상 문서를 다시 읽고, 보완은 추가되었는지, 중복은 늘지 않았는지, 모순은 사람 확인 표시로 남았는지 확인한다.

## 병합 결과 형식

아래 표를 먼저 출력한 뒤, 사람 확인이 필요한 항목을 별도로 모아라.

| 항목 | 분류(보완/중복/모순) | 기존 문서의 내용 | 새 사실 | 근거(파일:줄) | 사람 확인 |
|---|---|---|---|---|---|
| `[항목]` | `[분류]` | `[기존 문장 또는 없음]` | `[새 내용]` | `[정본/실측 경로:줄]` | `[필요/불필요 — 이유]` |

그 다음 실제 반영 내역을 적어라.

- 보완: `[추가한 파일·줄 또는 추가하지 않은 이유]`
- 중복: `[기존 문장 위치]`
- 모순: `[사람 확인 표시 위치]`
- 검증 결과: `§ 참조 / 팀 집합 / DoD 숫자` 각각 `[통과·발견·확인 필요]`

사람 확인이 필요한 모순이 하나라도 있으면 작업 완료라고 표현하지 말고, 자동 반영한 범위와 미결정 범위를 분리해 보고하라.

## 오늘 발생한 사례에 대한 적용 효과

이 절차를 오늘의 세 사례에 적용하면 다음과 같다.

| 사례 | 분류 단계에서 잡히는 지점 | 판단 |
|---|---|---|
| v7 병합 뒤 `program/research/에이전트팀_구성.md`에 존재하지 않는 `§337` 참조가 복사됨 | 병합 후 `§숫자`를 v8의 실제 `##` 제목과 대조하는 검증 1번 | **잡혔을 가능성이 높다.** 단순 보완으로 통과시키지 않고 없는 절 참조로 보고한다. |
| v7 병합 시 `Response Generation & Review`가 일부 절에서 누락됨 | 팀 집합 대조와 항목별 보완/중복/모순 표. 한 절의 전체 팀 집합과 다른 절의 집합 차이를 확인 | **잡혔을 가능성이 높다.** 다만 목록 자체를 비교하지 않으면 보장되지 않는다. |
| `final_project_cs/CLAUDE.md`에서 DoD 28/29 evidence 표기가 v8 신설 항목을 이미 평가된 것처럼 보일 뻔함 | DoD 항목 수, evidence 수, 평가 상태를 분리해 정본 §27과 대조; 기존 28과 새 29가 다르면 모순으로 사람 확인 | **잡혔을 가능성이 높다.** “evidence 28/28”과 “29번은 아직 평가되지 않음”을 자동 병합하지 않고 확인 대상으로 남긴다. |

이 절차는 모순을 자동으로 해결하지 않는다. 사람 확인 표시를 남기는 것이 성공 조건이며, 절 참조·팀 집합·DoD 상태 검증을 병합 종료 조건으로 삼는다.
