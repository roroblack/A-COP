# Composer — UI 배포 구조 점검 (2026-08-29)

점검 요청: "컴포저를 sample 에서 만들어 ui 프로젝트로 pip 제공하고 거기서
import 해서 쓰는 구조로 가기로 했고, 거기서 모듈·인스턴스 CRUD 가 가능하게
하기로 했다. 그 설계를 어떻게 해뒀고 지금 옳바른 상태인가."

점검 방식: 세 저장소(`final_project_sample`·`final_project_ui`·
`final_project_cs`)의 실제 파일을 읽고 대조했다. 추정이 아니라 실측이다.

---

## 0. 결론 먼저

**설계 방향은 맞다. 그러나 지금 상태는 그 설계대로 되어 있지 않다.**

결정된 3-패키지 구조 중 **UI 가 가져다 쓸 조각이 아직 존재하지 않는다.**
그 결과 UI 는 자기 클라이언트를 손으로 따로 만들어 쓰고 있고(중복 구현),
새로 만든 인스턴스 CRUD 계약(`/catalog`·`/changes`)을 **모른다** — 즉
"UI 에서 모듈·인스턴스 CRUD" 라는 요구는 **종단으로는 아직 성립하지 않는다.**

| 항목 | 결정된 것 | 지금 상태 |
|---|---|---|
| `acop_basement`(Core) | cs 가 항상 설치 | ✅ 존재 |
| `acop_composer`(대상 쪽 glue) | 관리용 빌드에만 설치 | ✅ 존재 |
| **UI 가 import 할 클라이언트** | sample 이 만들고 UI 가 pip 설치 | ❌ **없음** |
| UI 의 인스턴스 CRUD | 가능해야 함 | ❌ **불가**(계약을 모름) |
| pip 로 분리 배포 | 패키지별 독립 설치 | ❌ **단일 배포판** |

---

## 1. 먼저 — UI 작업을 이 세션에서 하는 게 맞나

**아니다.** 두 가지 이유다.

첫째, `final_project_ui` 는 **별도 저장소**이고 자기 작업 규칙을 갖는다.
`final_project_ui/CLAUDE.md` §0.1 은 "이 저장소의 작업 범위는 이 폴더
안이다. 다른 폴더를 읽어야 하면 먼저 허가를 받는다" 라고 못박는다. 반대로
이 세션(`final_project_sample`)에서 UI 파일을 고치는 것도 같은 경계를 반대
방향으로 넘는 일이다.

둘째, 역할이 다르다. **sample 이 할 일은 "UI 가 쓸 것을 만들어 내주는
것"이고, "UI 화면을 만드는 것"이 아니다.** 지금 sample 쪽에 빠져 있는 것은
화면이 아니라 **패키지**다(§2). 그러니 순서상으로도 sample 에서 패키지를
먼저 만들고, 화면은 ui 세션에서 그걸 설치해 쓰는 것이 맞다.

이 점검 자체를 위해 ui·cs 를 읽은 것은 사용자가 명시적으로 요청했기
때문이다.

## 2. 무엇이 빠져 있나 — UI 가 import 할 패키지

### 2.1 결정된 설계

`program/plan/A-COP_Composer_소유권_정정.md` 의 구조도는 **세 조각**을 그린다.

```
final_project_sample  (개발 저장소)
   ├── acop_basement    → cs가 pip install. Core/Team/Registry/Controller
   ├── acop_composer    → 대상 쪽 glue. 관리용 빌드에만 설치
   └── acop_composer_ui → UI가 pip install. 판단·요청 로직
                            ▲ import
                   final_project_ui  (독립 서비스)
```

`final_project_ui/CLAUDE.md` §0.3 도 이에 맞춰 정정돼 있다 — "대상은
`final_project_cs` 다. `final_project_sample` 은 대상이 아니다. sample 이
만든 패키지를 pip install 해서 쓰는 것은 이 원칙이 금지하는 대상이 아니다.
Composer 판단·요청 로직은 sample 에서 만들고 이 프로그램이 가져다 쓴다."

### 2.2 실제 상태

`final_project_sample/acop_composer/` 의 내용은 다음이 전부다.

| 파일 | 성격 |
|---|---|
| `api.py` | FastAPI **서버** 라우터(`/catalog`·`/changes`·`/toggle`·v2 3종) |
| `service.py` | 파일 검증·원자적 쓰기(**서버**) |
| `auth.py` | JWT 발급·검증(**서버**) |
| `catalog.py` | 카탈로그 선언(**서버**) |

**HTTP 클라이언트가 하나도 없다.** 즉 위 구조도의 세 번째 조각
(`acop_composer_ui`)은 **아직 만들어지지 않았다.**

★혼동 주의: `acop_composer` 는 이름 때문에 "UI 가 쓰는 것" 처럼 보이지만
**대상(cs) 프로세스 안에서 도는 서버 glue** 다. v3 설계 §8.1 이 그렇게
정의했고, 실제 구현도 그렇다. **이것을 UI 가 import 하면 안 된다** — 그
순간 `ProjectConfig` 검증 모델이 UI 프로세스로 들어와
`final_project_ui/CLAUDE.md` §0.2 가 금지하는 "검증 모델 복제" 가 된다.
(2026-08-24 Codex 교차검증도 같은 지적을 했다.)

## 3. 그 결과 — UI 는 클라이언트를 손으로 따로 만들어 쓰고 있다

`final_project_ui/console/composer.py` 는 **167줄짜리 자체 구현**이다.

- `_issue_access_token()` — JWT 발급 요청
- `_request()` / `_call()` — HTTP 전송·오류 정규화
- `read_current()` · `validate_candidate()` · `apply_candidate()` — v2 3종
- `toggle_target()` — v3 토글

이것이 바로 소유권 정정 문서가 없애려던 중복이다. 같은 계약을 두 곳에서
구현하면 한쪽만 고쳐지는 날이 온다 — 그 문서의 표현대로 "계약이 바뀌면 두
곳을 고쳐야 하고, 두 구현이 어긋나면 어느 쪽이 맞는지 알 수 없다".

★다만 이 중복은 **지금 당장 깨져 있는 상태는 아니다.** UI 클라이언트는
raw dict 만 주고받고 `ProjectConfig` 를 import 하지 않는다 — §0.2 위반은
아니다. 문제는 "위반" 이 아니라 **유지보수 중복**이다.

---

## 4. ★인스턴스 CRUD 는 종단으로 성립하지 않는다

이번 요구의 핵심인데, 여기가 끊겨 있다.

**서버 쪽(sample)은 준비됐다.** 2026-08-28~29 에 구현·검증했다.

| 엔드포인트 | 하는 일 |
|---|---|
| `GET /composer/catalog` | 고를 수 있는 구현 종류 + 입력 스키마 |
| `POST /composer/changes` | create/update/delete/enable/disable, dry_run, idempotency |
| `POST /composer/toggle` | v3 토글(위와 저장 경로 공유) |

**UI 쪽은 이 계약을 모른다.** `console/*.py` 전체에서 `catalog` 나
`/changes` 문자열이 **한 번도 나오지 않는다**(grep 결과 0건). UI 가 아는
것은 v2 3종과 toggle 뿐이다.

게다가 `toggle_target()` 의 docstring 은 이렇게 적혀 있다 — "이 설계는 아직
대상에서 확정·구현 중이라 필드명·경로가 최종 계약과 다를 수 있다 —
**화면에는 아직 연결하지 않는다**". 즉 토글조차 화면에 안 붙어 있다.

**따라서 지금 UI 화면에서 할 수 있는 것은 v2 전체 선언 편집뿐이고, "모듈·
인스턴스를 이름과 설정만 입력해 만든다" 는 요구는 아직 불가능하다.**

## 5. pip 제공이 지금 구조로는 안 된다

`final_project_sample/pyproject.toml` 은 배포판이 **하나**다.

```toml
name = "final-project-sample"
[tool.setuptools.packages.find]
include = ["app*", "acop_basement*", "acop_composer*"]
```

즉 `acop_composer` 만 따로 설치할 수 없다. UI 가 이걸 pip install 하면
`app/`(도메인 모듈)과 `acop_basement`(Core 전체)까지 통째로 딸려 온다 —
UI 에 있으면 안 되는 것들이다.

★"디렉터리를 나눴다" 와 "독립 배포 패키지다" 는 다르다. 지금은 전자까지만
와 있다. 2026-08-24 Codex 교차검증이 정확히 이 점을 지적했다.

참고로 `final_project_ui/requirements.txt` 에는 `acop_*` 의존성이 **없다**
(fastapi·uvicorn·psycopg·PyYAML·python-multipart 뿐). UI 는 지금 sample 에
아무 의존도 갖고 있지 않다.

## 6. 지금 상태가 "틀린" 것인가

**설계가 틀린 게 아니라 미완이다.** 구분해서 볼 필요가 있다.

| 판정 | 항목 |
|---|---|
| ✅ 맞게 돼 있음 | `acop_basement`/`acop_composer` 디렉터리 분리, 서버 쪽 CRUD 계약, grant ceiling, `pending_restart` 정직 반환, v2 무손상 유지 |
| ⚠️ 미완(설계대로 아직 안 만듦) | UI 용 클라이언트 패키지, 독립 배포 메타데이터 |
| ⚠️ 미연결 | UI 화면 ↔ 새 CRUD 계약 |
| ❗위험 | `acop_composer`(서버)를 UI 가 import 하는 것 — 하면 안 됨 |

즉 **잘못 만든 것을 되돌릴 필요는 없다.** 빠진 조각을 채우면 된다.

## 7. 권고 — 다음 순서

### 7-1. sample 에서 할 일 (여기서 한다)

1. **UI 클라이언트 패키지를 만든다.** 이름은 `acop_composer_ui`(가칭,
   소유권 정정 문서가 예시로 든 이름). 경계를 **엄격히** 제한한다.

   | 넣는다 | 넣지 않는다 |
   |---|---|
   | JWT 발급 요청, HTTP 전송, 오류 정규화, 계약 버전 협상, 엔드포인트 래퍼(`catalog`/`changes`/`toggle`/v2) | `ProjectConfig`·`TeamManifest` 등 Core 모델, 선언 유효성 판정, capability 충돌 검사, 권한 판정 |

   ★판정 로직을 넣는 순간 §0.2 위반이자 스키마 결합의 재현이다. **UI 는
   서버가 준 JSON Schema 로 폼을 그리고, 유효성은 서버가 판정한다.**

2. **배포 메타데이터를 분리한다.** 단일 `final-project-sample` 배포판으로는
   pip 제공이 성립하지 않는다. 최소한 UI 클라이언트만이라도 독립 배포
   가능하게 만들어야 한다(별도 `pyproject` 또는 다중 배포판 구성). 이때
   `acop_composer_ui` 는 **fastapi 의존이 없어야 한다** — 서버 패키지가
   아니기 때문이다.

3. **wheel 경계 테스트**를 붙인다. `acop_composer_ui` 빌드 산출물에
   `acop_basement`·`app` 파일이 0개인지 실제로 검사한다. v3 설계 §8.2 가
   basement↔composer 에 대해 권고한 것과 같은 방식이다(import 검사가 아니라
   빌드 산출물 파일 목록 검사).

### 7-2. ui 세션에서 할 일 (거기서 한다)

4. `console/composer.py` 의 자체 구현을 새 패키지로 교체한다.
5. 카탈로그를 읽어 인스턴스 목록·생성 마법사 화면을 만든다(`/catalog` 의
   `parameters_schema` 로 폼 생성).
6. `activation_state: pending_restart` 를 화면에 **정직하게** 표시한다 —
   저장됐다고 런타임이 그 설정으로 도는 것이 아니다.

### 7-3. 하지 말 것

- UI 가 `acop_composer`(서버 패키지)를 import 하는 것.
- UI 에 선언 유효성 판정을 넣는 것.
- 배포 분리 없이 "pip 제공" 이라고 문서에 적는 것 — 지금은 사실이 아니다.

## 8. 확인하지 못한 것

정직하게 적는다.

- **실제 HTTP 종단 시험을 하지 않았다.** sample 서버를 띄우고 UI 가 실제로
  붙는 것까지는 확인하지 않았다. 이 점검은 두 저장소의 코드 대조다.
- **cs 와의 계약 정합성**은 이번 범위 밖이다. cs 는 sample 을 pip 로 쓰지
  않고 v2 를 독자 재구현한 포크 상태다(2026-08-24 실측). cs 에도 `/toggle`
  이 있으나 sample 것과 필드가 완전히 같은지는 대조하지 않았다.
- **UI 의 introspection 버전 불일치**(UI 기본 `v1` vs cs `1.0`)가 2026-08-24
  대조 보고서에 기록돼 있는데, 그것이 지금도 유효한지는 재확인하지 않았다.
- `acop_composer_ui` 의 **패키지 이름은 확정된 것이 아니다.** 소유권 정정
  문서도 "예시" 라고 적었다.
