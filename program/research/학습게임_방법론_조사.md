# 대규모 코드베이스 학습 게임 방법론 조사

조사 기준일은 2026년 8월 30일이다.

## 결론

적합한 형태는 강의에 점수와 배지를 붙인 과정이 아니다. 학습자가 작은 실제 시스템을 먼저 끝까지 실행하고, 요청의 경로를 추적하고, 일부를 재구현하고, 의도적으로 심은 결함을 진단한 뒤, 실제 저장소의 작은 변경을 완료하는 **검증 가능한 임무의 연쇄**다. 핵심 루프는 `관찰 → 예측 → 실행/추적 → 설명 → 수정 → 회고`다.

게임성은 숨은 인과관계를 발견하고 예측을 실행으로 확인하는 데서 나와야 한다. 지도는 디렉터리 트리가 아니라 실행·데이터·상태·도구·권한·평가 경로를 겹쳐 보여 주는 지식 지도여야 한다. 2025~2026년에는 저장소에서 위키·코드 투어·이해 문항을 자동 생성하는 기술이 등장했지만, 임의의 대규모 저장소를 검증된 게임형 코스로 완전 자동 변환한 성숙 사례는 확인하지 못했다. 현실적인 방식은 정적·동적 분석으로 구조를 잡고, LLM이 후보 퀘스트를 만들며, 테스트·원본 링크·전문가 검토가 정답과 난이도를 보증하는 반자동 파이프라인이다.

## 1. LLM·AI 교육 선구자들의 교수법

### 1) Karpathy식 직접 구축

- **핵심 주장:** 작지만 실제로 작동하는 모델을 직접 만들고 내부를 한 층씩 확장해야 한다.
- **근거/출처:** [Zero to Hero](https://karpathy.ai/zero-to-hero.html)는 micrograd에서 GPT까지 처음부터 구축한다. [nanoGPT](https://github.com/karpathy/nanoGPT)는 작은 학습 루프로 핵심을 노출하고, 2025년 후속 [nanochat](https://github.com/karpathy/nanochat)은 토큰화·사전학습·미세조정·평가·추론을 한 최소 시스템에 담는다. [Eureka Labs](https://eurekalabs.ai/)는 교사+AI 조교 구조와 LLM101n을 제안한다. LLM101n 완성 코스의 효과 평가는 확인하지 못했다.
- **우리 코드베이스 학습 게임에 어떻게 적용되는가:** 첫 임무에서 `요청 → 오케스트레이터 → 도구 → 관찰 → 응답 → 평가`가 도는 미니 에이전트를 실행시킨다. 이후 컨텍스트, 라우팅, 메모리, 권한, 추적, 평가기를 실제 구현으로 하나씩 교체한다.

### 2) fast.ai의 top-down whole game

- **핵심 주장:** 먼저 유용한 전체 작업을 경험하고 같은 전체를 반복 방문하며 고수준 API에서 저수준 구현으로 내려가야 한다.
- **근거/출처:** [fast.ai teaching philosophy](https://www.fast.ai/posts/2016-10-08-teaching-philosophy.html)는 전체 그림을 먼저 주고 라이브러리를 제거하며 밑바닥 구현으로 내려간다. [Deep Learning from the Foundations](https://www.fast.ai/posts/2019-06-28-course-p2v3.html)은 code-first와 from-scratch를 명시한다.
- **우리 코드베이스 학습 게임에 어떻게 적용되는가:** `폴더 A → B → C` 대신 대표 사용자 시나리오를 먼저 성공시킨다. 다음 회차마다 호출 그래프, 상태·복구, 비용·보안을 같은 시나리오에 겹친다.

### 3) Perkins의 Making Learning Whole 7원칙

- **핵심 주장:** 초보자용 전체 게임, 가치 있는 목표, 어려운 부분, 전이, 숨은 구조, 협업, 자기조절을 함께 설계해야 한다.
- **근거/출처:** Harvard의 [Making Learning Whole](https://pz.harvard.edu/resources/making-learning-whole-how-seven-principles-of-teaching-can-transform-education)과 [Education at Bat](https://www.gse.harvard.edu/ideas/usable-knowledge/09/01/education-bat-seven-principles-educators)은 ① 전체 게임 ② 가치 ③ 어려운 부분 ④ 원정 경기 ⑤ 숨은 게임 ⑥ 팀 ⑦ 학습의 게임을 제시한다.
- **우리 코드베이스 학습 게임에 어떻게 적용되는가:** 전체 제품 흐름을 초보자 리그로 삼고 비결정성·동시성·도구 실패를 보스전으로 분리한다. 다른 서비스에서 같은 추적법을 쓰는 전이 임무와, 권한·비용·재시도 같은 숨은 규칙을 넣는다.

### 4) 실패·평가 중심 AI 엔지니어링 교육

- **핵심 주장:** 실제 실패를 관찰하고 평가 단위를 만들며 개선하는 과정으로 LLM 시스템을 배워야 한다.
- **근거/출처:** Chip Huyen의 [LLM applications for production](https://huyenchip.com/2023/04/11/llm-engineering.html)은 구성요소와 제어 흐름 평가를 제안한다. Hamel Husain의 [AI Evals](https://hamel.dev/notes/llm/evals/index.html)는 오류 분석에서 평가기로 이어진다. Eugene Yan의 [LLM systems patterns](https://eugeneyan.com/writing/llm-patterns/)는 평가·RAG·가드레일·피드백을 묶는다. Simon Willison의 [How coding agents work](https://simonwillison.net/guides/agentic-engineering-patterns/how-coding-agents-work/)는 LLM+프롬프트+도구 루프를 직접 만들 것을 권한다.
- **우리 코드베이스 학습 게임에 어떻게 적용되는가:** 트레이스 분류, 실패 가설, 평가 케이스, 수정, 회귀 방지 순으로 진행한다. 점수는 재현 가능성, 근거, 평가 오류, 회귀 방지에 준다.

### 5) 공식 에이전트 자료의 단순 패턴부터 확장하기

- **핵심 주장:** 증강 LLM에서 시작해 체이닝·라우팅·병렬화·오케스트레이션을 필요할 때만 추가한다.
- **근거/출처:** Anthropic [Building effective agents](https://www.anthropic.com/engineering/building-effective-agents), OpenAI [Agents SDK quickstart](https://openai.github.io/openai-agents-python/quickstart/)와 [orchestration](https://openai.github.io/openai-agents-python/multi_agent/), Google ADK [수동 튜토리얼](https://google.github.io/agents-cli/guide/hands-on-tutorial/)은 단순 구성에서 테스트·평가·트레이스로 확장한다.
- **우리 코드베이스 학습 게임에 어떻게 적용되는가:** 단일 호출 이해 전에는 멀티에이전트 구역을 열지 않는다. 비용·지연·정확도로 새 복잡성을 정당화해야 해금한다. 트레이스 뷰는 틱 단위 리플레이다.

## 2. 코드베이스 온보딩과 코드 이해 교수법

### 6) 인지적 도제와 스캐폴딩 페이딩

- **핵심 주장:** 전문가 사고를 보여 주고 발판을 제공한 뒤 숙련에 맞춰 도움을 제거해야 한다.
- **근거/출처:** Collins, Brown, Newman의 [Cognitive Apprenticeship](https://www.ideals.illinois.edu/items/18043)과 [Making Thinking Visible](https://www.aft.org/ae/winter1991/collins_brown_holum)은 modeling, coaching, scaffolding, articulation, reflection, exploration을 제시한다.
- **우리 코드베이스 학습 게임에 어떻게 적용되는가:** 첫 추적은 전문가 고스트가 검색어와 가설 수정 이유를 보여 준다. 다음에는 시작 파일·부분 그래프만 주고 점차 제거한다. 마지막에는 플레이어가 탐색 계획과 근거를 제출한다.

### 7) 가설 주도 프로그램 이해

- **핵심 주장:** 숙련자는 질문과 가설을 만들며 도메인 모델과 실제 제어 흐름 사이를 오간다.
- **근거/출처:** Letovsky의 [Cognitive processes](https://doi.org/10.1016/0164-1212(87)90032-X)는 질문과 추측을 관찰했다. von Mayrhauser와 Vans의 [Program comprehension](https://doi.org/10.1109/2.402076)과 [large-scale 연구](https://doi.org/10.1109/32.508315)는 여러 추상화 수준이 동시에 작동함을 보고한다.
- **우리 코드베이스 학습 게임에 어떻게 적용되는가:** 원인 가설 카드를 먼저 쓰고 검색·로그·실행으로 지지하거나 폐기한다. 읽은 파일 수보다 반증 가능한 상황 모델을 평가한다.

### 8) 능동적 코드 읽기와 코드 투어

- **핵심 주장:** 코드 읽기는 질문, 경로 선택, 요약, 실행 확인이 결합된 과업이어야 한다.
- **근거/출처:** 2025년 [data-enhanced active reading](https://doi.org/10.1186/s41039-025-00299-2)은 코드 읽기 행동 가시화와 능동 읽기를 결합했다. [Linear walkthroughs](https://simonwillison.net/guides/agentic-engineering-patterns/linear-walkthroughs/)는 실제 명령 출력과 소스를 인용한다.
- **우리 코드베이스 학습 게임에 어떻게 적용되는가:** “파일을 읽어라” 대신 “입력이 모델 인자로 변하는 다섯 지점을 찾아라”라고 묻는다. 각 단계에 파일·심볼·실행 증거·요약을 요구한다.

### 9) notional machine과 실행 추적

- **핵심 주장:** 문법보다 시스템의 단계별 상태 변화를 명시해야 한다.
- **근거/출처:** du Boulay의 [Some Difficulties of Learning to Program](https://doi.org/10.2190/3LFX-9RRF-67T8-UVK9)은 notional machine 오해를 핵심 난점으로 다룬다. [학생 코드 추적 전략 연구](https://cseweb.ucsd.edu/~bsimon/pubs/papers/icer2005_strats.pdf)는 추적 방법을 조사한다.
- **우리 코드베이스 학습 게임에 어떻게 적용되는가:** 대화 상태, 컨텍스트, 큐, 도구, 권한, 재시도, 캐시, 비용을 상태 전이로 정의한다. 다음 호출과 상태를 예측한 뒤 실제 트레이스를 공개한다.

### 10) Parsons 문제와 점진적 구성

- **핵심 주장:** 빈 편집기에 쓰기 전 코드 조각을 선택·배열해 생성 부담을 낮출 수 있다.
- **근거/출처:** [Python Grids](https://doi.org/10.1007/s40593-018-0156-y)는 실행 애니메이션과 Parsons 문제를 결합했다. Exercism은 [테스트가 주어진 stub을 완성](https://exercism.org/docs/using/faqs)한다.
- **우리 코드베이스 학습 게임에 어떻게 적용되는가:** 실제 에이전트 루프를 재배열하고, 정답 조각만 주는 단계에서 distractor, 빈칸 완성, 독립 변경 순으로 페이드한다.

### 11) 결함 주입과 mutation testing

- **핵심 주장:** 작은 의미 변화의 실패를 찾고 이를 잡는 테스트를 쓰면 제어 흐름과 명세를 함께 익힌다.
- **근거/출처:** [Mutation Testing for Teaching](https://doi.org/10.58459/icce.2014.413), [Decoding Debugging Instruction](https://doi.org/10.1145/3690652), 2025년 [교육용 mutation 스캐폴딩 연구](https://www.iris.unina.it/handle/11588/1005441)가 근거다.
- **우리 코드베이스 학습 게임에 어떻게 적용되는가:** 권한 확인 순서, idempotency, 도구 결과 기록 같은 실제 오개념을 변이로 심는다. 실패 재현, 가설, 최소 테스트, 수정 순으로 해결한다.

### 12) 작은 진짜 일과 buddy

- **핵심 주장:** 첫 주부터 범위가 좁은 실제 변경을 동료와 수행하면 코드·리뷰·배포를 함께 익힌다.
- **근거/출처:** Dropbox [Engineer onboarding](https://dropbox.tech/culture/a-day-in-the-life-engineer-onboarding-at-dropbox)은 buddy 프로젝트와 codelab을 공개한다. Microsoft [온보딩 사례 연구](https://arxiv.org/abs/2103.05055)와 Google SRE [온콜 학습 경로](https://sre.google/sre-book/accelerating-sre-on-call/)도 실제 과업·역공학·재난 역할극을 지지한다.
- **우리 코드베이스 학습 게임에 어떻게 적용되는가:** 최종 보스는 실제 backlog의 저위험 변경이다. buddy는 범위와 안전 경계를 정하는 코치다. 대형 회사가 코드베이스 온보딩 자체를 장기 게임화해 효과를 계량한 확실한 1차 사례는 찾지 못했다.

## 3. 학습에 직접 연결되는 게임 설계

### 13) 재미를 패턴 학습으로 보기

- **핵심 주장:** 지속적인 재미는 외적 보상보다 시스템 패턴을 발견하고 새 변형에 적용하는 데서 나온다.
- **근거/출처:** Raph Koster의 [Theory of Fun 강연](https://www.raphkoster.com/games/presentations/theory-of-fun/)과 [공식 사이트](https://www.theoryoffun.com/)는 재미·인지·패턴 학습의 관계를 전개한다. 코드베이스 교육의 직접 실험은 아니다.
- **우리 코드베이스 학습 게임에 어떻게 적용되는가:** “모든 외부 동작은 정책 게이트를 지난다” 같은 재사용 패턴을 발견하게 하고 다음 퀘스트에서 같은 패턴의 변형이나 예외를 찾게 한다.

### 14) desirable difficulties와 인출·간격·교차 연습

- **핵심 주장:** 답을 인출하고 시간을 두고 반복하며 유사 문제를 섞는 것이 장기 보존과 전이에 유리할 수 있다.
- **근거/출처:** UCLA Bjork Lab의 [연구 개요](https://bjorklab.psych.ucla.edu/research/)는 spacing, testing, variation, interleaving과 과도한 난이도의 위험을 설명한다. [The Critical Importance of Retrieval](https://doi.org/10.1126/science.1152408)은 반복 인출 효과를 보였다.
- **우리 코드베이스 학습 게임에 어떻게 적용되는가:** 빈 지도에서 실행 경로를 다시 그리고 1·3·7일 뒤 다른 모듈에서 같은 원리를 찾게 한다. 실패율이 높으면 힌트와 작은 단계가 돌아온다.

### 15) mastery learning과 AI 튜터

- **핵심 주장:** 시간을 채우는 대신 핵심 능력을 수행으로 확인하고 교정 후 다음 단계로 보내야 한다.
- **근거/출처:** Bloom의 [2 Sigma Problem](https://doi.org/10.3102/0013189X013006004)은 튜터링과 mastery learning을 다룬다. 2시그마 수치를 모든 환경의 보장치로 해석해서는 안 된다.
- **우리 코드베이스 학습 게임에 어떻게 적용되는가:** 레벨 해금 조건을 XP가 아니라 정상·타임아웃·권한 거부 트레이스 설명과 관련 테스트 통과로 둔다. AI 튜터는 답보다 오개념 진단과 힌트 강도 조절을 맡는다.

### 16) roguelike·metroidvania형 지식 구조

- **핵심 주장:** 반복 탐험과 능력 기반 재방문은 점진적 정신 모델과 잘 맞지만 직접 교육 효과가 입증된 공식은 아니다.
- **근거/출처:** [Metroidvania design](https://www.gamedeveloper.com/design/making-sense-of-metroidvania-game-design)은 새 mechanics가 진행을 여는 gating을 설명한다. [Vim Adventures](https://vim-adventures.com/)는 새 키가 실제 명령 능력을 열고 숙달 전 진행을 막는다.
- **우리 코드베이스 학습 게임에 어떻게 적용되는가:** 호출 그래프, 트레이스 필터, 테스트 설계를 익히면 과거 구역의 숨은 경로가 열린다. 매번 다른 장애 조합을 주되 발견한 불변식과 검증 명령은 남긴다. 우월성을 입증한 직접 연구는 확인하지 못했다.

### 17) pointsification 피하기

- **핵심 주장:** 점수·배지·순위표만 붙이면 의미와 자율성을 약화할 수 있다.
- **근거/출처:** Sebastian Deterding의 [Humanistic Design 논의](https://doi.org/10.1177/1056492618790912)와 [Meaningful Play](https://talks.ui-patterns.com/videos/meaningful-play-getting-gamification-right)는 얕은 pointsification을 비판한다. [교육 게임화 부정 효과 매핑](https://doi.org/10.1016/j.infsof.2022.107142)은 PBL과 경쟁의 부작용을 보고한다.
- **우리 코드베이스 학습 게임에 어떻게 적용되는가:** 진행 표시는 “인증 흐름 독립 추적 가능” 같은 능력 증거로 삼는다. 속도보다 정확도·안전·설명·협력을 보상하고 전역 순위표는 기본값에서 뺀다.

## 4. 실제 개발자용 게임·학습 도구

### 18) Build Your Own X와 작은 퍼즐

- **핵심 주장:** 실제 시스템을 작은 호환 단계로 다시 만들고 외부 테스트로 확인하면 내부 동작을 목적과 함께 배운다.
- **근거/출처:** CodeCrafters [How Challenges Work](https://app.codecrafters.io/concepts/overview)와 [Redis 과정 정의](https://github.com/codecrafters-io/build-your-own-redis)는 단계형 실제 구현을 보여 준다. [Advent of Code](https://adventofcode.com/2025/about)는 작은 이야기형 퍼즐과 예제 검증을 사용하며 2025년 전역 순위표를 제거했다.
- **우리 코드베이스 학습 게임에 어떻게 적용되는가:** 도구 호출, 오류, 병렬 호출, 중단·재개를 계약 테스트로 하나씩 구현한다. 속도 경쟁보다 관찰 결과의 호환성을 본다.

### 19) Boot.dev와 Exercism

- **핵심 주장:** 짧은 과제, 자동 테스트, 선행 개념 해금, 개인화 복습, 답을 주지 않는 도움을 결합한다.
- **근거/출처:** Boot.dev [Training Grounds](https://www.boot.dev/training)는 AI 개인화, 간격 반복, 코드 작성·버그 수정·인터뷰를 제공한다. [Boots](https://www.boot.dev/lessons/e4fac74c-9d67-41ad-a85c-c579cb3ad76f)는 현재 코드와 해답을 보되 소크라테스식 유도를 표방한다. Exercism [Getting Started](https://exercism.org/docs/using/getting-started)는 테스트, 해금, 인간 멘토를 결합한다.
- **우리 코드베이스 학습 게임에 어떻게 적용되는가:** 같은 개념을 경로 찾기·버그 수정·구두 설명으로 반복한다. AI는 한 단계 힌트, 인간은 조직 맥락과 아키텍처 의도를 맡는다.

### 20) 실제 도구가 곧 게임 입력인 형태

- **핵심 주장:** 학습 대상의 실제 조작이 게임 입력이면 연습과 전이가 분리되지 않는다.
- **근거/출처:** [Oh My Git!](https://ohmygit.org/)은 실제 Git과 내부 구조 시각화, [Vim Adventures](https://vim-adventures.com/)는 실제 키, [Regex Crossword](https://regexcrossword.com/)는 정규식 제약, [TIS-100](https://zachtronics.com/tis-100/)은 어셈블리·매뉴얼·디버거를 게임 규칙으로 쓴다.
- **우리 코드베이스 학습 게임에 어떻게 적용되는가:** 실제 git, 테스트, 검색, 트레이스, 디버거를 조작하게 한다. 초급 카드 UI는 같은 실제 명령에 대응하며 숙련되면 터미널로 페이드한다.

### 21) 코드로 플레이하는 지속 세계

- **핵심 주장:** 코드를 작성하고 장기 행동을 관찰하면 설계·피드백·최적화 반복이 자연스럽다.
- **근거/출처:** [Screeps](https://docs.screeps.com/introduction.html)는 JavaScript가 지속 세계의 유닛을 매 tick 제어한다. [Robocode](https://robocode.dev/articles/intro)는 탱크의 두뇌를 코딩하고 자동 전투 결과를 관찰한다.
- **우리 코드베이스 학습 게임에 어떻게 적용되는가:** 에이전트 정책을 샌드박스에 배치하고 성공률·비용·지연·안전·복구의 다목적 결과를 관찰한다. 대전 전 기준 장애 환경의 회귀를 통과시킨다.

### 22) CTF·Game Day·장애 대응

- **핵심 주장:** 현실적 장애, 역할 분담, 실제 도구, 사후 회고는 운영 구조를 가르친다.
- **근거/출처:** AWS [chaos engineering in incident response](https://aws.amazon.com/blogs/security/how-to-use-chaos-engineering-in-incident-response/), Google SRE [Incident Response](https://sre.google/workbook/incident-response/), GitHub [Secure Code Game](https://securitylab.github.com/secure-code-game/)이 실제 장애·보안 훈련 사례다.
- **우리 코드베이스 학습 게임에 어떻게 적용되는가:** 모델 지연, 잘못된 tool output, prompt injection, 큐 적체를 주입한다. 속도뿐 아니라 상황 모델, 안전한 완화, 증거 보존, 사후 테스트를 평가한다.

### 23) CI에서 생성되는 품질 퀘스트

- **핵심 주장:** 실제 커밋과 CI 결과에서 작은 개선 임무를 만들면 게임이 업무와 분리되지 않는다.
- **근거/출처:** Jenkins [Gamekins](https://github.com/jenkinsci/gamekins-plugin)와 [논문](https://arxiv.org/abs/2202.06562)은 커밋 기반 테스트 challenge·quest를 생성한다. [교육 적용 연구](https://arxiv.org/abs/2401.17740)는 결과 개선을 보고하지만 인과 일반화에는 추가 검증이 필요하다.
- **우리 코드베이스 학습 게임에 어떻게 적용되는가:** CI가 미실행 분기 재현, mutant를 죽이는 테스트, 불안정 평가 설명을 제안한다. 현재 커밋과 검증 명령을 포함하고 의미 있는 assertion을 평가한다.

## 5. 2025~2026 AI 튜터와 repo-to-course

### 24) 코드 인지형 단계적 AI 힌트

- **핵심 주장:** 최신 교육용 AI는 과제·현재 코드·실패 테스트를 보고 다음 한 걸음을 제안하며 정답 제공을 제한하는 방향이다.
- **근거/출처:** JetBrains의 2025년 [AI Hints](https://blog.jetbrains.com/education/2025/06/02/ai-hints-plugin/)는 설명과 diff로 다음 단계·컴파일 오류·실패 테스트 힌트를 준다. 2025년 ACL [프로그래밍 교육 LLM 설문](https://aclanthology.org/2025.hcinlp-1.21/)은 자동화와 인간 감독의 균형을 강조한다.
- **우리 코드베이스 학습 게임에 어떻게 적용되는가:** `관찰 요청 → 부분 힌트 → 전략 힌트 → 제한 예시` 순으로 제공한다. 플레이어가 예측을 제출해야 다음 힌트가 열리며 AI diff의 효과도 먼저 예측한다.

### 25) 코드 이해 문항 자동 생성

- **핵심 주장:** LLM은 실제 코드에서 개인화 문항을 만들 수 있지만 타당도와 정답 근거를 검증해야 한다.
- **근거/출처:** 2025년 [AutoMCQ](https://arxiv.org/abs/2505.16430)는 GenAI 이해 문항을 CodeRunner에 통합한다. [Testing Code Comprehension using GenAI](https://doi.org/10.1145/3754508.3754532)는 개인화 질문을 다룬다. 저장소 전체 코스 생성까지 입증하지는 않는다.
- **우리 코드베이스 학습 게임에 어떻게 적용되는가:** 상태 변화·호출 순서·실패 조건·변경 영향 문항을 만들고 실행 테스트 또는 파일·심볼 근거를 붙인다. distractor는 실제 오개념과 mutant에서 만든다.

### 26) 살아 있는 저장소 위키와 다이어그램

- **핵심 주장:** 자동 문서와 repo-aware Q&A는 실용화됐지만 읽기 자료 생성과 학습 성취는 다르다.
- **근거/출처:** Cognition의 2025년 [DeepWiki](https://cognition.com/blog/deepwiki)는 GitHub 저장소 위키·검색을 제공한다. Google의 2025년 [Code Wiki](https://developers.googleblog.com/ko/introducing-code-wiki-accelerating-your-code-understanding/)는 변경마다 재생성되는 문서, 코드 링크, 채팅, 다이어그램을 제공한다. 2026년 [CodeWiki 평가](https://aclanthology.org/2026.findings-acl.288/)는 저장소 수준 문서 생성을 평가한다.
- **우리 코드베이스 학습 게임에 어떻게 적용되는가:** 위키를 정답책이 아니라 세계 모델로 쓴다. 문서 노드를 코드·테스트·트레이스와 묶고 직접 검증한 항목만 발견 처리하며 변경 시 퀘스트를 재검증한다.

### 27) 정적 그래프+LLM 코드 투어

- **핵심 주장:** 큰 저장소는 전부 한 프롬프트에 넣기보다 호출·의존 그래프로 핵심 경로를 고르고 LLM이 설명하게 해야 한다.
- **근거/출처:** [LLM-Generated Code Tours](https://xdevroey.be/publication/balfroid-2024/balfroid-2024.pdf)는 CodeQL stack trace를 LLM이 설명한다. 2025년 [RepoMaster](https://arxiv.org/abs/2505.21577)는 호출·의존·계층 그래프로 핵심 요소를 선택한다. 2025년 [Multi-agent Onboarding Assistant](https://doi.org/10.1145/3696630.3728611)는 저장소·문서와 사용자 기록을 활용한다.
- **우리 코드베이스 학습 게임에 어떻게 적용되는가:** entry point, interface, 대표 구현, 테스트, 외부 I/O를 먼저 뽑는다. LLM은 근거 묶음에서 투어와 퀘스트를 만들고 모든 단계에 원본 심볼을 남긴다.

### 28) repo-to-course 반자동 파이프라인

- **핵심 주장:** 2026년 현재 가능한 것은 자동 초안이며 신뢰할 코스는 분석·실행 검증·난이도 보정·전문가 승인이 필요하다.
- **근거/출처:** DeepWiki·Code Wiki는 문서, AutoMCQ는 문항, [Linear walkthroughs](https://simonwillison.net/guides/agentic-engineering-patterns/linear-walkthroughs/)는 증거 기반 투어에 집중한다. 2026년 [(Im)Paired Programming](https://arxiv.org/abs/2607.26375)은 코딩 에이전트가 생산성을 높이면서 이해를 해칠 수 있고 자동 수락 같은 저노력 상호작용이 낮은 이해와 연결됐다고 보고한다.
- **우리 코드베이스 학습 게임에 어떻게 적용되는가:** `스냅샷 → 빌드/테스트 → 정적·동적 그래프 → 개념·선행 관계 → 퀘스트 후보 → 실행 oracle → 전문가 검수 → 파일럿 → 변경 감지`로 고정한다. LLM은 이야기·힌트·distractor 초안, 테스트와 트레이스는 정답을 맡는다.

## 설계에 채택할 원칙 10개

1. **첫 30분 안에 축소된 전체 시스템을 실행시킨다.**
2. **모든 퀘스트를 테스트·트레이스·재현 명령·코드 링크 같은 실행 증거로 끝낸다.**
3. **관찰·예측·실행·설명·수정·회고를 핵심 루프로 고정한다.**
4. **디렉터리보다 호출·데이터·상태·도구·권한·평가 관계로 지도를 만든다.**
5. **전문가 사고를 보여 준 뒤 발판과 힌트를 점진적으로 제거한다.**
6. **실제 장애·코드 리뷰·오개념에서 mutant와 보스전을 만든다.**
7. **시간·XP가 아니라 다른 맥락으로 전이되는 수행으로 숙달을 판정한다.**
8. **같은 개념을 1·3·7일 뒤 다른 문제 형식으로 인출하게 한다.**
9. **게임성은 패턴 발견과 의미 있는 선택에서 만들고 PBL은 보조로만 쓴다.**
10. **LLM은 생성자·코치로 쓰고 정답은 분석·실행 oracle·전문가 검수로 승인한다.**
