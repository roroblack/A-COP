## 먼저 결론

이 문서에서 **내부**는 우리 팀 6명끼리, **알파**는 같은 부트캠프 기수 약 21명, **베타**는 그 바깥의 실제 고객을 뜻한다.

알파까지는 **실제 소액 거래를 열어도 된다**. 21명에게 1인 1개를 팔면 거래 약 21건이므로, 법령사실 문서의 직전연도 거래횟수 50회 미만 면제 구간에 들어간다. 베타로 가기 전에는 통신판매업 신고 여부, 사업자등록, 개인정보 국외이전 경로, 결제·환불·정산 방법을 각각 확인하고 갖춘다.

다만 알파 21건은 “쇼핑몰을 실제로 운영해 본 증거”로는 충분하지만, 파인튜닝용 대규모 데이터로는 부족하다. 이번 10주의 목표는 파인튜닝이 아니라 **진짜 Case를 모으고, 평가셋과 회귀 테스트를 실제 흐름으로 보강하는 것**이다.

## A. 쇼핑몰 치명적 7건

### A-1. 통신판매업 신고

**결론**: 알파까지는 50회 미만 면제 구간으로 운영하고, 베타 전에 신고 여부와 사업자등록을 따로 확인해 갖춘다.

**왜 문제였나**: 법령사실 문서 1번은 직전연도 통신판매 거래횟수가 50회 미만이면 통신판매업 신고 의무가 면제된다고 정리한다. 같은 기수 약 21명에게 1인 1개씩 팔면 약 21건이므로 알파는 이 구간에 들어간다. 사업자등록은 통신판매업 신고와 별개 문제라서, 면제라는 이유만으로 사업자등록까지 끝났다고 말할 수는 없다(구체 적용은 확인 필요).

| 구간 | 이렇게 하면 된다 | 남길 증거 |
|---|---|---|
| 내부 | 판매 대상·수량을 6명 내부로 제한하고 주문 수를 기록한다. | 주문대장, 1인 1개 제한 규칙 |
| 알파 | 같은 기수 약 21명에게 1인 1개만 판매한다. 거래횟수 누계를 50회 미만으로 관리한다. | 주문번호, 구매자 식별 토큰, 거래횟수 |
| 베타 전에 | 통신판매업 신고 필요 여부와 사업자등록을 세무·법률 담당자에게 확인하고, 필요 요건을 갖춘 뒤 외부 판매를 연다. 면제여도 신뢰·거래처·결제수단 때문에 신고하는 편이 유리한지는 확인 필요다. | 신고·등록 판단 기록, 약관·사업자 정보 |

**이번 10주에 실제로 만들 것**: `sales_ledger`에 주문일·주문번호·판매 구간·수량·상태를 저장하고, 50회 도달 전 경고를 띄운다. 사업자등록과 신고는 서로 다른 체크박스로 둔 베타 개통 체크리스트를 만든다.

### A-2. 청약철회는 “산 물건을 무를 권리”다

**결론**: 기간 계산과 예외 판정은 코드가 하고, LLM은 사실을 정리해 안내 문구만 만든다.

**청약철회 = 산 물건을 무를 권리**다. 법령사실 문서 2번에 따르면 소비자는 계약 내용을 받은 날부터 7일, 상품이 더 늦게 오면 상품을 받은 날부터 7일 안에 이유 없이 무를 수 있다. 하자가 없어도 된다. 그래서 “환불 가능한가?”를 LLM에게 맡기면 법이 이미 된다고 정한 건을 LLM이 안 된다고 말하는 사고가 난다.

| 판정 업무 | 담당 | 입력·출력 |
|---|---|---|
| 7일 계산 | 코드 | 계약 내용 전달일·수령일·현재일 → 계산된 기한 |
| 법령사실에 적힌 예외 조건 확인 | 코드의 규칙표 | 상품 상태·사용 여부·예외 코드 → `eligible / needs_review` |
| 주문·배송·고객 말의 정리 | LLM | 원문 → 사실 목록·빠진 정보 질문 |
| 고객에게 보낼 표현 | LLM + 문구 템플릿 | 코드 판정 결과를 넘겨 쉬운 안내문 생성 |
| 최종 환불 실행 | Core 2 + 승인·idempotency | 승인된 `ActionProposal` → 실행·감사 기록 |

LLM의 출력에는 `법정 기한 판정값`, `예외 코드`, `확인 필요 사유`를 덮어쓸 수 없게 한다. 코드가 `eligible`이면 LLM이 “안 됩니다”라고 바꾸지 못하고, `needs_review`이면 자동 확정하지 않는다.

**내부 단계에서 할 것 / 알파에서 할 것 / 베타 전에 갖출 것**:

| 내부 | 알파 | 베타 전에 |
|---|---|---|
| 주문일·계약 전달일·수령일을 넣은 10개 테스트를 만든다. | 실제 문의에서 “이유 없는 철회”와 하자 문의를 각각 기록한다. | 정책표·코드·환불 승인·고객 문구가 같은 판정을 내리는 통합 테스트를 통과시킨다. |

**이번 10주에 실제로 만들 것**: `withdrawal_deadline.py`, 예외 코드표, `RefundEligibility` 계약, 판정 결과를 근거와 함께 남기는 audit event, 7일 경계값 회귀 테스트를 만든다.

### A-3. 개인정보 국외이전

**결론**: 배송에 필요한 원문은 제한된 보관소에 두고, Case와 LLM에는 토큰만 넣으며, 베타 전에 별도 동의 또는 계약 이행 목적 처리위탁·처리방침 공개 경로를 확인해 갖춘다.

**금지가 아니라 요건이 있는 것**이다. 법령사실 문서 3번은 별도 동의 경로와, 계약 체결·이행에 필요한 처리위탁·보관이면서 개인정보 처리방침에 법정 사항을 공개하는 경로를 제시한다. 그래서 실제 구매대행 업체가 영업한다는 사실과 국외이전 통제가 함께 성립한다. 적용 요건은 거래 구조별 확인 필요다.

동의를 받는다면 미리 네 가지를 알린다: **받는 자**, 이용 목적, 보유·이용 기간, 거부 방법과 거부했을 때의 효과. 받는 자는 법인이면 명칭과 연락처까지 적는다.

| 데이터 | 저장 위치 | LLM·Case 전달 |
|---|---|---|
| 이름·주소·연락처·통관에 필요한 원문 | `delivery_pii_vault`에 암호화 저장, 배송 Adapter만 접근 | `pii_tok_01`, `addr_tok_01` 같은 토큰만 전달 |
| 주문·배송 상태 | Case DB | 주문번호·상태·날짜는 전달. 주소 원문은 제외 |
| 문의 본문 | PII masking 후 Case | 가림 처리된 문장과 토큰화된 고객 키 |
| 해외 전달 기록 | `transfer_audit` | 받는 자·목적·시각·동의/처리방침 경로의 식별자만 기록 |

이렇게 하면 v6의 “저장·LLM 전달 전 PII masking” 규칙을 지키면서 배송에는 필요한 원문을 쓸 수 있다. 배송 Adapter가 토큰을 원문으로 바꾸는 권한을 갖고, Team·LLM·로그에는 원문을 주지 않는다.

| 내부 | 알파 | 베타 전에 |
|---|---|---|
| 가짜 주소로 토큰화·복원·권한 테스트를 한다. | 실제 배송에는 최소 정보만 쓰고, Case에는 토큰만 남긴다. | 별도 동의 또는 계약 이행 목적 처리위탁·처리방침 공개 경로를 선택하고, 네 가지 고지 항목·보유기간·거부 효과를 문서와 화면에 넣는다(적용은 확인 필요). |

**이번 10주에 실제로 만들 것**: `PiiTokenVault`, `DeliveryPiiResolver`, `transfer_audit`, masking 테스트, tenant·case ownership 권한표, 개인정보 흐름도 1장을 만든다.

### A-4. PG·정산·세무

**결론**: 알파는 결제수단을 하나 정해 수동 대장과 이중 확인으로 운영하고, 베타 전에 PG·정산·세무 흐름을 실제 거래 기준으로 갖춘다.

| 알파 선택지 | 장점 | 단점·확인 필요 |
|---|---|---|
| 계좌이체 | 구현이 가장 빠르고 수수료가 낮다. | 입금자 확인·환불 계좌 확인이 수동이다. 세무 증빙과 사업자 사용 가능 여부는 확인 필요 |
| 간편결제 링크 | 구매자가 편하고 결제 상태를 확인하기 쉽다. | 수수료·가맹 조건·취소 API가 있다. 알파 사용 가능 여부는 확인 필요 |
| 현금 | 테스트가 단순하다. | 기록·영수·분실 관리가 어렵고 베타로 이어가기 어렵다. 세무 처리는 확인 필요 |

알파에서는 계좌이체를 기본으로 두고, 주문마다 `입금 확인자 1명`, 환불 실행자 1명, 수동 대장을 둔다. 금전 상태는 `입금 대기→입금 확인→환불 대기→환불 완료`로 기록하고, 실제 돈을 바꿀 때는 idempotency key를 쓴다.

| 내부 | 알파 | 베타 전에 |
|---|---|---|
| Mock 결제·환불과 중복 요청 차단을 만든다. | 계좌이체 또는 승인된 간편결제 하나로 실제 소액 거래를 기록한다. | PG 계약·취소/환불 API·정산 주기·수수료·세금계산/영수 증빙·환불 책임자를 확인하고, 실패·중복·미입금 대장을 갖춘다(각 적용은 확인 필요). |

**이번 10주에 실제로 만들 것**: `PaymentRecord`, `SettlementLedger`, 수동 입금 확인 화면, 환불 승인 큐, 중복 환불 차단, 거래별 원장 CSV export와 베타 개통 체크리스트를 만든다.

### A-5. Team이 Adapter를 직접 호출하는 문제

**결론**: Team은 읽기·외부 호출·side effect를 직접 하지 않고 `ActionProposal` 또는 `TeamResult`만 반환하며, Controller와 Core 2가 Port 뒤에서 실행한다.

**왜 문제였나**: 확장안의 Return & Refund Team이 Marketplace Return Adapter를 직접 호출하면 승인·idempotency·audit 경계를 우회한다. v6는 Team이 read를 직접 호출하지 않고 Context Broker의 `ContextPack`을 받으며, 쓰기는 `ActionProposal`만 반환하도록 정했다.

| 바꿀 계약 | 내용 |
|---|---|
| Team 입력 | `TeamTask(case_id, context_pack, required_context)` |
| Team 출력 | `TeamResult(decisions, evidence, action_proposals, outcome)` |
| 실행 위치 | `Controller → Core 2 ExecuteAction → MarketplacePort/ReturnAdapterPort` |
| 필수 메타데이터 | `mandate_id`, `mandate_version`, `mandate_decision`, `idempotency_key` |

```python
class ReturnTeam(Protocol):
    async def execute(self, task: TeamTask) -> TeamResult: ...

class ActionExecutor(Protocol):
    async def execute(self, proposal: ActionProposal, approval: Approval) -> ActionResult: ...
```

**이번 10주에 실제로 만들 것**: Team 코드에서 Adapter import를 금지하는 정적 검사, `ActionProposal → ExecuteAction` contract test, 승인·중복·실패·`unknown` 통합 테스트를 만든다.

| 내부 | 알파 | 베타 전에 |
|---|---|---|
| Mock Adapter와 Proposal만으로 흐름을 검증한다. | 실제 주문·반품 요청은 Team이 제안하고 사람이 Core 2 승인 화면에서 실행한다. | 모든 외부 Adapter를 Port 뒤에 두고 승인·idempotency·audit·unknown 처리를 통과시킨다. |

### A-6. MCP 쓰기 tool 문제

**결론**: v6의 MCP read-only 3개를 유지하고, 주문·취소·반품·환불 변경은 REST 내부 승인 경로로만 처리한다.

**왜 문제였나**: 개인 AI가 `create_order`나 `request_return`을 직접 호출하면 돈과 주문 상태가 즉시 바뀔 수 있다. v6와 `CLAUDE.md §0.2`의 원래 이유는 승인 없이 결제를 건드리면 되돌릴 수 없고, 잘못된 환불 안내도 고객 손해로 이어진다는 안전 원칙이다.

| 경로 | 허용 |
|---|---|
| MCP | Case 조회, 주문·배송 상태 조회, Case 생성·분류 시작 등 read 중심 3개 |
| REST | v6의 정확히 5개 endpoint. 변경 요청은 scope·소유권·idempotency·승인 검사 |
| 내부 Action API | 실제 취소·반품·환불 실행. Core 2와 감사 로그가 담당 |

**이번 10주에 실제로 만들 것**: MCP schema에 `mcp:read`만 허용하고, 쓰기 시도 403/감사 로그를 남기는 보안 테스트와 REST 5개 contract test를 만든다.

| 내부 | 알파 | 베타 전에 |
|---|---|---|
| MCP read-only schema와 쓰기 거부 테스트를 만든다. | 개인 AI는 조회·Case 생성까지만 쓰고, 실제 변경은 운영자 승인 경로로 처리한다. | 외부 공개 scope와 승인 정책을 문서화하고 저위험 쓰기 개방 여부를 별도로 결정한다. |

### A-7. Agent Team 6개 제시와 기준선 2~3개의 충돌

**결론**: 내부 착수 Team은 2~3개로 고정하고, 6개는 최종 확장 그림으로만 제시하며 Registry 등록으로 늘린다.

**왜 문제였나**: 6개를 모두 실제 구현한다고 말하면 10주 안에 각 Team의 평가셋·시나리오·회귀 테스트를 채점하기 어렵다. v6는 Team 수를 상한으로 정하지 않지만, 착수 구성은 2~3개이고 확장은 Registry 등록으로 처리한다고 정한다.

| 이번 범위 | 계약 수준 수정 |
|---|---|
| 실제 구현 | `Billing/Order`, `Technical/Entitlement`, `Feedback/VOC` 2~3개 |
| 나머지 3개 | `TeamManifest`와 fixture stub만 둔다. 실제 실행·성능 주장은 하지 않는다. |
| 확장 방식 | `team_id`, `capabilities`, `required_context`, `allowed_tools`, `execution_type`을 Registry에 추가한다. Controller와 `TeamExecutorPort`는 바꾸지 않는다. |

**이번 10주에 실제로 만들 것**: 2~3개 Team의 `TeamManifest`, Team별 fixture·golden label·contract test, 미구현 Team은 “등록 예정” 표기만 하는 Registry 화면을 만든다.

| 내부 | 알파 | 베타 전에 |
|---|---|---|
| 기준선 2~3개 Team의 계약과 라우팅을 만든다. | 실제 Case를 세 Team에 라우팅하고, 빠진 capability는 `escalated`로 보낸다. | 외부 판매에 필요한 Team만 fixture·평가축·운영 담당자를 갖춘 뒤 Registry에 활성화한다. |

## B. 오너의 직접 질문

### B-1. 알파까지만 해도 쇼핑몰을 굴려봤다고 할 수 있나?

**결론**: “제한된 실제 파일럿 쇼핑몰을 운영했다”고 말할 수 있지만, “외부 고객 대상 상용 쇼핑몰을 검증했다”고 말할 수는 없다.

| 알파 21건으로 증명 가능 | 알파 21건으로 증명 불가 |
|---|---|
| 실제 주문 접수·입금 확인·배송 상태·문의·취소·반품·환불 흐름 | 외부 고객 전체의 수요와 재구매율 |
| 1인 1개 제한과 수동 운영 절차 | 대규모 트래픽·대규모 PG 정산 안정성 |
| 실제 고객 문장과 Case event | 외부 판매에 필요한 모든 법률·세무 요건을 갖췄다는 사실 |
| Agent의 분류·안내·승인 대기 경계 | 파인튜닝 효과나 일반 고객군 성능 |

발표에서는 이렇게 말하면 된다.

> “같은 기수 21명을 대상으로 실제 돈이 오가는 제한된 알파를 운영해 주문·배송·문의·반품·환불 Case를 수집했고, 베타 외부 판매에 필요한 남은 요건은 별도 체크리스트로 관리하고 있습니다. 이 결과는 상용 규모 증명이 아니라 실제 운영 흐름과 안전 경계를 검증한 결과입니다.”

### B-2. 21명으로 충분한 데이터가 나오나? 파인튜닝 될 만큼?

**결론**: 21건으로 파인튜닝은 안 된다. 대신 평가셋 보강·프롬프트 개선·RAG 사례 보강·상태 전이 검증에는 충분히 쓸 수 있다.

계획용 숫자는 다음처럼 잡는다. 주문 21건에서 문의가 주문당 0.2~0.5건 생긴다고 가정하면 문의는 약 **4~11건**이다. 반품·환불이 주문의 5~15%라고 가정하면 약 **1~3건**이다. 실제 비율은 이 알파에서 측정할 값이며, 이는 보장 수치가 아니다. 따라서 “Case 21건”이 아니라 “문의·반품·환불 Case가 대략 5~14건일 수 있다”고 계획한다.

일반적인 지시 튜닝은 수백~수천 개의 품질이 확인된 예시가 필요하다. 21건, 또는 그중 5~14건으로는 표현의 다양성·실패 유형·고객군 차이를 충분히 담지 못하므로 파인튜닝 결론을 내리면 안 된다.

| 21건의 쓰임 | 판단 |
|---|---|
| holdout을 새로 만드는 것 | 너무 작다. 기존 v6의 holdout 20건은 보존하고 알파는 별도 실사용 holdout으로 표시 |
| 프롬프트 개선 | 충분하다. 자주 틀린 질문과 빠진 정보 확인에 사용 |
| RAG corpus | 정책 원문을 대체하지는 못하지만 실제 질문·정답 근거 연결 사례로 보강 가능 |
| 시나리오 검증 | 충분하다. 주문→배송→문의→반품→환불 흐름과 상태 전이를 검증 |
| 파인튜닝 | 부족하다. 수백~수천 건을 별도로 모아야 한다 |

데이터를 늘리는 방법은 합성 사례, 과거 문의를 PII 제거 후 재사용하는 방법, 알파의 한 주문에서 배송·가격·지연·반품·환불 사건을 각각 Case로 분리하는 방법, 베타 승인 후 실제 외부 Case를 누적하는 방법이다. 합성은 경계값과 실패 재현에 쓰고, 실제 데이터는 고객 표현·운영 시간·진짜 결과 검증에 쓴다.

### B-3. 데이터는 어디서 얼마나 얻나?

**결론**: 정책·평가·도구 응답은 합성으로 먼저 만들고, 주문·배송·반품·환불의 결과와 외부 이벤트만 실제 또는 실제와 같은 Sandbox에서 확보한다.

| 데이터셋 | 무엇에 쓰나 | 필요 규모 | 어디서 얻나 | 합성/실제 | 없으면 무엇이 안 되나 |
|---|---|---:|---|---|---|
| 정책·FAQ 문서 | RAG 답변 근거 | 25건, 300~400 chunk | v6 문서·팀 작성 정책 | 합성/내부 작성 | 근거 있는 답변과 scope 검색이 안 됨 |
| golden / holdout | 성능 비교 | 60+20 | 팀 라벨링, 알파 사례 일부 추가 | 합성+실제 | A/B/Proposed 비교와 과적합 감시가 안 됨 |
| 감성·의도·이슈 라벨 | 인라인 분류 | golden 60건부터, 실제 Case 전수 라벨 | 두 명 독립 라벨·불일치 조정 | 합성+실제 | routing과 feedback 집계가 흔들림 |
| Team별 시나리오 fixture | Team 계약·라우팅 | Team당 정상·모호·실패 10개 이상 | 팀 작성 | 합성 | Team 실행을 반복 검증할 수 없음 |
| Tool 호출 mock 응답 | 성공·실패·timeout 재현 | Tool당 성공·중복·실패·unknown 4종 이상 | 개발 mock | 합성 | 외부 연동 없이 승인·재시도·unknown을 검증할 수 없음 |
| 주문·배송·반품 이력 | 실제 운영 Case | 알파 주문 약 21건, 사건은 주문별 여러 개 | 알파 실제 거래 | 실제 | 고객 표현과 실제 운영 시간·결과가 없음 |
| 상태 전이 회귀 Case | 재실행·철회·중복 검증 | 상태 경로별 3~5개 | 합성+알파 로그 | 둘 다 | 조기 종료·중복 환불을 잡을 수 없음 |
| Outcome 외부 이벤트 | 실제 결과 판정 | 배송완료·반품접수·환불완료 등 이벤트별 fixture | Sandbox webhook 또는 실제 공급자 이벤트 | 실제 필요, 없으면 mock | Outcome을 만족했다고 증명할 수 없음 |

알파 21명은 표에서 **주문·배송·반품·환불 이력**, 일부 **실제 라벨**, **상태 전이 회귀 Case**, **Outcome 외부 이벤트의 실제 예시**를 채운다. 정책 25건, golden 60+20, mock 응답은 알파가 없어도 합성으로 먼저 만든다. 알파에서 이력이 적으면 “실제 데이터가 적다”고 표시하고 합성 데이터와 섞어 실제처럼 세지 않는다.

## C. Mandate·Outcome 치명적 4건

Mandate는 고객이 에이전트에게 준 **위임장**이다. “배송조회만 해줘”, “이 조건이면 반품 접수해줘”처럼 허용 범위와 목표를 적은 약속이다. Outcome은 **고객이 원한 결과가 실제로 이뤄졌는지**다. Team이 “처리했다”고 말한 것과 고객 결과가 실제로 완료된 것은 다를 수 있다.

### C-1. MCP 쓰기 tool

**결론**: Mandate 조회는 기존 MCP read-only Case 조회에 포함하고, Mandate 변경·철회와 금전 작업은 승인된 REST·내부 경로로 둔다.

**사고 시나리오**: 고객이 개인 AI에게 “반품해줘”라고 말했고, 개인 AI가 `request_return`을 직접 호출한다. 상품 상태·기간·소유권 확인 전에 반품이 접수되거나, 환불까지 이어진다.

**해결책**: MCP는 현재 Mandate/Outcome을 읽기만 제공한다. 고객의 범위 축소·철회는 승인된 REST 또는 운영 command로 받고, `mandate_version`을 올린다. 실행 직전 Core 2가 다시 Guard를 통과시킨다.

### C-2. REST endpoint 5개 초과

**결론**: MVP는 Mandate 생성은 Case 생성 요청에서 만들거나 서버가 Case intent에서 파생하고, 별도 REST endpoint를 추가하지 않는다.

**사고 시나리오**: 계획서에 `POST/PATCH/revoke mandate`, `GET outcome`을 추가해 총 endpoint가 늘어난다. 클라이언트·권한·idempotency·contract test가 새로 필요하지만 기존 v6 5개 계약과 문서가 서로 달라진다.

**해결책**: 읽기 화면의 Case detail에 Mandate/Outcome projection을 포함한다. 외부에 별도 endpoint를 열기로 바뀌면 v6 DoD·handoff·scope·오류 응답을 함께 개정한 뒤 구현한다.

### C-3. 누가 위임장을 주고 뺏는지 없음

**결론**: 고객 또는 고객의 대리 Agent만 자기 Case의 범위를 줄이거나 철회하고, 운영자는 정책상 중지·escalate만 하며, Team은 Mandate를 만들거나 바꾸지 않는다.

**사고 시나리오**: Team이 “고객이 환불까지 맡겼다”고 해석해 허용 범위에 없던 환불을 제안한다. 나중에 고객은 배송조회만 맡겼다고 말하지만 actor와 근거가 없다.

| 주체 | 생성 | 수정·범위 축소 | 철회 | 기록 |
|---|---|---|---|---|
| 고객 | 가능 | 가능 | 가능 | actor·scope·시각 |
| 고객 대리 Agent | 고객 인증·소유권 확인 시 가능 | 가능 | 가능 | 위임 체인·token |
| 운영자 | 정책상 Case 생성 경로에서만 | 중지·escalate | 정책상 중지 | 사유·승인자 |
| Team | 불가 | 불가 | 불가 | 제안만 기록 |
| Controller | 검증만 | 검증만 | 검증만 | Guard 결과 |

### C-4. 실행 중 철회

**결론**: 실행 전에는 막고, 실행 중에는 취소 가능 여부에 따라 취소 또는 `unknown/escalated`로 남기며, 성공 뒤 철회는 과거 실행을 소급 취소하지 않는다.

**사고 시나리오**: 환불이 `approved`가 되어 PG 호출 직전인데 고객이 철회한다. 철회를 무시하면 원치 않는 환불이고, 이미 PG에 보낸 뒤 내부만 취소하면 실제 돈과 내부 상태가 달라진다.

| Action 상태 | Mandate 철회·만료 시 규칙 |
|---|---|
| `proposed` | 즉시 무효화. 실행 요청을 만들지 않는다. |
| `pending_approval` | 승인 큐에서 취소. 기존 proposal과 철회 event를 audit에 남긴다. |
| `approved` | 실행 직전 Mandate를 재검증한다. 유효하지 않으면 `cancelled`로 끝낸다. |
| `executing` | 공급자가 취소를 지원하면 취소를 시도한다. 결과가 확실하지 않으면 `unknown` 후 운영자 확인으로 보낸다. |
| `succeeded` | 소급 취소하지 않는다. 이미 실행된 사실과 이후 보상·재처리는 별도 Case로 남긴다. |
| `failed` | 자동 재실행하지 않고 실패 원인과 현재 Mandate를 다시 확인한다. |

## D. 정해야 할 것 3가지

### D-1. MCP 쓰기가 왜 닫혀 있나

**결론**: MCP는 개인 AI가 우리 서비스에 붙는 통로이고, 이번 기준선에서는 읽기 전용으로 둔다. 쓰기를 열려면 승인·범위·중복 차단·감사를 한 묶음으로 추가한다.

`MCP`는 개인 AI가 우리 서비스의 도구와 자료를 쓰게 하는 연결 통로다. v6와 `CLAUDE.md §0.2`가 읽기 전용으로 정한 원래 이유는 **개인 AI가 사용자를 대신해 결제·환불을 건드리면 되돌릴 수 없기 때문**이다.

| 선택 | 좋아지는 점 | 위험 |
|---|---|---|
| 읽기 전용 유지 | 고객 정보 조회와 Case 생성은 안전하게 제공 | 개인 AI가 주문·반품을 끝까지 자동 처리하지 못함 |
| 모든 쓰기 개방 | 자동화율과 편의가 가장 높음 | 잘못된 해석·중복 호출·무단 환불이 곧 side effect가 됨 |
| 승인 필수 쓰기 | 자동 제안과 사람 확인을 함께 얻음 | 승인 화면·scope·idempotency·감사가 필요 |
| 저위험 쓰기만 | 배송조회 Case 생성 등 일부 자동화 가능 | 저위험 정의와 오용 방지 규칙이 필요 |

이번 10주는 중간 선택지로 **MCP는 read-only 유지, 쓰기는 REST/내부 Action에서 승인 필수**로 간다. 이후 열 수 있는 저위험 후보는 배송조회 Case 생성처럼 돈·주문 상태를 바꾸지 않는 작업이다.

### D-2. 단계 정의

**결론**: 내부는 전부 시험용, 알파는 실제 소액 판매와 수동 환불, 베타는 외부 판매 전 요건을 갖춘 뒤 필요한 기능만 연다.

| 항목 | 내부 | 알파 | 베타 |
|---|---|---|---|
| 법규 | 끔: Mock·문서 검토 | 제한 켬: 실제 거래 기록, 신고 면제 구간 적용 | 켬: 신고·등록·약관·개인정보 경로 확인 후 |
| 결제 | 끔: Mock | 켬: 계좌이체 또는 확인된 간편결제 1개 | 켬: PG·정산·세무 흐름 확인 후 |
| PII | 끔: 가짜 데이터 | 제한 켬: 배송 원문은 별도 보관, Case·LLM은 토큰 | 켬: 동의 또는 처리위탁·처리방침 경로 확인 후 |
| MCP 쓰기 | 끔 | 끔 | 기본 끔. 열면 승인 필수 저위험만 |
| 실제 환불 | 끔: Mock | 켬: 1인 1개·소액·사람 확인 | 켬: PG 환불·원장·실패 처리 확인 후 |

법규 적용과 베타 개통 조건은 거래 구조에 따라 확인 필요다. 단계 자체는 위 표대로 고정한다.

### D-3. “내부 모델 / 외부 계약”이 무슨 말인가

**결론**: 여기서 모델은 AI 모델이 아니라 데이터 구조·클래스다. MVP의 Mandate/Outcome은 우리 서버 안의 내부 모델로 두고, 바깥에 직접 공개하는 외부 계약은 나중에 versioned contract로 연다.

| 말 | 뜻 | 장점 | 단점 |
|---|---|---|---|
| 내부 모델 | Mandate/Outcome을 우리 서버의 `state_json`, `case_events`, 내부 클래스와 Guard로만 사용 | 변경이 쉽고 개인정보·권한 노출이 작다 | 개인 AI·다른 회사 Agent가 구조를 직접 사용할 수 없다 |
| 외부 계약 | 바깥 Agent가 Mandate/Outcome 구조를 직접 보고 API·MCP로 호출 | 상호운용과 B2B 연동이 쉽다 | 버전 호환·권한·소유권·철회·보안 계약이 필요하다 |

원래 계획의 방향은 외부 Agent 연동을 포함하지만, v6의 실제 기준선은 REST 5개와 MCP read-only 3개이며 Mandate/Outcome 외부 write는 충돌한다. 리뷰의 실행안대로 MVP에서는 내부 모델과 읽기 projection만 만들고, 외부에 노출할 때는 `contract_version`, `RemoteTaskMandateView`, scope, ownership, revoke 규칙을 먼저 고정한다.
