# A-COP 아이디어 통합 분석

팀에서 나온 아이디어 문서 6건(4명)과 고도화 제안 5건을 한자리에서 판정한 문서다.
기준 문서는 `A-COP_구현계획서_v6.md`이며, 제약은 6명 / 10주 / 코드 0줄 / 실사용자·실데이터 없음이다.
모든 판정은 Claude와 Codex가 각각 독립 분석한 뒤 대조해 확정했다.

판정에 쓴 기준은 셋이다.

1. 정답셋이 존재하는가. 없으면 데모 장식이다.
2. 입력이 임의 배정에 의존하는가. 지어낸 값이 경로를 바꾸면 인과 사슬 전체가 가짜가 된다.
3. 코어 루프에 필요한가. 접수 → 분류 → 근거 수집 → 제안 → 생성 → 검토 → 승인 → 종결 → 집계.

## 1-2. 팀은 이미 수렴해 있다

여섯 문서를 나란히 놓으면 표현은 달라도 공통된 구조가 보인다.

따라서 실제 질문은 "누구 안을 고를까"가 아니다. 뼈대는 합의됐고 차별화 축만 남았다.
세 사람이 서로 다른 축을 제안했다.

- uh — 에스컬레이션과 리스크가 처리 경로를 바꾼다 (동작)
- sw — 상태를 잃지 않고 안전하게 처리하며 기업별로 이식된다 (엔지니어링)
- jh — 고객의 말에서 팔 것을 찾아낸다 (분석의 사업 가치)

다만 공통 명사가 곧 합의는 아니다. Case의 최소 입력 보장 범위, 피드백 분석이 실제로 어느 전이를
바꾸는지, 정답셋이 있는 기능과 없는 기능의 경계는 아직 정해지지 않았다.

## 1-4. 확정 에이전트 구성

cy가 제안한 5팀은 성격이 다른 둘과 배치 모듈로 갈린다. 배정되는 것과 주기적으로 도는 것이다.
응답 생성과 안전 확인은 별도 Team이 아니라 기존 Team 계약과 시스템 경계에 포함된다.

### 배정형 — Agent Team

케이스마다 필요할 때만 배정된다. 이것만 Team으로 센다.

| 팀 | 근거 |
|---|---|
| ORD 주문·반품·환불 | 조회 도구 선택 + 승인 대기 후 상태 기반 재진입이 실재 |
| LOG 배송·물류 | 외부 확인 요청 → 대기 → 재개 루프가 실재 |

### cy의 GEN·REV 제안은 어디로 갔는가

GEN·REV를 별도 Team, Port, Registry, Case 상태, 반려 카운터로 추가하지 않는다. v6의
`TeamResult.answer`가 근거 기반 고객 응답을 이미 생성하고, `warnings`가 출력 문제를 신고한다.
PII는 저장·LLM 전달 전에 masking하며, tenant scope와 redaction snapshot은 DoD 7과 보안 테스트로 확인한다.
응답에 side effect가 필요할 때도 Team은 `ActionProposal`만 반환하고 운영자 승인과 실행은 기존 경계에서 맡는다.
반복 실행은 graph step 12, Team task 6, tool call 12, 동일 signature 2회의 loop guard가 제한한다.

| cy 기능 | 실제 위치 |

| GEN 01 근거 기반 응답 초안 | Team의 `answer` 생성 — 이미 있음 |
| GEN 02 개인화 톤·채널 | Context Pack + 프롬프트 |
| GEN 03 FAQ 매칭 | 분류 단계 |

이 판단의 교훈은 기능 제안을 기존 계약과 먼저 대조해야 한다는 점이다. “빠져 있다”는 주장은
계약 필드와 실행 경계를 확인하기 전까지 가설로 남겨야 한다.

### 주기형 — 배치 모듈

| 모듈 | 근거 |
|---|---|
| SEL 판매자·품질 VOC | 정기 집계·클러스터링·룰 경보. 자율 도구 선택도 다회 턴도 없음 |

착수 시점의 에이전트는 ORD와 LOG 둘이다. 다만 이것은 상한이 아니다.
v6에서 Agent Team은 등록형 Team Module이므로 Registry 등록만으로 확장되며,
확장 시 Controller·`TeamExecutorPort`·`ActionProposal` 계약은 바뀌지 않는다.
A2A로 등록되는 Remote Agent도 같다. 확장을 막는 것은 아키텍처가 아니라 평가 여력이다.
Team이 늘면 골든셋과 라우팅 평가 축이 함께 늘어난다.

GEN·REV는 별도 관문이 아니다. Team이 `answer`와 `warnings`를 반환하고, 근거·정책버전·PII·권한
검사는 v6의 기존 계약과 저장·전달 경계, 골든셋 평가에 배치한다. 응답 생성 주체가 없다는 주장은
`TeamResult` 계약을 확인하기 전의 가설이었으므로 철회한다.

## 1-5. 계층과 Case 상태 — 격자는 만들지 않는다

uh의 L0~L3와 sw의 Case 상태를 두 개의 나란한 축으로 두려던 초안은 철회했다.
격자를 실제로 채워보면 대부분 비어 있다. L0는 종결과 추가정보 요청만, L3는 제안과 종결만 나오고,
상태 다섯 개가 모두 도는 층은 L2뿐이다.
더 결정적인 것은 uh 원문의 "문의 처리가 실패하면 다음 상태로 분쟁 격상"이라는 표현 자체가
L을 상태처럼 쓴다는 점이다. 직교성은 구현이 아니라 서술 단계에서 이미 깨져 있다.
이의제기와 외부 절차도 선형 층이 아니라 재진입 경로여서 격자로는 정상 경로와 구별되지 않는다.

확정: `layer`와 `owner_role`은 라우팅·권한 메타데이터 필드로만 둔다.
층이 결정하는 것은 모델 등급·도구 범위·승인 권한이고, 진행도는 전적으로 Case 상태가 답한다.
L0는 유지하되 층이 아니라 자동 종결 경로로 부르고, 여기에 자동 해결률 지표가 붙는다.

### 경계선
ORD와 LOG 두 에이전트가 `answer`와 구조화된 처리안을 만들고, 분류·리스크 룰·SLA 타이머·배치 집계가
그 입력과 경로를 결정하며, 운영자 승인으로 종결되고, 그 결과가 집계되어 다음 Case의 경로를 바꾸는 지점까지가 범위다.
루프 밖에 있는 연관 상품 추천, 재고 기반 교환, 배송 지연 예측은 전부 밖이다.
경계의 근거는 공수가 아니라 데이터와 평가 가능성이다.

## 1-7. 임의 배정 문제와 해법

cy는 판매자 단위와 배송사 필드가 데이터에 없어 임의 배정한다고 적었다.
갭을 표시한 것은 정직하지만, 그 값이 리스크 룰의 입력이 되면 인과 사슬이 통째로 가짜가 된다.

```
임의 판매자 배정 → 임의 분쟁률 → 임의 리스크 점수 → 선환불/소명 경로
```

이 상태로 높은 경로 정확도를 얻어도 모델이 판매자 위험을 발견한 것이 아니라
팀이 만든 매핑을 재현한 것이다. 같은 리뷰를 다른 판매자에 배정하면 환불 경로가 달라지므로
공정성 주장도 함께 무너진다.

해법은 판매자 분쟁률을 리뷰가 아니라 종결된 Case 판정 결과에서 누적하는 것이다.
시스템이 스스로 생성한 값이므로 인과 사슬이 진짜가 되고,
처리 → 집계 → 다음 케이스 경로 변경이라는 루프도 더 깔끔하게 닫힌다.
전제 조건은 Case를 시간순으로 처리하고 t 시점까지 종결된 것만 집계하는 것이다.
미래 케이스의 정답이 현재 입력에 섞이면 leakage가 된다.

배송사 단위 집계는 포기하고, 리뷰 기반 신호는 보조 입력으로만 쓴다.

## 2-2. 근거 + 정책버전 + 확신도 노출

앞의 둘은 v6에 재료가 이미 있다. 정책 문서에 시행일 버전이 있고 평가 지표가 근거 인용의 정확도를 측정한다.
`ActionProposal`에 `policy_version`과 `evidence_ids`를 추가하는 계약 변경 하나로 끝난다.

확신도가 문제다. LLM에게 자기 확신도를 물으면 숫자는 나오지만 실제 정확도와 상관이 낮다.
관측 가능한 특징으로 결정론적으로 유도해야 한다.

```
evidence_score
 = 0.35 × 핵심 주장에 연결된 유효 evidence 비율
 + 0.25 × 적용 정책 버전·tenant·시점 일치
 + 0.20 × 필수 DB fact 충족률
 + 0.10 × 독립 근거 간 비충돌률
 + 0.10 × 입력·검색 ambiguity의 역점수
```

가중치는 진실이 아니라 설정값이므로 버전 관리한다. 그러면 점수 구간별 실제 정확도를 비교하는
캘리브레이션 평가가 가능해진다. Brier score, Expected Calibration Error, reliability diagram을 쓰고,
필요하면 isotonic regression으로 보정한다. 골든 60건은 곡선의 일반화 근거로 부족하므로
"이 골든셋에서의 보정"이라고 보고하고, holdout 20건은 보정 파라미터를 고정한 뒤 확인한다.

두 가지 금지 조항이 함께 간다. 첫째, 이 점수를 환불·권리·제재 경로의 입력으로 쓰지 않는다.
확신도가 자동 응답 노출이나 사람 검토 여부를 바꾸면 경로가 오염된다.
증거가 없으면 점수를 깎고 `unknown` 또는 사람 검토를 반환하는 데까지만 쓴다.
둘째, 근거 개수를 세어 확신도를 올리지 않는다. 근거가 존재한다는 것과 근거가 결론을 지지한다는 것은
다르며, 후자는 골든 60건에 사람이 핵심 주장과 지지 근거를 라벨링해야 채점된다.

자동 채점이 가능한 것은 정책 버전 exact match, 인용한 evidence가 실제 Context Pack에 있는지,
claim과 값이 일치하는지까지다. 자연어가 근거를 충분히 설명했는지는 사람 라벨 없이 자동 정답으로 삼지 않는다.

## 2-3. 이슈 원인-영향 그래프화

"특정 옵션 재고부족 → 배송지연"은 인과 주장이다.
우리 데이터는 관측 데이터도 아니고 합성이므로 인과 추론이 성립하지 않는다.
합성 데이터에서 인과를 발견하면 우리가 심은 인과를 우리가 찾은 것이다.

관계 경로와 원인 후보로 낮추면 살아난다. 자동 채점이 가능한 범위는 Case·Issue·Product·배송 이벤트의
실제 FK 연결, 시간순 선후 관계와 집계 수치, 동일 기간·동일 엔티티의 공출현율,
정의한 규칙에 따른 alert 발생 여부와 재현성까지다. 화면은 거의 같아 보이는데 방어 가능성이 달라진다.

계약은 소규모로 확장한다. `Evidence`의 claim만으로 인과를 표현하면 안 되므로
`relation_type = contains | precedes | co_occurs | candidate_cause`와 근거 범위를 추가한다.
엣지 라벨을 `candidate_cause`로 낮추고 원인 확정, 제재, 자동 라우팅 변경은 하지 않는다.

통제된 fixture에서 원인과 결과를 생성하고 다른 원인을 차단한 대조쌍을 사람이 설계하면
원인 탐지 실험은 가능하다. 다만 그것은 인과 발견의 정답이 아니라 fixture 내 규칙 회수율이며,
발표에서는 원인 후보라고 부른다. 계절성, 프로모션 노출량, 판매자 구성 변화, 수집 지연이
통제되지 않은 상태에서 선행 관계를 인과로 부르면 안 된다.

이 기능은 Graph DB 도입 유혹을 부른다. 결론부터 말하면 현재 채택 조건을 충족하지 못한다.
제안된 관계가 정형 FK와 일일 집계로 대부분 재현되고 PostgreSQL JOIN·재귀 CTE가 같은 경로를
결정적으로 계산하기 때문이다. v6의 확장 조건은 A2A 위임 깊이 3 이상 반복,
가변 multi-hop에서 SQL 경로 근거의 지속적 누락, 임의 경로 탐색이 핵심 요구가 되는 경우이며
원인 후보 화면만으로는 어느 것도 만들지 못한다. `SqlGraphAdapter`를 유지한다.

## 2-4. 상품 미보유 vs 탐색 실패 구분

5건 중 가장 값이 나간다. 이유는 정답의 상당 부분을 사람이 만들지 않아도 되기 때문이다.
카탈로그 snapshot이 정답 원천이 된다.

두 갈래가 아니라 네 갈래로 나누는 편이 정확하다.

```
상품 식별 성공
  ├─ 카탈로그 없음            → catalog_absent
  └─ 카탈로그 있음
       ├─ 판매·재고 불가       → unavailable
       ├─ 검색 결과에 없음     → search_miss
       └─ 검색 결과에 있음     → found
```

존재 여부는 상품 ID 또는 정규화된 SKU의 exact match로, 검색 실패는 snapshot에 있으나 인덱스에
노출되지 않았거나 관련성 기준을 통과하지 못했는지로, 품절은 재고·판매상태의 시점 일치로 채점한다.
고객 표현을 어느 상품에 매핑할 것인가는 골든 60건에 사람이 라벨링한다.
카탈로그가 없으면 "없다"가 아니라 `unknown`을 반환한다.

그리고 같은 문의가 갈라진다. 탐색 실패는 응대 쪽으로 가서 검색 안내와 대체 상품 제시가 되고,
미보유는 분석 쪽으로 가서 수요 신호로 적립된다.

두 가지를 혼동하지 않아야 한다. 조회 결과는 사실 판정이고 수요 추정은 별도 주장이다.
"찾지 못했다"가 곧 수요가 있다는 뜻은 아니다.
또 동의어, 오탈자, 옵션·사이즈, tenant별 카탈로그 범위, 판매 기간, 인덱스 지연을 분리하지 않으면
검색 실패를 상품 부재로 오인한다.

기존 판정과의 관계를 분명히 해둔다. jh 트랙 C의 컷은 뒤집지 않는다.
그 컷은 추천과 수요 발굴이라는 출력에 적중·전환·운영자 우선순위 정답이 없다는 판정이었다.
이번 것은 추천이 아니라 카탈로그 사실 판정이므로 같은 아이디어의 부활이 아니라 다른 문제다.
실제 카탈로그·검색 로그·재고가 없어 fixture로 만들 경우, 거기서 자동 생성되는 정답은
시스템 테스트 정답이지 시장 수요의 정답이 아니다.

## 2-5. 기획전 우선순위 점수화

인자 넷 중 둘이 없다. 문의 증가율은 있고 미충족 수요는 2-4가 만들어 주지만,
재고 적합도는 재고 데이터가 없고 마진 가능성은 원가 데이터가 없다.
없는 둘을 Mock으로 채우면 우리가 방금 세운 임의 배정 금지 원칙을 우리가 먼저 어긴다.
그것도 우선순위를 바꾸는 입력에서 어긴다.

처음에는 두 인자(문의 증가율 × 미충족 수요)로 줄여 채택하려 했으나 철회한다.
인자를 줄여도 검증되지 않는 것이 남기 때문이다. 점수는 계산되지만
"그 순위가 맞는가"의 정답이 없다. 순위의 정답은 실제 클릭·전환·마진이거나
사전에 합의된 운영자 우선순위인데, 실사용자와 실데이터가 없는 지금은 어느 것도 없다.
사람이 한 번 순위를 매기는 것으로는 사업 성과의 정답이 되지 않으며,
그러려면 평가자 간 일치도와 시간이 지난 뒤의 성과 검증이 필요하다.
점수 화면만 만들면 이 아이디어의 핵심인 우선순위 결정값이 검증되지 않으므로 축소 채택이라 부를 수 없다.

곱셈식 자체의 위험도 있다. 문의가 많다는 것이 수요가 크다는 뜻은 아니다.
품절 상품은 문의가 많고, 마진이 낮은 상품이 고객 가치는 높을 수 있다.
각 항의 척도와 결측치 처리, 가중치에 결과가 강하게 의존한다.

이번에는 필요한 필드 계약과 결측 시 `unknown` 규칙만 설계하고 수식은 구현하지 않는다.
쓸모 있는 부분은 이미 2-4에 있다. `catalog_absent` 건수 집계는 채점 가능하며 그것으로 충분하다.

## 2-6. 상담원 피드백 학습루프

데이터가 부산물로 쌓인다는 점이 크다. v6에 운영자 승인과 감사 로그가 이미 있으므로
승인·수정 기록은 따로 만들지 않아도 생긴다.

문제는 학습이라는 단어다. 10주에 온라인 학습이나 파인튜닝은 무리이고,
더 큰 문제는 모델이 계속 변하면 A/B 비교가 불가능해진다는 점이다. 평가 재현성이 깨진다.

범위를 이렇게 낮춘다. 피드백을 기록하고, 배치로 오류 패턴을 찾아,
오프라인 평가를 통과한 라우팅 후보를 운영자 승인 후 버전으로 등록하는 데까지다.
자동 모델 업데이트와 즉시 라우팅 변경은 하지 않는다.
Team의 `warnings`와 기존 loop guard 기록에 이어지고, HITL이 안전장치일 뿐 아니라 데이터 생산 장치라는
서사가 생긴다.

세 가지 함정을 피해야 한다. 첫째, 승인율을 정확도의 대리변수로 쓰지 않는다.
빠른 승인, 특정 상담원의 습관, 업무량, 정책 변경이 전부 섞여 들어간다.
둘째, 피드백은 정답 라벨이 아니라 잡음 있는 관측이다. 상담원도 틀린다.
따라서 개선 여부는 승인율이 아니라 고정된 골든 60건과 holdout 20건에서
라우팅 정확도, 이슈 macro-F1, 승인 위반율, 근거 없는 주장 비율을 전후 비교해 판단하고
95% bootstrap CI를 붙인다. 셋째, 정책 변경 전에 holdout을 잠근다.

실제 상담원 기록이 없으므로 초기 데이터는 합성 승인·수정·반려 fixture다.
이것으로 파이프라인과 재평가 절차를 검증할 수는 있지만
"상담원 학습으로 실사용 성능이 개선됐다"고 주장할 수는 없다.

## 2-7. 5건의 의존 관계

```
Case / 카탈로그 / 정책 / 처리 이벤트
   │
   ├── [1] 근거·정책버전·결정론적 신뢰 신호 ──┐
   │                                          │ 근거 수준 소비
   ├── [2] 관계 경로·원인 후보 ──> 운영자 검토 우선순위
   │
   ├── [3] 카탈로그 사실·검색 실패 판정 ──┐
   │                                      │ 미충족 수요
   │                                      ▼
   │                              [4] 우선순위 점수화  ← Phase 2로 차단
   │
   └── 승인·수정·반려·최종 판정 ──> [5] 피드백 Analytics
                                          │
                                          ▼
                            오프라인 라우팅 후보 → 골든/holdout 재평가
                                          │
                                          ▼
                              승인된 Registry·policy version
                                          │
                                          ▼
                                    다음 Case 라우팅
```

직접 의존은 3 → 4와 1 → 5 둘이다.
3이 없으면 4의 미충족 수요 항을 계산할 수 없지만, 4를 잘라도 3의 사실 판정과 5의 루프는 살아 있다.
5는 1의 근거 수준을 소비할 때 가장 쓸모 있다.
확신도가 낮은데 승인된 건과 확신도가 높은데 반려된 건이 라우팅 개선의 표적이 되기 때문이다.
2는 1의 근거를 소비할 수 있으나 필수 결합이 아니고, 잘라도 나머지가 죽지 않는다.

4가 Phase 2로 빠지므로 코어가 4 하나 때문에 연쇄로 죽지 않도록 분리해 둔다.
착수 순서는 1 → 3 → 5 → 2이고 4는 계약 설계만 남긴다.

경계는 셋으로 정리된다.

- 1~3의 산출물은 기본적으로 Context Pack과 리포트다.
- 환불·제재·라우팅을 바꾸는 값은 확정 DB fact 또는 승인된 버전 규칙만 허용한다.
- 5는 곧바로 모델이나 라우팅을 갱신하지 않고, 평가 하네스를 통과한 후보만 Registry에 등록한다.

## 2-8. 공통 위험

5건 모두 무게를 분석 쪽으로 옮긴다. v6의 코어는 Case 처리이고 분석은 그 위에 얹히는 층이다.
분석 기능이 늘어 Case 처리 루프의 완성도가 떨어지면 심사에서 잃는 것이 더 크다.
uh 문서의 7:3 원칙을 그대로 적용한다. 코어 일곱, 확장 셋.

## 3-2. Agent Team을 늘리는 기준

v6의 Registry는 Team 수의 상한이 아니다. 다만 등록 가능하다는 사실만으로 새 Team이 정당화되지는
않는다. 기능이 많다는 것은 먼저 기존 Team 내부 tool을 늘릴 근거다.

판정은 두 단계로 고정한다.

1. 에이전트급인가: `FILTER-1(비정형 입력) ∨ FILTER-2(규칙으로 못 적는 판단) ∨ FILTER-3(상황별 도구 조합)` 중 **하나 이상**을 만족하고, 동시에 기존 세 기준인 정답셋 존재·임의 배정 비의존·코어 루프 필요를 **모두** 만족해야 한다. FILTER를 하나도 못 넘기면 tool·룰·배치이고, FILTER를 넘겨도 세 기준 중 하나가 빠지면 채택하지 않는다. (FILTER 셋을 모두 요구하면 배송 이력 조회가 중심인 LOG처럼 정형 입력 기반 Team이 자격을 잃는다.)
2. 별도 Team인가: 에이전트급인 후보 중에서 `권한 경계 × 외부 대기 주체 × 지식 범위 × 실패·재시도 정책`의 네 축 가운데 최소 둘이 ORD·LOG와 실질적으로 다르고, 그 차이를 Team Contract·라우팅·평가셋으로 고정할 수 있어야 한다. 데이터 소유권, 규제 경계, SLA 등급, 실행 위험도는 이 네 축을 확인하는 보조 증거이지 자동 분리 사유가 아니다. 기능 수와 모델 종류만으로는 분리하지 않는다.

이 기준은 가설을 조금 좁힌 것이다. 권한·규제·실행 위험은 권한 경계에, SLA는 외부 대기와 실패 정책에, 데이터 소유권은 지식 범위와 Context Pack에 대체로 들어간다. 별도 Team을 만들더라도 Controller·`TeamExecutorPort`·`TeamResult` 계약은 바꾸지 않는다.

현재 추가 Team은 없다. 판매자 소명과 결제·정산은 위 조건과 데이터 계약이 확보될 때 Phase 2 후보이며,
나머지는 새 Team보다 기존 Team의 tool·룰·배치가 맞다. 이는 “최소 둘이 다르면 새 Team”이라는 필요조건을
충족하더라도 정답셋과 코어 루프가 없으면 1단계에서 탈락한다는 뜻이다.

확장의 비용은 Team 하나마다 다음처럼 늘어난다. 골든셋에 권한·대기·재개·실패·재시도 라벨 축을 추가하고,
라우팅 평가에 오배정·대기 상태·SLA 만료·handoff를 추가한다. Registry 레코드 1개, Team Contract test,
프롬프트 버전과 Context Pack 토큰 예산도 별도로 관리한다. v6의 60건 골든·20건 holdout, 6명·10주라는
범위를 기준으로 한 추정으로, 착수 2개에 Phase 2 Team 1개를 더한 3개가 현실적 상한이다. 4개째부터는
Team당 최소 10~15개 대표 케이스와 라우팅 조합을 추가로 라벨링할 여력이 줄어들어 기존 Team의 회귀 검증을
잠식한다. 이 수치는 계획상 추정치이며 v6의 고정 상한이 아니다.

확장은 다음 최소 실험으로 증명한다. 새 Registry 레코드와 prompt version, 새 골든 케이스만 추가하고,
동일한 Controller·`TeamExecutorPort`·`TeamResult` canonical JSON·평가 harness를 실행한다. contract test는
라우팅→Team 실행→`answer`/`warnings`/`ActionProposal` 정규화→승인 대기→실패·재개를 확인하고, 기존 ORD·LOG
fixture의 결과가 변하지 않는지 회귀 비교한다. 이 실험이 통과하면 추가가 리팩토링이 아니라 등록과 데이터·평가
확장임을 보인다. 실패하면 새 Team을 만들지 않고 기존 tool 또는 배치로 되돌린다.

## 성공 조건

1. 리스크 점수가 실제로 선환불과 소명 우선 경로를 바꾼다
2. SLA 만료가 실제로 Case의 owner와 다음 상태를 바꾼다
3. 외부 holdout, 승인 위반율, 상태 전이, 경로 정확도를 합성 골든과 분리해 보고한다

셋 중 하나라도 빠지면 기능만 많은 CS 데모이지 심사 기준의 에이전틱 시스템이 아니다.

## 남은 결정

- 확신도 산식의 인자 가중치와 캘리브레이션 구간 설계
- 조건부 4건 중 실제로 착수할 항목 (택배비 상수, 재고 스키마, 패션 subset, 제품 ID 매칭)
- Team을 착수 2개에서 늘릴지 여부. 판단 기준은 구현 가능성이 아니라 골든셋 확장 여력
