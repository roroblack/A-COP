## 3. 각 안의 결정적 약점

**uh — 판매자 모드가 두 번째 프로젝트를 부른다.**
온보딩 하나가 4단계 파이프라인(시장 벤치마크 → 정보 수집 → 초안 생성 + 표시광고법 검수 → config 등록)이다.
본인이 SCOPE 규칙으로 3기능을 못 박았지만, 그 3기능 중 첫 번째가 이미 프로젝트 하나 크기다.
여기에 EXT-1(챗봇 내 구매 완결) · EXT-2(VLM 파손 판정) · EXT-3(다국어)까지 붙어 있다.
DEP 규칙 덕분에 잘라내도 본체는 안 다치므로, 실제 위험은 설계가 아니라 **팀이 안 자를 때** 발생한다.

**sw — 차별화가 없다.**
"안전하게 처리하고 감사 로그를 남기며 기업별로 이식된다"는 반박 불가능하지만 동시에 당연하다.
심사에서 "그래서 이 시스템만 하는 게 뭔가"에 답할 문장이 이 문서에는 없다.
Supervisor + 3팀도 v6의 2팀보다 하나 많아 소폭 초과다.
한국어 VOC를 합성으로 채우고 거래 골격을 Olist(브라질)에서 빌리는 선택은 정직하고 합리적이지만,
"한국어 응대 품질을 직접 증명하지 않는다"고 스스로 적어둔 만큼 평가 서사에 구멍이 생긴다.

**jh — 제안한 MVP가 새로운 것을 하나도 추가하지 않는다.**
MVP를 A+B로 잡았는데, A(분류 + 답변 초안 + 확신도 낮으면 사람)와 B(유사 문의 클러스터링·급증 탐지)는
v6에 이미 있는 것이다. 이 아이디어의 고유 가치는 전부 C와 D에 있고, 그 둘은 MVP 밖에 있다.
그리고 C(기획전 제안)는 채점이 불가능하다 — "수요는 있는데 노출 안 된 상품"의 정답셋이 존재하지 않고,
경로 ①(계절 패턴)은 시계열을 합성으로 만들면 우리가 심은 패턴을 우리가 찾아내는 자기예언이 된다.
또한 전체 문서에 Case·상태·승인·에스컬레이션이 없다. 에이전틱함을 증명할 메커니즘이 부재하다.

## 4. 구조적 관찰 — uh와 sw는 직교한다

이게 이번 비교에서 가장 중요한 발견이다.

| | uh의 L0~L3 | sw의 Case 상태 |
|---|---|---|
| 답하는 질문 | 누가 / 어느 권한으로 처리하는가 | 케이스가 어디까지 진행됐는가 |
| 값 | L0 문의 / L1 판매자 / L2 플랫폼 / L3 외부 | new / classified / gathering_evidence / proposed / waiting_approval / resolved |
| 결정하는 것 | 모델 등급, 비용, 승인 권한, 도구 범위 | 다음 행동, 재개 조건, 감사 이벤트 |

같은 것의 다른 표현이 아니다. 둘은 서로 독립이며 합치면 (층 × 상태) 격자가 된다.
`L1 / waiting_external`, `L2 / waiting_approval` 처럼 조합이 의미를 갖는다.

실익이 두 가지다. 하나, 층은 비용·권한 지표로, 상태는 완결성 지표로 **따로 평가**할 수 있다.
둘, uh의 "SLA 초과 시 L2로 자동 전이"가 sw의 상태 기계 위에 조건부 엣지 하나로 얹힌다 —
새 구조를 만드는 게 아니라 기존 그래프에 전이 규칙을 추가하는 일이 된다.

즉 두 안은 합치는 데 드는 비용이 생각보다 작다.

## 5. 권고

### 뼈대 = sw, 차별화 축 = uh, 잎사귀 = jh 트랙 D

**sw를 뼈대로 쓴다.** 확장 용이성과 v6 자산 재사용이 가장 높고, 평가 프로토콜이 이미 서 있다.
Case Lifecycle · Action Proposal 계약 · Port/Adapter · 골드셋/baseline/ablation을 그대로 채택한다.
팀 수는 3개를 유지하되 Seller Quality를 배치 분석 모듈로 얇게 가져간다(v6의 2팀 + 배치 구성과 일치).

**uh의 두 가지만 축으로 얹는다.**
- 층별 비용 전략(L0 소형모델·캐시 → L2 고성능)과 그 지표인 **자동 해결률**.
  이건 실무 CS가 실제로 쓰는 지표이고 측정이 깔끔하며, "좋은 성능 · 적은 비용"을 그림 한 장으로 설명한다.
- **리스크 기반 경로 분기**(선환불 vs 소명 우선). "분석 결과가 시스템 동작을 바꾼다"는 주제 요건의
  가장 강한 증명이며, sw의 상태 기계 위에서는 조건부 엣지 하나로 구현된다.

**jh는 트랙 D(리퍼브)만 흡수한다.** 이유는 세 가지다.
반품 사유는 이미 Case 안에 있어 추가 데이터 수집이 없고, 재판매 가부는 분류 문제라 채점이 가능하며,
무엇보다 **CS 시스템의 출구가 두 개로 대칭이 된다** — 구매자 쪽 출구(L3 외부 절차)와
재고 쪽 출구(리퍼브 재판매). 세 문서 중 아무도 "반품된 물건이 어디로 가는가"를 다루지 않았다.
발표에서 이 대칭은 값이 나가고 구현 비용은 분류기 하나다.

### 잘라내는 것
- uh 판매자 온보딩 전체(초안 생성 · 표시광고법 검수 · 시장 벤치마크) → 스토어 config는 수동 등록
- uh EXT-1 챗봇 내 구매 완결, EXT-2 VLM 파손 판정 → Phase 2
- jh 트랙 C 전체(기획전 제안 3경로) → 채점 불가
- sw의 실제 챗봇/폼 이원화 논쟁 → sw 본인 결론대로 통합 요청 폼 하나

### 살려두는 것
sw의 스토리보드 목업은 안이 확정된 뒤 그 안의 시나리오로 갱신해서 계속 쓴다.
팀 합의와 발표 리허설에 그대로 재사용되는 유일한 산출물이다.

## 6. 남은 결정 두 가지

1. **한국어 데이터 전략** — sw는 Olist(포르투갈어) 거래 골격 + 합성 한국어 VOC를 제안했다.
   uh는 AI Hub 쇼핑몰 리뷰를 스토어별 배정하는 안이다. 둘 중 하나로 정해야 하며,
   합성 비중이 커질수록 "우리가 만든 정답을 우리가 맞힌다"는 비판에 노출된다.
   외부에서 온 holdout을 최소 한 벌 확보하는 것이 조건이다.

2. **차별화 문장 한 줄** — 세 사람의 축 중 발표 첫 슬라이드에 올릴 문장을 하나만 골라야 한다.
   현재 후보는 "상태와 리스크 분석이 다음 행동과 승인 경로를 바꾼다"(uh 축)가 가장 강하다.
   sw의 이식 가능성과 jh의 수요 발굴은 그 아래 근거로 배치한다.
