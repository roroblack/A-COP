# COLLEAGUE.SKILL·AGENTS.md·Codified Context 적용 검토

검토 기준은 사용자가 제공한 네 가지 연구 요약과 2026-08-18 저장소 실측이다. 연구의 원문을 다시 확인한 것이 아니므로 수치와 결론은 제공된 요약의 범위에서만 사용한다.

## A. 세 층 구조의 현재 매핑

현재 저장소는 세 층 구조를 부분적으로 갖고 있지만, 층별 경계가 아직 정리되어 있지 않다.

| 층 | 이 프로젝트에서 맡을 역할 | 현재 파일의 매핑 | 판단 |
|---|---|---|---|
| 1층 헌법 | 모든 Codex 세션이 알아야 하는 작업 원칙, 아키텍처의 짧은 요약, 변경·검증·승인 규칙 | 공통 루트 헌법은 없음. `final_project_cs/CLAUDE.md` 213줄, `final_project_sample/CLAUDE.md` 212줄, `final_project_ui/CLAUDE.md` 78줄이 각각 존재 | 코드 디렉터리별 지침에 가깝다. 세 파일을 합쳐 1층으로 만들면 중복과 오래된 사실을 함께 상주시킬 위험이 있다 |
| 2층 도메인 전문가 | Core, 코드 프로젝트, 팀 모듈처럼 특정 작업에서만 필요한 실행 지침과 계약 | 각 프로젝트의 `CLAUDE.md`, 각 프로젝트의 `RULE.md`, `docs/handoff/`, `docs/plans/`, 팀 구성·계약 문서 | 현재 구조에서 가장 가까운 층이다. 다만 Core·팀별 전문가로 쪼개져 있지 않고 프로젝트별 지침과 상태 보고가 섞여 있다 |
| 3층 지식 기반 | 과거 결정, 근거, 상세 설계, 작업 기록을 필요할 때 검색하는 저장소 | `program/research/`의 76개 파일, `program/research/index.md`, `program/plan/archive/`, `program/briefing/archive/`, 코드의 `docs/history/`, `knowledge/` | 대부분 이 층이다. `program/research/index.md`는 지식 자체보다 탐색 색인·현재 기준 사실 표의 역할을 한다 |

`program/plan/A-COP_구현계획서_v8.md`는 어느 한 층으로 전부 넣기 어렵다. §0~§0-2의 상태·요약·절 색인은 1층 후보의 재료지만, 전체 문서는 42절·1,441줄로 계약·DDL·평가·일정·상세 구현 명세를 모두 포함한다. 따라서 전체를 매 세션 읽히는 헌법으로 두면 연구가 지적한 과도한 context의 문제에 가까워진다. 전체 계획서는 3층의 정본 또는 2층 전문가가 참조하는 설계 명세로 두고, 1층에는 짧은 요약과 정본 포인터만 두는 편이 맞다.

연구의 약 660줄은 목표 상한에 가까운 참고치이지 채워야 할 분량은 아니다. 현재는 공통 1층이 없고, §0-2 색인은 계획서 안의 약 47줄짜리 탐색 표일 뿐 660줄 근처가 아니다. 세 CLAUDE.md를 합산해도 503줄이지만, 그것은 공통 헌법 한 개가 아니라 서로 다른 디렉터리 지침의 합이다. 이 수치를 맞추기 위해 문서를 늘릴 근거는 없다. 이 프로젝트의 1층은 660줄보다 짧아도 되며, 실제로는 헌법적 규칙·아키텍처 요약·오케스트레이션 규칙·정본 경로만 담아야 한다.

현재 구조에서 특히 주의할 점은 정본의 일관성이다. `program/research/index.md`는 68개 파일을 추적한다고 쓰지만 사용자가 제시한 실제 `program/research/` 파일 수는 76개다. 또 저장소에서 읽은 `final_project_cs/CLAUDE.md`에는 DoD 28 표기가 남아 있다. 따라서 1층을 새로 만들기 전에 “현재 값” 표와 각 코드 지침이 같은 정본을 가리키는지 확인해야 한다.

## B. AI 자동 생성 문서가 이번 사례에 해당하는가

이번 사례는 연구가 경고한 실패 사례에 해당할 가능성이 있다. 다만 “AI가 초안을 만들었다”는 사실만으로 실패라고 단정할 수는 없다. Gloaguen 요약의 핵심 구분은 생성 주체가 아니라 사람의 검수·정제 여부와 문서의 범위다.

`program/research/index.md`는 현재 기준 사실, 정본 경로, 확인일, 근거 파일을 명시한다는 점에서 단순한 장문 context 자동 생성보다 안전한 형태다. `program/plan/` §0-2 색인도 42절을 찾기 위한 탐색 장치라면 범위가 좁고 유용하다. 반면 다음 조건에서는 위험하다.

- 사람이 정본 파일과 대조하지 않고 AI의 파일 목록·팀 목록·DoD 수를 사실로 승인하는 경우
- 색인이 “정본”과 “작업 기록”을 구분하지 않거나, 오래된 문서의 결론을 현재 사실로 승격하는 경우
- 절 번호·팀명·DoD 수처럼 여러 문서에 반복되는 값을 자동 복사만 하고 존재 여부와 충돌 여부를 검사하지 않는 경우
- 76개인 실제 `program/research/`를 68개로 적는 것처럼, 색인의 범위 자체가 틀린데도 색인을 신뢰하는 경우

오늘의 §337 복사 사고, Response Generation & Review 누락, DoD 18→28→29의 낡음은 모두 “자동 생성 문서를 검수하지 않고 context로 재사용할 때” 생길 수 있는 종류의 오류다. 특히 현재 저장소 실측에서 `final_project_cs/CLAUDE.md`에 DoD 28이 남아 있으므로, 29로 고친 한 파일이 있어도 체계 전체가 검수됐다고 볼 수 없다.

이번 사례가 허용 가능한 조건은 네 가지다. 첫째, 사람이 정본과 대조해 승인한다. 둘째, 색인은 좁은 목적의 항해 도구로 유지한다. 셋째, 각 사실에 정본·확인일을 붙인다. 넷째, 새 정보·중복·모순을 구분해 모순은 자동 확정하지 않는다. 이 조건이 충족되기 전까지 `program/research/index.md`와 §0-2는 “검수 전 AI 초안”이 아니라 “사람이 확인해야 하는 보조 문서”로 취급해야 한다.

## C. merger.md 원칙을 현재 문서 작업에 적용하는 방법

현재의 Codex 프롬프트 방식에는 다음 네 단계를 추가해야 한다.

1. 변경 전 정본과 보존본의 결론을 먼저 나열한다.
2. 새 내용마다 보완, 중복, 모순 중 하나를 표시한다.
3. 보완은 기존 결론 아래에 증분으로 추가하고, 중복은 새 문장을 만들지 않는다.
4. 모순은 최신 파일이라고 임의 결정하지 않고 사람에게 확인할 항목으로 남긴다.

여기서 “추가만”은 문서를 절대로 수정하지 않는다는 뜻이 아니다. 정정이 필요할 때는 기존 결론을 조용히 덮어쓰지 말고, 어떤 결론이 왜 바뀌었는지 변경 기록과 정본을 함께 갱신한다는 뜻으로 적용하는 것이 적절하다. 기존 결론을 보존본에 남기는 현재 `program/plan/archive/` 방식은 이 원칙과 잘 맞지만, 본문 병합 때의 충돌 분류가 별도 절차로 보장되지는 않는다.

오늘의 사고에 대한 판단은 다음과 같다.

- §337: append-only 원칙만으로는 잡히지 않는다. 잘못된 참조도 “새로운 증분”으로 추가될 수 있기 때문이다. 병합 직후 모든 `§숫자`가 실제 절에 존재하는지 확인하는 참조 검사가 함께 있어야 잡힌다.
- Response Generation & Review 누락: v7·v7.1·v8의 Team 목록을 집합으로 비교하고, 새 Team을 보완 또는 모순 후보로 분류했다면 걸릴 가능성이 높다. 단순 문장 추가만 했다면 누락될 수 있다.
- DoD 18→28→29 낡음: 정본의 수와 각 CLAUDE.md의 수가 충돌하는 순간 모순으로 사람에게 물었어야 한다. 현재처럼 `final_project_cs/CLAUDE.md`에 28이 남은 상태는 이 절차가 끝나지 않았다는 신호다.

따라서 v7→v7.1→v8 병합의 보존본·변경 요약은 좋은 기록이지만, COLLEAGUE.SKILL 방식에 충분히 부합한다고 보기는 어렵다. 다음 병합부터는 “추가 내용 / 기존 결론 / 충돌 여부 / 사람 확인 필요 여부”를 짧은 병합 기록으로 남기는 정도가 현실적이다.

## D. 10주 일정에 넣을 문서 검토와 드리프트 확인

선행과 공식 1W~9W를 합쳐 10주로 보고 2주 주기를 적용하면, 전체 검토는 5번이 적절하다. 시점은 2주차, 4주차, 6주차, 8주차, 10주차 종료 시점이다. 각 회차는 30~45분으로 제한한다. 코드가 바뀐 날의 관련 문서 갱신은 별도로 즉시 수행한다. 10주차 검토는 최종 정리와 겹치므로 새 체계를 설계하는 시간이 아니라 정본·코드·제출물의 일치 여부를 확인하는 시간으로 쓴다.

GitHub Actions가 없는 현재는 자동 드리프트 감지기를 새로 만들 필요가 없다. 매주 또는 변경이 큰 세션 뒤에 다음 수동 절차를 한 사람이 실행하면 된다.

- `git diff --name-only`로 바뀐 코드 경로를 확인하고, 해당 경로의 `CLAUDE.md`, `RULE.md`, handoff·evidence 문서가 갱신됐는지 본다.
- 정본 표의 반복 사실(기준선 v8, Team 목록, DoD 29, Docker 단계, 일정)과 `rg` 검색 결과를 대조한다.
- `§337` 같은 존재하지 않는 절 번호, 누락된 Team명, 18·28처럼 오래된 DoD 수를 검색한다.
- 발견한 불일치는 현장에서 임의로 덮어쓰지 말고 “정본 / 충돌 문서 / 판정 / 확인자 / 날짜” 네 칸의 짧은 기록으로 닫는다.

이 절차는 드리프트 감지기의 완전한 대체가 아니라 6명·10주 프로젝트에서 비용 대비 충분한 수동 통제다. 핵심은 도구의 자동화 정도보다 매 검토 때 같은 항목을 반복해서 확인하는 것이다.

## E. 착수 2일차의 이번 주 판단

이번 주에 할 만한 것은 세 가지다.

1. 공통 1층을 바로 660줄로 만들지 말고, 사람이 승인할 최소 항목만 정한다. 헌법적 규칙, 짧은 아키텍처 요약, 정본 경로, 문서 병합·검증 규칙의 목록을 먼저 확정한다.
2. `program/research/index.md`, `program/plan/v8` §0-2, 세 CLAUDE.md를 대상으로 기준선 v8, 현재 Team 목록, DoD 29, 일정, Docker 단계만 수동 대조한다. 특히 현재 읽힌 `final_project_cs/CLAUDE.md`의 DoD 28 표기를 판정 대상으로 삼는다.
3. 다음 Codex 문서 작업 프롬프트에 증분 병합 표와 “모순이면 사람 확인” 단계를 넣고, §번호 존재·Team 집합·DoD 수 세 가지를 작업 종료 전에 확인한다.

이번 주에 하지 말아야 할 것은 세 가지다.

1. 연구의 19개 도메인 전문가와 MCP 기반 34개 지식 문서를 그대로 복제하지 않는다. 현재 규모에서 필요한 복잡도인지 검증되지 않았다.
2. `program/research/` 76개 파일, 계획서, 브리핑, 세 코드 프로젝트를 한 번에 재분류·이동·통합하지 않는다. 문서 체계 개편 자체가 코드 착수보다 큰 변경이 될 수 있다.
3. AI가 색인·헌법·드리프트 검사기를 자동 생성하고 사람 승인 없이 정본으로 채택하지 않는다. 이번 저장소에서 이미 색인 파일 수와 CLAUDE.md의 DoD 수가 일치하지 않는 정황이 확인됐다.
