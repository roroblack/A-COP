이 문서는 공식 WBS와 A-COP 설계를 한 표로 연결한 작업 문서다. 공식 산출물의 주차와 날짜는 `program/research/_WBS원본_2026-08-17.md`를 기준으로 했다. 실제 구현 상태는 `final_project_sample/CLAUDE.md`의 2026-08-16 상태표를 기준으로 했다.

## 2. 공식 산출물과 우리 설계가 어긋나는 지점

### 2-1. 데이터 전처리 결과서·머신러닝/딥러닝 학습결과서·학습한 ML/DL 모델

우리 구조의 핵심 실행은 LLM API 호출과 Agent Team orchestration이다. 따라서 LLM API 호출 자체를 학습한 ML/DL 모델이라고 제출하지 않는다. **데이터 전처리 결과서**에는 CLAUDE에 있는 PII masking, Case fixture, knowledge documents 25건, knowledge chunks 300건, metadata·embedding 적재와 RAG corpus 품질 게이트를 담는다. 다만 RAG corpus v5가 재작업 중이므로 최종 인수는 확인 필요다. **머신러닝/딥러닝 학습결과서**에는 학습 결과 대신 v7 §27의 A/B/Proposed 평가와 Proposed+FT 비교 경로를 구분해 기록한다. 현재 확인된 것은 LLM API 기반 평가 540 관측이며, 파인튜닝 결과는 확인 필요다. **학습한 ML/DL 모델**은 자체 학습 모델이 없으면 “해당 없음”으로 제출할지 확인 필요로 남긴다. 강사가 학습 모델을 필수로 요구하면 v7 §27의 파인튜닝 경로를 별도 범위로 확정해야 한다.

### 2-2. 자체 sLLM 인공지능 (3, 4번 팀)

WBS 원본은 12번 산출물을 “3, 4번 팀”으로 적고, 6팀 행에도 포함한다. 6팀 필수 여부는 원본에서 확정되지 않는다. **필수가 아닌 경우**에는 자체 sLLM을 제출 범위에서 제외하고, v7 §27의 파인튜닝 경로를 선택 항목으로 표시한다. **필수인 경우**에는 공개 1차 모델과 알파 2차 모델을 같은 golden/holdout에서 비교하는 v7 §27의 경로를 5W 이후 별도 작업으로 확정한다. 어느 갈래가 적용되는지는 강사 확인 필요다.

### 2-3. 벡터DB/GraphDB 구축 결과서

5W 마감에 맞춰 “물리적인 외부 GraphDB 구축”으로 확대하지 않는다. v7은 `GraphStorePort`를 두고 MVP 구현체로 `SqlGraphAdapter`를 사용하며, PostgreSQL JOIN·재귀 CTE 기반 관계 조회를 계획한다. CLAUDE에는 이 Port와 Adapter가 구현되어 있고 Controller가 Port를 경유하는 상태가 기록되어 있다. 따라서 제출물은 PostgreSQL·pgvector 기반 Vector RAG와 `GraphStorePort`·`SqlGraphAdapter`의 구성, Case→Issue→Policy·Issue→Team·Case→Action 관계 질의 fixture 결과다. 외부 AGE·Neo4j Adapter를 5W까지 구축해야 하는지는 원본과 v7만으로 확정할 수 없으므로 확인 필요다. DoD 21의 정확성 판정이 부분 상태로 남아 있으므로 5W 전에 세 관계 질의의 evidence를 완성한다.

## 3. 리스크와 완충

4W는 9/18~9/28의 11일이다. 이 구간은 인력이 비는 구간으로 단정하지 않고, 3W에서 드러난 RAG corpus·중간발표 피드백·통합 결함을 처리하는 보정 구간으로 사용한다. 4W에 새 기능을 시작하지 않고 5W 산출물의 근거를 먼저 닫는다.

8W는 10/21~10/24의 4일이다. 이 기간에는 기능을 추가하지 않는다. 최종 PT·소스코드·시연영상의 재현 절차를 동결하고 seed Case, 승인, trace, evidence를 반복 확인한다. 7W와 10/21이 겹치므로 7W 말에 최종 발표 소재를 확정한다.

중간발표는 9/15에 다음 한 흐름을 보여준다. 고객 메시지가 Case가 되고, 분류와 Context Pack 구성이 수행되며, Billing 또는 Technical Team이 `TeamResult`와 `ActionProposal`을 반환한다. 고위험 작업은 `waiting_approval`에서 멈추고 운영 UI에서 근거·승인·audit을 확인한다. 분류 실패와 degraded Context는 자동 성공으로 말하지 않는다. A2A 실제 왕복, Graph Adapter 비교, 파인튜닝 결과는 완료되지 않았다면 시연 범위에 넣지 않고 현재 상태를 명시한다.

일정이 다시 줄어들면 다음 순서로 버린다.

1. GraphStorePort의 외부 Adapter 비교와 추가 Graph 시각화를 버린다. Port와 `SqlGraphAdapter`의 필수 관계 질의는 남긴다.
2. A2A Remote Team의 확장 시나리오를 버린다. 이미 있는 경계와 더미 검증을 남기고 실제 왕복의 추가 범위는 확인 필요로 둔다.
3. MCP tool 추가와 Commerce Ops 확장을 버린다. 현재 Case·승인·감사·평가 흐름을 우선한다.
4. 화면 장식과 추가 Team을 버린다. Billing/Technical과 VOC의 현재 계약, 운영 UI, 평가 harness를 남긴다.

이 순서는 v7의 “GraphRAG는 실패하면 버린다”는 원칙과 Registry·Team 확장은 평가 여력이 있을 때만 한다는 원칙을 일정에 맞춰 적용한 것이다.

## 4. 브리핑 HTML에 더 넣으면 좋을 것

`A-COP_브리핑_v7.html`의 목차에는 제품 구조, 핵심 그림, 아키텍처, Workflow, 데이터 구조, ERD, 외부 AI 연동, 할루시네이션 방어, A2A 실물, GraphRAG, 구현 로드맵, 역할 분담, 심사 Q&A, 엑셀 요약이 이미 있다. 아래 제안은 그 내용을 반복하지 않는 항목이다. 공수는 파일 수정 기준의 상대 크기로 적는다.

### 4-1. 공식 21건 제출 체크표

- (a) 심사자는 설계의 완성도와 공식 제출물의 누락 여부를 한 번에 확인해야 한다.
- (b) 현재 `10. 구현 로드맵` 뒤에 넣는다.
- (c) 공수는 중이다. 21건에 주차·담당·링크·상태 열을 추가하고 제출 폴더 링크를 연결해야 한다.

### 4-2. 중간발표와 최종발표의 시연 범위 비교

- (a) 9/15에 보여줄 기능과 최종 시연 기능을 구분해야 중간발표에서 미완성 항목을 과장하지 않는다.
- (b) `10. 구현 로드맵`의 `주차별 권장 일정` 뒤에 넣는다.
- (c) 공수는 작다. 두 발표의 화면 순서와 제외 항목을 한 표로 정리하면 된다.

### 4-3. 재현 가능한 demo runbook

- (a) 발표 당일에는 seed Case, URL, 승인 입력, 정상 결과와 실패 결과를 같은 순서로 재현해야 한다.
- (b) `4. 핵심 Workflow` 뒤에 넣는다.
- (c) 공수는 중간이다. CLAUDE에 기록된 고정 seed Case와 운영 UI 경로를 실제 실행 순서로 묶어야 한다.

### 4-4. DoD evidence 인덱스

- (a) “완료”라는 문장보다 테스트·로그·화면·fixture가 어디에 있는지가 심사에 직접 필요하다.
- (b) `9. 외부 AI 연동`의 `할루시네이션 방어` 뒤에 넣는다.
- (c) 공수는 중간이다. v7 §27의 28개 항목을 evidence 파일, 실행 명령, 화면 경로에 연결해야 한다.

### 4-5. 현재 한계와 확인 필요 목록

- (a) RAG corpus 재작업, 사람 judge agreement 미측정, A2A 실제 왕복, 파인튜닝 여부를 구현 완료처럼 읽히지 않게 해야 한다.
- (b) `심사 Q&A` 앞에 넣는다.
- (c) 공수는 작다. CLAUDE 상태표의 부분·미착수 항목을 발표용 문장으로 정리하면 된다.

### 4-6. 산출물의 데이터·모델 경계 설명

- (a) LLM API 사용 구조에서 전처리·평가·학습을 혼동하면 3W 산출물의 신뢰도가 떨어진다.
- (b) `9. 외부 AI 연동` 뒤와 `12. 엑셀 입력용 요약` 앞에 넣는다.
- (c) 공수는 작다. API 호출, RAG corpus 처리, 평가 harness, 파인튜닝을 네 칸으로 나누어 현재 상태를 표시하면 된다.

### 4-7. 실패 시 화면과 운영자 인계 표

- (a) A-COP의 핵심은 자동 응답보다 `waiting_*`, `unknown`, `escalated`, 승인 경계를 확인할 수 있는 운영 구조다.
- (b) `할루시네이션 방어` 뒤에 넣는다.
- (c) 공수는 중간이다. 분류 실패·degraded Context·provider timeout·승인 거부를 상태, 화면, 다음 담당자로 연결해야 한다.
