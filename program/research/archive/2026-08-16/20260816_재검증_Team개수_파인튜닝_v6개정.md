## 2. Team 개수 기능 판정

v6 §7의 기준은 업무 이름이 아니라 **Capability·책임·권한·지식·Tool 경계**다. 따라서 “주문 업무”와 “배송 업무”처럼 업무가 다르다는 이유만으로 Team을 나누지 않고, 경계를 합쳤을 때 사라지는 것을 함께 본다.

| Team | 고유 책임·권한·지식·Tool | 다른 Team과 합칠 수 있나 | 합치면 잃는 것 | 판정 |
|---|---|---|---|---|
| Catalog & Verification | 외부 Item/SKU/Variant, 가격, 규제·품목 적격성 확인. 카탈로그·외부 검색·가격/규제 검증 Tool | Procurement와 인접하지만 합치지 않는 편이 낫다 | 검증되지 않은 SKU가 구매 흐름에 섞이고, 규제 판단과 구매 재시도 책임이 한 경계에 들어간다 | 독립 Team |
| Procurement | 공급처 선택, Quote·구매 가능성, 공급처 재시도·대체. 공급처 Capability/Quote/재고 Tool | Order & Payment와 합칠 수 있다 | 공급처 조달 실패와 내부 결제·주문 상태의 원인이 분리되지 않아 재시도·감사·승인 경계가 흐려진다 | 독립 Team. 단, 이번 구현에서는 Order & Payment와 한 계약으로 묶을 수 있다 |
| Order & Payment | 내부 주문 상태, 결제 승인 상태, 취소·중복·고액 주문 판단. 주문/결제 상태 Tool | Procurement와 합칠 수 있다 | 구매 Quote와 결제 권한의 분리가 약해지고, 금액·idempotency·approval 테스트 축이 섞인다 | 독립 Team |
| Fulfillment & Logistics | 발주 이후 운송장·배송 지연·분실·통관 상태. 운송장/물류 조회·SLA Tool | Order & Payment와 합칠 수는 있다 | 주문이 성립한 뒤의 외부 대기와 배송 재시도, 지연 Case 생성 책임이 주문 상태에 종속된다 | 독립 Team |
| Return & Refund | 반품 정책·증빙·외부 반품 Case·환급 제안. 정책·Evidence·Return Adapter Tool | Order & Payment와 합치면 구현은 단순해진다 | 청약철회, 증빙, 고객 환급과 공급처 회수의 이중 원장·분쟁 경계를 잃는다 | 독립 Team |
| VOC & Store Manager | 이상징후·실패율·공급처 성능·backlog 감시, 리포트와 Task 위임. 집계·관측·알림 Tool | 모든 운영 Team과 결합 가능 | 특정 도메인 책임이 아니라 전체 관측 축이므로, 개별 Team에 넣으면 전역 시야와 독립 KPI를 잃는다 | 독립 Team으로 만들지 않고 Coordination/Feedback Analytics 운영 모듈로 둔다 |

### 적정 수와 10주 구현 수

기능상 적정 수는 **5개**다. Catalog, Procurement, Order & Payment, Fulfillment & Logistics, Return & Refund는 각각 지식·Tool·실패·승인 경계가 다르다. VOC & Store Manager는 Team처럼 부를 수 있는 운영 기능이지만 v6의 Team 분리 원칙을 적용하면 독립 Team보다 배치·관측 모듈이 맞다.

이번 10주에 실제로 만들 수 있는 수는 **3개까지**다. 기존 v6의 Billing/Technical/Feedback 축을 훼손하지 않는 범위에서, 쇼핑몰에서는 `Catalog & Verification`, `Order & Payment + Procurement` 통합 구현, `Fulfillment & Logistics`를 우선한다. Return & Refund는 증빙·정책·이중 원장까지 포함하면 별도 검증 축이 커지므로 Registry 계약과 Mock만 남긴다. VOC & Store Manager는 기존 Feedback Analytics·운영 UI에 연결한다. 이후 5개를 Registry에 독립 등록하되, Registry 등록과 실제 구현을 같은 말로 세지 않는다.

## 3. 파인튜닝 2단계 실행 계획

### 3.1 1차: 공개 데이터셋 사전 튜닝

사실문서 4번에 있는 데이터셋 중 우선순위는 다음과 같다.

| 선택 | 쓰임 | 확인할 것 |
|---|---|---|
| Bitext customer-support-llm-chatbot-training-dataset | `cancel_order`, `check_refund_policy`, `get_refund`, `track_refund`가 우리 주문·환불 Case와 직접 겹친다 | 대부분 영어이므로 한국어 번역·재작성 품질과 원 라이선스 확인 필요. 이 요건을 갖추면 사용한다 |
| Kaggle Customer Service Conversations | 주문조회·환불요청·주문취소·상품불만·계정문제의 표현 다양화 | Kaggle 이용 조건과 데이터 라이선스, 개인정보·재배포 조건 확인 필요. 이 요건을 갖추면 사용한다 |
| 기타 HuggingFace 데이터셋 | 멀티턴 및 전자상거래 표현의 보조 자료 | 합성 여부, 도메인 적합성, 라이선스 확인 필요. 주 학습셋이 아니라 보조셋으로 사용한다 |

1차의 목표는 지식을 모델 파라미터에 넣는 것이 아니다. 사실문서 5번의 원칙대로 다음 세 가지만 학습한다.

1. A-COP의 Case/intent/issue/action proposal 출력 스키마를 안정적으로 지키기
2. 주문·취소·환불·배송·증빙의 도메인 어휘와 한국어 표현에 적응하기
3. 정책을 단정하지 않고 근거·승인·보류를 표시하는 응답 톤 익히기

정책의 진실값과 현재 주문 상태는 계속 RAG·Context Pack·DB가 제공한다. 공개 데이터로 새로운 환불 정책을 암기시키는 방식은 목표에서 제외한다.

### 3.2 2차: 알파 실데이터 소규모 추가 튜닝

내부에서 만든 주문·배송·문의·반품 Case와 알파 Case를 비식별화하고, 성공·실패·보류·사람 수정 결과를 함께 저장한다. 500건 미만이면 epoch 1~2회로 제한한다.

2차에서 얻는 것은 다음 세 가지다.

| 얻는 것 | 수집 방식 |
|---|---|
| 실제 고객 표현 | 팀원·알파 사용자의 원문, 오타, 짧은 질문, 멀티턴 후속 질문을 원문과 라벨로 보존 |
| 우리 정책 어휘 | 실제 상품·주문·배송·환불 상태명, 내부 승인 문구, Case event 명칭 |
| 실패 유형 | 잘못된 intent, 누락된 tool 호출, 근거 없는 단정, 승인 누락, 대기·재개 실패를 실패 라벨로 저장 |

실데이터도 공개 데이터와 같은 세 목표, 즉 출력 스키마·도메인 어휘·톤에만 사용한다. 주문·가격·환불의 현재 사실은 모델이 아니라 시스템 Context에서 읽는다.

### 3.3 평가와 v6 평가 체계 연결

각 단계마다 고객지원 태스크의 held-out set을 분리한다. 태스크 지표는 intent accuracy, issue macro-F1, 스키마 유효성, tool-call 정확도를 기록하고, LLM-as-judge는 **충실도·tool 호출 정확도·지시 준수**를 판정한다. judge rubric은 v6의 correctness, policy_grounding, next_action, safety, personalization과 매핑한다.

파인튜닝 모델은 별도의 “새 제품”이 아니라 **Proposed의 모델 변형**이다. 따라서 기본 Proposed와 `Proposed+FT`를 같은 golden 60건과 보존된 holdout 20건에서 비교한다.

| 비교 | 의미 |
|---|---|
| Baseline A | 단일 LLM + 원문 prompt + 최소 DB 조회. 파인튜닝하지 않음 |
| Baseline B | 고정 workflow/rule + policy retrieval. 파인튜닝하지 않음 |
| Proposed | v6의 Case lifecycle + Context Broker + Team + approval + 경계 |
| Proposed+FT | 위 Proposed 구조에서 모델만 1차/2차 튜닝 모델로 교체 |

따라서 기존 A/B/Proposed 축은 유지하고, `Proposed+FT`라는 **paired ablation 축 하나**를 추가한다. golden 60건과 holdout 20건의 크기를 바꾸지 않으며, holdout으로 프롬프트나 학습 데이터를 다시 고치지 않는다. 비교는 task·grounding·tool-call·지시 준수와 비용·지연을 함께 보고, 모델 향상이 오케스트레이션 향상으로 잘못 해석되지 않게 분리한다.

### 3.4 비용과 일정

사실문서 5번의 기준은 RTX 4070 Ti 한 장으로 7B 모델을 반나절에 도메인 특화할 수 있다는 것이다. 이를 바탕으로 1개 7B 기반 LoRA/QLoRA 실험의 계획 추정은 다음과 같다.

| 구분 | 실소요 추정 | 내용 |
|---|---:|---|
| 생성 | 1일 | 데이터 정제·한국어 재작성 샘플링, 1차 튜닝, 2차 튜닝 1회. GPU 실행 자체는 단계당 반나절 기준 |
| 검증·통합 | 2일 | held-out 평가, judge 실행, schema/tool-call 회귀, Proposed 교체점과 보고서 연결 |
| 대기 | 1일 | GPU 예약·실행 대기, 실패 재실행 여유. 달력상 병렬화 가능 |
| 합계 | 4 작업일/최대 5 달력일 | 모델 1종·학습 설정 1개 기준. 여러 rank/모델을 비교하면 증가 |

10주에 순증으로 넣지 않는다. 파인튜닝을 넣는 대신 다음을 이번 범위에서 뺀다.

| 뺄 항목 | 이유 |
|---|---|
| 두 번째 외부 Marketplace Adapter | 파인튜닝보다 오케스트레이션·Case 증명이 우선이다 |
| Storefront 시각 polish와 B2B 패키징 일부 | 모델 비교 결과와 핵심 실행 경계를 검증하는 데 직접 필요하지 않다 |
| Return & Refund의 실연동 | 증빙·환급·이중 원장 오류를 얕게 구현하지 않기 위해 Registry/Mock으로 이동한다 |
| 6개 Team 모두의 독립 구현 | 기능상 5개를 인정하되 이번 실제 구현은 3개로 제한한다 |

### 3.5 하지 말아야 할 것

파인튜닝이 A-COP의 핵심 증명을 대체하지 않게 한다. A-COP의 증명 대상은 모델이 고객지원 문장을 더 그럴듯하게 쓰는지가 아니라 **Case lifecycle, Context Broker, Team routing, approval, idempotency, WAIT/RESUME와 경계가 함께 작동하는가**다. `Proposed+FT`가 좋아져도 orchestration 회귀 테스트와 v6의 A/B/Proposed 비교가 통과하지 않으면 채택하지 않는다.

## 4. v6 개정 필요성 양방향 판정

| 충돌 지점 | 확장안을 고쳐야 하나 | v6를 고쳐야 하나 | 판정과 이유 |
|---|---|---|---|
| MCP read-only 3개 고정 | 확장안의 결제·환불·주문 상태 변경 쓰기는 여전히 승인 경로로 보낸다. 다만 Case 생성·배송조회 요청처럼 돈·주문 상태를 바꾸지 않는 요청까지 금지하는 표현은 줄인다 | 고치는 편이 낫다. `CLAUDE.md` §0.2의 이유는 되돌릴 수 없는 side effect 보호인데, 모든 쓰기가 같은 위험은 아니다 | **v6 개정 필요.** read/write 이분법 대신 `read`, `reversible operational write`, `financial/order-state side effect`를 구분하고, 낮은 위험 쓰기는 scope·idempotency·audit·rate limit 조건 아래 허용한다 |
| 외부 REST 정확히 5개 | 확장안은 5라는 숫자를 억지로 맞추기보다 capability별 endpoint를 계약으로 제시한다 | v6와 handoff에는 5개를 반드시 지켜야 하는 설계 논리보다 구현·평가 범위 통제의 의미가 강하다. v6 본문은 REST/OpenAPI를 우선한다고 하지만 5의 불변 이유나 독립적인 자원 모델을 제시하지 않는다 | **v6 개정 필요.** 5는 아키텍처 상수가 아니라 당시 MVP 범위 숫자라고 명시한다. endpoint 수는 도메인 계약·권한·평가 가능성으로 결정한다 |
| Team이 side effect를 실행하지 않음 | 확장안의 `Return Team → Marketplace Return Adapter 직접 호출`은 고치고 `ActionProposal`과 승인·Gateway 경로로 돌린다 | 고칠 필요가 없다. 돈·주문·환불·외부 반품은 되돌리기 어렵고, Team 내부 호출은 audit·idempotency·권한 검사를 우회할 위험이 있다. CLAUDE §0.2와 v6 §7의 경계가 같은 문제를 막는다 | **확장안 수정. v6 유지.** 단, 조회와 실행 제안, 실행 승인을 구분해 Team이 충분히 유용하게 남도록 한다 |

### v6를 고친다면 제안하는 문장

`CLAUDE.md` §0.2의 MCP 부분은 다음처럼 바꾼다.

> MCP는 기본적으로 read-only이며, Case 생성·배송조회 요청·철회 가능한 운영 메모처럼 돈·주문 상태·권리를 변경하지 않는 reversible operational write는 별도 scope, idempotency key, audit log, rate limit, 실패 시 재처리 규칙을 갖춘 경우에 한해 허용한다. 결제·환불·주문 상태 변경·구독 변경·권한 부여는 여전히 REST/Gateway와 Human Approval 경로로만 실행한다.

v6의 REST 문장은 다음처럼 바꾼다.

> MVP의 외부 REST surface는 평가 가능한 최소 계약으로 시작하며 현재 기준선은 5개 endpoint다. 5는 아키텍처 상한이 아니고, 새 endpoint는 독립 resource·scope·idempotency·audit·평가 fixture가 있을 때 Registry/계약 버전으로 추가한다.

v6 §7의 side effect 문장은 다음처럼 유지·보강한다.

> Team은 외부 side effect를 직접 실행하지 않는다. Team은 근거와 범위를 담은 `ActionProposal`만 반환하고, Gateway가 scope·approval·idempotency·audit를 확인한 뒤 실행한다. 조회·분석·제안은 Team의 책임이며, reversible operational write도 이 실행 경계를 우회하지 않는다.

## 5. 내부 자가주문 방식 검토

### 5.1 무엇을 얻는가

팀원 6명이 각자 자기에게 필요한 물건을 구매대행 프로그램으로 주문하면, 내부 단계에서 실제 주문 lifecycle을 만들 수 있다. 주문 생성, Quote/가격 변화, 결제 상태, 배송조회, 배송 지연, 문의, 취소·반품 요청을 모두 Case와 이벤트로 남긴다. 다만 “주문 1건”과 “Case 여러 개”를 중복해 거래 건수로 세지 않도록 주문·배송·문의·반품을 별도 집계한다.

| 방법 | 주문 수 추정 | 주문당 추가 Case 추정 | 알파 이전 현실적 범위 |
|---|---:|---:|---:|
| 6명 × 1회 | 6 | 0~2개 | 주문 6, Case 0~12 |
| 6명 × 2회 | 12 | 4~12개 | 주문 12, Case 4~24 |
| 6명 × 3~5회 | 18~30 | 6~30개 | 주문 18~30, Case 6~60 |

계획상 보수적인 목표는 **주문 12~30건, 문의/배송·반품 Case 4~15건**이다. 모든 주문에서 문제가 생긴다고 가정하지 않고, 정상 배송은 정상 Case로, 실제 지연·문의·반품만 별도 Case로 저장한다. 6명이 여러 번 주문하는 것은 가능하지만 예산·배송기간·운영자 확인시간 때문에 30건을 넘는다고 미리 약속하지 않는다.

### 5.2 통신판매 해당 여부와 확인 조건

사실문서 1번은 직전연도 통신판매 거래횟수 50회 미만이면 신고 의무가 면제될 수 있고, 간이과세자도 별도 면제 요건이 될 수 있다고 정리한다. 그러나 **자기가 자기 물건을 사는 것**은 판매가 아니므로 그 주문을 통신판매 거래 건수로 그대로 더할 수 있는지는 확인 필요다. 팀원끼리 서로 판매·구매하거나 외부 참가자에게 판매하면 거래 성격이 달라질 수 있다.

따라서 이 방식은 “50회까지 자유롭게 판매한다”는 근거가 아니다. 내부 주문은 운영·평가 데이터로 기록하고, 실제 판매를 알파로 열기 전에는 통신판매업 신고, 사업자등록, 결제·환불·개인정보 처리를 각각 확인한다. 면제 요건에 해당한다면 판매 대상·수량·기록을 제한하고, 해당하지 않거나 판단이 모호하면 신고·등록 및 관련 요건을 갖춘 뒤 진행한다.

### 5.3 데이터 품질 한계와 보정

팀원이 만든 문의는 실제 고객을 흉내 낸 미션 데이터가 되기 쉽다. 편향은 다음과 같다.

| 편향 | 영향 | 줄이는 방법 |
|---|---|---|
| 팀원이 시스템을 잘 안다 | 일반 고객보다 정확한 주문번호·용어를 쓴다 | 주문번호 누락·오타·짧은 표현·멀티턴 후속 질문을 별도 시나리오로 수집 |
| 일부러 실패를 만들 수 있다 | 실제 빈도보다 지연·반품이 과다해진다 | 자연 발생 Case와 의도적 경계 테스트를 `organic`/`scenario`로 분리 |
| 팀의 상품·가격 선택이 좁다 | 상품 다양성·배송권역·문의 유형이 제한된다 | 상품군·배송상태·문의 intent별 quota를 두고, 알파의 자연 문의를 섞는다 |
| 평가자가 정답을 알고 있다 | 사람 수정과 judge가 관대해질 수 있다 | 라벨러와 실행자를 분리하고, holdout은 사전에 봉인한다 |

이 데이터는 실제 고객 데이터의 대체가 아니라 내부 재현·회귀·파인튜닝 2차의 씨앗이다. 알파에서 실제 고객 표현을 추가하고, organic과 scenario 결과를 KPI·학습셋·golden 후보에서 따로 표시하면 편향을 줄일 수 있다.
