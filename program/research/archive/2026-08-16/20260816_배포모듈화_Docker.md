# Docker 배포 모듈화 계획

## 결론

Docker는 v7의 본체 범위를 다시 만드는 일이 아니라, **자체 호스팅을 선택할 수 있게 하는 제품 특성**으로 설계한다. 시장격차 문서가 말하듯 자체 호스팅·온프레미스·air-gapped 선택지가 없으면 규제 산업에서 구매 장애가 된다. 다만 작성 시점에는 Docker가 설치돼 있지 않고, PostgreSQL도 Windows 서비스가 아닌 conda env `pgv` 프로세스다. 따라서 이번 문서는 배포 설계와 검증 계약을 정하며, 지금 당장 `docker compose up`을 실행했다는 전제를 쓰지 않는다.

## 1. 배포 프로파일

| 프로파일 | 켜는 것 | 끄거나 대체하는 것 | 목적 |
|---|---|---|---|
| 로컬 개발 | app, 현재 로컬 PostgreSQL, In-Process bus, 로컬 Team | Docker, Redis, 원격 A2A, 실제 결제·배송 | v7 본체 개발과 테스트 |
| 단일 호스트 Docker | app, worker, PostgreSQL+pgvector, 필요 시 Redis | 외부 관리형 DB, 다중 노드, 실제 결제·배송은 별도 게이트 | 고객사 한 대에서 재현 가능한 설치 |
| 고객사 자체 호스팅 | 위 구성과 고객사 네트워크·스토리지·키 관리 | 외부 관측·LLM API는 정책에 따라 차단 또는 프록시 | 데이터 주권, 온프레미스, 제한망 운영 |

로컬 개발은 현재 환경을 보존한다. Docker 프로파일은 `compose` 파일을 제공하되, 설치되지 않은 런타임을 이미 검증된 것처럼 표현하지 않는다.

## 2. 컨테이너 경계

| 경계 | 기본 역할 | 분리 이유 |
|---|---|---|
| app | REST/MCP, 운영 UI, Controller, Core, Team 실행 진입점 | 요청 수명주기와 백그라운드 재처리를 분리한다 |
| worker | Outbox replay, 일일 배치, 재시도·시간 제한 작업 | 앱 재시작과 배치 실패가 요청 처리에 번지지 않게 한다 |
| PostgreSQL+pgvector | Case, Action, audit, Outbox, RAG 벡터의 Source of Truth | v7의 저장 기준을 한 곳에 두고 백업·복구 경계를 명확히 한다 |
| Redis (선택) | 다중 프로세스 MessageBus·짧은 상태·rate limit이 필요할 때 | 단일 호스트 MVP에서 무조건 추가하지 않는다. Outbox와 PostgreSQL만으로 충분하면 끈다 |

기본은 3개(app·worker·DB)다. Redis는 처리량이나 여러 worker가 실제로 필요할 때만 켠다. DB를 app 컨테이너 안에 넣지 않는 이유는 데이터 수명·백업·마이그레이션을 앱 이미지와 분리해야 하기 때문이다. 반대로 app과 내부 Team을 모두 별도 컨테이너로 쪼개지는 않는다. v7은 Team을 Registry 등록형 모듈로 두고, 프로세스 분리가 필요한 곳은 A2A 경계로 한정한다.

## 3. 설정 외부화

v7의 수치 원천은 `config/guardrails.yaml` 한 곳으로 유지한다.

- 이미지에는 기본 경로와 예시 파일만 넣고, 운영값은 읽기 전용 볼륨으로 `/app/config/guardrails.yaml`에 마운트한다.
- `.env`에는 프로파일, DB 호스트, 포트, 로그 수준처럼 비밀이 아닌 연결 설정만 둔다. guardrail 수치를 `.env`에 복제하지 않는다.
- API key, DB 비밀번호, LLM key, 암호화 키는 `.env` 커밋본에 두지 않고 Docker secret 또는 고객사 비밀 저장소에서 주입한다. 로그에는 원문을 남기지 않는다.
- 설정 변경은 이미지 재빌드가 아니라 버전이 있는 설정 파일 교체와 재기동으로 한다. 시작 시 schema·범위·파일 checksum을 검증하고 audit에 남긴다.
- `guardrails.yaml`과 Alembic revision은 같은 배포 manifest에서 함께 승인한다. 서로 다른 수치가 환경별로 생기면 배포를 중단한다.

## 4. 데이터 주권 체크리스트

고객사 자체 호스팅 전 다음을 확인한다.

1. Case, 주문·배송 projection, Action, approval, audit, RAG 문서·임베딩, Outbox가 고객사 볼륨과 고객사 DB에만 있는가.
2. 백업 파일·로그·trace·crash dump에도 PII 원문이 남지 않는가. 배송 원문은 별도 암호화 Vault, Case와 LLM에는 토큰만 둔다.
3. app·worker·DB의 egress를 목록화하고, 업데이트 확인·telemetry·외부 로그 전송이 기본으로 켜져 있지 않은가.
4. DNS, 프록시, 인증서, 시간 동기화, 이미지 레지스트리 접근이 고객사 정책 안에 있는가.
5. LLM API를 호출하면 어떤 필드가 어느 사업자·리전에 가는지 명시적으로 고지했는가. PII masking, tenant·case ownership, 전송 audit가 먼저 실행되는가.
6. 완전한 외부 차단이 필요하면 로컬 모델·고객사 LLM endpoint·허용된 프록시 중 하나를 선택하고, 모델 부재 시 `unknown`/escalated로 남기는가.
7. 외부 LLM을 쓸 경우 개인정보 국외이전은 금지가 아니라 동의 또는 처리위탁·보관과 처리방침 공개 등 요건을 갖추면 된다. 실제 경로는 **확인 필요**다.

## 5. 마이그레이션·백업

v7 §16의 Alembic 단일 브랜치 규칙을 유지한다.

- migration job을 app/worker 시작 명령에 섞지 않고, 배포 전 한 번 실행하는 관리 작업으로 둔다.
- revision은 하나의 linear head만 허용한다. 두 head가 발견되면 배포하지 않는다.
- 순서: DB 백업 → 이미지와 migration checksum 고정 → `alembic upgrade head` → schema/contract smoke test → app·worker 기동.
- 백업은 PostgreSQL dump와 고객사 볼륨 정책을 함께 관리한다. Outbox·audit·Case·RAG metadata가 빠지지 않는지 복구 목록으로 확인한다.
- 복구는 새 격리 DB에 dump restore → 필요한 revision까지 upgrade → read-only smoke test → 트래픽 전환 순서다. 운영 DB에 즉시 덮어쓰지 않는다.
- worker는 복구 중 중지하고, 전환 뒤 Outbox의 pending/replay와 idempotency key를 점검한다. 이미 성공한 Action을 다시 실행하지 않는다.

## 6. Port와 Adapter

| Port | 로컬 개발 | 단일 호스트 Docker | 고객사 자체 호스팅 |
|---|---|---|---|
| `MessageBusPort` | `InMemoryMessageBus` 또는 PostgreSQL Outbox | 기본 `OutboxMessageBus`, 필요 시 `RedisMessageBus` | 고객사 정책에 맞는 Outbox 또는 Redis/RabbitMQ Adapter |
| `GraphStorePort` | `SqlGraphAdapter` | `SqlGraphAdapter` + PostgreSQL/pgvector | 기본 `SqlGraphAdapter`; Age/Neo4j는 별도 선택·검증 게이트 |
| `TeamExecutorPort` | `LocalTeamExecutor` | `LocalTeamExecutor`; 별도 A2A fixture 선택 | `LocalTeamExecutor` 또는 고객사 내부 A2A endpoint의 `A2ATeamExecutor` |

Controller는 프로파일을 직접 알지 않고 Factory/Registry가 Adapter를 고른다. 모든 경로는 같은 `TeamResult`, audit, 상태 매핑을 반환한다. 이 구조가 제품 특성인 이유는 고객사가 Docker를 쓰더라도 v7의 Core·Team 계약을 바꾸지 않고 저장소·메시지·실행 위치만 교체할 수 있기 때문이다.

## 7. 10주 범위와 검증 한계

| 작업 | 실소요 | 이번 범위 |
|---|---:|---|
| 생성 | 3~4일 | Dockerfile, compose profile, healthcheck, secret·volume 문서, migration/backup 명령, Adapter 선택표 |
| 검증·통합 | 3~4일 | 이미지 build 정적 확인, compose YAML·환경 계약 검사, 로컬 app/worker 계약 테스트, 백업·restore 절차를 기존 PostgreSQL로 검증 |
| 대기 | 1~2일 | 고객사 네트워크·키 정책 확인, Docker 설치 후 실제 build/기동 확인 |

순증을 막기 위해 이번 10주에는 Kubernetes, 다중 노드, air-gapped 이미지 미러 운영, 관리형 Redis/RabbitMQ, 자동 TLS·관측 SaaS, 실제 고객사 설치를 뺀다. Docker 미설치 상태에서는 `docker build`, 실제 compose 기동, 컨테이너 간 네트워크 검증을 완료로 표시할 수 없다. 대신 파일·설정·계약·현재 PostgreSQL의 migration/backup과 비-Docker 테스트까지만 검증하고, Docker 설치가 가능한 환경에서 별도 배포 게이트를 연다.
