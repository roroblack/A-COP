## 3. 줄 번호 기반 `cut()`

판정: 반대.

첫 줄만 확인하는 방식([trace_data.py:23](/C:/Users/playdata2/Documents/final_workspace/program/onboarding/trace_data.py:23))은 다음을 막지 못한다.

- 함수 내부가 길어져도 시작 줄과 시그니처가 그대로면 기존 `end`에서 조용히 잘린다.
- 함수가 짧아지면 다음 함수나 주석까지 들어갈 수 있다.
- `end`가 파일 끝을 넘어가도 조용히 짧은 조각을 반환한다.
- `expect in chunk[0]`은 부분 문자열 검사라, 다른 라우트나 비슷한 선언도 통과할 수 있다.
- 함수 앞에 주석 한 줄을 넣는 무해한 변경도 전체 HTML 빌드를 막는다.
- 기존 HTML과 MP4를 재생성하지 않으면 실패조차 발생하지 않아 낡은 산출물이 계속 배포된다.

고칠 것:

- Python은 AST에서 함수·메서드의 qualified name을 찾아 `lineno/end_lineno`로 추출한다. 데코레이터가 필요하면 첫 데코레이터 줄부터 포함한다.
- SQL은 `CREATE TABLE <name>`부터 해당 문장의 종료 `;`까지 찾는다.
- YAML은 파싱된 키 경로로 위치를 찾거나, 유일한 시작·끝 앵커를 함께 검증한다.
- 임의의 내부 블록이 꼭 필요하면 시작 앵커와 종료 앵커를 모두 지정하고 각각 유일한지 검사한다.
- 표시할 `path:line`은 앵커를 찾은 뒤 계산한다.
- 추출 결과가 비었는지뿐 아니라 예상 심볼, 종료 경계, 필요하면 해시 또는 핵심 토큰까지 검증한다.

## 4. 2.0MB 단일 HTML

판정: 동의.

독립 파일 하나를 전달한다는 요구라면 2MB 자체는 브라우저에 큰 부담이 아니다. CSS·JS·12단계 JSON보다 이미지가 문제다.

현재 포함되는 PNG 7장은 압축 상태 약 1.48MiB이고 base64로 약 1.97MiB가 된다. 디코딩된 RGBA 메모리는 합계 약 80MiB다. 모든 `<img>`에 지연 로딩과 크기 정보가 없다([build_trace_html.py:79](/C:/Users/playdata2/Documents/final_workspace/program/onboarding/build_trace_html.py:79)). 따라서 저사양 모바일에서는 초기 이미지 디코딩, 메모리, 아래쪽 레이아웃 이동이 실제 문제다.

조건:

- `<img loading="lazy" decoding="async" width="…" height="…">`를 생성한다.
- 이미지의 종횡비를 미리 확보한다.
- 웹 서버에서 반복 배포하고 브라우저 캐시가 중요한 경우에는 외부 이미지가 낫다.
- 독립 전달이 요구사항이면 base64를 없앨 이유는 없다.
- 엄격한 CSP 환경에 호스팅할 경우 inline CSS·JS와 `data:` 이미지가 차단될 수 있으므로 별도 배포판이 필요하다.

## 가장 위험한 것 3개

1. **두 개의 12단계 배열을 인덱스로 결합하면서 정체성을 검증하지 않는 것**  
   빌드는 성공하지만 낱장, 누적 상태, 실제 코드가 서로 다른 단계로 조용히 결합될 수 있다.

2. **import 순서에 따라 동작이 달라지는 monkey patch**  
   데이터 수집 대신 PNG가 생성되거나, 이후 그림 생성이 수집으로 바뀌는 전역 상태 결함이다.

3. **시작 줄 한 줄만 검증하는 코드 절단과 산출물 신선도 미검사**  
   무해한 변경에는 빌드가 깨지고, 경계 변경에는 잘못 잘린 코드가 조용히 들어가며, 재빌드하지 않으면 낡은 결과가 그대로 남는다.
