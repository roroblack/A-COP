Agent Team 세 사람의 공통 기초

담당 Team이 달라도 지켜야 할 계약은 같습니다. 이 절은 세 장에 똑같이 들어 있습니다.

가장 중요한 규칙 하나

Team은 부수효과를 실행하지 않습니다. 환불이 맞다고 100퍼센트 확신해도 환불을 하는 게 아니라 "환불하자"는 제안(ActionProposal)을 돌려줍니다. 실제 실행은 코어 2의 승인 경로에서 일어납니다. 이 경계를 넘는 코드는 리뷰에서 되돌려집니다.

Team 하나는 이렇게 생겼습니다

상속할 부모 클래스가 없습니다. manifest 속성과 execute() 메서드 두 개만 있으면 Team입니다. Core는 그 둘만 씁니다.

class 내Team:
    manifest = TeamManifest(
        team_id="...",              # config/project.yaml 의 team_id 와 같아야 한다
        capabilities=[...],         # 내가 할 수 있는 일. 다른 팀과 겹치면 조립이 실패한다
        allowed_tools=[...],        # 내가 부를 수 있는 도구. 목록 밖은 도구함이 거부한다
        knowledge_scope=[...],      # 내가 읽을 수 있는 지식 범위
    )
    async def execute(self, task: TeamTask) -> TeamResult: ...

계약 네 개를 먼저 읽습니다

  1. app/core/contracts.py:303 TeamManifest, :321 TeamModule자기소개서의 모양입니다. Registry는 이것만 보고 라우팅합니다.
  2. app/core/contracts.py:165 TeamTask들어오는 것입니다. context(근거 꾸러미), allowed_tools, deadline_at, resume가 핵심 필드입니다.
  3. app/core/contracts.py:223 TeamResult, :201 ActionProposal나가는 것입니다. next_action이 '승인 받아라'·'고객에게 물어라'·'사람에게 넘겨라'를 전부 표현합니다.
  4. app/core/contracts.py:94 Evidence모든 주장에 붙는 출처입니다. source_type·source_id·observed_at. 근거 없는 문장은 답변에 넣지 않습니다.
  5. app/tools/read_tools.py:38 ReadToolbox, :146 call()DB를 읽는 유일한 통로입니다. call()이 allowed_tools를 검사하고 같은 도구를 반복해 부르는 루프도 막습니다. 직접 SQL을 쓰면 안 됩니다.

ContextPack — 받은 근거가 온전하지 않을 수 있습니다

task.context에 근거가 실려 옵니다. 그런데 12,000 토큰 예산을 넘으면 일부가 잘려 나갑니다. 그때 degraded=true가 붙고 omissions에 무엇을 뺐는지가 적힙니다.

이 깃발을 무시하면 안 됩니다. 근거가 잘린 채로 확정 답변을 만들면 그게 바로 이 프로젝트가 막으려는 상황입니다. 정책 근거를 못 대면 escalate나 wait_for_input이 정답입니다.

둘 다 주문이 나간 뒤를 다룹니다. 김지혜의 팀이 배송 전을 맡고, 배송이 나간 순간부터 이쪽으로 넘어옵니다. 그 경계선을 두 사람이 같은 기준으로 잡아야 문의가 사이에 빠지지 않습니다.

Fulfillment & Logistics (110줄)

배송 추적, 배송 상태, 배송 예외를 다룹니다. 도구는 read.order, read.shipment, read.policy 셋입니다. 지식 범위에 delivery_exception이 따로 있는 것을 눈여겨보세요 — 정상 배송보다 예외 상황이 이 팀의 본업이라는 뜻입니다.

Return & Refund (161줄)

반품 가능 여부, 반품 접수, 환불 금액 계산을 합니다. 이 팀의 중심은 날짜 계산입니다. 반품 기한이 며칠인지가 사유마다 다르고, 그 값을 정책 문서에서 읽어 옵니다. 지금은 Mock 단계이며 실제 반품 시스템 연동은 검증 쇼핑몰 일정에 따라 붙습니다.

이 두 팀의 공통 어려움 — 날짜와 시간

배송일, 수령일, 반품 기한, 환불 처리일이 전부 시간 계산입니다. 그리고 시간 계산은 조용히 틀리기 쉽습니다. 하루 차이로 "반품 됩니다"가 "반품 안 됩니다"로 바뀌는데, 고객에게 잘못 말하면 되돌리기 어렵습니다.

return_refund.py:68의 _date()가 값을 날짜로 바꾸는 유일한 자리입니다. 파싱에 실패하면 None을 돌려주고, 그때 이 팀은 추정하지 않고 사람에게 넘깁니다.

함정

기한 판정에 기본값을 함부로 두지 않습니다

정책을 못 읽었는데 "보통 7일이니까 7일로 하자"고 두면, 그게 바로 RULE.md §3.2가 금지한 폴백입니다. 고객이 그 답을 믿고 반품을 포기하거나 헛걸음합니다. 모르면 escalate가 정답입니다.

배송 전과 후의 경계는 김지혜와 같이 정합니다

같은 주문을 두고 '배송 전'이라고 보는 기준이 두 팀에서 다르면 문의가 사이에 빠지거나 두 팀이 서로 다른 답을 냅니다. procurement_order_payment.py:113의 _is_pre_shipment()를 한 번 같이 읽어 두세요.

Return & Refund는 지금 Mock입니다

실제 반품 시스템 연동은 검증 쇼핑몰 일정에 달려 있습니다. "이미 연동됐다"고 발표에서 말하면 안 됩니다. 지금 검증된 것은 판정 로직까지입니다.

이 파트에서 실제로 났던 제일 큰 결함

feedback.py의 INTENTS가 옛 구독·청구 도메인 어휘(billing, technical)로 남아 있었는데, 이 함수가 운영 API의 기본 분류기였습니다. 쇼핑몰 문의는 전부 분류 실패로 떨어졌을 상태였습니다. 지금은 order, shipping, return, exchange, other입니다.

재발 방지로 INTENTS가 모든 Team의 accepted_case_types를 덮는지 검사하는 테스트가 있습니다. Team을 새로 만들면서 새 유형을 받겠다고 선언하면 이 테스트가 먼저 붉어집니다 — tests/unit/voc/test_feedback_intent_alignment.py.

프롬프트를 쓰면 DB에 등록해야 합니다

프롬프트 파일만 만들어 두고 등록을 안 하면, 감사 기록 경로로 불릴 때마다 no active prompt registered로 죽습니다. Response Review 팀이 실제로 이 상태로 한동안 있었습니다. python -m scripts.register_prompts를 잊지 마세요.

Core를 import하면 테스트가 붉어집니다

Team은 app/core/contracts.py와 app/tools/만 씁니다. Controller나 transition을 직접 부르면 tests/contract/test_core_isolation.py가 import 검사로 잡습니다. 의도된 것이니 놀라지 마세요.
