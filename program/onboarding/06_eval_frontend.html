A. 평가 — 먼저 할 일

알아야 할 말 다섯 개

golden과 holdout은 정답이 붙은 문제 묶음입니다. golden 60건은 보면서 고쳐도 되고, holdout 20건은 절대 보고 고치면 안 됩니다. 보고 프롬프트를 손보는 순간 그건 두 번째 golden입니다.

arm(군)은 비교하는 방식 하나입니다. A, B, Proposed 셋이 있고 run 단위로만 비교합니다. arm이나 데이터셋이나 실행 방식이 다르면 평균을 견줄 수 없습니다.

bootstrap 95% 신뢰구간은 같은 결과를 수천 번 다시 뽑아 차이가 어느 범위에 있는지 재는 방법입니다. 평균만 말하면 그 숫자가 얼마나 흔들리는지 알 수 없습니다.

McNemar 검정은 같은 문제를 두 방식에 똑같이 풀렸을 때 A는 틀리고 B는 맞은 건수와 그 반대 건수를 비교합니다. 짝지어진 비교라 표본이 적어도 씁니다.

judge와 rubric은 답변 품질을 LLM에게 채점시키는 것과 그 기준표입니다. judge가 사람과 얼마나 맞는지는 따로 확인해야 합니다.

코드 읽는 순서

  1. eval/datasets/golden.jsonl 의 첫 줄 하나제일 먼저 할 일입니다. 한 줄만 열어 무슨 필드가 있는지 보세요. 입력과 정답이 뭔지 모르면 나머지가 다 추상적입니다.
  2. eval/runners/common.py:141 run_config()세 군이 공유하는 실행부입니다. 모델·temperature·seed·프롬프트 버전을 고정하는 자리입니다. 이 값들이 안 고정되면 재현이 안 돼서 비교 자체가 무의미해집니다.
  3. eval/runners/baseline_a.py → baseline_b.py → proposed.py이 순서로 셋을 나란히 읽으세요. 세 파일의 차이가 곧 우리가 무엇을 더 했다고 주장하는지입니다.
  4. eval/judge/rubric.json 과 eval/check_judge.py채점 기준표와, 근거 없이 점수를 받은 행이 있는지 세는 검사기입니다. 하나라도 있으면 종료코드 1입니다. 채점자를 채점하는 코드입니다.
  5. eval/stats/make_pairs.py → bootstrap.py → mcnemar.py짝을 만들고 신뢰구간을 내고 검정합니다. 짧으니 입력이 무엇인지만 보면 충분합니다.
  6. eval/defense_metrics.py 와 eval/datasets/attack_fixtures.jsonl일부러 이상한 입력을 넣었을 때 막아 내는지 재는 부분입니다. 품질 지표와 안전 지표를 따로 잰다는 것을 확인하세요.

코드 읽는 순서

  1. config/project.yaml40줄이 안 됩니다. 모듈 6개, Port 3개, Team 6개가 전부 여기 선언돼 있습니다. 이 파일이 이 절의 주인공입니다.
  2. app/core/project_config.py:78 module_enabled(), :84 require_module()선언을 읽고 켜져 있나를 묻습니다. require_module()은 꺼져 있으면 예외를 냅니다 — 조용히 넘어가지 않는 게 핵심입니다.
  3. app/composition.py 의 build_ 함수들조립 경계입니다. Team을 하드코딩 import하지 않고 선언에 적힌 경로를 importlib로 불러옵니다. 그래서 Team을 늘려도 Core가 안 바뀝니다.
  4. app/application/composer_service.py선언을 고치는 로직입니다. read_current → validate_candidate → apply_candidate 순으로 읽으세요.
  5. app/presentation/api/composer.py그 로직을 여는 API 넷입니다. apply가 사유(reason)를 필수로 받는 것을 확인하세요 — 감사 기록의 근거입니다.
  6. app/presentation/ui/routes.py 의 _admin_snapshot()542줄로 저장소에서 제일 큰 파일이지만 여기부터 보면 됩니다. 지금 무엇으로 조립돼 있는지를 화면에 뿌리는 함수입니다.
  7. app/presentation/ui/theme.py디자인 시스템입니다. 색을 컴포넌트에 하드코딩하지 않고 토큰으로만 씁니다. unknown을 가장 센 위험색으로 칠한 이유도 여기서 보입니다.
  8. app/introspection/contract.py밖에서 지금 어떻게 조립돼 있냐고 물었을 때 답하는 계약입니다. 별도 프로그램 final_project_ui가 이걸 읽습니다.

함정

조립은 기동할 때 한 번만 일어납니다

선언을 고쳐도 떠 있는 서버는 안 바뀝니다. 재기동해야 합니다. 고쳤는데 왜 안 바뀌지의 대부분이 이겁니다.

--reload 자식 프로세스가 옛 코드를 서빙합니다

uvicorn을 --reload로 띄우면 자식 프로세스가 남아 고친 코드가 반영 안 된 것처럼 보일 때가 있습니다. 실제로 여기에 한참 쓴 적이 있습니다. 선언을 바꿔 가며 확인할 때는 --reload 없이 띄우세요.

voc 모듈은 끌 수 없습니다

2026-08-30 확정입니다. 끄면 앱이 아예 안 뜹니다. 인라인 분류가 Case 생성 경로에 붙어 있고 그건 선택 기능이 아니기 때문입니다. 계약 문서 docs/handoff/08_모듈_컴포넌트_목록.md §2에 표시돼 있습니다.

Composer 화면은 이 저장소에 없습니다

/ui/composer는 2026-08-18에 삭제됐습니다. 인증이 전혀 없이 고객 접근 가능한 앱에 물려 있었기 때문입니다. 같은 기능은 별도 프로그램 final_project_ui가 인증된 /composer/* API로만 제공합니다. 이 저장소에는 API 쪽만 있습니다.

화면을 열어서 확인하지 않으면 완료가 아닙니다

이 저장소 규칙(CLAUDE.md §4)입니다. 실제로 브라우저에서 승인 버튼을 눌러 보다가 결함 두 건을 찾은 적이 있습니다. 테스트만으로는 안 나왔습니다.
