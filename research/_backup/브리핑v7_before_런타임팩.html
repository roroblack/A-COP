1. 한눈에 보는 핵심 그림

이 프로젝트는 단순 챗봇이 아니라, 고객 피드백을 기반으로 실제 업무 단위의 전문 AI Agent Team이 협업하여 문제를 해결하는 Agentic Customer Operations Platform이다.

핵심 아이디어

  • 고객 피드백을 단순 답변용 입력이 아니라 Customer Case로 관리
  • 업무 책임 단위 Agent Team Module 구성. Team 종류와 개수는 요구사항 분석 후 정한다.
  • RAG, Memory, Shared State를 통해 Agent 협업

차별점

  • 고정 파이프라인이 아니라 동적 분기·재처리·승인
  • 외부 사용자의 개인 AI(ChatGPT/Claude/Gemini)가 우리 서비스 API/MCP로 접속 가능
  • 도메인 확장이 가능한 모듈형 Basement 구조

시연 포인트

  • 구독 해지 후 추가 결제
  • 권한 동기화 오류
  • 반복 VOC 탐지 및 리포트

2. 기존 Pipeline을 Agentic Customer Operations로 확장하는 이유

먼저 기존 구조가 해결하지 못하는 문제를 확인한다.

Agent 수를 늘리자는 제안이 아니다. 고정된 처리 단계를 Agent라고 부르는 대신, 실제 고객 업무에서 서로 다른 책임·지식·도구를 가진 업무 단위를 모듈형 Agent Team으로 구성하고, 상위 Agentic System이 이들의 협업과 상태를 관리하도록 만들자는 제안이다.

앞의 구조 변경에서 이어지는 개선점
위 비교에서 핵심적으로 바뀐 것은 ① 처리 단계를 Agent라고 부르는 구조에서 실제 업무 책임 단위 Team으로 전환하고, ② 한 번의 답변 생성 대신 Customer Case의 상태를 끝까지 관리하며, ③ 기존 분석·RAG·응대 기능을 이 Case 처리 흐름 안에 그대로 포함한 것이다. 이 변화로 다음 세 가지 개선점이 생긴다.
1

Multi-Agent의 이유가 생긴다

업무 책임 단위로 Team을 분리했기 때문에, 검색 Agent·생성 Agent처럼 처리 단계를 억지로 Agent화하는 문제가 줄어든다. 각 Team이 서로 다른 업무 목표·권한·Tool·Knowledge를 가지므로 Agent 간 협업이 실제 업무 분업과 연결된다.

2

LangGraph의 이유가 생긴다

답변 한 번이 아니라 Customer Case의 상태를 계속 관리하기 때문에, Team 재배정, 추가 정보 대기, Human Approval, 실패 후 재처리, 상태 복원 같은 분기·순환·중단·재개가 실제 요구사항이 된다. 이때 상위 Workflow를 Graph로 관리할 이유가 생긴다.

3

기존 과제를 버리지 않는다

기존 기능을 제거한 것이 아니라 더 큰 Case 처리 구조 안에 배치했기 때문에, 고객 피드백, 감성·의도·이슈 분석, RAG, Multi-Agent, 맞춤형 응대 요구는 그대로 유지된다. 단순 답변 Pipeline을 Customer Case 해결 시스템으로 확장하는 방식이다.

3-3. 컴포넌트 사전

각 카드는 클릭하면 기능·용어·입출력 설명이 펼쳐지고, 다시 클릭하면 접힌다.

Agent Gateway
외부 요청의 인증·인가 경계

Web·Personal AI·원격 Agent System의 REST/MCP/A2A 요청을 내부 Case로 넘기기 전에 신원·권한·요청 대상을 검증한다.

정확한 역할과 기능

  • Access Token의 유효성·만료·대상을 검증한다.
  • 사용자와 외부 AI Client를 식별한다.
  • 요청 기능이 허용 Scope 안인지 검사한다.
  • 고위험 요청은 추가 승인 정책으로 넘긴다.
  • A2A 요청의 원격 Agent 식별자, 대상 Agent, 요청 Capability와 인증 정보를 검증한다.

용어 해설

Trust Boundary외부 요청을 그대로 신뢰하지 않고 내부로 들어오기 전에 검증하는 경계.
OAuth비밀번호를 외부 AI에 주지 않고 제한된 접근 권한을 위임하는 표준 방식.
Access Token인증된 Client가 허용된 API를 호출할 수 있음을 나타내는 짧은 수명의 인증 정보.
ScopeToken이 사용할 수 있는 기능 범위.
A2A독립적으로 실행되는 Agent System끼리 Capability와 Task를 주고받기 위한 Agent-to-Agent 상호운용 방식.
입력: REST / MCP / A2A 요청 + Token → 출력: 인증·인가된 내부 요청 Context
Customer Case Layer
메시지를 지속 가능한 업무 Case로 변환

한 번의 문의를 단순 문자열이 아니라 상태·이력·승인·재개 지점을 가진 업무 단위로 관리한다.

정확한 역할과 기능

  • case_id를 발급하고 문의 원문과 상태를 보관한다.
  • 현재 담당 Capability/Team과 남은 작업을 기록한다.
  • WAIT 상태에서 사용자 응답이나 승인을 기다렸다 재개한다.
  • 상태 변경을 Event로 남겨 추적 가능하게 한다.

용어 해설

Case하나의 고객 문제를 접수부터 해결까지 추적하는 업무 단위.
LifecycleCase가 생성·실행·대기·종료 상태를 거치는 전체 흐름.
EventCase에서 일어난 상태 변화나 중요한 행위를 기록한 사실 데이터.
Checkpoint실행을 멈춘 뒤 같은 상태에서 재개할 수 있게 저장한 지점.
입력: 승인된 고객 요청 → 출력: case_id + lifecycle state
Context Broker
판단에 필요한 Context Pack 구성

Vector RAG, Graph 관계 탐색, DB 현재 상태, Case History, Memory에서 필요한 정보만 골라 Controller/Team에 공급한다.

정확한 역할과 기능

  • 현재 작업에 필요한 정보 종류를 결정한다.
  • RAG·DB·Memory 결과를 표준 Context Pack으로 조합한다.
  • 중복/불필요한 정보를 줄여 Context 크기를 관리한다.
  • Team별 Knowledge Scope를 적용한다.
  • Vector Search가 찾은 관련 Entity를 Graph Store에서 1~2 hop 확장해 연결된 Case·Issue·Policy·Action을 보강할 수 있다.

용어 해설

ContextAgent가 현재 판단할 때 함께 받는 업무 상태·지식·이력 정보.
Context Pack여러 원천의 정보를 현재 작업에 맞춰 정리한 표준 입력 묶음.
RAG생성 전에 외부 지식에서 관련 근거를 검색해 입력에 추가하는 구조.
Normalization서로 다른 형식의 정보를 일관된 구조로 맞추는 과정.
GraphRAG벡터 유사도 검색 결과에 지식 그래프의 관계 탐색을 결합해 연결된 근거와 맥락을 확장하는 검색 구조.
핵심 질문: “이 Agent가 지금 무엇을 알아야 하는가?”
Message Broker
Coordination의 비동기 Task / Event 전달

우리 Runtime 내부의 Local Team Worker에 Task/Event를 전달한다. 원격 Agent System과의 협업은 A2A Adapter가 담당한다.

정확한 역할과 기능

  • Controller가 발행한 Task를 Queue에 넣는다.
  • Team Worker가 Task를 소비해 실행하게 한다.
  • 실패 작업의 Retry를 처리한다.
  • 완료/오류 Event를 여러 구독자에게 전달할 수 있다.
  • Message Broker는 내부 Queue/Worker 통신용이며 외부 Agent 간 상호운용 프로토콜 역할을 하지 않는다.

용어 해설

Asynchronous요청자가 작업 종료까지 계속 기다리지 않는 실행 방식.
Queue처리할 작업을 보관하는 대기열.
Retry일시적 실패 작업을 정해진 정책에 따라 다시 실행하는 것.
Pub/SubEvent를 발행하면 여러 구독자가 받아 처리하는 전달 방식.
WorkerQueue에서 Task를 가져와 실제 작업을 수행하는 실행 프로세스.
Internal Runtime같은 서비스 또는 같은 운영 경계 안에서 Controller와 Worker가 작업을 전달하는 실행 환경.
소유 경계: Case Runtime & Coordination. Controller가 정책을 결정하고 Broker Adapter가 Task/Event를 전달한다.
Agentic Controller
Case의 상위 의사결정·라우팅

현재 Case 상태를 보고 어떤 Team을 호출할지, 대기할지, 재계획할지, 종료할지 결정한다.

정확한 역할과 기능

  • 필요 Capability를 판별한다.
  • Registry에서 적합한 Team Module을 찾는다.
  • TeamResult를 평가해 완료/재처리/위임을 결정한다.
  • 같은 Case에 여러 Team이 동시에 접근할 수 있는지, owner가 누구인지, 충돌 시 Retry/Replan/Cancel 중 무엇을 할지 결정한다.
  • 추가 입력이나 승인이 필요하면 WAIT 상태로 전환한다.

용어 해설

CapabilityTeam이 수행할 수 있다고 선언한 업무 능력.
Routing업무를 어느 Team/실행 경로로 보낼지 선택하는 과정.
Replan현재 계획으로 해결되지 않을 때 다음 처리 경로를 다시 구성하는 것.

정확한 역할과 기능

  • Vector Search 결과 Entity에서 1~2 hop 관계를 탐색한다.
  • 반복 VOC, 동일 Issue-Product-Version 패턴, 유사 Case 처리 이력을 찾는다.
  • Agent Team과 Capability·Tool·Knowledge 관계 탐색을 확장할 수 있다.
  • Customer Case 상태와 결제/Action Transaction의 원본 DB를 대체하지 않는다.

용어 해설

Graph Database데이터를 표의 행보다 Node와 Edge 관계 중심으로 저장·탐색하는 데이터베이스.
NodeCustomer, Case, Issue, Policy처럼 하나의 개체를 나타내는 그래프 요소.

Hop그래프 관계선을 몇 단계 따라 이동했는지를 나타내는 거리.

원칙: PostgreSQL/Shared State = 거래·상태의 Source of Truth / GraphStorePort = 관계 조회 Adapter

컴포넌트 사전의 핵심 6개는 Gateway, Case Layer, Context Broker, Controller, Agent Team, Shared State다. Registry·Broker·Tool/Action·Graph adapter는 계획서에서 상세히 다룬다.

3-4. Agent/Team 경합과 동시성 처리 책임 계획서 8-C

경합 처리를 “Coordination 정책 담당”과 “Backend CAS 구현 담당”으로 사람을 다시 쪼개지 않는다. 같은 Customer Case의 실행·상태 경합은 Core 1이 정책부터 DB 무결성까지 end-to-end로 담당한다. 반면 실제 환불·계정변경 같은 외부 Action의 중복 실행은 Core 2가 담당한다.

코드의 책임 경계와 사람의 담당 경계를 똑같이 만들 필요는 없다. 코드에서는 Coordination과 State/Tool Layer를 분리하되, 사람은 Core 1이 Case Runtime을 end-to-end로 담당한다.

경합/중복 문제처리 방식담당 영역
두 Team이 같은 Case를 동시에 처리 Ownership, 병렬 허용 여부, 실행 순서, Retry/Replan/Cancel 정책 Core 1 · Case Runtime & Coordination
같은 Shared State를 동시에 UPDATE version, Optimistic Concurrency, CAS, Transaction으로 충돌 감지·차단 Core 1 · Case Runtime & Coordination
State Conflict 발생 후 다음 행동 최신 State 재조회 → 결과 유효성 판단 → Retry 또는 Replan Core 1 · Case Runtime & Coordination
같은 환불/계정 변경 Action이 중복 호출 Idempotency Key, Permission, Approval, Audit로 Side Effect 1회 보장 Core 2 · Access & Action Platform
한 Agent Team 내부 Agent끼리 경합 Team 내부 Subgraph/State/merge/retry 정책으로 해결 각 Agent Team Module
중요: 코드 컴포넌트는 Controller, State Repository, Message Broker, Tool Gateway처럼 분리한다. 하지만 사람 역할은 이 컴포넌트 이름대로 잘게 쪼개지 않고, 하나의 기능 흐름을 끝까지 책임하는 수직 영역으로 묶는다.

4. 핵심 Workflow

왜 4-1을 단순화해서 표현하나? Level 1/2는 “Case가 어느 Team으로 가고 다시 돌아오는지”를 보여주는 상위 Graph이고, 실제 Team 내부에는 각자 별도의 LangGraph/Subgraph가 존재할 수 있다. 상위 Graph와 내부 Graph를 한 그림에 모두 펼치면 흐름이 오히려 읽히지 않기 때문에 계층을 나눈다.

4-5. Message Broker는 Coordination 축에 위치

Agentic Controller │ │ Team / Task / Retry 정책 결정 ▼ Message Broker / Message Bus │ │ Queue · Delivery · Retry · Event ▼ Agent Team Worker / Slot │ └─ result/event → Broker → Controller

Controller가 결정하고 Broker가 전달한다. Broker 자체는 어떤 Team이 적합한지 판단하지 않는다.

이 그림에서 읽을 것: Message Broker는 Coordination의 전달 계층이다.

논리적 소유: Case Runtime & Coordination
실제 구현: MessageBus Port + in-process / Redis / Redis Streams / RabbitMQ Adapter

Context Broker = “무엇을 알아야 하는가?” / Message Broker = “결정된 Task/Event를 어떻게 전달하는가?”

4-6. Local Team과 Remote A2A Team 실행

LangGraph 체크포인터는 AsyncPostgresSaver를 사용하고, thread_id는 case_id에 매핑한다.

Agentic Controller ↓ Agent Team Registry ↓ execution_type? ├─ LOCAL │ ↓ │ Message Broker → Local Team Slot │ ↓ │ TeamResult │ └─ A2A ↓ A2A Adapter → Remote Agent ↓ A2A Task State / Artifact ↓ TeamResult로 정규화 TeamResult ↓ Shared State 갱신 ↓ END / Retry / Replan

이 그림에서 읽을 것: Local과 Remote는 같은 TeamResult Contract로 Case에 돌아온다.

7-3. 연동·Graph 데이터

A2A Task는 case_id, 원격 Team, 상태, 결과 참조, idempotency key로 연결한다. Graph는 Customer·Case·Issue·Product·Policy·Team·Action 관계를 파생 데이터로 관리한다.

필드 전문과 예시는 구현계획서를 참조한다.

8. ERD(개념 수준)

Customer Case의 직접 자식 관계는 위·아래로 단순화하고, agent_team_registry와 knowledge_documents는 요청대로 agent_runs의 좌측 아래에 배치했다.

배치 이유: agent_team_registry와 knowledge_documents는 Customer Case의 직접 자식이 아니라 실행 중 참조된다. customer_cases.owner_team_id는 현재 Case의 소유 Team, agent_runs.team_id는 그 실행에 선택된 Team이다.

이 그림에서 읽을 것: Case 실행, Action 요청·승인, 근거 문서의 관계를 구분한다.

MCP는 도구를 빌려주는 것이고, A2A는 일을 통째로 맡기는 것이다. MCP tool 호출은 짧고 stateless에 가깝지만 A2A Task는 장기 실행과 자체 생명주기를 가진다.

9-1. Personal AI → 우리 서비스

사용자의 ChatGPT·Claude 같은 개인 AI가 사용자의 권한 범위 안에서 우리 Tool/Resource를 사용한다.

사용자 ↓ OAuth Consent Personal AI ↓ MCP / REST Agent Gateway ↓ Customer Case / Tool

주 목적: 사용자 대신 조회·문의·작업 요청.

9-2. Agent System ↔ Agent System

우리 Controller가 독립 배포된 외부 Agent System에 하나의 업무 Task를 위임하고 결과를 받는다.

Agentic Controller ↓ Registry resolve A2A Interop Adapter ↓ A2A Task Remote Agent System ↓ Result / Artifact TeamResult

주 목적: 다른 회사·다른 Runtime·독립 Agent Team과 상호운용.

이 프로젝트에서 A2A를 쓰는 세 경로

  • 우리가 클라이언트: Billing Team이 외부 Fraud Review Agent에 판단을 위임한다.
  • 우리가 서버: 외부 오케스트레이터가 SaaS 고객 문의를 우리 Agent에 맡긴다.
  • Team 분리 배포: 같은 Registry·TeamResult를 유지하고 실행 경로만 LOCAL에서 A2A로 바꾼다.

A2A Remote Team 실물

Catalog & Verification Team을 고른 이유는 SKU·Variant·가격·규제 증거를 검증하며, 정보가 부족하면 input-required를 자연스럽게 만들고 구매 side effect 없이 Artifact를 반환하기 때문이다.

Controller가 Catalog 검증 Task를 보낸다 → Remote Team이 “Variant와 인증 증거가 필요합니다”로 input-required → 운영자가 자료를 보충한다 → 같은 Task가 재개되어 verification report와 evidence manifest Artifact를 반환한다.

9-B. Graph DB / GraphRAG 활용 계획 계획서 9-D

GraphRAG는 문서에서 LLM이 관계를 추출하는 방식과, 이미 정형화된 관계를 질의하는 방식을 구분한다. 전자는 채택하지 않고 후자를 채택한다. MVP는 PostgreSQL JOIN·재귀 CTE 기반 SqlGraphAdapter로 시작한다. 시나리오 A/B/C의 관계 깊이는 1~2이고 반복 VOC 급증은 집계 질의다. “그거 그냥 JOIN 아니냐”에 대해서는 현재 규모에서는 맞다고 인정한다. 전용 Graph Store는 빼지 않되, MVP에 도입하지 않는다.

Graph가 실제로 유리해지는 지점: Remote Agent 위임 토폴로지는 관계가 외부로 뻗고 깊이가 가변이며 PostgreSQL FK에 없다. Case → Evidence → Document → Policy → Decision → Action 설명 경로도 고정 깊이가 아니다. 현재는 Team 2개와 Remote PoC 1개, 위임 깊이 2이므로 그래프 저장소가 필요하지 않다.

판단이 뒤집히는 조건은 Remote A2A Agent 2개 이상, 정책 계층 상속 도입, SQL 경로의 근거 포함률 미달이다.

11. 6명 팀 역할 분담

Core를 “Coordination 로직 담당”과 “Backend 구현 담당”으로 쪼개지 않는다. 같은 기능 흐름에서 정책과 실제 무결성 구현이 서로 붙어 있기 때문에, Core 1은 Case Runtime을, Core 2는 Access/Action을 각각 end-to-end로 담당한다.

Agent Team은 Tool을 직접 호출하지 않는다. 읽기는 Context Broker가 미리 제공하고, 쓰기는 ActionProposal로 반환한다. 따라서 Team 개발자 3명은 Core 2 인터페이스를 보지 않아도 된다. 두 Core의 접점은 ExecuteAction / ActionResult 한 쌍이다.

심사 Q&A

“Sierra나 Decagon이 이미 하는 거 아닌가요?”

고객응대 자체가 아니라, 멀티에이전트 고객운영의 통제·검증층이 주장이다. Team·Controller·A2A, 승인 경계, 재생 가능한 evidence와 평가 하네스를 한 실행 구조로 검증한다.

“그래서 자동화율이 몇 %인데요?”

분모·표본·CI를 함께 제시한다. 알파 전에는 “측정 중”이라고 답한다.

“기존 헬프데스크에 붙이면 되잖아요?”

대체가 아니라 그 위의 실행·검증층이다. 기존 Case 접점 위에서 승인·상태·evidence·감사를 통합한다.
