## "CS를 통한 상품 재기획팀"이 왜 기각되는가

정직하게 밝힌다. 이 아이디어 그대로는 Team이 아니다.

1. 출력이 "CS 사건 종결에 필요한 조치"가 아니라 상품기획자의 의사결정 참고자료다 — 코어 루프 밖.
2. "어떤 상품을 다시 설계해야 하는가"에 대한 Olist 정답셋이 없다.
3. 고객 문의가 실제 시장 수요를 대표한다는 보장이 없다 (jh 트랙 C가 기각된 이유와 동일).
4. 제품 개선안의 정확성을 held-out 거래로 직접 채점할 방법이 없다.

강등판으로만 살아남는다: **CS Voice-of-Customer Analytics 모듈** (SEL과 같은 배치 성격).
출력도 "재기획안"이 아니라 이 정도로 제한해야 정답셋이 유지된다.

```
상품 X에서 반복된 배송·파손·사이즈 관련 사건 수
상품 X의 낮은 리뷰 점수 및 불만 유형
동일 카테고리 상품 대비 사건률
근거 이벤트 목록
```

"그러므로 상품 Y를 새로 기획하라"까지 가면 다시 정답셋 없는 제안이 되어 기각된다.

## 대신 통과하는 것 — Case-grounded Commerce Handoff

핵심 재정의: **"좋은 추천인가?"를 평가하지 않는다.** 대신 이렇게 묻는다.

> 제안된 상품이 과거의 실제 거래 관계와 일치하는가?

미래를 예측하지 않고, 이미 일어난 실제 거래를 train/test로 나눠 "held-out 거래와
일치하는가"만 본다. LLM이 카탈로그를 보고 "아마 잘 맞을 것"이라 만든 후보는 정답셋이
없는 지어낸 값이므로 원천 금지한다.

### 후보 소스 4가지로만 제한

```
candidate_source ∈ {
  same_order_observed          동일 주문 내 실제 동시구매 상품
  same_customer_future_order   동일 고객의 실제 다음 구매 상품
  case_event_completed_replacement   case_events에 실제 완료된 교환·대체 상품
  same_category_observed_purchase    같은 카테고리에서 실제로 구매된 상품
}
```

"고객 문제에 가장 적합한 대체상품"처럼 판단이 들어가는 항목은 Olist만으로는 정답셋이
없으므로 명시적으로 금지한다.

### 정답셋 (실제 데이터 필드 기준)

| 기능 | 정답셋 | 데이터 필드 |
|---|---|---|
| 고객의 실제 다음 구매 | 기준 주문 이후 고객이 실제 구매한 첫 상품 | `customer_unique_id`, `order_purchase_timestamp`, `order_id`, `product_id` |
| 동시구매 교차판매 | 기준 주문과 실제로 함께 구매된 상품 | `order_id`, `order_items.product_id` |
| 상품 대체 후보 | 동일 사건에서 실제 교환·대체가 실행된 상품 | `case_events`의 `replacement_product_id`, `action_completed` |
| 상품군 대체 | 기준 상품과 같은 카테고리에서 실제 구매된 상품 | `product_id`, `product_category_name` |

Olist의 `customer_unique_id`는 여러 주문을 같은 고객으로 실제 연결하고([Olist 데이터 모델](https://deepwiki.com/olist/work-at-olist-data/3-olist-e-commerce-data-model)),
`order_items`는 주문별 상품·판매자·가격을 제공하므로 이 레이블들은 지어낸 값이 아니라
실제 거래에서 나온다.

**단, 재구매 고객은 전체의 3.04%(2,875명)로 희박하다** (WebSearch로 확인된 실측치).
그래서 "동일 고객의 실제 다음 구매"는 정답셋이 존재하되 희박하다고 명시하고,
1차 범위에서는 **동시구매(same_order_observed)와 case_events 완료 대체**부터 시작하는
편이 안전하다.

### 학습·평가 방식

```
과거 주문 80% : 상품 관계 생성 (train)
이후 주문 20% : held-out 정답셋 (test)
```

- Recall@K — 실제 후속구매 상품이 후보 K개 안에 들어왔는가
- MRR — 실제 상품의 순위
- Coverage — 근거를 생성할 수 있는 고객·상품의 비율
- **Abstention accuracy** — 근거가 없을 때 정직하게 "제안 불가"라고 했는가

마지막 지표가 특히 중요하다. 재구매 이력이 없는 고객에게 억지로 상품을 만들면
임의배정 금지 원칙에서 바로 탈락한다.

### 코어 루프 필요성 — "추천 배너"면 기각

```
접수 → 이슈·주문 식별 → 사건 근거 수집 → 해결안 제안
  → 상업 후속조치 후보 생성 → CS 담당자 검토 → 고객 동의/승인
  → 발송 또는 조치 기록 → 종결 → 결과 집계
```

"문제가 해결됐으니 관심 상품도 보여준다"는 코어 루프와 무관하므로 기각이다.
통과하려면 다음 중 하나여야 한다.

- 파손·분실 상품의 실제 대체상품 제안
- 품절·배송불가 상황의 실제 대체 주문 제안
- CS 보상·교환과 결합된 후속 구매 조치
- 고객이 문의한 상품과 실제 거래상 연결된 상품 제안

## Team 신설 판정 — Commerce Handoff Team

이름은 "추천 Team"이 아니라 **사건 근거 기반 상업 후속조치 Team**이다.

### FILTER 1~3 (에이전트급 판정)

| 필터 | 판정 | 이유 |
|---|---|---|
| FILTER-1 비정형 입력 | 통과 | 고객 문의·상품명·사건 내용에서 기준 상품·이슈를 추출해야 함 |
| FILTER-2 규칙만으로 못 정하는 판단 | 통과 | 사건 의미·상품 관계·구매 이력·교환 가능성을 함께 판단 |
| FILTER-3 상황별 도구 조합 | 통과 | `case_events` + 주문 이력 + 카탈로그 + 정책/재고 정보를 상황별로 조합 |

### 4축 비교 (ORD·LOG와 최소 둘 이상 달라야 함 — 실제로는 넷 다 다름)

| 축 | ORD / LOG | Commerce Handoff |
|---|---|---|
| 권한 경계 | 주문·반품·환불 또는 배송 처리 | 교환·대체·후속구매 "제안" + 고객 동의 요청 (실행 권한 더 낮음) |
| 외부 대기 주체 | 판매자·물류사·결제 시스템 | 고객의 선택·동의, 상품/재고 시스템 |
| 지식 범위 | 주문정책·배송정책 | 카탈로그·상품관계·거래 이력·상업 제안 정책 |
| 실패·재시도 | 배송 조회·환불 처리 재시도 | 상품 품절·가격 변경·고객 미응답·제안 만료 재시도 |

### Team Contract 초안

```
입력: resolved_case_id, order_id, product_id, issue_code
출력: evidence-backed action candidates
금지: 거래 근거 없는 상품 생성, 수요 예측, 임의 할인
승인: 고객 동의 및 CS 담당자 승인 필수
실패: 근거 부족이면 abstain (제안 없음으로 답변)
재시도: 고객 미응답·상품 품절·가격 변경에 한정
```

## 최종 권고

A-COP에 실제로 추가할 가치가 있는 것은 하나다.

> 기존 ORD/LOG가 해결한 사건을 입력으로 받아, 실제 거래·카탈로그·완료된 case event에
> 근거한 대체상품 또는 후속구매 조치를 생성하고, 고객 승인 후 실행·기록하는
> **Commerce Handoff Team**.

초기 구현 순서(재구매율이 낮으므로 안전한 순서대로):

1. 동일 주문 내 실제 동시구매 상품
2. `case_events`에 실제 완료된 대체상품
3. 동일 고객의 실제 후속구매 (표본 희박 — 나중에)
4. 근거가 없으면 제안하지 않는다 (abstain)

이 범위를 벗어나 계절성·관심 키워드·수요 예측·신규 상품 재기획으로 확장하면
기존 판정 기준상 다시 기각하는 것이 맞다 — jh의 트랙 C가 기각된 것과 같은 이유다.

## 착수 Team 구성 변화

착수 2개(ORD·LOG) 확정은 유지하되, Commerce Handoff는 **3번째 Team 후보**로 추가된다.
`A-COP_아이디어_통합분석.md` §3-2가 "착수 2개 + Phase 2 Team 1개를 더한 3개가 현실적
상한"이라 이미 명시했으므로, Commerce Handoff가 그 3번째 자리의 유력 후보가 된다 —
다만 판매자 커뮤니케이션·소명, 결제·정산과 우선순위를 다시 비교해야 한다.
