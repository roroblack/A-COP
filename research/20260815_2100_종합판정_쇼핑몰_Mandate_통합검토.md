# 쇼핑몰 확장안 + Mandate/Outcome 확장안 — 종합 판정

작성일: 2026-08-15. 기준선: `A-COP_구현계획서_v6.md`.
근거: `research/mall_review_codex.md`(Codex 상세 리뷰, 22건), `research/mandate_review_codex.md`(Codex 상세 리뷰, 22건),
AP2/UCP 웹 검증(이 문서에서 직접 수행).

## 결론

두 확장안 다 **조건부 채택**. 단 따로 결정하지 않는다 — 같은 세 가지 v6 원칙을 동시에 깨고 있어서
한쪽만 열면 다른 쪽에서 반드시 재론된다.

## 두 확장안이 동시에 깨는 v6 원칙

| 깨진 v6 원칙 | 쇼핑몰 확장안 | Mandate/Outcome 확장안 |
|---|---|---|
| MCP는 read-only 3개 (`CLAUDE.md` §0.2) | `create_order`, `request_return` 쓰기 tool 제안 | `mandate.update`, `mandate.revoke` 쓰기 tool 제안 |
| 외부 REST 정확히 5개 (v6, DoD 13) | — | mandate 생성/수정/철회 endpoint 추가 |
| Team은 side effect 실행 금지, `ActionProposal`만 반환 | Return Team이 Marketplace Return Adapter를 직접 호출 | (이 부분은 지킴) |

이게 우연이 아니라는 판단 근거: 실제 커머스를 붙이려면 어딘가에 쓰기 경로가 필요해지고,
Mandate/Outcome은 그 쓰기 경로에 "권한이 있는가"를 얹으려는 시도이기 때문이다.
따라서 **"MCP 쓰기를 열 것인가"가 두 확장안의 공통 전제**다.

## 웹 검증 — Mandate라는 이름은 임의가 아니다

Mandate 문서 자체 검토(Codex)는 외부 표준의 사실 여부를 판단 근거로 쓰지 않았다.
이 문서에서 별도로 확인한 결과:

- **AP2(Agent Payments Protocol)** — Google, 2025-09 발표. 모든 에이전트 구매를
  서명된 Mandate 3종(Intent/Cart/Payment)으로 표현하고 W3C Verifiable Credentials로 실어 나른다.
  런치 파트너 60곳(Mastercard·PayPal·Coinbase·Amex·Salesforce). v0.2가 2026-04, 2026-05 FIDO Alliance 기여.
- **UCP(Universal Commerce Protocol)** — Google, 2026-01 NRF 발표. Shopify·Etsy·Wayfair·Target·Walmart
  공동 개발. **AP2와 호환되며 A2A·MCP로 통합**된다고 명시.

즉 `Mandate`는 A-COP이 지어낸 이름이 아니라 AP2의 표준 용어이며, UCP가 A2A/MCP와 통합된다는 사실은
A-COP이 이미 확정한 두 프로토콜과 직접 맞물린다. "왜 이 개념을 지금 검토하냐"에는 외부 근거가 있다.

출처: [Announcing AP2 — Google Cloud](https://cloud.google.com/blog/products/ai-machine-learning/announcing-agents-to-payments-ap2-protocol),
[AP2 Specification](https://ap2-protocol.net/en/specification),
[Under the Hood: UCP — Google Developers](https://developers.googleblog.com/under-the-hood-universal-commerce-protocol-ucp/),
[Building UCP — Shopify Engineering](https://shopify.engineering/ucp)

## 예산 산수 재검증 (Codex 지적 #17을 직접 확인)

구현명세 642~644행:
```
= 6 × 50,000
+ 20 × 100,000
= 1,800,000 KRW
```
직접 계산: 6×50,000 = 300,000, 20×100,000 = 2,000,000, 합계 **2,300,000원**. 180만원이 아니라 230만원.
같은 문서 1482행은 또 다른 분해(30만+30만+20만+100만=180만)를 쓴다.
**한 문서 안에 서로 다른 예산 계산 두 개가 공존**하며 둘 다 표시값 180만원과 정확히 일치하지 않는다.

## 진짜 기여로 보이는 것

Mandate/Outcome 문서의 핵심 가치는 **"Action success ≠ Outcome success" 구분**이다.
v6에서 `action_requests.status = succeeded`는 "환불 요청을 보냈다"이지 "고객이 환불받았다"가 아니다.
이 공백은 v6에 실재하며, 쇼핑몰을 붙이는 순간(실제 배송·환불이 생기는 순간) 바로 문제가 된다.
두 확장안을 한 세트로 봐야 하는 실질적 이유가 이것이다.

Codex 판단(mandate_review #5)으로는 이를 위해 새 Case 상태를 만들 필요는 없고,
`Outcome SATISFIED`일 때만 `resolved`로 가는 close guard만 추가하면 된다.

## 먼저 정해야 할 것 3가지 (이 순서로 결정하면 나머지가 따라온다)

1. **MCP 쓰기를 열 것인가.** 두 확장안이 동시에 요구한다. 열면 `CLAUDE.md` §0.2를 고쳐야 한다.
2. **실제 판매를 할 것인가, Mock/Shadow까지만 할 것인가.** Mock/Shadow로 멈추면
   통신판매업 신고·청약철회·PII 국외이전·PG 정산 4개 법규 리스크가 전부 사라진다.
3. **Mandate/Outcome을 외부 통합 계약에 노출할 것인가, Case Runtime 내부 정책 모델로 둘 것인가.**
   내부로 두면 REST 5개·MCP 3개 충돌이 사라진다.

세 개 다 "닫는 쪽"을 고르면 두 리뷰의 치명적 항목(쇼핑몰 7건 + Mandate 4건 = 11건) 중
법규·계약 노출 관련 8건이 자동 해소된다. 남는 3건(Team이 Adapter 직접 호출, Mandate 권한 matrix 부재,
철회 타이밍 미정의)은 순수 설계 문제라 고치면 된다.

## 각 리뷰의 권고 요약

**쇼핑몰**(`mall_review_codex.md` 상세): Simulation Commerce(Mock) → Shadow → 팀 내부 저액 Live 단계.
일반 고객 대상 해외구매대행·PG·무인 환불은 기각. Mock 단계만으로도 Case lifecycle·WAIT/RESUME·
`ActionProposal`·idempotency 검증 목적은 6명 8~10일로 대부분 달성.

**Mandate/Outcome**(`mandate_review_codex.md` 상세): MVP는 Mandate 최소 Guard + Outcome 최소 close gate로 축소.
API·계약·감사·실패 전이·권한 주체를 먼저 고정하는 조건으로 채택. 신규 MCP write tool·REST endpoint·
별도 baseline UI는 제외.

## 문서 신뢰도로 지적된 것 (요약)

- Mandate 브리핑은 "기존 구조를 건드리지 않는 확장"이라 단정하지만 기술계획서엔 새 REST+테이블 2개+MCP tool.
- 쇼핑몰 브리핑 6명 역할표에 **평가 담당이 없다** — v6가 확정한 "검증&프론트 1명"이 누락.
- 쇼핑몰 브리핑 최종판정 "PASS WITH LIVE GATES"가 "PG 미결정·일반고객 결제 금지"와 한 블록이라
  전체 PASS로 오독 가능.
- 근거 없는 수치: Mandate "violation 목표 0"(측정 설계 없음), 쇼핑몰 "전환 40%·SLA 90%"(예시인데 기준처럼 보임).
