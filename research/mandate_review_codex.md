# A-COP Mandate / Outcome 계획서 검토

## 결론

**조건부 채택**이다. Mandate는 v6의 `ActionProposal`·`action_requests`·Human Approval과 이름만 다른 중복이 아니라, 시스템 capability/실행 승인보다 앞선 **이번 Case에서 고객이 Agent에게 부여한 목적·조건·범위**를 표현하는 의미 층이다. Outcome도 단순한 `TeamResult.outcome`의 이름 변경은 아니지만, v6의 Case 완료/종료 판단을 고객 목표와 검증 조건으로 구체화하는 보완층이다. 다만 현재 제안은 “기존 구조를 건드리지 않는다”는 선언과 달리 v6의 REST 5개·MCP 3개·계약 `extra=forbid`·DDL·Case 종료 전이와 충돌한다. 따라서 MVP는 Mandate의 최소 Guard와 Outcome의 최소 close gate로 축소하고, API·계약·감사·실패 전이·권한 주체를 먼저 고정하는 조건으로 채택한다.

## 판정 기준

인용은 파일명과 줄 번호로 표시했다. 새 문서의 예시와 주장은 v6 및 실제 구현 계약과 대조했다. 외부 기술 동향의 사실 여부는 이 검토의 채택 근거로 사용하지 않았으며, 문서 내부 정합성과 구현 가능성을 우선했다.

## 우선 수정안

1. **계약을 먼저 결정한다.** `CaseOutcome`과 Mandate를 Case Runtime 내부 모델로 둘지, v6 §21의 versioned contract로 외부에 전달할지 선택한다. MVP는 내부 모델 + audit metadata로 제한하는 편이 안전하다.
2. **권한과 상태 매핑을 먼저 고정한다.** 생성·수정·suspend·revoke 주체와 `Outcome status → CaseStatus` 매핑, 승인된 action의 revoke/expire 규칙을 표로 만든다.
3. **API/MCP를 기준선에 맞춘다.** 신규 MCP write tool은 제거하고, REST 5개를 늘리지 않는 MVP 경로를 선택한다. 늘려야 한다면 v6 §13/DoD 13/handoff를 동시에 개정한다.
4. **관측 가능한 평가로 바꾼다.** 조건별 expected/actual/source/event와 분모·분자를 정의하고 v6 평가 하네스에 fixture를 추가한다. 근거 없는 `0`, “작음”, “2~3주” 표기는 삭제한다.

## 3분류 요약

### 먼저 결정해야 할 것

- Mandate/Outcome을 외부 통합 계약에 노출할지, Case Runtime 내부 정책 모델로 제한할지.
- Mandate를 부여·수정·철회할 수 있는 actor와 scope.
- Outcome 조건의 AND/OR·부분 이행·외부 이벤트·revoke/expire 시 실행 규칙.
- 별도 테이블을 v6 DDL에 정식 추가할지, MVP에서 `state_json`·`case_events`로 축소할지.

### 고쳐야 할 것

- REST/MCP 추가안과 v6의 5 REST·3 read-only MCP 계약의 충돌.
- `ActionProposal`/`ExecuteAction`/audit에 Mandate version과 판정 메타데이터를 연결하는 계약.
- Outcome close gate와 기존 `running → resolved` 전이의 연결.
- 권한 주체, 실패·거부·만료·부분 이행·철회 경로.
- HTML의 “기존 구조 변경 없음”, 규모 등급, 0 목표, 2~3주 표현과 교환/환불 시나리오 불일치.
- 생성 / 검증·통합 / 대기 실소요일 및 기존 범위에서 제거할 항목.

### 무시 가능

- 별도 Mandate/Outcome Microservice를 만들지 않는 결정.
- Commitment와 Resolution Proof를 기존 `case_events`·action result·Evidence·audit에 우선 흡수하는 결정.
- A2A transport 자체를 재설계하지 않고 최소 subset projection을 향후 확장점으로 남기는 방향. 단, MVP의 실제 구현이 아니라 계약 문서 수준으로 제한해야 한다.
