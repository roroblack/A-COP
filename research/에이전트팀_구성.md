# A-COP 팀 모듈 구성

기준: `A-COP_구현계획서_v7.md` + `A-COP_확장안_구현명세_B2B중심_2026-08-15.md`
제약: 6명 / 10주

분류는 **어느 자리에 들어가는가**로 한다. 내부에서 LLM을 쓰는지는 Team이 정하는 구현 선택이며
자리 판정과 무관하다. v7 7절: "내부 Agent 수와 LangGraph/Subgraph 사용 여부는 Team이 결정한다."

| 슬롯 | 모듈 | MVP 착수 |
|---|---|---|
| 팀 모듈 | Procurement + Order & Payment | 착수 — 통합 (v7 §337) |
| 팀 모듈 | Fulfillment & Logistics | 착수 (v7 §337) |
| 팀 모듈 | VOC & Store Manager | 착수 — 배치/Team 계약 (v7 §337) |
| 팀 모듈 | Return, Refund & Evidence | Registry 계약 + Mock (v7 §337) |
| 팀 모듈 | Response Generation & Review | 미정 — v7 §337 목록에 없음. 아래 참조 |
| A2A 모듈 | Catalog & Verification | 착수 — 별도 프로세스 fixture로 실제 왕복 |

v7 §337이 착수 목록을 명시한다. LOCAL 3개(Procurement+Order 통합 / Fulfillment / VOC)와
A2A 1개(Catalog & Verification)가 실제 구현이고, Return & Refund는 Registry 계약과 Mock으로 남는다.

같은 절이 단서를 붙인다. **Registry 등록은 실제 구현을 의미하지 않는다.**
등록된 capability가 있어도 실행 가능한 module·fixture·contract test가 없으면 구현 완료로 세지 않는다.
따라서 Return & Refund는 슬롯 자격이 있고 Registry에 등록되지만 착수 카운트에는 들어가지 않는다.

Response Generation & Review는 v7 §337 목록에 없다. cy의 개정 설계가 v7 이후에 나왔기 때문이다.
넣으려면 LOCAL이 4개가 되므로 §337 목록을 개정하거나 다른 하나를 Mock으로 내려야 한다.
이것은 재산정 대상이며 지금 단정하지 않는다.

Procurement가 10주 안이라는 점이 중요하다. v7 §1-2의 "재고·가격·발주·배송·정산은 vision"은
**전면 Ops 자동화**를 가리키고, 검증 쇼핑몰의 발주 실행 자체는 착수 범위다.
검증 쇼핑몰 기획서도 공급처 거절 시 `Procurement 실패 → unknown/escalated → 대체 제안` 경로를 설계해 두었다.
Mock으로 남는 것은 국외 배송·해외 구매대행의 실제 Live 연동이다.

**슬롯 자격과 착수 시점은 다른 축이다.** 자격이 있어도 평가 여력과 데이터 사정으로 뒤로 밀 수 있다.

## 세 질문을 분리한다

이전 정리에서 이 셋을 하나로 묶어 판정한 것이 오류였다.

| 질문 | 무엇이 정하나 | 결과 |
|---|---|---|
| 이 자리에 들어가는가 | Team Contract를 만족하는가 | 팀 모듈 / A2A 모듈 / 아님 |
| 안에서 LLM을 쓰는가 | Team이 정한다. Core는 관여하지 않는다 | 분류에 영향 없음 |
| 채점할 수 있는가 | 정답셋·임의 배정·평가 여력 | MVP 착수 / Phase 2 |

FILTER-1·2·3(비정형 입력 / 규칙으로 못 적는 판단 / 도구 조합)은 **두 번째 질문**의 도구다.
"이 모듈 안에 LLM이 필요한가"를 가르는 데 쓰고, 팀 모듈 자격을 가르는 데 쓰지 않는다.

## 팀 모듈 슬롯에 들어가는 조건

v7 7절과 8-3절 기준이다. 넷을 모두 만족하면 팀 모듈이다.

1. Capability·책임·권한·지식·Tool 경계가 독립된다
2. `TeamTask`(capability + ContextPack)를 입력으로 받는다
3. `TeamResult`(answer / warnings / decisions / action_proposals / need_more_context)를 반환한다
4. side effect를 직접 실행하지 않고 `ActionProposal`만 반환한다

내부 구현은 자유다. LLM 다중 에이전트여도 되고, SQL 집계와 임계값 규칙이어도 된다.
Core는 `TeamManifest`와 표준 Contract만 보고 graph·prompt·retrieval을 import하지 않는다.

|---|---|---|---|---|
| Order & Payment | 주문 조회, 결제 상태, 취소·부분취소 제안, 상태 재진입 | PG·마켓플레이스 주문 API | 상태 변경은 Controller→Core 2→승인 | LLM 판단 + 결정론 계산 |
| Fulfillment & Logistics | 배송 추적, 지연·분실·통관 분기, 선제 알림 제안 | 택배사·통관·판매자 소명 | 조회·알림 제안만. 상태 변경·보상은 Core 2 | LLM 판단 + 조회 tool |
| Return, Refund & Evidence | 반품·교환 사유, 증빙, 정책 판정, 환불·반품 제안 | 고객·판매자·반품 adapter | 반품 Case와 refund ledger 분리. 실행은 승인 | LLM 판단 + 정책 RAG |
| VOC & Store Manager | 이상징후·반복 불만·공급처 성능 감시, 리포트·알림·위임 제안 | 내부 운영자·대상 Team | 직접 호출·직접 side effect 금지. 위임은 Controller 경유 | 착수 시점은 집계·임계값 규칙 |
| Response Generation & Review | 판단 결과를 고객 문장으로 생성(GEN)하고 검증(REV), 반려 시 재작성 | 없음. 실패 시 운영자 | side effect 없음. `ActionProposal`도 내지 않음 | 톤 결정은 규칙, 생성은 LLM, 검증은 결정론 3 + LLM 1 |
| Procurement | Quote 승인 후 공급처 구매·대체·재시도, 거절 시 `unknown`/escalated 분기 | 공급처·마켓플레이스 | 구매 실행은 승인·idempotency·금액 한도 | 착수. Order & Payment와 통합해 하나의 모듈로 구현 |

제품은 하나의 Runtime 위에 CS Pack(10주)과 Commerce Ops Pack(vision)을 둔다.
다만 팩 경계와 착수 경계가 같지 않다. v7 §1-2가 vision으로 둔 것은 재고·가격·발주·배송·정산의
**전면 운영 자동화**이고, 검증 쇼핑몰을 돌리는 데 필요한 발주 실행은 §337에서 착수 범위에 들어 있다.
즉 Procurement는 팩으로는 Ops 쪽이지만 착수로는 10주 안이다.

### 인라인 분류와 VOC의 소관

v7 §7-A에 따라 Case 생성 뒤 `classifying` 단계에서 `sentiment`·`intent`·`issue_code`를 항상 생성한다. 이는 VOC Team의 업무가 아니라 진입·분류 층의 공통 처리다. VOC & Store Manager는 이미 분류된 Case events를 받아 이상징후·반복 불만·공급처 성능을 감시하고 리포트·알림·위임 제안을 만든다.

### 모듈별 평가 지표

평가 여력이 실질적인 제약이라면 모듈마다 별도 측정 축을 잡아야 한다. 지표는 같은 golden/holdout 실행에서 모듈별 분모를 기록한다.

| 모듈 | 측정 항목 |
|---|---|
| Order & Payment | intent/issue 정확도, 주문·결제 상태 근거 정합률, 취소·부분취소 ActionProposal 유효성, 금액·idempotency 차단율, 스키마 준수율 |
| Fulfillment & Logistics | 배송 상태·지연 issue macro-F1, 운송장/예정일 근거 정합률, 지연·분실 분기 정확도, 불필요한 escalation 비율, p95 처리 지연 |
| Return, Refund & Evidence | 반품·교환·환불 intent/issue macro-F1, 증빙 recall, 정책 근거 정합률, 환불 가능성 과잉 단정률, 승인 전 side effect 0건 |
| VOC & Store Manager | alert precision/recall, 급증 탐지 지연, 반복 불만 issue macro-F1, 위임 제안 precision, 오탐 alert 비율 |
| Response Generation & Review | 결정론 검증 1차 통과율, 반려 사유 분포, 근거 인용 정합률, escalation 비율, 개인정보 노출율, 톤 사람 라벨 agreement |
| Catalog & Verification (A2A) | SKU/Variant·가격·규제 검증 정확도, evidence manifest 완전성, input-required/재개 성공률, LOCAL/A2A canonical 결과 일치율, timeout·auth failure 처리율 |

### VOC를 팀 모듈로 두는 이유

v7이 VOC를 Agent Team으로 등록하고, 기존 배치 파이프라인을 "VOC Team을 주기적으로 실행하는
배치 adapter/worker"로 규정했다. 즉 배치는 실행 형태이지 슬롯이 아니다.

슬롯 자격은 네 조건으로 판정한다. VOC는 집계·시계열·임계값이라는 고유 지식,
관측·알림 tool 경계, 다른 Team에 위임을 제안하는 고유 권한을 갖는다. 조건을 만족한다.

착수 시점의 내부 구현은 고정 공식이다. `오늘 count >= max(5, 1.5 × 최근 7일 평균)` 이고
`오늘 count − 평균 >= 3`. 이것은 구현 선택이지 슬롯 자격 문제가 아니다.
나중에 원인 축 판별과 위임 대상 선택에 LLM을 넣더라도 Registry 레코드와 Contract는 바뀌지 않는다.
그때 필요한 것은 위임 판단 골든셋이고, 그것이 착수/승격을 가르는 세 번째 질문에 해당한다.

### Response Generation & Review를 팀 모듈로 두는 이유

출처는 cy의 `REV, GEN 설계` · `REV,GEN 요약`(2026-08-16)이다. 이전 제안에서 요구하던
새 Port·Registry·Case 상태·별도 반려 카운터가 전부 빠지고, 하나의 Team Module로 정리됐다.
GEN과 REV는 별도 팀이 아니라 이 모듈 안의 두 호출이다.

슬롯 조건 넷을 만족한다. Capability(응답 생성·검증)와 지식 범위(톤 프로파일·금칙 표현·검증 규칙)가
독립되고, `TeamTask`로 3팀 판단 결과와 감성·긴급도를 받으며, side effect가 없다. 재시도 3회 루프가
모듈 내부에 있어 Controller의 loop guard와 Case 상태를 건드리지 않는다.

cy 설계의 표기는 v7 §21의 canonical `TeamResult`에 다음처럼 매핑한다.

| cy 표기 | `TeamResult` 매핑 |
|---|---|
| `final_response_text` | `answer` |
| `status` | `outcome` (`completed` / `escalated`) |
| `retry_count`, `review_history` | `decisions[]` |
| 반려 사유 | `warnings[]` |
| `escalation` | `outcome='escalated'` + `next_action` |

`TeamResult`는 `ConfigDict(extra='forbid')`이므로 cy 표기 필드를 그대로 반환할 수 없다. 계약을 바꾸지 않고
정규화한다. 계약 필드를 추가하거나 바꾸면 `contract_version`을 올리고 회귀 테스트를 함께 가져와야 하므로,
이번 개정은 v7 §21 계약과 기존 LOCAL/A2A canonical JSON 비교를 유지한다.

분리 근거는 중복 제거다. 문장 생성과 검증을 각 업무 모듈 안에 두면 톤 기준이 모듈 수만큼 갈리고
검증 로직도 그만큼 중복된다. 하나로 모으면 모든 응답이 같은 기준을 지난다.
생성과 검증을 같은 호출로 합치지 않는 이유는 자기 출력을 자기가 채점하면 후해지기 때문이다.

Human Approval과 겹치지 않는다. 승인은 고위험 케이스에서 사람이 "이 조치를 실행해도 되는가"를 보고,
응답 검증은 모든 케이스에서 "이 문장을 보내도 되는가"를 먼저 본다. 대상이 다르다.

v7 방향과도 맞물린다. v6 → v7 변경 요약의 할루시네이션 방어 항목이
`ActionProposal`의 대상·금액·수량·scope를 실행 직전 코드로 재검증하고 프롬프트가 아니라
강제 검사를 방어선으로 삼는다고 했다. 이 모듈은 같은 원칙을 문장 쪽으로 확장한다.

**착수 시 두 가지를 조정한다.**

- REV 4항목 중 톤 적합성은 재시도 사유에서 뺀다. 과잉약속(금칙어 사전), 근거 인용(원본
  `refund_amount`·`policy_ref`와 값 대조), 개인정보(정규식) 셋은 결정론적이라 자동 채점되지만
  톤은 사람 라벨이 필요하다. 톤은 경고만 남기고 재시도를 유발하지 않게 해야 재시도율 지표가 흔들리지 않는다.
- 결정론 검사를 LLM 검사보다 먼저 돌린다. 값 대조와 정규식이 먼저 거르면 LLM 호출이 줄고 재현성이 산다.
  자기채점 방지 논거는 LLM 판단에만 해당하고 결정론 검사에는 해당하지 않는다.

전용 지표는 1차 통과율, 에스컬레이션 비율(목표 5% 이하), 반려 사유 분포, 개인정보 노출율(목표 0%)이다.
개인정보 발견 시에는 재시도 없이 즉시 운영자에게 넘긴다.

## A2A 모듈 슬롯

| 모듈 | Capability | 왜 Remote인가 |
|---|---|---|
| Catalog & Verification | 상품·SKU·가격·규제·Variant 검증, Quote artifact 생성 | 공급처·외부 카탈로그라는 조직 밖 주체와 왕복한다 |

`execution_type: A2A`로 Registry에 등록된다. Agent Card, input-required 왕복, Artifact,
장기 실행, 인증·실패·취소를 실제로 검증하는 것이 A2A 채택 목적이다.

catalog snapshot과 quote만 반환하고 구매·등록 side effect는 금지한다.
LOCAL과 실행 경로가 다르므로 LOCAL 여력 계산과 별도로 보되, 평가셋 부담은 따로 진다.

A2A 모듈 개수도 상한이 아니다. Registry 등록 대상이며, 구조가 바뀌는 지점은 개수가 아니라 위임 깊이다.

## 슬롯에 들어가지 않는 것

| 후보 | 이유 | 실제 위치 |
|---|---|---|
| Customer Operations & Complaint | 여러 모듈의 권한·대기·지식을 포괄하는 합집합이라 경계가 독립되지 않는다 | Case intake·분류·에스컬레이션 층 |
| 환불 금액 계산, 반품 D-day 판정, 재고 누적 감지 등 개별 계산 | 독립된 권한·지식 경계가 없다. 다른 모듈의 업무 일부다 | 해당 팀 모듈의 tool·룰 |

GEN·REV는 이전 판정에서 "이미 계약에 있으므로 불필요"로 뒀으나 철회했다.
`TeamResult.answer` 필드가 있다는 것은 문장이 들어갈 자리가 있다는 뜻이지
누가 어떤 기준으로 만들고 무엇을 검사하는지가 정해졌다는 뜻이 아니었다.
개정된 설계가 새 컴포넌트 없이 하나의 팀 모듈로 정리되어 슬롯 조건을 만족하므로 팀 모듈로 옮긴다.

### jh 마케팅 확장안 8개

전부 새 슬롯이 아니다. 기존 모듈 안으로 들어간다.

| 항목 | 들어가는 곳 |

## 착수 판정 — 세 번째 질문

슬롯 자격이 있어도 아래를 만족해야 MVP에 넣는다.

```
정답셋 존재  AND  임의 배정 비의존  AND  코어 루프 필요  AND  평가 여력
```

평가 여력이 실질적인 제약이다. 모듈 하나마다 골든셋 라벨 축, 라우팅 평가 항목, Registry 레코드,
contract test, 프롬프트 버전, Context Pack 토큰 예산이 함께 늘어난다.

현재 표는 착수 자리를 남겨 둔 것이다. Bitext에 `cancel_order`·`get_refund`·`track_refund` 계열 intent가 이미 라벨링되어 있는지와 한국어 변환 품질이 확인되면, Order & Payment + Return의 사람 라벨 부담과 통합 근거를 다시 계산한다. 따라서 CS Pack 도메인 확정 후 재산정하기 전에는 LOCAL 착수 4개를 단정하지 않는다.

재산정 입력은 다음이다: CS Pack 도메인(Commerce) 확정, 모듈별 공개·스마트스토어·Olist 데이터의 실제 행/Case 수, Bitext intent 라벨과 라이선스 확인 결과, 한국어 번역·재작성 품질, golden 60/holdout 20의 모듈별 배분, 모듈별 사람 라벨 시간, Registry·contract test·라우팅 평가 축과 Context Pack 토큰 예산이다.

LOCAL 착수는 위 입력으로 재산정한다. 현재 표는 작업 가설이다.

| 착수 모듈 (v7 §337) | 골든셋 부담 |
|---|---|
| Procurement + Order & Payment | 재산정 필요. 공개 intent 라벨과 스마트스토어 Case 분포, 사람 라벨 시간이 확인되기 전에는 단정하지 않는다. 공급처 거절·대체 제안 경로가 축으로 추가된다 |
| Fulfillment & Logistics | 중간. 배송 상태·사유는 실데이터에서 상당 부분 나온다 |
| VOC & Store Manager | 작음. 내부 구현이 집계·임계값 규칙이다 |
| Return, Refund & Evidence | 착수 아님. Registry 계약과 Mock. 골든셋 부담 없음 |
| Response Generation & Review | 작음. 검증 3항목이 원본 데이터 대조로 자동 채점된다. 다만 §337 목록 밖이라 넣으면 LOCAL이 넷이 된다 |

재산정에서 정할 것은 Response를 §337 목록에 추가할지, 추가한다면 무엇을 Mock으로 내릴지다.
Return & Refund가 이미 Mock이므로 LOCAL 슬롯은 Procurement+Order / Fulfillment / VOC 셋이 차 있고,
Response를 넣으면 넷이 된다. Order와 Return의 통합 문제는 v7이 Return을 Mock으로 내리면서
이미 다르게 풀려 있으므로 재산정 대상이 아니다.

### 먼저 정할 것

먼저 정할 것은 SaaS와 Commerce를 동시에 고르는 일이 아니다. 하나의 Runtime 위에 CS Pack(10주)과
Commerce Ops Pack(vision)이 있고, 이 문서의 모듈은 Commerce 도메인의 CS Pack에 속한다. CS Pack의
도메인을 SaaS로 둘 것인지 Commerce로 둘 것인지가 실제 선택이며, 권고는 Commerce다. 검증 쇼핑몰과
실제 스마트스토어 데이터가 주문·배송·반품·리뷰 표현과 golden set을 하나로 정렬하기 때문이다.

팩 교체는 SaaS 팩 전체를 다시 만들지 않는다. Billing 하나를 stub으로 남기고 Registry 등록만으로
교체되는 contract test를 둔다. 골든셋을 SaaS에 붙이지 않아 슬롯 예산을 먹지 않게 하며, v7 §8-B의
“Team을 늘리는 일이 리팩토링이 되면 설계가 잘못된 것”이라는 기준을 실제로 검사한다.

## 확장 방법

새 모듈을 넣는 절차는 Registry 레코드 추가, 프롬프트 등록, 골든 케이스 추가 셋이다.
Controller·`TeamExecutorPort`·`TeamResult` 계약과 평가 하네스는 건드리지 않는다.

이것을 contract test로 증명한다. 새 모듈을 등록한 뒤 라우팅 → 실행 → `answer`/`warnings`/
`ActionProposal` 정규화 → 승인 대기 → 실패·재개를 확인하고, 기존 모듈 fixture의 결과가
변하지 않는지 회귀 비교한다. 통과하면 확장이 리팩토링이 아니라 등록임이 증명된다.

## 데이터 전제

데이터는 두 트랙으로 나눈다. 도메인 사실 트랙은 실제 스마트스토어 주문·반품·취소·교환·리뷰 데이터와
Olist이며, 표현·의도 트랙은 고객지원 문장의 다양화와 intent 학습을 위한 공개 데이터다. 실제 스마트스토어
데이터가 있다는 사실만 전제로 삼고 원문이나 개인정보를 이 문서에 옮기지 않는다. Olist는 주 소스가 아니라
스키마·관계 매핑 fixture와 비교 기준이다.

| 모듈 | 도메인 사실 트랙 | 표현·의도 트랙 |
|---|---|---|
| Order & Payment | 스마트스토어 주문·결제·취소 Case, Olist 주문·결제 관계 | Bitext의 `cancel_order`, 주문조회 표현, Kaggle Customer Service Conversations의 주문취소·계정 표현 |
| Fulfillment & Logistics | 스마트스토어 배송·지연·교환 상태, Olist 배송일·리뷰 관계 | Kaggle Customer Service Conversations의 배송·주문조회 표현, 보조 HuggingFace 전자상거래 데이터셋 |
| Return, Refund & Evidence | 스마트스토어 반품·교환·환불·증빙·정책 Case, Olist 관계 fixture | Bitext의 `check_refund_policy`·`get_refund`·`track_refund`, Kaggle의 환불요청 표현 |
| VOC & Store Manager | 스마트스토어 Case event·리뷰·반복 불만 집계, Olist 리뷰는 비교용 | Kaggle의 상품불만·계정문제 표현은 보조 입력이며 alert 정답은 도메인 트랙에서 만든다 |
| Response Generation & Review | 각 모듈의 근거·정책·ActionProposal와 스마트스토어 표현 | Bitext·Kaggle의 문장·톤 다양화, 한국어 번역·재작성 결과 |
| Catalog & Verification (A2A) | 스마트스토어 상품·SKU·Variant·가격, Olist 상품 관계 | 기타 HuggingFace 전자상거래 표현은 보조 자료. 검증 사실은 공개 문장으로 학습하지 않는다 |

리서치 문서에서 확인된 공개 데이터셋은 `Kaggle Customer Service Conversations`(1,002,235행),
`Bitext customer-support-llm-chatbot-training-dataset`(27개 intent·11개 카테고리),
`strova-ai/customer_support_conversations_dataset`(100% 합성·멀티턴),
`rjac/e-commerce-customer-support-qa`, `NebulaByte E-Commerce Customer Support Conversations`다.
Bitext와 Kaggle은 각각 원 라이선스·Kaggle 이용 조건·개인정보·재배포 조건을 확인해야 사용한다. Olist는
CC BY-NC-SA 4.0 조건을 지키며, 한국 정책·한국어 응대 정답으로 직접 쓰지 않는다.

v7이 확정한 golden 60건과 holdout 20건은 모듈별로 golden 10건씩 배정하고, holdout은 모듈별 3건씩
(18건)과 2건의 다중 모듈 통합 Case로 나눈다. 같은 Case가 여러 모듈을 지날 때는 각 모듈의 분모에
중복 집계하지 않고 통합 Case ID로 연결한다. 실제 라벨 수와 데이터 분포가 확인되면 이 배분을 재산정하되
총 60건·20건과 holdout 보존 원칙은 바꾸지 않는다.

파인튜닝은 공개 데이터 1차, 알파 실데이터 2차의 두 단계다. 1차는 라이선스 확인 후 Bitext를 중심으로
선별하고 Kaggle Customer Service Conversations를 표현 보조로 사용해 한국어로 번역·재작성한다. 2차는
비식별화한 알파 Case의 성공·실패·보류·사람 수정 결과를 소규모로 추가한다. 목표는 출력 스키마 준수,
도메인 어휘, 근거·승인·보류를 표시하는 톤이며 현재 주문·가격·환불 사실을 모델에 주입하지 않는다.
실데이터가 500건 미만이면 epoch 1~2회로 제한한다. 공개 데이터는 대부분 영어라 번역 품질과 스마트스토어
실데이터의 표현 차이가 남고, 데이터셋별 라이선스·개인정보·재배포 조건도 확정 전까지 확인 필요다.

되살아나는 정답셋은 주문·취소·반품·교환 상태 분류와 환불 가능성, 배송 지연·반품·교환 사유,
리뷰 이슈 분류다. 동시구매는 집계만 되살아나고 추천 적중 정답은 없다.

데이터가 입점 판매자 관점이라는 제약이 모듈 경계를 직접 제한한다. 해당 판매자의 주문·상품·재고·
리뷰와 판매자 정책으로 권한이 한정되므로 플랫폼 전체 수요, 다른 판매자 매출,
PG·택배사 내부 사정, 중재 결과를 사실처럼 추론할 수 없다.

개인정보가 포함되므로 v7 경계를 그대로 적용한다. 저장·LLM 전달 전 가명화·마스킹,
join key 분리 보관, ContextPack에 최소 증거만, 집계 alert에 재식별 방지 최소 기준,
골든셋에는 비식별 fixture와 해시만 남긴다.
