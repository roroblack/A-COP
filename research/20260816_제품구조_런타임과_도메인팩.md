# 제품 구조 재정의 — 하나의 런타임 + 두 도메인 팩

작성일: 2026-08-16  
근거: `A-COP_구현계획서_v7.md`와 본 문서의 사실 근거 목록. v7과 브리핑 v7은 수정하지 않는다.

## 결론

A-COP은 **하나의 A-COP Runtime과 두 개의 도메인 팩**으로 정의한다. 10주에 만드는 것은 Runtime, CS Pack, 검증 쇼핑몰의 제한된 Commerce 표면과 운영자 감독 화면이다. Commerce Ops Pack의 전면 자동화와 사이트 생성·판매는 vision으로 보낸다.

이 구조에서 소비자는 자기 에이전트 하나로 상품 탐색·주문·배송·CS를 경험하고, 운영자는 모든 Case와 운영 Action의 상태·근거·예외를 한 화면에서 감독한다. 운영자는 매 건 승인하는 사람이 아니라, 저위험 업무는 자동 처리하게 두고 이상 신호와 고위험 Action에 개입하는 **human-on-the-loop**다.

## 1. 제품 구조 재정의

### 1.1 전체 그림

```text
소비자 Agent ── cs.* / commerce.* MCP ──┐
                                         ▼
┌─────────────────────────────────────────────────────────┐
│ A-COP Runtime (Core)                                    │
│ Case · Controller · Registry · Context/Message · Port 3종│
│ 승인 경계 · Action Gateway · idempotency · 감사 · 평가   │
└───────────────┬───────────────────────┬─────────────────┘
                │ Registry Team 계약     │ Adapter/외부 표면
        ┌───────▼────────┐       ┌──────▼─────────────────┐
        │ CS Pack         │       │ Commerce Ops Pack      │
        │ Billing         │       │ 재고·가격·발주·배송·    │
        │ Technical       │       │ 정산·운영 workflow      │
        │ VOC             │       │ (vision)                │
        └─────────────────┘       └────────────────────────┘
```

### 1.2 구성 표

| 층 | 책임 | 10주 상태 |
|---|---|---|
| A-COP Runtime (Core) | Case 생명주기, Controller의 위임·대기·재계획, Registry, Context/Message, 승인·Action Gateway, idempotency, 감사·trace, 평가 harness | 구현·계약·검증 대상 |
| Port 3종 | `TeamExecutorPort`(LOCAL/A2A 교체), `GraphStorePort`(관계 조회), `MessageBrokerPort`(전달·재처리) | Core 계약으로 강제 |
| CS Pack | Billing / Technical / VOC Team. 도메인 지식·정책·분류·응대 결과를 제공하고 side effect는 `ActionProposal`로 반환 | v7 기준선 계승 |
| Commerce Ops Pack | 재고·가격·발주·배송·정산 등 운영 Team과 업무 정책·Adapter | vision. 10주에는 전면 구현하지 않음 |
| 표면 | `cs.*`는 본인 Case 조회·접수, `commerce.*`는 상품·장바구니·주문·배송 리소스 | read와 제한된 cart 계약만 10주 검증 |

### 1.3 Core와 팩의 판정 기준

기본선은 **도메인 지식이 필요하면 팩, 도메인과 무관하면 Core**다. 다음 질문으로 판정한다.

1. 다른 도메인으로 바꿔도 동일한 상태·권한·감사 규칙이 남는가? 남으면 Core다.
2. 상품·정책·업무 용어·외부 시스템의 의미를 알아야 하는가? 알아야 하면 팩이다.
3. 실패 시 공통적으로 필요한 것이 “재시도·unknown·승인 대기·trace”인가, 아니면 업무별 보정 판단인가? 전자는 Core, 후자는 팩이다.

| 경계 사례 | 판정 | 이유 |
|---|---|---|
| 주문 금액과 현재 가격을 재조회하고 불일치면 실행을 차단 | Core의 검증·승인 경계 + Commerce 팩의 가격 의미 | 금액 snapshot 대조·idempotency·audit은 공통이지만 어떤 가격이 유효한지는 Commerce 지식이다 |
| 환불 가능 여부 | Commerce/CS 팩의 정책 Team + Core의 승인·실행 | 청약철회·예외·고객 상황은 도메인 정책이고, 실제 환불 실행의 승인·unknown·중복 방지는 공통이다 |
| “답변 근거가 없으면 자동 확정하지 않음” | Core | CS든 발주든 근거 부족 시 중단·escalated·감사를 남기는 규칙은 도메인과 무관하다 |
| 재고 수량을 읽는 API Adapter | Commerce 팩 | 재고 스키마와 공급처 의미를 알아야 하며 Core는 Port/계약만 소유한다 |

### 1.4 팩 교체 가능성을 테스트로 강제하는 방법

“Team을 늘리는 일이 리팩토링이 되면 설계가 잘못된 것”이라는 원칙을 다음 계약 테스트로 고정한다.

| 테스트 | 강제할 사실 |
|---|---|
| Registry 등록 테스트 | 기존 Controller 코드 수정 없이 새 `TeamManifest`를 등록하고 Case를 실행한다 |
| Port 교체 테스트 | 같은 입력에서 Local Team과 A2A Team을 번갈아 주입해 canonical `TeamResult`가 같아야 한다 |
| Core import 경계 정적 검사 | Core가 `app.modules.*`나 특정 도메인 Team을 import하지 않는지 검사한다 |
| 도메인 팩 제거 테스트 | CS Pack을 비활성화해도 Runtime이 기동하고 Case·audit·approval 테스트가 통과해야 한다 |
| 도메인 팩 추가 테스트 | Commerce fixture를 추가해도 기존 CS golden/holdout 결과와 Core contract가 변하지 않아야 한다 |
| 직접 실행 금지 테스트 | Team의 Tool 직접 호출을 AST와 runtime spy로 차단하고, write는 `ActionProposal`까지만 허용한다 |

판정은 “새 팩 추가에 필요한 변경 파일 수”가 아니라 **Core 변경 0, 기존 Team 수정 0, 계약·등록·fixture 추가만으로 통과하는가**로 한다. 실패하면 팩의 도메인 지식이 Core로 새어 나온 것이다.

## 2. 양면 구조

### 2.1 소비자 면

```text
소비자 ── 자기 Agent 하나 ─────────────────────────────┐
       ├─ commerce.search_products / get_product       │
       ├─ commerce.cart / create_order / track_order    ├─ A-COP Gateway
       └─ cs.get_case / cs.create_case                  │
                                                        ▼
       상품·장바구니·주문·배송·문의의 통합 상태 ← Core Case/Action/audit
```

| 표면 | 제공하는 경험 | 실행 경계 |
|---|---|---|
| Commerce MCP | 상품 검색, 상품 상세, 장바구니, 주문·배송 조회 | 읽기는 표면에서 제공. 주문·결제·환불·주문상태 변경은 직접 실행하지 않고 ActionProposal→승인→Core 2로 보낸다 |
| CS MCP | 본인 Case 조회, 문의 접수 | 고객 소유권·tenant scope를 확인하고 Case Runtime으로 보낸다 |
| 소비자 Agent의 통합 경험 | “주문하고 배송을 묻고 문제를 접수”하는 단일 대화 | MCP namespace는 나누되 Gateway·scope·audit·Case 식별자를 공유한다 |

Commerce Tool은 `commerce.search_products`, `commerce.get_product`, `commerce.create_cart`, `commerce.add_to_cart`, `commerce.create_order`, `commerce.track_order`, `commerce.request_return`을 후보로 계승한다. 10주에는 read 계약과 cart 계약, 금액·수량·상품 식별자 mismatch 차단을 검증한다. UCP/AP2를 구현했다고 말하지 않으며, 나중에 매핑 가능한 내부 계약만 둔다. 결제 위임·실제 PG·무인 환불은 하지 않는다.

### 2.2 운영자 면: human-on-the-loop

```text
자동 처리 ── 저위험 read/분류/알림 ──┐
                                     ├─ 운영자 감독 화면
고위험 Action ── approval queue ─────┘       ├ 상태·처리량·지연
                                            ├ 자동화율·인계율·실패율
                                            ├ 근거·승인·unknown trace
                                            └ 이상 신호와 개입 버튼
```

| 운영 업무 | 자동 처리 | 사람에게 올리는 조건 |
|---|---|---|
| 조회·분류·근거 수집 | 자동 실행·Case 기록 | scope 위반, 근거 없음, Context degraded |
| 일반 답변·배송 상태 안내 | 정책 근거가 있고 read-only면 자동 | 불만·예외·답변 근거 충돌·반복 실패 |
| 취소·반품·환불·발주·정산 | 제안 생성과 사전 검증까지 | 돈·재고·주문 상태를 바꾸는 Action, mismatch, timeout/unknown |
| VOC 집계·알림 | 배치 집계와 임계값 후보 생성 | 새 정책 결정, 고객 보상, 임계값 변경 |

사장이 보는 한 화면은 “AI가 잘 답했는가”만 보여주면 안 된다. 기간·분모를 고정해 다음을 보여준다.

| 영역 | 지표·신호 |
|---|---|
| 운영량 | 전체 유효 Case, 유형별 Case, open/running/waiting/escalated/failed, 미처리 연령 |
| 정직한 자동화 | `자동 완료 Case / 전체 유효 Case`, 사람 인계율, 재처리율, 유형별 분모와 기간, 평가 CI(측정 전이면 확인 필요) |
| 안전 | approval 대기 수, unknown 수, mismatch 차단 수, 중복 실행 차단 수, degraded Context 수 |
| 품질 | 근거 포함률, 정책 충돌, 사람 수정률, 회귀 실패, VOC 급증 |
| 건강 신호 | 평소 기준 대비 오류율·지연·인계율·금액/재고 mismatch·외부 Adapter timeout의 변화 |

이상은 “수치가 높다”가 아니라 **기준선 대비 정해진 변화가 생긴 상태**로 정의한다. 내부 단계에서는 시나리오 fixture 기준선을 만들고, 알파부터 유형·시간대별 baseline을 저장한다. 베타에서 고객별 임계값은 확인 필요이며, 임계값과 개입 이유를 audit에 남긴다. 예: `failed/전체`, `unknown/Action`, `handoff/전체`, p95 처리 지연, mismatch 비율이 직전 비교 구간보다 상승하거나, 동일 오류가 연속 발생하면 이상 후보로 올린다. 정확한 수치 임계값은 실제 분포 측정 후 확정한다.

10주 우선순위와 화면 연결은 다음과 같다.

| 우선순위 | 화면에서 제품화되는 것 |
|---|---|
| 감사 가능성 제품화 | Case 입력→분류→근거→Team→승인→Action 결과→사람 수정의 재생 링크와 export |
| 정직한 자동화율 | 성공만 세지 않고 전체 유효 Case, 보류·실패·인계·분모·기간을 함께 표시 |
| 사람 인계 | approval queue, handoff packet, 인계 이유·필요 근거·기한·처리 결과를 표시 |

## 3. 검증 쇼핑몰의 재정의

### 3.1 의미 변화

만드는 구성은 기존 기획서와 같다. 상품·옵션·가격·재고, Mock catalog/order/delivery, 주문·배송·문의 Case, 제한된 MCP 표면, A-COP의 Action·Approval·evidence를 만든다. 달라지는 것은 **검증용 테스트 몰**에서 **사이트 제품의 1호 사례 후보**로 프레이밍하는 방식이다.

| 항목 | 기존 표현 | 새 표현 |
|---|---|---|
| 프레이밍 | A-COP 안전 자동화 검증용 쇼핑몰 | 운영자 감독과 소비자 Agent 표면을 함께 보여주는 사이트 제품의 1호 사례 후보 |
| 발표 문구 | 쇼핑몰에서 CS 흐름을 검증한다 | 하나의 Runtime이 소비자 주문·배송·CS와 운영자 감독을 연결하는 장면을 제한된 Commerce 사이트로 시연한다 |
| 측정 항목 | Case·Action·Approval·근거 | 위 항목 + Commerce/CS 표면 통합률, mismatch 차단, 소비자 handoff, 운영자 이상 신호·개입, 자동화율 분모 |

“1호 사례”라는 명칭은 다음 조건을 모두 충족할 때만 쓴다.

1. 소비자 Agent가 Commerce read/cart와 CS Case를 하나의 흐름으로 사용한다.
2. 주문·배송·문의·제한된 취소/반품 시나리오가 동일한 Case·Action·audit 원장과 연결된다.
3. 운영자가 처리량·자동화율·인계·unknown·mismatch를 한 화면에서 보고 개입할 수 있다.
4. 최소 한 번의 내부 운영 시나리오에서 성공·실패·사람 인계·재처리를 재생한다.
5. 무엇이 Mock/Sandbox인지, Commerce Ops Pack과 실제 결제·정산이 없다는 범위를 발표 자료에 명시한다.

Commerce Ops Pack이 없는 동안 주장 가능한 범위는 **“CS와 제한된 Commerce 표면을 하나의 Runtime에서 검증한 사이트 제품 1호 사례”**다. 재고 보충, 공급처 발주, 정산, 전면 배송 운영, 상용 결제, 일반 고객 매출까지 자동화했다고 주장할 수 없다. 내부 자가주문은 운영 실행층의 검증이지 시장 매출 증명이 아니다.

## 4. 10주와 vision 분리

| 구분 | 10주에 한다 | vision으로 보낸다 |
|---|---|---|
| Runtime | Case, Controller, Registry, Port 3종, 승인·감사·평가·사람 인계 | 장기 실행·대규모 메시징·멀티 LLM 등은 기존 vision 트리거로 판단 |
| CS | Billing/Technical/VOC 계약·통합·평가 | 고객별 Team 카탈로그·대규모 온보딩 |
| 소비자 | `cs.*`와 제한된 `commerce.*` 표면, read/cart·mismatch 계약 | UCP native server, AP2 서명·Payment Mandate, 실제 PG·무인 결제 |
| 쇼핑몰 | 1호 사례 후보: Mock/Sandbox 상품·주문·배송·Case·운영 화면 | 상용몰 전면 운영·외부 결제·실배송·전면 Commerce Ops |
| B2B 사이트 | 구조·포지셔닝·vision 문서와 1호 사례 | 프론트 빌더, 사이트 생성·판매 제품 |

범위 확대가 아니다. 새 실작업은 Commerce read/cart 계약, 제한된 쇼핑몰 연결, 운영자 신호 화면의 세 묶음이며, 그만큼 이번 10주에서 **전면 Commerce Team 구현, 실제 PG·정산·배송 Adapter, UCP/AP2 완전 구현, 사이트 빌더, 두 번째 외부 Adapter, Docker 의존 구현**을 명시적으로 제외한다. 쇼핑몰 기획서의 병행 상한(생성 4~5일, 검증·통합 2~3일, 대기 2~3일; 확인 필요)을 넘기면 1호 사례 주장을 보류한다.

| 제품 | 구매자 | 구매 이유 | 판매 가설 |
|---|---|---|---|
| 자동화 CS | 고객지원 책임자, 운영 책임자, 데이터 경계가 중요한 기업 | 문의를 Case로 처리하고, 전문 Team·승인·감사·평가로 실제 운영을 통제한다. 시장격차 문서가 Fin을 “single-agent system”이라고 정리하고, 실제 운영 자동화율은 “55-70%”에 머문다고 기록한 공백을 겨냥한다. 자체 호스팅·감사 요구도 같은 근거다 | 시장격차 문서 10번의 “per-resolution pricing”이 대안 탐색의 가장 큰 이유라는 근거에 따라, 해결 건당 과금은 피하고 플랫폼 기본료+좌석/처리량 구간+선택적 지원 또는 자체호스팅 라이선스+지원료를 검증한다. 금액은 확인 필요 |
| 자동화 사이트 | 소규모·중견 상거래 사업자, 사장/운영 책임자 | 사이트 운영을 자동화하고 사장은 human-on-the-loop로 예외와 이상 신호만 확인한다. 단, 10주에는 제품이 아니라 vision과 1호 사례로 제시한다 | 사이트 기본 패키지+Runtime 사용권+선택 도메인 팩/운영지원처럼 가치가 누적되는 구조를 가설로 둔다. 해결 건당 과금은 피한다 |

같은 Runtime의 판매 이점은 첫 도입 후 **다른 팩을 추가 구매할 수 있다는 확장 경로**다. CS 고객은 Commerce Ops Pack을 붙이고, 사이트 고객은 CS Pack을 붙일 수 있다. Core의 Case·승인·감사·평가가 공유되므로 도메인이 바뀌어도 운영 통제 방식이 바뀌지 않는다. 다만 실제 교차판매율·가격·지원 비용은 근거가 없어 확인 필요다.

## 6. 위험

| 위험 | 통제 |
|---|---|
| 범위 확대 압력 | 10주 DoD를 Runtime+CS+제한 표면+1호 사례 후보로 고정하고, 새 기능은 같은 크기의 항목을 빼지 않으면 받지 않는다 |
| “다 된다”는 인상 | 구현/제한 검증/vision을 모든 그림·표·발표 문구에서 분리하고, Mock/Sandbox·미구현 Pack·확인 필요를 표시한다 |

| 소비자 Agent의 잘못된 주문 | 가격·수량·상품 ID를 Core 2가 재조회하고 mismatch면 실행하지 않는다. 주문·환불·결제는 승인·idempotency·audit을 거친다 |
| 감독 불능 | 자동화율 분모, handoff 이유, unknown, 지연, 오류·mismatch 기준선을 화면에 고정한다. 임계값 미측정이면 확인 필요로 둔다 |
| 발표에서 vision과 구현 혼합 | “10주 구현”, “제한된 1호 사례”, “vision” 세 라벨을 문장·그림·데모 장면에 붙인다. “자동화 사이트 판매”는 구현 완료처럼 말하지 않는다 |

## 7. 엑셀·포지셔닝 수정안

### 7.1 v7 §1-1 포지셔닝 수정 문안

> **A-COP은 하나의 A-COP Runtime 위에 CS Pack과 Commerce Ops Pack을 교체·확장하는 B2B Agentic Operations Platform이다.** 소비자는 자기 Agent 하나로 상품·주문·배송·CS를 이용하고, 운영자는 Case·Action·승인·근거·평가를 한 화면에서 감독한다. 10주에는 자동화 CS와 제한된 Commerce 검증 사이트를 구현하며, 전면 사이트 생성·판매와 재고·발주·배송·정산 자동화는 vision으로 둔다. 모든 도메인 Team은 Registry로 교체되고, Core는 승인·idempotency·감사·평가를 공통으로 보장한다.

### 7.2 v7 §28 엑셀 설명 수정 문안

> 기업이 자사 고객 응대와 운영 업무를 Agentic AI로 감독하게 하는 B2B 플랫폼. 하나의 Runtime이 상태 있는 Case, 업무별 Team, 승인·idempotency·감사·평가를 공통 제공하고, CS Pack(Billing/Technical/VOC)과 Commerce Ops Pack(재고·가격·발주·배송·정산)을 Registry로 교체·확장한다. 소비자는 기존 자기 Agent로 Commerce MCP와 CS MCP를 통해 상품·주문·배송·문의까지 이용하며, 운영자는 human-on-the-loop로 이상 신호와 고위험 Action만 확인한다. 10주에는 CS와 제한된 검증 쇼핑몰을 구현하고, 사이트 생성·판매와 전면 Commerce Ops 자동화는 vision이다. 자체 호스팅 가능 범위와 미검증 항목은 별도 표시한다.

짧은 셀 버전:

> **A-COP — 하나의 Runtime과 CS/Commerce 도메인 팩을 갖춘 B2B Agentic Operations Platform.** 소비자는 자기 Agent로 구매·배송·CS를 이용하고, 사장은 자동화 운영을 human-on-the-loop로 감독한다. 10주는 Core·CS·제한 검증 사이트, 전면 사이트 생성·운영 자동화는 vision.
