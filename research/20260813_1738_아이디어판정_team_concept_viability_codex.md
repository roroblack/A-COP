# 멀티에이전트 CS 컨셉의 에이전트 팀 구성 실효성 검증

## 결론

현재 구성은 6명·10주 최종 프로젝트의 구현 범위를 넘는다. 8개 팀을 모두 독립 에이전트로 만들면 에이전트 수는 늘지만, 실제로 평가 가능한 핵심 동작은 흐려진다. 살아남는 핵심은 다음 두 가지다.

1. 케이스 상태와 SLA에 따라 L1→L2→L3로 전이하는 실행 그래프
2. 리스크 분석 결과가 `즉시 환불`과 `소명 우선` 경로를 실제로 바꾸는 L2 중재 흐름

따라서 `Supervisor`, `L1`, `L2 중재`를 중심으로 하고, 증거 수집과 리스크 산정은 L2 내부 모듈로 흡수하는 구성이 적절하다. 판매자 이의제기, 외부기관 연계, 유사 결정례 RAG, 인사이트 분석은 데모용 핵심 범위에서 제외하거나 Phase 2로 미룬다.

## 1. 판정표

## 2. 팀별 근거

### 1) Supervisor / 판매주체 판별

**A. 필요성**

접수 후 이슈·의도·판매유형을 정하고 케이스를 시작하는 라우팅은 필요하다. 다만 판매주체 판별 자체가 별도 팀이어야 할 이유는 약하다. 결과가 `직매입/위탁/오픈마켓` 같은 유한 라벨이고, 이후 전이도 상태 테이블로 표현 가능하다. 삭제해도 L1 또는 최상위 Controller가 같은 분류 함수를 호출하면 된다.

**B. 구현성**

합성 문의에 판매유형 라벨을 붙이면 학습·평가 데이터는 만들 수 있다. 공개 고객문의 데이터에서 실제 계약 관계와 책임 주체까지 정확히 라벨된 데이터가 있다고 가정하면 안 된다. 쿠팡 등 실제 플랫폼의 내부 책임 로직도 공개되어 있지 않다. 숨은 난이도는 판매유형이 문의 문장만으로 식별되지 않고 플랫폼·주문·입점 메타데이터에 좌우된다는 점이다.

**C. 평가성**

이슈/의도/판매유형의 분류 정확도와 confusion matrix는 만들 수 있다. 그러나 분류 결과가 법적 책임 주체를 보장하지는 않는다. 분류 평가와 법적 판정 평가를 섞으면 안 된다.

**판정: DEMOTE.** 소형 분류기 또는 LLM structured output + 규칙 라우터로 두고, 오분류 시 L2로 보수적으로 전이한다.

### 2) L1 테넌트 응대 봇

**A. 필요성**

판매자별 정책을 적용하고 판매자에게 소명을 요청하며 SLA 타이머를 시작하는 L1 단계는 3층 컨셉의 앞단으로 필요하다. 하지만 “스토어 config를 읽어 답변한다”만 수행한다면 독립 팀이라기보다 테넌트 정책 주입을 받은 단일 응대 모듈이다.

**B. 구현성**

스토어 2~3개, 정책 YAML, 주문·배송 mock DB, 합성 문의로 충분히 데모 가능하다. 다만 문서의 5~10개 스토어, 자동 생성, 판매자 페르소나 4종까지 동시에 넣으면 config 스키마·정책 충돌·테스트 케이스가 급증한다. 자동 생성의 실체도 새 모델을 만드는 것이 아니라 동일 실행 그래프에 config를 주입하는 것으로 명확히 해야 한다.

**C. 평가성**

정책 적용 여부, 답변의 필수 필드, 자동 승인 한도, SLA 시작과 초과 전이는 골든셋과 상태 전이 테스트로 평가 가능하다. 자연스러운 말투나 “스토어다운 느낌”은 핵심 지표로 삼기 어렵다.

**판정: DEMOTE.** L1 단일 에이전트 + 테넌트 config 모듈로 만들고, 스토어 수는 2~3개로 제한한다.

### 3) L2 증거 수집 에이전트

**A. 필요성**

판정 전에 주문번호, 배송 상태, 사진, 대화 이력 등 증거를 정규화해야 한다. 하지만 필요한 필드를 정하는 일은 케이스 유형별 체크리스트와 조회 도구로 대부분 고정할 수 있다. 별도 팀을 삭제해도 L2 중재가 `missing_evidence`를 반환하고 Controller가 요청을 재실행하는 방식으로 흡수된다.

**B. 구현성**

증거가 존재하는 경우와 누락된 경우를 합성해 만들 수 있다. 실제 사진 OCR·배송사 API·진위 판정까지 하려 하면 10주 범위를 벗어난다. 특히 “능동적으로 요구”하는 다중 턴 대화는 L1과의 책임 경계가 겹친다.

**C. 평가성**

케이스 유형별 필수 증빙 목록, 누락 탐지, 주문/배송 mock 조회의 정확도는 채점 가능하다. 증거의 진위나 사진만으로 귀책을 판단하는 것은 별도 검증 문제다.

**판정: MERGE → L2.** `evidence checklist + structured case file`로 구현하고, 증거 요청은 L2의 재질의 상태로 표현한다.

### 4) L2 중재·판정 에이전트

**A. 필요성**

이 컨셉에서 독립 팀으로 남겨야 할 핵심이다. 증거, 정책, 법정 기준을 조합해 판정 초안을 만들고 HITL 승인 후 환불 제안으로 연결한다. 삭제하면 3층 사다리는 단순 상담·라우팅 데모가 되고, “분석 결과가 시스템 동작을 바꾼다”는 심사 요건을 입증하기 어렵다.

**B. 구현성**

전자상거래법·표준약관·소비자분쟁해결기준 중 제한된 품목과 쟁점만 선정하고, 법령 코퍼스는 수동 정제해도 된다. 합성 케이스 50~100건 정도로 MVP 골든셋을 구성할 수 있다. 숨은 난이도는 법률 문장 검색이 아니라 사실관계의 법적 적용, 예외·기간·배송비 조건, 개정 시점, 상충 근거의 처리다. “조항을 인용했다”는 것이 “판정이 맞다”는 뜻은 아니다.

**C. 평가성**

`refund_eligible`, `responsible_party`, `reason_codes`, `evidence_ids`, `citation_ids`, `recommended_action`을 구조화하면 부분 점수화할 수 있다. 조항 인용은 문서 존재 여부만이 아니라 해당 사실을 실제로 지지하는지 별도 라벨이 필요하다. 평가는 완전 일치율 하나가 아니라 필드별 정확도·근거 포함률·환각 인용률·HITL 전 액션 차단율로 설계한다.

**판정: KEEP.** 단, 법률자문이나 자동 확정 판정이 아니라 제한된 케이스의 판정 초안 생성기로 포지셔닝한다.

### 5) 판매자 이의제기 심사 팀

**A. 필요성**

선환불 후 판매자가 부당 환불을 주장하는 시나리오는 현실적이다. 그러나 현재 프로젝트의 핵심 문제를 해결하는 데 필수는 아니다. 이 기능을 넣는 순간 구매자 분쟁, 판매자 분쟁, 환불 회수, 검수, 페널티라는 두 번째 상태 기계를 추가한다.

**B. 구현성**

반품 검수 결과와 판매자 소명을 합성하면 화면은 만들 수 있다. 그러나 실제 라벨·검수 신뢰도·양측의 증거 우선순위·환불 회수 정책은 mock으로 임의 설계된다. 그 결과 구현은 가능해도 “현실적인 심사”라는 주장을 검증하기 어렵다.

**C. 평가성**

합성 규칙과 일치하는지 채점할 수는 있다. 하지만 그 정답은 팀이 만든 규칙을 다시 맞히는 문제다. 실제 공정성·분쟁 해결력의 지표가 되기 어렵다.

**판정: DEFER (Phase 2).** MVP에서는 선환불 후 이의제기 상태와 수동 검토 버튼만 남긴다.

### 6) 리스크 스코어링 팀

**A. 필요성**

UP-0를 살리려면 금액, 증빙 수준, 반복 환불 이력, 판매자 분쟁률을 이용한 위험도 입력이 필요하다. 다만 위험도 계산은 설명 가능한 정책 함수가 더 적합하다. LLM 팀이 점수를 생성하면 재현성과 공정성, 기준 변경 추적이 나빠진다.

**B. 구현성**

mock 이력과 합성 케이스로 즉시 구현 가능하다. 공개 데이터로 고객별 환불 이력이나 판매자 분쟁률을 얻을 수 없으므로 실데이터 성능을 주장할 수 없다. 숨은 난이도는 임계값을 정하는 근거와 클래스 불균형이다.

**C. 평가성**

훈련이 아니라 고정 규칙으로 두면 입력→점수→경로의 결정론적 테스트가 가능하다. 목표는 사기 탐지 정확도가 아니라 “정의된 위험 조건에 맞는 경로를 선택했는가”로 제한한다. 실제 손실 최소화나 블랙컨슈머 판별 성능으로 확장하면 근거가 부족하다.

**판정: DEMOTE.** 버전 관리되는 가중합/룰 엔진으로 두고, L2가 점수와 기여 요인을 설명하도록 한다.

### 7) INSIGHT 피드백 분석 팀

**A. 필요성**

스토어별 이슈 급증을 운영자에게 보여주는 것은 가치가 있지만 케이스 처리 경로의 필수 단계는 아니다. 삭제해도 핵심 3층 에스컬레이션과 UP-0는 작동한다.

**B. 구현성**

AI Hub 리뷰나 합성 리뷰를 스토어별로 배정해 집계하는 것은 가능하다. 다만 공개 리뷰를 특정 판매자의 실제 분쟁률로 해석할 수 없고, 합성 배정은 현실 분포를 검증하지 못한다. LLM으로 “위생 이슈 급증” 같은 인사이트를 만들면 집계 오류와 과잉 해석이 생긴다.

**C. 평가성**

기간별 count, rate, threshold alert는 정확히 채점 가능하다. “운영자가 유용하다고 느끼는 인사이트”는 정답셋으로 깔끔하게 평가되지 않는다.

**판정: DEFER (분석 모듈).** 여유가 있을 때 SQL 집계 대시보드로만 추가하고, 독립 에이전트와 실시간 선제개입 주장은 하지 않는다.

### 8) L3 외부 절차 연계 에이전트

**A. 필요성**

플랫폼이 해결하지 못하는 경우의 출구를 보여준다는 의미는 있다. 그러나 외부기관에 실제 제출하거나 사건을 자동 접수하는 기능은 MVP에 필요하지 않다.

**B. 구현성**

서식 파일과 케이스 필드의 매핑은 구현 가능하다. 실제 소비자원 서식의 최신 버전, 제출 절차, 전자 접수 연계, 첨부파일 조건은 별도 확인이 필요하다. 문서가 기계 판독 가능한 원천과 안정적인 API를 제공한다고 가정하면 안 된다.

**C. 평가성**

필수 필드 누락, 값 매핑, 파일 생성 여부는 채점 가능하다. 생성된 패키지가 실제 기관에서 접수 가능한지, 법적으로 충분한지는 mock만으로 평가할 수 없다.

**판정: DEMOTE.** `escalation exit` 상태와 결정론적 PDF/JSON 패키저만 구현한다. 실제 외부 연계 에이전트는 Phase 2다.

## 3. 고도화 포인트 판정

### UP-0: 리스크 기반 하이브리드 환불

KEEP. 이 기능은 단순 분류 결과가 아니라 `risk_score → processing_route → side effect proposal`의 연결을 만든다. 단, 스코어 자체는 룰로 고정하고 비교 실험을 설계해야 한다. 최소 실험은 동일 케이스를 `항상 소명 우선`, `항상 선환불`, `하이브리드`로 실행해 즉시 해결률, 잘못된 환불률, 에스컬레이션률, 평균 단계 수를 비교하는 것이다. 합성 정답이 정책 룰에서 생성됐다는 한계는 명시해야 한다.

### UP-1: 유사 결정례 RAG

DEFER. 문서에 적힌 “한국소비자원 피해구제 사례·분쟁조정 결정례”의 공개성은 원문 접근성, 다운로드 안정성, OCR 품질, 사건 메타데이터, 최신성, 재사용 조건까지 보장하지 않는다. 사례가 검색된다는 것과 해당 사례가 현재 사실관계의 법적 근거가 된다는 것도 다르다. MVP에서는 법정 기준 원문과 팀이 수동 정제한 10~20개 사례만 근거로 제한하고, 유사 결정례는 성공 조건에서 분리한다.

### UP-3: 판매자 소명 지원

DEMOTE/OPTION. 별도 에이전트 팀이 아니라 판매자 콘솔의 `사실 누락 확인 + 소명 초안 생성` 기능으로 둔다. 평가는 문장 품질보다 필수 사실 보존율, 첨부 증거 연결률, 근거 없는 주장 추가율로 한다. 판매자 페르소나 LLM이 자유롭게 답하게 해 에스컬레이션을 재현하는 방식은 주 시나리오의 정답성을 흐릴 수 있다.

## 4. 치명적 가정

다음 가정 중 하나라도 틀리면 현재 컨셉의 강한 주장부터 무너진다.

1. 소비자원 피해구제 사례·분쟁조정 결정례를 안정적으로 수집·정제·재배포할 수 있다. 공개 페이지가 있다는 것만으로 기계 판독·대량 수집·재사용이 보장되지 않는다.
2. 전자상거래법과 소비자분쟁해결기준만으로 개별 케이스의 환불 여부와 귀책을 결정론적으로 정할 수 있다. 실제 판정에는 계약 조건, 증거 신뢰도, 사실관계, 예외, 개정 시점이 개입한다.
3. 법령 조항을 정확히 검색하면 판정도 정확해진다. 검색은 근거 후보를 줄 뿐 적용과 사실 인정까지 해결하지 않는다.
4. 합성 골든셋이 실제 분쟁 분포를 대표한다. 합성 데이터의 정답은 생성 규칙을 반영할 뿐 실제 소비자·판매자 행동의 외적 타당도를 보장하지 않는다.
5. 판매자 페르소나 LLM이 협조형·지연형·비협조형·공격형을 안정적으로 재현한다. 모델의 확률적 행동과 프롬프트 변화가 평가 결과를 바꿀 수 있다.
6. 판매유형을 문의 텍스트만으로 알아낼 수 있다. 책임 주체는 주문·입점·계약 메타데이터가 있어야 하는 경우가 많다.
7. 리스크 점수가 블랙컨슈머나 사기 위험의 객관적 대리변수다. mock 이력으로 만든 점수는 프로젝트가 정한 정책의 위험도이지 실제 부정행위 확률이 아니다.
8. L3 소비자원 서식이 최신·고정 형식이며 생성 파일이 실무 제출에 충분하다. 실제 제출 가능성은 별도 기관·절차 검증 없이는 주장할 수 없다.
9. 멀티테넌트 config 자동 생성이 진짜 확장성을 증명한다. config를 읽는 동일 그래프의 재실행일 수도 있으며, 정책 충돌·버전·권한·테스트까지 해결하지 않으면 확장성은 화면 효과에 그친다.
10. HITL 승인만 넣으면 법적·운영상 위험이 해결된다. 운영자가 초안을 검토한다는 것은 안전장치이지 판정 정확도의 증거가 아니다.

## 5. 범위 과잉 진단과 최소 생존 구성

8개 팀 + 3층 + 멀티테넌트 + 구매자↔판매자 분쟁 및 판매자↔플랫폼 이의제기라는 조합은 6명·10주에 맞지 않는다. 기존 `A-COP_구현계획서_v6.md`도 Team 2개와 Remote PoC 1개를 MVP로 잡고, Graph DB는 별도 도입하지 않는 수준이다. 그 기준보다 현재 컨셉은 도메인 규칙, 양측 상태, 외부 서식, RAG 코퍼스, 페르소나 평가를 동시에 추가한다.

최소 생존 구성은 아래와 같다.

```text
접수
  → 판매유형/이슈 분류 모듈
  → L1 단일 응대 에이전트 + tenant config + SLA
  → 증거 체크리스트/조회 모듈
  → 리스크 룰(UP-0)
       ├─ 저위험: 선환불 ActionProposal
       └─ 고위험/증거 부족: L2 판정 에이전트
  → HITL 승인
  → 환불/페널티 모의 트랜잭션
  → 실패 시 L3 상태 + 서식 패키저(선택)
```

핵심 데모 데이터는 스토어 2개, 케이스 유형 3개(미배송·파손·단순변심), 시나리오 12~20개, 각 시나리오의 기대 상태·점수·경로·판정·인용 근거로 제한한다. 실제 사용자가 없으므로 “대규모 자동화”보다 동일 케이스에서 입력 조건을 바꾸었을 때 경로가 달라지는 재현성이 더 중요하다.

## 6. 데모에서 보여줄 것과 슬라이드로 남길 것

### 실제로 보여줄 것

- 동일 문의에 대해 금액·증빙·이력만 바꾸면 `선환불`과 `소명 우선`으로 경로가 바뀌는 화면
- 판매자 무응답 또는 SLA 만료 후 상태가 L2로 전이되는 화면
- L2가 증거 목록, 법정 기준 인용, 판정 필드, ActionProposal을 남기는 화면
- 운영자 승인 전에는 환불 트랜잭션이 실행되지 않는 화면
- tenant config를 바꿔 스토어 정책·말투·자동 승인 한도가 바뀌는 작은 데모

### 슬라이드로만 주장해야 하는 것

- 소비자원 실제 자동 제출 또는 실제 기관 연계
- 실제 플랫폼의 쿠팡·네이버 정책과 동등한 책임 판정
- 실제 블랙컨슈머 탐지 및 판매자 위험도 예측
- 5~10개 스토어로의 운영 수준 멀티테넌트 확장
- 판매자 페르소나가 현실의 다양한 분쟁 행동을 대표한다는 주장
- 유사 결정례 RAG가 법적 판정의 정답을 제공한다는 주장

## 7. 평가 설계의 함정과 권장 지표

“법정 기준이라 정답 검증이 깔끔하다”는 문장은 절반만 맞다. 조항 검색과 필드 추출은 비교적 채점 가능하지만, 사실관계의 법적 적용과 귀책은 단일 정답이 아닐 수 있다. 팀이 만든 합성 규칙으로 만든 골든셋에 다시 맞추면 시스템의 법률 정확도가 아니라 자기 일관성만 측정한다.

평가셋은 생성 규칙과 분리해 사람이 직접 작성한 케이스를 일부 포함하고, 애매한 케이스에는 복수 허용 라벨과 판정 근거를 둬야 한다. 최소 지표는 다음과 같다.

| 평가 영역 | 지표 |
|---|---|
| 분류 | intent/issue/seller-type macro F1, confusion matrix |
| 상태 전이 | SLA·무응답·불복 조건별 전이 정확도, 잘못된 전이율 |
| 리스크 경로 | 위험 조건별 route accuracy, 경계값 테스트 통과율 |
| 판정 | 환불 가능 여부·귀책·사유코드 필드별 정확도/F1 |
| 근거 | citation precision, 근거 포함률, 무관·환각 인용률 |
| 증거 | 필수 증거 누락 탐지율, 불필요 요구율 |
| 안전성 | HITL 전 side effect 0건, 중복 액션 0건, 감사 로그 완전성 |
| 운영 효과 | 평균 처리 단계, 에스컬레이션률, 잘못된 환불률, 처리 시간 |

LLM-as-a-judge만으로 답변 품질을 평가하면 안 된다. 구조화 필드·상태·액션은 코드로 채점하고, 자유 텍스트는 소수의 블라인드 사람 평가로 보조한다. 또한 기준선은 `항상 소명 우선`, `항상 선환불`, `단일 LLM` 중 최소 2개를 두어 멀티에이전트라는 이름 자체가 아니라 경로 선택의 효과를 비교해야 한다.

## 최종 권고

컨셉은 “8개 전문 팀”으로 방어하면 약해진다. `1개 핵심 판정 에이전트 + 1개 얇은 L1 에이전트 + 결정론적 라우팅/증거/리스크/액션 모듈`로 재정의해야 한다. 발표 문장도 “많은 에이전트가 협업한다”가 아니라 “상태와 리스크 분석이 다음 행동과 승인 경로를 바꾼다”로 좁히는 것이 안전하다. 이 축소안을 10주 MVP로 고정하고, 이의제기·결정례 RAG·실제 외부 절차·인사이트 팀은 성공 기준과 개발 일정에서 분리한다.
