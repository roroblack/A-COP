# 에이전틱 AI 자동화 검증 쇼핑몰 기획서

## 먼저 답: 지금 구성이 맞나

현재 설계는 **쇼핑몰이 별도 Commerce Reference Vertical이고, A-COP이 그 위에 Case·Action·Approval·Outcome을 검증하는 CS 층으로 붙는 구조가 맞다.** 쇼핑몰 전체를 A-COP 안에 넣으면 상품·결제·배송·정산·법규가 A-COP 본체 범위가 되어 v7의 10주 계획을 잠식한다.

“여기서 다 완성”을 목표로 하려면 상품·주문·결제·배송·문의·취소·반품의 canonical 계약, 외부 service Adapter, PII Vault, 결제·정산 원장, 법규 게이트, Commerce MCP, 운영 화면이 더 필요하다. 이번 문서는 그 전체 상용몰을 약속하지 않고, A-COP의 안전한 자동화와 실제 Case 흐름을 검증할 수 있는 제한된 쇼핑몰을 정의한다.

## 1. 한 줄 정의와 목적

**매출을 만들기 위한 쇼핑몰이 아니라, 실제 주문·배송·문의·취소·반품 이벤트를 A-COP의 Case·Action·Approval·근거 대조로 검증하는 소형 Commerce Reference Vertical이다.**

## 2. 관계 그림

```text
[소비자 / 운영자 / 소비자 개인 AI]
       │ 웹·REST·CS MCP·Commerce MCP(계획 표면)
       ▼
[Commerce Surface / Tool·Action Layer]
       │ 상품·Cart·Order·Delivery canonical contract
       │ side effect는 proposal, approval, idempotency, audit
       ▼
[ A-COP Core ]
  Gateway → Controller → Case Runtime / Shared State
       │                 │
       │                 ├─ Context Broker / GraphStorePort
       │                 ├─ Agent Team Module
       │                 └─ Core 2 ExecuteAction
       ▼
[Commerce Adapter / Mock·Sandbox·제한 Live]
  상품·결제·배송·반품 provider 또는 fixture
       │
       └─ 이벤트·근거·상태 projection → Case / Outcome / Trace
```

Commerce는 별도 도메인 모듈로 두되, 실행은 v7의 Tool/Action Layer와 Core 2를 통과한다. Commerce MCP는 Commerce Surface에 붙고, CS MCP는 Case 조회·문의 접수 표면에 남긴다. Team이 marketplace adapter를 직접 호출하지 않고 `ActionProposal`만 반환한다는 v7 경계를 유지한다.

## 3. 단계별 운영 범위

| 항목 | 내부 | 알파 | 베타 |
|---|---|---|---|
| 목적 | 전부 시험용 | 같은 기수의 제한 소액 운영 | 별도 게이트 후 외부 판매 여부 판단 |
| 상품·주문 | fixture/Mock | 1인 1개 수준의 제한 주문 | 계약·재고·운영 책임 확인 후 필요한 것만 |
| 결제 | Mock | 계좌이체 또는 확인된 간편결제 1개, 사람 확인 | PG·정산·세무 흐름 확인 후 |
| 배송 | Mock/Sandbox | 제한 Live 또는 수동 상태 입력 | 배송 provider와 실패·취소 처리 확인 후 |
| 문의·Case | 시나리오 fixture | 실제 문장과 운영 Case | 외부 운영을 열 경우 별도 승인 |
| 취소·반품 | Mock, 결정표 테스트 | 사람 확인을 거친 제한 처리 | 법규·PG·원장·실패 처리가 확인된 범위 |
| PII | 가짜 데이터 | 배송 원문은 암호화 Vault, Case·LLM은 토큰 | 동의 또는 처리위탁·처리방침 경로 확인 후 |
| MCP 쓰기 | 끔 | 끔 | 기본 끔. 열면 저위험·승인 조건을 먼저 정함 |

알파까지는 같은 기수로 운영하고, 베타는 별도 게이트다. 법규 적용과 실제 판매 구조는 **확인 필요**이며, 충족해야 해당 기능을 연다.

## 4. 상품 선정 기준

다음 조건을 모두 만족하는 소수 품목을 고른다.

- 단가와 파손 위험이 낮고, 신체·식품·의약·안전 규제와 직접 연결되지 않을 것.
- 옵션·수량·배송 상태가 있어 상품 식별자, 재고, 가격, 주문 상태 대조를 시험할 수 있을 것.
- 배송 지연·오배송·파손·변심 문의가 자연스럽게 발생하지만, 손실이 작을 것.
- 반품이 가능하고 회수·환불 흐름을 Mock 또는 사람 확인으로 재현할 수 있을 것.
- 공급처 거절이나 재고 부족을 fixture로 만들 수 있을 것.

실제 판매 확대나 해외 구매대행을 상품 선정의 전제로 삼지 않는다.

## 5. 필요한 기능과 구현 방식

| 기능 | 방식 | 이번 판단 |
|---|---|---|
| 상품·옵션·가격·재고 | 직접 canonical contract + Mock catalog | 직접 만들 것 |
| 장바구니 | 직접 contract·idempotency·rollback | 직접 만들 것 |
| 주문 | 직접 Order projection, side effect는 제한 Adapter | 직접 만들 것 + Mock/Sandbox |
| 결제 | 결제수단 저장 금지, 결제 결과 contract | 내부는 Mock, 알파는 확인된 한 경로, PG는 외부 서비스 후보 |
| 배송조회 | Delivery projection·상태 이벤트 | 직접 만들 것, provider는 Sandbox/수동 입력 |
| 문의 | v7 Case 생성·CS MCP 경로 | 직접 만들 것 |
| 취소 | 상태·권한·idempotency·ActionProposal | 직접 만들 것, 실제 처리는 사람 확인 |
| 반품·환불 | `RefundEligibility`와 결정표·audit | 내부 Mock, 실제 환불은 제한 알파/베타 게이트 |
| 국외 배송·구매대행 | 이번 10주 전면 구현 | Mock만 두고 실제 Live는 제외 |

쇼핑몰의 모든 버튼을 A-COP 안에서 새로 만드는 것이 목표가 아니다. 외부 결제·배송을 쓰더라도 Adapter 뒤에 놓고, A-COP은 요청·근거·승인·결과·실패를 검증한다.

## 6. 자가주문으로 데이터 쌓기

앞선 재검증의 추정치를 계승한다. 21명에게 1인 1개를 판매하면 주문은 약 21건이고, 문의는 주문당 0.2~0.5건으로 약 4~11건, 반품·환불은 5~15% 가정에서 약 1~3건이다. 따라서 실제 Case는 보수적으로 **주문 12~30, Case 4~15** 정도를 계획하되 보장치로 말하지 않는다.

모든 기록에는 다음 태그를 붙인다.

- `organic`: 실제 사용자가 실제 필요로 주문·문의·취소·반품한 흐름.
- `scenario`: 배송 지연·오배송·파손·공급처 거절 등 의도적으로 만든 검증 흐름.
- `source`, `created_at`, `scenario_id`, `customer_id`, `order_id`를 함께 기록하고, 평가셋과 운영 로그를 섞지 않는다.

자가주문은 파인튜닝용 대규모 데이터가 아니다. 실제 문장·운영 시간·상태 전이·근거 대조를 회귀 테스트에 보강하는 용도다.

## 7. 법규 게이트

| 항목 | 내부 | 알파 | 베타 |
|---|---|---|---|
| 통신판매업 신고 | 문서 검토만 | 직전연도 거래 50회 미만이면 신고 면제 구간을 기록하되 사업자등록·판매 형태는 확인 필요 | 신고·사업자등록·약관 등 거래 구조별 요건을 확인하고 갖추면 된다 |
| 청약철회 | Mock 결정표·7일 경계 테스트 | 실제 주문은 7일 규칙과 예외를 사람 확인·코드 판정으로 적용 | 안내·환급·예외·감사 기록을 운영 절차로 고정하면 된다 |
| 개인정보 국외이전 | 가짜 PII, 외부 전송 없음 | 원문 배송정보 별도 Vault, 전송 audit, LLM masking | 별도 동의 또는 계약 이행에 필요한 처리위탁·보관과 처리방침 공개 등 요건을 갖추면 된다. 구체 적용은 확인 필요 |

법령사실 문서에 따르면 청약철회는 계약 내용 서면을 받은 날부터 7일, 상품이 늦으면 받은 날부터 7일이며 단순 변심도 인정된다. 예외 해당 여부는 LLM 단독 판단이 아니라 결정표와 사람 승인으로 처리한다.

## 8. 실패 시나리오와 A-COP 검증

| 실패 | Commerce 이벤트 | 검증되는 A-COP 흐름 |
|---|---|---|
| 배송 지연 | 예정일 초과, 배송 상태 미갱신 | Context 갱신→Case 생성→Fulfillment/VOC Team→안내 Action→대기·재계획 |
| 오배송 | 주문 상품 식별자와 수령 상품 불일치 | evidence 대조→Return/Refund proposal→승인→idempotency·audit |
| 파손 | 사진·수령 상태·배송 evidence | PII/첨부 범위 확인→정책 근거→사람 승인→Outcome close gate |
| 공급처 거절 | 공급처가 주문을 이행하지 않음 | Procurement 실패→`unknown`/escalated→대체 제안 또는 고객 확인 |

Team은 결과를 직접 확정하지 않는다. 상품·주문·배송의 원천 기록과 Action 실행 결과가 어긋나면 임의 성공으로 바꾸지 않고 `unknown` 또는 `escalated`로 남긴다.

## 9. 일정과 A-COP 잠식 정도

| 구분 | 실소요 | A-COP 영향 |
|---|---:|---|
| 생성 | 4~5일 | Commerce contract, Mock catalog/order/delivery, Case mapping, seed와 태깅 |
| 검증·통합 | 3~4일 | 주문→배송→문의→취소/반품 fixture, Action·approval·audit·PII 테스트 |
| 대기 | 1~2일 | 같은 기수 주문·응답, 배송/공급처 callback과 운영 확인 |

총 8~11 실소요일을 기존 10주 작업과 병행하되, A-COP 본체를 최대 **2~3명·5일 안팎의 병행 작업**만큼 잠식하는 상한으로 둔다. 전면 PG, 외부 배송, 해외 구매대행, 일반 고객 판매를 같이 하면 대부분을 잠식하므로 이번 범위에서 제외한다. v7의 Case·Core·평가·A2A·기존 CS MCP DoD를 줄여 쇼핑몰을 늘리지 않는다.

## 10. 중단 기준

다음 중 하나가 보이면 실제 쇼핑 흐름을 중단하고 Mock/Sandbox로 돌아간다.

- 가격·수량·상품 식별자 mismatch가 실행 직전 차단되지 않거나, 중복 주문·중복 환불이 발생한다.
- PII 원문이 Case·LLM·로그·외부 provider에 통제 없이 들어간다.
- 배송·결제 provider 실패가 `unknown`/escalated가 아니라 성공으로 기록된다.
- 청약철회 7일 경계나 예외를 코드와 사람 절차가 다르게 처리한다.
- 공급처·PG·배송 책임 주체와 환불·정산 원장이 확정되지 않는다.
- 실제 주문·Case 수가 계획보다 적어 상태·실패 다양성을 검증하지 못하거나, 반대로 운영 문의가 A-COP 본체 일정과 테스트를 밀어낸다.

중단은 실패 선언이 아니라 검증 대상의 위험도를 낮추는 전환이다. Mock으로 동일한 상태·근거·승인 계약을 계속 검증하고, 재개 조건을 충족한 뒤 제한 알파 또는 별도 베타 게이트를 다시 연다.
