## 핵심 재정의: "판결"에서 "모순 판정"으로

기존 uh 안의 문제는 "누구 말이 맞는가"를 AI가 판결하려 한 것이다. 그 진실은 시스템에 없다.
대신 고객의 주장을 세 갈래로만 분류한다.

```
1. 시스템 기록과 모순
2. 시스템 기록과 일치
3. 시스템 기록만으로 판정 불가
```

예시:
```
고객: "환불 승인 후에도 환불되지 않았다"
기록: refund_approved 있음, refund_completed 없음
→ 모순 아님 — 미완료 상태로 시스템 기록이 뒷받침

고객: "환불이 완료됐다고 안내받았다"
기록: refund_approved만 있고 refund_completed 없음
→ 시스템 기록과 불일치

고객: "상품을 실제로 받지 못했다"
기록: 배송완료 이벤트 존재
→ 판정 불가 (배송완료 기록은 운송 기록이지 실수령의 증거가 아니다.
   "고객 주장이 거짓"으로 처리하면 다시 임의의 외부 진실을 만드는 것이다)
```

세 번째 갈래(판정 불가)를 지우지 않는 것이 이 설계의 핵심이다. 모든 경합을 이분법으로
욱여넣으면 통합분석 문서가 이미 경고한 "우리가 심은 답을 우리가 찾는" 함정에 다시 빠진다.

## 전제 조건 — case_events가 정답셋이 되려면

에이전트가 생성한 주장만 담은 로그는 정답셋이 될 수 없다. 자기 출력으로 자기를 채점하는
순환이 된다. 이벤트를 최소 다음처럼 구분해야 한다.

```
claim_asserted     고객 주장
system_recorded    시스템이 기록한 사실
agent_proposed     에이전트 제안
action_approved    사람 승인
action_completed   실제 처리 완료
```

## 3기준 검증

- **정답셋 존재**: 이벤트 시각·상태·정책 버전으로 규칙 기반 라벨이 자동 생성된다
- **임의배정 비의존**: 판정 대상은 주문 ID와 이벤트 관계로 결정되며 지어낸 배정이 없다
- **코어루프 필요**: 근거수집 → 제안 → 검토 → 승인 → 종결 전 단계에 직접 쓰인다

## 처리 흐름

```
주장 추출 → 주장 유형화 → 관련 이벤트 수집
  → 모순 / 일치 / 판정불가 판정 → 답변·조치 제안 → 검토·승인 → 종결 또는 재오픈
```

별도 "분쟁조정 Team"을 새로 만들지 않는다. Team을 늘리는 비용(골든셋 라벨 축 추가,
Registry 레코드, Contract test, 기존 Team 회귀 검증 잠식)을 통합분석 문서가 이미
지적했으므로, ORD·LOG 안에 공통 검증 모듈로 넣는 편이 싸다.

## 부가 기능 4건 (같은 원리의 확장)

### A. 정책 시행일 기준 자격 판정
```
구매일 5/1, 정책v1(반품7일), 정책v2(반품14일, 5/10 시행), 반품요청 5/8
→ v1 기준 적용이 자동 산출된다 (요청 당시 시행 정책 기준)
```
탈락 조건: 정책 문서가 자연어로만 있고 시행일·조건이 구조화 안 되면 이 기능은 성립하지 않는다.

### B. 보상·환불 중복·초과 처리 방지
동일 주문에 환불·쿠폰·포인트·배송비 보상이 중복 승인되거나 결제액을 초과하는지 검사.
탈락 조건: `refund_approved`/`refund_completed`/`coupon_issued`/`point_credited`/
`compensation_completed` 이벤트가 없으면 "중복 지급 여부 판정 불가"가 되어 기능이 안 선다.

### C. 종결 자격·재오픈 판정
환불 승인만 있고 완료 없음, 필수 증빙 누락, 종결 후 배송상태 변경, 승인된 조치와 실제
완료 조치 불일치 — 이런 경우 종결 가능 여부를 자동 판정. "누가 옳은가"가 아니라
"처리가 끝났다고 말할 수 있는가"를 판정하는 기능이라, 분쟁 전담 Team 없이도 경합을
실제 운영 루프 안으로 들여온다.

### D. 이벤트 시간순서 무결성 검사
```
delivered < shipped
refund_completed < payment_confirmed
return_completed < return_requested
case_closed < case_opened
```
"배송사가 거짓말했는가"가 아니라 "우리 시스템 기록이 서로 양립 가능한가"만 판정한다.
탈락 조건: Olist에 상태변경 이력이 없고 최종상태만 있다면, 범위는 `case_events`에
실제로 기록된 이벤트로 한정해야 한다. 최종 상태만으로 전체 이력을 복원하려 하면 안 된다.

## 엄격히 탈락시킨 것

실제 수령 여부 판정, 판매자 고의 허위소명 판정, 제품 하자 객관 판정, 고객 감정·악성민원
판정, 시장가 기준 적정 보상액 산정, 배송사 실제 귀책 판정 — 전부 사진·상담원문·판매자
소명·운송사 원장·외부 시세 같은 지금 없는 데이터가 필요하다. 시스템 기록을 외부 현실의
진실로 과대해석하는 함정이라 채택하지 않는다.

## 최종 권고 우선순위

1. 고객 주장–시스템 기록 모순 판정
2. 정책 시행일 기준 자격 판정
3. 보상·환불 중복 방지
4. 종결 자격 및 재오픈 판정
5. 이벤트 순서 무결성 검사

Team 개수는 늘지 않는다 (착수 ORD·LOG 그대로). "경합상황을 다룬다"는 발표 포인트는
`Record Consistency & Resolution Guard`라는 이름의 공통 검증 계층으로 살아난다.
