# 참신도 재판정과 개선안

## 결론

이 아이템은 **기술 아키텍처만 보면 참신하지 않다.** LangGraph·RAG·상태머신은 표준 부품이다. 그러나 제품을 “답변을 잘하는 챗봇”이 아니라 **여러 전문 에이전트가 업무 Case를 넘겨받고, 승인·감사·평가를 거쳐 실제 운영되는 고객운영 시스템**으로 정의하면 참신한 축이 생긴다.

특히 시장 격차 문서가 지적한 단일 에이전트, 자체 호스팅 부재, 과장된 자동화율, 공개되지 않은 품질관리, 프로세스 오케스트레이션 공백에 A-COP의 현재 설계가 이미 맞닿아 있다. 다만 “있다”와 “팔 수 있다”는 다르다. 현재 상태는 PostgreSQL·pgvector 기반, 2개 내부 Team, A2A 교체점, 감사·승인·평가 하네스까지 구현됐지만, 자체 호스팅 패키지와 고객용 평가 제품은 아직 추가 산출물이 필요하다.

따라서 10주 발표의 한 문장은 다음이 적절하다.

> **A-COP은 자동화율을 부풀리는 챗봇이 아니라, 여러 Agent가 고객 Case를 처리하고 사람이 어디서 개입했는지와 결과의 근거를 재생·측정할 수 있게 하는 고객운영 실행층이다.**

## A. 참신도 재판정

| 축 | 참신한가 | 근거 |
|---|---|---|
| 기술 아키텍처 | 아니오 | LangGraph·RAG·상태머신 자체는 표준이다. A-COP의 가치는 부품이 아니라 Case lifecycle, Context Broker, Team 계약, 승인·idempotency를 한 실행 모델로 묶는 데 있다. |
| 제품 포지션 | 조건부로 그렇다 | 시장 격차 문서는 Fin에 “single-agent system with zero evidence of multi-agent support, agent-to-agent communication, or specialist routing”이라고 적는다. ### 격차 10의 가격 가설

해결당 과금의 대안은 **설치/플랫폼 기본료 + 좌석 또는 처리량 구간 + 선택적 운영지원**이 가장 자연스럽다. 고객이 자동화를 많이 할수록 비용이 선형으로 폭증하지 않게 하고, 자체 호스팅 고객은 인프라 비용을 직접 부담하는 대신 플랫폼 라이선스와 지원 범위를 명확히 한다. 아직 원가와 구매 의사 데이터가 없으므로 금액은 제시하지 않는다. 내부에서는 가상의 세 요금안을 비교하되, 발표에서는 “해결 건당 과금 회피를 목표로 한 구조 가설”이라고만 말한다.

## C. 개선안

아래 개선안은 모두 **순증 금지** 원칙을 적용한다. 기존 기능 하나를 제품 산출물로 재포장하거나, 새 기능을 넣는 대신 데모 polish·두 번째 Marketplace Adapter·6개 Team 독립 구현·실 PG를 뺀다. 실소요는 사람-일이 아니라 세 종류의 작업 슬롯이다.

### 개선안 1. 자체 호스팅·데이터 주권을 1급 제품 특성으로

**무엇**: 고객 PostgreSQL 안에서 Case·trace·평가 데이터를 운영하고, 설치·복구·데이터 경계를 제품 화면에서 확인하게 한다.

**왜 차별점인가**: 격차 2의 “no self-hosted option, no on-premise deployment, and no air-gapped capability”를 겨냥한다.

**A-COP에 이미 있는 것**: PostgreSQL·pgvector, `SqlGraphAdapter`, tenant 격리, masking, Port/Adapter, 로컬 실행 기반을 재사용한다.

**추가로 만들 것**: 설치 README/스크립트, 환경변수 템플릿, migration·backup/restore 체크, 데이터 흐름 표, `deployment readiness` 리포트.

**실소요**: 생성—설치 번들·문서 작성 슬롯 / 검증·통합—빈 DB 설치→seed→평가→복구 확인 슬롯 / 대기—DB/GPU가 필요한 실행 대기 슬롯.

**무엇을 빼는가**: Docker 의존 구현, 두 번째 외부 Adapter, air-gapped 인증을 이번 범위에서 뺀다.

**발표에서 어떻게 보여주나**: 외부 SaaS 화면이 아니라 로컬 PostgreSQL에서 Case를 만들고, 네트워크를 끈 상태의 데이터 흐름과 복구된 trace를 한 화면에 보여준다.

### 개선안 2. 감사 가능성을 제품 기능으로

**무엇**: 한 Case의 입력·분류·검색 근거·Team 위임·승인·Action 결과·사람 수정까지 재생하고 규제 검토용 trace를 내보낸다.

**왜 차별점인가**: 격차 6의 “complete trace for regulatory review”와 격차 7의 거버넌스 공백을 겨냥한다.

**A-COP에 이미 있는 것**: append-only events, evidence, approval, audit, `/ui/trace`, 버전 박힌 산출물, PII masking을 재사용한다.

**추가로 만들 것**: `trace_export.json` 계약, actor/model/prompt/Team/version/evidence/approval/result 필드, 재생 UI, export 권한과 누락 경고.

**실소요**: 생성—export schema·재생 UI 슬롯 / 검증·통합—정상·거절·timeout·재개 Case 회귀 슬롯 / 대기—외부 승인 입력 대기 슬롯.

**무엇을 빼는가**: 별도 Graph DB와 예쁜 리포트 PDF를 뺀다. 현재 `SqlGraphAdapter`와 구조화 export로 시작한다.

**발표에서 어떻게 보여주나**: 고객이 “왜 이 환불 제안이 나왔나?”라고 묻자 Case를 시간순으로 재생하고, 근거 문서·승인자·Action 결과를 하나의 export로 내려준다.

### 개선안 3. 정직한 자동화율 공개

**무엇**: 시스템이 자동화율, 인계율, 실패율, 재처리율을 분모·기간·Case 유형·95% CI와 함께 스스로 보고한다.

**왜 차별점인가**: 격차 3의 “90%+ demo”와 “55-70% production” 간극을 겨냥한다.

**A-COP에 이미 있는 것**: `classification_failed`/`escalated`, golden·holdout, 540 관측, bootstrap/McNemar, organic/scenario 구분, 표본이 작으면 작다고 말하는 규칙을 재사용한다.

**추가로 만들 것**: 자동화율 정의서, 분모·제외 사유, Case funnel, CI 계산 리포트, “현재 측정 불가” 상태. 자동화율을 한 숫자로 꾸미지 않고 유형별로 나눈다.

**실소요**: 생성—지표 계약·대시보드 슬롯 / 검증·통합—golden/holdout와 실제 내부 Case의 분모 대조 슬롯 / 대기—알파 Case가 쌓일 때까지의 관측 대기 슬롯.

**무엇을 빼는가**: 데모에서 90%를 암시하는 고정 KPI, 근거 없는 전환율·SLA·반품률을 뺀다.

**발표에서 어떻게 보여주나**: “자동화율 90%” 대신 전체 Case를 완료·인계·실패·보류로 펼치고, 현재 표본으로 무엇을 말할 수 없는지까지 같은 화면에 표시한다.

### 개선안 4. 고객용 평가 하네스

**무엇**: 고객이 자기 Case를 golden/holdout으로 라벨링하고, A/B/Proposed를 실행해 회귀·근거·Tool 호출 품질을 비교한다.

**왜 차별점인가**: 격차 4의 “end-to-end quality management capability” 비공개 공백을 겨냥한다.

**A-COP에 이미 있는 것**: golden 60·holdout 20, runner 3종, judge rubric, bootstrap/McNemar, ablation, 보존된 holdout을 재사용한다.

**추가로 만들 것**: Dataset version, 라벨 승인, holdout 봉인, Run 비교, 실패 샘플 export, 사람 라벨 agreement 화면.

**실소요**: 생성—label/import/run 화면 슬롯 / 검증·통합—holdout 변경 방지와 점수 재현성 슬롯 / 대기—고객 라벨·LLM 실행 대기 슬롯.

**무엇을 빼는가**: 새로운 judge 모델과 대규모 자동 라벨링을 뺀다. 사람 라벨 20건이 아직 미측정이라는 사실을 그대로 표시한다.

**발표에서 어떻게 보여주나**: 고객의 10개 샘플 중 2개를 holdout으로 봉인하고, 정책 문서가 바뀐 뒤 회귀가 난 Case만 자동으로 펼쳐 보인다.

### 개선안 5. 사람에게 넘길 지점을 설계로 명시

**무엇**: 컴플레인·정책 예외·금전·근거 부족은 자동 완료하지 않고, 인계 이유와 사람이 해야 할 판단을 포함한 handoff packet으로 넘긴다.

**왜 차별점인가**: 격차 8의 “technically right but tonally wrong” 문제를 인정하고 인계 품질로 승부한다.

**A-COP에 이미 있는 것**: Human Approval, WAIT/RESUME, `ActionProposal`, `unknown`, 분류 실패 시 escalated, ContextPack의 `degraded`/`omissions`를 재사용한다.

**추가로 만들 것**: handoff reason code, 누락 증거 목록, 추천 질문, 사람 수정 결과, 인계 후 재평가 지표.

**실소요**: 생성—reason code·handoff 화면 슬롯 / 검증·통합—불만·금액·근거 누락 시 인계 회귀 슬롯 / 대기—사람 승인·수정 입력 대기 슬롯.

**무엇을 빼는가**: 컴플레인 전면 자율처리와 무인 환불을 뺀다.

**발표에서 어떻게 보여주나**: 화난 고객의 환불 요구에 시스템이 억지 답변을 보내지 않고, “정책 예외 판단 필요·필수 증거 2개”를 사람에게 건네고 승인 뒤 재개한다.

### 개선안 6. Bring-your-own-Agent

**무엇**: 고객이 자기 Agent를 Agent Card와 A2A 계약으로 등록하고 A-COP Controller가 검증된 범위 안에서 Task를 위임한다.

**왜 차별점인가**: 격차 1의 멀티에이전트·A2A 공백을 제품 확장점으로 만든다.

**A-COP에 이미 있는 것**: Agent Card, A2ATeamExecutor, input-required, Artifact, 인증·실패·취소 설계, Registry와 Team Contract를 재사용한다.

**추가로 만들 것**: Agent 등록/검증 API, capability·scope·version 승인, timeout/unknown/cancel trace, 최소 외부 Agent fixture.

**실소요**: 생성—등록 화면·검증 fixture 슬롯 / 검증·통합—LOCAL↔A2A 교체와 실패·취소 회귀 슬롯 / 대기—원격 왕복·timeout 대기 슬롯.

**무엇을 빼는가**: 여러 외부 Agent marketplace와 공개 생태계 연동을 뺀다.

**발표에서 어떻게 보여주나**: 같은 Case에서 내부 Technical Team을 외부 검증 Agent로 바꾸고, Agent Card·input-required·Artifact·취소 trace가 동일 Case에 남는 장면을 보여준다.

### 개선안 7. 온보딩 비용 절감

**무엇**: 정책·샘플 Case·Tool 계약을 넣으면 첫 golden 후보와 부족한 근거·필요한 엔지니어링 작업을 자동으로 보여준다.

**왜 차별점인가**: 격차 9의 “engineering is still required upfront”를 없애지는 못해도, 어디까지 필요한지 투명하게 줄인다.

**A-COP에 이미 있는 것**: Context Broker, TeamManifest, Registry, Composer, Mock Commerce, 평가 하네스를 재사용한다.

**추가로 만들 것**: 온보딩 wizard, 문서 scope/PII 체크, Case 샘플 import, golden 후보, “통합 없이는 불가” 목록과 예상 작업 범위.

**실소요**: 생성—wizard·checklist 슬롯 / 검증·통합—샘플→Context→평가 첫 실행 슬롯 / 대기—문서 임베딩·LLM 평가 대기 슬롯.

**무엇을 빼는가**: 모든 헬프데스크에 대한 즉시 커넥터와 자동 영구 Catalog 승격을 뺀다.

**발표에서 어떻게 보여주나**: 정책 문서와 10개 Case를 넣자 시스템이 “이 3개는 근거 부족, 이 Tool은 scope 승인 필요, 첫 평가 세트는 이 8개”라고 온보딩 보고서를 만든다.

### 우선 발표용 3분 장면

1. 고객 컴플레인이 Case가 되고, Technical Team이 근거를 요청하다가 정책 예외에서 사람에게 넘긴다.
2. 사람이 승인하면 WAIT/RESUME를 거쳐 Action이 한 번만 실행되고, 전체 trace가 재생된다.
3. 같은 테스트 세트를 Proposed와 비교해 자동화율·인계율·근거 점수와 CI를 함께 보여준다.

### 심사위원 질문 5개와 답변

| 질문 | 답변 |
|---|---|
| “Sierra나 Decagon이 이미 하는 거 아닌가요?” | 답변을 자동으로 보내는 것만 비교하면 그렇다. 우리의 주장은 모델이나 RAG가 새롭다는 것이 아니다. 시장 격차 문서는 Fin의 단일 에이전트와 Sierra·Decagon의 공개되지 않은 end-to-end 품질관리, conversation-closure 중심의 한계를 지적한다. A-COP은 전문 Team/A2A, Case 전 과정 trace, 고객용 평가 하네스, 명시적 사람 인계를 하나의 실행층으로 묶는다. 이 네 가지를 실제 trace와 평가 화면으로 증명해야 한다. |
| “그래서 자동화율이 몇 %인데요?” | 현재 전체 운영 모집단의 숫자를 가장하지 않는다. 기준선 평가에는 540 관측에서 Proposed 40/180 성공과 grounding 3.98이 기록돼 있지만, 이것을 실제 고객 자동화율이라고 부를 수 없다. 발표에서는 분모·Case 유형·표본·CI를 함께 보여주고, 알파 데이터가 쌓이기 전에는 “측정 중”이라고 답한다. |
| “이걸 왜 우리가 사야 하죠? 기존 헬프데스크에 붙이면 되잖아요” | 헬프데스크는 티켓을 모으는 장소일 수 있지만, A-COP의 구매 이유는 티켓 답변이 아니다. 주문·배송·정책·승인·재처리·외부 Agent를 한 Case와 감사 원장으로 연결하고, 어떤 Agent가 무엇을 근거로 했는지 재생한다. 기존 시스템을 대체한다고 하지 않고, 그 위의 고객운영 실행·검증층으로 붙이는 포지션이다. |
| “자체 호스팅이 정말 되는 건가요?” | PostgreSQL·pgvector와 로컬 실행 기반은 이미 있다. 그러나 air-gapped 인증이나 상용 운영 패키지가 완료됐다고 말하지 않는다. 10주에는 설치·migration·backup/restore와 데이터 경계를 검증하고, 미검증 범위를 명시한다. |
| “컴플레인까지 자동화하면 책임은 누가 지나요?” | 컴플레인을 전부 자동 처리하지 않는다. 감정·정책 예외·금전·근거 부족은 handoff와 Human Approval로 멈추고, 사람에게 필요한 증거와 판단을 넘긴다. 자동화율보다 잘못 자동화하지 않는 지점과 인계 품질을 제품 기능으로 측정한다. |

## E. 범위 통제와 최종 우선순위

개선안을 모두 구현하면 원래 위험인 **범위가 계속 커지는 문제**가 그대로 반복된다. 10주에 반드시 고를 3개는 다음이다.

| 우선순위 | 선택 | 이유 | 기존 범위에서 뺄 것 |
|---:|---|---|---|
| 1 | 감사 가능성 제품화 | 이미 `/ui/trace`, events, evidence, approval이 있어 재사용률이 가장 높고, 격차 6·7·5를 동시에 겨냥한다. | PDF polish, 별도 Graph DB |
| 2 | 정직한 자동화율·평가 하네스 제품화 | 이미 golden/holdout·통계·실측 규칙이 있어 “말이 아닌 측정”을 바로 보여줄 수 있다. 격차 3·4를 동시에 겨냥한다. | 새 judge 모델, 근거 없는 KPI |
| 3 | 사람 인계 + 자체 배포 체크 | 컴플레인 리스크를 숨기지 않으면서 PostgreSQL 기반을 구매 이유로 만든다. 격차 2·8을 겨냥한다. | 무인 환불, air-gapped 인증 주장, 외부 일반고객 Live |

### 나머지 개선안의 처리

| 개선안 | 판단 | 위치 |
|---|---|---|
| BYOA | A2A는 이미 구현됐으므로 최소 fixture와 Agent Card 장면만 내부에 남긴다. 고객용 등록·생태계는 후순위다. | 등록·marketplace는 `docs/vision/` |
| 온보딩 비용 절감 | 10주에는 wizard 전체가 아니라 설치·평가 checklist와 부족한 근거 리포트만 남긴다. | 고객별 자동 통합은 `docs/vision/` |
| 가격 구조 | 금액 없는 가격 가설과 비용 측정 항목만 발표한다. 실제 가격은 구매 인터뷰·원가 데이터 뒤에 정한다. | 상용 요금표는 `docs/vision/` |
| 격차 11 통합 확장 | Adapter 계약과 Mock만 유지한다. Freshdesk·HubSpot 정식 연결은 하지 않는다. | 커넥터 로드맵은 `docs/vision/` |
| 5개 Commerce Team | 현재 계획대로 3개 구현 축을 넘지 않는다. Return & Refund는 Registry/Mock으로 남긴다. | 독립 Team 실연동은 `docs/vision/` |

최종적으로 A-COP의 참신함은 “새로운 모델”이 아니라 **운영 가능한 에이전트 협업을 감사·측정·인계 가능한 Case 시스템으로 만든다는 선택**에 있다. 이 문장을 증명하는 세 장면만 구현하고, 나머지는 비전으로 분리해야 참신도도 범위도 함께 지킬 수 있다.
