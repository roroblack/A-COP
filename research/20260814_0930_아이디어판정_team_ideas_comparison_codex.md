대상: `research/team_ideas_comparison.md`의 주장 A~E

전제: 6명, 10주, 코드 0줄, 실사용자·실데이터 없음. 평가는 에이전틱함, 분석 결과가 시스템 동작을 바꾸는지, 정량 평가 가능성을 우선한다. 선행 검증 문서의 결론인 “3층 에스컬레이션과 리스크 경로는 유지하되 8개 에이전트 포장은 버린다”를 전제로 삼았다.

## 2. 주장 A: “이미 다섯 지점에서 수렴했다”

반론은 절반만 성공한다. Case 단위 처리, 책임 주체 분리, HITL, 피드백 분석, 테넌트 분리라는 공통 방향은 실제로 네 문서에 반복된다. 따라서 “완전히 다른 아이디어 중 하나를 고르는 단계는 지났다”는 진단은 유지한다.

그러나 공통 명사는 합의가 아니다. uh는 문의 실패를 분쟁 사다리로 올리는 SLA·권한·리스크 구조를 핵심으로 보고, sw는 상태·근거·승인·감사 로그를 핵심으로 본다. jh는 고객의 말에서 수요와 상품 처분 기회를 찾는다. 세 문서는 다음을 합의하지 않았다.

- `Case`가 어떤 최소 입력을 보장하는가. sw에는 주문번호·상품·수량·첨부 증거가 있지만 jh D에 필요한 검수·재고 필드는 없다.
- 피드백 분석 결과가 실제로 어느 전이를 바꾸는가. sw의 Seller Quality는 운영자 검토안이고, uh의 분쟁률은 환불 경로 입력이다.
- 정답셋이 있는 기능과 없는 기능을 어디서 자르는가. jh C의 기획전 제안은 정답셋이 없고, uh의 법정 사실 인정도 합성 규칙에 의존한다.
- 판매자·플랫폼·배송사 역할과 L0~L3 층이 하나의 라우팅 모델인지 별도 모델인지.

따라서 A는 “기반 구조는 수렴했다. 그러나 제품 범위와 평가 계약은 아직 수렴하지 않았다”로 수정한다.

## 3. 주장 B: sw의 확장성과 v6 재사용

### v6 재사용은 살아남는다

sw 문서는 Case Lifecycle, Supervisor, Agent Team 계약, Context Pack, Action Proposal, 승인, 감사 로그, baseline·ablation을 v6의 용어와 거의 일대일로 이어간다. 10주 프로젝트에서 이미 팀이 이해한 계약을 다시 쓰는 편이 안전하다. 이 점에서 sw가 최상이라는 평가는 원문의 근거와 대체로 같다.

다만 “확장 용이성”은 다른 근거가 필요하다. sw 원문은 Port/Adapter 분리, COMMON ENGINE, TENANT CONFIGURATION을 선언하고 Phase 4에 기업 이식 구조를 둔다. 이는 좋은 경계 설계이지, 확장성이 검증됐다는 증거는 아니다. 특히 문서의 구현 순서는 Phase 1~3에서 한 기업·Mock DB·한국어 Case를 만들고 Phase 4에서 이식 구조를 넣는 방식이다. 10주 안에 Phase 4까지 실제로 증명하지 못하면 선언에 머문다.

### 10주 안에 증명할 최소 실험

전체 기업 이식은 하지 않는다. 동일한 Case 엔진에 두 개의 Adapter와 두 개의 tenant config만 붙인다.

1. `OrderPort`, `LogisticsPort`, `ActionPort`를 공통 계약으로 고정한다.
2. `tenant_a`와 `tenant_b`가 환불 한도·SLA·정책 문서만 다르게 갖게 한다.
3. 같은 Case fixture를 두 tenant에 실행해 결과 JSON, 상태 전이, 승인 여부를 비교한다.
4. Adapter를 Mock A에서 Mock B로 바꾸어도 Controller와 Team 코드는 수정하지 않는다.
5. 이 교체를 contract test 하나로 재현하고, import 경계와 tenant 누출 테스트를 남긴다.

이 실험을 통과하면 “문서상의 분리”가 “작은 범위에서 증명된 분리”가 된다. 통과하지 못하면 발표에서는 확장 가능성이 아니라 확장 설계라고 말해야 한다.

## 4. 주장 C: 계층과 Case 상태는 정말 직교하는가

### 개념상 분리

uh의 L은 처리 주체·권한·비용·출구를 나타내고, sw의 상태는 처리 진행도를 나타낸다. 이 정의만 놓고 보면 별도 필드로 모델링할 수 있다. 예를 들어 플랫폼이 판매자 응답을 기다리는 `L1 / waiting_external`, 플랫폼 운영자 승인을 기다리는 `L2 / waiting_approval`은 의미가 있다.

### 현재 문서에서는 직교성이 깨진다

두 축이 모든 값을 자유롭게 조합할 수 있다는 뜻은 아니다.

- L0는 uh 문서에서 조회·안내·경량 처리의 종료층이다. 그런데 `L0 / waiting_approval`은 자동 승인 한도를 넘은 주소 변경·취소라면 의미가 있지만, 기본 경로의 정상 조합은 아니다.
- L3는 소비자원 피해구제 서식 패키징과 절차 안내라는 출구다. `L3 / gathering_evidence`는 외부 서식에 필요한 자료를 모으는 단계로 의미가 있을 수 있지만, L3가 “외부 절차로 넘어간 뒤”라는 뜻이면 L2의 증거 수집과 중복된다.
- `L1 / proposed`와 `L2 / proposed`는 서로 다른 권한 주체의 Action Proposal인지, 단순히 같은 Proposal 상태를 층별로 표시한 것인지 정의가 없다.
- uh의 “문의 처리가 실패하면 다음 상태로 분쟁 격상”이라는 설명은 L을 상태처럼 사용한다. 반면 sw의 `classified → gathering_evidence`는 처리 단계다. 원문 표현 자체가 두 축을 섞는다.
- seller quality, 판매자 이의제기, 외부 절차는 선형 층이 아니라 재진입 경로다. 단순한 4×6 격자로 표현하면 정상 경로와 재진입 경로가 구별되지 않는다.

결론은 “수학적으로 분리 가능하다”이지 “현재 설계에서 저비용으로 합쳐진다”가 아니다. 대부분의 격자 칸은 비어 있거나 추가 설명 없이는 같은 의미를 두 이름으로 표시한다.

### 유지할 경우 필요한 구현과 비용

최소 구현은 `layer`, `workflow_status`, `owner_role`, `checkpoint`, `transition_reason`을 Case에 함께 두고, 허용 조합 표를 별도로 두는 방식이다. 단순히 두 enum을 추가하는 것으로 끝나지 않는다.

- 상태 전이 검증: layer가 바뀌는 전이와 status만 바뀌는 전이를 구분한다.
- 체크포인터: `waiting_external`에서 재개할 때 layer·owner·필요 증거를 함께 복원한다.
- 충돌 처리: L1 판매자 응답과 L2 플랫폼 판단이 동시에 도착했을 때 최신 status만 덮어쓰지 않게 한다.
- 평가 라벨: 상태 전이 정확도와 층·권한 라우팅 정확도를 별도로 라벨링한다.
- UI·로그: “어느 단계인가”와 “누가 권한을 갖는가”를 분리해 보여준다.

추정 비용은 MVP 기준으로 공통 스키마·전이 검증·체크포인트·UI·테스트에 1~2인주, 유효 조합 전체와 재진입 평가까지 하면 2~3인주다. 여기에 케이스 라벨과 시나리오 설계가 10~15% 늘어난다. 이 수치는 기존 구현 측정값이 아니라 문서상 요구사항을 작업 단위로 환산한 계획 추정치다.

따라서 C는 “uh의 층을 표시용·정책 메타데이터로 제한하면 sw 상태 위에 얹을 수 있다”로 수정한다. L0~L3와 Case 상태의 완전한 격자는 만들지 않는다.

## 5. 주장 D와 대안 조합

아래 확률은 코드 0줄, 6명, 10주에서 “핵심 데모와 정량 리포트까지 완성”할 확률의 계획 추정치다. 정확한 통계가 아니라 범위 비교용이다.

| 조합 | 10주 완주 추정 | 심사 점수 전망 | 장점 | 실패 지점 |
|---|---:|---:|---|---|
| (a) sw 단독 + uh 축 전부 배제 | 75~85% | 6.5~7.5/10 | 계약·상태·평가를 가장 빨리 완성 | 일반적인 Case 오케스트레이션으로 보이고, 분석이 동작을 바꾸는 장면이 약함 |
| (b) uh 단독을 뼈대로 | 35~50% | 완주 시 7.5~8.5/10, 기대값 5.5~6.8/10 | SLA·리스크·역할 분기로 에이전틱한 장면이 강함 | L0~L3, 판매자 모드, 법정 RAG, 이의제기, 데이터 제작이 동시에 커짐 |
| (c) 제3의 조합: sw core + uh의 M-0 리스크 경로와 M-3 SLA만 유지 + jh B를 배치 집계로 흡수 | 65~75% | 8.0~8.8/10 | 상태·승인·평가를 재사용하면서 분석 결과가 환불 경로와 격상을 바꿈 | uh 축의 입력 정의와 정책 엔진을 먼저 고정해야 함 |

가장 나은 선택은 (c)다. 원래 D의 “sw 뼈대 + uh 차별화”는 살아남지만, 차별화 축을 L0~L3 전체가 아니라 두 개의 검증 가능한 동작으로 줄여야 한다.

- M-0: 금액·증빙·이력·스토어 분쟁률을 결정론적 리스크 룰로 계산하고 선환불/소명 우선 경로를 바꾼다.
- M-3: 판매자·배송사 응답 SLA가 만료되면 같은 Case를 다음 권한 주체로 재개한다.
- jh B: 반복 VOC·급증 집계 결과를 스토어 분쟁률 또는 검토 우선순위 입력으로 연결한다.

자동 해결률은 보조 지표로 유지한다. L0~L1의 정의가 uh와 sw 사이에서 달라질 수 있으므로, 주 지표는 route accuracy, 상태 전이 정확도, 승인 위반율 0%, 리스크 경로 정확도로 둔다.

## 6. 잘못 자른 것과 잘못 남긴 것

### 컷 목록에서 일부 살릴 것

- uh 판매자 온보딩 전체는 기능으로는 자르되, 마지막의 `config 등록`과 tenant 교체 fixture는 남긴다. 온보딩 에이전트를 만들 필요 없이 수동 입력으로 config를 추가하고 그래프·SLA·승인 한도가 바뀌는 1분 데모를 만든다.
- uh EXT-3 다국어는 평가 대상이 아닌 발표용 확장 카드로만 남길 수 있다. 다만 한국어 평가를 흐리지 않도록 MVP 기능으로 포장하지 않는다.
- uh의 L0는 별도 에이전트가 아니라 접수·분류·조회 비용 계층으로 남긴다. 완전히 배제하면 “분쟁만 처리하는 시스템”으로 회귀한다.
- sw의 storyboard는 계속 살린다. 단, 확정된 (c)의 리스크 분기와 SLA 재개 장면으로 갱신해야 한다.

### 남긴 목록에서 잘라낼 것

- jh 트랙 D는 MVP에서 자른다. 현재 sw Case 입력에는 반품 사유·주문·상품·수량·첨부자료가 있지만, 검수 결과·실물 상태 등급·재고 위치·재판매 가능 채널·가격 재산정 근거가 없다. 반품 사유는 “고객이 왜 돌려보냈는가”이지 “검수 후 다시 팔 수 있는가”의 충분조건이 아니다.
- D를 구현하려면 최소한 `inspection_result`, `condition_grade`, `defect_type`, `inventory_location`, `resale_channel`, `original_cost`, `resale_price_rule`, `quantity`가 필요하다. 검수 이벤트와 재고 상태 변경, 가격 계산, 리퍼브 Action 승인까지 붙으므로 분류기 하나가 아니다.
- sw의 Seller Quality를 독립 에이전트로 유지하지 않는다. 개별 Case에 필요한 판매자 품질 조회와 jh B의 반복 VOC 집계를 결정론적 배치 모듈로 두고, 운영자 검토안만 반환한다. v6의 Agent Team 2개 원칙과도 맞는다.
- “구매자 출구 L3 ↔ 재고 출구 리퍼브”의 대칭은 발표상 매력은 있지만, 대칭성 자체는 입력과 정답을 대신하지 못한다. 시각적 대칭 때문에 데이터 모델을 확장하지 않는다.

## 7. 주장 E에 대한 별도 판정

반품 사유가 Case에 있다는 전제는 맞다. 그러나 원문의 세 가지 이유 중 “추가 데이터가 없다”와 “분류 문제라 채점된다”는 성립하지 않는다.

- 재판매 가부의 정답은 반품 사유만으로 라벨링할 수 없다. 단순 변심이어도 개봉·사용·오염 여부에 따라 결과가 달라진다.
- 상태 등급을 사람이 검수하지 않으면 모델은 사진이나 텍스트만으로 재고 의사결정을 추정한다. uh EXT-2 VLM도 컷 대상으로 삼은 상황에서 D만 남기는 것은 더 큰 입력 공백을 만든다.
- 재고 위치가 없으면 “팔 수 있음”을 판정해도 어느 창고에서 어떤 채널로 출고할지 결정할 수 없다.
- 가격 재산정이 없으면 리퍼브 기획전 제안은 상품 분류가 아니라 문구 생성이다. 원가·판매가·할인 하한·재고 체류일이 필요하다.

D를 살리고 싶다면 Phase 2에서 별도 모듈로 재제안한다. 그때도 “리퍼브 기획전 자동 실행”이 아니라 “검수 완료 Mock 재고에 대한 판매 가능성·가격 제안, 사람 승인 후 등록”으로 범위를 정한다.

## 8. 데이터 전략과 외부 holdout

선택은 sw의 Olist 거래 골격 + 통제된 합성 한국어 VOC다. 이유는 Case의 주문·상품·결제·배송 연결과 재현 가능한 상태 전이를 먼저 확보해야 하기 때문이다. uh의 AI Hub 스토어별 배정은 한국어 품질에는 유리할 수 있지만, 리뷰를 스토어별로 임의 배정하면 tenant·책임 주체·SLA 라벨이 인공적으로 생긴다. 이는 라우팅 평가를 오염시킨다.

단, 합성 한국어 VOC를 외부 근거처럼 말하지 않는다.

- 개발·튜닝: Olist 거래 skeleton + 합성 한국어 VOC. 합성 데이터에는 생성 규칙, 주입한 정답, 원문·사실 필드를 분리해 기록한다.
- 텍스트 외부 holdout: AI Hub 쇼핑몰 리뷰 중 접근권·라이선스를 확인한 별도 subset을 사용한다. 학습·프롬프트 예시·스토어 배정에 쓰지 않고, 의도·감성·이슈·중복 클러스터 평가에만 사용한다. 주문·배송 상태와 연결되지 않으므로 route·환불 정답 평가에는 사용하지 않는다.
- 결정·근거 holdout: 팀이 만든 합성 분쟁 규칙과 분리된 공공데이터포털 소비자 분쟁 상담·피해구제 자료를 사용한다. 정책 RAG 기능에 먼저 넣지 않은 문항을 holdout으로 보관하고, 인용 정확도와 판정 필드만 평가한다. 파일 이용 조건과 최신 시행일은 별도 확인한다.
- 외부 데이터 접근이 승인되지 않으면 AI Hub나 공공 자료를 외부 holdout이라고 부르지 않는다. 그 경우 공개 출처 기반 holdout 확보가 완료될 때까지 한국어 품질·법정 판정의 외부 일반화 주장을 보류한다.

평가셋은 개발/튜닝, 내부 golden, 외부 holdout 세 묶음으로 해시와 생성·수집 시점을 기록한다. 합성 데이터의 정답을 그대로 맞히는 성능과 외부 텍스트의 일반화 성능을 분리해 보고한다.

## 9. 발표 첫 슬라이드 한 문장

“고객의 피드백과 거래 근거를 분석해, 케이스마다 다음 행동과 승인 경로를 바꾸는 멀티에이전트 CS 운영 시스템.”

여기서 핵심은 “답변을 잘 만든다”가 아니라 “분석 결과가 경로와 승인 상태를 바꾼다”이다. sw의 Case·근거·감사 구조는 이 문장을 실행 가능하게 하고, uh의 리스크·SLA는 화면에서 차이를 만들며, jh의 B 집계는 분석 입력을 제공한다.

## 최종 권고

채택안은 “sw Case 오케스트레이션 core + uh M-0 리스크 경로 + uh M-3 SLA 격상 + jh B의 결정론적 VOC 집계”다. uh의 전체 L0~L3 격자, 판매자 온보딩, EXT-1·EXT-2, jh C·D, 독립 Seller Quality 에이전트는 MVP에서 제외한다.

이 구성의 성공 조건은 세 가지다.

1. 리스크 점수가 실제로 `proposed` 이후의 선환불/소명 우선 경로를 바꾼다.
2. SLA 만료가 실제로 Case의 owner·layer 메타데이터와 다음 상태를 바꾼다.
3. 외부 holdout, 승인 위반율, 상태 전이, 경로 정확도를 합성 golden과 분리해 보고한다.

이 세 조건을 충족하지 못하면 통합안은 기능을 많이 가진 CS 데모일 뿐, 심사 기준에 맞는 에이전틱 시스템이라고 방어하기 어렵다.
