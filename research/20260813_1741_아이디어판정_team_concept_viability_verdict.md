## 0. 한 문장 결론

컨셉의 뼈대(3층 에스컬레이션 상태기계 + 리스크 기반 경로 분기)는 실효성이 있고 지켜야 한다.
반면 "에이전트 팀 8개"라는 포장은 실효성이 없다 — 실제로 에이전트여야 하는 것은 2개뿐이고,
나머지 6개는 결정론적 모듈일 때 더 강해진다. 두 검증이 이 지점에서 독립적으로 일치했다.

## 2. 두 검증이 독립적으로 일치한 지점 (신뢰도 높음)

### 2.1 판매주체 판별은 자기모순이다
테넌트 config에 `sale_type: marketplace`가 이미 선언되어 있다(문서 02섹션). 선언된 값을 LLM이
"판별"한다는 설계다. Codex는 다른 각도에서 같은 결론에 도달했다 — 판매유형은 문의 문장이 아니라
주문·입점·계약 메타데이터로 결정되므로 텍스트 분류로 맞힐 수 있다는 가정 자체가 틀렸다.
→ 조회로 강등. Supervisor에 남는 실질은 이슈·감성 분류뿐.

### 2.2 리스크 스코어링은 에이전트가 아니라 함수여야 한다
LLM으로 점수를 내면 재현성이 깨져 UP-0의 평가가 통째로 무너진다. 결정론적이면 임계값 스윕이
가능해지고 "오환불률 vs 처리시간" 트레이드오프 곡선을 그릴 수 있다.
발표에서 가장 좋은 그림이 여기서 나온다.

### 2.3 "법정 기준이라 정답 검증이 깔끔하다"는 절반만 맞다
결정론적인 건 청약철회 기간·예외 사유 같은 소수 구간이고, 실제 분쟁의 결정변수는 사실 인정이다
("파손이 배송 중인가 발송 전인가"). 팀이 만든 합성 규칙으로 골든셋을 만들고 거기에 맞추면
측정되는 것은 법률 정확도가 아니라 자기 일관성이다.

### 2.4 페르소나 시뮬레이터 + UP-3 = 평가 순환 오염
우리 LLM이 소명을 쓰고 우리 LLM이 심사한다. UP-3까지 넣으면 순환이 삼중이 된다.
문서 02섹션의 "팀원이 판매자 역할로 직접 개입"이 이미 정답을 갖고 있다 —
시뮬레이터는 부하 생성용으로만 쓰고, 평가셋 소명은 사람이 쓴다.

### 2.5 범위 과잉
8팀 + 3층 + 멀티테넌트 + 2개 분쟁 전선은 6명·10주에 맞지 않는다.
v6에서 잠근 MVP(Agent Team 2개)보다 도메인 규칙·양측 상태·외부 서식·RAG 코퍼스·페르소나 평가를
동시에 얹는 구조다. 특히 데이터 제작 공수가 개발 공수를 넘어설 위험이 크다.

## 3. 두 분석이 갈린 지점 (판정)

### 3.1 L1 테넌트 봇 — Codex의 축소안은 시그니처를 죽인다
Codex는 스토어 2~3개로 줄이고 단일 응대 모듈로 강등하라고 한다. 진단은 맞다(현재 config가 바꾸는 건
한도·SLA·문체 = 전부 파라미터이고 그래프 구조는 동일하다). 그러나 처방이 과하다. 이 컨셉에서
멀티테넌트는 차별화의 절반이다.

**채택안**: 스토어 수는 3개로 줄이되, config가 그래프 **구조**를 바꾸는 사례를 최소 하나 확보한다.
예 — `sale_type: 직매입`이면 판매자 소명 단계 자체가 존재하지 않고 플랫폼이 즉시 책임 주체가 되어
L1 노드가 통째로 스킵된다. 구현 비용은 조건부 엣지 하나이고, "테넌트 추가 = 다른 그래프"를
라이브로 증명한다. 이게 없으면 프롬프트에 정책 텍스트 끼워넣기로 보인다.

### 3.2 피드백 분석 — Codex는 DEFER했으나 자기 논리와 충돌한다
Codex는 7번을 빼도 핵심이 작동한다고 했지만, 같은 문서에서 KEEP한 UP-0의 입력에
"판매자 분쟁률"이 들어간다. 그 값을 만드는 게 정확히 7번이다.
더해서 부트캠프 주제가 "고객 피드백 분석 및 맞춤형 응대 자동화"이므로 분석 층을 빼면 주제 이탈이다.

**채택안**: KEEP하되 "인사이트 에이전트"가 아니라 배치 집계 모듈로 축소한다.
LLM으로 "위생 이슈 급증" 같은 서술형 인사이트를 만드는 부분은 Codex 말대로 채점 불가이므로 뺀다.
대신 출력(스토어별 분쟁률·이슈 분포)을 리스크 스코어의 입력으로 **명시적으로 배선**한다.
이 배선이 닫히면 "분석 결과가 시스템 동작을 바꾼다"가 슬로건이 아니라 코드 경로가 된다:
스토어 분쟁률 상승 → 리스크 점수 상승 → 같은 케이스가 즉시환불에서 소명절차로 경로 변경.
현재 컨셉 문서에서 가장 큰 업그레이드 여지가 여기다.

### 3.3 유사 결정례 데이터 — 기능과 평가 용도를 분리해야 한다
Codex는 UP-1을 통째로 DEFER했다. 기능(양측에 유사 사례 제시)은 동의한다.
그러나 소비자원 품목별 피해구제 사례(공공데이터포털 15090382, 질문·답변 포함)를 함께 버리면
2.3의 순환 비판에 대한 유일한 방어책이 사라진다.

**채택안**: RAG 제시 기능은 Phase 2. 해당 데이터셋은 **holdout 평가셋 출처로 MVP에 유지**한다.
팀이 만들지 않은 케이스와 결론으로 채점하면 "정답을 정해놓고 맞췄다"는 반론을 막을 수 있다.
단 kca.go.kr 분쟁조정 결정례는 웹 열람만 확인됐고 대량 기계수집 가능성은 미검증이므로,
공공데이터포털 파일 데이터 쪽으로만 의존한다.

### 3.4 증거 수집 — Claude 판정을 철회한다
가장 에이전트다운 팀으로 봤으나, 이슈 유형별 필수 증빙이 사실상 고정 테이블이라는
Codex 지적이 맞다. 독립 팀 대신 L2가 `missing_evidence`를 반환하고 재질의하는 상태로 구현한다.
에이전트다움은 팀 개수가 아니라 이 재질의 루프에서 나온다.

## 4. Codex가 놓친 것 — 차별화 주장이 부분적으로 반증된다

컨셉 문서 01섹션: "141개 기존 프로젝트에 이 형태는 없음".

`research/skn_final_top_projects.html:546` 에 SKN19-FINAL-5Team "똑소리"가 있다 —
법령·분쟁조정사례·상담사례 기반 소비자 분쟁 RAG + Multi-Agent 챗봇이며, 상위 10위로 평가된
프로젝트다. 즉 L2 판정 레이어만 놓고 보면 이미 선례가 있고 완성도도 인정받았다.

차별화가 실제로 성립하는 지점은 세 개뿐이다:
1. 3층 에스컬레이션 상태기계(SLA·불복 기반 자동 전이)
2. 판매자 = 테넌트 config (구조 분기가 있을 때만)
3. 리스크 기반 환불 경로 동적 선택 (UP-0)

발표에서도 정확히 이 세 개로만 방어해야 안전하다. "법령 RAG 판정"을 차별화로 내세우면
심사에서 선례와 비교당한다.

## 5. 최소 생존 구성

```
접수
  → 이슈·감성 분류(소형) + sale_type 조회
  → L1 응대 에이전트 (tenant config 주입, SLA 타이머 시작)
       └ sale_type=직매입이면 L1 스킵 ← 구조 분기 데모
  → 증거 체크리스트 / mock 조회
  → 리스크 룰 (금액·증빙·환불이력·스토어분쟁률[배치 집계 입력])
       ├ 저위험: 선환불 ActionProposal
       └ 고위험·증거부족: L2 판정 에이전트 (법정 기준 인용)
  → HITL 승인 → 환불/페널티 모의 트랜잭션
  → 판매자 이의제기 시 L2 재진입 (같은 판정기 재사용)
  → 중재 실패 시 L3 상태 + 서식 패키저
```

데이터 상한: 스토어 3개(sale_type 최소 2종), 이슈 3종(미배송·파손·단순변심),
시나리오 12~20개, 각 시나리오에 기대 상태·점수·경로·판정·인용근거를 붙인다.
반품 검수 데이터는 만들지 않는다(이의제기는 기존 증거 대조로만 처리).

## 6. 평가 설계 — Codex안 채택 + 보강

핵심은 기준선 비교다. 동일 케이스 집합을 `항상 소명 우선` / `항상 선환불` / `하이브리드` 세 정책으로
실행해 즉시해결률·오환불률·에스컬레이션률·평균 처리단계를 비교한다.
이게 UP-0을 주장이 아니라 측정으로 바꾸는 유일한 방법이다.

| 영역 | 지표 |
|---|---|
| 분류 | issue/intent macro F1 |
| 상태 전이 | SLA·무응답·불복 조건별 전이 정확도, 오전이율 |
| 리스크 경로 | route accuracy, 경계값 테스트 통과율 |
| 판정 | 환불가부·귀책·사유코드 필드별 정확도 |
| 근거 | citation precision, 환각 인용률 |
| 증거 | 누락 탐지율, 불필요 요구율 |
| 안전성 | HITL 이전 side effect 0건, 감사로그 완전성 |

holdout은 팀 합성 규칙과 분리한다(3.3 참조). 자유 텍스트는 LLM-as-judge 단독으로 평가하지 않는다.

## 7. 데모에서 실제로 보여줄 수 있는 것 / 슬라이드로만 남길 것

보여줄 수 있는 것
- 금액·증빙·이력만 바꾸면 같은 문의가 선환불과 소명 우선으로 갈리는 화면
- SLA 만료 → L2 자동 전이
- L2의 증거 목록·조항 인용·판정 필드·ActionProposal
- 운영자 승인 전에는 환불이 실행되지 않는 것
- config 교체로 스토어 정책과 **그래프 경로**가 바뀌는 것

슬라이드로만 주장할 것
- 소비자원 실제 접수·연계
- 실제 블랙컨슈머 탐지 성능
- 5~10개 스토어 운영 수준 확장성
- 페르소나가 현실 분쟁 행동을 대표한다는 주장
- 유사 결정례가 법적 정답을 제공한다는 주장

## 8. 팀원에게 전달할 요약

컨셉 자체는 살릴 가치가 있다. 다만 방어선을 "전문 에이전트 8개"에서
"상태와 리스크 분석이 다음 행동과 승인 경로를 바꾼다"로 옮겨야 한다.
지금 형태로 8팀을 다 만들면 각 팀이 얕아져 전부 프롬프트 래퍼가 되고,
심사에서 "이게 왜 에이전트인가"에 답할 수 있는 팀이 하나도 남지 않는다.

컨셉 문서에서 고칠 곳 3군데:
- 01섹션 "141개에 이 형태 없음" → 선례 존재. 차별화를 3개로 좁혀 서술
- 03섹션 Supervisor "판매유형 판별" → 조회임을 명시
- 03섹션 리스크 스코어링 팀 → 결정론 정책 엔진으로 표기 변경

추가할 곳 1군데:
- 피드백 분석 출력 → 리스크 스코어 입력 배선을 다이어그램에 명시
